### The duration question, settled before building rather than after

A 10–20 s handler needed checking before it was worth writing, and Cloudflare's own limits documentation answers it:

| | Workers Free | Workers Paid |
| --- | --- | --- |
| **Duration (wall clock), HTTP request** | **No limit** | **No limit** |
| **CPU time per HTTP request** | 10 ms | **5 min (default 30 s)** |
| Subrequests per invocation | 50 | 10,000 |

The decisive sentence, verbatim: *"CPU time measures how long the CPU spends executing your Worker code. **Waiting on network requests (such as `fetch()` calls, KV reads, or database queries) does not count toward CPU time.**"* And: *"There is no hard limit on duration for HTTP-triggered Workers. As long as the client remains connected, the Worker can continue processing…"*

So a Workers AI call is almost entirely excluded from the only limit that exists. This endpoint's own CPU work — bucketing candles and building a ~16 KB string — is milliseconds against a 30 s budget, and it issues roughly 6–8 subrequests against a ceiling of 10,000.

**ONE REAL CAVEAT, quoted rather than paraphrased:** *"Cloudflare updates the Workers runtime a few times per week. The runtime gives in-flight requests a **30-second grace period** to finish. If a request does not finish within this time, the runtime terminates it. This scenario is very unlikely because it requires a long-running request to coincide with a runtime update."* A 20 s request can in principle collide with that. It is rare, non-deterministic, and would present as a dropped connection rather than an error body.

**ASSUMED, NOT VERIFIED: that this account is on Workers Paid.** The billing plan is not readable from here. The inference is that Durable Objects require a paid plan and this project runs three. **If it were Free, the 10 ms CPU limit would likely break the prompt builder outright** — so this is worth knowing rather than assuming forever.

### What fails the request, and what is merely reported

The rule: **the model is asked only when the question can be grounded, and every other gather failure is REPORTED rather than propagated.**

- **No candle window → the request fails.** `assessCandidate`'s `no_price_history` precondition (step 37) does the refusing, **unbypassed**, before any model call. A strategy pick with no prices could only come from the training knowledge 21.5 requirement 1 forbids. A mutant that bypassed the precondition is caught.
- **Concentration failed, or the paused news slot → the assessment RUNS.** The prompt already states missing inputs plainly, the model is instructed to treat them as unknown, and the failure comes back verbatim in `bundle.concentration` with the producing module's own code. Refusing here would be exactly the over-propagation `gather.ts` was built to avoid: **losing a usable, grounded assessment because an unrelated D1 read failed.** The human still sees the gap, prominently, in the same response. A mutant that blocked on a failed concentration read is caught.
- **A bad model answer is a failed request, not a degraded success.** `AssessParseError` becomes a **502** carrying the parser's own code — the model answered and its answer was unusable, which is exactly the distinction `candles_unavailable` draws one stage earlier. The twenty parse codes are mapped by class in one place rather than as twenty near-identical rows in `STATUS_BY_CODE`, so each real code still reaches the wire without a second vocabulary to keep in step.

### A correction to the attribution, made here rather than inherited

The operator's report credited the "no assessment was attempted" improvement to step 39. **It is this step's**, and the record should not carry the wrong provenance: `git` shows `handlers.ts` at +178/−0 and entirely uncommitted at the time of writing, with HEAD at step 39's `envAssessModel` commit, which touched no endpoint.

**What the change is, and why it was needed.** `assessCandidate` refuses a bundle with no usable candle window and its code says only *that* — `no_price_history` — because at that layer the reason genuinely is not known. At the endpoint it **is** known: the candle slot is right there carrying the producing module's own error. Reporting the proximate cause would send an operator to check the venue's prices when the real answer is *"you asked for an interval this system has never verified"*.

So the handler surfaces the underlying code and status (`interval_not_verified` → 400, `candles_unavailable` → 502) with the precondition itself **unchanged and still the thing that refused**. It was prompted by a unit test during this step's own development — a test written expecting 400 that got 503 — and it is now confirmed under a real end-to-end call rather than only against its own fixtures.

### ⚠ THE DATA THIS RAN ON IS NOT A REAL MARKET

**This is the most important thing in this entry, and it must not be lost in a successful result.**

The real candle data behind the assessment shows **long flat stretches — 83 minutes at a single price, and roughly five hours at another.** That is consistent with the Gemini sandbox's known behaviour, which step 29 already recorded from the other direction when a targeted live run found that *"the sandbox's candle window does not slide"*. The sandbox is thin to the point of being frozen for long periods.

**Two statements, and both are true at once:**

1. **The model's grid recommendation is CORRECTLY GROUNDED in the data it received.** Given a series that barely moves, "range-bound, not trending" is the right reading, and grid is the strategy this system has for that. The pipeline did its job. Nothing about the reasoning is wrong.
2. **That data's low liquidity is a TESTNET ARTIFACT, not BTC's market character.** A flat sandbox series is an artifact of nobody trading in it. Real BTC over the same window did not sit at one price for five hours.

**So this run verifies the PIPELINE and says nothing about the QUALITY OF THE JUDGEMENT.** "The model recommended grid for BTC" is a sentence this entry deliberately does not endorse, and anyone reading it later should treat every strategy conclusion drawn from sandbox data as **mechanically correct and financially meaningless**.

There is a sharper edge to this worth naming: **frozen data is exactly the input most likely to produce a confident-looking grid recommendation**, because flatness reads as a tight, stable range. That is the shape of a proposal that would look good and be built on nothing — which is the characteristic failure 21.3 names about hype-driven candidates, arriving here by a completely different route. **Answer quality cannot be assessed until this pipeline is pointed at a market with real price movement**, and that is now the open question that matters most.

**S1 and S2 are the entry's least flattering finding, and the most useful.** The tests asserted `expect(cited.value).not.toBe("")` and `expect(cited.source).not.toBe("")`. **A dropped field is `undefined`, and `expect(undefined).not.toBe("")` PASSES.** That is precisely the weak-assertion bug decision log 36 recorded and named — reintroduced verbatim by the session that had written that entry.

It is the **sixth** instance in this project of a test passing for the wrong reason (steps 26, 28, 29, 30, 36/39 hold the others), and it is the **first that repeats a previously-documented mechanism rather than finding a new one**. The earlier five each taught something; this one only demonstrates that documenting a failure mode does not prevent it. Closed by asserting type **and** content, plus cross-checking each resolved citation against the same id in the evidence table so the two cannot drift into disagreeing about one datum.

**S7 is an equivalent mutant and is recorded as worthless rather than papered over.** `jsonSafe(result.settings)` is a no-op because `ASSESS_MODEL_SETTINGS` contains no bigint — numbers and a JSON schema. The call is kept as defensive insurance for a settings object that might later gain a `Money` field, and **no test was manufactured to make a no-op look guarded**. Same category as the worthless mutants in logs 30 and 39.

### Assumptions, flagged so they can be checked rather than discovered

1. **Workers Paid is INFERRED** from Durable Object usage, not read from the billing plan.
2. **The 30-second runtime-update grace period is a real if unlikely failure mode** for a 20 s request, and would present as a dropped connection.
3. **`latencyMs` measures the ASSESS CALL ONLY.** It is taken with `ctx.now()` around `assessCandidate` and excludes gather, so it is not end-to-end request time — the operator's 11,470 ms is the model call, not the whole request.
4. **Failure responses carry NO bundle.** `fail()` sets `data: null`, so a 502 or 503 loses the gather detail and `/gather` must be called separately to see it. Accepted, and worth revisiting if it proves annoying in practice.
5. **Five live samples is five.** The latency band and the envelope shape are consistent across all of them, and that is still not a distribution or a compliance rate.
6. **The sandbox data caveat above is the largest assumption-shaped thing in this entry**, and it is stated as a finding rather than an assumption because the flat stretches were observed directly.
