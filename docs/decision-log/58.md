## PART 1 — THE BUG THIS CLOSES

`#resumePass` did, in order: status check → global kill-switch latch → account
breaker latch → re-subscribe to the feed → write `running` and clear
`haltReason`/`haltedAt` → `#mirrorStatus` → `resolveHaltAlerts` → audit.

**It never read an order, never called `checkOpenOrders`, and never inspected WHY
the bot halted.** `haltReason` is opaque prose and nothing branched on it.

Confirmed live: reconciliation halted two real testnet bots for a **meaningful
`order_state_drift` finding** — their own fill counts disagreeing with the
exchange's real counts — and an operator resumed both. Resuming cleared the halt,
cleared `haltReason`, and closed the halt alert. **It corrected nothing.** The
wrong number was still the wrong number, and the bot went back to sizing orders
and evaluating its stop-loss and take-profit against it.

Section 9 halts and alerts and **deliberately never auto-corrects**, so
"reconciliation owns it" was never going to put the number back on its own. The
halt *was* the entire mechanism, and resume dismantled it in one click while
looking like an ordinary review — silently converting **known-wrong, halted,
alerted** into **known-wrong, running, unalerted**.

## PART 2 — THE INVESTIGATION, INCLUDING WHERE THE PLAN WAS WRONG

### The brief's premise was structurally false, and this is recorded rather than worked around

The build brief assumed `resume()` could branch on the halt reason to tell a
drift-caused halt from an ordinary one. **It cannot.** `HaltReason` is
`DcaHaltReason | GridHaltReason` and resolves to exactly **seven** values:

`stop_loss` · `take_profit` · `breakout_take_profit` · `take_profit_reached` ·
`order_rejected` · `unhandled_error` · `manual`

**There is no drift reason, because reconciliation does not have one.**
`workers/reconciliation.ts` halts through its `haltBot` port, which is
`halt("manual", detail, "reconciliation")`. The **global kill switch** does the
identical thing with a different actor, and **a human clicking halt** is `manual`
too. All three land as the same value. `order_state_drift` and
`cancel_fill_discrepancy` — which the brief named as halt reasons — are
`alert_type` and `FindingKind` values that never reach `halt()` at all.

The only thing separating the three is the **detail prose**: `haltReason` holds
the string `"manual: reconciliation run {id} found meaningful drift: ..."`.

### String-matching that prose was considered and REJECTED

Matching something like `/reconciliation run .* found meaningful drift/` would
have satisfied the brief. It was rejected because it puts the safety of a bot's
books on **a sentence nothing tests, which any reword silently defeats**, on the
one path where failing open means resuming trade on known-wrong numbers. A gate
that fails open under a copy-edit is not a gate.

### The reframing that actually works

Stop asking *"why did it halt"* and ask *"are this bot's books currently
trustworthy"* — a question the codebase **already answers structurally**.

`ORDER_STATE_DRIFT_ALERT_TYPES` (`src/shared/alert-types.ts`) is a curated set of
alert types meaning "repairable order-state drift on this bot", tied to the real
`FindingKind` union by a type assertion so **a rename fails the Worker typecheck**
rather than silently emptying the set. It is already imported by
`dashboard/src/driftAlerts.ts` to decide whether the **"Apply missed fills"**
control appears. An **unresolved** row of one of those types, for this bot, **is**
the untrustworthy-books signal — durable, queryable, and owned by writers other
than `resume()`.

Decisively: `resolveHaltAlerts` owns only `halt_*` rows and has **always
explicitly excluded** these ("`order_state_drift` is reconciliation's,
ingested"). So this is a condition **resume cannot dismiss by running**, which is
exactly the property the fix needs and did not have to be built.

It also makes the gate and the repair control agree **by construction**: the
button is on screen exactly when resume is refused.

### The dependency check, done explicitly

**No new flag was invented, and that was a decision, not an omission.** The brief
allowed for adding a durable boolean that only fix 3's repair action could clear.
That was rejected: with fix 3 unbuilt, **nothing could clear it**, so every
drift-halted bot would become permanently unresumable — a worse trap than the bug
being fixed, and a partial fix 3 smuggled in through the back door. Reusing the
existing alert means **this fix has no dependency on fix 3**, and any future
repair action inherits the gate for free by resolving the row it already has to
resolve.

### The honest limit on that choice

The gate is **exactly as strong as the alert's lifecycle**, and that lifecycle
has holes found in the investigation and **not fixed here**:
`resolveClearedAlerts` closes the row when the finding stops recurring, and
`act` consumes it when a tier action "lands" even where that action was an
`already_halted` no-op. Entry 57's fix already narrowed the main one — a refused
cancellation now keeps the order in `openOrderIds`, so reconciliation keeps
re-finding the drift instead of losing sight of it — but the rest is fix 3/fix 4
territory and is stated rather than implied.

## PART 3 — WHAT WAS BUILT

### A distinct error code, mapped to 409

New `BotInstanceErrorCode` **`position_unverified`**, added to `STATUS_BY_CODE`
in `src/api/envelope.ts` as **409**, alongside that file's existing conflict
codes `invalid_status`, `account_tripped` and `globally_tripped`.

- **Why 409:** the request is well formed and conflicts with current state, and
  clearing that state makes the identical request work — the exact shape those
  three neighbours already carry. **Not 403:** this is not about who is asking,
  and no actor may resume a bot whose books are in question.
- **Why not `invalid_status`:** the status is **not** the problem. The bot *is*
  halted, and resuming a halted bot is precisely what this method is for. What is
  wrong is the state it would resume **onto**. An operator reading
  `invalid_status` on a correctly-halted bot would reasonably conclude the
  request was malformed and retry it.

### Where the gate sits

In `#resumePass`, **after** both existing risk latches and **before**
`#subscribeToFeed` — making it the third and narrowest latch: **global → account
→ this bot's own books**, matching the file's own stated ordering rule ("Global
first: it is the broader condition"). It refuses **before any side effect or
status write**, so a bot that fails the gate is still halted in its own state and
in D1, and its halt alert is still open.

### What it queries

Unresolved `alerts` rows for **this** `bot_instance_id` whose `alert_type` is in
the whole `ORDER_STATE_DRIFT_ALERT_TYPES` set — **deliberately not scoped by
`source`**. Both the bot's own detector (`#onOrderStateError`, when the order
state machine refuses a fill) and reconciliation write into that set, and **either
one standing means the same thing about the same books**. Scoping by writer would
mean one of the two detectors could not stop a resume.

Reading the condition rather than the reason is also **strictly wider, and
deliberately so**: a bot halted on `stop_loss` while a drift row stands is just as
unsafe to resume as one halted by reconciliation. Why it stopped does not change
whether its numbers are right.

### The operator-facing message, worded not to promise an unbuilt fix

It names the alert types and the count, states plainly that resuming would put
the bot back to sizing orders and evaluating its stop-loss and take-profit
against a quantity known to be wrong and that **resume neither checks nor
corrects that number**, and names what **can** close the row today:
reconciliation ceasing to re-find the disagreement, and `apply-missed-fills`
(which **is** built and wired at `POST /api/bots/:id/apply-missed-fills`).

Then it states the limit, in the message itself: **that repair reaches only
orders still in `openOrderIds` — if the order has already gone terminal locally,
there is no automated correction for it today and it needs a human decision about
the position.** That is a deliberate choice. It is also exactly the situation of
the bots that exposed this chain, and the message says so rather than implying a
button that does not exist.

## PART 4 — VERIFICATION, REAL NUMBERS

### Five tests added to `resume (section 7.2 step 5)`, plus one endpoint test

1. **`refuses to resume while an order-state-drift alert stands`** — the live
   scenario, set up the way reconciliation actually halts (`halt("manual",
   "reconciliation run r-1 found meaningful drift: ...", "reconciliation")`).
   Asserts the refusal, and that the bot is still `halted` in **both** the
   Durable Object and the `bot_instances` row, the **halt alert is still open**,
   and the drift row is still unresolved.
2. **`refuses on the bot's OWN drift alert too, not just reconciliation's`** —
   an untiered `order_state_drift` under `source: "bot-instance"`. Proves the
   gate is not source-scoped.
3. **`resumes once the drift alert is resolved by its owner`** — the gate is a
   latch on a **condition**, not a permanent brand. Refuses, the row is resolved
   by someone else, resume succeeds.
4. **`does not refuse on ANOTHER bot's drift alert`** — the row is scoped to its
   bot.
5. **`resumes normally for every ORDINARY halt reason`** — all **seven**
   `HaltReason` values in a loop with no drift row present. The majority path,
   unregressed. Driving grid-only reasons through a DCA bot is deliberate: it
   proves the gate does not consult the reason **at all**.
6. **API (`api.test.ts`):** the endpoint returns **409** with
   `error.code === "position_unverified"` and a message matching
   `/disagrees with the exchange/`, and the bot is still halted. This also proves
   the new code **survives the Durable Object RPC boundary**, which
   `snapshotIfCreated`'s docblock warns is not automatic.

## PART 5 — FOUND, NOT FIXED

### The disarmed poll alarm — confirmed real, untouched, and NOT caused by resume

A resumed bot whose `openOrderIds` is empty is **not polled**: `#pollArmed`
returns false on an empty list, so `#syncAlarm` has nothing to arm, and nothing
observes that bot until it places a new order.

**Stated precisely, because the brief's framing was slightly off:** this is
`#pollArmed`'s existing behaviour and is correct on its own terms — a timer
firing against an empty list is rate-limit cost with no possible finding. It is
**not something `resume()` causes**, and **this gate does not change it**. It
matters because it compounds: a bot resumed after a halt that cancelled
everything is both unobserved *and*, before this fix, possibly carrying wrong
numbers. Fix 2 removes the second half only. Untouched, still open.

### The stale `exitOrderId` — confirmed present, deliberately not touched

`#placeTakeProfitSell` returns `"exit order already live"` against an
`exitOrderId` that names a dead order, permanently, while `#placeBuy` has **no
equivalent guard** — so such a bot can keep buying while never being able to
place an exit. Confirmed present. **This is fix 5's territory** (the original
position-tracking bug: `applyEntry` has no inverse, `exitOrderId` is cleared only
by `#completeCycle` and `#completeLiquidation`), not fix 2's, and it was left
entirely alone.
