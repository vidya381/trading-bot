## Step 38: The `ai` binding and the test suite, resolved by one option — and entry 37's "structural" framing corrected

Date: 2026-08-11 · **no deploy was run this session.** Every figure below was
measured locally by running the suite, the typechecker, or
`wrangler deploy --dry-run`.

Step 37 closed with a named blocking open problem: declaring
`{"ai": {"binding": "AI"}}` in `wrangler.jsonc`'s testnet environment broke the
entire test suite, and the entry called this **"structural and unsolved"**,
recording it as "the single thing standing between this step's tested code and a
real implementation".

**That framing was wrong, and this entry supersedes it.** The decision log is
append-only, so entry 37 cannot be edited; this paragraph is the correction, and
`vitest.config.ts` now carries a comment pointing here so anyone reading the
config finds the resolution rather than the obsolete diagnosis.

The incompatibility is not structural. It is a **default**.

### The real root cause

In the **installed** `@cloudflare/vitest-pool-workers@0.18.6` — read from
`node_modules`, not from documentation — the remote handshake is gated on a
single pool option:

```js
// dist/pool/index.mjs:2514
remoteBindings: z.boolean().default(true),

// dist/pool/index.mjs:2603
const remoteProxySessionData = options.remoteBindings
  ? await wrangler.maybeStartOrUpdateRemoteProxySession({
      path: options.wrangler.configPath,
      environment: options.wrangler.environment,
    }, preExistingRemoteProxySessionData ?? null)
  : null;
```

**`remoteBindings` defaults to `true`.** So whenever the pool is pointed at a
wrangler config containing a binding with no local simulation, it opens a remote
proxy session to the real Cloudflare account **at config-parse time, before a
single test runs**. In this project that session is refused — the testnet Worker
sits behind Cloudflare Access and there is no service token in the test
environment — and the run reports **0 tests with one error per test file**.

Workers AI is such a binding, and miniflare's own source says why:
`AI_PLUGIN.getBindings` and `AI_PLUGIN.getServices` both unconditionally build a
`remoteProxyClientWorker`, with **no local branch anywhere in the plugin**. There
is nothing to simulate against.

The failure was therefore never "this project's config is incompatible with
Workers AI". It was "the pool's default is to reach Cloudflare, and this project
cannot reach Cloudflare from tests". **One line changes the default.**

### The fix

- **`wrangler.jsonc`** — the real binding is back in the **testnet** environment
  (+3 lines, nothing removed):

  ```jsonc
  "ai": {
      "binding": "AI"
  },
  ```

- **`vitest.config.ts`** — `remoteBindings: false` on the `cloudflareTest`
  options, with the reasoning attached as a comment citing this entry, the
  installed line numbers above, and what the choice costs.

`remoteBindings` is a typed, first-class pool option
(`WorkersPoolOptions.remoteBindings?: boolean` in `dist/pool/index.d.mts`), not
an undocumented escape hatch.

### The three options, each verified by a real run rather than by reading docs

The investigation was framed around three candidate approaches. All three were
checked against the installed packages and, where the question was empirical,
against an actual test run — the discipline this arc already learned the hard way
when Cloudflare's own generated type for the model output turned out to be wrong
(entry 37).

**Option 1 — declare `ai` ONLY in `vitest.config.ts`'s `miniflare` key, keeping
it out of `wrangler.jsonc`. Works technically, and solves nothing.**

Tested literally: `ai` removed from `wrangler.jsonc`, `ai: { binding: "AI" }`
added to the `miniflare` key, `remoteBindings` left at its default. Result: **no
crash, 2 tests passed.** So the pool does **not** special-case `ai` bindings into
a forced handshake regardless of where they are declared — the trigger is the
**wrangler config path plus `remoteBindings`**, not the presence of an `ai`
binding in the miniflare key.

But the problem was never "tests need an AI binding". It is "**deploys** need
one, without breaking tests", and a miniflare-only declaration gives a deploy
nothing at all. Correct mechanism, wrong target.

**Option 2 — a fake/mock `ai` binding for tests. Impossible, tested directly.**

Two independent reasons, one read and one measured:

1. **Miniflare has no hook for it.** `AI_PLUGIN` has no local branch: both
   `getBindings` and `getServices` unconditionally construct a
   `remoteProxyClientWorker`. There is no in-process implementation to point at
   a fake.
2. **A `serviceBindings` override does not shadow an `ai`-type binding.** The
   documented canned-response pattern —
   `serviceBindings: { AI(request) { return new Response(...) } }` — was added
   alongside the wrangler `ai` binding and the suite run: `env.AI` **still**
   threw `Binding AI needs to be run remotely`. The `ai` plugin binding won.
   This was **tested, not assumed**, and the experiment was reverted afterward.

Even standalone it would not help: a service binding exposes `.fetch()`, while
the application calls `.run()`.

**The consequence is a design confirmation rather than a gap.** A mock must live
at **this project's own port**, not at the platform layer — which is exactly what
`AssessModel` (`src/research/assess.ts`) already is, and why every Assess test
already drives an injected stub.

**Option 3 — declare it for deploys while excluding it from tests. Yes, and
without a second config file.** `remoteBindings: false` achieves the goal
directly. No separate wrangler config for vitest, no environment split, no
duplication of the testnet environment. `vitest.config.ts` keeps
`environment: "testnet"` unchanged, so step 4.1's rule — *"Tests must never load
production config or production bindings, even locally"* — is untouched.

### The pinning test, and the two facts it defends

**`src/workers/ai-binding.test.ts`** (new, 2 tests). The resolution is a
**configuration** fact, and a configuration fact with no test is one edit away
from silently reverting.

1. **The binding EXISTS in tests.** If `env.AI` were absent, the wrangler
   declaration would have been lost — and a deploy would then ship a Worker whose
   `env.AI` is undefined, which nothing else in the suite would notice. Measured:
   `env.AI` is defined.
2. **Calling it FAILS, locally and loudly.** With `remoteBindings: false` the
   binding is wired to a proxy client with no connection string, so any use
   throws `Binding AI needs to be run remotely`. Confirmed in two ways: by
   reading miniflare's `remote-proxy-client.worker.js`, where
   `makeFetch` calls `remoteProxyConnectionString || throwRemoteRequired(bindingName)`
   **before constructing any request**, so nothing is sent; and by running the
   test, which observes the throw.

**The second property is the load-bearing one.** It is not a limitation being
tolerated — it is the guarantee that **no test in this repository can reach a
real model or spend money**, stated as a test rather than as a comment. A test
that somehow did call `env.AI` should fail loudly rather than quietly contact a
paid API, and now it does.

If someone later flips `remoteBindings` back to true, that test is where the
reasoning lives, rather than in a stack trace from the pool.

### Assumptions, flagged so they can be checked rather than discovered

1. **`remoteBindings: false` is safe here ONLY because no other binding in this
   project is remote-only.** Verified by reading `wrangler.jsonc`: D1, KV, R2 and
   the Durable Objects are all locally simulated by miniflare, and **none is
   declared with `experimental_remote`**. **If a genuinely remote-only binding is
   added later, this flag will silently disable it in tests too** — silently,
   because the symptom would be a binding that exists and does not work, which is
   the same symptom `env.AI` now has by design. That is the real cost of this
   setting and it is stated here rather than discovered later.
2. **Only the TESTNET environment got the binding.** Production `wrangler.jsonc`
   is untouched — a deliberate, separate decision, not an oversight. Section 21
   is nowhere near production, and adding a binding to production config for code
   that does not exist would be the opposite of this project's habit.
3. **The dry run proves manifest inclusion, not a successful deploy.** `env.AI`
   is in the binding list `wrangler deploy --dry-run` prints; whether a real
   deploy of that manifest succeeds is unobserved. No deploy was run.
4. **The pool's behaviour was read from the installed 0.18.6 and confirmed by
   running it.** A different version may gate the handshake differently, and the
   `remoteBindings` default in particular is the kind of thing that changes
   between minor releases. The comment in `vitest.config.ts` names the version
   and the line numbers so a future upgrade can re-check rather than re-derive.

### What is still NOT done, explicitly

  **no `AI` field**, and **no application code can reference `env.AI` and
  typecheck**. The pinning test narrows the binding locally with a cast for
  exactly this reason. **`npm run cf-typegen` is a real prerequisite for
  `envAssessModel`**, it rewrites a 551KB tracked file, and it was deliberately
  left out of a step scoped to the binding/test conflict.
- **`envAssessModel` is still unbuilt.** `AssessModel` remains an abstract port
  with nothing behind it, exactly as it was after step 37. This step removes the
  blocker; it does not use it.
- **No deploy was run**, so the deployed testnet Worker still has **no** `ai`
  binding. The next deploy is what gives it one.
- **Nothing else was touched.** The diff is `wrangler.jsonc` (+3),
  `vitest.config.ts` (+36), and one new test file. **Zero deleted lines** in
  either tracked file.
- **Section 21's unbuilt pieces are unchanged**: Stage 3 (Derive), Stage 4
