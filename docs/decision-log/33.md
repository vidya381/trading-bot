### The finding that changed the design before any code was written

The step was scoped as "add a suffix check inside `checkTradable`". Reading the
call sites first turned up something the scope did not anticipate, and it is the
most important thing in this entry.

**`checkTradable` has FIVE callers, not four.** The fifth is
`assertBotPairIsSpotTradable` — step 32's gate — where it runs **first**, before
`checkSpotInstrument`. So a heuristic placed unconditionally inside
`checkTradable` would not have landed only on the research paths. It would have
landed on `POST /api/bots`, ahead of the structural check, with two
consequences:

1. **`HYPEUSDCPERP` — the exact string the operator live-verified in step 32 —
   would from then on have been refused by a naming inference**, never reaching
   `product_type`. The refusal a human reads on the endpoint that reserves
   capital would have been downgraded from a fact Gemini stated to a guess this
   repository made from a suffix Gemini has never documented.
2. **It would have MASKED the structural check.** Both signals reach the same
   conclusion about the same input, and the heuristic runs first, so
   `parseInstrumentKind`'s `swap` branch — or `checkSpotInstrument` entirely —
   could have been deleted outright with every test in the repository still
   green.

**That is step 32's own standing convention arriving one layer up.** Step 32
recorded it about two FIELDS inside one parser: *"when a check reads multiple
fields that can each independently signal the same conclusion, a fixture that
supplies all of them at once lets any one field silently backstop the others."*
Here it is two **functions** at one gate, composed in an order that makes the
weaker one authoritative. **The convention generalises further than the entry
that recorded it, and this is the evidence.**

The operator was asked before anything was built, and chose the resolution:

> `checkTradable` grows a **required argument** distinguishing call sites that
> want the naming heuristic from those that don't. The four research paths opt
> in. `POST /api/bots` opts **out**, with a comment stating why: it has a real
> structural check and must not have a weaker inference answer first, both to
> preserve the real evidence in its refusal message and so the structural check
> keeps being exercised by realistic input rather than getting masked. A future
> sixth call site must explicitly choose; there is no default.

The alternatives were named and rejected: running it unconditionally (simplest,
literal reading of the scope, and it accepts both consequences above), or running
it unconditionally while reusing `instrument_not_spot` as the code (which keeps
the masking **and** hides it behind an unchanged code, so the bot path looks
externally identical while the evidence behind it has silently weakened).

**Nothing is lost by opting out.** The gate's structural check is strictly
stronger than the heuristic: it catches perpetuals no naming rule would.

### The two checks, and why they are not equally strong

| where | what it reads | cost | strength |
| --- | --- | --- | --- |
| `POST /api/bots` — `checkSpotInstrument` (step 32) | Gemini's own `product_type` / `contract_type` | one uncached request **per symbol** | **structural.** The venue states it |
| watchlist, candles, both candidate entry points — `checkTradable`, opt-in | the symbol's last characters vs a per-venue table | **free** | **an inference.** Gemini publishes no such rule |

The cost column is the whole reason there are two. `checkTradable` runs on every
watchlist add, every candle fetch, and up to ~15 coins × each quote asset per
candidate-selection run; folding the structural check into it would turn one
KV-cached catalogue read into dozens of live per-symbol requests. Step 32 already
argued that and refused to fold them; this step is that argument's other half.

### The venue table, and why the empty array is an answer

```ts
const DERIVATIVE_NAME_SUFFIXES: Readonly<Record<ExchangeId, readonly string[]>> = {
  gemini: ["perp"],
  binance: [],
};
```

A `Record<ExchangeId, …>` rather than a lookup with a default, for the same
reason `VENUE_PUBLISHES_INSTRUMENT_TYPE` is one: **a third exchange fails to
compile here until someone answers the question for it.** Defaulting silently to
"no perps on this venue" is not a neutral default — it is a false accept applied
to an entire venue at once, and false accepts are the direction that is silent.

- **`gemini: ["perp"]`** — observed, not documented. `HYPEGUSDPERP` and
  `HYPEUSDCPERP` in the real catalogue (log 31), `HYPEUSDCPERP` confirmed live
  to report `product_type: "swap"` (log 32). Lower-case because the comparison
  folds the **pair**, never the table.
- **`binance: []`** — an answer, not a blank. This system reaches only Binance's
  spot host (`/api/v3/exchangeInfo`); its perpetuals live on `fapi.binance.com`,
  which this system has no client for and cannot reach, so there is no
  derivative catalogue to name-match against here. **It says "nothing to match",
  not "nothing exists"**, and it becomes wrong the day such a client is added.

The policy argument is a string-literal union rather than a boolean, so a call
site reads as its own documentation:

| call site | passes |
| --- | --- |
| `addToWatchlist` | `"reject-derivative-names"` |
| `fetchCandleWindow` | `"reject-derivative-names"` |
| `selectNamedCandidate` | `"reject-derivative-names"` |
| `selectGeneralCandidates` | `"reject-derivative-names"` — **inert**, and opted in anyway |
| `assertBotPairIsSpotTradable` | `"structural-check-elsewhere"` |

`selectGeneralCandidates` was already structurally safe and stays so:
`${BASE}${QUOTE}` cannot construct a `PERP` suffix, so the heuristic never has a
perp presented to it there. It is opted in regardless, because four research
paths differing on a risk check for a reason that is *true today and true by
accident* is exactly how the copy that drifts becomes the one nobody watches.

### `endsWith`, never `includes`, and the pair it protects

Step 31's research flagged this before any of this code existed, and step 32
repeated it as a reason not to use a naming rule at the order path at all:
**`PERP` is a real ticker.** Perpetual Protocol trades as `PERPUSD` elsewhere. A
substring match would refuse a genuine spot pair and tell an operator it was a
derivative.

So the match is a **suffix** match, and a test asserts `PERPUSD` specifically is
**not** rejected — at the heuristic directly, at the watchlist, at the candle
fetch and at the named entry point. Two mutants (`includes`, `startsWith`) prove
those assertions are load-bearing rather than decorative.

**The check runs AFTER the catalogue answers, never before.** That ordering is
step 32's honesty rule one file over: the strongest **true** fact should be the
one that surfaces. An unlisted `FOOPERP` is `pair_not_tradable` — which is what
is actually wrong with it — and only a pair the venue really does list can be
refused for looking like a derivative. A mutant that reaches the name check for
unlisted pairs is caught.

### What this protects, what it does not, and the residual risk in both directions

Stated here as plainly as it is stated in the code, because burying it is how an
inference gets read as a guarantee two steps later.

**PROTECTS.** A perpetual cannot be watchlisted, cannot have candles fetched for
it, and cannot be selected as a named or general research candidate.

**DOES NOT.**

- **It does not replace step 32's order-path check**, and the order path does
  not use it at all.
- **It is not a structural guarantee.** Gemini's derivatives reference states
  **no naming convention whatsoever**. This is an observation about their
  current data, and an observation can stop being true without anyone announcing
  it.
- **FALSE ACCEPT:** a real perpetual that does not end in `perp` sails through
  every research path. Nothing here would notice.
- **FALSE REJECT:** a real spot pair whose symbol ends in those letters is
  wrongly refused. `PERPUSD` is the known near-miss the suffix match handles; a
  future pair literally ending in `PERP` would not be.

### The failure direction was chosen, and it stays the safe one

**A false reject is preferred, and it is preferred because it is LOUD.** An
operator hits it immediately, and the refusal message names the heuristic, says
in as many words that it is an inference rather than the venue's statement, and
names `DERIVATIVE_NAME_SUFFIXES` in `src/research/tradability.ts` as the fix.
One table entry plus a test.

**Two things make that more than an assertion**, and both were checked rather
than assumed:

1. **A false reject cannot block a legitimate bot.** `POST /api/bots` never
   consults this heuristic. The blast radius of a wrong entry is three research
   conveniences, not the money path.
2. **The refusal really does say so on deployed infrastructure**, verbatim —
   confirmed live, below.

A false accept is silent by construction: a perpetual on the watchlist looks
exactly like a spot pair on the watchlist, and would be discovered by something
downstream mis-modelling margin, funding or liquidation. That is section 5.6's
asymmetry — a refusal is a fact, a wrong acceptance is a fact nobody has yet.
