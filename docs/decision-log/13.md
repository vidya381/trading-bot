## Step 13: Attaching a live exchange client to BotInstance (execution wiring, part 1 of 2)
Date: 2026-07-29

### Scope: the execution-wiring step, split in two

This is the step deferred since step 6 and named at every step since (11 open
Q1, 12's closing note): the one that puts a real exchange client and a real
price feed behind a `running` bot so it actually trades. It has two independent
halves, and they were assessed as too large and too different in risk to do in
one session:

1. **Attach a live exchange client** to `BotInstance` in every deployed
   environment (this entry).
2. **A real price feed that drives `onPriceUpdate`**, which needs the section 4.1
   `subscribeToPriceFeed` closure signature REDESIGNED for the WebSocket
   Hibernation API (a callback closure cannot survive object eviction; step 6
   question 3 diagnosed this), plus a topology decision (per-bot socket vs. a
   shared feed per account+pair) and real reconnect-with-backoff + REST gap
   backfill (section 4.6). This is a whole new component with a heavy,
   hard-to-reverse interface change.

Attachment was done FIRST, deliberately, and the operator agreed:

- It is the smaller, contained, low-risk half — one seam, no new component, no
  interface change.
- It is a PREREQUISITE for the feed being meaningful: feeding prices into a bot
  that still throws `not_attached` the instant it tries to place accomplishes
  nothing. With attachment in place, a `running` bot given a single price (from
  a test, or eventually the feed) actually places a real order — the natural
  verifiable milestone and the natural read-only-first → first-real-order
  checkpoint before an always-on socket is added.
- The hibernation redesign deserves its own session with a design discussion up
  front, not to be rushed alongside this.

So part 2 (the price feed) is its own next session, opening with that design
discussion. Nothing here builds or presumes it.

### What was built

One seam in `src/durable-objects/bot-instance.ts`, plus tests. No interface
change, no new file in `src/`, no migration, no schema change.

- **`#rawExchange(config, now)`** — the raw exchange client for this bot:
  - an **injected** client (a test's `attach({ exchange })`) always wins and
    short-circuits resolution, so every existing test is unaffected and the
    automated suite still makes no live call;
  - otherwise — the production path — it resolves the account's real client from
    the bot's OWN stored `config.exchange` and `config.accountLabel` through
    **`resolveExchangeForAccount(config.exchange, this.env, now)`**, "the single
    dispatch home the future execution path reuses" that step 11 decision 7 built
    for exactly this. `isExchangeId` guards the stored string first; every
    fail-closed reason (non-trading `ENVIRONMENT`, missing secret, unknown
    exchange, null factory) becomes a `not_attached` `BotInstanceError` carrying
    the resolver's OWN message.
- **`#exchange`** now takes its raw client from `#rawExchange` and wraps it in
  the account rate limiter (the gate) exactly as before. The dead **`#deps()`**
  (which existed only to throw the old "no default exchange" `not_attached`) was
  removed.
- Comments on `attach()` and `BotInstanceDependencies.exchange`, and the
  `src/durable-objects/README.md` "Attaching the exchange client" section,
  updated: the object no longer needs a test to attach an exchange, and step 6
  decision 13's "there is no default" is now false — there IS a production
  default (resolved on demand), and only the credentials-absent case fails
  closed.
- **`src/durable-objects/exchange-attachment.test.ts`** — 4 tests, real D1 + real
  Durable Object storage, no live call.

1247 tests pass (up from 1243), typecheck clean. The one miniflare
worker-teardown error on close is the same pre-existing artifact steps 11 and 12
recorded, unrelated to this change.

### Decisions made

**1. The seam is LAZY, inside `#exchange`, not an eager constructor.** *(the
operator chose this from two options)*

A Durable Object's constructor cannot read its config from storage synchronously,
so it cannot know the account/exchange to build a client for at wake time. The
config IS available at every point a trade is attempted, because `#exchange` is
only ever reached with a `config` in hand. Building on demand there is both
possible and correct: it costs nothing on an idle wake, the client's constructor
sends nothing (step 3.2), and `#gated` memoises the result so the resolution and
the clock-drift sync happen once per object life, not per call.

**2. An injected client wins; the resolver only runs when nothing was injected.**

This is the same shape step 3.2 chose for reconciliation's `exchangeFor`: tests
supply a `FakeExchange` and never reach the resolver, so the automated suite
never depends on a real secret and never makes a network call. Because the guard
is "injected wins," ~all existing DO tests — which attach a fake — are untouched,
and the resolution path is exercised only by the new tests that deliberately
attach no exchange.

**3. A client that cannot be built HALTS a running bot (section 7.5), not a soft
skip.** *(deliberate; not special-cased like `throttled`)*

When `#rawExchange` throws `not_attached` inside `onPriceUpdate`, it falls
through to `#haltOnUnexpected` like any other unexpected error, so the bot is
marked halted with the resolver's honest reason and a `system` alert. This was a
choice, not an accident: a missing credential or a mis-registered exchange is NOT
transient (unlike backpressure, which `onPriceUpdate` catches and retries), so
the safe, loud default is to stop and alert a human, not to silently no-op every
price forever. A halted bot needs a human `resume()` anyway once the secret is
set.

**4. The object resolves from `config.exchange`, not from a fresh `accounts`
lookup.** *(reuse, not re-derive)*

`config.exchange` and `config.accountLabel` are already on every stored config
(written at create, where step 11 made the account registry authoritative). The
DO does not re-read the `accounts` table at trade time — the exchange was already
decided and denormalised onto the bot when it was created. This keeps the trading
path free of a D1 read it does not need and keeps `resolveExchangeForAccount` the
one place that turns an `ExchangeId` into a client.

### A real consequence, stated plainly: human liquidation is now LIVE in production

`#halt` / `liquidate` reach `#exchange` to cancel open orders and place the
liquidation sell. Before this step, that threw `not_attached` in production (no
client). After it, a production liquidate on a real bot resolves a live client
and places a REAL cancel/sell on the account. That is on-path and desired — it is
part of what "real execution" means — but it is the first place this code path
touches real (sandbox) funds, so it is called out rather than left implicit. On
testnet/sandbox with secrets set, liquidating a bot that holds a position will
now actually sell it.

Note what is still NOT live: a bot does not trade on its OWN. Nothing calls
`onPriceUpdate` in production yet (that is part 2), so a `running` bot still sits
idle until either a human acts (liquidate — now live) or the price feed exists.
Attachment makes the client AVAILABLE; the feed is what will drive it.

### Test coverage — what it proves, and what it deliberately does not

Automated (real D1 + real DO storage, no live call):

- **injected wins** — with no Binance secret set (so resolution WOULD halt), an
  injected `FakeExchange` still places the base order and the bot stays running.
  Proves injection short-circuits resolution.
- **missing Binance secret** — nothing injected, testnet env, no secret: the
  first price update HALTS the bot, `halt_reason` carries the resolver's own
  message naming `BINANCE_API_KEY`, one `system` alert, and zero orders in the
  object's history. Proves the real resolver runs and fails closed.
- **dispatch threading** — the same path for a bot whose stored `exchange` is
  `"gemini"` halts naming `GEMINI_API_KEY` and NOT `BINANCE`. Proves
  `config.exchange` is dispatched to the RIGHT resolver, not always Binance.
- **unknown exchange** — a stored `"kraken"` (a legal D1 `TEXT` value; the column
  has no CHECK) is refused by `isExchangeId` before any resolver, halting with a
  reason naming `"kraken"` and placing nothing.

What is deliberately NOT automated: the SUCCESS branch — a resolved LIVE client
actually placing an order. The suite makes no live call (section 14), and the
task's own framing puts the exchange behind a mock in automation and the real
order behind the Gemini sandbox tier. So the automated suite owns "the object
reaches for the right client and fails closed when it cannot have one"; the real
placement is verified below.

### How this gets verified against Gemini's real sandbox (the tiered plan)

Same read-only-first approach as every prior real-exchange check (step 3.3's
`verify-exchange.ts`, step 3.4's `verify-gemini.ts`), and it does NOT need this
session's code deployed to begin:

- **Tier 0 (read-only, no funds moved):** with `GEMINI_API_KEY`/`_SECRET` set on
  testnet, confirm sandbox reachability from the Cloudflare edge and that
  `getSymbolFilters` / `getCurrentPrice` / `getAccountBalances` return sane values
  — the still-open step 11 Q4 "Gemini-from-edge reachability" probe. This is the
  gate; nothing below runs until it is green.
- **Tier 1 (one real order, cancellable):** create a `gemini-main` bot on the
  sandbox with a tiny allocation and a limit price far from the market so it rests
  unfilled, then drive ONE `onPriceUpdate` (manually, since the feed is part 2) and
  confirm a real resting order appears on the sandbox account, is mirrored to D1,
  and that `liquidate` cancels it. This exercises the exact production resolution
  path built here end to end.
- **Tier 2 (a real fill):** only once Tier 1 is clean, allow one small order to
  fill and confirm the fill/position/PnL mirror.

Gemini first, not Binance: Binance geo-blocks the Cloudflare edge (step 3.3, seen
live as HTTP 451), so the sandbox that is actually reachable is Gemini's. Note the
capital asset — Gemini pairs quote in USD while the create form defaults to USDT
(step 11.1 open Q1); the sandbox bot needs its capital asset set to match an
existing ledger row.

### Deviations from the spec / prior entries

- **Step 6 decision 13 ("there is no default exchange client, and the object
  refuses to trade without one") is now superseded for the credentials-present
  case.** There IS a default: the account's real client, resolved on demand. The
  refusal it described survives, narrowed to exactly the credentials-absent /
  misconfigured case, and is now a HALT on the running path rather than only a
  thrown error on an RPC.
- **Section 3.2 open question 2 and 3.4 open question 4 (execution wiring reuses
  the base-URL derivation / the dispatch is unbuilt for a live path) are half
  closed.** The bot's execution client now resolves through
  `resolveExchangeForAccount`, inheriting the "impossible to point testnet at
  production" derivation with no second home. Half, because only the client is
  wired; the price feed that drives it is part 2.

### Open questions carried forward

Still open and unchanged: everything the price feed will settle, plus the prior
list. Specifically relevant now:

1. **The price feed is still the missing half.** Nothing calls `onPriceUpdate` in
   production; a `running` bot trades only via a human liquidation (now live)
   until part 2 builds the hibernation feed. This is the deferred half of THIS
   step, not a new gap.
2. **The success branch — a resolved live client placing an order — is unverified
   in automation, by design.** Its verification is the Gemini sandbox tiers
   above, not the suite. Recorded so "1247 pass" is not misread as "a real order
   has been placed."
3. **Gemini-from-edge reachability (step 11 open Q4) is the gate for all of the
   above** and is still unconfirmed; Tier 0 is where it is first observed.
4. **`credential_ref` remains unbuilt (step 11 decision 2).** The resolvers read
   fixed secret names by convention, which is exactly what `#rawExchange` relies
   on. The moment two accounts share an exchange with different keys, the column
   and the resolver change land together — and `#rawExchange` needs no change,
   since it delegates the secret→client mapping entirely to the resolver.
