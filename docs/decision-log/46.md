## PART 1 — ⚠ THE ARCHITECTURAL FIRST: A REAL BROWSER ACCESS SESSION, NOT A MINTED TOKEN

**This is new ground for this project's verification history and it should be
recorded as such rather than absorbed into "the feature worked".**

Every authenticated call this project has ever verified — every `curl` in entries
10 through 45, every `/assess`, every `/derive`, every watchlist write, every
`POST /api/bots` — went through a **manually obtained Access token supplied to
`curl`**. That path exercises `src/api/access.ts`'s verification, and it proved
the verifier works. **It does not exercise the way a human actually reaches this
system**, and until this step nothing did:

1. A browser requests the deployed Worker's hostname.
2. **Cloudflare Access intercepts, runs the interactive login flow, and sets its
   own session cookie for that hostname.** No application code participates and
   none of it is visible to the page.
3. On every subsequent request the Access proxy validates that cookie and injects
   `Cf-Access-Jwt-Assertion` and `Cf-Access-Authenticated-User-Email`.
4. `src/api/access.ts` **independently verifies the RS256 assertion** against the
   JWKS at `https://vidya-991.cloudflareaccess.com/cdn-cgi/access/certs`, checks
   the `AUD` against the `ACCESS_AUD` secret, and **requires the email header to
   match the token's own `email` claim** so two Access-provided values cannot
   disagree.
5. That verified email becomes `ctx.actor` — the `requestedBy` on the candidate,
   the actor on the `audit_log` row, and the actor on the proposal record.

**Step 5 is why this matters beyond plumbing.** 21.5 requirement 2's standing
rule is that the actor is the email verified off the Access token and never a
caller-supplied string. Until this run, the identity in every proposal record
this system ever wrote came from a token a human minted at a terminal. **This run
is the first where a permanent, undeletable proposal record carries an identity
established by a real interactive login.**

### ⚠ ONE CORRECTION TO HOW THE MECHANISM WAS DESCRIBED, MADE BEFORE IT IS QUOTED FORWARD

The brief for this step described the browser mechanism as
`credentials: 'include'`. **The source says `credentials: "same-origin"**
(`dashboard/src/api/client.ts:71`), and that is not a detail — `include` would be
a real widening, and this is the kind of paraphrase entry 44 recorded getting
loose about the `news` prefix rule.

`same-origin` is correct **and sufficient**, because the dashboard and the API are
genuinely the same origin. `wrangler.jsonc` serves the built dashboard as static
assets **from this same Worker**, with:

```jsonc
"assets": {
  "directory": "./dashboard/dist",
  "not_found_handling": "single-page-application",
  "run_worker_first": ["/api/*", "/health"]
}
```

One deployment, one hostname: `/api/*` and `/health` reach the Worker's fetch
handler, everything else is served from `dist`. So the page and the endpoint it
calls share an origin, Access covers both with one session, and the cookie rides
along under the strictest credentials mode that works. **`include` would grant
cross-origin credential sending this design has no use for**, and the comment in
`client.ts` says the mode is spelled out explicitly *for clarity that we rely on
the cookie* rather than because anything needed loosening.

**There is no login UI in this dashboard and there is deliberately nothing to
build.** An expired session returns Access's HTML redirect rather than JSON, which
`requestJson` already guards for and reports as `unauthenticated` — a guard
written in step 10.4 and, until this step, never reachable from a browser doing
the thing it was written for.

## PART 2 — THE DESIGN DECISIONS, AGREED BEFORE THE BUILD

Each of these was settled with the operator in advance rather than discovered
while coding, and each is the reason some obvious alternative is absent.

### CLIENT-SIDE ONLY. No new endpoint, no new backend code, no new safety mechanism.

The dashboard makes the two calls a human has been making by hand since step 42,
performs the projection between them, and renders the result. **`src/` gained
nothing.**

The tempting alternative — one backend endpoint that does both — was refused on
the grounds the split was made for. Entry 42 measured a single combined chain at
**88,480 ms** of model time and split it precisely so that **no single HTTP
request carries more than one inference**. A "do both" endpoint rebuilds the long
request that split was made to avoid, and would then have to re-answer the
resubmission question the split already answers. It would also be strictly worse
on this run's evidence: the Derive call alone took **77,344 ms**, so a combined
request would have been over ninety seconds long.

**Nothing here checks anything.** Every guarantee stays where it was:
`parseResubmittedAssessment` re-resolves every citation against the evidence
`/derive` gathers for itself; the real create-bot decoders, the real strategy
validators, the mandatory stop-loss, the venue floor and the capital headroom all
run server-side unchanged; the proposal record is still written by the backend,
still automatically, still fail-closed. The client calls, projects, and reports.

### NAMED ENTRY POINT ONLY

`entryPoint=general` still 503s and the watchlist door still has no dashboard
control, because **no trending vendor has been chosen** (entries 30, 31, 45). That
is unchanged, independent work, and it is blocked on a decision — not on this
page. Entry 45 raised the bar on it further: `TrendingCoin.raw` would land in
`inputs_json` permanently and undeletably, which makes every surveyed vendor's
data-storage clause a **hard precondition** rather than a consideration.

The page has no control that could reach either door, so there is no affordance
that fails.

### THE PASTE PAGE IS KEPT, UNCHANGED, AND IT IS NOT A LEGACY PATH

`/proposal` (entry 44) still exists, still makes **no network request of any
kind**, and was not modified. It is the fallback and the debug tool, and both jobs
are real:

- It renders a response saved hours ago **with no backend, no Access session and
  no spend** — which is how a past proposal gets re-read, and how the renderer
  gets worked on at all.
- It is where **adversarial input** goes. Entry 45's blank-screen crash was found
  by pasting a hand-built file with a `dca` label over grid-shaped params. **A
  trigger cannot produce that input**, because the backend cannot emit it — so
  retiring the paste page would retire the only route to the class of bug that
  actually took the whole page black.

### REAL PROGRESS STATES, NOT A SPINNER — AND NOT A PROGRESS BAR EITHER

Two waiting states, because there are exactly two calls, each reported when that
call really starts: *"Asking which strategy fits…"* then *"Deciding grid
parameters…"* — where **`grid` is the strategy Assess actually answered**, read off
the completed Stage 2 response, not predicted.

**The projection between them gets no phase.** It is a synchronous object rebuild
that takes no measurable time, and a step that flashes for zero milliseconds is a
spinner wearing a label — it would report the client as working when the client
was not.

**There is no percentage and no countdown, deliberately.** `MEASURED_LATENCY`
carries real samples from entries 37–46 rather than an invented estimate, and its
docblock states the things that must not be lost when they are quoted: `latencyMs`
is **model time only** (the gathers, the tradability check and the record write sit
outside it), nine and four samples are **not a distribution**, and they are
**sandbox** measurements from the environment entry 40 found is not a real market.
A bar built from those numbers would fill to 100% and then sit there while the
request was still genuinely running.

⚠ **AS SHIPPED FOR THE LIVE RUN, THAT WAS NOT ENOUGH, AND PART 4 RECORDS WHY.**
The panel rendered a bare range — *"Derive has taken 27–47s"* — and a bare range
shown during a wait reads as a bound on that wait no matter how carefully it was
sourced. **PART 4a is the fix, made in this same commit**: sample counts published
with every range, `expected…` renamed to `observed…`, and the elapsed counter
promoted to the primary readout.

### REAL ERROR CODES, WITH THE STAGE AS THE HEADLINE

There is no "something went wrong" anywhere in `runErrors.ts`, and a test asserts
that literally, over every code these two endpoints can emit. Every branch —
including the default one — carries the backend's own `code`, `status` and
`message`, rendered verbatim in monospace.

Two properties are doing the real work:

**1. ⚠ THE SAME CODE MEANS TWO DIFFERENT THINGS AT TWO DIFFERENT STATUSES.** This
is the subtlety the whole module is shaped around. `missing_field`,
`unexpected_field`, `duplicate_key`, `strategy_not_recognised` and
`citation_unknown` all appear **both** in `envelope.ts`'s 4xx table as REQUEST
faults **and** in the parsers' vocabulary, which `getAccountAssess` and
`getAccountDerive` re-throw at **502** when a MODEL answered badly.
`missing_field` at 400 means this dashboard built a bad request; at 502 it means
the model's answer was missing a field. Reporting the second as the first sends an
operator to fix a form that is working correctly.

**2. A DERIVE REFUSAL IS NOT AN ASSESS REFUSAL.** An Assess refusal usually means
the run never started and nothing was spent. **A Derive refusal means an Assess
inference has already been paid for**, and the strategy judgement it produced is
still real and still readable. So the failed outcome **carries the successful
assessment through** rather than discarding it, `assessAlreadySpent` is an explicit
field rather than something to infer from the stage badge, and the panel names the
Assess proposal record's id so the operator can still act on it.

### THE CODING SESSION MAKES NO LIVE CALL

Unchanged from every backend step since 37. `runProposal` takes an injected
`ProposalClient`; **every test drives a fake**. A test suite that could
accidentally trigger a run would be a standing hazard, because each run is two
paid inferences and two permanent rows — and that is the strongest reason this
project has ever had for the rule it already had.

## PART 3 — WHAT THE CLIENT ACTUALLY CONTRIBUTES, AND HOW IT IS PINNED

The client's entire contribution to the pipeline is entry 42's one line:

```
citations: [.citations[].id]
```

`/assess` publishes each citation as a whole `EvidenceItem` (`{id,label,value,source}`);
`/derive` requires **bare id strings** inside exactly four fields. That asymmetry
is not a size optimisation — `parseResubmittedAssessment` refuses an object
citation with `citation_not_a_string` and says why: a resubmitted item's `label`,
`value` and `source` are a rendering of data **as it stood at the original call**,
`/derive` re-resolves every id against its own fresh gather, and **a field
accepted and ignored reads exactly like one that was used.**

### ⚠ THE FOUR-FIELD LIST IS A MIRROR, AND THE TEST IS WHAT STOPS IT DRIFTING

`RESUBMITTED_ASSESSMENT_FIELDS` is the backend's own constant and importing it
would be the honest thing. **It cannot be imported**: `assess-resubmit.ts` pulls in
`assess-prompt`, `assess-parse`, `../db/schema` and `gather`, which drags the
Worker's D1 and Workers types into the dashboard's `tsc -b` and breaks it — the
failure `dashboard/src/derive.ts` already records and the reason `staleness.ts`
had to be written with zero imports to cross that seam (entry 45).

So the four names are written twice. Entry 45's rule is that **not having a copy
beats testing one**, and where a copy is forced the test must compare the copies
directly rather than assert around them. So:

- the first test asserts `RESUBMITTED_FIELDS` **equals the real backend constant**,
  element for element and in order;
- and the decisive test **runs the real `parseResubmittedAssessment` over this
  module's real output**, against a real `CandidateGatherBundle` whose evidence ids
  come from the real `buildAssessPrompt`.

That is `citations.test.ts`'s pattern (entry 44) one layer up, for the same
reason: a test written against a hand-typed expected object would pin the
dashboard's **belief** about the contract rather than the contract, and would keep
passing on the day the contract gained a fifth field while every real run came
back 400.

**The drift refusals are provoked by ordinary events, not by fabricated ids** — a
40-candle window shrinking to 3 (so `candles.bucket.19` no longer exists), and a
candle fetch that now fails outright (collapsing nineteen ids to one). Both are
things entry 45 watched happen live.

## PART 4a — THE HONESTY FIX, MADE IN THIS COMMIT

**This was not a performance problem.** Nothing in this system controls Workers AI
inference time, and a 77-second Derive is not a regression to fix. **It was an
honesty problem**: the page was quoting a specific range that one of this
project's own real runs had already disproven, during the wait it was describing.

### The full history, re-derived from the log rather than assumed

| | samples | entries | range |
| --- | --- | --- | --- |
| **Assess** | **9** | 37 (×3), 39, 40, 41 (×2), 42, **46** | **10,546–41,511 ms** |
| **Derive** | **4** | 41 (×2), 42, **46** | **27,473–77,344 ms** |
| **Whole chains** | **4** | 41 (×2), 42, **46** | **41,712–91,772 ms** |

Every sample was traced to the entry that recorded it rather than carried forward
from the previous constant. The 11,470 ms Assess sample is entry 40's; entry 42's
eight-sample tally is the authoritative aggregation of everything before it.
**Across both stages the full span is 10.5 s to 77.3 s**, which is the figure to
quote if a single one is ever needed.

**Only Derive's numbers moved.** Entry 46's 14,428 ms Assess sample sits
mid-band and widens nothing; the Assess range is **unchanged**.

### ⚠ THE NAMING WAS PART OF THE BUG, AND IT IS PART OF THE FIX

The accessors were called `expectedStageRangeSeconds` and
`expectedRunRangeSeconds`. **A function called `expected…` invites a caller to
render its output as an expectation**, which is what the page did. They are now
`observedStageRangeSeconds` and `observedRunRangeSeconds`, they return an
`ObservedRange` carrying **`runs`** — the sample count — as a required field, and
the constant's header opens with the rule rather than burying it:

> ⚠ THESE ARE A RECORD OF WHAT HAS HAPPENED. THEY ARE NOT A BOUND. Read this
> before rendering any of them, because this file has already been wrong about it
> once and in the direction that misleads.

**The sample count is the whole difference between a fact and a law.** *"Derive
takes 27–77s"* is a claim about the future; *"Derive has run 27–77s across 4
measured runs"* is not. Making `runs` a required field of the return type means a
caller cannot render the range without having the count in hand.

### The exact copy now on the page

**Cost banner, before the run:**

> One press makes **two paid model calls**. The 4 whole runs measured so far took
> **42–92 seconds** of model time — and longer in real terms, because the data
> fetches sit outside that. **That is a record of what has happened, not a limit**:
> this project does not control inference time and has never established a ceiling.
> Each successful call writes a proposal row that nothing in this system can delete.

**Waiting panel, per stage** (the elapsed figure is now the emphasised one):

> **14s elapsed** on this stage. For reference only: Derive has run 27–77s of model
> time across 4 measured runs — that is what has happened before, not a limit on
> this one.

**Waiting panel footnote:**

> Those figures are model time only — each call also fetches candles and reads the
> ledger before, and writes its proposal record after, so the real wait is longer.
> **Nothing caps how long a run can take: the longest Derive on record (77s)
> happened on a run this page was calling a 47-second job at the time.** Leaving
> this page abandons the run; the inferences already made are still paid for and
> still recorded.

⚠ **That last sentence puts this step's own mistake on the screen, deliberately.**
It is the most direct available answer to *"is this range a promise?"*, it is true,
and it costs one line. The same argument entry 44 made for stating the absent
liquidity test rather than inventing a threshold: **an unstated gap is the failure
mode; a stated one is a limitation.**

### What holds it in place

Three new tests, beyond updating the existing ones:

- **the entry-46 samples are named individually** (`toContain(14_428)`,
  `toContain(77_344)`, and `maxMs` asserted **greater than** the old 46,969
  ceiling) — so pruning the outlier to make the range look tidier fails loudly;
- **`runs` must equal the real sample-array length** on all three accessors, so a
  count can never drift from the data it describes;
- **every whole-chain total must be expressible as a real Assess sample plus a real
  Derive sample.** Entry 42's table establishes that a chain's model time IS the
  two stages summed (13,080+28,632=41,712; 41,511+46,969=88,480;
  17,622+27,473=45,095), and entry 46 continues it (14,428+77,344=91,772). Pinning
  it means a total can never become a figure no pair of real measured stages
  produced.

**Suite 2,629 → 2,632** (and 2,551 → 2,632 across the whole step). The page copy itself remains, as ever, untestable here
and verified by the operator's eyes.

### The two survivors are the value of the exercise, and both exposed a missing TEST rather than a missing check

**E1 — the `status === 409` guard on `citation_unknown` was unreachable, and
removing it broke nothing.** That was true and it was still the wrong conclusion.
The 502 block above already handles the model-invented-an-id meaning, so the guard
never fired in any tested path. **What it protects is the ADVICE**: that branch is
the only one in the file whose copy says *this is expected drift, run it again*,
and `citation_unknown` is the one code **deliberately left out of `envelope.ts`'s
status table** precisely because it means three different things at three
statuses. A fourth meaning arriving at a fourth status must not inherit "this is
normal". Closed with a test that hands it a third status and asserts it does
**not** get the drift copy.

**E1b — found while closing E1, and not from a mutant at all.** The
`strategy_not_recognised` branch hardcoded *"Derive: the resubmitted assessment…"*
regardless of stage. `/assess` has no resubmission in it — the only way it can
produce that code is `AssessParseError` at 502, already handled above — so an
assess-stage one would have named **a thing that does not exist on that call**. Now
guarded on the stage, falling through to the default arm, which prints the truth.

**E7 is an EQUIVALENT MUTANT and is recorded as one rather than as a survivor.**
`slash <= 0` → `slash < 0` changes nothing reachable: at `slash === 0` the layer
is the empty string, which is never a key in `VALIDATION_LAYERS`, so the existing
`undefined` check already returns `null`. Exhaustive over the sign of `slash`.
Stated so **22/23 is not read as 22 catches out of 23 meaningful mutants**.

### ⚠ TWO REAL BUGS WERE FOUND BY READING THE PAGE, NOT BY ANY TEST

Both are in `ProposalRun.tsx`, and **no test in this repository could have caught
either**, which is the honest frame for them:

1. **A failed `/symbols` load locked the run button permanently**, while the copy
   beside the field said *"you can still type a symbol — the endpoint checks it for
   real"*. That endpoint is a real exchange call behind a KV cache and it genuinely
   fails (the Binance geo-block is a confirmed live example), and holding no list
   **is not the same as knowing the pair is wrong**. A control that contradicts its
   own instructions is worse than one that is plainly disabled. Now the typed value
   is sent and `selectNamedCandidate` answers with `pair_not_tradable` if it is
   wrong — which is where that judgement belonged anyway.
2. **An unexpected throw would have left the spinner running forever.**
   `runProposal` refuses by *returning*, so only a genuine bug throws — and
   rethrowing rejected a promise nobody awaits: React does not catch it, and **an
   error boundary does not catch an async throw**. The page would have sat on
   "Running…" indefinitely, **indistinguishable from a call still in flight** — the
   same unreadable-failure class as entry 45's blank screen, arrived at from the
   opposite direction. Now it is shown through the same failure panel, with
   `readFailure` reporting it as what it literally is at status 0 rather than
   dressing it as a backend refusal.

## PART 6 — ⚠ WHAT IS STILL NOT DONE

### No "create a bot from this proposal" flow — and the safety constraints are already agreed

**Explicitly scoped as the next step**, and the constraints were settled with the
operator before any of it is built, so they are recorded here rather than
re-derived later:

- **It must route through the exact same real create-bot form** and its full
  validation. Not a variant, not a fast path, not a second form that "does the same

- **It must not silently change a proposal's outcome on mere navigation.**

  prefilled, so nobody reviews model output believing they typed it.

⚠ **This is the affordance 21.1 is most suspicious of**, and entry 44 refused to
build even a link toward it: *"a one-click bridge from a proposal to a creation is
the affordance that turns 'the human approves' into a rubber stamp"*. The four
constraints above are what would make a prefill something other than that bridge,
and **none of them is implemented yet.** Today there is no approve button, no
prefilled link, and no path from this page to a bot.

### ⚠ AN OPEN, UNRESOLVED INVESTIGATION INTO DASHBOARD POLLING LATENCY AND FREQUENCY

**Raised by the operator, genuinely open, and deliberately NOT attributed to this
feature — nor ruled unrelated to it.** Both would be conclusions and neither is
supported yet.

What is established, from the operator's real HAR-file evidence:

- Observed request spacing: **kill-switch ~2.6 s**, **bots/alerts ~5.25 s**.
- **A progressive server-side slowdown is RULED OUT** by that evidence.
- **An accumulating client-side leak is RULED OUT** by that evidence.

What is **not** established, and should not be written up as though it were:
**baseline latency** and **whether the polling frequency is appropriate at all**
are both genuinely unresolved.

⚠ **One source-grounded observation, offered as a HYPOTHESIS FOR THAT
INVESTIGATION TO TEST AND EXPLICITLY NOT AS A FINDING** — nothing here was
measured by this session:

`POLL_INTERVAL_MS` is **5000**, and **every** `usePolling` call site takes that
default; not one passes a custom interval. So a configured ~5 s matches the
observed bots/alerts figure, and **the ~2.6 s kill-switch figure is close to half
of it**. There are **two independent kill-switch pollers mounted at once on `/`**:
`KillSwitchBanner`, which `App.tsx` mounts **outside** the routed area so it never
unmounts, and `Dashboard.tsx`'s own `killSwitchPoll`. Two offset 5 s timers hitting
one endpoint would produce an average inter-request gap near 2.5 s. On
`/kill-switch` there is a **third** (`KillSwitchPage`).

If that is the cause it is a duplicate-poll question rather than a latency one,
and it long predates this step. **It is a reading of the source, not a
measurement, and the investigation stays open.**

check behind this run still answers *"is this internally consistent, currently

matter more.** Until today, obtaining a proposal cost a human two `curl` commands,

thirteenth bot on the same pair. The human in 21.1 is still the only part of this
loop that can tell a well-grounded proposal from a good one, and that human now
