## PART 1 — THE FEATURE

A **Clone** action on every bot's detail page opens the create-bot form
pre-filled from that bot's current configuration: pair, strategy, account label,
capital asset, every strategy-specific parameter for both DCA and grid, and the
allocated capital. Every field is **fully editable before submission**, and
**nothing is ever auto-submitted** — the operator lands on a form and presses
the same submit button a manual creation presses, running the same validation,
the same tradability gate, the same mandatory stop-loss check and the same
binding capital compare-and-swap.

**The source bot is a read source and nothing else.** Three facts, each
structural rather than a promise:

1. **Nothing is written to it.** The clone module makes no request of any kind,
   in either direction — no `api/client` import, no `fetch`. The existing
   source-level guard now enforces that over this path too (Part 4).
2. **The new bot's id is not carried.** `botInstanceId` is conspicuously absent
   from the prefill's type, its URL vocabulary and its decoder. The create-bot
   form mints a fresh random id at mount and this prefill has no way to override
   it, so a cloned bot cannot inherit or collide with the source's id. The
   absence is now asserted by a test rather than assumed, because adding the
   field later would typecheck and look helpful.
3. **The source id never leaves the browser.** `sourceBotId` exists so the
   provenance banner can name where the numbers came from. It is not read by
   `POST /api/bots`, `bot_instances` has no parent or source column, and a new
   guard assertion fails the build if the identifier appears in any file other
   than the clone module and its banner.

The new bot therefore gets a fresh id, an empty order/trade/alert history, its
own Durable Object, and its own capital reservation. Its only relationship to
the source is that a human started from the same numbers.

### The two decisions the operator made BEFORE the build, which shaped everything

Both were stated as settled and not to be re-opened, and both are recorded here
because the implementation answers to them throughout:

1. **The Clone action shows on EVERY bot, unconditionally, regardless of
   status.** No gating on `running`, `halted`, `stopped` or `archived`. This
   makes Clone the **only control on the bot detail page with no status
   condition**, and the asymmetry is the point: every neighbour there (start,
   halt, resume, liquidate, archive) is gated because it *changes* the bot and
   would only fail if offered at the wrong moment. Clone changes nothing about
   the bot at all. Gating it would remove the feature at the exact moment an
   operator most wants it — just after watching a bot finish.
2. **Every field pre-fills, including allocated capital.** It is editable like
   every other field, so there was no reason to leave it blank. This is what
   makes Part 3's first finding matter: once capital is carried, *which* capital
   figure is carried becomes a real question with a wrong answer available.

## PART 2 — THE CENTRAL DESIGN DECISION: A PARALLEL DECODER, NOT A RELAXED ONE

### The alternative that was considered and rejected

`readProposalPrefill` (`dashboard/src/research/proposalPrefill.ts`, entries
**44**–**46**) already decodes a complete strategy configuration out of
`/bots/new`'s query string, and already feeds every `useState` initialiser on
that form. It returns `null` unless **both** a `proposalId` and a recognised
`strategy` are present.

The cheap move was obvious: widen that identity check to *"a `proposalId` **or**
a `cloneFrom`"* and reuse the whole thing. **It was rejected.** What was built
instead is a second, separately-named module — `botClonePrefill.ts`, with
`readBotClonePrefill` / `cloneSearchParams` / `cloneBotHref` — that refuses
everything it does not recognise.

### Why, in order of weight

**1. The proposal decoder's other fields have no equivalent for a bot's config,
and supplying them empty would manufacture a false doubt.**

`ProposalPrefill` does not carry only form values. It requires `generatedAt`
(the derive call's `selectedAt`) and `stalenessInputs` (four per-source
`{key, at, thresholdMs}` fetch-time triples), and the banner over the form
computes a **live freshness verdict** from them against the current clock — the
mechanism entry **46** built so a stale proposal cannot arrive at the
capital-committing screen looking fresh.

A bot's configuration has none of that. It was not derived from dated fetches;
it is a configuration, not a derivation. A clone forced through that type would
have to supply both empty — which puts `generatedAt` and `freshness` into
`incomplete`, and makes `worstVerdict` resolve to **`unknown`**. The operator
would then be shown *"this prefill is incomplete"* and *"freshness unknown"*
about a configuration that is neither: it is exactly complete, and freshness is
not a concept that applies to it.

**That is a degraded result presented as if it were a real one** — which is
precisely the failure `proposalPrefill.ts`'s own fail-closed design exists to
prevent. Reusing the type would have made that module violate its own stated
principle in order to accommodate a second caller.

**2. A single fail-closed rule would become a disjunction with a genuine
fall-through gap.**

Today the rule is one sentence with a test per clause: no id, no prefill.
Relaxed, it becomes *"one of these two ids, and then a second switch decides
which of two banners and which of two provenance stories applies."* The branch
that goes wrong in that shape is the one where **neither** id is present and
control falls through to the more permissive arm. Two decoders that each refuse
what they do not recognise have no such arm to fall through.

**3. The proposal decoder feeds the capital-committing proposal-to-bot path, and
that path now carries ZERO changed lines.**

`proposalPrefill.ts` was **not edited at all** — not one line. The path with the
most invariants pinned to it, the one that commits capital on model output, is
byte-identical to what it was before this feature existed. A parallel module
cannot regress it, because it does not touch it. That is a weaker-sounding
argument than the first two and it is deliberately placed last, but it is the
one that is checkable by `git diff`.

### The real cost of the chosen approach, stated rather than glossed

**A second decoder duplicates the field-mapping logic**, and that mapping is the
error-prone part rather than an incidental one. Grid and DCA **both** have a
parameter literally called `stopLossPct`, and they are two different inputs in
two different fieldsets of the create-bot form (`gridStopLossPct` /
`dcaStopLossPct`). DCA additionally maps `takeProfitPct` → `dcaTakeProfitPct`. A
mapping that is right for one strategy and wrong for the other **typechecks,
renders, and creates a bot with no stop-loss where a human saw one**. Duplicating
that translation is a real, named liability, not a theoretical one.

**Two safeguards hold it down:**

1. **The wire field lists are IMPORTED, not copied.** `WIRE_FIELDS` comes from
   `proposalPrefill.ts`, and an **existing** test there already pins it
   element-for-element against the backend's authoritative
   `GRID_PROPOSAL_FIELDS` / `DCA_PROPOSAL_FIELDS` in
   `src/research/proposal-shape.ts`. A parameter added to a strategy therefore
   reaches **both** encoders or **neither** — there is no version of this where
   the clone silently drops a field the proposal path gained.
2. **A test feeds one parameter set through BOTH decoders and asserts the
   resulting fields are identical.** The same query string, differing only in
   which identity key it carries, is decoded by `readProposalPrefill` and by
   `readBotClonePrefill`, and the two `fields` objects must be deep-equal — plus
   `accountLabel`, `pair`, `capitalAsset` and `allocatedCapital`. Either decoder
   drifting, in the mapping or in the boolean parsing or in what counts as
   "unset", fails that test. (`incomplete` is compared with `generatedAt` and
   `freshness` filtered out, since a clone legitimately has neither — which is
   reason 1 above, showing up as a two-line exclusion in a test.)

### One further property, put in the decoder rather than in the caller

`readBotClonePrefill` refuses **any** URL that also carries a `proposalId`,
unconditionally, before it reads anything else. A hand-built URL holding both
ids would otherwise be readable as either, and the two banners say materially
different things — one of them would be a lie.

`CreateBot.tsx` does ask the proposal decoder first, but **that ordering is an
optimisation, not the safety property**. The refusal lives inside the decoder so
that a future reordering of the two calls cannot silently become a regression. A
test pins that distinction explicitly.

## PART 3 — THREE FINDINGS FROM READING THE EXISTING API RESPONSE

`GET /api/bots/:id` was confirmed to carry everything the create-bot form needs:
strategy, pair, account label, capital asset, allocated capital, and every
strategy-specific parameter for both DCA and grid (money already rendered to
decimal strings by the backend's `jsonSafe`). Reading it closely produced three
findings worth recording.

### 1. Two allocated-capital figures that can technically diverge

The response carries the allocation **twice**:

- **`allocatedCapital` on the D1 row**, which `resizeBotCapital`
  (`src/capital/ledger.ts`) rewrites, and
- **`config.allocatedCapital` inside the Durable Object's stored config**, which
  is written once at creation and **never updated by a resize**.

They agree on every bot today, because **no API route currently reaches
`resizeBotCapital`** — the function exists and is exercised by its own tests,
but nothing routes to it. So this is a latent divergence, not an observed one,
and it is recorded as such.

**The deliberate choice: the clone uses the ROW's figure.** The row is what
`botSummary` publishes and what `BotSummary` renders, which means it is the
number the operator is **actually looking at on screen** when they press Clone.
A clone that quietly used the creation-time figure would put a different amount
in the box than the page above it shows — and given the operator's decision that
capital pre-fills, that discrepancy would be invisible and would be submitted.

**The test fixtures were deliberately constructed with the two values
DIFFERENT** — the row at `4000.00000000`, the config at `3500.00000000` — so the
assertion can only pass if the correct source was used. Both strategies assert
the value **is** the row's *and* **is not** the config's. Had the fixtures been
built the realistic way, with the two agreeing, the test would have passed
either way and proved nothing.

### 2. `exchange` is deliberately NOT carried through the clone URL

The exchange is **read-only on the create-bot form**: it is derived from the
account registry once the selected account resolves, it is never an input, and
`POST /api/bots` **rejects a body whose exchange disagrees with the registry**
(step 11's dispatch fix — the account registry is authoritative and a
disagreement is treated as a client bug rather than silently overridden).

Carrying it would therefore put a value in the URL that **no field consumes** and
that **could contradict the source of truth**. It is omitted, and the omission is
asserted by a test so a future edit adding it "for completeness" fails rather
than lands.

### 3. Orphaned bots have no configuration to copy — resolved WITHOUT status gating

`config` is `null` when a bot row exists but its Durable Object holds no state —
the `orphaned: true` case. There are no parameters to copy, so **no honest URL
can be built**. This is the one place the literal form of the operator's "no
gating" decision met a case where a working link genuinely **cannot exist**.

**It is not a status gate and must not be read as one.** Orphanhood is
orthogonal to `status`: a running, halted, stopped or archived bot can each be
an orphan or not, and the clone link is offered for all four statuses (a test
iterates every one of them, plus the archived case, and asserts a link **is**
offered).

**How the spirit of the decision was preserved:** the `CloneBotLink` control
**still renders unconditionally on every bot, orphans included**. What changes
for an orphan is only the contents — it states, in place, that there is no
configuration to copy and why, and notes that the create-bot form is still
reachable on its own. It does **not** silently hide itself.

This deliberately breaks `LiquidateAction`'s house rule (*"if it's not a valid
action, don't render it"*) the same way `ArchiveAction`'s held-position case
already does, and for the same reason: an operator who has been told Clone
appears on every bot, and finds nothing on one of them, reads a **missing
control as a broken page**. The sentence explaining why is worth more than the
consistency.

The same in-place refusal covers a second, related case: a config whose
parameters do not match their own strategy label, or whose strategy disagrees
with the bot row's. Both refuse the link rather than prefilling a form with
`undefined` — the fault that once took a page to a blank screen, refused one
layer earlier, on the screen that commits capital instead of the one that
renders a table.

## PART 4 — A SELF-CAUGHT SAFETY-TEST CONFLICT, AND HOW IT WAS RESOLVED

Partway through the build, the **existing** guard
`prefill-does-not-approve.test.ts` failed:

```
⚠ `proposalId` is attached to a request by exactly one function, in one file
/dashboard/src/research/botClonePrefill.ts:178: proposalId: "proposalId",
```

That guard scans all dashboard source and enforces that **only** `withProposalId`
may put a `proposalId` into an object — so that *"the outcome link is attached at
submit and nowhere else"* stays checkable by reading one call site.

The offending line was **harmless in substance**: an entry in the clone module's
URL key table, naming the proposal's parameter purely so the decoder could
**detect it and refuse** (Part 2's ambiguity clause). It never wrote it anywhere.

**The fix was to remove the conflicting shape from the NEW code, not to weaken
the existing guard.** The key was taken out of the table and replaced with a bare
`const COMPETING_PROPOSAL_KEY = "proposalId"`, which the guard's pattern does not
match because it is not an object member.

**This is recorded as the correct instinct, deliberately.** The tempting fix was
an exception in the guard — the occurrence really was benign, and one narrow
carve-out would have looked reasonable. But **a guard that has to distinguish
harmless occurrences from real ones is a guard with an exception list**, and the
next benign-looking case is judged against a precedent rather than a rule. An
established safety rule should not bend to accommodate new code; new code should
conform to it. The clone module now simply never writes that shape.

### The guard was also EXTENDED to cover the new path

Three files were added to its `NAVIGATION_PATH` set — `botClonePrefill.ts`,
`CloneBotLink.tsx`, `CloneSourceBanner.tsx` — so none of them may import
`api/client` or name any state-changing endpoint. The extra reason beyond the
proposal path's is worth stating: **the source of a clone is a live bot rather
than a stored document.** The proposal path's worst failure is recording an
outcome nobody chose; this path's would be **touching a running bot** — halting,
resizing, archiving it — as a side effect of copying its numbers.

`pages/BotDetail.tsx` is deliberately **not** in that set: it legitimately holds
the API client, because polling the bot is its whole job. The link it renders was
made a separate component precisely so the navigation path itself stays
checkable — the same reasoning the guard already records for
`ProposalSummaryCard.tsx`.

| Block | Tests | What it covers |

**The five interference assertions**, proving the two prefill flows cannot
interfere in **either** direction: a proposal URL still decodes into exactly the
prefill it always did; a **clone** URL yields **no** proposal prefill (for both
strategies); a **proposal** URL yields **no** clone prefill; **a URL carrying
BOTH ids is refused entirely** by the clone decoder itself rather than by call
order; and both decoders map one parameter set to byte-identical fields.

**The ten fail-closed cases:** a **sanity check that the unmodified URL does
decode** (without which every negative below could pass vacuously); no
`cloneFrom` → `null`; empty and whitespace-only ids → `null`; missing strategy →
`null`; five bogus strategy strings → `null`; an empty query string treated as an
ordinary manual visit; **missing fields correctly named in `incomplete` with the
form's own default kept, never guessed**; the **boolean-string parsing trap**
(`Boolean("false")` is `true`, so an unreadable boolean is unreadable rather than
false, and is named); an unreadable `spacing`; and a present-but-junk value
passed through **verbatim** for the form's own validator to reject rather than
silently dropped.
