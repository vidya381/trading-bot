## Step 42: The derive endpoint — a Stage 2 result resubmitted from an earlier, SEPARATE call, re-verified against evidence gathered now; the probe deleted; and the staleness case firing live, unprompted

`GET /api/accounts/:label/derive` is the first thing in this system that accepts
a model-stage result **which came back over the wire from a previous HTTP
request**. Everything else about Stage 3 — the two conditional prompts, the real
create-bot decoders and validators, the venue floor check, the citation
machinery, `envDeriveModel` — is step 41's and is reused unchanged.

**The entire new surface is one boundary:** an assessment that a client held
across real time is untrusted text, and the evidence it cites may no longer
exist. Step 41's probe could not test this and was never meant to: it called
Assess **fresh, inside the same request**, and passed the resulting object
straight down the call stack, so the assessment and the evidence were the same
objects and drift was impossible by construction.

That distinction is the whole of this step, and the live verification below
confirmed it in the one way that matters: **the same evidence id resolved to two
genuinely different real values ten minutes apart.**

### What was built

- **`src/research/assess-resubmit.ts`** — new, pure, no I/O.
  `parseResubmittedAssessment(text, bundle)` reads a client's resubmitted Stage 2
  result against a freshly-gathered bundle, or throws. `assessEvidenceOf(bundle)`
  exposes the citable set. `AssessResubmitError` carries eighteen codes.
  `RESUBMITTED_ASSESSMENT_FIELDS` pins the four-field contract.
- **`getAccountDerive`** in `handlers.ts`, plus `deriveContextPortsFor` —
  `gatherPorts` composed with `symbolDetailsFor`, the **real** adapters.
- **Serialization** in `serialize.ts`: `deriveResultView`, `validatedProposalView`,
  `resubmittedAssessmentView`, `deriveContextView`, `symbolFiltersInputView`.
- **Three status rows** in `envelope.ts`, and one code deliberately left out.
- **`src/api/debug-derive-probe.ts` DELETED**, with its route, its import, its
  twelve tests, and every ⚠ TEMPORARY marker on the `deriveModel` fields.

### Requirement 1, checked from source rather than assumed: `/assess` already supported resubmission

The brief asked not to take step 40's shape on trust. Traced:
`assessResultView` (`serialize.ts`) publishes `strategy` (the exact literal),
`claims[].statement`, `claims[].citations[]` as whole `EvidenceItem`s
(`{id,label,value,source}`), plus `envelope` and `duplicateKeyCheck`. That is
**all four fields of `ParsedAssessment`**.

**Nothing had to change in `/assess`.** The client performs one projection —
`citations: [.citations[].id]` — and that is its entire job. Confirmed live in
check 2 below and pinned by a test that asserts the projected object's key set is
exactly the four the contract names.

### THE CENTRAL QUESTION: was the fresh-evidence re-verification new code, or a consequence of existing logic?

**Both halves are true and only stating both is honest.**

**The checking LOGIC needed nothing new.** `resolveCitations` (`assess-parse.ts`)
was already written as a set-membership test over an **injected**
`ReadonlyMap<string, EvidenceItem>`, with no opinion whatever about where that map
came from or when it was built. Verifying against an evidence set the caller has
never seen before therefore needs **no new logic at all** — only a new call site
handing it a different map. The same reuse holds for `requireExactFields` and
`findDuplicateKey`. Step 37's decision to extract those into shared code with an
injected `ParseRefusal` vocabulary is what made this step small.

**But the CALL SITE is genuinely new, and its absence was a real gap.** Before
this step `resolveCitations` had exactly two kinds of caller: the Assess model's
response against the Assess prompt's evidence, and the Derive model's response
against the Derive prompt's evidence. **Nothing ever passed an INBOUND assessment
through it.** `collectAssessment` (`derive-prompt.ts`) merely *renders* the
claims' ids into prompt text —
`claim.citations.map((item) => item.id).join(", ")` — and its docblock states the
assumption out loud:

> The claims arrive as `CitedClaim`s that already passed `parseAssessResponse`'s
> grounding check … and, because both prompts build their bundle evidence with
> `collectBundleEvidence`, an id this prompt emits too.

**That is true for a same-request chain and false for a resubmission.** So the new
work is a decoder plus **one call** to the existing grounding check. Zero new
grounding logic; one genuinely missing verification.

Stating it as "resolveCitations already handles this" alone would have been
wrong — it handles it *when someone calls it*, and nobody did.

### Why the evidence set is the ASSESS set, and not Derive's

The map is built from `collectBundleEvidence` over the fresh bundle — precisely
and only what `buildAssessPrompt` emits — rather than from `buildDerivePrompt`'s
wider set. Two reasons, and the second is load-bearing:

1. An Assess claim could never legitimately have cited `capital.row.01.available`
   or `filters.min_quantity`: those ids do not exist in Stage 2's prompt.
2. **Derive's evidence set CONTAINS `assessment.claim.N`, built FROM the
   assessment being verified.** Checking the assessment against a set derived
   from itself is circular and would pass by construction — **the
   check-that-cannot-fail this project has already refused once**, in step 37's
   duplicate-key "theatre" finding. A test asserts that `assessment.strategy` and
   `assessment.claim.1` are both refused, and a mutant that widens the map to
   include them is caught.

### The drift is reachable through ORDINARY OPERATION, which is what makes the check real

The naive reading is that evidence ids are stable strings (`candles.last_close`,
`candles.range_pct`) so the check can never fire, making it decorative. **That
reading is wrong, and the ways it is wrong are ordinary rather than exotic.**
From `collectBundleEvidence`:

- **`candles.bucket.NN` exists for `min(CANDLE_BUCKET_COUNT, n)` buckets**, where
  `n` is how many candles the venue actually returned. A window 1,440 deep at
  `/assess` time and 12 deep now emits buckets 01–12 and **not** bucket 19 —
  which a claim about a price range is exactly the kind of thing to rest on.
- **A candle fetch that succeeded then and fails now collapses NINETEEN ids into
  ONE** (`candles.status`, carrying MISSING).
- **`concentration.flag.N` exists only while the account is FLAGGED.** Stopping
  one bot between the two calls removes it.
- **`candidate.source.N`** follows how many sources the candidate has, which a
  watchlist edit changes.

Each has its own test. **And check 7 of the live run then produced this for
real, unprompted** — see below.

### Citations are bare ids, and that omission IS the contract

`/assess` publishes whole `EvidenceItem`s; `/derive` takes **id strings**, and an
object is refused with `citation_not_a_string` rather than having its `id`
helpfully extracted.

Deliberate, and it is this module's own reasoning applied to its own input: the
`label`, `value` and `source` in a resubmitted item are a rendering of data as it
stood at the **original** call, and every one may now be stale —
`candles.last_close` is a different number, as the live run proved. This stage
resolves the id against **current** evidence and returns the **current**
rendering, so the submitted rendering is something it must ignore entirely.
**Accepting a field and ignoring it is how a caller concludes their data was
used** — the same objection `getAccountGather` raises against silently dropping a
`pair` on a watchlist run. Requiring ids puts "your values are not used" in the
contract instead of in a comment. A mutant that extracts `.id` from an object is
caught by two tests.

### The two audit fields that are carried and NOT verified, said out loud

`envelope` and `duplicateKeyCheck` describe the **original** model call, which
this system did not witness and stores nothing about. They are checked against
their literal unions and otherwise **taken on the client's word**.

They are **required rather than defaulted**, and that is the whole point:
`ParsedAssessment` has four fields, and defaulting two of them would mean this
module inventing an audit fact and publishing it under a field name that reads as
an observation. **A manufactured audit fact is worse than an unverified one.**
The response therefore nests them under `unverifiedOriginalCall`, beside
`source: "client_resubmitted"` and `citationsReverified: true`, so a reader can
see exactly which of the three claims this system actually stands behind. A
mutant that defaults them instead of checking is caught.

**Nor is the statement TEXT verified.** A claim's prose is whatever the client
sent; nothing here can know the original model wrote it. The guarantee is
narrower than it looks and is the one that matters: **every claim arrives attached
to a real evidence id THIS RUN really emitted**, so the human reads the sentence
beside data that exists right now.

### The duplicate-key scan genuinely runs here — the first path where it can

On both model paths the transport parses the bytes before this system sees them,
so `duplicateKeyCheck` has to report `unavailable_transport_parsed` (step 37).
**This module holds the caller's own bytes**, so `findDuplicateKey` really runs,
and `{"strategy":"dca","strategy":"grid"}` — which `JSON.parse` silently resolves
to `grid` — is refused rather than quietly becoming a strategy nobody
unambiguously asked for. Tested end to end through the endpoint.

### NO PERSISTENCE BRIDGES THE TWO CALLS, and the reason is recorded in the endpoint's own docblock

**No D1 row, no KV key, no cache, no temporary store of any kind.** The client
holds the Stage 2 result and hands it back.

There are two ways to stop a caller inventing an assessment: store it, so the
resubmission is only an id; or **re-verify it against reality**. This endpoint
does the second. So the absence of storage is **not** an unsolved trust problem —
trust is answered without it.

The reason is that **21.5 requirement 5 specifies a real, persistent proposal
record** — prompt text, settings, model id, raw responses, both upstream inputs,
an audit trail a human can return to — and that record belongs to Stage 4's
pipeline assembly, which does not exist. A throwaway bridge invented now would
have a different shape, a different lifetime and a different owner than the thing
actually coming, would solve a problem already solved, and would almost certainly
be deleted when requirement 5 lands. **The decision is to carry the constraint in
the open rather than build storage twice**, and it is stated in
`getAccountDerive`'s docblock rather than only here.

### The real port wiring, and what the probe did differently ON PURPOSE

`deriveContextPortsFor` is `{ ...gatherPorts(ctx), getSymbolDetails: symbolDetailsFor(ctx) }`
— the cached `tradablePairsFor` and uncached `candleSourceFor` that `/gather`,
`/candles` and `/assess` all use, plus the same `SymbolDetailSource` bot
creation's spot-instrument gate uses. **A derivation cannot reach a different
venue, a different cache or a different account resolution than the assessment it
derives from did.**

The probe rebuilt those three adapters locally, and that was **correct for a
probe**: exporting `handlers.ts`'s private adapters for a file about to be deleted
would have left a permanent widening behind after the temporary thing was gone. A
real endpoint has the opposite requirement. Both docblocks now say so.

### Statuses: three new rows, and one code deliberately ABSENT

| code | status | why |
| --- | --- | --- |
| `capital_unreadable` | **503** | with `no_price_history` — an upstream read failed, so real headroom is UNKNOWN and retrying when D1 answers is the right response |
| `symbol_filters_unreadable` | **503** | the one check 21.5 requirement 3 names that nothing else performs before an order is placed could not run at all |
| `no_capital_headroom` | **409** | and deliberately NOT 503. **The read SUCCEEDED.** The account genuinely has nothing fundable — a well-formed request conflicting with current state, `duplicate_bot_instance`'s shape, fixed by funding or stopping a bot and never by retrying. 503 would send an operator hunting an outage that is not happening |

**`citation_unknown` is deliberately NOT in `STATUS_BY_CODE`,** and the reasoning
is recorded in the table itself. It is the one code in this system carried by
**three** error classes whose correct statuses genuinely differ:

- `AssessParseError.citation_unknown` → **502**, the Assess MODEL invented an id.
- `DeriveParseError.citation_unknown` → **502**, the Derive MODEL did.
- `AssessResubmitError.citation_unknown` → **409**, the CALLER resubmitted a
  result whose citation no longer resolves. Well formed, conflicting with current
  state, fixed by running `/assess` again — **never the vendor's fault**, which is
  why 502 would be wrong, and not nonsense the caller sent, which is why 400 would
  be wrong.

All three handlers raise an `ApiError` carrying the status explicitly. **A row
here would silently make one of the three wrong, and the wrong one would be
whichever handler someone later simplified into a bare `throw`.** A mutant that
downgrades the resubmission case to 400 is caught by three tests.

**One evidence id. Two calls ten minutes apart. Two genuinely different real

### ⚠ CHECK 7: THE STALENESS CASE FIRED FOR REAL, UNPROMPTED

**This is the finding of the step.**

A shallower candle window on the second call meant a **real original citation**
— `candles.bucket.12` or `.13`, emitted by check 1's own `/assess` run and cited

the endpoint correctly refused with `citation_unknown`.

this step's own module header argues is "reachable through ordinary operation"

That matters more than the passing test that predicted it, and for a specific

Check 6 is that case. **Check 7 is not.** It is a caller behaving perfectly
correctly, resubmitting exactly what they were given, refused because the world
moved. The check is a freshness check, and it has now been seen being one.

the fresh gather and **before** the model call, by construction, and a mutant that

### Assumptions and limits, stated so they can be checked rather than discovered

1. **The transport encoding was this session's choice.** The brief fixed `GET`; a
   nested `claims` array in a GET essentially forces one URL-encoded JSON query
   parameter, so `?assessment=<json>` it is. A real submission is ~1–2 KB
   (~2–3 KB encoded) and the live run confirms it works, but **there is no
   explicit length guard** and a very long claim list could approach a URL cap.
2. **`envelope` and `duplicateKeyCheck` are unverifiable** and are taken on the
   caller's word — see above. So is every `statement`.
3. **The re-verification fires BEFORE `deriveParameters`' own preconditions.**
   With a broken candle fetch on the second call the answer is
   `409 citation_unknown`, **not** `503 no_price_history`. Intentional and tested,
   but it is a status difference from `/assess` on what looks like the same
   failure.
4. **`curl --data-urlencode name@file` includes the trailing newline** `jq -c`
   writes. `parseResubmittedAssessment` trims before parsing, so it is harmless —
   but the duplicate-key scan runs on the **trimmed** text, not the raw bytes.
5. **Still no live DCA derivation.** Both of entry 41's runs produced grid and so
   did this one. The DCA prompt, its schema and its field contract remain
   **verified only against fixtures**, three live Derive runs later.
6. **Three Derive samples are three data points**, not a distribution and not a
   compliance rate — the same caveat entry 41 attached to two. Nothing here
   isolates the two-endpoint split from ordinary vendor variance as the reason
   this run's Derive figure is the lowest of the three.
7. **`temperature: 0` = greedy decoding and seed reproducibility remain ASSUMED**,
   unchanged since entry 37, and **no identical-input determinism replay has been
   run** for either stage.
8. **Entry 41's two open citation-semantics questions are untouched** and remain
   open by intent: a parameter grounded in `assessment.claim.N` rather than in
   fetched data, and `news.status` — an absence marker — cited as grounds for a
   value.

### ⚠ DERIVE STILL CANNOT DETECT A BAD UPSTREAM JUDGEMENT

Carried forward from entries 40 and 41 **without dilution**, because a successful
live run is exactly when it is most likely to be lost.

Every check this endpoint performs — the fresh-evidence re-verification included
— answers *"is this internally consistent, currently grounded, and acceptable to
the real create-bot validators?"* **Not one answers *"was the data worth reasoning
about?"***

**The re-verification makes the grounding fresher. It does not make the judgement
better.** An assessment whose reasoning was financially meaningless when it was
made is still meaningless after every one of its citations resolves cleanly
against a newer window — it is now meaningless *and current*, which is arguably
the more convincing failure. The sandbox caveat of entry 40 applies in full: **this
run verifies the PIPELINE and says nothing about the QUALITY OF THE JUDGEMENT.**

The human in 21.1 is the only part of this loop that can tell the two apart.
