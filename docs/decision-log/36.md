### The three doors, and the deviation from 21.2 recorded as one

21.2 names **two** entry points. This adds a third, and that is a deviation
rather than an interpretation, so it is written down as one.

| door | selection | gather | status |
| --- | --- | --- | --- |
| `?entryPoint=named&pair=` | `selectNamedCandidate` | `gatherCandidateData` | works |
| `?entryPoint=watchlist` | `selectWatchlistCandidates` | `gatherCandidateSetData` | works |
| `?entryPoint=general` | — | — | **503, before any work** |

**The justification is 21.2's own rule.** The doors "differ **only** in how the
candidate coin or coins are chosen", and that is exactly and only what this
differs in: same `CandidateSet`, same `Candidate`, same everything downstream, no
second prompt set and no second code path below selection. What 21.2 forbids is a
**general run that quietly degrades** into a watchlist re-read when the trending
pull fails — and that prohibition is untouched. `selectGeneralCandidates` still
throws `trending_unavailable` rather than degrade, **nothing routes to the
watchlist door as a fallback**, and a caller reaches it only by naming it. A door
an operator must ask for by name is the opposite of a silent degradation.

This was not invented here. `candidates.ts` has said since step 31 that "an
explicit watchlist-only entry point is a thing an operator could be given later,
**ON PURPOSE and under its own name**; what must not exist is a general run that
quietly becomes one." This is that sentence's second half, and the README now
records it as spent rather than available.

**`WatchlistCandidatePorts` holds no `TradablePairSource`**, so the door cannot
re-check tradability even by mistake — matching `selectGeneralCandidates`'
treatment of the identical watchlist rows exactly. That symmetry is the point: a
door that re-validated where the other did not would make two doors disagree
about the same table, which is worse than either behaviour. The staleness gap
steps 28 and 31 recorded stays one gap.

### `general` refuses, and refuses in the right place for the right reason

There is **no `TrendingSource` implementation anywhere in this repository** —
only the type, the port field, one call site, and stubs in `candidates.test.ts`.
No vendor has been chosen (logs 30, 31). So `entryPoint=general` cannot run, and
the question was only ever *how* it should fail.

It raises `no_trending_vendor` (503) **at the top of the handler**: before the
interval is parsed, before the registry is read, before anything. Two tests pin
that ordering, including one against an account that does not exist.

**The rejected alternative was handing the module a stub that fails**, which
would produce `trending_unavailable` — a code meaning *a pull was attempted and
did not answer*. No pull was attempted. There is nothing to attempt one with, and
a message implying a transient outage would send an operator to check a status
page for a vendor this project has never had. **This is exactly the distinction
`NEWS_NOT_YET_AVAILABLE` draws one layer down** — "this is NOT a failed fetch, no
request was made" — applied at the HTTP boundary. The two sentences must never be
produced by the same branch, and here they cannot be.

`trending_unavailable` is nonetheless mapped to 503 in `STATUS_BY_CODE`,
**unreachable over HTTP today**, for the reason `requires_human_actor`'s row
exists: the module still throws it, and when a vendor finally lands it must not
silently become the table's 400 default.

### The serialization boundary, which is where this step's real risk lived

The bundle shape is the reason this endpoint is more than plumbing, and **two of
its three hazards are invisible to every test that stops at the module.**

**1. `Error` serializes to `{}`.** `name`, `message` and `stack` are
**non-enumerable**, so `JSON.stringify(new CandleWindowError(...))` yields
`{"code":"candles_unavailable"}` — `code` is an own property and survives,
`message` is not and does not. A bundle put on the wire unserialized returns
**200, correctly shaped, and mute about what went wrong**: coded, and with no
explanation. Not a throw, not a warning. `moduleErrorView` exists solely for
this.

**2. Two raw `bigint`s reach `JSON.stringify` and throw outright.** Both were
flagged in steps 34/35 and both are in places nobody auditing money would look:

- **`ConcentrationFacts.policy.assetCapitalShareFlagAtPct`** — the policy is
  echoed verbatim so a human can reconstruct the numbers, and the threshold
  inside it is `40n * ONE`. It is a *policy* field, not an amount, which is
  precisely why it is easy to miss. Unconverted, **every successful gather
  returns 500.**
- **`AccountExposure.committed[].allocatedCapital`** — one per bot rather than
  one per result.

Both are handled by **reusing `jsonSafe`**, and the candle window by **reusing
`candleWindowView` verbatim**, so a candle from this endpoint is byte-identical
to one from `GET /api/accounts/:label/candles`. Nothing was reimplemented; the
only genuinely new serialization code is the two error views.

**3. The failure reporter can itself fail.** `threw_unexpectedly` carries
`unknown`, and `String(Object.create(null))` throws `TypeError: Cannot convert
object to primitive value`. Unguarded, that escapes into `handleApiRequest`'s
catch and turns a 200-with-one-failed-slot into a **blanket 500** — losing the
concentration result that was read successfully, which is the exact failure
`gather.ts`'s isolation exists to prevent, reintroduced one layer up at the last
possible moment. `thrownErrorView` wraps the conversion and reports a value that
will not describe itself as exactly that.

### What comes back, and the field that is deliberately absent

```jsonc
{ "data": { "entryPoint": "watchlist",
    "set": { "set": { /* the whole CandidateSet: watchlist.readAt, trending: null */ },
             "exposure": { "outcome": "ok",
                           "value": { "rowsRead": 13,
                                      "committed": [ { "allocatedCapital": "500.00000000" } ] } },
             "count": 8,
             "bundles": [ { "candidate": { "pair": "ETHUSD", "sources": [ /* entryId, note, addedBy, addedAt */ ] },
                            "candles":       { "outcome": "ok", "value": { "fetchedAt": 1760…, "count": 1440 } },
                            "news":          { "outcome": "not_yet_available", "reason": "…", "decisionLogEntry": "docs/decision-log/30.md" },
                            "concentration": { "outcome": "ok", "value": { "assessment": "flagged",
                                                 "policy": { "assetCapitalShareFlagAtPct": "40.00000000" } } },
                            "assembledAt": 1760… } ],
             "assembledAt": 1760… } }, "error": null }
```

A failed slot carries the producing module's **own** code and message plus
`failedAt`; a thrown one carries `{name, message}` and **no `code`**, because
inventing one would dress a port failure as an enumerated refusal.

**THERE IS NO TOP-LEVEL SUCCESS FLAG, and its absence is the design.** A 200
means *assembly ran*, never *every input worked*, and **a 200 with every slot
failed is a correct response**. A boolean summary is precisely what would let a
reader stop looking at which inputs actually worked — and deciding whether a
bundle is fit to use is Stage 4's judgement, which does not exist. The endpoint
publishes the facts and refuses the verdict, which is `concentration.ts`'s rule
applied at the wire.

### The conclusion, stated at exactly the width the evidence supports

**At N=8, sequential research-path candle fetches against real Gemini are fully
survivable, with no sign of an approaching limit even when re-run immediately.**

**This does NOT establish that no limit exists.** What was tested is N=8, twice,
at one interval, on one venue, on one account. Specifically **untested**:

- **Larger N.** 21.3 caps the watchlist at 10, so 9 and 10 are untested and near.
- **N beyond the watchlist.** A future trending pull adds candidates **on top of**
  the watchlist, so a real general run is "a dozen or more" (step 35's own
  estimate) — half again what was measured, and unmeasured.
- **Sustained repetition.** Two runs is not a rate window.
- **Concurrency.** Still sequential; the burst question is untouched.

The honest form is **"N=8 confirmed safe, larger N untested"**, not "there is no
rate limit". The distinction is the same one this log has drawn repeatedly
between a checked thing and an assumed one, and the failure mode of the
overclaim is specific: it would license removing the sequential ordering, or
growing the candidate count, on evidence that covers neither.

### The question was wrong, and the correction is the more useful half

Step 35 asked "whether that trips **section 5.4's rate budget**". Checked against
the spec this session, that question has an **analytic answer requiring no live
run at all**: 5.4 is scoped to *"All **order-execution** requests for bots on that
account"*, mirroring **Binance's** limits from response headers. A research
candle fetch is not order execution and is not on that budget.

The code agrees, and goes further:

- **`clientForAccount` never applies `withRateLimit`.** The gate is applied by
  callers, and neither `envCandleLister` nor `envSymbolLister` applies it. The
  research candle path is **ungated**.
- **`resolveGeminiExchange` builds a client with no `RateLimiter` binding at
  all**, and says so in its own docblock: *"Gemini sends no used-weight header
  for a client to report… The request-count gate a Gemini account needs is
  applied by the wrapper at dispatch time, **which is out of scope for this
  step**."*

So the real question — the one the live run actually answered — is **whether N
sequential requests trip Gemini's own limits, and whether this system can see it
if they do.** The measured answer to the first is "not at N=8". **The answer to
the second is no, and that is unchanged by a clean run.** Nothing on this path
reports usage into any budget, so a future run that *does* trip a limit will
surface as `candles_unavailable` on some tail of the bundle list and **nowhere
else** — no alert, no counter, no reserve. The bundle would report it honestly,
which is step 35's isolation working; "honestly reported and routinely empty"
remains a design problem rather than a success.

**A clean result at N=8 therefore does not close this.** It moves it from "the
first thing to check" to "the thing that has no instrumentation when it happens".

### Item 8 reassessed: the revalidation gap is real, and currently empty

Steps 32, 33 and 34 each recorded that the spot/perp gates run at **creation
time only**, so the pre-existing bots are never re-validated. Carried forward
unqualified a fourth time, that reads as a live exposure. **It is not one today,
and step 34's own live read already established why — it just was not stated in
those terms.**

All 13 bots are on **`BTCUSD` (11)** and **`DOGEUSD` (2)**. Neither is a
perpetual: no suffix, no ambiguity, two of the most ordinary spot pairs Gemini
lists. `v-perp-1` is a `BTCUSD` bot with a misleading name, which step 34 already
pins with a test by name for exactly this reason. **The concrete risk — an
existing bot on an instrument this system cannot model — is empirically empty for
the entire current population**, not unknown.

What remains is delisting (`BTCUSD`/`DOGEUSD` leaving Gemini: not a near-term
concern) and reclassification (not a thing — a perp is a different symbol, not a
changed one).

**Assessment: no follow-up step now. Re-scope the flag instead of repeating it.**
The wording should be *"there is no revalidation path; the population is 13 bots
on `BTCUSD`/`DOGEUSD`, confirmed spot 2026-08-10, so the gap currently has no
exposure"* — a true statement about code that stops implying a risk the data says
is absent. That inversion is the same failure step 34 named against itself over
DOGE: a true partial statement generalised into a false impression.

**The gap is standing, not one-time**, and is empty only because the population
is small and boring. So it gets a **trigger rather than a date**: build
revalidation **when the proposal pipeline can create bots itself** — when bot
creation stops being exclusively human-driven, which is what section 21 is for
and what this endpoint is a step toward. **It belongs inside reconciliation
(section 9)**, which already runs every five minutes and already halts on drift,
not as a new mechanism. Naming the home now stops the eventual step inventing a
second cron.

### The halt/archive UI-gating correction

The operator asked for the exact halt/archive paths before disposing of
`v-spot-1` and `v-perp-1` manually. The API answer and the **dashboard** answer
differ, and the difference would have been discovered as a dead end:

- **`HaltAction` renders only for `running`.** `created` is excluded
  **deliberately, not by mirroring the backend** — its docblock says the backend
  *would* accept it and that "the honest control for a bot that should not run is
  to simply not start it."
- **`ArchiveAction` renders only for `halted`/`stopped`/already-archived.** "A
  `running` or `created` bot that is not archived gets nothing at all — not a
  disabled button."

So a `created` bot shows **neither control**, and since both leftovers were
created by the step 32/33 verification runs and never started, the halt step
needs `curl` (`POST /api/bots/:id/halt` with a required non-empty `reason`);
archive then works in the UI, and needs no body at all.

**And halt + archive does NOT release the capital.** Only the `stopped`
transition releases a reservation, via `releaseBotCapital`, and
**`BotInstance.close()` has no route in the table** — so there is no HTTP path to
`stopped` at all. The $50 each stays reserved against the `gemini-main` ledger
and keeps counting in every account rollup and in concentration's `committed`
total after archiving. The dashboard's own archive dialog already says this
("archiving is not closing"), so the UI and this record agree. **"Archived" means
hidden, not cleaned up**, and log 32's stated disposition — "archived **and
released**" — is not currently reachable.

### Deferred, deliberately

  `selectGeneralCandidates` still has **no reachable caller**. Step 30's three
  conditions are unmet; log 31's storage-clause question is unanswered.
- **No concurrency.** Gathering is still sequential. The live run measured the
  sequential shape, so making it concurrent would invalidate the one number this

- **No revalidation of existing bots**, per the reassessment above — real,

- **Section 21's four unbuilt pieces** — Assess, Derive, Explain, the proposal
