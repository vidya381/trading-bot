## Step 64: `close()` refuses rather than wiping an unresolved order — and the investigation that caught a fix which would not have worked

Date: 2026-08-21 · **NOT COMMITTED** as of writing. Four files sit modified on
disk: `src/durable-objects/bot-instance.ts`, `src/api/envelope.ts`, and their two
test files.

### What this is

This closes a gap **first found during fix 1's build (entry 57)** and recorded
there as "found, not fixed": `#closePass` wipes a bot's tracked order list
unconditionally on `close()`.

**It was investigated BEFORE any fix was attempted, and the investigation is the
substantive part of this entry.** It corrected **two** wrong assumptions carried
in the build brief — one about why the bug was thought to be harmless, and one
about what the fix should be. The second correction caught a fix that would have
compiled, read correctly, passed review, and changed **zero** real behaviour.

The split held: no `wrangler`, no deploy, no HTTP call, no real D1, no browser.

---

## PART 1 — THE BUG

`close()` can leave a bot permanently `stopped` while one of its orders was never
actually confirmed resolved. Two ways that happens, both real:

- **an unrecorded fill** — entry 57's gate refused to close the local record
  because the exchange reported more filled than this bot had recorded, so the id
  stayed on `openOrderIds`;
- **an unconfirmed cancellation** (`cancel_failed`) — the cancel request could not
  be confirmed, so **the order may still be live on the exchange.**

`#cancelOpenOrders` deliberately leaves both classes on the list. `#closePass`
then wiped the list wholesale on the way past.

**And once a bot is `stopped`, NOTHING in this system ever looks at that order
again.** This was checked exhaustively rather than assumed, and the finding is
that **every possible observer is gated on bot STATUS, not on whether an id
remains in the tracked list**:

| Observer | What gates it |
| --- | --- |
| the 30-second poll | `#pollArmed`: `openOrderIds.length > 0 && status !== "stopped"` |
| `checkOpenOrders` | refuses a stopped bot outright |
| `applyMissedFills` | requires `halted` |
| `repairPosition` (entry 59) | gate 2 requires `halted` |
| reconciliation | `RECONCILED_STATUSES = ["created", "running", "halted"]` — **`stopped` excluded** |

So the order is not merely *forgotten*. **It becomes permanently unobservable the
moment the bot stops**, and on a bot whose capital has just been returned to the
account.

## PART 2 — TWO WRONG ASSUMPTIONS, CORRECTED BEFORE ANY CODE

### WRONG ASSUMPTION 1 — that the flat-position requirement made this harmless

The brief reasoned that `close()` already requires a flat position
(`assertFlatBeforeRelease`, step 56), so a bot cannot close while anything
material is outstanding.

**That reasoning is backwards, and the gate is structurally blind to this case.**

`assertFlatBeforeRelease` reads `heldQuantityOf(snapshot)` — `position.quantity`
for DCA, `ladder.heldQuantity` for grid. **An unobserved fill leaves that number
flat PRECISELY BECAUSE the fill was never applied.** The position only moves when
a fill is *applied*, and the entire premise of this bug is a fill that was not.

So the check is reading **the exact number a missing fill would have changed**.
It cannot detect a problem that is *defined by* that number staying wrong.
"Looks safe" and "is unobserved" produce the **identical read** on this field.

That is a real logical trap, not a minor imprecision — a guard whose input is
disabled by the very condition it is being asked about. It is reachable without
anything exotic: a DCA bot with `autoRestart`, cycle completes, position flat, a
new base buy resting, that buy partially fills between two poll passes, operator
clicks Close.

### WRONG ASSUMPTION 2 — that the fix should RETAIN the id, mirroring entry 57

The brief specified mirroring fix 1: keep a suspect order id on `openOrderIds`
instead of wiping it.

**Investigation checked every real consumer of that list and found retention
would have been INERT.** Per Part 1's table, once a bot's status is `stopped`,
**no code path reads `openOrderIds` at all** — retained or not. Entry 57's
retention works because a *halted* bot stays observable and the retained id is
handed to the poll, which repairs it. After a close there is nobody to hand it
to.

**A fix built to that specification would have compiled, looked correct, matched
an established pattern in this codebase, and changed nothing whatsoever.** It is
recorded here as a fix that would not have worked, **caught before being built
rather than after** — which is the entire value of the investigate-first step and
the reason it is written up ahead of the fix rather than as a preamble to it.

### A factual correction to the brief's premise

`assertFlatBeforeRelease` lives in the **API handler layer**
(`src/api/handlers.ts`), not inside `close()`. It is called by `closeBot` and by
`archiveBot`. **The Durable Object's `close()` has no flat-position precondition
of its own.** Recorded as a factual correction rather than a design flaw: the
handler layer is a reasonable place for it, and both routes that release capital
do call it.

Also corrected: the wipe is at **`bot-instance.ts:3376`**, not the line 2606 the
brief carried from entry 57's session. The file has moved substantially since.

## PART 3 — WHAT WAS BUILT, AND THE DELIVERATE DEVIATION

`#closePass` now **refuses** to close while its cancel sweep leaves ANY order
unresolved on `openOrderIds`.

Placement matters and is the same discipline entry 57 established: the check sits
**after** the cancellation attempt and **before `releaseBotCapital`** — the
actual point of no return, since that call flips the row to `stopped` and returns
the allocation. A refusal after it would leave a half-closed bot, which is what
this is protecting against.

New `BotInstanceErrorCode` **`orders_unresolved`**, mapped to **409** beside
`position_unverified`, `invalid_status`, `account_tripped` and
`globally_tripped`: the request is well formed, conflicts with current state, and
resolving the outstanding orders makes the identical request work.

### The deviation: reading the residual list, not re-querying the exchange

The brief specified re-applying fix 1's local-versus-remote comparison to each
order about to be dropped. **The fix reads the RESIDUAL `openOrderIds` instead**,
and this is a better design rather than a shortcut:

- `#cancelOpenOrders` **already removes every id it successfully resolved**.
  Anything still on the list afterwards is there for exactly one of two reasons —
  entry 57's gate refused it, or the cancellation could not be confirmed. The
  residual list **is the outcome of that comparison**, already performed.
- Re-querying the venue would be a **second, independently-worded comparison of
  the same two quantities** — precisely the class of drift entries **57** and
  **61** were both built to eliminate. Entry 61 parameterised `driftAgainst`
  rather than duplicate it for exactly this reason.
- **It catches a case the specified method would have missed entirely.** A
  local-versus-remote fill comparison says nothing about `cancel_failed`, where
  the fills may agree perfectly and the problem is that **the order may still be
  genuinely live on the exchange**. Reading the residual list catches both
  classes. That is a real, wider safety property **gained** by deviating, not
  merely a lateral move.

## PART 4 — VERIFICATION, REAL NUMBERS

### Five tests

1. **`REFUSES to close while the sweep left an order with an unrecorded fill`** —
   entry 57's scenario on the close path. Asserts the refusal carries
   `orders_unresolved`, the bot is still `running` in D1, `total_allocated` is
   untouched at `400`, and the order is still on `openOrderIds`.
2. **`REFUSES to close while a cancellation could not be confirmed`** — the
   `cancel_failed` class, with its alert asserted, and the bot still `running`.
3. **`closes normally once the outstanding order resolves`** — the refusal is a
   latch on a condition, not a dead end: clear it and the identical request
   succeeds.
4. **`still wipes the list and closes when the sweep resolves everything`** — the
   common path, unregressed: `openOrderIds: []`, status `stopped`, the resting
   order `cancelled`, D1 `stopped`.
5. **API: `refuses to close when the cancel sweep left an order unresolved (409)`**
   — `orders_unresolved` with a message matching `/NOTHING observes it/`, the bot
   still `running`, and **zero `capital.released` audit rows**. Its comment
   records that the flat-position gate passes here precisely because the position
   *is* flat — Part 2's finding, asserted end to end.

### A self-caught test-authoring mistake, recorded rather than omitted

An early draft of the API test used an anchor that sat **inside an existing test
body**, nesting a new `it()` within another test and breaking an unrelated one
(`refuses a bot that still holds a position, and sells nothing`). The suite caught
it and it was relocated properly before anything shipped.

Worth keeping in the record because of the specific shape of the danger: the file
**typechecked cleanly** with the nested block in place. Only running the suite
exposed it. A structural error in test code can look entirely healthy to the
compiler while quietly disabling an assertion someone is relying on.

### Mutation test

The gate reverted to the old unconditional-wipe behaviour (`if (false && …)`).
Typecheck clean, then both affected files run:

```
× refuses to close when the cancel sweep left an order unresolved (409)
× REFUSES to close while the sweep left an order with an unrecorded fill
× REFUSES to close while a cancellation could not be confirmed
× closes normally once the outstanding order resolves

Tests  4 failed | 413 passed (417)
```

**Caught by 4 of the 5.** The fifth — `still wipes the list and closes when the
sweep resolves everything` — **correctly did NOT fail**, because the mutant is
behaviourally identical on that path. A failure there would have meant that test
was not exercising the gate at all. Restored; the marker greps to 0; typecheck
clean.
