## Step 21: Making the poll safe to interleave, part 3 of 3
Date: 2026-08-03

Step 19 built the observation primitive. Step 20 armed it on a 30-second alarm
and recorded, as the reason for a third step, that "the alarm and the price feed
can now both reach this object concurrently". This is that step: it makes the
concurrency safe. It deliberately does **not** change what a fill does once
observed — that is step 22.

### Section 0 first, because it decided how much of the rest was real

This project has been carrying one sentence about the runtime since step 8, in
`rate-limiter.test.ts`: *"A Durable Object serialises nothing across an await."*
It is the only thing in the repository that looks like evidence, and it is not
evidence. That test drives its competitor as a direct in-process method call
from inside `runInDurableObject`, never through the stub, so it demonstrates
that the lost-update **arithmetic** is safe. It says nothing about whether the
runtime would deliver a second call at all.

The whole shape of this step depended on the answer, so it was **measured
before anything was built**. `src/durable-objects/concurrency-model.test.ts`:

1. **An RPC is delivered, and runs to completion, while the object is suspended
   on an exchange call.** So every read → network await → write in this object
   is a real lost update.
2. **An alarm is delivered on the same terms.** Two `getOrderStatus` calls were
   observed outstanding at once (`read-1:begin, read-2:begin, read-1:end,
   read-2:end`), and the bot has one open order, so the second read can only be
   the alarm's. This is exactly the concurrency step 20 introduced.
3. **A storage-only read-modify-write survived a two-pass race on one
   `fillId`** — exactly one pass applied it.

So: defend everything spanning an exchange call or a D1 write; treat
storage-only sequences as probably atomic but do not build on it.
**`beginAttempt` is therefore untouched**, measured as sufficient rather than
assumed to be — its bare get-then-put was the one thing result 3 was needed to
settle.

**A methodological trap, avoided and then walked into anyway.** The obvious
probe suspends the object on a promise the test resolves by hand. That is
invalid: a hand-made promise is not I/O, resolving it queues an ordinary
microtask, and a microtask interleaves regardless of what any gate does — such a
probe "proves" the object is unserialised no matter what is true. The
suspensions used are genuine (every exchange call goes through a real
cross-object RPC to `RateLimiter`), and the probes observe **arrivals**, which
the runtime decides, rather than **orderings**, which microtasks decide.

The trap was then walked into in a second disguise. Probe 3's first version used
a FULL fill and passed **with both identity checks deleted** — because a full
fill is guarded twice more over: the first application takes the order terminal,
so the second is refused as `fill_after_terminal`, and failing that as
`overfill`. Four independent guards, and the probe could not see past the outer
two; it was measuring the state machine's belt and braces, not the thing it
named. At **half** the order the rung stays `partially_filled` and two
applications total exactly its quantity, so neither of those fires and the
`fillId` check is genuinely alone. The same two-line mutant now doubles the
position.

The probe also **segfaulted `workerd`** when first run with the full suite while
passing alone, twice over: a real alarm firing a pass that outlived the test's
D1 binding, and `settle()` — a fixed 10ms — used as a barrier. A fixed delay is
never a barrier; it is a guess about a loaded machine. Now condition waits, every
RPC tracked and awaited in `afterEach`, and the alarm's pass drained on its
schedule re-arm rather than a timer.

### `#mutateState`: writes that reverted each other

`{ ...snapshotTakenEarlier, oneField: newValue }` is not a field update. It is a
whole-state overwrite that silently reverts every other field a concurrent pass
wrote — a position, a ladder, an `openOrderIds` entry, or a `status`. Every
`#putState` now goes through `#mutateState`, which re-reads **after** the await
and takes a delta.

Two of the sites it fixes are worth naming because neither needed the alarm to
bite:

- **`#placeTakeProfitSell` assigned `openOrderIds: [exitId]`**, discarding
  whatever `#cancelOpenOrders` had just failed to cancel. That order is still
  live on the exchange, and dropping it meant it was never polled or cancelled
  again — on the one path where the bot is trying to get flat. **One failed
  cancel was enough**; no concurrency required, and it is in the deployed build.
- **`#cancelOpenOrders` assigned the list it believed in when it started**,
  after N throttled network cancellations. A poll folding a fill mid-sweep
  places a grid replacement, and that id was erased: a live order on the
  exchange, untracked, unpolled, never cancelled, on a bot that had just halted.
  It now removes what the sweep *resolved* and leaves everything else.

`#allocateSequence` came out of the same discipline. The sequence **is** the
`clientOrderId`, so two passes reading it mint one id for two orders.
`beginAttempt` already caught that — and being caught means the second order is
**skipped**, so a rung silently goes missing until the next price update.
Allocating atomically means the collision does not happen; `beginAttempt` stays
the backstop it was built to be.

### The point of no return

`#mutateState` fixes writes that revert each other. It cannot help with a
**decision** taken against state that has since changed, because once the order
is on the exchange nothing takes it back. So every send site re-reads the status
immediately before sending.

This is what finally makes step 19's `placeReplacement: fresh.status ===
"running"` mean what it says. Steps 18 and 19 both worked for that invariant —
19 specifically refused to hardcode `true`, and a mutant confirmed the test
suite caught it — but the gate reads the status and then crosses two D1 writes
(`#mirrorOrderUpdate`, `#mirrorTrade`) and a possible filter refresh before
`#placeGridOrder` sends. A halt landing in that window left the
derived-not-hardcoded gate deciding on a status that was no longer true, and a
halted bot put a live order on the exchange anyway. The gate was right; it was
just reading too early.

**Cancellation is deliberately not gated this way.** Cancelling is safe under
every status, and refusing to cancel because the bot changed state is how orders
get left live.

### The poll yields, one way

The asymmetry is a property step 19 established rather than a general principle:
**everything the poll does is re-derivable.** It invents nothing, it dedupes on
the exchange's own `fillId`, and abandoning a pass costs thirty seconds and a
re-read. Nothing else here has that property — a price tick that skipped its
stop-loss check has simply not checked it.

So `#outsidePoll` counts non-poll passes in memory (a DO's alarm and its RPCs
share an instance; an evicted object has no in-flight pass to remember), and the
poll stands aside when any is in flight — before its loop, and **again after
each `getOrderStatus` returns**, which is the check that matters, because that
read is exactly the window section 0 measured events arriving in.

**One-way, deliberately.** A symmetric lock would have reintroduced, at the
scheduling layer, precisely the head-of-line blocking that §5.4's reserved
rate-limit slice exists to prevent: a stop-loss queued behind a routine status
read is the outcome this system is built to avoid. That is the decisive
objection to `blockConcurrencyWhile`, and the reason it is not used.

Poll-vs-poll is **not** covered, on the strength of probe 3: what it would cost
is a duplicate read, not a duplicate fill.

### `deferred`, and the two mutants that survived

A deferred pass is neither `unreadable` (the venue answered) nor `skipped`
(nothing was read and refused), and folding it into either breaks one of step
20's lifecycles: counted as a failure it backs a busy bot off to the five-minute
floor and reports `poll_blind` on a reachable venue; counted as a success it
resolves standing alerts it never looked for. So it is its own outcome — the
same separation step 20 made between `skipped` and `unreadable`, for the same
class of reason.

**Two mutants survived the first version, and both were right to.** They traced
to one line: the post-read yield did `reads -= 1`, reasoning that the discarded
read had not really happened. That forced `reads` to zero, and zero is what both
downstream guards already treat as "nothing to read" — `observedEverything`
starts with `reads > 0`, and `#runScheduledPoll` returns early on `reads === 0`.
A deferred pass was indistinguishable from an empty one, so neither guard could
be observed working. The read **did** happen and it **did** succeed; what a
deferred pass did not do is finish, and `deferred` is what says so.

Removing that line exposed a second thing: **`#runScheduledPoll`'s explicit
`deferred` branch was dead**, and worse than dead. A pass that failed to read
order A and then deferred on order B has real evidence the venue is unreachable,
and returning early on `deferred` threw it away — suppressing the backoff and
`poll_blind` for exactly the bot that needed them. The branch is gone; the
existing `unreadable === 0` condition is already correct in both cases.

The post-read deferral also could not be tested in `bot-instance.test.ts` at
all: driving a competitor to completion inside a seam means the poll defers
*before* its loop, with `reads === 0`. The interesting deferral needs a
genuinely still-running competitor, which needs the stub harness — a halt parked
inside its own cancellation while the poll resumes from its read. That test
lives with the probe, and it is the only one that exercises
`!pass.deferred`.

`OrderCheckResult` now reports `deferred`, because three empty arrays are
otherwise indistinguishable from a clean pass, and "your books are up to date"
is a very different answer from "I did not look".

### Tests

**10 new (1494 → 1504)**: 4 in `concurrency-model.test.ts`, 6 in
`bot-instance.test.ts`. Every one forces a real interleaving through a seam the
object actually uses, in the shape step 8's rate-limiter test established.

Six mutants, all caught:

| mutant | result |
| --- | --- |
| take-profit assigns `openOrderIds` instead of appending | 1 failure |
| the halt sweep assigns the list it started with | 1 |
| no point-of-no-return check before a buy is sent | 1 |
| the poll never yields (both checks disabled) | 2 |
| a deferred pass counts as having observed everything | 1 |
| the post-read yield does not report itself as deferred | 1 |

The fifth is the one that **survived until the source was fixed**, and the sixth
exists only because fixing it made the flag observable.

Backend `tsc --noEmit` clean; full suite stable across three consecutive runs;
dashboard `tsc -b && vite build` clean (nothing it imports changed).

### Deliberately not done

- **A fill still does not drive a decision.** A poll-observed fill waits for the
  next price tick, per step 21's design discussion: the poll has no price, and
  every action either strategy can take needs one. `liquidatePosition` already
  refuses `lastPrice` as a fallback and fetches fresh; deciding a stop-loss off
  a stale tick would contradict that. Step 22.
- **Nothing verifies a tick is actually coming**, which is what makes "wait for
  the next tick" sound. `lastPriceAt` is written and still read by nothing.
  Step 22.
- **`bot.open_orders_checked` still writes nothing on a refusal**, so
  `#foldTerminalState`'s quantity-gate refusal — the `bot-44400a` condition — is
  recorded nowhere durable. Step 22.
- **`checkOpenOrders` is still unreachable** from the API. Step 22.
- **Not deployed.** Nothing has been run against a live bot.
- **`applyMissedFills` and the halt-sweep interaction still untouched** at the
  operator's standing direction (step 19), though `#cancelOpenOrders` no longer
  destroys concurrently-added ids.

### Open questions

1. **Poll-vs-poll is unguarded by design.** Probe 3 says the fill dedup holds;
   what is not measured is two polls racing `#foldTerminalState` or the ladder.
   The cost is believed to be a duplicate read, not a duplicate fill.
2. **`#passesInFlight` is in memory and therefore per-instance.** Correct today
   (one object, one instance), but it is the kind of assumption that a future
   change makes quietly false, and nothing asserts it.
3. **Probe 3's result is weak evidence, not a guarantee** — storage-only
   sequences were not observed interleaving, which is not proof they cannot.
   `#mutateState` is correct either way, which is why it re-reads regardless;
   `beginAttempt` is the one place resting on the weaker reading.
4. **The suite has a pre-existing unhandled error** (one test file uncounted,
   plus a "close timed out" on teardown) present before this step and unrelated
   to it. Not investigated.
5. Steps 19's open question 1 (the 0.00031777 BTC with no in-system home), 20's
   1–3, and 18's 2 and 3 all stand.
