## Step 22: The observability half — verifying the tick, recording the refusal, reaching the pass
Date: 2026-08-04

Steps 19–21 built the fill-observation path and made it safe to run
concurrently. Three things were left explicitly open at the end of 21, and this
step is those three: nothing verified that the tick a poll-observed fill waits
for is actually coming; a pass that identified a real problem and refused to act
wrote nothing durable; and `checkOpenOrders` was unreachable by a human.

### The deployment fact, and why it is at the top this time

Step 21 recorded, correctly at the time, that steps 19 and 20 were "merged and
deployed nowhere" and the races it fixed were "dormant, not live". **That is no
longer true, and it was checked against Cloudflare rather than carried forward
from the log.** Testnet deployed `2026-08-04T03:44:56Z`; step 21's commit
`6e575e7` landed `2026-08-04T03:44:34Z` — **22 seconds earlier**. So the whole
19–21 arc is live on testnet right now: the 30-second alarm is firing against
real bots, and the interleaving defences are load-bearing rather than
anticipatory. Production is untouched since `2026-07-24`.

This changes what this step is. Item 1 is not a nicety for a future deploy — the
poll it makes honest is running today, and step 21's "wait for the next tick"
is, until this lands, an unverified assumption in production-shaped code.

### 1. `lastPriceAt`, read for the first time

Step 21 decided that a poll-observed fill does not act: the poll has no price,
every action either strategy can take needs one, and `liquidatePosition` already
refuses `lastPrice` as a fallback and fetches fresh. That decision is right and
is unchanged. What it rests on is that **a next tick is coming**, and the log
recorded the gap plainly: "`lastPriceAt` is written and still read by nothing."

`#checkPriceFreshness` is that read, and it runs first in `#pollOpenOrders` —
before the empty-list return and before the yield — because it is derived from
this object's own state and clock and needs no exchange call. A pass that stands
aside for another has still observed the tick clock perfectly well.

**Why this is not a second copy of `price_feed_blind`.** The feed has its own
blindness machinery and it is good, but it is structurally incapable of seeing
this condition, in four separate ways:

- **`PriceFeed`'s staleness clock advances on any inbound frame, and it counts
  heartbeats.** `#lastMessageAt` moves on a `heartbeat` (it is recognised as
  liveness, deliberately, rather than dropped). So a socket heartbeating happily
  every ~5s while delivering no candles is **permanently fresh** to the feed.
  That shape is not hypothetical — step 14's deployed live check has a named
  verdict for exactly it (`connectionOpened: true`, `candlesUpdateReceived:
  false`).
- **Fan-out failure is invisible from there.** A subscriber whose RPC returns
  `"ignored"` is a *successful* RPC, so a bot that has silently stopped
  consuming looks healthy to the feed by construction.
- **A bot missing from the subscriber registry** gets nothing at all while the
  feed is entirely well.
- **`price_feed_blind` carries `bot_instance_id: null` by design** — it is a feed
  concern and the column is a foreign key — so it can never appear on a bot's
  page or gate a bot-level control.

Every existing check is per-socket and account-level. This is the only
end-to-end, per-bot one: *did this bot receive a price.*

#### The threshold: 10 minutes, and where the number comes from

From step 14's live probe (Q1/Q2), not a guess:

- heartbeats every ~5.0s (min 4.8 / max 5.2 over 71 samples), carrying no price;
- candle frames arriving **only on activity, 35–70s apart**;
- Q1 unanimous 6/6 **CURRENT-ONLY**: a closed candle is forwarded only when a
  frame carrying a *newer* `openTime` arrives.

So `lastPriceAt` advances once per forwarded closed candle, and the worst-case
gap between two forwards is the same arithmetic step 14 used to size its own
deployed 120s live-check window: up to ~60s to the minute boundary plus up to
~70s of quiet ≈ **130s**. Typical 30–70s.

**600_000 ms** is 4.6× that worst case — the same headroom discipline
`STALENESS_MS` already uses (20s = ~4 missed 5s heartbeats) — and about ten
consecutive one-minute boundaries with no forward. It also sits deliberately
**above the feed's own recovery envelope**: a dead socket is detected at 20s and
five reconnects run over ~31s, so a *recoverable* outage never reaches this
threshold, and this alert fires only on something the feed's machinery did not
fix.

Generous on purpose, because the costs are asymmetric: a late alert costs
minutes on a condition reconciliation still backstops, while a false one on a
genuinely quiet pair costs the alert fatigue step 18 measured at 186 identical
criticals in four hours.

`warning`/`system`, matching `poll_blind` — the same family ("a thing that
should be watching has stopped being able to"), and the message says what was
*observed* rather than diagnosing a cause this object cannot know.

#### Running-only, and the two consequences of that

`#onPriceUpdatePass` returns `ignored` before writing `lastPriceAt` for any
status but `running`, so a halted bot's price clock is **frozen by design**.
Checking one would alert on every halted bot with a resting order, permanently,
for behaving exactly as specified.

The useful half falls out free: a bot that halts while this condition stands
stops re-finding it, so its next pass resolves the row. A halted bot receiving
no prices is not a fault and the alert correctly stops claiming it is. **The
test for that had to be rewritten once**, and the rewrite is the interesting
part: it failed first because a clean halt cancels every order, empties
`openOrderIds` and disarms the poll — and the resolve half is gated on
`reads > 0`. So the row can outlive the condition, exactly as step 20's open
question 2 records for `poll_blind`, for the same reason and in the same safe
direction: only a pass that actually looked may close a row. The test now fails
the cancel on purpose, which is what leaves something to read. The source
comment overclaimed before that failure and was corrected with it.

A **null `lastPriceAt` raises nothing.** It means "running, no tick ever", there
is no `startedAt` in this object's state to measure an age against, and the
scheduled path cannot reach it anyway: every order-placing site sits inside
`#onPriceUpdatePass`, which writes the timestamp before deciding anything, so a
running bot with a resting order has provably seen a tick — and a bot with no
resting order arms no alarm. Only a manual call reaches it. See open question 1.

### 2. The audit gate, and making `refused` structural rather than arithmetic

`applied || closed` meant a pass that hit **`#foldTerminalState`'s quantity
gate** — the exact `bot-44400a` condition, an order that ended terminal on the
exchange with more filled than this bot recorded — wrote **nothing durable at
all**. Neither did an `OrderStateError`, nor an unattributable fill. Those are
the passes whose reasoning an operator most needs to reconstruct afterwards, and
the poll was recording only the ones where everything went fine.

The gate is now `applied || closed || refused`. The part worth recording is that
**`refused` is a list, not a subtraction.** It was derivable as
`skipped.length - unreadable`, which is true today purely because every
unreadable read happens to push exactly one line — an invariant nothing states
and nothing enforces. Every refusal now goes through a `refuse()` helper that
writes both lists, and `#foldTerminalState` takes that helper instead of the raw
`skipped` array, so the two cannot disagree.

**Unreadable passes are still deliberately excluded**, and that is the whole
reason the split has to exist rather than the gate simply reading `skipped`.
`skipped` holds both kinds; gating on it would write a row on every pass of an
outage — ~2,880 a day per bot at 30 seconds — saying "the venue is still down".
That condition already has a lifecycle built for it: the backoff, and one
standing `poll_blind`. Step 20 separated these two for this class of reason and
the separation earns its keep again here.

The audit row carries `refused` alongside the whole `skipped` list, so the row
says *why it was written* without losing the honest full account.

### 3. `POST /api/bots/:id/check-open-orders`

Thin, in the shape of `startBot`/`resumeBot`/`applyMissedFills`. What is worth
recording is the **gate on the dashboard control**, because it is deliberately
different from its neighbour's and the difference is the point.

`ApplyMissedFillsAction` renders only on an open drift **finding**: it writes
trades to correct a belief the system has just proved wrong, and §9's stance is
that such a correction needs a human acting on a specific finding.
`CheckOpenOrdersAction` renders on **capability** — not stopped, and something
resting — for two reasons:

1. It re-derives what is true right now rather than acting on a stored belief,
   and it is byte-for-byte the pass the alarm has been running unattended every
   30 seconds. A human pressing it introduces no operation the system was not
   already performing.
2. **It is needed exactly when no finding exists to gate on.** A blind poll
   raises `poll_blind`, not drift. Gating the recovery control on the machinery
   that is broken is the silent-gap-on-a-correction-surface failure 18.1's
   addendum refused to leave in a backlog, in a new place.

The control highlights itself, and the cross-bot alert feed links to it, when a
poll-health alert is open — the same "see an alert, act on it" path 18.1 built
for drift, with `repairable` winning where both could apply, since a bot with an
open drift finding has a decision waiting that outranks re-observing.

**The dialog says it can place orders, because it can.** On a *running grid*
bot a folded buy places its paired replacement sell, exactly as a live fill
would, because step 19 derives `placeReplacement` from `status === "running"`
rather than hardcoding it. That is correct — it is the grid recycling, and
suppressing it would leave the ladder silently short a rung — but it is also a
live order reaching the exchange from a button labelled "check", which an
operator must be told before pressing rather than after. Its sibling passes
`false` unconditionally, so the two genuinely differ and the copy states which
one this is. `deferred` gets its own outcome banner for the same honesty
reason it exists in the type at all: three empty arrays are indistinguishable
from a clean pass, and "I did not look" is not "your books are up to date".

**The alert-type strings moved to `shared/alert-types.ts`** as
`POLL_HEALTH_ALERT_TYPES`, and `POLL_STANDING_ALERT_TYPES` is now built from
them. The dashboard needs those three strings to decide when to surface this
control, and a hand-copied list there is precisely the failure that module was
created to end: a rename produces no error, no failing request and no 404, just
a control that quietly stops appearing on a bot whose observation has died.

### Tests

**22 new (1504 → 1526)**: 13 in `bot-instance.test.ts`, 1 in
`grid-bot-instance.test.ts`, 6 in `api.test.ts`, plus the guard rewrite. Backend
`tsc --noEmit` clean; dashboard `tsc -b && vite build` clean; full suite stable
across three consecutive runs. `FakeExchange` gained
`orderStatusFailureFor` — a per-order read failure, so the **mixed** pass (one
order unreadable, another refused) can be expressed at all; the existing
all-or-nothing flag cannot state it.

Six mutants, all caught:

| mutant | result |
| --- | --- |
| staleness checked on halted bots too | 2 failures |
| the audit gate stays `applied \|\| closed` | 3 |
| an unreadable read counted as a refusal | 2 |
| the staleness key never added to `standing` | 4 |
| staleness raised through `#alert` | 2 |
| threshold tightened to 60s | 2 |

Two of these are worth the space:

**The fourth is the self-resolving loop**, and it is why it fails four tests
rather than one. Raising without adding the key to `pass.standing` means the
next clean pass closes the row it just wrote, then re-raises it, forever — the
dedup silently becomes an unconditional insert with an extra write per cycle.
That is step 18's failure mode reached through the back door, and it is invisible
in any single-pass test.

**The sixth exposed a test that asserted nothing.** The first version of the
cadence test advanced the clock by 70s and *delivered a tick* before each pass,
so the measured age was zero every time — it would have passed at any threshold
whatsoever, including one second. The real shape is the poll firing *between*
ticks, so it now polls every 30s across the full ~130s worst-case gap with no
tick at all, asserting silence at each step. That version fails at 60s. Without
the rewrite, the one number this step was asked to justify had no test behind it.

**The fifth is caught by a guard that previously would not have caught it.**
`standing.test.ts`'s source-level check listed the three standing types by hand,
so a *fourth* was covered only if whoever added it also remembered to extend the
guard — and the entire purpose of that guard is that they did not remember.
`price_updates_stale` was exactly that fourth type. It now imports the real
exported set.

### Deliberately not done

- **No escalation tier for `price_updates_stale`.** `poll_blind` gets louder
  after 30 minutes; this raises one `warning` and stops. A second tier needs a
  second persisted flag and a second lifecycle, and the value is unclear while
  the first tier has never fired in anger. Recorded as a knob, not an omission.
- **The poll interval and the 5-failure threshold are still decisions, not
  measurements** (19.3, 20.1, unchanged). The staleness threshold is the first
  number in this arc that is derived from a real measurement.
- **Not deployed.** Everything here is committed and runs in the suite; nothing
  in this step has been run against the live testnet bots — unlike steps 19–21,
  which now have been.
- **`applyMissedFills` and the halt-sweep interaction still untouched**, at the
  operator's standing direction (step 19).

### Is the fill-observation effort (19–22) complete?

**The effort as scoped, yes.** A fill on a resting order is observed (19), on a
schedule (20), safely under concurrency (21), with the tick it defers to now
verified, its refusals recorded, and the pass reachable by a human (22). Every
"deliberately not done" item that steps 19–21 assigned to step 22 is closed.

**Three things are genuinely still open**, and none is a loose end of this step
so much as a boundary it declined to cross:

1. **A poll-observed fill still does not drive a decision within the pass** — it
   waits for the next tick. That remains the right call and is now a *sound* one
   rather than a hopeful one, which is what this step was for. It is not the
   same as "the fill is acted on immediately".
2. **`bot-44400a`'s 0.00031777 BTC still has no in-system home** (19.1). Nothing
   in this arc was ever going to recover it.
3. **Nothing here has run against a live bot.** Steps 19–21 are deployed as of
   this morning and have not been observed in production use; step 22 is not
   deployed at all.

### Open questions

1. **A running bot that never receives its FIRST tick is still unmonitored.**
   `lastPriceAt` null raises nothing (above), and the poll never runs on such a
   bot because it has no open orders to arm the alarm — which is the same
   condition, since it cannot place its base order without a price. Closing it
   means either a `startedAt` in runtime state or arming the alarm for every
   running bot regardless of open orders, and the second is a materially
   different draw on the timer budget. This is a real gap, deliberately not
   closed here.
2. **`price_updates_stale` can outlive its condition**, exactly as 20.2 records
   for `poll_blind`: a bot whose orders all close while it is stale keeps an
   open warning until it places another order and polls again. Same rule, same
   safe direction.
3. **The staleness resolution is gated on the venue being readable**, because
   the resolve half is one call covering every type this object owns. So a feed
   that recovers while the exchange is unreachable leaves the row open longer
   than the condition lasted. Consistent with §5.6 and the safe direction, but
   it is a coupling between two independent conditions and worth naming.
4. **The threshold is derived from Gemini BTCUSD-shaped activity.** All four
   live bots are Gemini today, but "35–70s between candle frames" is a
   liquidity-dependent measurement, and a genuinely thin pair could sit quiet
   past ten minutes without anything being wrong. The first false positive is
   the signal to revisit, and the constant is one line.
5. **Step 21's open questions 1–4 all stand** (poll-vs-poll unguarded,
   `#passesInFlight` per-instance, probe 3's weak evidence, the suite's
   pre-existing uncounted test file and teardown error — still present, still
   uninvestigated, `60 passed (61)`), as do 19.1, 20.1–20.3, and 18.2–18.3.
