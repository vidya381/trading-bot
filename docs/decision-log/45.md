## PART 1 — THE STORAGE SHAPE

### 21.5 names `audit_log`, and `audit_log` is the wrong answer

The requirement says the record *"mirrors this project's decision-log discipline and
its `audit_log` practice (section 8.2)"*, so the obvious reading is that a proposal
should simply BE an `audit_log` row with a fat `details_json`. That reading was
traced through every one of the table's real writers — `capital/ledger.ts`,
`watchlist.ts`, `circuit-breaker.ts`, `kill-switch.ts`, `reconcile.ts`,
`bot-instance.ts`, `placeholder-balance.ts` — rather than dismissed on taste, and it
does not work. Four findings, in descending weight:

**1. A PROPOSAL HAS A LIFECYCLE; AN AUDIT ENTRY IS AN EVENT.** The outcome is
knowable only LATER, when a human acts or never does, so recording it means
UPDATING the record. **Not one `audit_log` writer in this system has ever updated a
row** — every one only INSERTs, and that append-only property is precisely what
makes the log trustworthy for every other reader. Adding an outcome by rewriting a
past entry would break it for all of them, to store a fact about one feature.

**2. `Repository` CANNOT FILTER ON A JSON COLUMN, BY DESIGN.** `/src/db/table.ts`
throws `unsupported_filter` on the attempt, with its reasoning inline. `audit_log`
has no `account_label`, no `pair` and no `stage` column, so *"every proposal for
this account"*, *"every proposal on this pair"* and — decisively — ***"every
proposal nobody acted on"*** would all be unaskable questions. That last one is the
specific measurement 21.5 exists to make possible.

**3. EVERY READ OF `audit_log` WOULD PAY FOR THE PAYLOAD, AND THE COST WAS
MEASURED RATHER THAN ESTIMATED.** `Repository.findMany` always selects the full
generated column list; there is no projection anywhere in the layer. A test builds
the deepest payload this pipeline can produce — a 1,440-candle window plus the
23,383-character Derive prompt entry 41 measured — and reports **290,459 bytes**.
In `details_json` that is what `listReconciliationRuns` (the one endpoint that
already queries `audit_log`, by `action`) would drag on every unrelated read. Every
other `details_json` in this system is a handful of scalars.

**4. THE OUTCOME LINK NEEDS A REAL, CONSTRAINED REFERENT.** `POST /api/bots` now
accepts an optional `proposalId`. A foreign key into `audit_log` would point at a
table where any row of any action could be named, so `proposalId` would be a CLAIM
rather than a reference, and `approval_names_a_bot` would have nothing to constrain.

**So: a dedicated table for the RECORD, and an `audit_log` row for the EVENT**,
written through the existing `db.auditLog` path in ONE `Database.batch`. That is
exactly the shape migration 0008 established for the watchlist — *"the row and its
audit entry go in ONE batch, so a watchlist entry with no record of who added it is
not a state this table can reach"* — and **there is deliberately no second audit
mechanism.** The audit entry carries a POINTER, never a copy; the operator measured
a real one at **273 bytes**.

### Two rows per run, not one, and one link deliberately absent

`/assess` and `/derive` are two separate HTTP calls that each perform their OWN
fresh gather — entry 42's decisive check 5 proved it, with the same evidence id
resolving to 63775.31 and 63757.71 ten minutes apart. Their inputs are therefore
genuinely different data, and one row carrying "the" inputs would have to pick one
gather and silently discard the other. `stage` (`assess` | `derive`) distinguishes
them, and **each row is INDEPENDENTLY COMPLETE** — its own bundle, its own prompt,
its own raw model response — so requirement 5's *"trace back to its exact cause"* is
satisfied by either row alone.

⚠ **WHAT IS NOT LINKED, stated rather than left to be found: a `derive` row does NOT
carry the id of the `assess` row it derives from.** Nothing in the request carries
that link, and an `assessProposalId` taken from the caller would be a
client-asserted claim this system cannot verify — the same class as `envelope` and
`duplicateKeyCheck`, which `assess-resubmit.ts` carries only because refusing to
carry them would mean inventing an audit fact. Nothing needs the join today, and the
resubmitted assessment is stored verbatim on the derive row, so the two are
reconstructable by content.

### `ignored` is deliberately NOT a stored value

21.5 names three outcomes. Only two — `approved` and `rejected` — are DECISIONS a
human makes and a system can witness. **"Ignored" is an ABSENCE**, and nothing
observes a human failing to act.

Storing it would need either a cron sweep flipping pending rows after some deadline
(inventing a deadline nothing defines, and rewriting history to record a non-event),
or a human clicking "ignore", which is a rejection under a softer word. So the
column holds NULL until a decision is recorded, and **`outcome IS NULL` IS 21.5's
"ignored"**, read after the fact. That needs no threshold and no sweep: the signal
the requirement asks for is *"the system kept proposing things nobody wanted"*, and
a NULL that stays NULL is precisely that. `idx_proposals_unresolved` is the partial
index for counting it.

⚠ **The honest qualification:** a proposal made thirty seconds ago also has a NULL
outcome, so the count is only meaningful over rows old enough that a human would
have acted, and **no threshold is invented for that either** — the same stance
`dashboard/src/proposal.ts` takes on the absent liquidity test. A stated gap is a
limitation; an unstated one is the failure mode.

### Automatic on every real call, and a failed write FAILS the request

There is no `?log=true`, no separate action to invoke, and no way to run either
endpoint without producing a record. The signal 21.5 wants is a RATE over proposals
GENERATED, and an opt-in denominator is *"the runs someone chose to log"* — which
are systematically the interesting ones, so the measurement would be biased in
exactly the direction that hides the failure. It is the same objection `assess.ts`
raises against a retry loop: an answer selected FOR passing a check is fail-open
wearing the costume of reliability. It is also the convention every other
consequential write here already keeps, none of which takes a parameter that turns
it off.

⚠ **A FAILED D1 WRITE FAILS THE ENDPOINT, AND THE MODEL CALL HAS ALREADY BEEN PAID
FOR** — 10–47 s of latency and ~490–1,270 neurons per entry 41. The record cannot be
written before the thing it records exists, so that cost is unrecoverable. It is
still right on requirement 6's terms: the alternative is returning a proposal that
is NOT in the permanent record, to a human with no way to tell, which is a degraded
result indistinguishable from a good one. Returning it with a warning is not
available either — requirement 3 already refuses that shape for validation (*"not
shown with a warning, not shown greyed out with an 'approve anyway' affordance"*).

**A refused run writes NO row.** `assessCandidate` and `deriveParameters` catch
nothing, so a parse refusal, a validator refusal, a stale resubmission or a missing
precondition throws before this module is reached, and there is deliberately no
`catch` to change that. That is 21.5's own wording followed exactly — *"every
PROPOSAL generated"* — and a refusal generated none. **See PART 8 for the
consequence.**

### `/gather` writes no row, and that is the measurement working

**A DEVIATION from the brief for this step, recorded as one.** `/gather` produces no
reasoning, no strategy, and nothing a human could approve or reject — it is Stage 1,
deterministic, with no model in it. Three of this table's columns would have nothing
truthful to hold for it.

The decisive argument is the measurement above: gather rows could never be acted on,
so they would enter the "nobody acted" numerator forever and inflate it without
bound, destroying the one signal this table exists to produce. **Nothing is lost,
and that is checkable rather than asserted:** every logged row carries the FULL
gather bundle in `inputs_json`, because both endpoints gather and store it. A
gather's data is in the record; a gather is not a proposal.

## PART 2 — THE OUTCOME LINK

### Why it had to be built now rather than deferred

Before it, **nothing connected a real create-bot action back to the proposal that
suggested it.** `proposals.outcome` could therefore only ever hold `rejected` and
NULL, and *"the system kept proposing things nobody wanted"* would have had no way
to distinguish a proposal nobody wanted from one that became a real bot. **A
permanent record whose outcome column can never say `approved` is permanently
incomplete for its own stated purpose.**

### ⚠ IT IS NOT A NEW PATH TO A BOT, AND 21.1 IS UNTOUCHED

Worth stating precisely, because a field connecting a proposal to a bot creation is
exactly the shape 21.1 is suspicious of. `proposalId` changes NOTHING about how the
bot is created: every parameter still arrives in the body, typed or confirmed by a
human; every decoder, the mandatory stop-loss, the tradability gate, the
spot-instrument check and the ledger's binding compare-and-swap all run unchanged
and unweakened. **NOTHING is read out of the proposal record and used as an input** —
the record is written to, never read from except to check it can take an outcome.

A field that PREFILLED the form from a stored proposal would be the one-click bridge
21.1 forbids. This one only records, after the fact, that a human did the work
themselves. **The proposal cannot supply a value, so it cannot supply a wrong one** —
and a test submits a body that deliberately DISAGREES with the proposal and asserts
the bot gets the body's numbers.

### Checked last, and the one failure that cannot move earlier

`checkProposalCanTakeOutcome` runs with the other free checks, **before** the
tradability gate and long before `create` — `createBot`'s own documented "FREE
CHECKS FIRST, NETWORK LAST" rule. An unknown id, an already-resolved proposal, an
`assess` record, or one belonging to a different account therefore refuses the
request while **nothing has happened**: no capital reserved, no row written, no
Durable Object brought into existence. The property is not "creation is refused" but
"NOTHING HAPPENED", which is the standard `assertBotPairIsSpotTradable` is held to.

⚠ **The outcome WRITE cannot move earlier.** `outcome_bot_instance_id` is a foreign
key and `approval_names_a_bot` requires it, so the row it names must exist first — a
link to a bot that does not exist yet is the fabricated audit fact
`assess-resubmit.ts` refuses to manufacture. By then a real bot exists, capital is
reserved, and orders may follow within the minute.

**So that one failure is REPORTED, not raised.** The endpoint still returns 201 with
`proposalLink.recorded: false` and the real error in the body. Failing the response
would tell an operator that creation failed when it did not, and the recovery they
would attempt — creating it again — is the worst available action. **This is
`undoReservation`'s precedent (`capital/ledger.ts`), which handles a post-commit
failure the same way and for the same reason.** The fail-closed rule of PART 1 and
this soft failure are not inconsistent: one write happens before anything
irreversible, the other after.

`proposalLink` is **ABSENT rather than null** when no proposal was named, so an
ordinary creation's response shape is byte-identical to what it was before.

### `POST /api/proposals/:id/reject`, and why it exists now

Curl-only, like every other section 21 surface. It exists NOW, with no dashboard
control, for a schema reason rather than a product one: `outcome`'s CHECK constraint
had to name its values at migration time because **SQLite cannot alter a CHECK
without rebuilding the table** — which for THIS table would mean rebuilding the
permanent record it exists to keep. A value with no possible writer would be exactly
the check that cannot fire: **step 37 refused one** (the duplicate-key "theatre")
and **step 41 refused another** (a `minNotional`-only floor that would have passed
every proposal forever on the only venue this system runs against, while reading in
review like a floor).

⚠ **EITHER STAGE MAY BE REJECTED; only a derivation may be approved.** That
asymmetry is the point of keeping Stage 2 rows at all: rejecting an assessment
records that a human read a strategy judgement and chose not to spend a Derive
inference on it, which is the cheapest real signal this feature produces.

**The consequence, stated: outcome counts are only meaningful GROUPED BY `stage`.**
Pooling them would compare a population that can be approved against one that
structurally cannot.

### The constraints are DATABASE facts, not application conventions

Four CHECKs, and each is tested by writing PAST the repository with raw SQL —
because otherwise deleting the code check would leave every test green:

| constraint | what it forbids |
| --- | --- |
| `outcome_is_recorded_whole` | a half-recorded decision — an actor with no verdict, a verdict with no time, a note with no decision. The shape `halt_requires_reason` (0001), `tripped_requires_reason` (0003) and `removal_is_recorded_whole` (0008) already use |
| `approval_names_a_bot` | `approved` with no bot named |
| `rejection_names_no_bot` | `rejected` naming one, since none was created |
| `only_a_derivation_can_be_approved` | approving an `assess` row — it has no parameters, so no bot could have come from it |

⚠ **Those raw-SQL tests live in `/src/db/constraints.test.ts`, not beside
`proposal-log.ts`'s own**, and that placement was forced rather than chosen:
`no-raw-d1.test.ts` fails the build on `.prepare(` outside `/src/db`, so /src/db is
the one place the write can be made. **Both halves are needed** — without the code
tests a refusal arrives as an opaque SQLite error; without the constraint tests the
code check is the only thing between a mis-wired caller and a false record.

### Retention: section 8.7 applies here unchanged, and structurally

- **NO DELETE PATH EXISTS**, and structurally rather than by intention: `Repository`
  offers no `delete` method at all, and `no-raw-d1.test.ts` fails the build on any
  file outside /src/db reaching past it. A test asserts the absence on the real
  repository object, so a future widening of the access layer fails where the
  retention promise is written down.
- **NO SOFT-DELETE COLUMN EITHER.** Unlike `watchlist.removed_at` and
  `bot_instances.archived`, nothing about a proposal record is meant to leave the
  set, so there is deliberately no equivalent — and a test asserts that absence
  rather than leaving it to be noticed.
- **NO SUMMARIZATION.** The full inputs and full reasoning are stored as they were.
- **The ONE mutation is NULL → an outcome, once**, written with `outcome IS NULL` in
  the UPDATE's WHERE clause so the `changes` count IS the decision — the
  `setArchived` / capital-ledger idiom. No stored fact is ever overwritten.

## PART 3 — THE FOUR STALENESS THRESHOLDS (21.5 requirement 4)

Entry 44 satisfied the timestamp half and left the flagging half open, stating the
absence on the page rather than inventing a number in a rendering layer. Spec 21.7
open question 4 is exactly this gap: *"What 'a meaningful delay' is … is unset, and
should probably differ by strategy (a grid's bounds go stale faster than a DCA's drop
percentage)."*

| input | threshold | the dependency, which is what the number is grounded in |
| --- | --- | --- |
| price history, **grid** | **15 min** | `upperBound`/`lowerBound` are ABSOLUTE PRICES. Every live derivation this project has produced bracketed its own derive-time close (entry 42: 62660.91 < 63757.71 < 64036.14). Once price leaves the ladder the bot created is not the one reviewed — it places the whole ladder on one side, or nothing |
| price history, **dca** | **60 min** | Every DCA parameter that decides BEHAVIOUR is RELATIVE — `dropPct`, `stepMultiplier`, `takeProfitPct`, `stopLossPct` apply to whatever price the base order actually fills at. Nothing in `DcaParams` names an absolute price |
| capital ledger | **1 hour** | `allocatedCapital` is a PREFILL (entry 41); the BINDING check is `createBotInstanceWithCapital`'s compare-and-swap at creation. A stale figure makes a form fail validation, not a bad bot |
| bot list | **24 hours** | Changes only by human action — this account moved 11 → 13 bots across the whole of entries 34–41 |
| venue rules | **7 days** | Slowest-moving. The real filter check happens at order time (`validateOrder`, section 4.3) regardless of what this says |

### ⚠ READ THIS BEFORE QUOTING ANY OF THESE NUMBERS AS THOUGH IT MEANT SOMETHING

They are **POLICY CHOICES**, in exactly the category `DEFAULT_CONCENTRATION_POLICY`
(`concentration.ts`), `VERIFIED_INTERVALS` (`candles.ts`) and
`DERIVATIVE_NAME_SUFFIXES` (`tradability.ts`) already occupy: **no backtest supports
them, no volatility model produced them, no market data was consulted, and no
operator has yet said they are the right numbers.** They are named, in one place, so
that changing them is a visible edit rather than a tuning session.

What the reasoning supports is the **ORDERING** and the rough **RATIO**. The
absolute values it does not. A different operator would defend 5 and 30, or 30 and
120, just as well.

⚠ **THE ONE PIECE OF REAL DATA WAS DELIBERATELY NOT USED AS EVIDENCE.** Entry 42
measured `candles.last_close` moving 17.60 over 600 s. That is a real observation
about the **GEMINI SANDBOX**, whose data entry 40 found is not a real market — a
series that sat at one price for 83 minutes. Quoting it as evidence about how fast
bounds go stale would be exactly the sandbox mistake entry 40 warns about. The
600 s figure informed only the ORDER OF MAGNITUDE of the grid threshold, so that an
ordinary two-call review does not trip it.

⚠ **DCA IS NOT PRICE-INDEPENDENT**, and 60 minutes rather than "no threshold"
because of it: `baseOrderSize`/`additionalOrderSize` are absolute quote amounts, and
`derive-parse.ts` evaluates the minimum-order check at the newest real close. An
hour bounds the drift on a check whose backstop is `validateOrder` at order time,
rather than pretending the dependency is absent.

### Why four thresholds, and why `oldest` is NOT the cheap version of this

`freshnessOf` already computes the stalest fetch, so comparing THAT against one
number looks equivalent. It is not, and the difference is the whole design — the
thresholds span **15 minutes to 7 days**, nearly three orders of magnitude:

- A 2-hour-old venue-rules fetch is very likely the `oldest` of the four and is
  nowhere near stale.
- A 20-minute-old price fetch on a GRID proposal IS stale, and is almost certainly
  NOT the oldest.

**Both cases a single-threshold implementation gets backwards are pinned by tests**,
in the policy module and again through the dashboard's rendering path.

### Three states, not two

An input that never produced a value has no fetch time, so there is nothing to
compare and it is `unknown` — **neither fresh nor stale.** That is section 5.6's rule
applied to time, and the same distinction `MinimumOrderCheck`'s `none_published` and
`DuplicateKeyCheck`'s `unavailable_transport_parsed` both exist to preserve: a
guarantee that could not be checked is reported, never faked. `stale` outranks
`unknown` outranks `fresh`, and an EMPTY input set is `unknown` rather than fresh.

### `staleness.ts` has NO IMPORTS, and that is load-bearing

The dashboard imports it **directly** — the fourth file to cross that seam after
`src/shared/alert-types.ts` (18.1 addendum), `src/shared/money.ts` (step 25) and now
`src/research/proposal-shape.ts`. It earns the crossing on their terms:
dependency-free by contract, so both toolchains compile it unchanged despite the
deliberate TypeScript 5.7 / 7 split, **verified by building rather than assumed.**

The alternative was a documented MIRROR, the way `dashboard/src/derive.ts` mirrors
`applyPercent`. **A mirror is exactly what fails silently here.** A diverged
threshold would not throw and would not fail to compile — the page would simply show
"fresh" about a proposal the policy calls stale, on the screen read to decide whether
to commit capital. Not having a second copy closes that better than testing one does.

⚠ The cost, stated: `staleness.ts` cannot import `StrategyType` from
`/src/db/schema` (it would pull the Worker's D1 types into the dashboard's `tsc -b`
and break it — the failure `dashboard/src/derive.ts` already records). It declares
its own two-member union, **pinned to `StrategyType` by a two-way type assertion in
its test**, so the pair is a compile error to diverge. **Adding ANY import to that
file breaks the dashboard build.**

## PART 4 — ⚠ THE MUTATION HARNESS WAS LYING, AND THAT IS THE LESSON OF THIS STEP

**Found during this step's own development, before any live verification.**

The first two mutants run against the logging write path — both making a row stamp
the WRITE time instead of 21.5 requirement 4's FETCH time — were reported as
**SURVIVED**. That would have been a serious finding: the requirement's central
field, unprotected.

It was false. The harness detected failures with:

```
grep -oE "Tests  [0-9]+ failed"
```

**vitest wraps the failure count in ANSI colour codes on the FAILING path and not on
the passing one.** So the grep matched nothing whenever a mutant was caught, `FAILED`
came back empty, and the harness printed SURVIVED for exactly the mutants that had
been detected. A harness that reports the opposite of the truth is worse than no
harness, and it fails **silently and in the safe-looking direction**.

**It was found by manually reproducing one** — applying M1 by hand, confirming the
mutation was present in the file, and running the tests, which failed 3 tests. Only
then was the harness the suspect rather than the code.

The fix strips ANSI, cross-checks **vitest's real exit code**, and **refuses to
report at all when the two signals disagree** (`HARNESS-ABORT`) rather than guessing.
**Every mutant in this step was re-run under the fixed harness**, and the numbers
below are from those runs only.

⚠ **This is the same class of error entries 10.14, 41, 42 and 44 each recorded** —
41's `perl -0p` mutating a docblock instead of a code line, 42's `void x;` no-ops
that mutated nothing, 44's grep-after-apply rule. The standing rule was *"the
harness must be verified to have landed before its result is trusted."* **This step
extends it one layer: the harness's own REPORTING must be verified too, because a
mutation that lands and is caught can still be reported as surviving.** The rule now
has a matching implementation — the harness aborts rather than guesses.

The same lesson arrived a third time while re-establishing state after an
interruption: a hand-written script checking that five exports existed reported all
five MISSING, because its pattern did not allow for `export async function`. Recorded
because the reflex it argues for is the same one, and because a false alarm reported
is worth more than a false alarm quietly dropped.

## PART 5 — ⚠ THE REAL RENDERING BUG: A BLANK BLACK SCREEN, FOUND LIVE

**Found by the operator, mid-verification, in a real browser.**

### What happened

A hand-constructed test file carrying `strategy: "dca"` over GRID-shaped params
reached `<ProposalParameters>`, which read `params.baseOrderSize` (absent), handed
`undefined` to `formatMoney`, and threw out of `roundDecimal`
(`dashboard/src/format.ts:31`):

```
TypeError: undefined is not an object (evaluating 'value.startsWith')
```

React's default behaviour on an uncaught render error is to unmount the whole tree,
so **the entire page went blank and black with no visible error at all** — the worst
available outcome, because it is indistinguishable from a page that has not loaded,
from a routing bug, and from a backend outage. The operator had no way to tell which.

### Root cause, stated precisely

`fieldsFor` dispatched on `params.strategy` and then read that strategy's fields
**on the assumption that they were there.** No defensive check that a params object's
fields actually match what its own strategy label implies.

### ⚠ A REAL BACKEND RESPONSE CANNOT PRODUCE THIS, AND THAT IS NOT A REASON TO SKIP THE CHECK

The mismatch is unrepresentable in three independent places: `DERIVE_MODEL_SETTINGS`
sends a per-strategy JSON schema naming exactly one strategy's fields;
`requireExactFields` refuses a response with any field missing or extra; and
`validatedProposalView` builds from a discriminated union on
`ValidatedProposal.params.strategy`. **The crash was reached by a hand edit, not by
anything this system can generate.**

The check is still right, for the reason the page exists at all: **the proposal
view's input is PASTED** (entry 44 — it makes no network request, by design), so it
is untrusted text in exactly the sense a resubmitted assessment is.
`parseResubmittedAssessment` does not skip validating a resubmission because a
well-behaved client would have sent a good one, and this does not skip validating a
paste for the same reason. **What the backend guarantees about its own OUTPUT says
nothing about what arrives in a textarea.**

### The fix, and why it reuses an existing banner rather than inventing one

`checkParamsShape` (`src/research/proposal-shape.ts`) runs FIRST, and a mismatch
renders **the same red `role="alert"` banner `ProposalStrategy` already renders for a
Stage 2 / Stage 3 strategy disagreement.** That is not a styling coincidence: both
are the same category of fault — **PASTED INPUT WHOSE PARTS DO NOT AGREE** — and only
the manifestation differs. One is two labels disagreeing; this is a label disagreeing
with the object underneath it. A reviewer should recognise it as one thing rather
than learning a second convention.

**The field lists are the backend's own** — `GRID_DERIVE_FIELDS` /
`DCA_DERIVE_FIELDS` from `derive-prompt.ts`, spec 21.4 Stage 3's own quotation —
imported directly, not mirrored. A mirror here is worse than usual: a diverged copy
would not fail to compile and would not throw; it would **refuse a good proposal, or
pass a bad one straight through to the crash the module exists to prevent.**

**Pinned two ways.** Against those spec lists, and — the pin that matters — against
the real key set `validatedProposalView` emits when driven over a real
`DeriveResult`. **The component reads the VIEW's output, not the prompt's field
list**, and those are separately hand-written; their agreeing today is a fact worth
checking rather than assuming.

**Two rules the fix turns on:**

- **`null` is present; `undefined` is missing.** The view emits `null` for an unset
  optional (`takeProfitAmount`, `breakoutThresholdPct`) and never omits the key. A
  rule accepting "absent or null" would let the original crash straight through.
- The presence test is `Object.hasOwn` AND `!== undefined`. Neither half is
  redundant: `hasOwn` alone accepts `{ baseOrderSize: undefined }`, which is the
  exact crashing value.

### Defence in depth: the error boundary

`ErrorBoundary` wraps the parameters section, the evidence section, **and the whole
proposal** — nested, so a reader who loses one block keeps the concentration flag,
the limits, the freshness verdict and the evidence, and can see in place which part
failed. It is deliberately OUTSIDE the textareas, so a crashing paste never removes
the inputs needed to fix it — which was the practical problem with the blank screen:
the operator could not re-paste without reloading and losing both bodies.

It does not retry or "recover": a render that threw produced no trusted output, and
re-running it against the same input produces the same throw.

Its pure half is `dashboard/src/renderError.ts`, and **it must never throw** — it
runs where nothing is left to catch a second failure. 13 throwable shapes are driven
through it, including the null-prototype object whose `String()` conversion throws
(**a bug this project already hit once**, recorded in `api.test.ts`) and a circular
object that defeats `JSON.stringify`.

### ⚠ TWO REAL GAPS THE FIX ITSELF FOUND, BEYOND THE REPORTED BUG

**(a) The first definition of "unexpected field" was wrong, and its own test caught
it.** "Belongs to neither strategy" meant that an object carrying **BOTH**
strategies' fields — the shape a naive merge of two responses produces — satisfied
grid's list, had no field from outside the union, and **PASSED**. It would have
rendered as a grid bot while **silently dropping a complete DCA description sitting
in the same object.** Closed by measuring extras against the CLAIMED strategy's exact
field list, which is `requireExactFields`' own rule: a field set is exact, and extra
is as much a fault as missing.

**(b) A mutation test found the guard's own CALL SITE unreachable by any test.**
`checkParamsShape` was covered exhaustively, but the one line that CALLED it —
`shape.ok ? fieldsFor(...) : []` — lived in a `.tsx`, and **React's CJS build does
not resolve in the Workers runtime this suite runs in**, so a test importing it
collects **ZERO tests rather than failing loudly.** A mutant that deleted the guard
and restored the original crash **SURVIVED.**

**A guard whose call site nothing can check is most of the way to no guard.** So the
decision moved to `dashboard/src/proposalFields.ts`, which returns the check and the
field list **TOGETHER**, making "refused but rendered" **structurally
unrepresentable rather than merely untested** — a failing check comes back with an
empty field list, so there is nothing for a component to render. That mutant is now
caught by 13 tests, and `ProposalParameters` is presentational.

Three smaller crash routes were closed while there, each named rather than folded in:
the `Strategy` cell now renders the CHECKED value (a pasted object there throws
"Objects are not valid as a React child" — another route to the blank page);
`MINIMUM_ORDER_COPY` gained a fallback so an unrecognised value cannot silently drop
the sentence about whether a floor was checked; and the `unknown`/`stale` distinction
is rendered with words as well as colour, for `ProposalCitations`' reason.

⚠ **What is NOT closed:** the three top-level money fields (`referencePrice`,
`availableAtProposal`, `allocatedCapital`) sit OUTSIDE the params object, so a
truncated paste can still crash on them. That is now contained visibly by the
boundary rather than blanking the page — the designed defence-in-depth split. Ad-hoc
guards for three fields were deliberately not added, because that invites "why not
every field" and the boundary is the general answer.

## PART 8 — WHAT IS STILL NOT DONE, EXPLICITLY

- ⚠ **DCA HAS STILL NEVER BEEN EXERCISED BY A REAL MODEL CALL.** Every live
  derivation this project has produced is grid — entry 41's two, entry 42's one,
  entry 44's render, and this step's. A **synthetic DCA-shaped fixture** was
  constructed here, and it is used **only to pin the shape-check logic and the field
  lists**; it is **explicitly NOT claimed as verification of the DCA path**, and it is
  labelled as such in three places in the source. Closing entry 44's assumption 1
  needs an actual live Derive call that happens to answer `dca` — not a hand-built
  object, and not a grid response with its label edited (which is now precisely what
  the shape check refuses).
- ⚠ **THE REFUSAL RATE IS NOT MEASURABLE FROM THIS TABLE.** A failed model call, an
  unparseable answer, a stale resubmission and a failed precondition all write **no
  row**, because 21.5 logs every *proposal generated* and a refusal generated none.
  How often the model answers unusably is **the other half of "how good is this
  feature"**, and it is invisible here. Deliberately deferred: a failure record has
  different columns — a code, no strategy, no outcome — and would be **a different
  table**, not nullable fields on this one.
- **NO COMPONENT OR JSX TESTS EXIST.** No render test, no snapshot, no DOM assertion:
  still no jsdom or testing-library in this project's toolchain. `react-dom/server`
  was probed in the Workers pool and **both `server.edge` and `server.browser` fail
  on their CJS requires**, and React itself does not resolve either — so a test
  importing a `.tsx` collects zero tests rather than failing. Prominence, ordering,
  colour and the boundary's CATCHING are verified by the operator's eyes and by
  nothing else. What is no longer eye-verified is every DECISION behind the render:
  `proposal-shape.ts`, `proposalFields.ts`, `staleness.ts` and `renderError.ts` are
  all React-free and all tested.

### ⚠ THE RECORD MAKES NOTHING TRUE THAT WAS NOT TRUE BEFORE

Carried forward from entries 40, 41, 42 and 44 **without dilution**, because a step
that finally satisfies a long-open requirement is exactly when it is most likely to
be lost.

**A permanently logged proposal is not a good proposal.** Every check behind these
rows answers *"is this internally consistent, currently grounded, and acceptable to
the real create-bot validators?"* **Not one answers *"was the data worth reasoning

nothing can delete. The human in 21.1 is still the only part of this loop that can
tell a well-grounded proposal from a good one.
