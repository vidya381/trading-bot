## ⚠ PART 0 — THE ONE BEHAVIOUR CHANGE VISIBLE OUTSIDE THIS SYSTEM

**A second `POST /api/bots/:id/close` now returns `200` with
`action: "already_stopped"`. It used to return `409 bot_already_stopped`.**

This is called out first, on its own, because it is the only change here that an
API consumer can observe and the only one that is not purely additive. It is
**not** a side effect of the reliability fix; it is a decision taken knowingly,
and it was put to the operator before the work started.

- **What did not change, and is the property the old 409 existed to protect:**
  no capital moves twice. `releaseBotCapital`'s conditional update
  (`status <> 'stopped'`) is the mutual exclusion and it is **untouched**. It
  still refuses the second release; exactly one `capital.released` audit row is
  ever written. `src/api/api.test.ts`'s "never releases the same capital twice"
  still asserts precisely that.
- **What changed:** the refusal no longer **aborts the cleanup steps that follow
  it**. `#closePass` catches `CapitalError` with code `bot_already_stopped` —
  that code and no other — and continues to the state write, the halt-alert
  resolve, the audit row and the feed unsubscribe.
- **Why:** a close that threw partway through its own cleanup left a `stopped`
  bot with an order uncancelled, no audit row and a live feed subscription — and
  **every retry died on the release line before reaching any of it**. The bot
  could not be finished by any code path that existed. Making the retry
  corrective is the entire point.
- **Which errors still propagate untouched:** `release_exceeds_allocated` (the
  ledger and the bot rows disagree about real money), `unknown_bot_instance`,
  `allocation_conflict`. Only the "already done" case continues.
- **How a caller tells the two apart:** `result.action` is `"closed"` on the
  call that actually released capital and `"already_stopped"` on a
  cleanup-only pass.
- **Where it is documented for a reader who did not diff `handlers.ts`:** the
  `closeBot` header carries a `⚠ BEHAVIOUR CHANGE` block; `dashboard/src/api/`
  `client.ts` and `types.ts` say the same in their close comments; and this
  section.

## PART 1 — THE INCIDENT

A stop-loss halt on **`bot-xs0ufw`** (2026-08-24) wrote `status = 'halted'` and
`halt_reason` correctly, and then:

- left a **sell order uncancelled**;
- wrote **no `bot.halted` audit row**;
- left the bot **still subscribed to its `PriceFeed`**.

That combination is consistent with a throw between the durable status write and
the cleanup that follows it — cancellation, mirror, alert, audit, unsubscribe.

**The shape of the bug is not the specific throw.** It is that those five steps
were sequenced as bare `await`s. Each is **independent of the others**:
cancelling orders does not need the audit row, unsubscribing does not need the
mirror. Sequencing them that way let the first failure decide how much of the
halt happened — a decision none of them is entitled to make.

**The status write itself is not the problem and is not wrapped.** `#halt`'s
header argues for marking halted *before* cancelling, precisely so a crash
leaves a halted bot with live orders (visible, alerted, safe) rather than a
running bot with some orders cancelled. That ordering is correct and is kept.

## PART 2 — THE FIX

### `#cleanupStep`

One private helper runs a step, catches its throw, alerts
`cleanup_step_failed` (critical), and returns the step's name. Callers collect
the names and report them.

**The dividing line is "already committed".** A step belongs behind
`#cleanupStep` only if the transition is correct without it. So:

- **`#halt`:** wrapped — `#cancelOpenOrders`, `#mirrorStatus`, the halt alert,
  the audit row, `#unsubscribeFromFeed`. **Not wrapped** — the `#mutateState`
  status write.
- **`#closePass`:** wrapped — the stopped-state write, `resolveHaltAlerts`, the
  audit row, `#unsubscribeFromFeed`. **Not wrapped** — `releaseBotCapital`
  (except for the one tolerated code in PART 0) and, before it, the cancel sweep
  and the `orders_unresolved` gate, which run *before* the point of no return
  and whose whole job is to refuse.

### `PipelineResult.detail`

When every step ran, `detail` is unchanged — the halt reason, which is what
existing callers read. When a step failed, `detail` is **replaced** by
`cleanup incomplete: <steps> failed`, so a caller cannot read a half-finished
halt as an ordinary one. The reason is still on the bot row and in the alert.

### The nested guard on `#unsubscribeFromFeed`'s alert

That method's contract is "never throws" — leaving `running` is a safety action
that must not be blocked by a feed hiccup. But its failure path **wrote an alert
to D1**, and D1 is exactly the dependency most likely to be down at the moment a
feed RPC has just failed: one storage timeout takes both. The reporting failure
then propagated out of a method that promises not to, and the caller lost every
later step. The alert now has its own `try/catch` ending in `console.error` —
there is nowhere else to write when the thing that failed *is* the alert path.

### The unsubscribe moved above `already_halted`

Re-halting an already-halted bot is **not** a mistake to short-circuit: the
global kill switch and reconciliation both do it deliberately, sweeping every
bot they select. That makes it the one path that runs repeatedly against a bot
in the broken state, and it walked past the leak every time. `unsubscribe` is
idempotent and best-effort, so repeating it is free.

**Deliberately NOT also self-healed there:**

- **`#mirrorStatus`** — `#resumePass`'s own comment reserves that convergence
  for the detector in `docs/open-items/resume-split-brain.md` part 3b, and
  widening it into `#halt` is the exact change that comment declines to make.
  Overriding a written decision was not in scope for a reliability fix.
- **the cancel sweep** — it would spend risk-exit rate budget on every
  kill-switch pass over every already-halted bot, and the 30-second poll already
  observes halted bots' open orders. The subscription has **no** such observer,
  which is why it is the one that moves.

## PART 3 — THE DETECTOR THAT DID NOT EXIST

`halted`/`stopped` **and** an open order is a combination that should be
impossible, and **nothing in this system looked for it**:

- reconciliation cannot — `RECONCILED_STATUSES` is
  `created`/`running`/`halted`, so it never reads a `stopped` bot at all, and
  `mirrorFindings` compares order lists rather than asking whether an order
  should exist given a status;
- the 30-second poll cannot — `#pollArmed` excludes `stopped`, and a halted bot
  whose object lost track of an order is not polling for it;
- no `CHECK` constraint can — it spans two tables.

`findInactiveBotsWithOpenOrders` (`src/db/integrity.ts`) is that query, exposed
read-only at **`GET /api/integrity/inactive-bots-with-open-orders`**.

- **Reads orders first, then their bots.** The open-order set is small and the
  terminal orders that dominate the table are excluded by the first query, so
  the second is an `IN` over a handful of ids rather than a scan of every bot.
- **`OPEN_ORDER_STATES` is derived** from `ALLOWED_TRANSITIONS` and `isTerminal`
  rather than written out, so it cannot drift from the state machine, and a
  seventh state added later classifies in the safe direction.
- **It corrects nothing.** Section 9's rule — halt and alert, never
  auto-correct — applies with more force to a detector: a query that "fixed"
  what it found would destroy the evidence of how the invariant broke. The
  corrective action is re-halting the bot, which now completes the cleanup.
- **Not scheduled.** Wiring it into the reconciliation cron would mean widening
  `RECONCILED_STATUSES` to include `stopped`, which changes what that job
  considers in scope. That is a larger decision than this detector needed and is
  left open deliberately.

## PART 4 — TESTS

Five new tests in `bot-instance.test.ts`, eight in `integrity.test.ts`, four
route tests in `api.test.ts`. The three the brief named:

1. **cancel sweep throws → still unsubscribes and writes the audit row.** The
   exchange's `cancelOrder` throws outright; the halt still lands, the feed is
   unsubscribed, `bot.halted` is written, and `detail` names
   `cancel_open_orders`.
2. **audit write throws → still cancels orders and unsubscribes.** The failing
   step is *later* in the sequence than the cancel sweep, which is what proves
   the wrapping is per-step rather than one `try/catch` around the tail.
3. **re-halting an already-halted bot with a leaked subscriber clears it.** The
   first halt's unsubscribe throws, reproducing the leak; the second call
   returns `already_halted` **and** unsubscribes — and writes no second alert
   and no second audit row, which is the "only the subscription self-heals"
   claim under test.

Two existing tests were rewritten rather than deleted, both to the new close
contract, both keeping their original safety assertion: `bot-instance.test.ts`'s
"cannot release the same capital twice" and `api.test.ts`'s second-close test.

**Results:** `3298 passed / 3298` across 119 files (baseline before this work:
`3281 passed / 3281` across 118). `tsc --noEmit` clean. Dashboard build clean.
The one unhandled worker-pool error at teardown reproduces on a stashed baseline
and is unrelated.

## PART 5 — `bot-xs0ufw` IS UNTOUCHED, ON PURPOSE

The live bot carrying this bug was **not** repaired, and its data was not
edited. It is the real-world test for this fix: once deployed, **re-halting it**
should be the thing that finally unsubscribes it, cancels its dangling order and
writes its missing audit row. Repairing it by hand now would spend the only
natural end-to-end verification this fix has.

`GET /api/integrity/inactive-bots-with-open-orders` should list it **before**
the deploy and stop listing it **after** the re-halt. That is the check to run.
