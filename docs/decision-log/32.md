## Step 32: A real tradability gate on bot creation, and the spot-versus-perpetual check that closes step 31's flagged gap at the one place it ends in an order
Date: 2026-08-09

### What was built

Step 31 flagged, at the operator's direction, that **nothing in this system
distinguishes spot from perpetual**. The research that followed found something
broader and worse alongside it: **`POST /api/bots` — the endpoint that reserves
capital and eventually places real orders — performed no tradability check of any
kind.** `pair` was a free-typed string stored verbatim; `bot-instance.ts` has
never called `listTradablePairs`. A typo, a delisted symbol, a pair from the
wrong venue and one of Gemini's perpetuals all reached bot creation identically.

This step closes both, at that one endpoint:

- **`src/shared/exchange-client.ts`** — `InstrumentKind` (`spot` /
  `derivative` / `unknown`) and an **optional** `instrument` on `SymbolFilters`.
- **`src/exchange/gemini/filters.ts`** — `parseInstrumentKind`, reading the
  `product_type` / `contract_type` fields `parseSymbolDetails` has been
  receiving and discarding since step 3.4.
- **`src/workers/symbols.ts`** — the `SymbolDetailLister` port and
  `envSymbolDetailLister`.
- **`src/research/tradability.ts`** — `checkSpotInstrument`, beside
  `checkTradable`, plus the per-venue `VENUE_PUBLISHES_INSTRUMENT_TYPE` table.
- **`src/api/handlers.ts`** — `assertBotPairIsSpotTradable`, and `createBot`
  restructured so the gate runs before anything is spent.
- **`src/api/envelope.ts`** — three new status rows and `statusForCode`.
- **`src/api/index.ts`**, **`src/api/router.ts`**, **`src/research/index.ts`** —
  port wiring and exports.

### The assumption that was wrong, caught by querying instead of trusting

The research this step began from recommended checking live testnet state before
building, on the grounds that a spot-only filter might invalidate something
already there. It predicted both the watchlist and the bot list would be empty.

**One half was right. The other was wrong, and it was wrong in the direction
that matters.**

| | predicted | actually found |
| --- | --- | --- |
| `watchlist` | empty | **empty**: 1 row total, **0 live** — step 28's `BTCUSD`, added and removed |
| `bot_instances` | empty | **11 bots**, with real allocated capital |

The eleven: **9 on `BTCUSD`** (7 running, 2 halted, 1 of those archived) and
**2 on `DOGEUSD`** (both running), all on `gemini-main`/`gemini`. Registered
accounts are `gemini-main`/`gemini` and `main`/`binance`.

**Nothing broke, and that is not the point.** Both pairs are real Gemini spot
pairs; no perpetual and no malformed symbol was among them; and the gate is on
the *creation* path, so it never re-validates an existing bot. The reason this
is recorded as a correction rather than a footnote is that **the prediction was
derived from reading this log, and this log does not record current state** —
exactly the failure 10.14 already named ("anything which can change after an
entry is written must be read from the system, never quoted from this log").
Step 28's entry records adding and removing one watchlist row; nothing anywhere
records eleven bots being created, because bot creation is ordinary use rather
than a logged decision.

**The correction cost one `SELECT`.** It is recorded because the cheap check
that disproves an assumption is worth more than the assumption was.

### The request-cost story, corrected from source before anything was built

The research note raised the possibility that bot creation already fetches the
symbol-details payload, which would have made the instrument check free. **It
does not.** Confirmed by reading `bot-instance.ts`:

- `create` and `createGrid` initialise runtime state with `filters: null` and
  never call `getSymbolFilters`.
- The only caller is `#ensureFilters`, reached from the **order-placement** path
  — at *start*, not at *create*.

So the honest cost is: **bot creation now spends one additional uncached
exchange request** (`GET /v1/symbols/details/:symbol`, unsigned). What is reused
is the endpoint, the parser, and `clientForAccount`'s single resolution path —
not a payload already in hand. The catalogue check beside it is usually free,
sharing the hour-long KV cache with the watchlist and the pair dropdown.

This is recorded because "it reuses data already fetched" was plausible, was
believed briefly, and was false. One request per bot creation is a price worth
paying; pretending it is zero would have been a claim the next reader inherits.

### The field is real, and that is the whole reason this is not a suffix rule

Verified from Gemini's own reference for `GET /v1/symbols/details/:symbol`:

| field | documented values | meaning |
| --- | --- | --- |
| `product_type` | `spot` / `swap` | **"Instrument type"**; `swap` is a perpetual |
| `contract_type` | `vanilla` / `linear` / `inverse` | `vanilla` for spot; the other two are perpetual settlement conventions |

**[P]** primary — the vendor's own endpoint reference

Their documented spot example is `"product_type": "spot", "contract_type":
"vanilla"`.

**A naming heuristic was available, was cheaper, and was deliberately not used
here.** `PERP` as a suffix is a convention *observed* in Gemini's data and
documented as a rule **nowhere** in their reference — the derivatives section
states no naming convention at all. Inferring from it is a guess in both
directions: a perpetual named without the suffix passes, and a real spot pair
whose base asset is literally `PERP` (Perpetual Protocol is a real token, traded
as `PERPUSD` elsewhere) would be refused. **The gate that stands between a
human's typo and a real order reads a field.**

**`product_type` decides; `contract_type` corroborates.** `product_type` is the
field Gemini documents as meaning instrument type and has exactly two values,
one of which is the question. `contract_type` describes settlement maths, and
`linear`/`inverse` settle the question on their own. A **contradiction**
(`product_type: "spot"` with a non-`vanilla` contract) maps to `unknown` and
refuses — mapping it to `spot` on the strength of one field would be this code
deciding it understands Gemini better than Gemini does, which is the same
posture `mapStatus` and `parseStatus` already take on an unrecognised enum. A
**missing** `contract_type` is not a contradiction and does not refuse.

**The comparison is exact and lower-case**, matching the documented spelling with
no case folding. That is step 28's casing lesson one field over: accepting
`"SPOT"` would mean accepting a value this code has never seen in a real payload.

**`parseInstrumentKind` does not throw on an unmappable value**, deliberately and
asymmetrically to `mapStatus`. A throw would take down `getSymbolFilters` for the
**order path** too, where these fields have never been needed and where section
4.3's validation must keep working for all eleven existing bots. The caller that
cares refuses; the parser reports.

### Two checks at one gate, and why they were not folded into one

`checkTradable` answers *"does this venue list this string"* from the pair
**catalogue** — one full-catalogue request, KV-cached for an hour, shared with
the watchlist and the dropdown. `checkSpotInstrument` answers *"what IS this
instrument"* from that symbol's **details** — one uncached per-symbol request.
Different questions, different endpoints, different costs, different refusals.

**Folding them would have been the obvious move and would have been wrong.**
Every existing caller of `checkTradable` — `addToWatchlist`, `fetchCandleWindow`,
`selectNamedCandidate`, `selectGeneralCandidates` — would start paying the
per-symbol request whether or not it wanted the answer, and
`selectGeneralCandidates` checks up to fifteen trending coins times each quote
asset per run. One cached catalogue read would become dozens of live requests.

So they stay separate and are **composed at the gate that wants both**. This is
not the second implementation 21.5 warns about: it does not re-answer the
tradability question, it answers a different one, and it lives in the same file
precisely so the two are read together and neither grows a private copy.

**The order is cheap-first.** The catalogue check runs first and rejects the
overwhelmingly common mistake — a mistyped or non-existent pair — usually
without an exchange request at all. The per-symbol request is only ever spent on
a pair the venue has already confirmed it lists. That ordering also makes the
messages honest: a perpetual **is** on the venue's list, so it passes the first
check and is refused by the second, **by name** — reporting it as
`pair_not_tradable` would be flatly untrue and would send an operator hunting
for a spelling mistake that is not there.

Strategy parameters are decoded **before both**, since deciding them is pure and
local — the "free checks first, network last" order `addToWatchlist` documents.
A request malformed in both its params and its pair reports the params and
spends nothing.

### Fail closed in three directions, including the one that looks wrong

```
  the venue says swap/perpetual        -> instrument_not_spot      400
  the answer is unmappable, OR ABSENT
    on a venue that publishes it       -> instrument_type_unknown  502
  the details could not be read at all -> instrument_unreadable    503
```

**The middle one will look like pedantry to whoever reads it next, and it is
not.** Gemini lists spot pairs and perpetuals in **one catalogue on one host**,
so on that venue "no instrument type reported" and "this might be a perpetual"
are the same sentence. Section 5.6's rule is that a failed read is never data;
this is that rule one level up — **a field that did not arrive is not a field
that said "spot"**.

The statuses reuse the shape-matching logic the table already applies:
`instrument_not_spot` takes 400 with `pair_not_tradable` (a field value the
caller can fix by asking differently); `instrument_type_unknown` takes **502**
with `no_candles_returned` (the venue answered successfully and the answer was
unusable — there is nothing to rephrase); `instrument_unreadable` takes 503 with
`tradable_set_unreadable`, `not_attached` and `throttled` (a refusal to act on
input that could not be verified). `pair_not_tradable` and
`tradable_set_unreadable` are **not repeated** in the table — bot creation reuses
`checkTradable` and therefore its existing rows, which is the point.

`statusForCode` was added rather than writing `400` at the call site, because
these two checks **return** refusals rather than throwing (so `errorResponse` has
no coded error to catch) and the alternative would have quietly made
`envelope.ts`'s opening claim — "the single place an error becomes an HTTP
status" — false.

### The venue table is exhaustive on purpose, and Binance's answer is structural

```ts
const VENUE_PUBLISHES_INSTRUMENT_TYPE: Readonly<Record<ExchangeId, boolean>> = {
  gemini: true,
  binance: false,
};
```

A `Record<ExchangeId, …>` rather than a lookup with a default, so **a third
exchange fails to compile here until someone answers the question for it** — the
same "a new value must be handled, not guessed" property `exchange-dispatch.ts`
gets from its exhaustive `switch`. A default would silently pick one of two
answers for a venue nobody checked, and both answers are wrong for some venue.

**`binance: false` is a structural fact, not a concession.**
`/api/v3/exchangeInfo` **is** the spot API; Binance's perpetuals are a different
product on a different host (`fapi.binance.com`, whose `exchangeInfo` carries
`contractType: PERPETUAL`) that this system has no client for and cannot reach.
There is no instrument-type field on the spot payload because there is no
non-spot instrument in it to distinguish. Spending a request to ask an
unanswerable question would be theatre, so on Binance the details call is not
made at all — asserted by a test.

**What is NOT claimed, and is deferred rather than hidden:** that everything on
Binance's spot endpoint is something this system should trade.
`parseTradablePairs` filters on `status === "TRADING"` alone and reads neither
`isSpotTradingAllowed` nor `permissions` (documented values include `SPOT`,
`MARGIN`, `LEVERAGED`), so a margin-only or leveraged-token symbol would pass it
today. That gap is recorded in the table's own docblock rather than in a comment
nobody reads, because that table is where a future reader will come looking for
"what does this system believe about Binance instruments".

### The gate is in the handler, and the property is "nothing happened"

Both checks run in `createBot` **before `botStub` is even asked for**, because
the property that matters is not "creation is refused" but **NOTHING HAPPENED**.

`BotInstance.create` reserves capital through `createBotInstanceWithCapital` —
the `bot_instances` row, the `capital_ledger` reservation and the
`capital.allocated` audit entry are one pipeline — and then writes the object's
own storage. A check *inside* that method would already have instantiated the
Durable Object; a check *after* the reservation would leave capital allocated to
a bot that was refused. **A gate that returns the right error after reserving
capital is worse than no gate, because it looks correct.**

Held to by an instrumented run against real D1 and the real `handleApiRequest`
(temporary file, since deleted, diff verified clean afterwards):

```
ledger BEFORE request: total_allocated=0
1. checkTradable -> listTradablePairs (cached catalogue)
2. checkSpotInstrument -> getSymbolFilters("HYPEUSDCPERP")
   venue reported product_type -> instrument="derivative"
3. REFUSED 400 instrument_not_spot
4. bot_instances row .......... NONE
   capital_ledger allocated ... 0
   audit_log rows ............. 0
5. same bot id re-used on a SPOT pair -> 201 (409 would mean a DO existed)
```

Line 5 is the load-bearing one: **the id is still free afterwards**, so no
Durable Object was ever brought into existence — a live object answers `409
already_created` on id reuse.

**0. The one flagged unverified assumption was settled FIRST, before deploying.**
This session shipped the gate with `product_type`'s live presence documented but
**not observed**, flagged prominently, with the note that if the field were
absent in the sandbox every Gemini bot creation would return `502
instrument_type_unknown`. The operator resolved it with two unauthenticated
public calls to `api.sandbox.gemini.com` before anything else:

| symbol | `product_type` | `contract_type` |
| --- | --- | --- |
| `BTCUSD` | **`spot`** | **`vanilla`** |
| `HYPEUSDCPERP` | **`swap`** | **`linear`** |

**Both fields are genuinely present on real sandbox data, with the documented
values.** That is the assumption discharged — and it is **the exact branch pair
the mutation testing found masking itself**, now confirmed against a real venue
rather than only against a reference page.

**1. A real perpetual was refused.** `POST /api/bots` with `HYPEUSDCPERP` →
**400 `instrument_not_spot`**, the message naming the instrument and citing
section 4.5.

**2. An untradable pair was refused.** `FAKEUSD` → **400 `pair_not_tradable`**,
consistent with the refusals steps 28 and 29 verified for the watchlist and the
candle fetch.

**3. A valid spot pair succeeded.** `BTCUSD` → **201**, full bot object
returned.

**4. THE LOAD-BEARING CHECK — both refusals left no trace.** Confirmed by real
D1 queries after the fact:

- `bot_instances` contained **only the one successfully created bot**.
- `capital_ledger.total_allocated` reflected **only the real pre-existing
  allocations plus the one new bot** — nothing from either rejected attempt.
- `audit_log` contained **exactly one `capital.allocated` row**, for the
  successful bot only.

**5. THE SHARPEST PROOF — the same `botInstanceId` that was rejected on a perp
pair returned 201, not 409, when retried on a valid spot pair.** A live Durable
Object would have answered `409 already_created` on id reuse. So the refusal
happens before **any side effect of any kind**, not merely before a database
write. That is the difference between a gate that is ordered correctly and one
that merely reports correctly, and it is now observed rather than argued.

### Tests, and the mutation survivors that taught the real lesson

**+20 tests, 1814 -> 1834.** `api.test.ts` 135 -> 144; `gemini/filters.test.ts`
18 -> 29. **15 mutants, 15 caught**, none by typecheck alone.

Four existing `createBot` tests **failed the moment the gate landed**, all with
`503 tradable_set_unreadable`, because they had never injected a symbol lister
and the real one has no credentials in the suite. That is the gate failing
closed on its first contact with existing code, and they were updated to supply
the ports rather than the gate being softened.

Mutants aimed where the operator asked: five at the ordering
(gate moved after `create`; the two checks swapped; either refusal not thrown),
six at the instrument comparison, four at the gate's use of the answer.

**Two survived the first pass, and they were the same bug:**

| survivor | what it exposed |
| --- | --- |
| `product_type: "swap"` made to return `"spot"` | **Survived.** Every perpetual fixture supplied **both** fields, so `contract_type: "linear"`/`"inverse"` answered on the line above and the `swap` line was never reached |
| `inverse` dropped from the contract-type check | **Survived**, reciprocally: `product_type: "swap"` in the same fixture caught it on the next line |

`parseInstrumentKind` answers `derivative` from **two independent lines**, and a
fixture carrying both fields — which every realistic perpetual payload does — is
answered by the first and never reaches the second. **Each line masked the
other**, and the test whose entire purpose was to check one of them was passing
on the strength of the other.

Closed with three fixtures that **isolate one field at a time**: a swap with
`contract_type` deleted; `linear` **and** `inverse` with `product_type` deleted;
and `swap` + `vanilla` to pin that it is the swap that decides rather than the
absence of a contract objection. Both mutants now caught.

### THE STANDING CONVENTION this establishes, and it is not about this file

This is **the second time in two consecutive steps** that a passing test was
found to be passing for a reason other than the one it was written for, and the
seventh in the project (steps 26, 28, 29, 30, twice in 31, and here). Step 31's
was *a test aimed at the path where the failure is structurally unreachable will
pass forever*. This one is a **sharper, more general, and more mechanical**
version of it, and it is recorded as a convention rather than an anecdote:

> **When a check reads MULTIPLE FIELDS that can each independently signal the
> same conclusion, a fixture that supplies all of them at once lets any one
> field silently backstop the others. A test aimed at one field can pass forever
> while never exercising it. Fixtures must isolate ONE field at a time, and
> there must be a fixture per signalling field, not per conclusion.**

The failure is invisible to inspection: the fixture looks *more* realistic for
carrying every field, the assertion is correct, the test name is accurate, and
the suite is green. Only a mutant deleting one branch reveals that the branch
was never reached. **It is worth applying to every future multi-field check in
this project**, not just this one — the candidate shapes are already visible:
anything that would combine `status` with `permissions` on the Binance side, and
any future rule reading both a venue's instrument type and a naming convention
at once.

The corollary is that **mutation testing earned its keep here specifically
because the tests were good**. Nine well-named, well-targeted assertions could
not find this; two one-line mutants did.

**What the numbers do not prove.** All 1834 tests use stub listers. **No test in
this repository has spoken to Gemini.** The perpetual symbols in the fixtures are
real strings from step 31's live run copied into a stub, not a live listing —
which is exactly why the operator's sandbox calls above matter, and why they were
made before the deploy rather than after it.

One pre-existing oddity, named so a future reader does not attribute it to this
step: the full-suite run reports **`Test Files 68 passed (69)`** with one
"Worker exited unexpectedly" error and no failing test. **Verified pre-existing
on clean `HEAD`** by stashing all changes and re-running — identical output at
1814 tests. It is a miniflare worker-teardown artefact, not a result of this
work.

### Deliberately not done, and open questions

- **The suffix-heuristic follow-up was NOT built**, per the operator's explicit
  scoping. The cheaper research paths — `addToWatchlist`, `fetchCandleWindow`,
  `selectNamedCandidate`, `selectGeneralCandidates` — still have **no spot
  check** and would still accept a perpetual today. They cannot cheaply use the
  structured field for the reason given above (per-symbol requests at candidate
  volume), so they are a separate, smaller follow-up whose likely answer is a
  maintained per-venue pattern **explicitly labelled a naming-convention
  heuristic and not a structural guarantee**. Step 31's gap is closed **at the
  gate where it ends in an order**, and nowhere else.
- **The Binance `isSpotTradingAllowed` / `permissions` gap remains explicitly
  deferred**, recorded in the venue table's docblock.
- **A real `v-spot-1` bot with $50 allocated now exists on testnet**, created by
  the verification run and **left in place; its disposition is undecided.** It is
  a real row with a real reservation against the `gemini-main` capital ledger,
  and it should be either adopted deliberately or archived and released — it is
  named here so it is a decision rather than a bot nobody remembers creating.
  The eleven pre-existing bots are untouched.
- **No decision was taken about the eleven existing bots.** The gate does not
  re-validate them, and `readWatchlist`-style staleness applies here too: a bot
  created before this step is not re-checked, so a pair delisted since its
  creation stays a running bot. Same shape as the watchlist gap steps 28 and 31
  both recorded, one table over.
- **Nothing was deployed by this session**, and the operator's deploy was of the
  branch under test; **this entry records the code and the verification, not a
  release decision.**
- **The `instrument` field is optional on `SymbolFilters` and only Gemini
  populates it.** That is deliberate — absence means "this venue publishes no
  such field" rather than "not checked" — but it does mean a third exchange that
  *does* publish one will need both a parser change and a table row, and only the
  table row is enforced by the compiler.
