### The bundle shape

```ts
// The envelope. Three states, no error vocabulary of its own.
type GatheredInput<T, E> =
  | { outcome: "ok";                 value: T }
  | { outcome: "failed";             error: E;       failedAt: Timestamp }
  | { outcome: "threw_unexpectedly"; error: unknown; failedAt: Timestamp }

type CandleInput        = GatheredInput<CandleWindow,        CandleWindowError>
type ConcentrationInput = GatheredInput<ConcentrationResult, ConcentrationError>
type ExposureInput      = GatheredInput<AccountExposure,     ConcentrationError>

// The paused input. A one-armed union, on purpose.
interface NewsNotYetAvailable {
  outcome: "not_yet_available"
  reason: string                  // "...NOT a failed fetch -- no request was made..."
  decisionLogEntry: string        // "docs/decision-log/30.md"
}
type NewsInput = NewsNotYetAvailable
const NEWS_NOT_YET_AVAILABLE: NewsNotYetAvailable   // Object.freeze'd, shared

interface CandidateGatherBundle {
  candidate: Candidate            // selection's real result, verbatim, NO envelope
  candles: CandleInput
  news: NewsInput
  concentration: ConcentrationInput
  assembledAt: Timestamp          // documented as NOT a fetch time
}

interface CandidateSetGatherBundle {
  set: CandidateSet               // whole: trending.fetchedAt / watchlist.readAt survive
  exposure: ExposureInput         // the ONE bot_instances read
  bundles: readonly CandidateGatherBundle[]   // set order, never filtered
  assembledAt: Timestamp
}

interface GatherPorts extends CandleWindowPorts, ConcentrationPorts {}
```

### It returns an HONEST PARTIAL bundle, and that is not a weakening of 21.5

Assembly's job is **collection, not judgement**. A bundle comes back whenever a
candidate exists, carrying each input's real state. Whether the result is good
enough to show a human is **Stage 4's** job (21.4, "Explain and assemble"), which
does not exist yet, and putting that decision in the collection layer would put a
policy judgement in the one place nothing downstream could see it.

The distinction that keeps this compatible with 21.5 requirement 6 is the whole
design and is worth stating in the two directions it runs:

- **WITHIN each input, fail-closed is untouched.** `fetchCandleWindow` still
  throws six ways rather than returning a short window; `readAccountExposure`
  still throws rather than reporting "no concentration" for a read it could not
  do. Nothing here catches those and substitutes a value.
- **BETWEEN inputs, a failure is RECORDED, not propagated.** A failed candle
  fetch puts the real `CandleWindowError` — with its real code — in the candles
  slot and leaves every other slot alone.

The failure a whole-bundle throw would cause is specific and bad: **one
unreachable venue would erase a concentration flag that was read successfully
from D1** and is exactly the thing 21.4 wants "presented prominently". Losing a
real risk signal because an unrelated fetch failed is not failing closed; it is
failing closed on the wrong thing.

What no reader may do is mistake a recorded failure for a success, and that is
enforced by the type rather than by care: the value is reachable **only** through
the `ok` arm — the `ExchangeOutcome` discipline section 5.6 imposes one layer
down, applied one layer up.

### Three design notes on the shape

**1. `Candidate` has no envelope, and the absence is a statement.** A `Candidate`
exists only because selection already succeeded. Selection's failures are
refusals thrown out of `selectNamedCandidate`/`selectGeneralCandidates` — an
untradable named coin, an unreachable trending pull — and they produce **no
candidate to bundle**. An `ok`/`failed` wrapper here would model a state
unreachable by construction, which this folder consistently makes
unrepresentable rather than checks for (`Candidate.sources` as a non-empty tuple,
`ConcentrationResult` as a variant rather than a flag list). What IS asserted is
that the candidate arrives **verbatim, by identity** — merged provenance and all
— because a summarised one would destroy exactly what 21.5 requirement 2 needs.

**2. `threw_unexpectedly` is a distinct state because it is REACHABLE, and the
gap that makes it reachable is real.** `fetchCandleWindow` **does not wrap its
ports**: `ports.db.accounts.findOne` and `ports.getCandles` are awaited directly,
so a `Database` or `CandleSource` that throws raw produces something that is not
a `CandleWindowError` and never will be. Folding that into `failed` would mean
typing `error` as `CandleWindowError` while sometimes holding a D1 exception — a
lie the type system would happily tell, and the exact class of thing this file
exists to refuse. Kept separate, "this module refused for a reason it enumerated"
and "something beneath it broke" are two different facts, the same distinction
`tradable_set_unreadable` draws against a merely absent pair. `error` is typed
`unknown` rather than `Error`, because a thrown non-`Error` is legal JavaScript
and narrowing it would be the same papering-over in miniature.

**3. Concentration's `threw_unexpectedly` is currently UNREACHABLE, and a test
pins that.** `readAccountExposure`'s `catch` is deliberately total and normalises
everything — including a thrown string — into a `ConcentrationError` with code
`bot_list_unreadable`. So the arm exists in the type (the envelope is generic and
one shape is better than two) but nothing can produce it today. That is recorded
rather than assumed: a test drives a `Database` whose `findMany` throws a bare
string and asserts the slot comes back `failed` with the module's own code.
**If someone removes that broad catch, the failure surfaces in that test rather
than in a proposal.** The asymmetry between the two inputs is a fact about the
two modules, not an inconsistency in this one.

### The isolation trace — control flow, not an assertion

The brief asked for this to be shown rather than claimed. Every step is in
`src/research/gather.ts`:

1. **`gatherAgainstExposure` contains no `throw` statement and no early return.**
   It runs `runInput(fetchCandleWindow…)`, then `foldConcentration(…)`, then
   constructs and returns the object. Both calls are unconditional.
2. **The fold cannot observe the candle result.** `foldConcentration`'s
   parameters are `ports`, `candidate`, `request`, `exposure`. The candle outcome
   is not among them, so the coupling is absent by signature rather than by
   discipline — a later edit would have to add a parameter to introduce it.
3. **`runInput`'s `catch` is total and returns a value.** Nothing rethrows, so
   `fetchCandleWindow`'s six enumerated refusals and any raw port throw all
   terminate inside the candle slot.
4. **There is no shared mutable state between the two** — no accumulator, no
   first-error variable, no ordering dependency, nothing either writes that the
   other reads.
5. **At set level, `gatherCandidateSetData` does one `readExposure`, then a `for`
   loop that pushes unconditionally.** No `break`, no `continue`, no filter, no
   predicate of any kind between the gather and the push.

The type makes the three-way distinction a caller needs real:
`bundle.candles.outcome === "failed"` and `bundle.concentration.outcome === "ok"`
are independent fields with **no shared status field and no "first error"**, so
"this candidate's candles failed", "this candidate's concentration check failed"
and "everything succeeded" are three distinguishable states rather than one
degraded one.

### It composes the existing types and invents no error vocabulary

`GatheredInput`'s `failed` arm carries **the producing module's own error
object**, so `error.code` reads exactly as it would for a direct caller —
`candles_unavailable`, `interval_not_verified`, `pair_not_tradable`,
`bot_list_unreadable`, `missing_field`. A second vocabulary restating those as
some flatter `fetch_failed` would drift from the first, and 21.5's rule about
duplicated risk checks applies unchanged to duplicated failure descriptions: the
copy that drifts is the one nobody is watching.

The same principle governs what is NOT modelled. A `candidate.exchange` that
disagrees with the registry row `fetchCandleWindow` reads is **not** a new error
state: both values are in the bundle (`candidate.exchange` and
`candles.value.exchange`), so the disagreement is visible to anyone who looks,
and inventing a code for a mid-run registry change would add vocabulary for a
fact the bundle already carries.

### The news slot is a state, not a TODO

Every bundle carries `NEWS_NOT_YET_AVAILABLE`, a **frozen, shared** value sitting
in the same discriminant position every other input's state lives in — so an
exhaustive `switch` must handle it and cannot silently skip it.

**It has no `error`, no `failedAt` and no `fetchedAt`**, and that absence is the
structural half of step 30's pause: no request was made, and a timestamp would
claim one was. A proposal saying "news could not be fetched" invites a retry and
implies a transient problem; the truth is a deliberate, recorded pause with three
named conditions for lifting it, none met. **Those two sentences must never be
produced by the same branch**, and here they cannot be, because there is no
branch that produces the first.

`NewsInput` is a **one-armed union on purpose**. The `ok` and `failed` arms are
not pre-declared, because nothing can produce them and a state no code can reach
is a claim about a fetch this system has never made. When a vendor is chosen, the
arms are added and **every exhaustive switch downstream stops compiling until
each is handled** — loudly, at build time, which is the whole reason the pause
lives in the type instead of a comment. A test pins the union to exactly one arm
so that widening it is a deliberate act.

The guarantee is structural at the port layer too: **`GatherPorts` holds no news
source**, so assembly cannot reach a vendor even by mistake — the same technique
`candidates.ts` uses to stop the named entry point from reaching a trending
vendor.

### Every fetch keeps its own timestamp (21.5 requirement 4)

The sub-fetches are not simultaneous, so **no bundle-level fetch time is
manufactured**. Each timestamp stays where the module that earned it put it:
`candles.value.fetchedAt` is the venue's answer instant,
`concentration.value.readAt` the D1 read's, `candidate.sources[]` carries each
provenance time (`requestedAt` / `addedAt` / `fetchedAt`), and a failed slot's
`failedAt` is when the failure was **observed**, since no fetch succeeded to
supply one. `assembledAt` sits beside them and is documented on the field as
**not one of them** — it is when assembly ran, the same kind of thing
`CandidateSet.selectedAt` is.

The test for this drives a clock that **moves on every read**, so a version that
collapsed the sub-fetch times into one instant fails there rather than in a
proposal that claims data was fetched when it was not. The stub venue answers at
an instant deliberately far from anything the test clock produces, so
`fetchedAt` surviving into the bundle is a real assertion and not two clocks
agreeing by accident.

### One read for N candidates, and what a failed read then means

`gatherCandidateSetData` does **one** `bot_instances` read for the whole set —
step 34's design, reused rather than re-derived — and reports it on `exposure`
for 21.5 requirement 2's reason ("the actual raw data it used").

If that read fails, **every candidate's concentration slot carries that same
error object by identity**, asserted with `toBe` rather than by code equality.
That is not a duplicated guess: it genuinely was one read, so N identical
recorded failures is an accurate report of what happened. Re-wrapping it per
candidate would restate one fact N times and invite the copies to drift. Candles
are unaffected and still fetched per candidate.

Per-candidate concentration failures are still possible and still isolated: the
**fold** can refuse a single candidate (a blank pair, or an account label that
disagrees with the one the exposure was read for) while its neighbours succeed.
A test covers exactly that.

Aimed specifically at the failure-isolation logic, per the brief.

| | Mutant | Caught by |
| --- | --- | --- |
| M1 | candle failure rethrows instead of recording | 13 tests |
| M2 | failed candles short-circuit the concentration fold | 3 tests |
| M3 | failed bot-list read throws before candles are fetched | 5 tests |
| M4 | failed read reported as a clean concentration result | 5 tests |
| M5 | every throw dressed up as the module's own refusal | **1 test** |
| M6 | news slot rebuilt per bundle instead of shared/frozen | 6 tests |
| M7 | set drops candidates whose candles failed | 2 tests |
| M8 | set stops at the first failing candidate | **1 test** |
| M9 | set re-reads `bot_instances` per candidate | 2 tests |
| M10 | operator's stated quote assets dropped instead of merged | 1 test |

**M5 and M8 were each caught by a single test, and that is recorded as thin
rather than glossed.** It is thin in the sense that matters — one test failing is
one edit away from zero — but it is not accidental: in both cases the single
catcher is the test **written for that exact property** (`separates a port that
threw from a refusal the module enumerated` for M5; `keeps a failing candidate in
position without disturbing its neighbours` for M8), not a bystander that
happened to trip. The honest reading is that the property has exactly one guard,
which is enough to catch the mutant and not enough to be redundant if that test
is ever weakened.

M4 deserves naming separately for the same reason step 34's case-folding mutant
did: it is the mutant whose **survival would have been invisible**. A clean
concentration result is a perfectly well-formed answer, and it is the answer that
hides the exact risk the check exists to surface. The test that catches it
asserts the absence of the value rather than the presence of an error, because
that is the shape the bug would take.

### Assumptions, stated so they can be checked rather than discovered

1. **`interval` is REQUIRED on `GatherRequest`, with no default.** A `Candidate`
   carries an account, an exchange, a pair and its provenance — it says nothing
   about a timeframe, because "which timeframe this run reasons over" is the
   caller's decision and not a property of the coin. `VERIFIED_INTERVALS`
   currently holds only `"1m"`, so a default would even be a **correct guess
   today** — and would silently become a wrong one the moment that array is
   widened. **The failure mode is why this is not a style preference: each venue
   spells the wider intervals differently (Gemini writes `"1hr"`/`"6hr"`/
   `"1day"`), so a wrong interval does not error — it returns correctly-shaped
   candles of a DIFFERENT duration, which passes every type check and which no
   downstream reader can distinguish.** A proposal derived from six-hour candles
   believed to be one-hour candles is precisely the "degraded proposal
   indistinguishable from a good one at a glance" of 21.5 requirement 6. Stated
   by the caller, refused by `fetchCandleWindow` if unverified.
2. **The quote-asset merge is asymmetric between the two entry points, and the
   asymmetry is structural rather than an oversight.** `gatherCandidateSetData`
   reads the operator's own quote assets off `CandidateSet.trending.quoteAssets`
   and **merges** them into `request.quoteAssets` for concentration's base-asset
   split — that is requirement "don't re-derive anything already resolved by
   `candidates.ts`" applied literally, since `selectGeneralCandidates` already
   normalised that list. `gatherCandidateData` gets **none**, because it takes a
   single `Candidate` and there is no set to read them from. A candidate has no
   quote assets on it and inventing some would be exactly the silent mis-split
   `AssessConcentrationOptions.quoteAssets` documents against. **Merge, not
   replace:** both lists are additive input on top of the observed set, and
   `normaliseQuotes` sorts longest-first so a longer suffix still wins. A named
   run contributes none, since `set.trending` is null on that path.
3. **Gathering is SEQUENTIAL, not concurrent.** N candidates cost N venue candle
   requests; firing them at once would put a burst against the rate budget
   section 5.4 owns, for a run nobody is waiting on interactively yet. Isolation
   does not depend on the ordering either way — see the trace above — so this can
   become concurrent later without changing what a bundle means. (See the open
   question below, which is the other half of this.)
4. **`fetchCandleWindow` re-reads the registry row and re-runs `checkTradable`**
   for a candidate `candidates.ts` already validated. The duplication is accepted
   rather than worked around: it is that module's own rule that the venue comes
   from the registry and never from a caller (step 11), the listing is KV-cached
   so the check is usually free, and the alternative is an internal entry point
   that trusts a caller's word about tradability — which is a validation that
   validates nothing.
5. **A `candidate.exchange` disagreeing with the registry is not a new error
   state.** Both values are in the bundle; the disagreement is visible without
   inventing a code for it.
6. **A failed set-level exposure read lands on every candidate's concentration
   slot as the same error object.** Accurate, because it was one read.

### OPEN QUESTION — the rate-budget cost of an N-candidate gather

**This is the one thing this step introduces that no run in this system has ever
done, and it is recorded here as a named open question rather than a footnote.**

**No run in this system has ever issued N sequential candle requests as one
logical operation.** Every candle fetch to date has been one request per
operation: a bot's own strategy tick, or the single-pair
`GET /api/accounts/:label/candles` endpoint. `gatherCandidateSetData` is the
first thing in this repository that issues a whole series of them under one
caller's single request.

**A general run is exactly that shape.** 21.3 specifies a fixed watchlist of 5–10
coins **plus** a live trending pull, and both feed one `CandidateSet`. So a
realistic general run is a dozen or more candidates, and therefore a dozen or
more venue candle requests, in sequence, with no pacing of this module's own.

**What is unknown:** whether that trips section 5.4's rate budget — and
therefore whether **`candles_unavailable` becomes the NORMAL outcome for the tail
of a candidate list rather than an exception.** That would be a proposal run in
which the first few candidates have real price history and the rest have none,
for a reason that has nothing to do with those coins. The bundle would report it
honestly — that is what this step's isolation guarantees — but "honestly reported
and routinely empty" is a design problem, not a success.

**This is unanswerable by stubs.** Every test here drives an injected
`CandleSource`; the rate budget, the venue's real limits and the real latency of
a dozen sequential requests are facts about production that no fixture can
produce. The tests prove the outcome is *recorded* correctly per candidate; they
say nothing about how often it will occur.

**It should be checked once `gather.ts` has a real caller — an endpoint or the
Assess stage — and NOT before.** Nothing invokes this module in production today:
there is no endpoint, no pipeline and no non-test caller. Answering it now would
mean standing up a temporary caller purely to generate load, which means
inventing the request shape, the candidate count and the interval that the real
caller will decide — **re-deriving exactly the conditions this step correctly
deferred**, and then measuring against guesses rather than against the thing that
will actually run. The measurement would have to be redone the moment the real
caller existed, and the intervening number would be worse than no number because
it would look like an answer.

Two smaller facts belong beside it: `VERIFIED_INTERVALS` still holds only `"1m"`,
so any real run reasons over minute candles alone; and assumption 3's sequential
ordering is the current mitigation for this question, chosen before the question
could be measured.

### Why no live check for this step

Judged unnecessary, and the operator agreed independently.

**No new read, write or wire-format boundary exists here.** Assembly introduces
no query, no endpoint, no persistence and no vendor call. It is composition over
three inputs whose own live behaviour is already proven — the candle fetch and
its interval gate (steps 29, 33), candidate selection (step 31), the
concentration read against real testnet data (step 34,
**2026-08-10T20:35:36Z**).

**The one property this step actually adds — failure isolation — is a structural
claim about control flow, and a live run tests it no better than the mutation
matrix does.** Isolation is a statement about which code paths can reach which
others, and the way to falsify it is to break a path and watch a test fail, which
is what the ten mutants did. A live run would mostly re-verify
`fetchCandleWindow` and `readAccountExposure` — which is what steps 29 and 34
already did, against the same real account.

The genuinely live-only question this step raises is the rate-budget one above,
and it is deliberately deferred rather than answered here, for the reason given.

### Deferred, deliberately

- **No endpoint.** Consistent with candidate selection and the concentration
  flag, neither of which has one either.
- **No judgement of any kind.** `gather.ts` does not rank, score, filter or
  refuse a bundle. That is Stage 4's job, and building it in the collection layer
  would put a policy decision where nothing downstream could see it.
- **No helper that summarises "what failed" in a bundle.** Stage 4 will want one;
  writing it now, before the consumer exists, is how it gets shaped to a caller
  nobody has written.
- **No concurrency**, and no news vendor — the first pending the open question
  above, the second pending step 30's three conditions, none of which has
  happened.
- **`gather.ts` has no non-test caller**, because the thing that would call it is
  the proposal pipeline.
