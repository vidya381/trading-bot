## Step 18: The order-state-drift correction path, and standing alerts
Date: 2026-08-01

Two consequences of step 17, now that reconciliation can see the exchange again:
three orders are confirmed filled while this system believes them `pending`, and
the finding that says so has been re-alerting every five minutes since.

### The correction path: `applyMissedFills`

Section 9 halts and alerts on order-state drift and **deliberately never
auto-corrects it**, because correcting means writing trades and moving a position
away from a belief the system has just proved wrong. That judgement is a
human's. So this is a human-initiated action:
`POST /api/bots/:id/apply-missed-fills` → `BotInstance.applyMissedFills(actor)`,
a thin wrapper in the same shape as start (12), resume (15) and liquidate (10.3).
No cron reaches it. `ctx.actor` is an Access-authenticated person, and it lands
in the `bot.missed_fills_applied` audit entry.

Two constraints in the existing code shaped this far more than convenience did,
and both rule out the obvious implementation.

**1. Fill ids are never synthesised.** `#recordCancellation`'s docblock (step
3.1's open question 1) already explains why: `applyFill` deduplicates on
`fillId`, so a made-up id means that when the real fill arrives it "either
double-counts or is silently swallowed". That is why `#recordCancellation`
alerts on an unexpected cancel-time fill instead of folding it in — and why the
same restraint binds here. The ids used are Gemini's own `tid` values, read via
`getOrderStatus`, which has always sent `include_trades: true` so the per-fill
price and fee are available. The whole repair is therefore built out of real
executions.

That also makes the operation **idempotent for free**: a second run finds every
`fillId` already on the order and applies nothing. It is not defended by a flag
or a "has this run before" record, which could disagree with reality; it is
defended by the same identity check the live path uses.

**2. A grid fill normally places an order.** `#applyGridFillToOrder` places the
paired sell when a buy level fills. Running that during a repair would put live
orders on the exchange from a **halted** bot — resuming trading through the back
door, which is exactly the consent the operator withheld. Confirmed rather than
assumed: `#halt` → `#cancelOpenOrders` only trims `openOrderIds`, it never clears
the ladder, and on 2026-07-31 every cancellation failed, so the ladder is fully
intact.

So `placeReplacement` is threaded into `#applyGridFillToOrder`, false only from
this path. It suppresses the placement and nothing else.

This turns out to be **clean rather than a fudge**, which was worth checking
before relying on it: `planFill` clears the FILLED level's slot itself and
returns the replacement as a separate intent — it is `#placeGridOrder` that
writes the new slot. So skipping placement leaves **no phantom order**. The
ladder honestly shows the acquired base, its cost, and an empty rung. A test
asserts exactly that, because a phantom would make the very next reconciliation
pass raise fresh drift and the repair would have made things worse.

Everything else is reused verbatim: `applyFill` for the order transition,
`applyEntry` / `planFill` for the position and average entry,
`#mirrorOrderUpdate` for `pending → filled` in D1, `#mirrorTrade` for the missing
trade rows. **No new arithmetic exists in this path**, which is the property that
stops a repaired position from disagreeing with a normally-recorded one.

Three deliberate refusals:

- **Not on a running bot.** `invalid_status`, so a repair cannot race the bot's
  own pipeline.
- **Never changes status.** Halted before, halted after. Resuming stays separate.
- **An unreadable order is reported, not assumed.** Section 5.6 again. And a
  response carrying no `trades` at all is distinguished from one carrying an
  empty `trades`: the former means the detail was not reported, which is not the
  same as "nothing filled", so it is reported as unread rather than as done.

A 200 does **not** mean everything was repaired. `skipped` carries what could not
be read or applied, and a caller has to look at it.

### Standing alerts

The same three findings had written **186 identical unresolved criticals in four
hours** — 3 per pass, ~864/day, for one unchanged fact.

Diagnosed before changing anything: this is only half unintended. Section 10's
KV cooldown throttles the outbound *ping* (15 min per alert type per bot) and was
working correctly. `notifications/cooldown.ts` is explicit that it governs
notifying and never row-writing: "recording and notifying are two separate
concerns". What was unthrottled is the D1 row.

The unconditional insert was a reasonable convention when every alert marked a
discrete event. It is wrong for a condition that is **re-detected on a schedule
and deliberately never auto-corrected**, because the row count then measures how
long the condition has persisted rather than what is wrong — and "how many
unresolved critical alerts are there" stops meaning anything, which is the one
number that most needs to.

So `raiseStandingAlert` writes one row per open incident, keyed on
`(alert_type, bot_instance_id)` — the same key the cooldown uses, so the two
layers agree on what "the same alert" is. The message is deliberately not part of
the key: a re-detection whose wording drifts (a run id, a changing quantity) is
the same incident, and keying on text would defeat the point.

**Nothing historical is lost, which is what makes this safe.** Every run already
writes its complete findings list to `audit_log.details_json`. The per-detection
record still exists, in the table built for history. `alerts` becomes what its
own `resolved` column always implied: a list of open incidents. The cooldown is
untouched.

`resolveClearedAlerts` is the other half, and without it this would be strictly
worse than the old behaviour — one row that never clears and suppresses every
future alert of that kind forever. It closes standing alerts whose finding did
not recur, and it is **gated on the pass having actually read something**. A run
that skipped its exchange reads found nothing because it saw nothing, and
treating that as "resolved" would clear a live incident on the strength of an
outage. That is section 5.6 applied to the alert lifecycle, and it is the
nastiest failure available here — a mutant removing the gate is caught.

Applied to severe findings too, for the same reasons.

## Step 18.1: Dashboard control for `apply-missed-fills`
Date: 2026-07-31

Step 18 closed with "no dashboard control" as open question 1, and gave the
condition for building one: "the API is the honest surface until it has been used
once in anger." It has been. This is the control, following the liquidate (10.9),
kill-switch (10.10), create-bot (10.11) and resume (15) patterns.

Frontend, plus **six backend endpoint tests** (below). No backend source file was
touched — `applyMissedFills`, the handler and the route are byte-for-byte as step
18 left them.

### The gate: an open finding, not a permanent button

*(the brief's central "how are you detecting a genuine reason" question)*

The control renders only while **this bot has an unresolved order-state-drift
alert**. `GET /api/bots/:id` already returns this bot's full `alerts` array, so
this costs no request and no new endpoint — the same "reuse how alerts are
already fetched" the brief asked for.

Five alert types qualify, enumerated in `dashboard/src/driftAlerts.ts` by
construction (tier prefix × kind) rather than by pattern-match, so adding one is a
deliberate edit:

| type | written by |
| --- | --- |
| `order_state_drift` | the bot object's own `#onOrderStateError` |
| `reconciliation_meaningful_order_state_drift` | reconciliation's observed drift — **the 07-31 incident's shape** |
| `reconciliation_meaningful_reported_order_state_drift` | the same finding reached by ingesting the row above |
| the two `reconciliation_severe_*` counterparts | nothing, today |

The severe pair is **unreachable**: `TIER_CEILING.order_state_drift` is
`meaningful`, and order-level findings carry no magnitude, so this kind cannot
escalate. They are listed anyway — a future ceiling change must not silently stop
the control appearing on the *worse* tier.

**`cancel_fill_discrepancy` and `cancel_failed` are deliberately excluded**, and
this is the one judgement worth recording. They are the same family of problem
and reconciliation classifies them beside drift, so including them looks
obviously right. But `applyMissedFills` iterates `state.openOrderIds` only, and a
cancelled order has already left that set — this step's own open question 2. The
button would have appeared, been clicked, returned an empty `applied`, and left
the operator working out why. Offering a repair that provably cannot reach the
finding is worse than not offering it.

`resolved` doing real work here is a payoff of this step's standing alerts: since
one row means one *open incident*, an unresolved row means the drift is there
**now**, not that it happened once. Under the old unconditional insert, the gate
would have been permanently true forever after the first detection.

### Refusing on a running bot, in two layers

The backend refuses anything but `halted` with `invalid_status`. That is mirrored
**before** the request, not only after it: when a drift alert stands but the bot
is not halted — a reconciliation halt that failed, or a bot resumed with the
incident still open — the panel renders with the button **replaced** by copy
naming the reason (a repair and a live pipeline would race, and the books are
exactly what is in doubt). Shipping a button that can only ever 409 is the same
mistake as create-bot's `sellOnStopLoss` toggle (10.11 decision 7).

The 409 branch still exists, for the bot being resumed between page load and
click — the same race liquidate handles (10.9, open question 2).

### The grid copy, and why it is this specific

The DCA dialog says what actually changes: each missed fill becomes a real trade
and an entry in this cycle, so held quantity, cost and **average entry price** are
recalculated — and the take-profit target moves with that average.

The grid dialog carries a bordered warning making three separate statements,
because two of them are consequences an operator would otherwise discover from a
ladder that looks broken:

1. **The paired replacement sell will not be placed.** A grid buy that fills
   normally places a sell one rung up; `placeReplacement: false` suppresses it.
2. **The rung stays empty, and nothing fills it later.** Not just "not now":
   `#placeInitialLadder` runs once on `placed: true`, so **resuming does not
   re-place it either**. The ladder is genuinely short those rungs until someone
   re-places them by hand — which the step-18 entry already identified as part of
   the *resume* decision, not this one.
3. **This is deliberate, and here is why**: placing a live order from inside a
   correction endpoint, on a bot that may still be halted, puts real orders on the
   exchange without the consent the operator withheld by leaving it halted —
   resuming trading through the back door. A repair writes books; it does not
   trade.

Plus the honest upside, so "short a rung" is not misread as "corrupt": no phantom
order is created, because `planFill` clears the filled level itself and returns
the replacement as a separate intent. The ladder afterwards shows the acquired
base, its cost, and an empty rung — all three true.

The success banner **repeats point 2** whenever a grid repair applied anything,
because that is when it becomes a fact about this bot rather than a caveat about
the action.

### The outcome is the result, never "done"

A 200 does not mean everything was repaired, so there is no generic success. Four
shapes are distinguished from the real `MissedFillsResult`:

| applied | skipped | tone | reading |
| --- | --- | --- | --- |
| >0 | 0 | success | everything read, everything applied |
| >0 | >0 | warning | **incomplete** — both lists shown |
| 0 | >0 | warning | nothing applied; every reason shown |
| 0 | 0 | info | already repaired (idempotent) or the orders really are resting |

`applied` renders as a table — order, **exchange fill id**, quantity, price — so
"what exactly did this write" is answerable, and the fill ids on screen are the
venue's own `tid`s, which is the whole basis of the operation's safety.

`skipped` lines are shown **verbatim**. The backend deliberately distinguishes an
unusable read from a response carrying no `trades` at all ("the detail was not
reported" is not "nothing filled"), and that distinction lives in its prose;
re-deriving it by string-matching in the frontend would be a second, weaker copy
of a judgement already made. One legend line restates the distinction once so the
lines are read correctly, and says the finding stays open.

Every result also states the status it came back with and that resuming is
separate — the operation never changes status, and the banner should not let
anyone assume otherwise.

Errors: `invalid_status`, `not_attached`, `not_created`, `unauthenticated`, a
generic branch, and a dropped request as an explicit **"outcome unknown"** — which
here carries a genuinely useful fact rather than only a caveat: **re-running is
safe**, because the repair deduplicates on the exchange's own fill ids. That
branch also forces a refetch, so the history below shows whatever actually landed.
Same `submitting` double-click guard and mounted-guard as every other write
surface.

Placed **above** resume on the detail view: repair the books first, then decide
whether to resume — the same "recoverable before irreversible" ordering step 15
used, extended by one.

### The alert-feed path (brief item 6): done, not deferred

It was straightforward, because `AlertList` was already generalised at 10.12. An
**open** drift row in the cross-bot feed now links to
`/bots/:id#apply-missed-fills` instead of the top of the page, and carries an
"Apply missed fills →" chip. The chip renders only on a *linked* row: on the
per-bot list the control is already on the same page, and a chip that looks like
an action but is not a link would be a lie. One shared predicate
(`isOpenDriftAlert`) drives both the feed's link and the bot page's gate, so the
feed can never advertise a repair the bot page would not offer.

**The link scrolls; it does not act.** The hash brings the control into view and
tints its border; the dialog still has to be opened by hand. A confirmation a link
can open is not a confirmation.

### Tests: six, at the endpoint, each asserting a claim the UI makes

The dashboard still has no test runner (typecheck + build only, unchanged since
10.6), so coverage goes where step 15 put it — `src/api/api.test.ts`. The DO's own
behaviour was already covered by step 18's 15 tests; **the endpoint had none**.
Each new one exists because the UI states it to an operator:

1. **Returns exactly what it corrected** — `applied` equal to the full four-field
   object with money as decimal strings, `skipped` empty, `result.status` and the
   refreshed `bot` both still `halted`, the D1 order `filled`, one trade row, and
   `bot.missed_fills_applied` audited to the **verified human**.
2. **409 `invalid_status` on a running bot**, and no trade written — the refusal
   the UI mirrors pre-flight.
3. **An unreadable order is a 200 with `skipped` non-empty** — the "a success is
   not a repair" contract the partial branch depends on.
4. **"No per-fill detail" is distinguished from "nothing filled"** — the
   distinction the skipped legend must not flatten.
5. **Idempotent over the wire**: a second POST applies nothing and the trade count
   stays 1 — the "outcome unknown, retrying is safe" copy is a claim about this.
6. **A grid repair places NO order** through the real endpoint — the grid dialog's
   central promise, previously asserted only at the DO level.

### Addendum (same day): 18.1's open question 2 is closed, not carried

The entry above recorded the shared-alert-type risk and deferred it to "the
shared generated contract 10.6's open question 2 already names". That deferral
was wrong for this particular string, and the reason is the failure *mode* rather
than the size of the duplication: every other hand-mirrored contract in this
project fails **loudly** — a renamed API field surfaces as a runtime `undefined`
in the UI, a renamed request field as a 400. This one fails **silently**. The
repair button stops appearing on a bot that has drift, which on screen is
indistinguishable from "there is no drift", on the one surface whose entire job is
to make a known-wrong position visible. That is step 16's bug 2 in miniature (143
passes that read nothing and alerted nothing), and it does not belong in a
backlog.

It was also worse than described: the format had **four** independent copies, not
two. `reconcile.ts` built it at both raise sites, `resolveClearedAlerts` matched it
with a pair of hand-written `startsWith("reconciliation_severe_")` /
`startsWith("reconciliation_meaningful_")` checks, and `driftAlerts.ts` rebuilt it
a third time. A new tier would have had to be remembered in three places.

**`src/shared/alert-types.ts`** is now the only place the format is spelled:
`reconciliationAlertType(tier, kind)`, `isReconciliationAlertType`,
`ALERTING_TIERS` (`minor` deliberately absent — it raises no row), and
`ORDER_STATE_DRIFT_ALERT_TYPES`. Every one of the four sites goes through it.

**This is the one file the dashboard imports from the Worker's source tree**, and
that crossing is the point rather than a shortcut — a re-derived copy is exactly
what fails silently. It is constrained to earn the exception: **dependency-free by
contract**, no imports at all, so both toolchains compile it unchanged despite the
deliberate TypeScript 5.7 / 7 split (10.6 decision 3). Verified rather than
assumed: `tsc -b && vite build` clean (73 modules, one more than before), and
`vite dev` serves it over `/@fs/` with no `server.fs.allow` change needed — checked
with a real request, not reasoned about.

Because the shared module cannot import `findings.ts` (that would drag Worker
types into the dashboard), the tie runs the other way, as two type assertions that
do real work:

```ts
export const ORDER_STATE_DRIFT_FINDING_KINDS: readonly FindingKind[] = ORDER_STATE_DRIFT_KINDS;
export const ALERTING_DRIFT_TIERS: readonly DriftClassification[] = ALERTING_TIERS;
```

Renaming a `FindingKind` or a `DriftClassification` now fails the Worker typecheck
at those two lines instead of quietly emptying a set.

**Seven tests, and the lists in them are derived, never hand-maintained** — a
second hand-copied list would have reproduced the bug being closed. Six in
`src/shared/alert-types.test.ts` (which imports the dashboard's own predicate,
since the dashboard still has no test runner): every drift alert type the writer
can produce is recognised; every *other* `FindingKind` — read from `TIER_FLOOR`'s
keys, so a new kind is covered the moment it exists — is not, which also pins the
deliberate `cancel_fill_discrepancy` / `cancel_failed` exclusions; the gate's set
contains nothing the writer cannot construct (catching a stale entry left by a
rename); and a resolved alert never offers the repair. The seventh is in
`reconcile.test.ts` and is the end-to-end one: it drives the **real** detection and
`raiseStandingAlert`, serializes the written row through the **real** `alertView`,
and asks the dashboard's predicate whether it would offer the control.

Mutation-checked, four mutants, all caught:

| mutant | result |
| --- | --- |
| change the shared format to `reconciliation_{tier}-{kind}` | 9 failures |
| dashboard rebuilds its own set with one typo'd member | 2 failures |
| widen the drift set to include `cancel_failed` | 1 failure |
| rename a `FindingKind` in `findings.ts` alone | typecheck error, before any test runs |

The first is worth noting: it fails 9 tests, because the existing suite already
pinned the literal wire format (`reconcile.test.ts`, `dispatch.test.ts`). The
format was never the unprotected part — the *agreement between the two sides* was.

Backend `tsc --noEmit` clean, dashboard build clean, full suite **1416 pass**
(1409 + 7). 18.1's open questions 1 and 3 stand.
