## PART 1 — ⚠ THE FIDELITY FINDING, AND THE BRIEF HAD IT BACKWARDS

The brief for this step asked, as requirement 1, whether a stored row could be
reconstructed into the same wire shape `ProposalView` already renders — and named
the expected answer:

> *"If reconstruction is NOT fully faithful (e.g. some transient wire-only field
> like envelope/duplicateKeyCheck isn't persisted), report that precisely."*

**It was traced through source before anything was built, and the premise does not
hold. Nothing is lost. The record is a strict SUPERSET of the response**, and the
reason is mechanical rather than fortunate.

### The trace, in three lines of `getAccountDerive`

```ts
const inputs    = deriveProposalInputsView(result, set.selectedAt);   // called ONCE
const reasoning = deriveProposalReasoningView(result, latencyMs);
await logDeriveProposal(proposalLogPorts(ctx), result, { ..., inputs, reasoning });
return ok({ entryPoint, selectedAt, proposalId: record.id,
            bundle: inputs.bundle, context: inputs.context,
            assessment: inputs.assessment,
            derive: deriveResultView(result, latencyMs) });
```

and, in `serialize.ts`:

```ts
export function deriveProposalReasoningView(result, latencyMs) {
  return { ...deriveResultView(result, latencyMs), promptText, response };
}
```

**The reasoning view is the response's own `derive` object, SPREAD, plus two
fields.** So `envelope`, `duplicateKeyCheck`, `settings`, `latencyMs`, `promptChars`
and `promptVersion` are all inside `reasoning_json` — **they were never wire-only,
so there was never anything to lose.** `serialize.ts` had already stated the
property that makes this true, in its own words, and it is the sentence the whole
step turns out to rest on:

> **THE HANDLER STORES THE VERY OBJECT IT PUTS IN THE RESPONSE.** *"'what was stored
> differs from what the human was shown' is not a bug that can be introduced here;
> it would take deleting a parameter."*

### The consequence, which is the design rather than a detail

Because the stored payload IS the response, **history does not reconstruct an
approximation and then render it with a parallel component. It reassembles the real
response and hands it to the unchanged `ProposalView`.** Same summary card, same
concentration banner, same three-way citation classification, same evidence tables
and offered/cited difference, same `<details>` collapse rule, and the same staleness
policy recomputed on the same one-second tick. A proposal from last week and one
from thirty seconds ago go through the same code.

| wire field | where the row keeps it |
| --- | --- |
| `entryPoint` | the `entry_point` **column** |
| `proposalId` | the `id` **column** |
| `selectedAt`, `bundle`, `context`, `assessment` | `inputs_json` |
| `derive` / `assess` | `reasoning_json`, less the two record-only fields |

⚠ **THE TWO SCALARS COME OFF THE COLUMNS, NOT THE PAYLOAD, AND THAT IS LOAD-BEARING
IN BOTH CASES.** `getAccountDerive` writes the literal `"named"` into its response
because it serves one door; the COLUMN holds the real entry point, and the CHECK
constraint already names `watchlist` and `general` (deliberately, since SQLite
cannot widen a CHECK without rebuilding the permanent record). Reading the literal
would render every historical proposal as `named` the day a second door produced
one, and nothing would fail. And `proposalId` is what an operator copies into
`POST /api/bots` and the reject endpoint — an id taken from a payload is an id that
can be **wrong**, which would attach a decision to a different proposal in a record
nothing can delete. **The mutation section's R2 is exactly this fault, and it SURVIVED.**

### ⚠ THE ONE LOSS THAT COULD HAVE EXISTED, AND WHY IT DOES NOT

The D1 JSON codec is plain `JSON.stringify` / `JSON.parse` (`columns.ts`), and the
wire is JSON too, so the two are identical by construction. **The single class of
loss available is that `JSON.stringify` DROPS a key whose value is `undefined` and
KEEPS one whose value is `null`** — and entry 45's crash fix turns on precisely that
difference: the views emit `null` for an unset optional (`takeProfitAmount`,
`breakoutThresholdPct`, `missingHistoryMs`) and never omit the key, while
`ProposalParameters` reads an ABSENT key as a fault.

**If storage had lost those keys, a historical grid proposal would render entry 45's
red shape-mismatch banner instead of its parameters.** It does not, and that is
asserted rather than reasoned: every stored payload in `proposal-replay.test.ts` is
driven through a real `JSON.parse(JSON.stringify(...))` round trip first, because
that is not a formality — it is literally what the `json()` codec does in both
directions.

### How the claim is pinned, and why not with a hand-written expected object

A test asserting the replay against a typed-out expected shape would pin **this
module's belief** about the wire contract rather than the contract, and would keep
passing on the day `serialize.ts` gained a field. So it is
`resubmission.test.ts`'s pattern one layer up:

- the decisive unit tests **build the live response the way the handler builds it**,
  from the same functions over the same result object, and compare;
- `REPLAY_STAGE_FIELDS` is pinned **in both directions** against the key set the real
  `assessResultView` / `deriveResultView` emit — one direction alone would let the
  replay demand a field the view never sends, or refuse a good record;
- a test asserts that each reasoning view **is** its stage view plus exactly
  `RECORD_ONLY_FIELDS`, so a third record-only field added later fails there rather
  than silently changing what history renders;
- and the decisive test of all is in `api.test.ts` against **real D1**: run a real
  `/assess` and a real `/derive`, capture the real response bodies, read the rows
  back through the real endpoint, and `toEqual` the whole objects. Every layer —
  `JSON.stringify` into a TEXT column, SQLite, `JSON.parse` out, the handler,
  `JSON.stringify` onto the wire again — is in that loop.

### The two fields the record has that the wire never did

`promptText` (~16 KB Stage 2, ~23 KB Stage 3) and `response` (the transport's answer,
`text` and `raw`) are **cut OUT of the replayed stage object** — *"the same shape"*
has to mean the same shape, and an object carrying two keys no live response ever
carried is a different object — and **published beside it in `recordOnly`.**
Withholding them would be the summarization section 8.7 forbids, from the one
endpoint that reads the record they exist for, and 21.7 open question 3 cannot be
settled without the bytes. Entry 45's live check 2 confirmed the prompt is *"stored
server-side, never returned over the wire"*; **this is the one endpoint where that
changes, on purpose.**

## PART 3 — WHAT A HISTORICAL RECORD GENUINELY CANNOT DO, AND NEITHER IS A STORAGE LOSS

Two real limits. Both are published **as data on the wire**
(`replay.fidelity.assessResponseUnavailable`, `renderableByProposalView`) rather than
left for a reader to infer from an absent section, which is entry 44's rule: an
unstated gap is the failure mode; a stated one is a limitation.

### 1. ⚠ A DERIVE RECORD CANNOT SHOW STAGE 2's OWN EVIDENCE, AND MIGRATION 0009 SAID SO FIRST

`ProposalView` takes an OPTIONAL `assess`, and with it renders Stage 2's own evidence
table and the two-gather drift comparison. A derive row does not carry the id of the
assess row it derives from — and entry 45 recorded that as a **decision**, in
capitals, rather than as a gap discovered later:

> ⚠ **WHAT IS NOT LINKED, stated rather than left to be found: a `derive` row does
> NOT carry the id of the `assess` row it derives from.** Nothing in the request
> carries that link, and an `assessProposalId` taken from the caller would be a
> client-asserted claim this system cannot verify.

So `/proposals/:id` renders with `assess={null}` — **which is not a degraded mode
invented for history.** It is the state `ProposalView` has supported since step 44,
and exactly what a reviewer holding only the derive response has always seen. The
FULL Stage 3 proposal is present; what is absent is the second stage's raw evidence
set, which was never on this row. A banner above the proposal says so in those terms.

### 2. ⚠ AN ASSESS RECORD CANNOT GO THROUGH `ProposalView` AT ALL, AND THAT IS STRUCTURAL

`ProposalView` is built around a derivation: headline numbers off `proposal.params`,
per-field citations, an allocated capital, a reference price. **An assessment has
none of those** — which is the same fact migration 0009 enforces in SQL as
`only_a_derivation_can_be_approved`: *"an assessment carries a strategy choice and
its reasons, not the parameters a bot needs."*

**The payload is NOT what is missing.** An assess row rebuilds into the exact
`AssessResponse` the live endpoint returned, asserted against a real `/assess` run.
What cannot be reused is the RENDERER, so `ProposalAssessRecord` renders it — and it
is deliberately **not** a second proposal renderer:

- **reused unchanged**, because they are genuinely about a bundle or an evidence set:
  `ProposalConcentration` (all three states, including entry 49's `unknown`),
  `CitationLegend`, `CitationList` (including the never-collapsed *"rests on no
  fetched data"* warning), and `EvidenceTable` — which was **exported rather than
  copied**, because a second copy of the offered/cited difference is the *"copy that
  drifts is the one nobody is watching"* fault this project refuses everywhere else.
- **deliberately absent, and each absence NAMED ON THE PAGE:** no freshness table and
  no data-limits panel. Both are computed over Stage 3's own two reads — the capital
  ledger and the venue filters — **and Stage 2 made neither.** A four-row table with
  two rows blank would report *"the capital ledger's age is unknown"* about a stage
  that never read the capital ledger, which is entry 49 PART 3's exact fault: an
  unestablished state rendering as an established one.

⚠ **AND NO STALENESS VERDICT IS COMPUTED THERE.** The fetch time is printed as a
time; nothing judges it. `stalenessOf` is per-input and per-strategy, and a narrower
second implementation over one of the four inputs would be a policy copy that drifts
from the one the proposal view uses.

## PART 4 — ⚠ A PROJECTION ADDED TO /src/db, AND WHY THE ALTERNATIVE CONTRADICTED THE TABLE'S OWN FOUNDING ARGUMENT

**The one storage-layer change in this step, argued rather than slipped in, because
entry 45 stated the absence of exactly this as a fact about the layer.**

Migration 0009's THIRD argument for giving proposals their own table was measured
rather than estimated:

> **EVERY READ OF `audit_log` WOULD PAY FOR THE PAYLOAD, AND THE COST WAS MEASURED
> RATHER THAN ESTIMATED.** `Repository.findMany` always selects the full generated
> column list; **there is no projection anywhere in the layer.** … a test builds the
> deepest payload this pipeline can produce … and reports **290,459 bytes**.

**That argument does not stop applying to `proposals` itself.** A list endpoint is
exactly the read that needs `pair`, `stage`, `outcome` and `created_at` and needs
NEITHER `inputs_json` NOR `reasoning_json` — and `SELECT *` for a 25-row page is up
to ~7 MB of candle windows and prompts read, decoded and thrown away to render a
table of short strings. **Building the list on `findMany` would have reproduced,
inside the table that exists because of that argument, the exact cost the argument
was about.**

So the layer gained a projection rather than the endpoint gaining a workaround:

- **`findManyProjected(columns, options)`**, returning `Pick<Row, K>` — so reading a
  column you did not project is a **compile error**, not an `undefined` that renders
  as a blank cell.
- It shares `#where`, `#tail` and every per-column codec with `findMany`, so a money
  column still arrives through its `CAST(… AS TEXT)` and a JSON column still parses.
  The batched form cannot drift from the executed one for the same reason the rest of
  this class cannot.
- ⚠ **IT ADDS NO WAY TO WRITE AND NO WAY TO DELETE.** `proposal-log.test.ts` asserts
  the absence of `delete` / `deleteMany` / `truncate` / `remove` on the real
  repository object precisely so a future widening fails where the section 8.7
  retention promise is written down. **This widening is a narrower READ, which is the
  one direction that promise does not constrain**, and a test in `table.test.ts`
  re-asserts the absence beside the new method.

`PROPOSAL_LIST_COLUMNS` + `PROPOSAL_PAYLOAD_COLUMNS` are asserted equal to the
table's own column set, so **a column added to `proposals` later fails that test
rather than silently never being listed** — `schema.test.ts`'s literal-table-list
rule, applied to a projection.

## PART 5 — ⚠ THE SECOND BRIEFED FINDING WHOSE PREMISE DID NOT EXIST: "THE KEYSET PAGINATION CHOICE"

**A whole design decision, asked for by name, that was never made. Recorded here
rather than written up, and then answered on its merits — because unlike PART 2, the
concern behind it is REAL and the build does not close it.**

The brief asked this entry to cover:

> *"the keyset pagination choice and why (correctness under concurrent inserts, since
> this table is actively written to by live proposal generation)"*

**There is no keyset pagination in this system.** `listProposals` passes
`limit` and `offset` to `findManyProjected` and runs a second `COUNT(*)`; the
handler, the query module and its 32 tests are all written in those terms, and
`Repository`'s `#tail` emits `LIMIT ? OFFSET ?`. Writing up a seek-method design
would have described code that does not exist, in the one document a future reader
trusts about why things are the way they are.

### What was actually built, and the one part of the concern it DOES answer

`ORDER BY created_at DESC, id DESC` — **a total order, and the tie-break is not
decoration.** `/assess` and `/derive` write two rows that can share a millisecond,
and `proposal-log.test.ts` drives an injected clock that makes ties routine. Under
LIMIT/OFFSET an unstable sort does not merely reorder: **a row can appear on two
consecutive pages while another appears on neither**, which is a paging bug that
looks like data loss. That is closed, and an end-to-end test drives five real
proposals written in one millisecond through three consecutive two-row pages and asserts the
union is all five, each exactly once.

The cap is **refused rather than clamped**, for a related reason: a silently
shortened page looks complete, and paging on from it skips the records it did not
show.

### ⚠ WHAT IS NOT CLOSED, AND THE BRIEF WAS RIGHT ABOUT IT

**OFFSET PAGING IS NOT STABLE UNDER CONCURRENT INSERTS, AND THIS TABLE IS ACTIVELY
WRITTEN TO.** The mechanism, stated exactly:

- rows are ordered **newest first**, so a new proposal is inserted at the **TOP**;
- entry 46's trigger writes **two** rows per press, and entry 49 observed that they
  accumulate faster now that a button produces them;
- so a proposal generated while a human is reading page 1 shifts everything down by
  two, and **paging to `offset=25` re-shows two rows already seen** — and, at the
  boundary, can hide a row entirely.

**Keyset (seek) pagination on `(created_at, id) < (last_created_at, last_id)` is
immune to it**, because the cursor names a position in the data rather than a count
of rows skipped, and this table already has the total order that makes such a cursor
well-defined and `idx_proposals_created` to serve it.

**It is a named open item, not a deferred plan, and it is deliberately not built
here** for two reasons stated so they can be argued with rather than discovered:

1. **Keyset paging cannot answer `total`.** *"26–50 of 312"*, a last page and a page
   count all need a `COUNT(*)`, and the seek method offers a next cursor and nothing
   else. Whether an operator browsing a permanent record wants a stable window or a
   real denominator is a **product** question this session should not settle alone —
   and 21.5's whole signal is a RATE, which makes the denominator less obviously
   expendable here than in an ordinary feed.
2. **The observed failure is duplication, not loss.** A shifted offset re-shows rows;
   with the total order in place it cannot silently drop one from an unstable sort.
   That is a real defect and it is a mild one, and the row that a boundary case could
   hide remains reachable by any other filter or by the neighbouring page.

⚠ **AND THE SMALLER RACE IS STATED IN SOURCE RATHER THAN HIDDEN:** `total` is a
SECOND query at a slightly different instant from the page read, so a row written
between them makes the count one larger than the page it describes. **It is not
corrected**, the only writer is a real paid inference, and the drift is one row per
real run.

## PART 6 — THE READ-ONLY GUARANTEE

**The guarantee this step is judged on**, and the narrow statement of it first.

`proposals.outcome` moves off NULL in exactly two places in this whole system:
`recordProposalApproval`, reached only from `POST /api/bots` and only AFTER `create`
has returned a real bot, and `rejectProposal`, reached only from
`POST /api/proposals/:id/reject`. **Neither is reachable from this feature.** Both
new routes are `GET`; the handlers run one `findManyProjected`, one `COUNT(*)` and
one `findOne` between them, and write no row, no `audit_log` entry and no outcome.

Three things hold it, and the third is the one that could have rotted:

**1. A real end-to-end test against real D1.** Run a real `/assess` and a real
`/derive`, then browse the list and open both records through the real endpoints, and
assert against **the real rows**: all four outcome columns still NULL on both, zero
bot rows, and **the `audit_log` count unchanged** — a check on real state, not a
restatement of the test's own setup.

**2. No create-bot control, and it is a SUPPRESSION rather than a fork.**
`ProposalRecord` passes `offerCreateBot={false}` to the SAME `ProposalView`. The path
from a proposal to a bot exists **once**, through a live proposal, built to entry
46's four agreed constraints — and a second entry point from history would be a
second place the copy that stops a human mistaking a prefill for an approval lives
and drifts. ⚠ **It suppresses an AFFORDANCE, never a guarantee:**
`prefill-does-not-approve.test.ts` holds identically either way, `createBot` is still
called in exactly one place in the whole dashboard, and the guard now asserts that
`offerCreateBot={false}` appears in **exactly one file** — so a future page cannot
quietly acquire the suppression, and the live pages cannot quietly lose the link.

**3. ⚠ THE GUARD CAUGHT THIS STEP'S OWN PAGE COPY, AND THE COPY WAS CHANGED RATHER
THAN THE GUARD.** `prefill-does-not-approve.test.ts` fails the build when a proposal
page contains `/reject`, and it cannot tell a call from prose about a call. The
history page's footer explained that rejection is curl-only and **spelled the path**,
so the build went red. **Loosening a guard so a sentence can pass is how a guard
stops being one**, so the sentence was rewritten to name the endpoint without its
path, and the full path with the real id is still printed where it is actually usable
— on each proposal's own record page. The reason is recorded in the source beside the
copy, so the next person does not "fix" it back.

Both history pages were also added to that guard's page list, and they are the two
that most needed it: **unlike the others they DO import `api/client`, because reading
the record is what they are for**, so "they read and never write" is a property the
navigation-path rule structurally cannot cover. A new assertion checks them against
the same twelve-writer list.

### The two survivors are the value of the exercise, and BOTH exposed a missing or misdirected TEST rather than a missing check

**R2 — `proposalId` read from the payload with a fallback to the row, and nothing
failed.** No real payload carries that key, so the fallback always fired: **the check
had no test behind it at all.** This is entry 45's mutant M3 in a new place and its
fix is M3's — that fixture *"put the wrong strategy only under `reasoning`, so a
mutant reading `inputs.strategy` found nothing to read"*, and the close was *"putting
a conflicting twin of every scalar where a mutant would look."* Two tests now store
payloads carrying **conflicting twins of both scalars in BOTH payloads** and assert
the row wins. It matters because `proposalId` is what an operator copies into
`POST /api/bots` and the reject endpoint.

**Q1 — `hasMore` from `offset + limit`, and THE TEST NAMED FOR CATCHING IT WAS
GREEN.** All three of its cases give the same answer under both formulas, so it
asserted the right property against inputs that could not discriminate. ⚠ **This is

it stated** (see also the `1e3` bug below), and it also disproved a sentence in this
step's own source: the docblock claimed the two formulas *"differ on the last page"*,
and on an ordinary last page they agree. **They differ on exactly one region** — a
page that comes back SHORTER than the limit while more rows still match — which is
reachable here precisely because `total` is a second query at a different instant.
The test now leads with that case and the docblock was corrected rather than left
plausible.

### ⚠ R10's FIRST ATTEMPT WAS INEFFECTIVE, AND SAYING SO IS THE POINT

It inserted an inert extra key into `REPLAY_STAGE_FIELDS` rather than swapping the
two lists, and **survived for a reason that had nothing to do with test coverage.**
Caught by inspecting a survivor rather than reporting it; re-expressed as a real
swap, it was caught by 8 tests. **A survivor is a question, not a result** — entry 49
recorded the same discipline for the same reason, and a mutation report that never
mentions a bad mutant is one nobody checked.

### ⚠ A REAL BUG FOUND BY A TEST BEFORE ANY MUTANT RAN, AND ITS SISTER TEST WAS ALSO PASSING FOR THE WRONG REASON

Both `parseCount` (backend) and `historyOffsetFrom` (dashboard) validated with
`Number.isInteger(Number(raw))` — **which accepts `"1e3"`, because `Number("1e3")` is
exactly 1000.** They also accepted `"5.0"`, `"+5"` and `"0x10"`. The dashboard's own
test caught it on its first run.

**And the backend test asserting that `limit=1e3` was refused had been passing for
the wrong reason:** 1e3 parses to 1000, 1000 exceeds `MAX_PROPOSAL_LIMIT`, and the
**cap** refused it while the **parse** waved it through. `offset` has no cap, so
there the same hole had nothing behind it and `offset=1e3` was accepted outright.
Both now match digits as text before converting (with `Number.isSafeInteger` still
asserted after, for the 2^53 bound `columns.ts` enforces on every integer column),
and the test pins a value **inside** the cap so only the parse can refuse it.

### Assumptions and limits, stated so they can be checked rather than discovered

1. **The reconstruction is exact for every row this pipeline has ever written**, and
   that is a property of the handler storing the object it returns. A row written by a
   different `serialize.ts` would carry unexpected fields; those are **reported and
   carried through, never refused** (a table with no delete path will outlive its
   serializers), and the page names them.
2. ⚠ **PART 7's "all four inputs past threshold" is not confirmed.** At 126 h the
   7-day venue-rules threshold had not been crossed; three of four had. The overall
   `STALE` verdict is correct either way.
3. **`accountLabel` is NOT checked against the account registry**, deliberately
   diverging from `listWatchlist`, which 404s an unknown label. Section 8.7 keeps
   every row forever and an account can be de-registered, so a 404 driven by today's
   registry would hide undeletable history. The typo hole is closed at the UI end by a
   `<select>`, not by the endpoint.
4. **`total` is a second query at a different instant from the page read** and can
   disagree by a row. Not corrected; stated in source.
5. **The history list does not poll**, unlike every other list view. An append-only
   record does not change while it is read, and entry 46's polling investigation is
   still open — adding a fifth timer to it would be the wrong contribution. There is an
   explicit refresh.
6. **The re-run link carries no query parameters**, because `ProposalRun.tsx` reads

   and ignored"*, which `parseResubmittedAssessment` refuses one layer down for the
   same reason. The copy names the account and pair instead.
7. **`ProposalView`'s header and footer copy is now conditional** on `offerCreateBot`.

   record it is false, and it is the one sentence a reader would act on.
8. **`proposalRecordView`'s docblock claimed the two payload sizes were "published
   instead", and they never were.** The comment was corrected; no behaviour changed.
9. **One live browse is one observation.** The 11 records, the four outcome figures
   and the 126-hour staleness verdict are each a single real observation, not a rate.
10. **The 89-second failing run's failing tests are unknown**, and the contention
    explanation is a hypothesis.
11. **The pre-existing `[vitest-pool]` teardown error is present in every run** and is
