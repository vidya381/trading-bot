## PART 1 — THE BUG: A SEVERITY INVERSION

Entry 79 built `grid_ladder_vacant`, a standing alert whose entire purpose is
**reassurance**. A grid bot whose spot price has fallen below its lowest grid
line — but not below its stop-loss — is `running`, subscribed, evaluating the
market, and correctly placing nothing. From outside, that is indistinguishable
from the dead-ladder defect entry 79 existed to fix. The alert says which one you
are looking at. It is informational. It is not about trading, risk, or capital.

**It ran on every price-update tick, and it made its own database call to do so.**

`#reportLadderVacancy` is reached from the `place_initial_ladder` branch, and
entry 79's own `decide` docblock already recorded why that branch re-fires
forever in this state: *"a FRESH bot started below its stop-loss places nothing …
and, now that a zero-order pass no longer latches `placed`, would re-enter this
gate on every tick."* Candles are one minute. So for an idle-below-range grid
bot, the advisory check ran **once per minute, indefinitely**, each time reading
`alerts` from D1 through `raiseStandingAlert`.

That call sat inside the `try` of `#onPriceUpdatePass`, whose **only** handler is
`#haltOnUnexpected` — a handler that responds to any exception by halting the
bot permanently.

**This is the inversion, stated plainly: a cosmetic status report had the power
to stop real trading, while the actual trading logic in the same pass was
entirely unaffected by whatever went wrong.** The pass had already made its
trading decision — `gridDecide` had run, `#placeInitialLadder` had returned, the
`PipelineResult` was already computed — before the advisory check was even
reached. Nothing the bot does with money depended on it. It could halt the bot
anyway, because it shared an error-handling path with genuine trading failures.

### The live incident

On **2026-08-25 at 9:07 PM**, roughly two hours after entry 79 deployed, real
testnet grid bot **`bot-gnqel3`** halted with:

```
unhandled_error: Error: D1_ERROR: D1 DB storage operation exceeded timeout
which caused object to be reset.
```

The bot was healthy. It was correctly idle, sitting below its grid range,
watching price, holding no position and no open orders.

**The prior investigation's conclusion, referenced and not re-derived here:** that
error string appears **nowhere** in this codebase outside test fixtures, and the
D1 access layer wraps D1 in no try/catch, no retry and no timeout logic of its
own — the message is a **raw Cloudflare platform error**, surfaced verbatim
through `#haltOnUnexpected`'s `${error.name}: ${error.message}`. It was a
transient, platform-side event, **unrelated to this codebase and unrelated to the
operator's own local network** (every alert involved is written by code running
inside Cloudflare, about failures observed inside Cloudflare). The investigation
further established that the halt itself was safe: `openOrderIds` was empty, so
`#cancelOpenOrders` made zero exchange calls, and DO storage records `halted`
before any D1 work. No data was lost.

**THIS ENTRY DOES NOT FIX THE D1 TIMEOUT.** The platform blip was a one-off
external event and is not this codebase's to fix. What is fixed is **this
codebase's response** to any such failure on this one advisory path.

## PART 2 — THE FIX, AND TWO CORRECTIONS TO THE BUILD BRIEF

The vacancy check now **fails silently rather than halting the bot**. If it
cannot complete, for any reason, the failure is swallowed and the price-update
pass continues exactly as if the check had never been attempted. Nothing is lost
by skipping a tick: the gate re-fires every tick while the condition holds, so
the check is retried automatically the next minute regardless.

Two things were found by **tracing the current source**, not assumed, and both
correct the brief this build started from.

### Correction 1 — there are TWO database operations at risk, not one

The brief named one. `#reportLadderVacancy` has two branches, and **each makes
its own separate D1 call**:

| Branch | Condition | D1 call |
| --- | --- | --- |
| **Raise** | ladder still vacant | `#raiseStanding` → `raiseStandingAlert` → `alerts.findMany` |
| **Resolve** | ladder no longer vacant | `resolveClearedStandingAlerts` → `alerts.findMany` |

Both needed the same protection. Wrapping only the raise half would have left the
resolving branch — the one a **recovering** bot reaches as price returns into
range — exposed to the identical halt. A test in PART 3 covers each branch
separately for exactly this reason.

### Correction 2 — the fix belongs at the call site, NOT in the shared function

The obvious-looking fix is to make `raiseStandingAlert` swallow its own failures.
**That would have quietly defanged alerts that are supposed to be loud.** The
shared standing-alert machinery in `alerts/standing.ts` is used far beyond this
one advisory case:

| Shared function | Call sites verified this session |
| --- | --- |
| `raiseStandingAlert` | **2** direct in `reconciliation/reconcile.ts` (lines 360, 1563 — reconciliation's own **critical** findings), plus `#raiseStanding` in `bot-instance.ts` with **6** call sites, of which **5 are not this one** — including `poll_blind` (line 3092) and `poll_blind_escalated` (line 3104), the poll-blindness detector |
| `resolveClearedStandingAlerts` | **4** non-test sites, of which **3 are not this one**: `reconcile.ts:408`, `reconcile.ts:1527`, and `bot-instance.ts:2574` (the poll's own resolve half) |

Silencing failures inside `standing.ts` would have suppressed reconciliation's
critical findings and hidden a bot that had gone **genuinely blind to its own
open orders** — the precise condition `poll_blind` exists to shout about. Fixing
narrowly, at this one advisory call site, was **necessary to avoid weakening real
safety mechanisms elsewhere in the same shared code**. `alerts/standing.ts` is
untouched by this entry.

### The scope judgment, documented at the fix site

**The entire advisory check is wrapped, not only its database calls.** The method
opens with a `#state()` read — DO storage, not D1 — and halting over that failure
would be just as pointless: the pass has already read state successfully and
already decided, and the `PipelineResult` is already computed. Narrowing the
`catch` to the D1 lines alone would have left a second way for a purely advisory
report to halt a bot it has no business halting. The method's contract is now
simply **"this never throws"**, and the docblock states why.

### The diagnostic improvement, and why it is in scope

The investigation recorded a secondary finding: `#haltOnUnexpected` records only
`${error.name}: ${error.message}` and **discards the stack**, which is why
identifying the failing call site took an exhaustive elimination of alternatives
rather than a glance. This fix's failure path now logs the **bot's own id, the
full error object, and its stack trace at the point of capture**, via
`console.error` — matching the existing swallow-and-log precedent at
`api/handlers.ts:696`, with `observability` already enabled in `wrangler.jsonc`.

**Logged, not alerted, deliberately.** Raising an alert row about a failed alert
would be a D1 write — precisely the operation that just failed — reintroducing
the exact risk the `catch` exists to remove.

**This is explicitly NOT a rework of `#haltOnUnexpected`**, which is unchanged
for every other case in the system. A future advisory operation failing this way
should be easier to place than this one was; that is the whole of the intended
benefit.

## PART 3 — VERIFICATION

### The four new tests, each named

All in `grid-bot-instance.test.ts`, under
`describe("the vacancy report is best-effort and cannot halt the bot")`.

1. **`does not halt when the vacancy alert's own D1 read fails`** — the live
   incident reproduced verbatim. Spot at 85 (below the lowest line at 90, above
   the stop-loss at 81), with `alerts.findMany` throwing the **real platform
   string**, `D1_ERROR: D1 DB storage operation exceeded timeout which caused
   object to be reset.` Asserts the pass returns `running` / `placed_initial_ladder`;
   DO state is `running` with a null halt reason; D1 mirrors `running`; no system
   alert row was written; **and the very next tick, with D1 healthy, raises the
   vacancy alert cleanly** — proving nothing is lost by the skipped tick.
2. **`does not halt when the RESOLVE half's D1 read fails`** — the second branch
   found in PART 2. A recovering bot returning into range reaches
   `resolveClearedStandingAlerts`; asserts the bot stays `running` and that the
   ladder was still built, so the failure touched only the reporting.
3. **`leaves the ordinary path completely unregressed`** — the full
   raise-then-resolve lifecycle against a healthy database: one row raised, still
   exactly one row after a second idle tick (standing, not per-tick), then
   resolved once price returns into range and the ladder places.
4. **`still halts on an unrelated failure in the same pass`** — **a SCOPE-PROOF,
   not a regression guard.** A genuine trading write (`orders.insert`, the order
   mirror) fails in the same pass, reached from the same `try`; asserts the bot
   **does** still halt with `unhandled_error … exceeded timeout`. This proves the
   fix did not become a blanket suppression of the bot's real safety mechanism.

Test doubles proxy the real `Database`, replacing exactly one repository method
with a thrower and binding all other methods to the real instance — `Database`
and `Repository` both hold `#` private fields, which resolve against the actual
instance and would throw if `this` were the proxy. The existing `run()` helper
gained one **additive** optional `database` parameter defaulting to the suite's
real D1; **no existing call site changed**.

`npx tsc --noEmit` exits **0**.

### Mutation testing

The fix was reverted to its **exact pre-fix state** — the `try`/`catch` removed
and the body restored byte-for-byte, docblock retained — and the four tests re-run:

| Test | Against the mutant |
| --- | --- |
| 1. vacancy read fails | **FAILED** — `expected 'halted' to be 'running'` |
| 2. RESOLVE read fails | **FAILED** — `expected 'halted' to be 'running'` |
| 3. ordinary path unregressed | passed |
| 4. scope-proof | passed |

**Tests 1 and 2 reproduce the original live incident precisely** — the mutant

**Tests 3 and 4 passing with AND without the fix is by design, and is stated here
rather than glossed:** neither tests the `catch`. Test 3 asserts the healthy path
was not disturbed; test 4 asserts the halt mechanism still works for real
failures. Both must hold in either state, and a mutation result of "all four
failed" would have meant the scope-proof was accidentally coupled to the fix.

The fix was then restored and `tsc --noEmit` re-run clean.

## PART 4 — WHAT THIS CONFIRMS EMPIRICALLY ABOUT THE INVESTIGATION

The prior investigation concluded, **by reading code**, that for a grid bot idle
below its own range the vacancy alert's `alerts.findMany` was the **only D1
operation in the entire price-update pass** — everything else that pass touches
(`#config`, `#state`, `#mutateState`) being `ctx.storage`, with no per-tick D1
price mirror. That claim is what made tonight's new code the necessary culprit
rather than a suspect.

**Test 1 confirms that claim empirically, not by re-reading the same source.**
With `alerts.findMany` forced to throw, the rest of the pass **completed
normally** and returned `placed_initial_ladder`. It could not have done so if any
other D1 call existed anywhere on that path — that call would have thrown too,
and the bot would have halted. A code-reading claim has now been converted into a
measured one.
