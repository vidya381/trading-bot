## Step 3: Exchange integration layer
Date: 2026-07-21

### What was built

A new `/src/exchange` folder: `credentials.ts`, and `binance/` holding
`signing.ts`, `filters.ts`, `parse.ts` and `client.ts`, plus an `index.ts` barrel
and a folder README. `src/shared/exchange-client.ts` was revised in place.

`BinanceClient` implements the eight REST methods of section 4.1. 210 tests
across the five new modules (431 in total across the project), all passing,
typecheck clean.

Before writing anything, the exchange's published reference (`rest-api.md`,
`filters.md`, `enums.md`, `errors.md`) was fetched and read directly. Step 2's
open question 3 flagged the supporting types as guesses; four of them were wrong,
and the corrections below come from those documents rather than from memory.

### Decisions made

**1. Every interface method returns `Promise<ExchangeOutcome<T>>`.** *(asked, confirmed)*

Section 4.1 writes them as `Promise<Price>`, `Promise<OrderResult>` and so on.
That signature cannot express section 5.6's central rule.

*Keeping `Promise<T>` and throwing on failure — rejected.* A rejected promise
does not stop a caller from catching the error and carrying on with the value it
already had, which is exactly the confusion between "the price has not moved" and
"we cannot reach the exchange" that section 5.6 exists to prevent. Worse, section
7.5 escalates any unhandled exception to an immediate halt plus alert, so a
routine 503 would become a halt event.

*Adding parallel `try*` methods returning outcomes — rejected.* Doubles an
eight-method interface to sixteen, and leaves the unsafe variant with the
shorter, more inviting name.

With the outcome in the return type, `isUsable` is the only way to the value, so
a failed request cannot reach a stop-loss evaluation without the type system
objecting. Section 5.6 becomes structural rather than advisory.

*Revisit if:* never, realistically. This is the whole point of `downtime.ts`.

**2. The interface is split into `RestExchangeClient` and `ExchangeClient`.** *(asked, confirmed)*

`RestExchangeClient` holds the eight REST methods; `ExchangeClient` extends it
with `subscribeToPriceFeed`. `BinanceClient` implements the former.

*A throwing `subscribeToPriceFeed` stub — rejected.* Section 4.6 puts the
WebSocket inside a Durable Object using the Hibernation API, so the connection
must outlive the request that opened it and cannot belong to a per-request client
object. A stub would make the class *look* complete and fail at runtime; the
split records the boundary at compile time, and code that only reads prices and
places orders can depend on the narrower type.

*Revisit if:* step 6 finds the two-interface split awkward once the Durable
Object implements the second half.

**3. The Binance client lives in `/src/exchange`, a new top-level folder.** *(asked, confirmed)*

*Putting it under `/src/shared/binance/` — rejected.* It would honour step 1's
folder structure, but `/src/shared`'s single defining property is that nothing in
it performs I/O, reads a clock, or touches storage — which is what makes those
modules reusable unchanged in backtest mode (section 13). A module doing real
network I/O next to them would force that claim to be qualified. A second
exchange later becomes a sibling folder here.

This does contradict step 1's decision 9 preference against inventing top-level
folders, and that trade was made deliberately.

**4. Tests drive an injected `fetch` port; the documented `fetchMock` does not exist.** *(asked, confirmed)*

The client takes a `fetch`-shaped option defaulting to the global. The plan was
to test mostly through it and add a few tests through the pool's `fetchMock`, per
section 14's "the tool's request-mocking recipes".

**`fetchMock` is not exported by `@cloudflare/vitest-pool-workers` v0.18.6.** The
`cloudflare:test` module exports exactly nineteen names and `fetchMock` is not
among them; the `MockAgent` types are declared in the `.d.ts` but nothing exports
an instance. Verified against both the type declarations and the shipped runtime
module. This is the same class of problem as step 1's `defineWorkersConfig`
finding: the published docs describe an API the installed version does not have.

The default-wiring tests use `vi.stubGlobal("fetch", ...)` instead, which
establishes the same thing that mattered — that omitting the option really does
reach the runtime's own fetch.

*Revisit at:* any pool upgrade. If `fetchMock` appears, the three
`default fetch wiring` tests could move onto it.

**5. Retrying is the caller's job, not the client's.**

No method retries internally. `withRetry` in `downtime.ts` already takes an
operation of exactly the shape these methods have, so it composes for free.

*Retrying inside the client — rejected.* It would put a retry loop around
`placeOrder`, and section 5.1 is explicit that an order whose outcome is unknown
must be recovered by looking it up, never by re-sending. Making retry opt-in at
the call site keeps that decision visible in the diff.

**6. The rate limiter is a reporting sink, not a gate.**

The client parses `X-MBX-USED-WEIGHT-1M` and calls `syncFromExchange`. It does
not ask permission before a request.

Gating belongs in the RateLimiter Durable Object (section 5.4), which arrives at
step 6 and is the only thing that can see all bots on an account. A per-request
client object cannot. `ENDPOINT_WEIGHTS` is exported now so step 6 has a single
source for the documented per-endpoint costs.

Specifically the *one-minute* header, because `WeightBudget` is configured with a
60-second window; feeding it the hourly total would look like a vastly overspent
minute and stall everything for a full window.

**7. The clock offset is biased 500ms backwards.**

The exchange's timing rule is asymmetric: a request is rejected outright if its
timestamp is more than **one second ahead** of server time, but lateness is
tolerated all the way to `recvWindow`, default **five seconds**. Over-estimating
the offset is therefore five times more dangerous than under-estimating it.

The offset itself is computed against the midpoint of the round trip rather than
against the reply time, since the reported time was true at some unknown instant
between sending and receiving. The round trip is retained and exposed, because a
sample taken over a slow link is a less certain sample.

`timestampFor` **throws** rather than falling back to the raw local clock when
unsynced. A silent fallback would sign with a clock nothing has verified, and it
would surface as an authentication error that says nothing about drift.

**8. A `-1021` response clears the offset; `-1006`/`-1007` are reclassified as transport.**

`-1021 INVALID_TIMESTAMP` drops the offset so the next signed request re-syncs
instead of repeating a rejected timestamp.

`-1006` and `-1007` arrive with 4xx-shaped bodies, which `classifyStatus` would
read as a definite refusal. The exchange's own wording for both is "execution
status unknown" — the order may well be resting on the book. They are
reclassified to `transport`, matching how section 5.6 treats a dropped
connection, so recovery goes through the section 5.1 idempotency records rather
than concluding the order was never placed. This is the single most dangerous
misreading available in this file.

**9. The local timeout (15s) is deliberately longer than the exchange's (10s).**

When the exchange gives up it replies with `-1007`, which confirms the request
was *received* — strictly more information than a locally aborted request
provides. Aborting first would discard that and leave an order's fate less clear.

**10. A 200 whose body will not parse is a failure, not data.**

Non-retryable, since the same request returns the same unreadable body. Section
5.6 admits only valid, successful responses into strategy logic, and a
successfully delivered response this code cannot understand is not one.

**11. `validateOrder` takes a rounding mode, so the two checks genuinely differ.**

Section 4.3 requires validation twice, "as a second, independent check". A single
pure function serves both call sites, but the modes are not the same job:
`adjust` at construction moves values onto the grid; `verify` before sending
reports an off-grid value instead of repairing it.

*Rounding again at send time — rejected.* It would silently repair exactly the
corruption the second check exists to catch, making the second call decorative.

Price rounding is side-dependent (buy floors, sell ceils, each away from the
trader's own interest); quantity always floors regardless of side, because
rounding a quantity up risks an insufficient-balance rejection of the whole
order. This follows step 2's decision 3, which anticipated both.

**12. A filter bound of zero means the rule is disabled.**

The published filter rules state this explicitly for `PRICE_FILTER`. It matters
mechanically as well as semantically: `roundToStep` rejects a non-positive step,
so passing a zero `tickSize` straight through would throw rather than accept the
price unchanged. Applied uniformly to every bound, with tests for each.

**13. An unrecognised symbol status or order status throws.**

*Treating an unknown symbol status as "not tradable" — rejected.* It is the safer
default in isolation, but it would leave a bot permanently and inexplicably idle.
Throwing surfaces as a failed outcome with a real cause, and section 7.5 turns it
into an alert a person can act on. The same reasoning applies to an unmapped
order status: guessing which state an order is in is not acceptable.

Note this is narrower than step 2's decision 5, which added `rejected` and
`expired` precisely so that *documented* statuses never fall through. Every
status the exchange documents is now handled; only a genuine API change reaches
the throw.

### Deviations from the spec

Four of step 2's invented types were wrong against real payloads, exactly as its
open question 3 predicted:

- **`Fill` has no timestamp on the exchange's side.** A fill object is
  `{price, qty, commission, commissionAsset, tradeId}` — no time field at all.
  `Fill.executedAt` is now inherited from the parent order's `transactTime`, so
  every fill in one response shares it. Accurate enough for section 5.5's
  "price at time of fill" (the executions are milliseconds apart) but it is an
  inherited value, not an observed one, and the type says so.
- **`Fill.fillId` maps to `tradeId`, which is a JSON number**, not a string. It
  is stringified immediately so the duplicate-fill check in `applyFill` compares
  identity that cannot be affected by float precision.
- **`OrderStatus.fills` cannot be populated and is now optional.** Neither the
  order-status nor the open-orders endpoint returns a fills array; only the
  order-*placement* response does. A required `readonly Fill[]` could only ever be
  satisfied by `[]`, which would assert "this order has no executions" — false
  for a partially filled order read back later. `cumulativeQuoteQuantity` was
  added as the field that *is* available, and is the only route to an average
  fill price. Per-fill history for such an order must come from the account trade
  list, which is reconciliation's concern at step 7.
- **`SymbolFilters` was missing three order-rejecting rules.** Added `minPrice`
  and `maxPrice` (the price filter has three parts; step 2 modelled only
  `tickSize`), `maxNotional` (the current notional filter is a *range*, not the
  floor section 4.3 describes), and `status` (a symbol can be `HALT`, `BREAK`,
  `END_OF_DAY` or `CANCEL_ONLY`, and no order may be placed then). Both the
  current `NOTIONAL` filter and the legacy `MIN_NOTIONAL` are read, since symbols
  carry one or the other depending on age.

Also:

- **Section 4.1's signatures changed shape** (decision 1) and the interface was
  split in two (decision 2).
- **`Price` carries no exchange timestamp.** The price ticker returns a symbol
  and a price and nothing else, so `Price.at` is *receipt* time. Section 5.6's
  freshness checks key off this field, so what they actually measure is "how long
  since we heard", which is the right question but is not the price's own age.
  Documented on the type.
- **`subscribeToPriceFeed` not built**, per section 4.6 and this session's scope.
- **Section 14's `fetchMock` recipe does not exist** in the installed version
  (decision 4).
- **`cancelOrder` still returns `void`**, matching section 4.1 — but the
  exchange's cancel response actually echoes the cancelled order including how
  much of it had filled. That is discarded. See open question 1. *(Since
  superseded: it now returns `OrderStatus`. See the step 3.1 entry.)*
- **Time-in-force is hardcoded to GTC** rather than added to `OrderRequest`.
  Sections 6.2 and 6.3 place resting ladder orders, section 4.5 rules out market
  orders, and an immediate-or-cancel limit would defeat a grid.
- **No live network call anywhere in the suite**, per section 14. Binance's real
  testnet is deliberately not touched by CI; that remains a separate manual
  verification step.

### Open questions carried forward

Still open from step 2: bot instance ids must be short slugs (2.4); the D1 layer
must enforce CAST-on-read centrally (2.5); coverage measurement is unresolved
(2.6); no integration test yet exercises two modules together (2.8, now partly
addressed — `client.test.ts` drives the real `WeightBudget` from response
headers).

Resolved from step 2: the credential shape (2.1) and whether
`subscribeToPriceFeed` was buildable at step 3 (2.2).

New:

1. **`cancelOrder` discards the exchange's final filled quantity.** The response
   body carries it and section 7.2's halt path cancels orders that may be
   partially filled. Returning it would mean adding a type to section 4.1's
   surface, so it was left alone pending a decision. Worth settling before step 6
   builds the halt path. *(Resolved in step 3.1: it returns `OrderStatus`.)*
2. **The client reports rate-limit weight but does not gate on it.** Nothing yet
   refuses a request that would exceed the budget. Step 6's RateLimiter Durable
   Object closes this, and until then a runaway loop is limited only by the
   exchange.
3. **`Retry-After` is parsed but unused.** `parseRetryAfterMs` exists and is
   tested; no caller consumes it, because retry lives at the call site. Whoever
   wraps these calls in `withRetry` should prefer it over computed backoff when
   the exchange has stated a wait.
4. **A `tradeId` of `-1` would break fill deduplication.** The exchange uses it
   where a trade id does not apply. Normal spot limit fills carry real ids, so
   this is not reachable today, but `applyFill` would reject a second `"-1"` as a
   duplicate.
5. **`recvWindow` and the 500ms clock bias are untested against real latency.**
   Both are reasoned from the documented timing rules, not measured. The manual
   testnet trial is where a genuinely drifting or slow connection would show
   whether the margin is right.
6. **Nothing verifies the API key lacks withdrawal permission.** Section 4.4
   makes that the primary v1 safeguard, and it is enforced only when the key is
   created on the exchange. No code can check it.

## Step 3.1: `cancelOrder` returns the cancelled order
Date: 2026-07-21

A scoped fix between steps 3 and 4, not a build-order step of its own. Resolves
step 3's open question 1.

### What changed

`cancelOrder` returned `Promise<ExchangeOutcome<void>>` and threw away the
response body. It now returns `Promise<ExchangeOutcome<OrderStatus>>`.

Three files: `src/shared/exchange-client.ts` (the interface and the `OrderStatus`
type), `src/exchange/binance/parse.ts` (a new `parseCancelledOrder`), and
`src/exchange/binance/client.ts` (wiring). 445 tests, up from 431; typecheck
clean.

### Decisions made

**1. `cancelOrder` returns `OrderStatus`, not `void`.**

A second deliberate deviation from section 4.1's literal signature, of the same
category as step 3's decision 1.

Driven specifically by section 7.2. A halt cancels every open order for a bot
instance, and section 5.3 already accepts that some of those will be partially
filled at that moment — step 2's decision 4 added `partially_filled -> cancelled`
for exactly this reason. The filled quantity at the instant of cancellation is
what determines the position the halted bot is actually left holding, so it is
not incidental detail; it is the number that says what the bot still owns.

The exchange reports it in the cancellation response. Discarding it forced a
follow-up `getOrderStatus` per cancelled order, which is wrong three ways:

- **Slower**, during a halt, which is the one path where speed is a safety
  property rather than a nicety.
- **More weight** against the section 5.4 budget at the worst possible moment,
  and a halt that cancels a full grid ladder is many orders at once.
- **Racy.** The order is live until the cancel lands. A separate read afterwards
  is a different observation at a different instant, and while the window is
  small it is exactly the window in which a resting order fills. The cancellation
  response is the exchange's own account of where the order finished, taken from
  the same operation that ended it — there is no window at all.

*Returning `void` and reading status separately — rejected*, for the above.

*A new `CancelResult` type — rejected.* It would have carried the same fields
under a second name, leaving step 6 to handle two nearly identical shapes for
what is one concept: an order and where it ended up.

**2. `OrderStatus.createdAt` became optional.**

The cancellation payload carries `transactTime` and no creation time whatsoever.

*Filling `createdAt` from `transactTime` — rejected.* It is available and the
types would have been happy, which is what makes it dangerous: every cancelled
order would claim to have been created at the moment it was cancelled. That is a
fabricated value wearing an authoritative type, and section 9's reconciliation
compares timestamps.

*Keeping `createdAt` required by introducing a separate type — rejected*, per
decision 1.

Nothing is actually lost. A bot cancelling an order placed it, so it holds the
creation time in its own `TrackedOrder`. The field exists for reconciliation
reading back orders it did not necessarily place, and those come from the status
endpoints, which do report it.

**3. A separate `parseCancelledOrder`, because the payload has two client order ids.**

This is the part worth remembering.

The cancellation response contains BOTH `clientOrderId` and `origClientOrderId`.
They are not duplicates: `clientOrderId` is the id of the **cancel request**,
freshly generated by the exchange, while `origClientOrderId` is the order that
was actually cancelled. The status endpoints have no such split and correctly use
`clientOrderId`.

Reusing `parseOrderStatus` here would therefore have attributed the result to an
id this system never issued — and **nothing would have thrown**. The field is
present, it is a string, and the returned object would have type-checked
perfectly. A halt would have recorded a filled quantity against a nonexistent
order while the real order's final fill went unrecorded, surfacing much later as
an unexplained position discrepancy in section 9 reconciliation. The kind of bug
that is cheap to prevent and expensive to find.

The shared fields are factored into one `parseCommonOrderFields` so the two
parsers cannot drift, while identity and timestamps — precisely where the
payloads differ — stay explicit in each. There is a test asserting
`parseCancelledOrder` rejects a status-endpoint body outright, as a guard against
the two being used interchangeably later.

Secondary reason for the split: the cancellation payload has no `time` or
`updateTime`, so `parseOrderStatus` would have thrown on it regardless. Only the
id problem was silent.

**4. `updatedAt` is the cancellation instant.**

`transactTime`, which is exactly the moment the reported `filledQuantity`
describes. A caller reading the filled quantity knows precisely what instant it
was true at, which is what makes it safe to write straight into a position.

### Deviations from the spec

- **Section 4.1 writes `cancelOrder(...): Promise<void>`.** It now returns the
  cancelled order. Section 7.2 needs the data and the exchange already sends it.
- **`OrderStatus.createdAt` is optional**, so the one interface type covers both
  the status endpoints and cancellation without either fabricating or duplicating.

### Open questions carried forward

Step 3's open questions 2 through 6 stand unchanged. Question 1 is resolved here.

New:

1. **`state` on a cancelled partial fill comes from the exchange, not from the
   fill maths.** A cancellation of a partially filled order reports `CANCELED`,
   so `parseCancelledOrder` returns `cancelled` with a non-zero `filledQuantity`
   — consistent with step 2's decision 4, and `compareWithExchange` only looks at
   `state` and `filledQuantity`, so the two agree. Worth re-checking at step 6
   when the halt path actually drives `closeOrder` from this value.

## Step 3.2: real credentials provider and testnet exchange wiring
Date: 2026-07-24

A scoped follow-up, like step 3.1: not a build-order step of its own. It builds
the thing step 3's `credentials.ts` header promised and deliberately withheld —
"the real, secret-backed implementation is a thin wrapper over `env`, added at
the point this actually deploys" — and wires it so the reconciliation cron's
`exchangeFor` returns a live `BinanceClient` on testnet. Real Binance **testnet**
credentials (`testnet.binance.vision`, fake funds, real API behaviour) were set
as Wrangler secrets `BINANCE_API_KEY` / `BINANCE_API_SECRET` on the testnet
environment. This partially resolves the long-standing open question 4.1.1
(whose exchange account) — for testnet; production is still deliberately
unwired.

### What changed

- **New `src/workers/exchange.ts`** — the binding-aware wrapper. `baseUrlForEnvironment`
  maps `env.ENVIRONMENT` to a base URL; `resolveDefaultExchange` reads the two
  secrets, fails closed if either is missing, and otherwise returns an
  `ExchangeFactory` building a `BinanceClient`.
- **New `src/workers/exchange.test.ts`** — 14 tests, all offline. Pins the
  base-URL mapping in both directions and the fail-closed reasons.
- **`src/workers/reconciliation.ts`** — the default `exchangeFor` was
  `NO_EXCHANGE_CONFIGURED = () => null`; it is now `resolveDefaultExchange(env,
  now)`, resolved after `accountLabels` and only when at least one account
  exists. Header updated; the `NO_EXCHANGE_CONFIGURED` constant removed.

1112 tests pass (up from 1098), typecheck clean. No live network call anywhere in
the suite: reconciliation's tests inject the `FakeExchange`, and the new tests
only *construct* a client (its constructor sends nothing) — nothing calls a
method.

### Decisions made

**1. The base URL is a pure function of `ENVIRONMENT`, never a setting.**

This is the answer to "make it impossible to get backwards." There is no
`BINANCE_BASE_URL` var or secret anywhere, and there must not be one.
`baseUrlForEnvironment` is a total switch: `testnet → testnet.binance.vision`,
`production → api.binance.com`, everything else (including `"unconfigured"`,
`""`, `undefined`) **throws**. No default branch yields a URL.

`env.ENVIRONMENT` is a per-environment `var` in wrangler.jsonc, and Wrangler
`vars` are non-inheritable — the same property the config already relies on to
keep the two D1 `database_id`s separate. So the testnet deploy carries
`"testnet"`, production carries `"production"`, and neither can carry the
other's value.

Because the URL is *derived* from that var rather than configured beside it,
there is no combination of settings that points testnet at real Binance. To do
it you would have to set `ENVIRONMENT: "production"` on the testnet deploy —
which is not a quiet URL swap: it also flips `/health`, the bound D1 database
(a different `database_id`), and the dashboard banner. You would be deploying
"production" in every visible respect. And an unrecognised value fails closed
(throws) rather than guessing.

*Enforced by:* the derivation itself (there is nothing else to set), plus
`exchange.test.ts` asserting testnet resolves to the testnet host and **never**
`api.binance.com`, production to real Binance and **never** the testnet host,
and unknown values throw. A future edit that swaps the two lines fails CI.

*A separate configurable base URL with a validation check — rejected.* A check
can be forgotten or weakened; a value that cannot be set independently cannot be
set wrong.

**2. Credentials are resolved lazily — after the schema guard, and only when an
account exists.**

Not at the top of the handler. Two guards it must sit behind:

- *After the schema guard*, so production deployed empty before go-live still
  no-ops on "no schema" rather than on a missing secret it is not meant to hold
  yet.
- *Only when `accountLabels` is non-empty*, so an environment with a schema but
  no bots is not made to fail for a secret nothing yet needs. This mirrors the
  pre-existing final guard, which already only complained when accounts existed.

The practical proof this is right: the two `schema-guard.test.ts` cases that
drive the default path (no injected `exchangeFor`) — "proceeds and runs" with a
schema but no bots, and "a constraint error still propagates" — keep passing
untouched. An eager resolution broke both; this ordering is what a missing
secret must *not* disturb.

**3. A missing secret fails closed with a specific reason, not a silent skip.**

The old null-default skipped every account quietly, which was correct when no
credentials existed anywhere. Now that testnet is expected to have them, a
missing secret on an environment that *has accounts* returns `{ ran: false,
reason }` naming exactly which secret and the `wrangler secret put … --env`
command to set it — the same shape as `notifications.ts`'s `DISCORD_WEBHOOK_URL`
check and `access.ts`'s `ACCESS_AUD` refusal. Blank is treated as missing (a
blank secret would otherwise sign an HMAC over an empty key and fail at the
exchange with a signature error that names nothing). The secret value never
appears in a message — asserted by a test.

**4. The client is handed the account's `RateLimiter` as its weight reporter.**

`resolveDefaultExchange`'s factory passes the account's `RateLimiter` Durable
Object stub to `BinanceClient` as its `WeightReporter`. This is the *reporting*
half of section 5.4 (the *gating* half is still `withRateLimit`, applied by the
caller); it closes the loop the DO was explicitly built to receive, so the
account-wide budget is corrected by the exchange's own `X-MBX-USED-WEIGHT`
header rather than running on reserved estimates alone. Leaving it unwired would
have been a "looks connected but isn't" gap of exactly the kind step 3.1's
`parseCancelledOrder` note warns about.

### Deviations from the spec / prior entries

- **The reconciliation Worker's "THERE IS NO EXCHANGE CLIENT" invariant is
  retired for testnet.** Steps 6, 7 and 8 all recorded that no client existed in
  either environment (step 4.1's decision 2). That is now false on testnet and
  still true on production. `bot-instance.ts`'s own "no default client" stance
  (its decision 13) is unchanged — this step wired only the reconciliation
  cron's `exchangeFor`, not the bot object's injected `exchange`.

### Open questions carried forward

Step 3's open questions 2–6 stand. In particular **question 5** (recvWindow and
the 500ms clock bias are reasoned, not measured) and **question 6** (nothing can
verify the key lacks withdrawal permission) are now directly checkable against a
live endpoint for the first time — that is the manual verification this step
unlocks. 3.1's question 1 stands.

New:

1. **Production is still unwired, on purpose.** `resolveDefaultExchange` is
   symmetric — it will build a production client the moment
   `BINANCE_API_KEY`/`BINANCE_API_SECRET` exist on that environment — but no
   production secret is set, and production's database is still empty, so the
   cron no-ops on "no schema" regardless. Wiring production is a go-live
   decision, not this step.
2. **The bot object's `exchange` is still injected and unset in production.**
   `BotInstance` takes its client as a dependency and has no default (its
   decision 13). Nothing constructs a live bot client yet; only reconciliation
   reads the exchange so far. When order execution is wired, it should reuse
   `resolveDefaultExchange`'s base-URL derivation rather than re-deriving it, so
   the "impossible to get backwards" property has a single home.

## Step 3.3: Live reachability check from the deployed Worker
Date: 2026-07-24

### What was built

Two things, one of them deliberately short-lived.

First, `scripts/verify-exchange.ts` — a throwaway, git-ignored, local-only tool
that runs Tier 0 (`getCurrentPrice`, unsigned) then Tier 1
(`getAccountBalances`, signed) against `testnet.binance.vision`, importing the
real `BinanceClient` so a green run exercises the production signing/transport
path rather than a mock. Running it from a laptop returned a Binance HTTP 451
"Service unavailable from a restricted location" — the client reached the
exchange and correctly classified the refusal as a non-retryable
`exchange_error` outcome (section 5.6 working as intended), but the request
origin is geo-blocked, so the round-trip could not complete locally. The tool is
kept for reuse behind a VPN; it never lives in the repository.

Second, to check reachability from where the bot ACTUALLY runs — Cloudflare's
edge, not a laptop — a **temporary diagnostic route** `GET
/api/debug/exchange-check` (`src/api/debug-exchange-check.ts`, wired in
`src/api/index.ts`). It runs the same two tiers from inside the deployed testnet
Worker, using the real testnet secrets via `resolveDefaultExchange`, and returns
the price and a balance summary as JSON. It reads no secrets itself and returns
none.

*(Since removed, 2026-07-28: the route did its job — it confirmed Binance
geo-blocks a Cloudflare Worker and a US-based Oracle VM identically, i.e. the
block is on request-origin IP regardless of environment — and was then deleted
as always intended. `src/api/debug-exchange-check.ts` and the wiring block +
import in `src/api/index.ts` are gone; no route, handler, or reference to it
remains. This entry is kept as the historical record of why it briefly existed.
The open question below about unpredictable geo-blocking still stands.)*

### Decisions made

**1. The `/api/debug/exchange-check` route is TEMPORARY, not a feature.** *(explicit; since fulfilled — the route was removed on 2026-07-28, see the note above)*

It exists only to answer one question once — can the deployed Worker reach
Binance? — and is to be removed immediately after a single confirming request.
It is not a monitoring endpoint, not a health probe, and nothing a real user or
bot should ever call. Both the file header and the wiring block in `index.ts`
carry removal instructions; removal is: delete `debug-exchange-check.ts`, delete
the marked block and its import in `index.ts`. Recorded here so the route's
absence later is expected, and its reappearance would be a regression.

*Revisit if:* never — it is meant to be deleted. If a permanent reachability
signal is ever wanted, it should be designed as one (authenticated, rate-aware,
alerting), not by promoting this stub.

**2. It reuses the `/api/*` gating rather than adding any new surface.** *(honours the "no new permissions or Access changes" constraint)*

The route lives under `/api/`, so it is behind Cloudflare Access at the edge and
the JWT re-check in `handleApiRequest`, exactly like every real API route — no
new Access application, policy, or permission. It is wired AFTER `authenticate()`
but BEFORE the schema guard and `ApiContext`, because the diagnostic needs
neither the D1 schema nor the `BOT_INSTANCE` binding, and coupling it to them
would only add unrelated failure modes.

*Path note.* The request originally sketched `GET /debug/exchange-check`. That
path is NOT under `/api/`, and Access here is scoped to `/api/*` (that is why
`/health` can be unauthenticated). A `/debug/*` route would therefore be
ungated unless an Access policy were added — the opposite of "no Access
changes." Moving it to `/api/debug/exchange-check` inherits the existing gating
with zero configuration, which is why the path differs from the sketch.

**3. It reuses `resolveDefaultExchange` verbatim.** *(no duplicated secret path)*

Rather than read `BINANCE_API_KEY`/`BINANCE_API_SECRET` itself, the handler
calls the same secret-backed factory the reconciliation cron uses. So it gets
the same fail-closed behaviour, the same base-URL-from-`ENVIRONMENT` derivation
(it can never point at production from testnet), and the same guarantee that no
secret value appears in any message. The account label handed to the factory is
a throwaway (`"debug-exchange-check"`), so the diagnostic's rate-limit weight
does not land in any real account's budget.

### Open questions carried forward

Step 3's questions and 3.2's stand. New:

1. **Binance geo-blocks by request-origin IP, and Cloudflare Workers have no
   fixed egress IP — this is a standing operational risk, not something this
   test can settle.** Binance's restriction is applied to the IP the request
   comes FROM, independent of the account's region or the API key. Cloudflare
   Workers do not egress from a stable address: a request is served by whichever
   edge location Cloudflare routes it to, and the outbound IP follows from that.
   So a production request to Binance could be geo-blocked *unpredictably*,
   depending on which edge handled it — and a diagnostic hit that succeeds today
   proves only that the edge location serving THAT request was not blocked, not
   that every edge location that might serve a future request is clear. A single
   green `/api/debug/exchange-check` neither rules this risk in nor out. It is
   worth understanding and monitoring for as an ongoing concern: a geo-block
   would surface as `exchange_error` outcomes on live trading calls, potentially
   intermittently. How to detect it deliberately (rather than discovering it
   through failed orders), and whether any mitigation exists given Workers'
   routing model, is open and left for a later step to weigh.

   *Update, 2026-07-28: partially narrowed.* Two independent origins were tried
   and both were blocked identically by Binance — a Cloudflare Worker (via the
   now-removed `/api/debug/exchange-check` route) and a US-based Oracle Cloud VM.
   That two unrelated networks fail the same way points at request-origin
   IP/geography as the cause, not any one cloud provider's IP reputation, so the
   "is it just Cloudflare's IPs?" reading of this question is effectively ruled
   out. What remains open and unresolved is the other half: whether a Worker's
   routing could unpredictably vary which edge location — and thus which egress
   geography — handles a given request, and so intermittently succeed or fail
   even from a setup that is not itself US-adjacent. Both origins tested so far
   are US-adjacent and fail consistently; the intermittent, routing-dependent
   case has not been observed either way and still stands.

## Step 3.4: Gemini exchange implementation (second `RestExchangeClient`)
Date: 2026-07-28

### What was built

A second implementation of the section 4.1 interface, for Gemini, structurally
mirroring `binance/` but not a copy of it. A new `/src/exchange/gemini/` folder:
`signing.ts`, `parse.ts`, `filters.ts`, `client.ts`, each with a test file; plus
`src/workers/exchange-gemini.ts` (the binding-aware base-URL + credentials shell,
the Gemini counterpart of step 3.2's `exchange.ts`) with its own test. The
`/src/exchange` barrel and folder README were extended; a throwaway,
git-ignored `scripts/verify-gemini.ts` was added mirroring `verify-exchange.ts`.

`GeminiClient` implements the eight REST methods of `RestExchangeClient`. 91 new
tests across the five modules; **1203 tests in total, all passing; typecheck
clean.** No live network call anywhere in the suite (client tests inject a
mocked `fetch`; the resolver tests only construct).

Before writing anything, Gemini's published REST reference
(developer.gemini.com — authentication, orders, market-data, order-status) was
fetched and read directly, because the task was explicit that Gemini's shapes do
NOT translate from Binance's. They do not, in several places, and the corrections
below come from those documents rather than from Binance's shapes or from memory.

Nothing about `BotInstance`, the strategies or reconciliation changed. This is
purely a new implementation behind the same interface, and both exchanges coexist.

### Decisions made

**0. Build Gemini fully behind the interface; DEFER the Binance-vs-Gemini
dispatch to its own step.** *(asked, confirmed)*

The one genuinely ambiguous point the task flagged: how a bot instance chooses
which exchange. Today nothing does — `resolveDefaultExchange` always builds a
`BinanceClient`, and no field anywhere names an exchange. Asked whether to add
that selection now (a per-bot D1 column, or a per-environment `EXCHANGE` var) or
to build Gemini behind the interface and leave the dispatch for later. Confirmed:
**defer the dispatch.** So this step delivers the full Gemini client, its own
`ENVIRONMENT`-derived base URL and fail-closed credentials resolver, and complete
mocked tests — but nothing routes to Gemini yet. This mirrors the established
precedent of step 3.2, which built the production Binance path symmetrically and
left it unwired on purpose (its open question 1). The dispatch (and any schema
migration) is a separate, data-model decision that deserves its own step.

**1. The signing scheme was confirmed from real docs, and it is a different
mechanism, not a variation on Binance's.** *(the task's central instruction)*

Verified: a private request signs `hex(HMAC-SHA384(base64(JSON payload)))`, where
the payload JSON carries `request` (the endpoint path) and a `nonce` alongside the
parameters. The key, the base64 payload and the hex signature travel as the
`X-GEMINI-APIKEY` / `X-GEMINI-PAYLOAD` / `X-GEMINI-SIGNATURE` headers of a **POST
with an empty body**. Every material difference from Binance is real: **SHA-384**
not SHA-256; a **base64 JSON payload** not a query string; **headers** not a
signed URL; an **empty POST body** not URL parameters.

*Test vector — a deviation from the Binance approach, forced by Gemini.* Binance
publishes a worked example with an expected signature, which is what lets its
signing test assert against *the exchange's own* output rather than the
implementation's. Gemini publishes no such signed example. To keep the same
guarantee — an expectation not computed the way the code computes it — the
signing test asserts against a vector produced by an **external tool** (`openssl
dgst -sha384 -hmac`) over a fixed secret and payload. A test that called this
module's own `sign` to derive the expectation would have agreed with a broken
`sign`; an `openssl` value does not.

**2. There is NO clock synchronisation, because Gemini signs with a nonce, not a
server-compared timestamp.**

This is the largest structural divergence. Binance signs a `timestamp` the
exchange checks against its own clock, and step 3 built an entire
`ClockOffset`/`getServerTime`/500ms-bias estimator around a hard rejection for
drift. Gemini instead requires a `nonce` that "need only increase with respect to
the session" — a monotonically rising number, compared to nothing. So the whole
of that apparatus has no analogue here. `NonceGenerator` replaces it: milliseconds
since the epoch, floored up to `last + 1` whenever the clock has not advanced, so
it is always at least wall-clock ms and always strictly increasing. It needs no
I/O and no server clock, which is why signing stays exactly reproducible in a test.

**3. `getServerTime` returns a clear failure rather than a fabricated value.**

The interface declares it (section 4.1), so it must exist, but Gemini exposes no
server-time endpoint and — per decision 2 — needs none. Returning the local clock
labelled as "server time" would be an authoritative-looking value that is not what
the type promises, which is exactly the class of fabrication this codebase refuses
elsewhere (step 3.1's decision 2 refused to fill `createdAt` from a cancellation
time for the same reason). So it returns a non-retryable `exchange_error` naming
why. This is safe: a search of the codebase confirms `getServerTime` is only ever
the Binance client's own internal clock-sync helper — no strategy, reconciliation
or bot code calls it — so a Gemini client's `getServerTime` failing disturbs
nothing.

**4. Order state is derived from BOOLEAN FLAGS, because Gemini has no status
string.** *(corrected against real payloads)*

Gemini reports `is_live` and `is_cancelled` (plus `is_hidden`, `was_forced`) and
the amounts; there is no `"FILLED"`/`"NEW"` enum to map. `toOrderState` derives it:
`is_cancelled` wins outright → `cancelled` (carrying whatever `executed_amount`
was reached before the cancel, which is exactly the shape step 3.1's open question
1 relies on); `is_live` with a partial fill → `partially_filled`, otherwise
`pending`; not live and not cancelled → `filled`. There is deliberately no
`rejected`/`expired` branch — Gemini reports a rejection as an ERROR BODY
(`{result:"error"}`), never as an order object, so a rejection is handled by
`classifyFailure` before any order is parsed and never reaches this function.

**5. The symbol-detail field names are INVERTED, and this is the trap worth
remembering.** *(corrected against real payloads)*

Confirmed verbatim from Gemini's reference: `tick_size` is the increment of the
**base** currency (the order amount) and `quote_increment` is the increment of the
**quote** currency (the price). So Gemini's `tick_size` maps to our `stepSize`
(quantity grid) and Gemini's `quote_increment` maps to our `tickSize` (price grid)
— the opposite of what the names suggest. Reading them the intuitive way would
swap the price and quantity grids on every symbol, and nothing would throw:
`roundToStep` would happily round a price to a quantity increment and produce a
plausible, wrong order. `parseSymbolDetails` applies the inversion explicitly with
the reasoning inline, and a test pins it (`tick_size 1e-8 → stepSize`,
`quote_increment 0.01 → tickSize`).

Secondary trap in the same payload: `tick_size` and `quote_increment` are JSON
**numbers** (one in scientific notation, `1e-8`), while `min_order_size` is a
**string**. A number has already been through the float parser, so — to keep it
out of the money path — `incrementToMoney` re-renders it via `toFixed(8)` and
parses the decimal string, and refuses (rather than silently zeroing) an increment
finer than the 8-decimal money scale, since a zero step would make `roundToStep`
reject every order on the symbol with no visible cause. This is the one place a
JSON number is deliberately admitted into a `Money` conversion, and it is narrow
and documented; the order-payload parser (`parse.ts`) still rejects any numeric
monetary field outright, exactly as Binance's does.

**6. `validateOrder` and `SymbolFilterCache` are exchange-agnostic and kept as a
single implementation, re-exported through `gemini/filters.ts`.**

They operate purely on the shared `SymbolFilters` type and `Money`; nothing in
them is Binance-specific. Rather than duplicate ~180 lines or reach across from
the Gemini client into `binance/`, `gemini/filters.ts` re-exports them from
`binance/filters.ts`, so the Gemini client imports everything filter-shaped from
its own sibling and the shared logic has one home. Their physical location under
`binance/` is a step-3 accident (there was one exchange then). Hoisting them to a
neutral `src/exchange/filters.ts` is the clean refactor; it was **deliberately not
done this step**, to keep the step purely additive and avoid churning Binance's
files and tests — which the task's "don't change Binance, both coexist" framing
asked for.

**7. `cancelOrder` is a lookup-then-cancel, because Gemini cancels by numeric
`order_id` only.** *(corrected against real docs)*

The interface identifies an order by `clientOrderId`, and Binance's cancel accepts
`origClientOrderId` directly. Gemini's `/v1/order/cancel` accepts ONLY the numeric
`order_id`. So a cancel first calls `/v1/order/status` by `client_order_id` to
learn the `order_id`, then cancels by it. The extra call is the id resolution, not
a second read of the result: the cancel response still echoes the final
`executed_amount`, so the halt-time filled quantity step 3.1 cares about comes
from the cancel itself, and if the lookup fails the failure is returned rather than
a blind cancel attempted. Note this is the mirror image of Binance's step 3.1
trap and its *inverse* — Binance's cancel had TWO client ids and reading the wrong
one was a silent mis-attribution; Gemini's cancel returns the FULL order under the
SAME `client_order_id`, so there is no such trap here, only the extra lookup.

**8. Balances are derived: `locked = amount - available`.** *(corrected against
real payloads)*

Binance reports `free`/`locked` directly. Gemini reports `amount` (total) and
`available`, so the reserved figure is `amount - available`. A negative result
(available exceeding total) is impossible and is **refused** rather than clamped,
so a genuine API change surfaces loudly instead of producing a plausible wrong
balance.

**9. Fees, fills and cumulative value follow Gemini's names.** *(corrected against
real payloads)*

A fill's fee is `fee_amount` in `fee_currency` (Binance: `commission` /
`commissionAsset`) and its id is `tid` (Binance: `tradeId`), and — unlike a
Binance fill, which inherits the parent order's time — a Gemini trade carries its
own `timestampms`, so `executedAt` is the fill's own observed time. Section 5.5's
rule that a fee is never assumed to be in the quote currency is honoured by
carrying `fee_currency` through verbatim. Gemini has no cumulative-quote field, so
`cumulativeQuoteQuantity` is derived as `avg_execution_price * executed_amount`
(floored, conservatively, as the Binance notional is).

### Deviations from the spec / prior entries

- **`getServerTime` does not return a server time on Gemini** (decision 3). The
  interface method exists; Gemini has no such endpoint and needs none, so it
  fails clearly rather than fabricating one.
- **No used-weight reporting.** Gemini's rate limiting is request-count based and
  sends no `X-MBX-USED-WEIGHT`-style header, so `GeminiClient` has no
  `WeightReporter` and `resolveGeminiExchange` takes no `RateLimiter` binding.
  The request-count gate a Gemini account needs is a dispatch-time concern
  (`GEMINI_METHOD_WEIGHTS` for the `RateLimitedExchange` wrapper), deferred with
  the rest of the dispatch (decision 0).
- **`getOpenOrders` filters client-side.** Gemini's `/v1/orders` returns every
  active order on the account with no per-symbol variant, so the client filters to
  the requested pair to honour the interface's per-pair contract.
- **The base-URL environment names differ from Gemini's own.** The project uses
  `testnet`/`production`; Gemini calls its non-real host the *sandbox*.
  `geminiBaseUrlForEnvironment` maps the project's `ENVIRONMENT` (`testnet` →
  `api.sandbox.gemini.com`, `production` → `api.gemini.com`) so there is one
  environment concept per exchange, and the same "derived, never settable, throws
  on anything unrecognised" guarantee as step 3.2's `baseUrlForEnvironment`.

### Open questions carried forward

Binance-specific open questions from steps 3–3.3 are unaffected (they concern the
Binance client, which is untouched). New, Gemini-specific:

1. **Nonce ordering across concurrent Worker isolates sharing one API key.**
   Gemini enforces nonce ordering per API key. One `NonceGenerator` instance
   orders one client object's traffic, but two isolates using the same key could
   interleave and one could send a lower nonce. The mitigation is operational, not
   code: the Gemini API key should be created with **session-scoped nonces** (so
   the requirement is only "increasing within a session"), which is what makes the
   per-client monotonic generator sufficient. This is the Gemini analogue of
   Binance's step 3 open question 5 (recvWindow/clock bias reasoned, not measured)
   and is untestable without a live account under real concurrency — the manual
   sandbox trial is where it would first show.

2. **The `symbols/details` increment semantics should be re-confirmed against a
   live response.** The authoritative reference shows increment VALUES (`1e-8`,
   `0.01`); a third-party source showed decimal-place COUNTS (`8`, `2`).
   `parseSymbolDetails` trusts the authoritative value semantics, and a live
   Tier 0 `getSymbolFilters` call (read-only) against the sandbox is the cheap way
   to confirm the shipped API matches before anything touches an order.

3. **Gemini geo-availability is unverified from Cloudflare's edge.** Step 3.3
   found Binance geo-blocks Cloudflare Workers by request-origin IP. Whether
   Gemini's sandbox/production do the same from a Worker is unknown and is the same
   standing operational risk; the read-only `verify-gemini.ts` Tier 0 is the first
   place to observe it.

4. **Dispatch is unbuilt, on purpose** (decision 0). `resolveGeminiExchange` is
   symmetric and ready, but nothing calls it and no `GEMINI_*` secret is set, so
   the system is exactly as it was for any live path. Wiring which-exchange is a
   go-live/data-model decision, not this step.
