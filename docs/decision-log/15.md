## Step 15: Resume-bot action (backend endpoint + dashboard control)
Date: 2026-07-31

### What was built

Section 7.2 step 5 as a dashboard action. `BotInstance.resume` has existed since
step 6 — designed into the object from the first Durable Object session, and
called by `assertGlobalArmed`/`assertAccountArmed`, the kill-switch tests and the
reconciliation tests — but its only callers were tests. A halted bot could not be
brought back from the UI at all. That gap is closed, following the start (step 12)
and liquidate (step 10.9) pattern exactly.

- **`POST /api/bots/:id/resume`** (`resumeBot` in `src/api/handlers.ts`, routed in
  `src/api/index.ts` between start and liquidate). Confirmed absent first, not
  assumed: `ROUTES` carried only `/start` and `/liquidate`. A thin wrapper over
  `BotInstance.resume(actor)` that refetches the D1 row + snapshot and returns
  `{ result, bot }`, byte-for-byte the same shape and refetch as `startBot` and
  `liquidateBot`. No business logic added — `resume` remains the sole authority.
- **`ResumeResult` / `ResumeResponse`** in `dashboard/src/api/types.ts` and
  **`resumeBot()`** in `dashboard/src/api/client.ts`, mirroring the start types.
- **`ResumeAction.tsx`** — the control: renders only when `bot.status === "halted"`
  (re-checked in the component, not just at the caller), a plain yes/no confirm
  dialog (NOT type-to-confirm), the bot's **real halt reason** inside the dialog,
  mounted-guard + in-flight/double-click guard, immediate `poll.refetch` on
  success. Wired into `BotDetail.tsx` **above** the liquidate control.
- **Four backend tests** in `src/api/api.test.ts` (below).

### `resume()` confirmed from source — its failure surface is WIDER than `start`'s

The brief said to confirm resume's real failure surface rather than assume it
matches start's. It does not match. Read in execution order from
`src/durable-objects/bot-instance.ts:998-1032`:

| # | Failure | Code (HTTP) | Does `start` have it? |
| --- | --- | --- | --- |
| 1 | no stored config | `not_created` (404) | yes |
| 2 | status is not `halted` | `invalid_status` (409) | yes, mirrored |
| 3 | global kill switch pulled | `globally_tripped` (409) | **no** |
| 4 | account circuit breaker tripped | `account_tripped` (409) | **no** |
| 5 | no `PRICE_FEED` binding | `not_attached` (503) | yes |
| 6 | uncoded (D1 write, feed RPC) | 500 `internal_error` | yes |

**3 and 4 are the real find.** `resume` calls `assertGlobalArmed` **and**
`assertAccountArmed`; `start` calls neither. That asymmetry is deliberate and
documented at the call site: creation and resume are the two ways a bot on a
latched account could begin trading again, so both latches gate both, "or the
control lasts exactly as long as it takes someone to click resume". Starting a
`created` bot is not one of those two ways. So resume has two refusals with no
analogue in `StartAction`, and each gets its own copy naming the right reset —
neither is fixable by retrying, and both resets deliberately resume no bot on
their own, so the operator lands back on this button afterwards.

Every one of 1–5 is raised **before** the status flip, so each message can
truthfully end "the bot is still halted".

### Decision: no error branch for "the feed or exchange is still unreachable"

The brief named this as a case to handle with distinct copy (`e.g. the price feed
or exchange still unreachable`). **It is not a failure this endpoint can return.**
Traced from source rather than assumed:

`resume` → `#subscribeToFeed` → `PriceFeed.subscribe` → (empty registry, since the
halt unsubscribed) `startFeed` → `#ensureConnected`, and that method wraps its
`connect` in a `try/catch` whose catch calls `#scheduleReconnect()` and
**returns normally** (`price-feed.ts:439-455`). Nothing propagates. So a resume
with Gemini unreachable is a **200**: the bot enters `running` blind, and the feed
raises its own `price_feed_blind` warning, escalating to
`price_feed_blind_escalated` after 30 minutes.

Writing a `feed_unreachable` branch would have produced a dead code path that can
never render, and — worse — implied to the operator that a successful resume
proves the feed is up. It does not. The **success banner** carries that fact
instead: if no order appears within a few minutes, check the alerts for
`price_feed_blind`, because an unreachable feed does not fail this action. This is
the same discipline as step 12's "handle only what the method returns", applied in
the other direction: there, branches were dropped because the method could not
fail that way; here, one is dropped for the same reason and the honest statement
moved to the success path, where the operator will actually be looking.

### Point 8 verified from source: the re-subscription is correct

Asked to confirm rather than assume, given Session D wired exactly this
transition. The full round trip:

1. `#halt` calls `#unsubscribeFromFeed` best-effort (`bot-instance.ts:2254`), so a
   halted bot is **not** on the feed's registry.
2. If it was that pair's last subscriber, `unsubscribe` → `stopFeed` closed the
   socket, cleared `#current`/`#primed` and **reset the watermark to null** — the
   deliberate "going idle" teardown, so a later restart re-primes fresh instead of
   backfilling a day of candles nobody was listening for.
3. `resume` calls the same fail-closed `#subscribeToFeed` `start` uses, **before**
   the status flip.
4. `PriceFeed.subscribe` sees `before === 0`, so it takes the first-subscriber
   branch: `startFeed(config)` → `configure` → `#ensureConnected` → fresh socket,
   `beginConnection()`, `subscribeMessage(pair)`, health alarm armed.

So resuming genuinely re-enters the live path rather than rejoining a dead one.
Already covered by C2/D's own test — `"re-subscribes on resume after a halt"`
(`bot-instance.test.ts:1121`), asserting two subscribes and one unsubscribe across
create→start→halt→resume — and re-verified here by mutation (below).

### Decision: the dialog shows the halt reason, and does NOT reuse start's "what it will place"

**The halt reason is in the dialog** (brief item 4), not only on the page behind
it: `resume` deliberately never clears `halt_reason` (migration 0001's
`halt_requires_reason` CHECK is one-directional precisely so a resumed row keeps
it), the detail payload already serves it, and a resume without reading it is the
blind retry this control exists to prevent. `haltedAt` is shown beside it. When no
reason was recorded, the dialog says so and points at the alerts rather than
leaving an empty box.

**`StartAction`'s `plannedOrderSummary` was deliberately NOT reused**, and this is
the one place the resume copy diverges from start's rather than mirroring it. A
`created` bot is flat by definition, so start can name the exact order — the DCA
base order, or the grid's full ladder — from config alone. A **resumed** bot is not
flat by definition, and `decide()` is a function of the current position
(`dca.ts:446`): it may place an additional buy, a take-profit sell, or hold. Worse,
a bot halted on `stop_loss` whose price has not recovered re-halts on the **very
first** candle. Naming a specific order here would be a guess wearing the costume
of a fact — exactly the class of copy 12.1 deleted. The dialog states the mechanism
(same live execution path, next real closed 1-minute candle, real capital, no dry
run) and then says plainly that which order fires depends on the position it holds
now, and that an unfixed halt condition will simply halt it again.

Placement: **above** liquidate on the detail view. Both apply to a halted bot; the
recoverable action should be read before the irreversible one.

### Tests: four, targeting what is unique to resume

Backend, in `src/api/api.test.ts` (the dashboard has no test runner — typecheck
and build only, unchanged since 10.6):

1. **Resumes a halted bot**: 200, `{ status: "running", action: "resumed" }`, D1
   row `running`, `bot.resumed` audited to the verified human actor — **and the
   halt reason survives** in both the response body and the row.
2. **Refuses a non-halted bot**: 409 `invalid_status`.
3. **Refuses while the account breaker is tripped**: 409 `account_tripped`, and
   the row is asserted **still `halted`**.
4. **Refuses while the global kill switch is pulled**: 409 `globally_tripped`, row
   still `halted`, **then succeeds after a human reset** — proving the refusal was
   the latch and not a permanent block. The pull itself halts the bot, so this is
   the realistic path into the state rather than a hand-built one.

**Mutation-checked, four mutants, all caught** — the discipline 14.8/14.10
established, applied to a test that would otherwise be easy to write green:

| mutant | result |
| --- | --- |
| handler calls `start(actor)` instead of `resume(actor)` | 4 failures |
| `resume` clears `halt_reason` when mirroring | 1 failure |
| both latch assertions moved to AFTER the status flip | 2 failures |
| `resume` does not re-subscribe to the feed | 1 failure (Session D's own test) |

The third is the one worth having: a suite that only checked the 409 codes would
stay green while the bot was left `running` on a latched account.

### Deviations from the spec / prior entries

- **None from the spec.** Section 7.2 step 5 required a human-only path out of
  `halted`; the object always had one; this is its first UI.
- **From the brief:** the "feed/exchange unreachable" error branch was not built,
  because it cannot fire (see above). Raised here rather than silently omitted.
- **The dashboard still mirrors the API contract by hand** (open since 10.6):
  `ResumeResult`/`ResumeResponse` were mirrored from `handlers.ts`. A backend
  rename surfaces as a runtime `undefined`, not a failed typecheck.

### Open questions carried forward

Unchanged and still open: **feed→bot→order has never completed live.** 14.8 got a
real refusal from Gemini, 14.10 identified the wrong-nickname cause and fixed it
against the docs and tests, and no live signed call has been made since. This
session adds the control that makes the retry a one-click human action instead of
a test-only method — but the retry itself has not been run.

New:

1. **This endpoint has never been called against a real deployed origin.** Like
   every dashboard write before it, it is verified against real D1 and real
   Durable Objects in the Workers runtime, with only the exchange faked.
2. **A successful resume does not prove the feed is up.** By design (the
   reconnect-and-return above). The operator's evidence is the absence of a
   `price_feed_blind` alert plus an actual order in the history — which is exactly
   what the next live run is watching for.
