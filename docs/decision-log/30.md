## Step 30: The news/sentiment vendor question, investigated and deliberately paused
Date: 2026-08-09

### Status: PAUSED, NOT RESOLVED AND NOT ABANDONED

No news or sentiment vendor has been selected. None has been paid for. None has
been contacted with a real API key from this repository, ever.

What exists after this step is a **complete, tested, uncommitted CoinDesk module
sitting in the working tree**, a survey of three alternative vendors, and one
finding that may disqualify all of them independently of price. Section 21 as a
whole remains **PLANNED, NOT YET BUILT**, and 21.4 Stage 1's second bullet — news
and sentiment — is now the part that is blocked on a decision rather than on
code.

This entry exists because the work is worth more written down than the code is
worth committed, and because "we looked at this and stopped on purpose" is a
different fact from "nobody got to it", and only one of them is recoverable six
months later.

### What was built, before the vendor question stopped it

A full CoinDesk-specific `fetchNewsSentiment` was built and mutation-tested
across two sessions.

- **`src/research/news.ts`** — `fetchNewsSentiment`, the three-variant
  `NewsSentimentResult`, `NewsSentimentError`, the `NewsSource` port,
  `COINDESK_WIRE_FIELDS`.
- **`src/research/news.test.ts`**, **`src/workers/news.ts`** (`envNewsFetcher`,
  `newsRequestUrl`, `COINDESK_ENDPOINTS`), **`src/workers/news.test.ts`**.
- **48 tests. Suite 1728 → 1776.** Typecheck clean.

**It is deliberately left uncommitted in the working tree**, along with the
`src/research/README.md` and `src/research/index.ts` edits that go with it. Not
discarded, not committed. It is the reference for whoever picks this question
back up — a working answer to "what would this look like" that cost real effort
and should not be re-derived from scratch. If the vendor decision lands on
CoinDesk, most of it is ready; if it lands elsewhere, the parts that survive are
named below.

**No HTTP endpoint was built and no decision was recorded at the time**, both
deliberately, pending exactly the verification decision this entry now defers.

### The mutation run, and the one survivor that mattered

**40 mutants written. 37 caught on the first pass.** All three survivors were
resolved; the final state is **40/40 caught, every one by a test, none by
typecheck**.

| survivor | what it exposed |
| --- | --- |
| a blank API key accepted | **The real one.** The blank-key test installed no `fetch` stub and asserted only that the outcome failed. With the `trim()` branch deleted, a whitespace key fell through to a **real outbound `fetch` at CoinDesk** — and the test still passed, because a blocked or errored outbound call also produces `ok: false`. It asserted the right conclusion for entirely the wrong reason, and under mutation it pointed the suite at the live API. Closed by recording requests and asserting **zero were sent** |
| the envelope object check weakened | Genuine but smaller. A bare string or array payload was still refused — by the `Data`-is-an-array check one line down. Behaviour identical, only the **diagnostic** degraded. That diagnostic is what a first live run reads to learn *which* assumption was wrong, so it is load-bearing here even though nothing observable changed. Closed by asserting the distinguishing message fragments |
| "quiet reported as covered" | **A worthless mutant, and the session that wrote it said so.** It was a cast of a string literal to its own type — equivalent by construction, incapable of failing. Discarded and replaced with one that deletes the quiet branch so an empty list falls into `covered`; the replacement was caught |

Neither fix added a test, so the suite count did not move: both tightened
assertions inside tests that already existed. **That is the point.** Two of these
tests passed before and passed after, and only one of those two was ever
checking anything.

Recorded because it is the third time in this project a passing test has been
found to be passing for the wrong reason (steps 26, 28, 29 each have one), and
because the first survivor is the sharpest example yet: a test that would have
gone on "passing" precisely because the network it should never have touched
happened to be unreachable.

### What the module's wire format is worth: nothing has been verified

**No call to CoinDesk has ever been made from this repository.** Their reference
documentation renders client-side from a spec obtainable only by calling the API
host, which was deliberately not done. The host, paths, `Authorization: Apikey`
scheme, `{ Data, Err }` envelope, every field name in `COINDESK_WIRE_FIELDS`, and
the `PUBLISHED_ON`-is-seconds assumption are **inferences from CoinDesk's public
documentation index and published descriptions**, not observations.

The module is written so that a wrong guess is loud rather than quiet — every
assumption is checked at parse time and a violation throws
`unexpected_category_payload` / `unexpected_article_payload` naming the field, so
a bad field name produces a refusal and never zero articles. That is the correct
posture, and it is still not verification.

**One correction to the spec's premise was established** and belongs here: 21.4
says CoinDesk was chosen "specifically for its pre-scored sentiment field" and
calls it a score a human can check. It is a **label** — `POSITIVE` / `NEUTRAL` /
`NEGATIVE` — produced by prompting a general-purpose LLM to categorise the
article. The reasoning survives (it is computed outside *this* system and a human
can check it against the headline) but it is not calibrated, so the module
returns labels and counts and **no derived sentiment index of any kind**.

### Then the vendor stopped being free

**Verified from CoinDesk's own announcement**, not from a third-party summary.
The coding session found this via secondary comparison articles; it was
re-checked against the primary source for this entry, at
`data.coindesk.com/blogs/changes-to-coindesk-data-indices-api-free-tier-access`:

> "As of **May 21, 2026**, we will be retiring our free API tier"

> "accounts without a subscription will no longer have API access" … "your
> current access will stop returning data."

On pricing, the announcement says only that "our team can help you find the right
plan for your needs" and directs readers to sales. **No public pricing, no trial
tier, no self-serve plan.** The provenance upgrade is recorded because this log's
standing rule is that a measurement and a plausible story do not go in the same
column, and "a comparison blog said so" and "the vendor announced it" are not the
same evidence.

So the module's first live run — the run that would settle whether any of its
assumed field names are right — now costs a sales conversation and an unquoted
subscription. That is a decision, not a task, which is why it is on this page
instead of in a commit.

### The vendor survey, before spending anything

Three alternatives were investigated. Source reliability is tagged throughout,
because on this question the vendors' own marketing and their own legal terms
turned out to disagree with each other.

**[P]** primary — vendor's docs, pricing page or ToS · **[V-blog]** vendor's own
blog or marketing page · **[S]** third party · **[?]** unknown

| | CoinGecko | NewsData.io | APITube |
| --- | --- | --- | --- |
| pre-scored sentiment | **none at all** **[P]** | yes, **paid tiers only** **[V-blog]** | **yes, on the free tier** **[P]** |
| news endpoint access | **Analyst plan and above** — not free **[P]** | free tier exists, without sentiment **[V-blog]** | free tier, 1,000 req/day, 10 req/min, 10 results/req, 5-page pagination cap **[P]** |
| article delay | **[?]** | ~12 h **[V-blog]** | **~12 h** **[P]** |
| auth | **[?]** | `apikey` **query parameter** **[V-blog]** | `X-API-Key` **header** **[P]** |
| commercial use, free tier | n/a | permitted **[V-blog]** | **self-contradictory — below** |

**CoinGecko is not a candidate.** Settled from primary source and disqualified
twice over: its news response carries `title, url, image, author, posted_at,
type, source_name, related_coin_ids` and **no sentiment field**, and the endpoint
requires a paid Analyst-tier-and-above plan anyway.

**NewsData.io is not a free candidate.** Sentiment exists but not on the free
plan. Two of NewsData.io's own blog posts disagree about whether it starts at
Basic or at Professional; **both agree it is absent from Free**, which is the
decision-relevant part, and the disagreement is recorded rather than resolved
because neither is the pricing page. As a paid option it competes directly with
CoinDesk on price, with worse auth — its key travels in the query string, which
lands in every log and proxy that handles the request, and which
`envNewsFetcher` deliberately avoids.

**APITube is the only free tier carrying pre-scored sentiment**, and its shape is
richer than CoinDesk's: a numeric score *and* a polarity, in three independent
scopes, per their docs **[P]**:

```
"sentiment": { "overall": {"score": 0.07, "polarity": "positive"},
               "title":   {"score": 0.11, "polarity": "positive"},
               "body":    {"score": 0.03, "polarity": "positive"} }
```

with a documented threshold rule — a value above 0.4 decides the polarity, and
*"If none of the values exceeds 0.4, the sentiment is considered mixed"*, a
fourth state the current three-label taxonomy cannot represent. It also exposes
**"Suggest" enumeration endpoints** (entities, categories, topics, industries)
**[P]**, which is the only reason a coverage check of the kind the module already
implements might survive a move to this vendor at all — though its documented
entity filters are person / organisation / brand, with **no cryptocurrency
ticker parameter mentioned** **[P, negative]**.

**How APITube produces its sentiment is not disclosed anywhere in its
documentation [P, negative].** That is worse than CoinDesk on 21.5 requirement
2's terms, not better: CoinDesk's categorisation prompt is at least public, so a
reviewer knows what kind of judgement they are looking at. A score with no stated
provenance is closer to the "unverifiable, ungrounded judgement" 21.5 exists to
keep out of proposals than a labelled one is.

### APITube contradicts itself about commercial use, on its own domain, today

Both of these are APITube's own words, live at the time of writing, and they
cannot both govern:

> **Terms of service:** "The Developer plan may be used for development and
> testing in a development environment only, and cannot be used in a staging or
> production environment" — with the license revoked if integrated outside a
> development environment.

> **Marketing FAQ:** "Yes, the free tier can be used for commercial applications
> within the request limits."

**The pricing page names the zero-cost plan "Free", not "Developer" [P].** So the
ToS restricts a plan that does not appear on current pricing, and whether
"Developer" is the former name of "Free" or a separate thing **cannot be
determined from outside APITube**. This was read from primary sources by the
investigating session and **independently re-confirmed by the operator via a
fresh search** — it is a current, live contradiction, not a stale page or a
misreading.

Marketing copy does not override a ToS clause. Until APITube answers this in
writing, the free tier must be treated as **possibly prohibited for this use**,
which is what "fail closed" means applied to a licence.

**Its ToS also appears to restrict storing returned data** — no clause grants
long-term storage, and the terms prohibit storing data "unless expressly
authorized herein" **[P, needs confirmation]**. If that reading is right it
collides directly with **21.5 requirement 5**, which demands every proposal be
permanently logged with its full inputs and retained indefinitely per section
8.7. **CoinDesk's terms have not been checked for the same clause.** This may
turn out to be a constraint on the audit design generally rather than a reason to
prefer one vendor, and it is recorded as an open question rather than as a
finding about APITube alone.

### The 12-hour delay, which may decide this regardless of price or terms

**This is the finding most likely to outlive every other line on this page, and
it is vendor-independent.**

APITube's free tier delays articles by roughly 12 hours **[P]**. NewsData.io's
free tier does the same **[V-blog]**. Whether NewsData.io's paid tiers or
CoinDesk's paid tiers remove the delay is **unknown [?] and unchecked** — the
honest generalisation is not "every tier everywhere is delayed" but "every free
tier surveyed here is, including the only free one carrying sentiment".

Why it matters more than the money: **`fetchedAt` is honest about when the code
fetched, and says nothing about how old the data already was when it arrived.** A
proposal stamped with a fetch instant, built on twelve-hour-old sentiment, is
timestamped truthfully and still wrong about the world — and 21.5 requirement 4
exists specifically so a human cannot approve a stale claim by accident. It is
requirement 6's "degraded proposal indistinguishable from a good one at a glance"
arriving through the one channel the current design does not measure.

**This is the same shape as step 29's truncation problem**, and the same answer
applies: the fix is not to reject delayed vendors reflexively, it is to make the
delay **observable** — a first-class field on the result, the way `CandleWindow`
carries `truncated` and `missingHistoryMs`, so a later stage cannot mistake
half-day-old news for this morning's. The current `NewsSentimentResult` has no
such field, because CoinDesk's delay was never established either.

### Does the built module survive a vendor change? Two-thirds of it

Recorded plainly, because the tempting answer — "it's behind a port, just remap
the field names" — is wrong, and acting on it would produce a quiet mess.

**Genuinely vendor-agnostic, worth keeping whatever happens:**

- The **three-variant result union** — covered / `no_articles_in_window` /
  `not_covered` — as a *concept*. The three facts are facts about any news
  vendor.
- **`articles: readonly [NewsArticle, ...NewsArticle[]]`** — the non-empty tuple
  making "covered with zero articles" unrepresentable. Pure type discipline, zero
  vendor content, and the best thing in the module.
- **Fail-closed throughout**, every failure a thrown `NewsSentimentError`, no
  empty result ever standing in for a failed fetch.
- **`raw` carried through by identity**, and `sentimentAsReported` kept verbatim
  beside the normalised value — 21.5 requirement 2's "the actual raw data it
  used", not a rendering of it.
- **No caching, by design** — a 21.5 requirement 4 consequence, not a CoinDesk
  fact.
- The **port returning `ExchangeOutcome<unknown>` with all parsing in the
  module**, so the parse is testable and the transport is dumb.
- The **publication-time unit plausibility window**, which refuses both
  directions of a seconds/milliseconds error and never rescales.

**Structurally CoinDesk-specific, and NOT a field-mapping swap:**

- **The two-call coverage protocol.** `NewsQuery` has exactly two resources and
  `fetchNewsSentiment` hard-codes "ask the category list, then ask for
  articles". That is not a field name — it is an assumption that **the vendor
  publishes an enumerable asset index**. NewsData.io takes a `coin=` filter;
  APITube takes entity/topic filters. Neither shares the assumption the whole
  design was built around.
- **The three-label sentiment taxonomy.** `SentimentLabel` is a closed union of
  three and `SentimentCounts` is three buckets plus `unrecognized`. APITube's
  numeric score, three scopes and fourth "mixed" state do not fit it, and
  stringifying a float into `sentimentAsReported` to make it fit would be the
  papering-over this module was written to avoid.
- Everything the first item drags into the result type: `category` on two
  variants, `categoriesListed` on the third, **`coverageCheckedAt` on all three**
  (meaningless without a separate coverage call), and two of the eight error
  codes (`categories_unreadable`, `asset_spelling_mismatch`) that exist only
  because an enumerable list exists.

**Roughly two-thirds reusable, one-third a real redesign** — and the third that
needs redesigning is the part the module is *about*. Rewriting it now, against a
vendor set of one, would mean designing an abstraction to fit the only vendor it
has ever seen, which is how the wrong seam gets set in concrete.

### Why paused rather than decided

**Nothing else in section 21 is waiting on this.** Candidate selection (21.3's
watchlist exists; the trending pull does not), the Assess stage, the Derive
stage, the proposal record and the audit table are all unbuilt and none of them
takes news as an input today. Deferring costs nothing but the deferral itself.

Committing now costs an unquoted subscription to validate a module whose wire
format is guessed, for a pipeline stage whose consumers do not exist, against a
staleness constraint nobody has decided is acceptable. Every one of those becomes
cheaper to answer later and none becomes more expensive.

The alternative — pick the free one and move on — is available and was rejected:
APITube's licence position is unresolved, its sentiment provenance is
undisclosed, and its delay is the same 12 hours that may disqualify the category.
"It was free" is not a reason to build on it.

### What has to happen before this is picked back up

Any one of these unblocks it. None has happened.

1. **A written, unambiguous answer from APITube** on whether the plan named
   "Free" may be used in production, plus an answer on how its sentiment is
   produced, plus clarity on the data-storage clause against 21.5 requirement 5.
   Marketing FAQ text does not count.
2. **A decision on whether ~12-hour-old sentiment is acceptable for this use
   case at all.** If it is not, every free tier surveyed is out and the question
   becomes which paid vendor removes the delay — which is a question nobody has
   asked any vendor yet.
3. **A decision to simply pay** — CoinDesk (sales-quoted, and the module is
   already written for it) or a paid NewsData.io tier.

Whichever way it goes, **the delay must become a first-class field on the
result** before news feeds a proposal, for the reason above.

### Open questions, carried forward

- **21.7 open question 2 is still open**, and this step adds a harder one beneath
  it: the "is this coin covered at all" distinction may not be *expressible* with
  a vendor that publishes no enumerable asset index, and if so the honest answer
  is a plain statement that the vendor cannot tell the two apart — never a
  heuristic that guesses which happened.
- **Whether any vendor's terms permit the permanent, full-input audit log 21.5
  requirement 5 mandates.** Raised against APITube, unchecked against CoinDesk
  and NewsData.io.
- **Coverage of newly-listed and thinly-traded coins is undetermined for all
  three vendors.** No vendor's documentation answers it; the marketing figures
  are counts of publishers, not depth of coin coverage. This is exactly what
  21.3's hype hazard cares about and exactly what none of them will tell you.
- **CoinDesk's real wire format remains unverified**, and now costs a
  subscription to verify.
