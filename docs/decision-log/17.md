## Step 17: Two Gemini parsing bugs, uncovered by fixing step 16's wrong-venue bug
Date: 2026-07-31

### The sequence, because the order is the point

Step 16 fixed reconciliation's dispatch so a Gemini account is read from Gemini.
Deploying it did not produce the clean pass step 16 predicted. It produced a
worse-looking outcome that was actually progress: **both bots halted within one
reconciliation pass.**

That is not a regression introduced by the fix. Both bugs below are in the
Gemini response parsers, and both were **unreachable** for as long as
reconciliation was talking to Binance. The dispatch fix did not create them; it
was the first thing to ever exercise that code against a real Gemini response.

### Bug 1: `expected an object, got object`

`asRecord` refused arrays with `expected an object, got ${typeof value}`. Since
`typeof []` is `"object"`, the message read **`expected an object, got object`**
— the least useful error this system has produced. It named nothing actionable,
and it halted both bots.

The message was fixed *first and deliberately*, as its own deployable step,
because it was the only way to learn the real shape: the payload is not recorded
anywhere (`client.ts` calls `response.json()` and keeps no raw body), Gemini's
docs site is JS-rendered and returned nothing to a fetch, and the sandbox
endpoint is signed, so it could not be called by hand without the Worker
secrets. Guessing the shape and writing a test against the guess would have been
worthless. So `describeShape` was deployed, and the next scheduled run reported
the answer in its own alert text:

```
order status: expected a single object, got an array of 1 whose first element
has keys [avg_execution_price, client_order_id, exchange, executed_amount, id,
is_cancelled, is_hidden, is_live, options, order_id, original_amount, price,
remaining_amount, side, symbol, timestamp, timestampms, trades, type,
was_forced]
```

A one-element array wrapping exactly the documented order-status object.

`unwrapSingleOrder` now accepts both shapes — the bare object Gemini's reference
documents and does return for some requests, and the wrapped form it returned
here. Both, not one swapped for the other: this is the same lesson as **14.10**,
where the wire shape had to be established from a real response rather than from
the prose.

**What it deliberately does not do** is `body[0]`. An empty array and a
multi-element array are both refused with specific messages. An empty array
means the order was not found, and quietly reporting that as "no such order"
would let a real order vanish from reconciliation's view — precisely the class
of thing section 9 exists to catch. More than one answer to a single-order query
means an assumption here is wrong, and taking the first would bury that under a
plausible-looking result. A mutant that does `return body[0]` is caught by two
tests.

The same unwrap is applied to `parseCancelledOrder`, whose own docblock asserts
it is the same shape as order-status. Stated honestly in the code: a wrapped
CANCEL response has **not** been observed. It is precautionary, and safe only
because it changes behaviour for arrays alone, which today throw outright.

### Bug 2: a real balance with 11 decimal places

Gemini returned `"99829.54180779832"` for USD `available`. `fromDecimalString`
refuses more than `SCALE` (8) decimal places with "rounding must be explicit",
so the entire account became unreadable — no snapshot, no drift detection, on
every pass.

The strict rule is right for anything this system **sends**: a price or quantity
we invented must not be silently altered. It is wrong for something an exchange
**reports**, which we neither control nor can refuse. Refusing to represent a
balance at all is strictly worse than representing it to 8 places and stating
which way it was rounded.

So `fromDecimalStringRounded(input, rounding)` was added — reusing the module's
existing `Rounding` union rather than inventing a parallel vocabulary, because
that union already encodes the no-default discipline ("There is deliberately no
default anywhere in this module"). `"exact"` still throws. `fromDecimalString`
is untouched and remains the only way in for a value going back out.

Balances parse with **`"floor"`**, and the direction is the whole decision:
rounding up would overstate funds by up to 1e-8 and let the capital ledger
believe in money that is not there, which is the direction that can overspend.
`"floor"` never overstates for either sign. `"trunc"` coincides for the positive
balances seen in practice but understates a debt, so `"floor"` is the stronger
guarantee. A mutant using `"ceil"` fails three tests; one collapsing `"floor"`
into `"trunc"` fails the negative-value test.

One ordering bug was caught by its own test while writing this: `"exact"` threw
on `"1.5000000000000"`, which loses nothing and is exactly `1.5`. The
lost-something check now precedes the `"exact"` refusal.

Tests use the **real** captured values throughout — the 11-decimal string and
the captured key set — not synthetic stand-ins, per the same discipline 14.8
adopted after `toMatchObject` stayed green through a live failure.

### The audit: are these the only two?

Asked explicitly, and the answer is **no, not provably**. Every `requireMoney`
call in `parse.ts` reads an exchange-**reported** value and is therefore the same
class of hazard as the balance one. The at-risk fields, none of which has been
observed failing:

- `avg_execution_price` — a computed average, the single most likely field to
  carry excess precision. This is the one that would fire next.
- `fee_amount` on a fill — also computed.
- fill `price` / `amount`, `original_amount`, `executed_amount` — echo values we
  sent, so they *should* match our 8 places, but Gemini is not obliged to.
- `pubticker.last`.

They are **not** changed here, deliberately. There is no captured evidence of
any of them exceeding 8 places, and this session's own standard is real values
over synthetic ones — a fix tested against an invented payload would assert a
guess. Note also that the order-status parse failed at `asRecord`, *before*
reaching any money field, so the 20:40 run is the first evidence any of them
parse at all; they did, so none of them exceeded 8 places for these orders.

`filters.ts` carried the identical misleading `typeof` message; that message is
fixed, though `parseSymbolDetails` genuinely does want a single object.

Recommended follow-up, not done: extend the reported-value policy across
`parse.ts` with a per-field direction (`"ceil"` for costs so a fee is never
understated, `"floor"` for holdings), once a real payload justifies each.

### What reconciliation found the moment it could see

The 20:40 pass, both accounts, `skipped: 0`:

- **`gemini-main`** — 6 assets (BCH, BTC, ETH, LTC, USD, ZEC), a genuine Gemini
  sandbox account, against `main`'s 445 Binance assets. That contrast is the
  clearest possible confirmation that step 16's dispatch fix is real.
- **Three of the five resting orders are FILLED on Gemini** while D1 and the
  bots still believed them `pending`: `v1-bot-b23y63-1` (0.00077893),
  `v1-bot-328qgw-2` (0.00047554), `v1-bot-328qgw-3` (0.00047000) — each fully
  filled and no longer on the book.

This retires the "quiet market" theory the investigation opened with. The orders
were not sitting unfilled; three of them filled and nothing in this system knew,
because the only component that would have noticed had been reading the wrong
exchange and then failing to parse the right one.

### A second account is now reconciled

Step 16's `reconcilableAccounts` reads the `accounts` registry, where step 11's
provisioning registered both `main` (Binance) and `gemini-main` (Gemini). The
old `accountLabels` looked only at `bot_instances` and `capital_ledger`, and
`main` has neither a bot nor a ledger row — so **it had never been reconciled at
all.** It is now, cleanly (tier `None`, no findings, no skips).

This is correct: an account holding funds is in scope whether or not it has
bots, which is the reasoning `accountLabels` already documented. It is also a
volume change worth knowing — 445 assets per pass at a five-minute cron is
~128,000 snapshot rows a day for that account alone. Retention for
`balance_snapshots` is an open question that now has a real number attached.

### Open questions

1. **The three filled orders are unreconciled.** Both bots are halted and were
   deliberately left that way. Their believed state is wrong, and correcting it
   is a human decision, not a cron's.
2. **The remaining `requireMoney` fields** above, pending real payloads.
3. **Cancellation is unverified against a wrapped response.** The five failed
   cancellations at 20:00 all failed at the status lookup, so
   `parseCancelledOrder`'s unwrap has never executed against a live payload.
4. Step 16's open questions all stand: no dead-man's switch for the cron itself,
   and reconciliation still cannot detect a constant error in its own input.
