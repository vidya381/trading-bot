## PART 1 — WHAT WAS BUILT

A **third strategy** alongside `grid` and `dca`.

| | |
| --- | --- |
| **Parameter** | `trailPct`, and only that. Bounds **1–20%, PROVISIONAL** (spec 22.5 open question 1) — enforced, and the refusal says it is provisional |
| **Entry** | One, sized by `allocatedCapital` (see PART 2) |
| **Exit** | `price <= max(entry_price, highWaterMark) × (1 − trailPct)` |
| **On exit** | Sell the whole position, then **halt** — never a cycle completion |
| **New state** | `BotRuntimeState.highWaterMark`, optional, ratchets upward only |

Everything is real rather than stubbed: `decodeTrailingStopParams` and
`validateTrailingStopParams` shared by `POST /api/bots` and Stage 3's
deterministic validation (one implementation, two callers — 21.5 requirement 3);
`createTrailingStop` on `BotInstance` reserving capital through the same
`createBotInstanceWithCapital` pipeline; `decide()` as a pure function; and the
exit routed through `#placeTrailingStopSell` → `#completeTrailingStopExit` →
`#halt`.

The build followed spec 22.4's own advice — **widen the type union first and
follow the compiler** — which worked, and its stated limits held exactly. Three
classes of site were invisible to `tsc` and had to be found by hand
(`decodeWithRealDecoder`, `positionOf`, the schema-version dispatch), and a
**fourth** class the spec had not anticipated turned up: `EVERY_HALT_REASON` in
`alert-types.test.ts` fires on `HaltReason`, **a union one step removed from the
one being widened**. 22.4 now records it.

## PART 2 — KEY DESIGN DECISIONS AND WHY

### The literal `trailing_stop`, not `trail` or `trailing`

The objection to `trailing_stop` was that `grid` and `dca` are short and
unpunctuated, and the value is baked permanently into `CHECK` constraints, stored
JSON and prompt text. **The objection does not survive contact with the
codebase.** `OrderState` already persists `partially_filled`, and that literal is
written into a SQL `CHECK` in `0001_initial_schema.sql` — the same shape of
constraint being widened here. `grid`/`dca`'s brevity is a coincidence of two
naturally short names, **not a house convention**. `trailing_stop` is the only
candidate that is self-explanatory in the two places it is read by non-authors:
the SQL constraint and the model prompt.

### The single entry is sized by `allocatedCapital`

**Not stated in the original spec, and the only reading consistent with it.**
With `trailPct` the sole parameter (22.2 decision 1) there is no field that could
size an order, and with exactly one entry (22.2 decision 4) there is nothing to
divide the allocation between.

It is **load-bearing in three places** — `orderSizesOf` (the one size a venue
floor must clear), `plannedSpendOf` (the worst-case spend written into the audit
record) and `validateTrailingStopParams` — so it was **not** left implicit. Spec
22.2 now states it as a consequence of decisions 1 and 4, and each of the three
sites carries a `⚠ THE INFERENCE` comment pointing back at it.

### `exitKind: "trailing_stop"` and `haltReason: "trailing_stop_reached"`

DCA already demonstrates the pairing, so no new naming rule was invented:

| | `exitKind` | halt reason |
| --- | --- | --- |
| DCA | `"take_profit"` | `"take_profit_reached"` |
| **Trailing stop** | `"trailing_stop"` | `"trailing_stop_reached"` |

The `_reached` suffix marks a strategy's own **positive** exit. That matters
concretely: `#halt` computes `positiveExit` from a fixed list and alerts `info`
when true, **`critical` when false**. A trailing-stop exit is the strategy's
intended successful outcome, so omitting it from that list would have raised a
critical alert on every healthy exit — training the operator to ignore the one
surface that would report a real failure.

### The exit halts; it never reaches `#completeCycle`

`#applyFillToOrder` dispatched on `exitKind` as a **binary either/or**:
`"liquidation"` → `#completeLiquidation`, **everything else** → `#completeCycle`.
A trailing-stop exit would have fallen through to DCA's cycle completion, which
increments `cycleCount`, writes a `bot.cycle_completed` row, and reads
`config.params.autoRestart` off a config that has no such field.

Tracing `autoRestart` showed it **performs no action at all**: on `true` it
returns `{ status: "running" }` and nothing else — the restart is emergent,
because the cleanup has already left the bot flat and running and DCA's `decide`
re-enters on the next candle. There is nothing to reuse, and **a restart would be
a second entry**, which is exactly what 22.2 decision 4 excludes. The exit is
terminal by construction.

`#completeTrailingStopExit` is modelled on `#completeLiquidation`, not
`#completeCycle`: no `cycleCount`, no `autoRestart`, but **`unmodelledBase` is
accumulated** — exit sells round the held quantity DOWN onto the symbol's step,
so this strands base exactly as entry 69 found DCA's completion did. Skipping it
would have reopened a closed leak in the one strategy with no later cycle
boundary at which anyone would notice.

### `highWaterMark` is optional, not `Money | null`

The obvious declaration is `readonly highWaterMark: Money | null`, matching
`lastPrice` beside it. **That would have been a bug.** `lastPrice` can be
non-optional because it has existed since the state shape did; this field is
**additive to a shape live bots already have on disk**. `#state()` casts stored
JSON rather than parsing it, so a non-optional declaration would be a type lie for
every existing bot, and would need a `schemaVersion` bump and a migration to
become true.

Optional is the section-16-additive treatment this codebase already uses for
exactly this — **`exitKind`, `pendingReplacements` and `unmodelledBase`, the last
of which entry 69 declared for the same reason.** Absent means "no high recorded
yet", and `decide`'s `max(entry, mark)` needs no special case for it.

The ratchet lives in **one** place: `raisesHighWaterMark`, called from the same
state write that records `lastPrice`. `decide()` **reads** the already-updated
mark and never recomputes it — a second ratchet could disagree with the stored
one, and the stored one is what spec 22.8's integrity detector will read.

### No new `CHECK` for trailing stop's risk field

`dca_requires_take_profit` exists because `take_profit_pct` is **nullable** —
optional for grid, mandatory for DCA. A trailing stop has no such field: its stop
is `stop_loss_pct`, **already `NOT NULL CHECK (> 0)` for every row** (section
6.1), and it has no take-profit to require — per 22.1 the strategy exists so a
profit target need not be guessed.

**The real hazard is different, and SQL is the wrong place for it.** If the trail
level *is* the stop-loss, then `stop_loss_pct` (a column) and `trailPct` (a key
inside `strategy_params_json`) are **one quantity with two homes**, free to
disagree. A `CHECK` could only compare them through `json_extract`, coupling table
integrity to the internal shape of a blob `schema.ts` deliberately types as
`unknown`. It is settled in `createTrailingStop` instead, which writes the column
from `params.trailPct` and nowhere else: **params authoritative, column its
mirror** — one implementation, per 21.5 requirement 3.

## PART 3 — THE MIGRATION THAT PASSED EVERY LOCAL TEST AND FAILED THREE TIMES IN PRODUCTION

**This is the most important part of this entry.**

Spec 22.4 touchpoint 9: two `CHECK (strategy_type IN ('grid','dca'))` constraints
shadow `StrategyType` in SQL, are invisible to TypeScript, and fail at runtime
against a real bot. SQLite cannot alter a `CHECK` in place — there is no
`ALTER TABLE ... DROP CONSTRAINT` — so both tables must be rebuilt. Migration
`0010` is the first in this project to rebuild rather than add; 0002 and 0007 are
`ALTER TABLE ... ADD COLUMN`, which SQLite supports directly.

### What happened

| Environment | Result |
| --- | --- |
| Local D1 (`.wrangler/state`) | **17 commands, zero errors** |
| Miniflare / full test suite | **passed**, verified by `schema.test.ts` column-by-column and a manual `sqlite_master` probe |
| **Remote D1 (testnet)** | **failed 3 consecutive times**, auto-rolled-back by D1, **zero data loss each time** |

```
D1 DB was reset and rolled back to its last known good state because the
application left the database in a state where constraints were violated:
FOREIGN KEY constraint failed: SQLITE_CONSTRAINT (extended:
SQLITE_CONSTRAINT_FOREIGNKEY)
```

### What it was not

Both obvious explanations were checked and **both are wrong**.

- **Not the PRAGMA.** Cloudflare's D1 documentation is explicit: `PRAGMA
  foreign_keys = OFF` is **not supported** ("D1 enforces that foreign key
  constraints are valid within all queries and migrations… user queries cannot
  change this"), while `PRAGMA defer_foreign_keys` **is**. The deferred form was
  the only mechanism available, and it was used correctly.
- **Not bad data.** `PRAGMA foreign_key_check` against a real testnet export
  returns **empty**. There were no pre-existing orphans, no ordering problem, no
  index or trigger interaction.

### The actual cause

**SQLite's deferred foreign-key enforcement is a violation COUNTER, not a
re-check of the data.**

`DROP TABLE bot_instances` performs an implicit delete of every parent row, which
**increments that counter once per orphaned child**. On testnet: **30 bots, and
1,099 child rows** referencing them.

| Child table | Rows referencing `bot_instances` |
| --- | --- |
| `alerts` | 478 |
| `audit_log` | 345 |
| `trades` | 138 |
| `orders` | 134 |
| `proposals` | 4 |
| **Total** | **1,099** |

`ALTER TABLE ... RENAME TO` is a **schema** operation. It puts the rows back where
children can see them, but it **never decrements the counter**. At `COMMIT` the
counter was still 1,099 and the transaction was refused.

**The database was genuinely correct at the moment it was rejected.** Reproduced
locally against a real export, immediately before the failing commit:

```
rows present after rename: 30
orphans after rename:      0        ← LEFT JOIN across every child table
COMMIT → FOREIGN KEY constraint failed (19)
```

That is the whole finding in three lines: **consistent data, refused commit.** No
amount of inspecting the data explains the failure, and the fix is not about the
data either.

### ⚠ Why no local test could ever have caught this — a permanent gap, not a lapse

With empty or near-empty tables, `DROP TABLE` orphans nothing, the counter stays
at **0**, and the commit succeeds. **The bug is structurally invisible without
populated child tables.** The 17 clean local commands were not a false pass — they
were a true pass of a case that cannot exhibit the defect.

**This generalises, and should be treated as standing guidance: for any future
migration that rebuilds a table with real foreign-key dependents, local D1,
miniflare and the test suite are all incapable of detecting this class of failure.
Such a migration must be rehearsed against a restored copy of production-shaped
data before it is run anywhere real.** This is the third time this codebase has
recorded a defect that testing could not reach — entry 81's leak surfaced as a
billing anomaly a month in, entry 82's incomplete halt surfaced on a real bot at
3,281 passing tests — and the first where the gap is a property of the environment
rather than of the tests.

### The fix

**An `INSERT` into a parent decrements the deferred counter; a `RENAME` does
not.** So the rows are parked in an unreferenced staging table, the replacement is
renamed into place **empty**, and the rows are then re-inserted by DML — taking
the counter back to zero before commit.

```sql
CREATE TABLE bot_instances_backup AS SELECT * FROM bot_instances;
CREATE TABLE bot_instances_new (...);   -- widened CHECK
DROP TABLE bot_instances;               -- counter += 1099
ALTER TABLE bot_instances_new RENAME TO bot_instances;
INSERT INTO bot_instances SELECT ... FROM bot_instances_backup;  -- counter -= 1099
DROP TABLE bot_instances_backup;
```

Same end state, same column order, one extra copy.

**The migration header carries this warning, and it is repeated here because it is
the part most likely to be undone by someone acting reasonably:**

> ⚠ **DO NOT "SIMPLIFY" THIS BACK INTO stage-drop-rename. It will pass every test
> you can run locally and fail in production, which is exactly what happened.**

### Verification

**Authoring session, local, against a real testnet export** — the failure
reproduced, then the fix verified: migration exit 0, `bot_instances` and
`proposals` dumps **byte-identical** before and after, `PRAGMA foreign_key_check`
empty, zero staging tables left behind, 7/7 indexes rebuilt, and a `trailing_stop`
row accepted by the widened constraint. **No remote call was made from the
authoring session.**

**REMOTE VERIFICATION, THE OPERATOR'S** — applied to testnet after the fix, with
five checks: row counts unchanged (**30** bots, **14** proposals),
`PRAGMA foreign_key_check` empty, `CHECK` constraint text confirmed to contain
`trailing_stop` on both tables, zero staging tables left behind, **21 commands
executed successfully**.

**Spec 22.3 — the dropped-candle requirement — is discharged by two files that
prove different things.** The six `decide()`-level cases establish the structural
property: **the exit is a level test, not a latched crossing event**, so a candle
that never arrives cannot consume the exit. The end-to-end file proves the real
machinery behaves as that rule assumes — a real `PriceFeed` with its real
`#forwardClosed`, fan-out, watermark and `price_feed_fanout_failed` alert, and a
real `BotInstance` from `createTrailingStop`, with the delivery failure induced
exactly as `price-feed.test.ts` induces one. It asserts the candle is **genuinely
gone** (absent from what was delivered, watermark advanced past it — entry 81's
"suppressed forever"), and that the bot exits on the next delivered candle with
its mark still at the peak.

**Mutation-tested rather than merely passing:** severing `decide()`'s read of the
persisted high-water mark **fails** the end-to-end test. It catches the bug it
exists to catch.

### ⚠ The one honest limitation

**The end-to-end test delivers prices to the bot directly in the harness, not over
the cross-Durable-Object RPC hop production uses**, because a DO cannot be entered
re-entrantly from inside another object's callback in this setup. The feed decides
what is delivered — including the drop, the watermark advance and the alert — and
the bot receives exactly the `Price` objects the real fan-out produced and nothing
else. **This is a limit of the test harness, disclosed rather than hidden. It is
not evidence of a problem in the code**, and it is recorded in spec 22.3 too.

**What no test covers, because the design does not:** a dip below the trail that
recovers *entirely within* dropped candles produces no exit. That is inherent to
candle-close evaluation and is 22.6's explicitly out-of-scope sub-candle case — a
real limit, not a covered one.

## PART 5 — STILL OPEN, NOT YET DONE

**`ASSESS_STRATEGIES` has no pin, and the pipeline does not know this strategy
exists.** It is a standalone `["dca","grid"] as const` with nothing tying it back
to `StrategyType` — **the one union in this family with no tripwire** — so
widening `StrategyType` produced no error there at all. Stages 2, 3 and 4 have no
trailing-stop branch. **Trailing-stop bots must be created manually.** This is
also what spec 22.7 requires independently: the strategy must run on testnet in
human-created bots for at least a week before Stage 2 may recommend it.

**The dashboard does not show the strategy's own numbers.** `BotList.tsx` and
`BotSummary.tsx` gate the entry-price display on `strategy === "dca"`
specifically, so a trailing-stop bot falls through to a quantity-only render, and
`highWaterMark`/`trailLevel` are serialized but never displayed. Touchpoint 5 —
**cosmetic, not functional**; the API carries all three figures today.

**`cycleCount` stays permanently at 0 for trailing-stop bots.** Deliberate: the
field is required on `BotRuntimeState`, and making it optional would be a
state-shape change affecting every existing DCA and grid bot for no gain. **⚠ Do
not read a 0 here the way you would for DCA.** For a DCA bot it means "no cycle
has completed"; for a trailing-stop bot it means nothing at all, because the
strategy has exactly one cycle by construction and `#completeTrailingStopExit`
never increments it.

### ⚠ NOT YET DEPLOYED, NOT YET RUN

**The migration is applied to testnet and the code is on disk and committed-ready,
but no trailing-stop bot has ever run.** Nothing has been deployed; no real bot
has been created; `decide()` has never seen a live candle; the exit path has never
placed a real order; and `highWaterMark` has never been written by anything but a
test.

Spec 22.7 gates what comes next and is **stricter** than 21.6's: not less than one
full week of live testnet operation across at least a few manually-created bots
before Stage 2 may propose this strategy at all. Entries 81 and 82 are the
argument for that gate — both were found through weeks of real operation, not by a
suite that was passing the whole time.
