### The finding that does matter: their storage clause versus 21.5 requirement 5

This is the same *class* of problem step 30 raised against APITube, it is live
against the vendor **the spec itself names**, and it is **not** a reason to
reject the vendor. Quoted from CoinGecko's API Terms:

> **6.1** We do not encourage caching or storage of Data. However, if you must
> cache or store Data:- **6.1.1** You should refresh the cache at least every 24
> hours; **6.1.2** Strong encryption and other security measures should be
> applied to stored Data;

> **6.1.4** In the event that CoinGecko terminates your access to or use of the
> CoinGecko API (regardless of reasons), you agree to promptly and permanently
> delete all Data … without keeping any copy thereof unless required by
> applicable law.

> **6.2** Except as expressly permitted hereunder this API Terms, you are not
> allowed to duplicate, reproduce, copy, store, derive from or translate any
> Data …

**21.5 requirement 5 mandates the opposite**: every proposal "permanently logged
with its full inputs", retention per section 8.7, "indefinite, no automatic
summarization". A proposal's full inputs would include the trending item that
put the coin on the list. 6.1.1's 24-hour refresh is about a *cache* and is
arguably not about an audit record; 6.1.4's delete-on-termination is not
arguable — an immutable audit log cannot promise to delete itself.

**Step 30 raised this against APITube and left CoinDesk unchecked. It is now
established for a second vendor, which makes it look less like a fact about one
vendor and more like a constraint on the audit design.** The open question is
therefore sharper than "which vendor": *what may a permanent proposal record
actually contain from a third-party feed* — the raw item, a derived subset, or
only this system's own record that a coin trended and when.

**Nothing in this step is affected, because this module persists nothing.** That
is now a stated reason rather than a coincidence: candidate selection writes no
row, and the raw vendor item it carries is in-memory for the duration of a run.

- **ToS 4.1.1** defers scope to the plan description on the pricing page.
- **The pricing page** lists "Commercial license" as a feature of Basic and

### What the endpoint measures is narrower than "interest", and that is the hype hazard

**Verified [P]:** the endpoint returns "trending search coins … on CoinGecko in
the last 24 hours". Not trading volume, not social volume, not market interest —
**searches on one website**.

21.3 already says trending "is a measure of attention, not of quality" and that
its coins are "disproportionately the ones with the least history and the most
noise". The primary source makes that sharper than the spec's prose does: the
signal is one company's search box, and a coin can top it because of a news
cycle, a listing rumour, or a coordinated push. Nothing downstream may read
`rank` as evidence in a coin's favour, which is why the field is documented that
way in `candidates.ts` and why trending candidates keep a `kind` discriminant
the Explain stage can branch on rather than having to remember to.

### The shape, and the one thing dedup must not do

```
CandidateSet { entryPoint, accountLabel, exchange, requestedBy, selectedAt,
               candidates[], watchlist | null, trending | null }
Candidate    { accountLabel, exchange, pair, sources: [S, ...S[]] }
S            = NamedCandidateSource     { kind, requestedAs, requestedBy, requestedAt }
             | WatchlistCandidateSource { kind, entryId, note, addedBy, addedAt }
             | TrendingCandidateSource  { kind, pullId, vendor, fetchedAt,
                                          coinId, symbol, name, rank, raw }
```

Both entry points return `CandidateSet`, holding the same `Candidate`, because
21.2 says they "differ **only** in how the candidate coin or coins are chosen"
and "a divergence between them is a bug". They are kept from converging by their
**ports**: `NamedCandidatePorts` contains no trending source, so the named path
cannot reach a vendor even by mistake. That is a structural guarantee rather than
a convention, in the same spirit as `watchlist.ts` refusing automated actors.

**`sources` is a non-empty tuple**, borrowing the one thing step 30 called "the
best thing in" `news.ts`: a candidate that came from nowhere is unrepresentable
rather than checked for.

**Deduplication merges provenance; it never drops it.** A coin on both the
watchlist and the trending pull is ONE candidate carrying TWO sources, in its
watchlist position. The convenient alternatives — a boolean, a set of source
names, first-one-wins — are all smaller and all destroy 21.5 requirement 2's
"**which** watchlist entry, or **which** trending pull" at the moment of
merging, with nothing downstream able to recover it. This is step 28's argument
for keeping the two tables apart, arriving one layer later: the sources are
merged into one *list* and never into one *record*.

`watchlist` and `trending` are **null** on a named run rather than zeroed. A
report of "zero entries read" would claim a read that never happened.

### A failed trending pull is fatal. That is a cost, and it was chosen.

21.5 requirement 6 names "the trending source is unreachable" as a fail-closed
condition, so `selectGeneralCandidates` **throws** `trending_unavailable` and
returns nothing — including the perfectly good watchlist candidates it had
already read. The error message names how many were discarded.

The cost is real and is not hidden: an operator whose vendor is down gets
nothing on a day when eight watchlist coins were available. It was chosen anyway
because a watchlist-only result is **not a smaller general run**. 21.3 says the
trending pull exists because "it is the only way the system can ever surface
something the operators did not already think to look for"; without it the
general entry point is, in 21.3's own words, "a slightly more convenient way of
re-reading a list you wrote yourself". Returned under the name "general
candidates", that is a degraded result indistinguishable from a good one — which
is exactly what requirement 6 exists to prevent.

**The escape hatch is available and deliberately not built.** An explicit
watchlist-only entry point could be added later, under its own name, where the
human asking for it knows what they are asking for. What must not exist is a
general run that quietly becomes one. Tightening this later would be a breaking
change; loosening it later is an addition.

**A tradable set that cannot be READ aborts too**, and is specifically **not**
recorded as a rejection. A rejection list saying fifteen coins are untradable
when nobody could tell is a false record of what the venue offers — section
5.6's rule, one layer out, and the same call `watchlist.ts` and `candles.ts`
already make. It aborts on the **first** unreadable answer rather than grinding
through every coin to reach the same conclusion.

**An empty result is a FACT and is reported as one.** `TrendingPullReport`
carries `returned`, `accepted`, `pairsMatched` and every rejection.

### The symbol-to-pair mapping is a hypothesis that the catalogue judges

**This is the assumption in this step, stated plainly because it is the one most
likely to be wrong in a way that looks like nothing.**

A trending vendor reports a coin (`"bitcoin"`, `"BTC"`); a venue lists a pair
(`"BTCUSD"`). Nothing in this system maps between them: `SymbolListing` carries
pair strings with no base/quote split, and the only decomposition available
(`getSymbolFilters`) costs **one exchange request per pair**, which is a poor
trade for filtering a list of fifteen.

So `pairHypotheses` **constructs** `${BASE}${QUOTE}` and then checks it against
the real catalogue through the shared `checkTradable`. The ordering is what makes
it safe: the concatenation is never stored or trusted, and a hypothesis that
passes is **by definition the catalogue's own spelling, character for
character**. Step 28's finding survives intact — the comparison stays exact and
case-sensitive, and nothing is case-folded on the venue's side.

The ticker **is** upper-cased, and that is a different act from case-folding a
comparison: it translates a vendor's vocabulary into this system's, where
`parseSymbolList` has upper-cased every venue's catalogue since step 3. A vendor
reporting `"btc"` would otherwise contribute nothing at all.

**What it assumes:** base-then-quote, no separator. True for both venues this
system speaks to (Gemini `BTCUSD`, Binance `BTCUSDT`). **Not universal** — venues
exist that write `BTC-USD`, and on such a venue every hypothesis would fail and
the trending pull would contribute nothing while erroring about nothing.

**Both halves of this were confirmed against real data after the fact** (see the
live run below): CoinGecko returns uppercase symbols, and `${BASE}${QUOTE}`
matched Gemini's real catalogue exactly for three of fifteen trending coins. The
upper-casing is therefore a **no-op for CoinGecko specifically** and is not
load-bearing for that vendor; it stays because the port is vendor-neutral and no
vendor is chosen. `candidates.ts` records that so nobody reads it as a fact
something depends on.

That is precisely why `TrendingRejection.triedPairs` exists. The failure is
legible in the report as *fifteen coins rejected, and here are the fifteen pairs
that were tried* rather than as a quiet day. Same posture as step 29's
`truncated`/`missingHistoryMs`: the limit is not worked around, it is made
observable.

`quoteAssets` is **required with no default**, for the same reason: which quote
asset an account trades in is an operator's decision, and a default would make it
silently and be wrong on the venue it was not written for.

### The perpetuals finding, and the hole it exposed in the test written for it

**The most useful thing the run produced was a near-miss that was correctly not
a near-miss.** `HYPE` trended. Gemini lists **no spot `HYPEUSD`** — but its real
catalogue **does** carry `HYPEGUSDPERP` and `HYPEUSDCPERP`.

A perpetual is a **different instrument**, not a spelling variant: different
margin, funding and liquidation semantics, while every order, fill and PnL path
in this system is spot. So the right behaviour is to reject `HYPE` plainly and
say nothing about the perps, and that is what happens — `checkTradable`'s
near-match is an **exact case-insensitive equality**, so `hypeusdcperp` never
folds to `hypeusd`, and `selectGeneralCandidates` records `reason:
"not_tradable"` with `triedPairs: ["HYPEUSD"]` and nothing else.

**It is right, and it is right by accident.** That equality was written for step
28's casing lesson; nothing in it is about perpetuals. `grep -rn "PERP" src/`
returns **nothing** — this repository has no concept of a perpetual anywhere. So
the behaviour is unowned, and the change that would break it is somebody
widening the near-match to a prefix or substring test, which in isolation looks
like a usability improvement.

A pinning test was added. **The first version of it did not work, and that is
worth more than the test is:**

| | |
| --- | --- |
| the pinning test as first written | asserted the general path returns no candidate and that no `"PERP"` string appears anywhere in the `CandidateSet` |
| the mutant it was written to stop | near-match widened from `===` to `.startsWith(...)`, which makes `HYPEUSDCPERP` a near-match of `HYPEUSD` |
| what happened | **the mutant survived.** The test passed unchanged |

The reason is structural and was invisible until the mutant ran:
`selectGeneralCandidates` **discards the refusal message** on the
`pair_not_tradable` path, keeping only a reason code and the tried pairs. So a
bad near-match physically cannot reach a general run's caller — and the test
asserting on a general run therefore cannot see it either. It was asserting the
right conclusion on the one path where the bug is unreachable.

**`selectNamedCandidate` is the path that leaks**, because it propagates
`checkTradable`'s message verbatim into the thrown error. Under the mutant it
answers: *"HYPEUSD" is not tradable … that venue spells it "HYPEUSDCPERP"* —
**recommending a perpetual to a human, by name, in a message written to be
helpful.** The test was rewritten against that path and now asserts the refusal
message contains neither `"PERP"` nor `"spells it"`. Both the `.startsWith` and
`.includes` mutants are caught.

**This is the fifth time in this project a test has been found passing for the
wrong reason** (steps 26, 28, 29, 30, and twice in this one). The pattern here
is new and worth naming on its own: *a test aimed at the path where the failure
is structurally unreachable will pass forever, and reads exactly like a test
that is working.*

### FLAGGED GAP, PRIORITIZED: nothing in this system distinguishes spot from perpetual

**This is not a routine open question and must not be read as one.** It is
recorded here at the operator's direction, as a gap requiring **its own
follow-up decision before it can be considered closed.**

**It is already live in production, today, and it is reachable by an ordinary
mistake rather than by unusual input:**

- `parseSymbolList` (`gemini/parse.ts`) pushes **every** non-empty string from
  `/v1/symbols` through, upper-cased, with **no filtering of any kind**. The
  perpetuals are genuinely in the tradable set — they are part of the 392 pairs
  step 28 counted live.
- **`addToWatchlist` would accept `HYPEUSDCPERP` with zero resistance.** Its
  `assertTradable` gate passes, because the pair *is* on the venue's list.
- **`fetchCandleWindow` would fetch candles for it**, for the same reason.
- **`selectNamedCandidate` would accept it as a named candidate**, for the same
  reason.
- **Nothing anywhere would flag that it is not spot**, at any later stage, up to
  and including a bot proposal a human is asked to approve.

The trending path is the **only** place this is structurally safe, and only
incidentally: `${BASE}${QUOTE}` cannot construct a `PERP` suffix. **Every
human-typed path has no protection at all** — and a human typing a symbol they
saw on the venue's own listing is the ordinary case, not an edge case.

**What closing it requires — a decision, not a task.** Either:

1. **A spot-only filter at the shared tradability level**, where `checkTradable`
   already is, so the watchlist write path, the candle fetch and both candidate
   entry points inherit it from one place rather than growing three copies of a
   suffix rule — 21.5's standing rule about second implementations of a risk
   check applies directly. This needs a per-venue answer to "what marks an
   instrument as not-spot", which is a real question: `PERP` is a Gemini
   convention observed in one listing, not a verified rule, and Binance's
   convention is unexamined.
2. **Or an explicit, recorded accepted-risk decision** that operators are
   trusted not to enter perpetual symbols, with the reasoning written down.

**It is deliberately NOT fixed in this step**, per the operator's direction to
scope this step to candidate selection only. That is a scoping decision about
*when*, and explicitly not a judgement that the gap is small.

### Watchlist entries are not re-validated here. Stated as a deviation.

21.3's tradability requirement is attached to the trending source, and that is
where it is enforced. A watchlist pair was checked when it was added and is not
checked again at selection time, so a pair delisted since then stays a candidate.

Step 28 already recorded this gap on the read path — `readWatchlist` "says
nothing about the tradable set having gone stale underneath" its entries — and
closing it would change what membership of the watchlist *means*, from "a human
vouched for this" to "a human vouched for this and the venue still agrees". That
is a decision, and it was not in this step's scope. A test asserts the current
behaviour explicitly rather than leaving it to be discovered.

### Tests and mutation results

**38 tests. 24 mutants, 24 caught — every one by a test, none by typecheck.**
Mutants were aimed where they were asked to be: twelve at dedup and provenance,
six at the fail-closed trending and unreadable-catalogue paths, four at the
guards those two depend on, and **two added after the live run** at
`checkTradable`'s near-match (`===` widened to `.startsWith` and to `.includes`),
which are what the perpetuals pinning test exists to stop.

**Twenty-one of the first twenty-two fell on the first pass. Two survivors
across the whole session, and both were real:**

| survivor | what it exposed |
| --- | --- |
| the candidate list sorted by pair name instead of first appearance | **Every fixture in the file happened to be alphabetical.** `BTCUSD, ETHUSD`; `BTCUSD, ETHUSD, SOLUSD`. So the two tests whose entire purpose was to assert ordering asserted a list that sorting produces identically, and the documented "watchlist first, then trending, in first-appearance order" guarantee was checked by nothing at all. Closed with two tests whose fixtures are deliberately not alphabetical — watchlist `SOLUSD` then `BTCUSD`, trending `ETH`, expecting `SOLUSD, BTCUSD, ETHUSD` |
| the near-match widened to a prefix test, against the **first** perpetuals pinning test | Full account in the perpetuals section above. The test asserted on `selectGeneralCandidates`, which **discards the refusal message**, so the leak it was written to stop was unreachable on the path it was watching. Re-aimed at `selectNamedCandidate`, which propagates the message verbatim; both the `.startsWith` and `.includes` mutants are now caught |

**That is the fourth and fifth time in this project a passing test has been found
to be passing for the wrong reason** (steps 26, 28, 29 and 30 each have one).
Two distinct lessons, and the second is new:

- *A fixture chosen for readability will tend to be sorted, and a sorted fixture
  cannot test order.*
- *A test aimed at the path where the failure is structurally unreachable will
  pass forever, and reads exactly like a test that is working.* Step 30's
  blank-key survivor was the same shape — an assertion true for a reason other
  than the one it was written for — but this one is sharper, because the path
  was chosen deliberately and the choice was what made the test empty.

**What the numbers do not prove.** 24/24 is against the mutants written for
them, and two survivors are the evidence that the first list of assertions was
not exhaustive either. **No test here has spoken to any venue or any trending
vendor**: every `TrendingSource` in the suite is a stub written by the same
session that wrote the code it checks, and the perp catalogue entries are real
strings copied into a stub, not a live listing.

Unlike the rest of this step, the live run above **is** the real thing — and it
verified the *hypothesis and the vendor*, not the module. Nothing has yet
exercised `selectGeneralCandidates` end to end against anything real, because
there is no endpoint to reach it through.
