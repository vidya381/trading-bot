## PART 1 — WHAT TRIGGERED THIS, AND WHAT THE INVESTIGATION CORRECTED

[Entry 84](84.md)'s diagnostic flagged `resolveClearedStandingAlerts`
(`src/alerts/standing.ts`) as running an unfiltered fleet-wide D1 query on every
poll pass: it read `WHERE source = ? AND resolved = 0` and then filtered to the
calling bot in JS.

**The diagnostic was half right, and the half it got wrong determined the shape
of the fix.** The function has **four** callers, not one, and they do not share
a scope shape:

| Call site | What it is | `source` | Reads the fleet to act on one bot? |
| --- | --- | --- | --- |
| `bot-instance.ts:2947` | the open-order poll | `bot-instance` | **YES** |
| `bot-instance.ts:5532` | `#reportLadderVacancy` | `bot-instance` | **YES** |
| `reconcile.ts:408` | `resolveClearedAlerts` | `reconciliation` | **No** — genuinely account-wide |
| `reconcile.ts:1527` | `auditEmptyBalanceSet` | `reconciliation:{account}` | **No** — already narrow |

**Why the two `BotInstance` callers really were reading the fleet.**
`BOT_ALERT_SOURCE` (`bot-instance.ts:931`) is the single literal string
`"bot-instance"`, shared by **every bot in the fleet**. `source` is therefore not
a per-bot filter and never was, so a `source`-only query returns every bot's open
rows — on a 30-second timer, to act on one bot's.

**Why the other two are not that.** `reconcile.ts:408` passes
`inScope: (id) => id === null || botIds.includes(id)` — an **account-wide** pass
covering N bots **plus** the account-scoped rows that belong to no bot at all
(`auditBlindness` and its siblings write those with a null `bot_instance_id`).
`reconcile.ts:1527` passes `inScope: () => true` because its `source` is
**already account-qualified**; the source string *is* the scope, and there is
nothing for a bot filter to add.

**Stated plainly: applying a single narrowing fix to all four call sites would
have broken account-wide reconciliation and the source-scoped pass.** The first
would have stopped closing the account-scoped rows only it covers; the second
would have gained a filter on a column its rows do not meaningfully use. This is
why the fix could not be "just add a `WHERE` clause," and it is the reason the
callers were enumerated before anything was changed rather than after.

**What was checked and found clean.** `inScope` was only ever consulted per-row,
after `owns` — no fleet-wide aggregate, no cross-bot comparison, no count over
other bots' rows depended on the broad read. Every alert the object writes goes
through `#raiseStanding` (`bot-instance.ts:6893`), which hardcodes
`botInstanceId: config.botInstanceId`, so **under `source = 'bot-instance'` there
are no null-bot rows** and a `bot_instance_id = ?` clause is *exactly* equivalent
to the predicate it replaces — not merely close.

## PART 2 — WHY B OVER A

Two implementations were on the table.

| | **A — additive** | **B — scope descriptor** |
| --- | --- | --- |
| Shape | keep `inScope`, add an optional `botInstanceId` field pushed into the `WHERE` | replace `inScope` with a discriminated union describing the scope |
| Diff | two call sites, one optional field | four call sites, one interface change |
| Scope described in | **two places** — the new field and the surviving predicate | **one place** — the descriptor |
| Failure mode | the field and the predicate silently disagree | none available; both are derived |

**B was chosen, and the reason is correctness, not diff size or style.** Under A
the query narrowing and the row check are two independent statements of the same
rule, kept in step only by whoever edits them next. That is **the exact failure
shape this module's own header exists to prevent** — `shared/alert-types.ts`
exists because the alert-type FORMAT was duplicated, and `standing.ts` exists
because the alert LIFECYCLE was going to be. Reintroducing the same class of
duplication *inside the module built to close it* to save two call sites of churn
would have been the wrong trade.

Recorded explicitly as a **deliberate correctness-over-diff-size tradeoff**, so a
later reader does not mistake B for a preference about taste.

## PART 3 — THE SCOPE DESCRIPTOR

```ts
export type StandingAlertScope =
  | { readonly kind: "bot"; readonly botInstanceId: string }
  | { readonly kind: "account"; readonly botInstanceIds: readonly string[] } // + rows with a null bot
  | { readonly kind: "source" };
```

**Two derivations, one source of truth.**

| Derivation | Produces | Role |
| --- | --- | --- |
| `scopeFilter(scope)` | the `WHERE` fragment | **an optimisation** — narrows the read |
| `scopeCovers(scope, botInstanceId)` | the row-level predicate | **the authority** — decides what may be closed |

`scopeCovers` **still runs on every returned row**, including rows the `WHERE`
clause already guaranteed. That is not redundant defence; it is what keeps the
filter honest. The predicate is the *definition* of what a pass may close and the
filter is a way of reading fewer rows to reach the same answer, so a future scope
whose SQL narrowing is imprecise — **or absent, as `account`'s is** — remains
correct rather than quietly over-closing.

**Why `account` cannot narrow in SQL.** `db/table.ts`'s `Where` builder supports
`eq` / `in` / `isNull` and **has no `OR`**. The `account` scope is irreducibly
`bot_instance_id IN (...) OR bot_instance_id IS NULL`. Widening the query layer
to express that would serve one caller on a **5-minute cron**, when the read this
work exists to cut is the **30-second** one. Deliberately not done.

### The four call sites

| Call site | Old `inScope` | New `scope` | Narrows in SQL? |
| --- | --- | --- | --- |
| `bot-instance.ts:2952` | `(id) => id === config.botInstanceId` | `{ kind: "bot", botInstanceId }` | **Yes** |
| `bot-instance.ts:5537` | `(id) => id === config.botInstanceId` | `{ kind: "bot", botInstanceId }` | **Yes** |
| `reconcile.ts:413` | `(id) => id === null \|\| botIds.includes(id)` | `{ kind: "account", botInstanceIds: botIds }` | No |
| `reconcile.ts:1534` | `() => true` | `{ kind: "source" }` | No |

Both reconciliation scopes are preserved **exactly**. Neither narrows.

## PART 4 — THE INDEX

`migrations/0011_alerts_standing_lookup.sql`:

```sql
CREATE INDEX idx_alerts_standing_lookup ON alerts (source, bot_instance_id)
  WHERE resolved = 0;
```

**Partial, following migration 0004's precedent** (`idx_alerts_pending_notification`):
the interesting set is the OPEN incidents, almost always empty or tiny, while the
table grows without bound (section 8.7 retains everything). `source` leads
because it is in **every** caller's `WHERE` — the account- and source-scoped
passes narrow on nothing else and get a seek out of this index too;
`bot_instance_id` second so the single-bot case seeks the pair.

**Why 0001's three indexes do not serve it:**

| Index | Why not |
| --- | --- |
| `idx_alerts_created (created_at)` | wrong column |
| `idx_alerts_bot_created (bot_instance_id, created_at)` | leads on the bot, cannot seek on `source`; indexes the whole table, not the open rows |
| `idx_alerts_unresolved (severity, created_at) WHERE resolved = 0` | right predicate, but **leads on `severity`** — a lookup by `source` cannot seek it |

`EXPLAIN QUERY PLAN` confirms the new index is chosen:
`SEARCH alerts USING INDEX idx_alerts_standing_lookup (source=? AND bot_instance_id=?)`,
and the un-narrowed callers get `(source=?)` from the same index.

**This is `CREATE INDEX` only. No `ALTER`, no table rebuild.** [Entry 83](83.md)'s
deferred-foreign-key-counter hazard **does not apply**: that counter is
incremented by `DROP TABLE` orphaning children, and nothing here drops anything.
No column order changes, so `schema.ts` and `schema.test.ts` need no matching
edit.

**Bonus finding.** The same index also serves `resolveHaltAlerts`
(`halt.ts:97`), which was **already** filtering on
`(source, bot_instance_id, resolved = 0)` — it narrowed in SQL from the start,
and was reading it off **no supporting index at all**. A second caller for free,
and part of why the index is this shape rather than one built only for the poll.

**The typecheck errors are not this change's.** All 14 sit in `src/api/serialize.ts`
and `src/research/*` and reference `trailing_stop` / `TrailingStopParams` — entry
83's widened `StrategyType`, whose consumers were never updated. Confirmed rather
than asserted: a **clean worktree at `HEAD`** was created and typechecked
separately, producing the same 14, and the error file set has **zero overlap**
with the nine files this change touches.

**The Miniflare pool-teardown "error" is pre-existing.** The summary line reads
`Test Files 123 passed (124)` with one unhandled `Worker exited unexpectedly`.
The baseline worktree produces the **identical** line. The JSON reporter shows
**all 124 files and all 3353 tests genuinely passed** (791/791 suites). It is a
vitest-pool-workers shutdown flake, **not a regression and not a masked failure**.

### The equivalence test

The only thing that makes this a performance fix rather than a behaviour change
is that it closes **exactly the same rows**. So that is what is asserted — against
`resolveTheOldWay`, a **verbatim transcription of the replaced implementation**,
rather than against a hand-reasoned expectation. A re-derived expectation would
encode the same mistake twice if the reasoning were wrong. Both run against
identically seeded fresh databases; the assertion compares resolved ids **and**
the full table afterwards, for **all three** scope kinds, plus a mixed
`stillOpen` case and the account-scoped row a bot filter must never close.

### The self-correction

An initial comment on the rows-read test claimed the assertion **would fail if
migration 0011's index were dropped**. This was **checked with
`EXPLAIN QUERY PLAN` rather than left as an assumption, and found to be wrong**:
with the index dropped, SQLite falls back to 0001's `idx_alerts_bot_created` —

```
SEARCH alerts USING INDEX idx_alerts_bot_created (bot_instance_id=?)
```

— which **still seeks by bot** and still reads only that bot's rows. The
rows-read bound passes with the index absent. The real cost of dropping it lands
on the **account- and source-scoped** callers, which have no bot column to fall
back on.

Two things followed. The comment was corrected to state **what the test actually
proves** (the *shape* of the read: one bot, not the fleet). The index-specific
assertion was **moved to `schema.test.ts`**, where an index belongs and where it
is pinned by name, partiality and column order.

**The general lesson, stated plainly: a test's own comment claiming what it
catches is itself a claim, and needs checking like any other. It is not
something to trust by default** — least of all when it is the sentence that would
persuade a later reader they are already covered.

## PART 6 — MEASURED VS PROJECTED

Held to [entry 84](84.md)'s standard: what was measured is separated from what is
extrapolated, and the extrapolation is labelled.

### Measured

Seeded 12-bot fixture, read through a wrapper that records **D1's own
`meta.rows_read`** — the billing unit, not a proxy for it. One resolve pass, one
bot:

| Read | `rows_read` |
| --- | --- |
| fleet-wide, then filter in JS | **37** |
| narrowed in SQL | **4** |

**An 89% reduction.** Both did exactly one lookup; only the rows it touched
changed. The important property is not the ratio but its shape: **the old cost
grows with the fleet and the new one does not.**

This is a **real measurement** from local D1, not an estimate.

### Projection — not confirmed

**Entry 84's ~25,700 queries/day figure is UNCHANGED by this work.** The number
of queries made per day is identical; only the **rows read per query** drops.
Nothing here removes a query.

Extrapolating the 37→4 fixture ratio to production **assumes a similar number of
concurrent unresolved `bot-instance` alerts to what the fixture models**, and
that has **not been observed in production**. The real ratio depends entirely on
how many open incidents the fleet is carrying at the moment each pass runs — a
quiet fleet reads few rows either way.

The resolve call is additionally gated on `observedEverything(pass)`, so the
**real firing frequency is below the raw poll count**.

**The follow-up, concretely: check D1 `rows_read` metrics roughly 24 hours after
deploy before treating this cost reduction as confirmed.** A fixture measurement
is a measurement of the fixture.
