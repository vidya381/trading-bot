## PART 1 — WHAT WAS ASKED, AND WHAT WAS ACTUALLY WRONG

Asked for as a fix for the same **"not grid means DCA"** fall-through already
found and fixed on the dashboard's bot detail page. The fall-through was exactly
where it was said to be, at `validatedProposalView`:

```ts
result.proposal.params.strategy === "grid"
  ? { strategy: "grid", ...nine grid fields }
  : { strategy: "dca",  ...nine DCA fields }
```

That `:` was never a default case. It was an unstated claim that every non-grid
proposal is a DCA proposal, and it had been false since **22.4 touchpoint 8**:
`ValidatedProposal["params"]` has carried a `trailing_stop` arm since then,
`decodeWithRealDecoder` decodes one with the real decoder, and
`validatorNamesFor` is already exhaustive over all three. The value reaching this
function really could be `{ trailPct }`.

### ⚠ THE CORRECTION: THIS IS NOT A RENDERING CRASH, AND THE FAILURE MODE IS WORSE IN ONE SPECIFIC WAY

The premise carried over from the dashboard fix — that this "will crash
`/proposals/:id` the same way the bot detail page crashed" — is **wrong about
where and how it fails**, and the difference is the reason this entry exists
rather than a one-line note under `be281f8`.

`money(x)` is `toDecimalString(x)`, which does `value < ZERO` and `magnitude /
ONE` against `bigint` constants. Handed `undefined` it does not return a bad
string; it throws, and the throw was reproduced rather than reasoned about:

```
TypeError: Cannot mix BigInt and other types, use explicit conversions
```

**That throw happens inside the Worker, not in a browser.** The call chain is
`validatedProposalView` ← `deriveResultView` ← `deriveProposalReasoningView`,
and `handlers.ts` builds that view at **line 2731**, while
`logDeriveProposal` writes the permanent record at **line 2735**. So the order
is: run Stage 2, run Stage 3, **throw**, and never reach the write.

A trailing-stop proposal attempt would therefore have produced:

* a **raw 500** from `POST /api/proposals/run`,
* with **two paid model inferences already spent**,
* and **no permanent record written at all** — the row 21.5 requirement 5 exists
  to guarantee, absent for precisely the request that failed.

No page goes blank because **no response is ever built**. The dashboard's
`LoadError` would render its honest message; the operator would see a server
error, not a black screen. The information destroyed is not a screen — it is the
audit record, which is the more expensive thing to lose.

## PART 2 — WHY IT WAS LATENT, NOT LIVE

⚠ **PRODUCTION WAS NOT AFFECTED BY THIS PARTICULAR BUG, AND A READER MUST NOT
INFER OTHERWISE FROM PART 1.** Two independent gates, both upstream, already made
a trailing-stop proposal impossible to generate:

1. **`ASSESS_STRATEGIES = ["dca", "grid"]`** (`research/assess-prompt.ts:126`).
   Stage 2 refuses a `trailing_stop` answer outright with
   `strategy_not_recognised` — no trimming, no nearest-match. The pipeline stops
   before Stage 3 is reached at all.
2. **`DERIVE_MODEL_SETTINGS`** (`research/derive.ts:200`) has no `trailing_stop`
   entry. `deriveParameters` indexes it with `assessment.strategy`, so even past
   gate 1 the settings would be `undefined` before the serializer is reached.

So the bug was **real, correct to fix, and unreachable** — a trap armed behind
two closed doors, which would have sprung on the first person to open them. It is
worth being precise that finding it cost nothing and fixing it cost little,
whereas finding it *after* lifting those gates would have cost a paid inference
and an audit gap, in the one part of the system whose entire purpose is being
auditable.

## PART 3 — THE REAL SCOPE, AND A FALSE ACCUSATION THAT WAS ALREADY LIVE

### Fixing `serialize.ts` alone would have introduced a new bug

The corrected view emits `{ strategy: "trailing_stop", trailPct }` — a valid,
complete shape. `checkParamsShape` (`research/proposal-shape.ts`) did not
recognise it: `PROPOSAL_STRATEGIES` was still `["grid", "dca"]`, so
`isProposalStrategy("trailing_stop")` was false and the answer was
`strategy_not_recognised`. The proposal page would then have raised its red
**"⚠ This params object does not match its claimed strategy … Do not act on
it"** banner over a perfectly genuine response.

**A guard that refuses real data is worse than the crash it replaced.** The crash
is loud and obviously a fault; a false corruption warning is quiet, credible, and
sends an operator to hunt for damage that does not exist.

### ⚠ AND THAT FALSE WARNING WAS NOT HYPOTHETICAL — IT WAS LIVE, ON `bot-ts1`

`checkParamsShape` is not only used on pasted proposals. `cloneSearchParams`
(`dashboard/src/research/botClonePrefill.ts`) runs it on **real bot configs**,
with the label put back in:

```ts
const shape = checkParamsShape({ ...config.params, strategy: config.strategy });
if (!shape.ok) return null;
```

`bot-ts1` is a real trailing-stop bot with a correct, complete config. Every
render of its detail page therefore took this path, got
`strategy_not_recognised`, returned no link — and `CloneBotLink`, which inferred
its refusal message from `bot.config === null` alone, told the operator:

> *"Its stored parameters do not match the strategy they are labelled with, so
> there is nothing coherent to put in a form."*

**That sentence was false, and it was on a live page.** The parameters match
their label exactly. The real reason is that `/bots/new` has no trailing-stop
controls. A refusal naming the wrong cause is worse than a refusal, because it
accuses the data instead of the form.

Fixed by deciding the cause where it can be tested rather than guessed at in JSX:
`cloneRefusal` returns `"no_config"` / `"incoherent_config"` /
`"strategy_not_creatable"`, and `CloneBotLink` words each. The third now says the
configuration **is fine** and names the strategy.

**The staleness threshold is a judgement call and is marked as one.**
`trailing_stop` gets **1 hour**, placed with DCA rather than with grid, by
applying the file's own stated test — does the strategy name an ABSOLUTE price?
`trailPct` is a percentage applied to a high-water mark discovered at runtime, so
no; but the single entry is sized by `allocatedCapital`, an absolute quote amount
checked against the reference price, exactly as DCA's `baseOrderSize` is. Same
structure, same threshold, same `validateOrder` backstop. **Nothing was
measured.** The only trailing-stop bot ever run never filled its entry
(`be281f8`, and entry [86.md](86.md)), so there is no evidence about how a trail
behaves across a stale window. Worth an operator's disagreement.

**Every one of these call sites was found by the compiler, not by reading.**
Completing the two unions turned four of them into build errors in a single pass.

## PART 4 — ⚠ THE NEGATIVE-CONTROL ASYMMETRY: A STANDING PROPERTY, NOT A ONE-OFF FIX

This is the sharpest technical finding of the session and it should outlive the
fix. Two negative controls were run, each adding a fake fourth strategy:

| Control | What it caught it | What it did NOT catch it |
| --- | --- | --- |
| **A.** `mean_reversion` added to `StrategyType` (`db/schema.ts`) | The source-scan coverage test, ×2 (`proposalParamsView has no arm for "mean_reversion"`, and the same for `proposalFieldsFor`) | **`tsc` is completely silent at `serialize.ts`** |
| **B.** A fourth arm added to `ValidatedProposal["params"]` | `tsc`: `src/api/serialize.ts(1098,67): error TS2366` | — |

**The two guards watch different things, and the gap between them is real.**
`proposalParamsView` switches on `ValidatedProposal["params"]`, so the compiler
fires when *that union* grows. It does not fire when `StrategyType` grows,
because the params union is declared by hand in `derive-parse.ts` and is not
derived from `StrategyType`. **Those two can drift, and while they are drifted
the compiler has nothing to say.**

That drift is not hypothetical either: it is exactly the state the codebase was
already in. `StrategyType` gained `trailing_stop` in step 83; the params union
gained its arm in 22.4 touchpoint 8; `PROPOSAL_STRATEGIES`, `StalenessStrategy`
and the dashboard's `Strategy` never did, and nothing failed to compile at the
serializer as a result.

**The standing rule for the next strategy:** completing `StrategyType` is not
completing the system, and `tsc` alone will not tell you which seams you missed.
Only a test that reads `StrategyType` at runtime and checks each seam against it
closes the gap. That is what
`src/api/proposal-params-coverage.test.ts` now does — it parses the union out of
`db/schema.ts` rather than restating it, and asserts an arm per member in both
`proposalParamsView` and `proposalFieldsFor`, plus that the seam is still SHAPED
as an exhaustive switch (no `default:`, no returned ternary). A future edit that
"fixes" a compile error by adding a `default` that reuses a neighbouring
strategy's arm type-checks perfectly and is precisely the edit that made this
bug.

### ⚠ AND THE COVERAGE TEST'S OWN FIRST VERSION PASSED VACUOUSLY

Found mid-implementation, and recorded because the general lesson is worth more
than the fix. `functionBody` locates a function's end by searching for a closing
brace in **column zero**. The `code()` helper it reads through was copied from
the dashboard's equivalent, which **trims every line** to strip comment prose —
so every nested `};` inside the switch also landed in column zero, and the
"function body" ended at the **first `return { … };`**. The scan was checking one
arm and calling it three.

It failed loudly only by luck: `grid` happens to be the first arm, so the `dca`
assertion failed and exposed it. **Had the arms been ordered differently the test
would have passed while checking almost nothing** — a guard reporting green over
a fault it never looked at. Fixed by preserving indentation while still dropping
comment lines, with the reason written into the file so the next person copying
this helper does not reintroduce it.

**The lesson, stated generally: a test that passes vacuously is worse than a test
that is obviously broken.** An obviously broken test gets fixed. A vacuous one
gets counted. This is the same finding [45.md](45.md) recorded when a mutant
deleted a guard's call site and survived, and the same reason every source-scan
guard in this repository opens with a "found the sources to check" assertion —
that assertion exists because this failure mode is the normal one, not the
exotic one.

**A related gap found while recovering from an interruption, and worth naming:**
`dashboard/tsconfig.app.json:39` excludes `src/**/*.test.ts` from the app build,
deliberately and with its own comment. The consequence is that **a dashboard test
file is typechecked by nothing.** A half-written test referencing a real export
with no import statement produced a clean `tsc -b` and four `ReferenceError`s at
run time. Not a bug, but a property to know: for dashboard test files the suite
is the only compiler.
