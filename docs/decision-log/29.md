### What `getCandles` actually was, read from source

21.4 says the extension is needed because "today it is reached through a bot's
attached client". Reading the code rather than the prose found something sharper.

`getCandles` is a **method on `RestExchangeClient`** (`shared/exchange-client.ts`),
so reaching it means holding a client, and every route to one ran through
something that already had a bot. But `grep -rn "\.getCandles("` over `src`,
`scripts` and `dashboard` returns **no production caller at all**: the
rate-limit decorator's pass-through, six tests, and `scripts/verify-gemini.ts`.
Not even the price feed, which the interface's own docblock names as its
consumer — decision-log 14.3 replaced the REST backfill with the WS replay batch
and the method has been reachable-but-unreached ever since.

So the spec's sentence describes the only **available** route, not an actual call
site. Worth recording because it changed the shape of the work: with no caller
depending on `ExchangeOutcome<Candle[]>`, extending the interface would have been
free of compatibility risk — and was still the wrong move, for the reason below.

### The interface was not changed. A wrapper was added.

`RestExchangeClient.getCandles` still returns `Promise<ExchangeOutcome<Candle[]>>`,
untouched. `fetchCandleWindow` is a new function that wraps it.

The alternative — widening the interface to carry depth metadata — would have
meant editing both clients, the rate-limit decorator and the fake to serve a
shape only one caller reads, and would have put policy (what counts as
truncation) inside the transport. The interface's documented contract is
deliberately narrow and honest already: `since` is "BEST-EFFORT, bounded by the
window the exchange's endpoint returns". Measuring how well that best effort did
is a caller's job.

**Before and after, stated plainly:**

| | shape |
| --- | --- |
| `getCandles` (unchanged) | `ExchangeOutcome<Candle[]>` |
| `fetchCandleWindow` (new) | `CandleWindow`, or throws `CandleWindowError` |

`CandleWindow` carries the candles **exactly as the client returned them** —
oldest-first, in-progress candle included, no filtering of its own — plus
`fetchedAt`, `requestedSince`, `earliestOpenTime`, `earliestCloseTime`,
`latestCloseTime`, `truncated` and `missingHistoryMs`. Everything after the
array describes it rather than altering it.

### Reuse, not a second path — in both directions

21.5's rule about risk checks ("a second implementation of a risk check drifts
from the first, and the copy that drifts is the one nobody is watching") applied
twice here, and both times the fix was to lift something out rather than write it
again.

**Client resolution.** `envSymbolLister` had performed two steps inline since
step 11: resolve the account's exchange, then ask the resolved factory for a
client. `clientForAccount` is those two steps named and moved to
`exchange-dispatch.ts` — whose own docblock had already anticipated this ("the
future bot-execution wiring reaches for the same function"). `envSymbolLister`,
`envCandleLister` and therefore the watchlist's tradability check now resolve a
client through one function.

**Tradability.** `assertTradable` moved to `tradability.ts` as `checkTradable`,
which **returns** a refusal instead of throwing one. Each caller keeps its own
error type — `WatchlistError` for a write that must not land, `CandleWindowError`
for a fetch that must not run — and both take the code and the message from the
shared function. Same codes, same order, same 400/503 mapping; the watchlist's
existing tests were the guard on the move.

One message string changed: the near-match tail now reads "the symbol must match
the exchange's own spelling exactly" rather than "the symbol is stored exactly as
the exchange reports it", because "stored" is false for a candle fetch. Recorded
because it is text the operator saw over the wire at step 28.

### Truncation is measured off the client's own contract

`getCandles` promises candles whose close time is **after** `since`. So the
oldest candle a fully-satisfied request can return is the one still open at that
instant — its open time is at or before `since`. An open time strictly **after**
`since` therefore means the venue's window began later than asked.

```
missingHistoryMs = requestedSince !== null && earliest.openTime > requestedSince
  ? earliest.openTime - requestedSince : null
truncated        = missingHistoryMs !== null
```

Derived from the returned data, not from the interval's length, so it holds for
every interval and for a venue that trims its window without announcing it.
`truncated` is **derived from** the shortfall rather than computed beside it, so
a `truncated: true` carrying a null shortfall — a report that looks honest and
says nothing — is unrepresentable.

With no `since`, `truncated` is false and `missingHistoryMs` is null. That is not
a claim the window is deep; there is simply no requested range to fall short of,
and `earliestCloseTime` is the field that answers depth in that case.

### Fail closed, five ways, and the empty array is one of them

| condition | code |
| --- | --- |
| interval declared but unverified on a venue | `interval_not_verified` |
| no such row in `accounts` | `unknown_account` |
| the venue does not list the pair | `pair_not_tradable` |
| the tradable set could not be READ | `tradable_set_unreadable` |
| the candle call failed | `candles_unavailable` |
| the call succeeded and returned nothing | `no_candles_returned` |

The last one is a judgement call and is recorded as such. A successful-but-empty
response is not a call failure, so treating it as one goes past the letter of the
requirement. It was chosen because an empty array is the exact shape a silent
failure takes here: it survives every type check, flows into an average or a
volatility figure as though it meant something, and reaches a human
indistinguishable from a coin that did not trade. 21.5 requirement 6 forbids
"fall back to fewer candles and not say so"; zero is fewer.

### Only `1m` is a verified interval, and now that is enforced

`CandleInterval` declares all seven timeframes both venues nominally support, and
its docblock has said since step 14 that only `1m` is exercised in v1 and each
wider interval "must be verified per exchange before first use". Nothing enforced
it. `VERIFIED_INTERVALS = ["1m"]` does, with a hard refusal.

**The reason it has to be hard here rather than a warning** is the failure mode.
Each venue spells the wider intervals differently — Gemini writes
`1hr`/`6hr`/`1day` — so a wrong mapping does **not** error. It returns
correctly-shaped candles of the **wrong duration**, which every type check
passes, which no downstream reader can detect, and which 21.4 Stage 2 would hand
to a model to reason about volatility from. A proposal derived from six-hour
candles believed to be one-hour candles is precisely 21.5 requirement 6's
"degraded proposal indistinguishable from a good one at a glance".

The gate runs **first**, before the registry read and before the tradability
call, because it needs no I/O to answer — the same "free checks first, exchange
call last" ordering `addToWatchlist` uses.

**Widening it is one line in `candles.ts` plus one line in `candles.test.ts`,**
and the second line is deliberate rather than an oversight. A test pinning
`VERIFIED_INTERVALS` to its current contents means widening cannot happen as a
silent one-character edit; it has to appear in a diff and earn a decision-log
line. Neither line is the hard part: an interval belongs on that list only once
somebody has read that venue's candles at that timeframe and confirmed the
duration is what it claims.

### The endpoint, and the status mapping it reuses

`GET /api/accounts/:label/candles?pair=&interval=&since=`. Read-only, behind
Access like every other route, 405 on any write method, no `audit_log` row
because there is nothing to record.

Thin in the strict sense step 28 established: the gate, the registry lookup, the
tradability check, the refusals and the truncation arithmetic all stay in the
module. What the layer adds is query parsing, port wiring, and serialization.

**The tradability port is `tradablePairsFor(ctx)` — the same one the watchlist
endpoints use.** Shared deliberately, so the candle gate and the symbol dropdown
an operator reads cannot disagree about what the venue lists, and so a fetch
spends no extra full-catalogue request. A test asserts two candle requests cost
**one** venue call, which is what proves it goes through `listAccountSymbols`
rather than around it.

**`candleLister` is a new injected port**, mirroring `symbolLister` and defaulting
to `envCandleLister`. Kept separate from `symbolLister` because the two ask the
venue different questions and only one is cached — a candle's entire value is
that it is current, and 21.5 requirement 4 times a proposal from when its data
was fetched. A cache here would make that timestamp a lie that looks like the
truth.

**Money must be serialized.** `Candle` carries five bigints per row and a window
is hundreds of rows; `JSON.stringify` throws on a bigint outright, so a missed
conversion here is a 500, not a wrong number. `candleView` renders all five as
exact decimal strings. `closed` is carried through rather than filtered on —
dropping the in-progress candle would silently shorten every window by one and
take the choice from the consumer.

**Statuses reuse existing tiers rather than inventing per-endpoint ones:**

| code | status | why that one |
| --- | --- | --- |
| `interval_not_verified` | 400 | a bad field value the caller fixes by asking differently, like `pair_not_tradable` and `invalid_parameter` |
| `unknown_account` | 404 | the thing named is not there, like `unknown_bot_instance` and `not_watched` |
| `candles_unavailable` | 502 | a read the caller asked for that the venue failed to serve — the symbols endpoint's `exchange_unavailable` tier |
| `no_candles_returned` | 502 | the venue answered and the answer was unusable, which is what a bad gateway IS. **Not 404**: tradability passed first, so the pair is listed and this is not a missing resource |
| `tradable_set_unreadable` | 503 | unchanged, and deliberately a **different** status from the two above: this is a refusal to act on unverifiable input, not a relayed read failure |

**`unknown_account: 404` is the load-bearing row.** The same code is thrown
elsewhere in this surface as a `notFound(...)` `ApiError`, which carries its own
status and never consults the table. `fetchCandleWindow` throws it as a *module*
error, so without that row it would take the table's 400 default — the same
missing account answering 404 on `/symbols` and 400 on `/candles`. A mutant
deleting it is in the harness.

The layer's own parse refusals reuse existing codes too: `missing_field` (no
`pair`, no `interval`), `invalid_filter` (a string that is not an interval at
all), `invalid_field` (a bad `since`). `1w` and `6h` are refused by **different
tiers on purpose**: one answers "is that an interval at all", which the HTTP
layer must decide to produce a typed value, and the other answers "has it been
verified", which is policy the module owns and re-checks for every caller.

### The window does not slide, and 21.7 open question 1 is NOT settled

The first run's 20,000 ms shortfall on a 24-hour request looked wrong against a
9.78-hour window, so the operator ran a **second, targeted verification** —
three calls (unbounded, `since=48h`, `since=72h`) asking one question: is the
reported boundary a genuine sliding time window, or something else?

**Verified, operator-run, 2026-08-08. This session made no live calls.**

| observation | result |
| --- | --- |
| `earliestOpenTime` across `since=24h`, `48h`, `72h` | **identical**: `1786156920000` in all three |
| `count` across all three | **identical**: 558, regardless of `since` |
| `missingHistoryMs` across all three | 20,000 / 86,429,000 / 172,828,000 ms — scaling **linearly and correctly** with the requested `since` |
| `latestCloseTime` between two runs ~28 minutes apart | **identical** |
| `count` between those same two runs | **dropped, 587 → 558** |

**The arithmetic is correct and the boundary does not move.** Those three
`missingHistoryMs` values imply `since` values 86,409,000 and 86,399,000 ms
apart — 24 hours each, to within the seconds that elapsed between the three
`curl` invocations. The shortfall is computed exactly right. It is computed
against a boundary that is the same value no matter what is asked of it.

**The apparent depth is shrinking, not holding.** 587 one-minute candles is
exactly 35,220,000 ms, which matches the reported `spanHours: 9.783333…` to its
last digit — so the series is contiguous and the count *is* the span. 558
candles is 9.30 hours. With `latestCloseTime` identical between the two runs,
the **oldest** bound advanced exactly 29 minutes across ~28 minutes of real
time while the **newest** bound did not move at all.

**So 9.78 hours is not a measurement of anything.** It is the size of a gap
between a newest bound that is frozen and an oldest bound that is not, read at
one instant while that gap was closing at roughly one candle per minute. Half an
hour later the same call reported 9.30. A figure that decays with wall-clock
time is not a window depth, and nothing may treat it as one.

**This is more consistent with Gemini's testnet sandbox serving a fixed,
non-advancing block of historical candles** than with a live venue window: the
"now" end appears frozen, or advancing far slower than real time, and the depth
figure is an artifact of that rather than a property of Gemini's windowing.

**21.7's open question 1 is therefore NOT settled**, and this data cannot settle
it. What the endpoint proved is that it can ask the question and report the
answer honestly; the answer it got back was about a sandbox, not about Gemini.

### The count drift, recorded as an observation and not as a mechanism

`count` fell 587 → 558 across ~28 minutes while the newest bound stayed fixed.
Twenty-nine candles, twenty-eight minutes, one-minute candles: the oldest bound
advanced almost exactly with real time while the newest did not advance at all.

**That is the observation, and the observation is where this stops.** Whether
the cause is paused sandbox data generation, a floor pinned to real time over a
frozen data set, a testnet quirk, or something else entirely is **not
determinable from outside Gemini's infrastructure**, and guessing at a mechanism
here would put a plausible story into this log where a measurement belongs. The
numbers are recorded so the next run can compare against them; the explanation
is not recorded, because there is not one to record.

### The question this replaces it with, and why it is not cheap to answer

The specific open question is now: **is this fixed / non-advancing window a
sandbox artifact, or does Gemini's production API behave the same way?**

It matters directly. If production slides properly, 21.7's depth limit is real
but unmeasured and the sandbox simply cannot be used to measure it. If
production behaves like this too, then the depth limit is a different shape of
problem than 21.7 describes, and every downstream assumption about "a fixed
recent window" needs re-reading.

**Answering it requires reading candles from production Gemini, and this project
has deliberately never done that casually.** The obstacle is not the call
itself — `/v2/candles` is unsigned public data. It is that reaching it through
this system means `clientForAccount` resolving a **production** client, which
means production `GEMINI_API_KEY`/`GEMINI_API_SECRET` present in an environment
a verification run is pointed at. That is the same posture section 16 and step
3.4 established and the reason `resolveDefaultExchange` derives its base URL
from `ENVIRONMENT` alone so the two are "impossible to get backwards". Real
funds are eventually involved on that side, and a read-only errand is not a
reason to relax it. **Deferred, deliberately, with the cost of answering stated
rather than the answer assumed.**

### The first verification attempt 404'd, and it was not the code

Worth recording, and distinct from step 28's near-identical-looking lesson.

**Every request returned `no API route`.** The branch was written, committed and
green, and had not been deployed. Nothing was wrong with the endpoint; there was
no endpoint running.

Step 28's failed first attempt was the mirror image — a 302 to an Access login
page because `cloudflared` was not installed and not logged in. That was a
precondition of the **client**. This is a precondition of the **server**, and the
two fail in ways that look nothing alike and nothing like each other.

The process lesson is on the verification commands, again. This step's handover
did include preconditions — `cloudflared` present, a token minted, `/health`
answering unauthenticated — and every one of them **passed**, because `/health`
was answering perfectly well from the previously deployed build. `/health`
returns `{ status, version, environment }` precisely so that "a deployed version
must always be confirmable against what is actually running" (section 16), and
the check that would have caught this in one line is comparing that `version`
against the build under test. Asserting the host is reachable is not the same as
asserting the code is there. Nothing was built for that here either.

### Deliberately not done, and open questions

- **`envCandleLister`'s actual `getCandles` call is exercised by nothing in the
  suite.** Its tests build a real client from synthetic credentials and assert
  the resolution; none calls `getCandles` through it, because that needs a
  network. The live run above is the **first and only** time that path has
  executed, which makes the endpoint's real value partly that it is the only
  coverage that path has.
- **The wider intervals — `5m`, `15m`, `30m`, `1h`, `6h`, `1d` — remain
  unverified against any real venue**, on Gemini or Binance. That is the state
  the gate now enforces rather than merely describes. `1m` is verified on **real
  Gemini** as of this run; it is still unverified on Binance.
- **Gemini's real candle depth is unknown, and 21.7's open question 1 is
  open.** The testnet sandbox returns what looks like a frozen block rather than
  a sliding window (above), so no depth figure has been measured — the 9.78-hour
  reading was 9.30 half an hour later. Nothing downstream may assume a window
  depth; it must read `earliestCloseTime` from the response.
- **Whether that behaviour is sandbox-only is the new open question**, and
  answering it needs production Gemini credentials in a pointed environment,
  which is deferred deliberately (above).
- **No dashboard control**, for the candle window or the watchlist. Both have a
  curl-able endpoint; a UI is its own step, deferred again on purpose.
- **No candidate selection, no trending pull, no news or sentiment fetch, no
  Workers AI call, no proposal record.** All of section 21 beyond this function
  and the watchlist remains unbuilt, and 21.7's other four open questions are
  untouched.
- **`readWatchlist` still has no non-test caller.** `fetchCandleWindow`'s only
  caller is its endpoint. Both are the seams the pipeline will consume; that is
  the intended state.
- **Deep history is still not obtainable.** Extending the reach to arbitrary
  pairs removed a *scoping* limit; the *depth* limit is untouched and was not
  worked around — no second data source, no stitched history, no retry at a wider
  interval hoping for more. Whether an R2 cache (section 8.4) or a second source
  is the answer stays 21.7's unsettled question, and it is now known that the
  testnet sandbox cannot supply the number.
- **Not deployed by this session.** The operator deployed testnet to run the
  verification above; production is untouched.
