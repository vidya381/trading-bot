# 77 — Split-brain `resume()`: the write order, the detector that found a flaw in its own design, and the emergency stops that stopped trusting the mirror

**NOT COMMITTED.** Thirteen files on disk (nine modified, four new, plus this
entry and its README row); `HEAD` is still **`b727dad`** ("Make reconciliation's
terminated-order tolerance venue-independent").

**Three pieces, one fix.** 3a reorders `resume()`'s two status writes. 3b adds
the detector that finds and repairs the mismatch. 3c stops both emergency stops
from depending on the mirror being right. They were built in that order, in one
session, each with its own tests and mutants.

**The split held.** No `wrangler`, no deploy, no HTTP call, no query against real
D1, no browser, and **nothing whatsoever done to `bot-gvtr1a` or any other live
bot** at any point. Every figure below was measured in this session. Every live
fact was supplied by the operator from their own reads and is labelled as such.

---

## PART 0 — THE LIVE EVIDENCE THIS STARTED FROM

Read by the operator, not by the session:

- `bot_instances.status = 'halted'` in D1 for **`bot-gvtr1a`**, a real testnet bot.
- `GET /api/bots/bot-gvtr1a` returned `state.status = "running"`,
  `state.haltReason = null`, `state.haltedAt = null`, and a **current**
  `state.lastPriceAt` — subscribed to its price feed and receiving live prices.
- **Zero orders with `created_at > halted_at`.** It had traded nothing since the
  mismatch began. It was inert only because its ladder was never rebuilt (all
  eight slots null) — **not because any safeguard stopped it.**

**WHY THIS MATTERS BEYOND ONE BOT, and it is the whole reason all three pieces
exist.** Both emergency stops chose their targets by reading D1:

- global kill switch — `kill-switch.ts:70`, `:171` — `status IN ('created','running')`
- account circuit breaker — `circuit-breaker.ts:95`, `:196` — the same set

`halted` was the one non-terminal status neither sweep selected. So a bot in
exactly this state was **live and invisible to both mechanisms that exist to stop
it** — the global kill switch and its account's circuit breaker — at the one
moment that invisibility costs something.

## PART 1 — ROOT CAUSE

`#resumePass` (`bot-instance.ts:3191`) wrote:

| # | Write | Store |
| --- | --- | --- |
| 1 | `#subscribeToFeed` — fail-closed, before any status write | PriceFeed DO |
| 2 | `#mutateState → status: "running"` | **Object storage** |
| 3 | `#mirrorStatus(config, "running", …)` | **D1** |
| 4 | `resolveHaltAlerts` | D1 |
| 5 | `#audit("bot.resumed", …)` | D1 |

**No transactional guarantee is possible between steps 2 and 3, and none was
missing by oversight.** Durable Object storage and D1 are separate platforms with
no cross-store transaction. `#mutateState` is durable the moment it returns.
`#outsidePoll` is a bare in-flight counter — no `try/catch`, no compensating
write. An interruption there (a D1 hiccup, an eviction, a deploy landing
mid-call) is **permanent by construction**. `bot-gvtr1a`'s missing `bot.resumed`
audit row — written at step 5, after the failed step 3 — is precisely the
signature that predicts.

**WHY `resume` SPECIFICALLY.** The two neighbouring transitions were already safe,
and only by luck of which statuses the sweeps happen to select:

| Transition | Interrupted state | Swept? |
| --- | --- | --- |
| `start` | object `running` / D1 `created` | **Yes** — `created` is in the set |
| `#halt` | object `halted` / D1 `running` | **Yes** — `running` is in the set |
| `resume` | object `running` / D1 `halted` | **NO** |

`resume` was the only transition in the system able to aim its failure at the one
status nothing looked at.

**And nothing repaired it.** `mirrorFindings` (`reconcile.ts:653`) compared this
system's two stores **order by order** and had never compared the bot's own
status. A grep of `state.status` across all non-test source returned 29 hits,
**every one inside `bot-instance.ts` reading its own state**:
`snapshot.state.status` was read by nothing outside the Durable Object at all.
Reconciliation held both values in hand on every pass and compared neither.

## PART 2 — 3a: THE REORDER

**The change.** `#mirrorStatus` (D1) now runs BEFORE `#mutateState` (object).
`#subscribeToFeed` stays first, fail-closed. `resolveHaltAlerts` and the
`bot.resumed` audit row stay **last**, after both status writes — unmoved and
pinned by a test.

**Why this direction.** An interruption now leaves object `halted` / D1
`running`. Both sweeps still see it; halting it is a no-op because it already is;
and — the part that actually matters — **nothing anywhere starts trading because
D1 says so.** `#onPriceUpdatePass` reads the object's own state and returns
`ignored` before reaching any order-placing site, and no code outside the object
reads `snapshot.state.status`. A stale `running` row can mislead a human; it
cannot place an order. That property is asserted **behaviourally** rather than by
reading a field back.

**Why steps 4–5 stay last.** An interrupted resume now leaves a `running` row
beside an unresolved critical halt alert and no `bot.resumed` entry — **a visible
contradiction rather than a silent one.**

**WHAT 3a DOES NOT DO, stated plainly rather than left to be inferred:**

- It does **not** stop mismatches happening. It only chooses which way the
  wreckage points.
- It does **not** self-heal `bot-gvtr1a`, or any bot already in the bad state.
- It relies on a relationship **nothing enforces structurally** — that `halted`
  is the excluded status and that `start`/`#halt` happen to fail safe. The two
  lines look interchangeable; a reasonable person tidying up would swap them
  back. The ordering pin is what makes it an invariant instead of a coincidence,
  and 3b is what makes the property checked rather than assumed.

**3b was therefore necessary, not optional.**

## PART 3 — 3b: THE DETECTOR, AND THE FLAW BUILDING IT EXPOSED

**The mechanism.** `botStatusFindings` in `reconcile.ts` compares
`bot_instances.status` against the object's own `snapshot.state.status`, for
every bot the run already fetched, reading the snapshot the order pass had
already loaded — so the comparison costs **no extra cross-object RPC** on the
ordinary run where the two agree.

`RECONCILED_STATUSES` is `created` / `running` / `halted`. **`stopped` is
excluded**, and was already excluded before this work: its capital is released
and it holds no position, so there is nothing of its to compare. (The brief for
this step named `stopped` as part of the set. It is not, and a test now pins that
so the misconception cannot recur.)

### THE FLAW, AND IT WAS FOUND BY BUILDING, NOT BY RE-READING

**The design that went into this session had the safe polarity — object `halted`,
D1 `running` — auto-correcting on FIRST sighting, with no delay,** on the
reasoning that it is only a stale mirror and `mirror_drift` corrects those
immediately.

**That was unsafe, and 3a is what made it unsafe.** With D1 written first, a
perfectly healthy human resume — caught in the brief window between its two
writes — presents as **exactly** that polarity: the row already says `running`,
the object still says `halted`. Correcting the row "back" to `halted` there would
**silently overwrite a real human resume**, and the object finishing its own
write moments later would leave `running` / `halted`:

**the detector would have MANUFACTURED the split-brain state it exists to
prevent, out of a healthy transition.**

This was discovered by attempting to build the design as written, not by
re-reading it. As shipped, **neither direction acts on a first sighting.** Both
require the same disagreement, in the same direction, on a later run.

### The three finding kinds — three, not the one originally planned

| Kind | Floor / ceiling | Purpose |
| --- | --- | --- |
| `bot_status_unconfirmed` | minor / **minor, pinned** | First sighting, either direction. Logged into the run's findings, which is also the memory the next run reads. No alert, no halt, no correction. |
| `bot_status_drift` | meaningful / meaningful | The dangerous polarity, confirmed: the object believes it is `running` while D1 says otherwise. Alerts and halts that bot through the existing `haltBot` port. |
| `bot_status_mirror_stale` | minor / **minor, pinned** | The safe polarity, confirmed: D1 corrected **from** the object, per section 8.1. The object is never touched. |

**Why `bot_status_mirror_stale`'s ceiling is pinned at minor, and the pin is
load-bearing rather than modest:** this kind's tier action is a **write to D1**,
and a kind whose action is a write must never be promotable into a tier whose
action is a **halt**. It carries no magnitude today; the pin makes that a
property of the kind rather than of the one call site that happens not to attach
one. `bot_status_unconfirmed`'s pin follows `order_drift_unconfirmed`'s reasoning
verbatim: the kind means "not yet confirmed", so letting magnitude promote it
would act on exactly the evidence the kind exists to call insufficient.

### `statusPair`, and why direction is in the memory key

A new structural field on `Finding`, recorded as `status_pair` in the run's audit
row, carrying `"<d1>/<object>"`. The memory key is `${botId}::${statusPair}`, not
`${botId}`.

**Direction is part of the identity, not decoration.** A bot seen `halted/running`
and then `running/halted` has **flapped**, not persisted — escalating that would
be confirming one condition with evidence of a different one. Carried
structurally rather than left inside `detail` for the reason `clientOrderId`
already states verbatim: matching a safety decision by searching prose is the
trap entry 58 recorded and refused.

### The memory reader, generalised rather than duplicated

`unconfirmedDriftFromRecentRuns` read exactly one kind and required a
`client_order_id`. It now scans once and fills a per-kind table,
`CONFIRMABLE_KINDS`, which is the single place naming which kinds confirm across
runs and how each says "the same condition". Two readers would have meant two
audit-log scans per run for one question, two places to keep the recorded-finding
shape in step with, and the standing risk of a later fix to the window or the row
cap landing on only one of them.

### THE SECOND SELF-CAUGHT GAP: a stated safeguard was shipping untested

The design named three safeguards. The third — **"re-read the D1 row immediately
before acting"** — was implemented, and **no test exercised it.** The mutant that
removed it **SURVIVED on the first mutation run**: 136 of 136 reconciliation tests
passed with the safeguard deleted.

The reason it survived is worth recording, because it is the shape of a whole
class of false confidence: the false-positive test in place at that moment had the
transition completing **between** two runs, so the confirming run's own top-of-run
reads already agreed and the re-read was never reached. The safeguard only matters
when the transition completes **during** the confirming run — after the rows were
read, after the first snapshot, before the finding is acted on.

**Fixed by strengthening the test, not by weakening the mutant.** A second half
was added to the false-positive guard driving a port that reports `halted` on its
first call and `running` on every call after, asserting both that the confirm path
asked a second time and that it dropped the finding. The mutant is now caught.

**Mutation testing did not confirm the work here. It found a real gap in it.**

## PART 4 — 3c: THE EMERGENCY STOPS STOP TRUSTING THE MIRROR

**The operator's own framing, and it is the right one: this is not a fix for the
found cause. It is insurance against causes not yet found.** 3a fixed the known
cause; 3b detects the condition. 3c makes both emergency stops catch a bot that
is internally live but marked `halted` **regardless of why it got that way, and
without waiting for a detector pass to have run first.** In the operator's words:
*"if somehow the status didn't update like running to halt but it shows halt, then
that would be secretly trading."*

### Two findings that changed the build from what was briefed

**1. A single widened status set would have defeated an existing guard.**
`reconcile.ts:1945` re-sweeps an already-latched account only when
`activeBotsOnAccount` finds something, and that guard's own comment says it exists
*"so a quiet latched account does not write an audit row every five minutes"*.
Tripping the breaker halts every bot on the account — so a latched account always
has halted bots. Widening the shared constant would have made that guard
**permanently true on every latched account, forever**, and
`tripAccountCircuitBreaker` writes its audit row **unconditionally** (only the
alert is `newlyTripped`-gated). The result would have been a
`circuit_breaker.swept` row every five minutes, forever, on every account that had
ever tripped — exactly what the guard exists to prevent.

Found by tracing that guard's own comment before building. **Two constants were
used instead:** `ACTIVE_STATUSES` (narrow, unchanged, keeping the guard and the
dashboard's "this will halt N bots" preview) and a new `SWEPT_STATUSES` used only
by the sweeps themselves.

**2. `HaltBotPort` discarded the answer.** It was
`(botInstanceId, detail) => Promise<void>`, so it threw away `halt()`'s own
`already_halted` vs `halted` result — **the sweep could not have reported the
distinction even if asked to.** Fixed by threading the real outcome through
(`HaltBotOutcome`, with `void` still accepted so an indifferent test double stays
valid and is counted as a halt — today's meaning).

The result is split in two, and the split is the point:

- **`haltedBotIds` — MEANING UNCHANGED.** What this call actually stopped. This is
  the number a human reads in an emergency to answer "how much was still
  running", and quietly folding already-stopped bots into it would inflate exactly
  that. **41 existing assertions on this field across the suite now serve as the
  proof it did not change** — and `circuit-breaker.test.ts`'s
  `expect(second.haltedBotIds).toEqual(["dca-eth-1"])` passes **unchanged** through
  the whole of 3c.
- **`alreadyHaltedBotIds` — new.** Bots the sweep visited and found already
  halted. Reported rather than merged, because it is the only evidence the
  insurance pass actually covered them.

### Scope, with its real reasoning

- **`halted` IS swept.** The actual goal.
- **`stopped` is NEVER swept, and this was a correctness fact, not a judgment
  call.** `BotInstance.#halt` **THROWS** on a stopped bot (*"a stopped bot cannot
  be halted; its capital is released"*). Sweeping one would not be a harmless
  no-op — it would land in `failures` and produce a false **"FAILED to halt N"**
  on the critical alert of **every single pull**.
- **`archived` is NOT filtered on at all, in either direction.** It is orthogonal
  to `status` by explicit design, and an archived-but-halted bot's object can be
  secretly live exactly like any other. Exempting it would quietly turn "hidden
  from the dashboard's default view" into "exempt from the kill switch".
  **Pinned by its own test specifically to prevent that drift.**

### Found beyond the brief: `emergencySweepOrder`

The sweep is a **sequential** loop of awaited cross-object RPCs, and the query
carries **no `ORDER BY`** — so row order is unspecified. Adding halted bots could
put them ahead of a genuinely live one and **delay when that bot actually stops,
during a real emergency**. `emergencySweepOrder` puts everything D1 believes is
live at the front. Its test inserts the halted bots first, so the raw query order
would fail it.

### Checked against 3b — four cases traced

| Case | Result |
| --- | --- |
| Sweep visits a genuinely halted bot | `already_halted`, **zero writes** — nothing for 3b to see |
| Sweep visits a secretly-running bot | Full `#halt` converges both stores; 3b's re-read finds agreement and **drops its now-stale finding** rather than acting |
| Sweep's `#halt` interrupted mid-way | Leaves object `halted` / D1 `running` — the safe polarity, which 3b corrects |
| 3b's own halts | Use the same `haltBot` port; unchanged |

**They cover complementary cases, not overlapping ones.** 3c covers **every manual
pull and every genuine trip**. 3b covers the **quiet latched-account case 3c's
guard deliberately leaves alone** — the one place the re-sweep does not fire.

## PART 5 — VERIFICATION

### 3a — `resume-write-order.test.ts`, a new file so `bot-instance.test.ts` is untouched

1. `fails closed when the D1 write fails: the object stays halted and nothing is claimed` — object stays `halted` with its reason intact, **both stores still agree**, halt alert still open, no `bot.resumed` row.
2. `leaves the safe direction when the object write fails: D1 running, object halted, and it trades nothing` — the aimed failure mode, with the safety claim asserted **behaviourally** (a real price update produces no order), plus a **non-vacuousness control** proving the same fixture DOES place an order once the object really is running.
3. `pins the D1 write before the object write` — **THE ORDERING PIN.** A recording `Database` double and a `storage.put` hook capture the sequence, and independently capture what the object's storage said at the instant of the D1 write.
4. `resolves the halt alert and audits only after both status writes` — the full observed sequence `d1:running → object:running → alert:resolved → audit:resumed`.

**17 existing resume tests pass unchanged**, in a file this session never edited.

**1 mutant — `writes swapped back to object-first`: CAUGHT, all 4 failing.** Test 3
failed with `expected [ 'object:running', 'd1:running' ] to deeply equal
[ 'd1:running', 'object:running' ]`; test 1 failed with `expected 'running' to be
'halted'` — **`bot-gvtr1a`'s condition reproduced in a unit test.**

### 3b — `bot-status-drift.test.ts`, 11 tests across the 7 specified categories

| Category | Tests |
| --- | --- |
| 1 · raised / inverse / never when agreeing | `is raised on object-running / D1-halted, on the inverse, and never when they agree` · `never examines a stopped bot at all` |

| 3 · second sighting confirms | `second sighting confirms: haltBot called exactly once, alert raised` |

| 5 · correction direction | `writes D1 from the snapshot and never resumes the object` · `gives reconciliation no way to resume a bot at all` (**structural-absence half** — a source scan in `no-raw-d1.test.ts`'s shape, because the property is an absence and no behavioural test can pin one; vacuity-checked by adding a `resumeBot` port and watching it fail) |

## PART 6 — WHAT HAPPENS TO `bot-gvtr1a`

**NOT repaired by this session. Deliberately untouched throughout.**

Expected self-correction once deployed — three paths, none observed:

1. **Via 3b**, automatically, within roughly two reconciliation cycles (~10
   minutes at the `*/5` cron): pass one records `bot_status_unconfirmed`, pass two
   confirms and halts the object through `haltBot`, converging both stores.
2. **Via 3c**, immediately, the next time the kill switch or the account's circuit
   breaker is pulled — it is now in the swept set.
3. **On its own**, if price crosses its stop-loss or breakout level first:
   `gridDecide` evaluates both from `ladder.levels` before any slot is consulted,
   so `#gridExit → #halt` would fire and converge the stores — taking the evidence
   with it.

**Two live warnings, still true until deployment:**

- **Do NOT archive this bot.** Archive is *permitted* today because D1 says
  `halted`, and `archiveBot` then calls `close()` on an object that believes it is
  running — releasing capital under a bot that thinks it is live. It is the one
  operator action currently available that would do real damage in this state.
- **Do NOT click Resume.** It would throw `invalid_status` ("only a halted bot can
  be resumed; this one is `running`") — harmless in itself, but an action against
  known-bad live state.

## PART 7 — VISIBLE BUT UNUSED

`alreadyHaltedBotIds` is returned by the API and **displayed nowhere**. That is
deliberate: `KillSwitchTrigger.tsx` sits beside the kill-switch banner on the
operator's do-not-touch list, and the display stays honest without it precisely
because `haltedBotIds` kept its meaning. Surfacing it would be **more
informative, not more correct** — a real optional future step, not a defect.
