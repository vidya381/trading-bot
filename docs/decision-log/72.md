## PART 1 — THE DISTINCTION THAT MAKES THIS SAFE: RECEIPT VS CONDITION

This is the entry's central idea, and everything else follows from it.

`alerts.resolved` answers one question: **is this still going on?**

- A **CONDITION** alert describes something that **might still be true**.
  `order_state_drift` and `cancel_fill_discrepancy` say base really moved and was
  really never attributed. Resolving one **asserts that a discrepancy went away**
  — and if nothing actually resolved it, that assertion is false. Entry 65 spent
  its safety argument on exactly this, and refused to widen its scope because of
  it.
- A **RECEIPT** alert describes something that was **already fully complete the
  instant it fired**. A cycle closed. A liquidation filled. A repair committed. A
  click landed and found nothing to sell. **There is nothing left that could
  later make it "still true" or "true again."**

So for a receipt, `resolved: true` at the moment of insertion is **the honest
value, not a workaround**. The row was never an open incident; recording it as
one was the error. Every receipt sat `resolved: false` forever — nothing closes
them, because there is nothing to close — inflating the single number an operator
reads to decide what needs attention, while describing things that had already
finished.

**And it is not a suppression**, which was checked against all three consumers
rather than assumed: the notification dispatcher selects on
`notified_at IS NULL` and never reads `resolved`, so the outbound ping is
unaffected; `GET /api/alerts` applies no default `resolved` filter, so the row is
still listed; `driftAlerts.ts` and `pollAlerts.ts` gate on their own type sets,
neither of which contains any of these. What changes is `statusCounts.ts`'s
unresolved COUNT, which is exactly the number that was wrong.

  folding in by resemblance, and "it looks like the others" is not an argument
  about what it means.

Fixing only `liquidation_noop` would have been the partial fix; sweeping in all
six by resemblance would have been the careless one.

## PART 3 — THE `circuit_breaker_reset` ROW, PROVEN A MANUAL ARTIFACT

The single `circuit_breaker_reset` row carried `source: "wrangler-d1"`. That was
**proven** to be impossible from real system behaviour, not assumed:

1. **`circuit_breaker_reset` has exactly one writer** in the whole codebase,
   `src/reconciliation/circuit-breaker.ts`.
2. That writer **hardcodes `source: "dashboard"` as a string literal, not a
   parameter** — there is no code path that could vary it.
3. **`"wrangler-d1"` appears nowhere in `src/` or `dashboard/src/`.**
4. The complete set of alert `source` values any code can write is
   `"bot-instance"`, `"dashboard"`, `"price-feed"`, `"reconciliation"`,
   `"human"`. `"wrangler-d1"` is not among them.

That row was inserted directly through `wrangler d1 execute`, almost certainly
during earlier manual testing. **It was excluded from the backfill entirely — on
two independent grounds:** its type is out of scope (Part 2), and it did not come
from real system behaviour at all. Silently resolving a row that no code path
produced would be the backfill claiming to have tidied up after a system that
never made the mess.

## PART 4 — THE FORWARD FIX, AND A GAP IN ITS OWN BUILD BRIEF

`#alert` gained an optional `resolved?: boolean` **defaulting to `false`**, so
every existing caller is unchanged and an alert remains an open condition unless
it explicitly says otherwise. The four receipt sites opt in.

**The build brief for the backfill assumed a canonical list of receipt types
already existed to reuse. It did not.** The forward-fix session marked four call
sites `resolved: true` **individually**, with nothing tying them together as a
maintained list — which is the right place to make the decision, and leaves no
enumeration behind.

So one was built: **`RECEIPT_ALERT_TYPES` and `isReceiptAlertType` in
`src/shared/alert-types.ts`**, beside the project's existing precedent for
exactly this kind of cross-cutting list — `ORDER_STATE_DRIFT_ALERT_TYPES` and
`POLL_HEALTH_ALERT_TYPES`, both of which live there for the same reason.

**Why a single source of truth matters here specifically:** the backfill finds
old rows *by the list*, while the forward fix marks new ones *at four scattered
literals*. Nothing structural connects them, so without one definition they could
drift apart silently — a type added to the list but never marked would make the
backfill claim to handle something it does not, and a type marked but never
listed would leave its old rows permanently missed. **A pin test closes that**:
it drives all four types through their real code paths and asserts every member
is both reachable and raised resolved, so either kind of drift fails the suite.

## PART 5 — THE DELIBERATE DESIGN DIFFERENCE FROM ENTRY 65's BACKFILL

Entry 65's halt-alert backfill **joins to `bot_instances` and requires
`status = 'stopped'`** before touching anything. That is correct there: a
`halt_*` row is only stale once the bot is terminal, because a halted bot's halt
alert is **current**, and `resume()` legitimately owns closing it.

**This backfill does not join to bot status at all**, and that is deliberate
rather than an omission.

A receipt describes something **already complete regardless of the bot's current
state**. Several of these types fire on bots that are still running perfectly
normally — `take_profit` is raised on every completed cycle, and with
`autoRestart` on the bot carries straight into the next one. **Requiring
`status = 'stopped'` here would have silently excluded real, legitimate rows for
no safety benefit whatsoever** — the very bots most likely to have accumulated
`take_profit` receipts are the ones still trading.

The two backfills therefore look similar and are scoped on different axes: entry
65's on **bot state**, this one on **what the alert IS**.

### A self-caught test bug, recorded rather than smoothed over

The pin test's first version tried to trigger `position_repaired` on a bot with
nothing to repair. `repairPosition` correctly returned `no_change`, no alert was
raised, and the test failed with *"position_repaired was never raised"*.

to catch, caught against my own setup. **Fixed by building a genuine two-phase
scenario** (full cycle → resume → partial exit → halt → repair) so the repair has
real work to commit, **not by weakening the check** to tolerate a missing row.
