## PART 1 — WHAT WAS BUILT

All ten methods of `RestExchangeClient`, **confirmed against
`/src/shared/exchange-client.ts` itself before a line was written** rather than
against a remembered list — the interface's own docblocks carry constraints that
the method names do not (`cancelOrder` returns the cancelled order and why;
`getCandles` returns oldest-first with `since` best-effort; `OrderStatus.fills`
is optional and its absence is meaningful).

**Structurally it follows `gemini/client.ts`, and that remains a finding rather
than a preference.** Entry 90's 2.1 table established the three properties that
decide it, and all three held through the build: Kraken authenticates with a
monotonic nonce (so section 4.2's `ClockOffset`/clock-sync machinery has no
role, exactly as on Gemini and unlike Binance), every private call is a POST, and
there is no signed query string anywhere. The transport skeleton — `#request` →
`#transport` → parse → `#unreadable` — is Gemini's shape.

**Where Gemini is the wrong template, the file says so at the method.** Four
places:

- **`getServerTime` returns a real value.** `GeminiClient` refuses honestly
  because Gemini publishes no such endpoint; Kraken publishes `/0/public/Time`
  (live again this session: `{"error":[],"result":{"unixtime":1788415303,…}}`),
  so copying the refusal would have been copying the code rather than the
  reason.
- **The error array is read before the HTTP status**, inverting Gemini's order.
  Entry 90 PROBLEM 3: Kraken answers 200 to a bad key, an unknown pair and a
  throttle alike, so the status carries nothing. `classifyStatus` is reached
  only when the body is **not a Kraken envelope at all** — an edge or proxy
  failure that never reached Kraken's application layer, which is the one case
  where a status genuinely means what it says.
- **A catalogue fetch sits behind almost every method**, which neither existing
  venue needs. `AssetPairs` and `Assets` are fetched concurrently and cached for
  an hour; `fetchedAt` is stamped with the **older** of the two receipt times,
  because the catalogue is exactly as fresh as its staler half and
  `SymbolFilters.fetchedAt` is read straight off it.
- **There is deliberately no `SymbolFilterCache`.** Gemini needs one because it
  fetches filters per symbol from a separate endpoint. On Kraken filters are
  *derived* from the catalogue entry (`parsePairFilters` reads `pair.raw`), so a
  second cache would give one document two staleness clocks and the newer of
  them would let an hour-old catalogue present itself as fresh trading rules.

**Nothing from the other four files was reimplemented.** `signing.ts` builds and
signs every private body and owns the nonce; the client POSTs the exact bytes
`signedRequest` returned and never rebuilds them. `catalogue.ts` answers every
name question — **there is no `toGeminiSymbol` analogue in this file and there
must not be one** (entry 90 PROBLEM 1). `filters.ts` supplies the filters and the
shared `validateOrder`. `parse.ts` reads every payload and classifies every error
string.

One ordering detail inside `placeOrder` is load-bearing rather than tidy: **the
pair is resolved through the catalogue before the order is validated.**
`validateOrder` *throws* when `filters.pair !== input.pair`, and Kraken's filters
are keyed by this system's ticker (`BTCUSD`). A caller passing `XBTUSD` or
`XXBTZUSD` — both names Kraken itself uses — would have tripped that throw
instead of placing an order. Resolving first makes all four of Kraken's names
mean the market they name.

## PART 2 — ⚠ THE ENDPOINT CORRECTION: `QueryOrders` CANNOT SERVE THE READ DECISION 2 SPECIFIED

**This is the most important finding in this entry, and it is in the single most
safety-critical path the client has.**

### What entry 90 specified

[90.md](90.md) PROBLEM 4 identified the sharpest conflict in the whole Kraken
integration: `cancelOrder` returns the cancelled order precisely so a halt does
not need a follow-up read, and Kraken's `CancelOrder` answers `{count, pending}`
and **nothing else** — no filled quantity, no state, no order id. DECISION 2
resolved it in as many words:

> `cancelOrder` issues `CancelOrder`, then a single **`QueryOrders`** read, and
> reports the order's state honestly as of that read.

### What the venue's own schema says

Verified during this build against **Kraken's published OpenAPI document**,
`docs.kraken.com/openapi/spot-rest.yaml`, fetched and read this session rather
than recalled. `QueryOrders`' request body schema (`components.schemas.query`):

```yaml
query:
  title: Query Orders Info Request Body
  required: [nonce, txid]
  properties:
    nonce: …
    trades: …
    userref: { type: integer, format: int32 }
    txid: { description: The Kraken order identifier. …comma delimited list of up to 50 ids. }
    consolidate_taker: …
    rebase_multiplier: …
```

**`txid` is REQUIRED, and there is no `cl_ord_id` property at all.** `cl_ord_id`
appears in `QueryOrders`' *response* (every order record carries one) and
nowhere in its request. The only two identifiers it accepts are the Kraken
transaction id and the numeric `userref`.

**The interface hands `cancelOrder` a client order id, not a txid**
(`cancelOrder(pair: Pair, clientOrderId: string)`). So `QueryOrders` is not a
poor choice for that read — it is **structurally incapable of serving it**. There
is no argument to call it with.

### What that would have cost, stated plainly

Had this not been caught, the cancel-then-read path would have been **broken from
the first line it ran**. That path is exercised by **every halt**: section 7.2
cancels every open order for a bot instance, and the filled quantity at the
instant of cancellation is what determines the position the halted bot is
actually left holding. A `QueryOrders` call built around a `cl_ord_id` would have
been refused by the venue with an argument error — meaning the cancel would have
gone through and the read would have failed, so **every halted order would have
come back as a failure with no final quantity**, on the one path where getting
that number right is the entire point.

Worse, it is a failure that **local tests would not have found**. A test double
answering a `QueryOrders` route returns whatever the fixture says regardless of
which parameters were sent; only the real venue rejects it. The discovery point
would have been a **real halt in production**, which is the worst possible place
to learn it.

### The fix, and what did NOT change

**`ClosedOrders` is used instead.** Its request body (`requestBodies.closedOrders`)
does carry `cl_ord_id` — *"Restrict results to given client order id"* — and it is
the correct endpoint on the merits anyway: **a cancel that took effect places the
order among the closed orders**, which is exactly the state the read exists to
observe. The rejected alternative was Gemini's shape (look the order up to learn
its numeric id, then cancel by id, then read), which is **three private requests
on the halt path instead of two** and buys nothing, because Kraken's
`CancelOrder` accepts `cl_ord_id` directly (`components.schemas.cancel` carries
both `txid` and `cl_ord_id`).

**⚠ DECISION 2'S SAFETY DESIGN IS PRESERVED EXACTLY. Only the endpoint changed.**
Every element of it is intact and implemented:

- **One cancel, one read.** Two private requests, pinned by a test that asserts
  the exact path sequence.
- **Never a loop.** No polling, no retry, no waiting for `pending` to clear —
  because the budget is scarcest precisely when this path runs, and an unbounded
  chase competes for it with the *remaining* cancellations of the same halt.
- **Honest reporting on an ambiguous read.** When the one read finds nothing —
  the `pending: true` race DECISION 2 accepted knowingly — the client returns a
  **non-retryable failure naming the `count` and `pending` the cancel reported**.
  It does **not** fabricate "cancelled, nothing filled", which would be a
  quantity nobody observed, in the field that decides a halted bot's position.
  Non-retryable because re-cancelling an order that is already cancelling is not
  a recovery, and the loop that would resolve it is the thing DECISION 2 refused.
  Section 9 reconciliation is the mechanism that settles it, exactly as DECISION 2
  said.

Two further refusals were added around the same read, both from properties this
log already recorded. The returned order's `cl_ord_id` is **re-checked locally**
even though Kraken was asked to filter on it, because an unfiltered
`ClosedOrders` returns recent orders wholesale and a filter the venue ignored
would hand back a plausible-looking order belonging to another bot. And **two
orders carrying one id is refused rather than resolved** — genuinely reachable
rather than theoretical, since entry 90 DECISION 3 recorded that Kraken enforces
`cl_ord_id` uniqueness *only across open orders*, so a closed-order search can
legitimately return a reused id.

### ⚠ THE PATTERN, WHICH IS THE PORTABLE PART

**This is the second time in this build that a specifically named detail carried
forward from entry 90's research turned out wrong on live re-verification, and
the third correction of that shape overall.**

| # | Entry | The named detail | What re-verification found |
| --- | --- | --- | --- |
| 1 | [91.md](91.md) PART 2 | The worked signing example's **secret** | Not Kraken's published example. A signature test built on it would have gone green against a signer Kraken rejects. |
| 2 | [92.md](92.md) PART 1 | Entry 90's 2.1 table: Kraken's decimals *"go straight onto `fromDecimalString`"* | True of the **format**, false of the **precision**. Live pairs publish 9–12 decimal places; the strict parser made real markets entirely unreadable. |
| 3 | **this entry** | Entry 90 DECISION 2's named endpoint, **`QueryOrders`** | Its request schema accepts only `txid`/`userref`. It cannot be called with the identifier the interface supplies. |

Entry 91 drew the lesson for prompt-supplied constants — *treat any documented
example, hash or expected value as a claim to verify.* **This entry extends it to
the shape of the API itself:** a **named endpoint or parameter** is a claim of
the same kind, and it must be checked against the venue's real request schema
before code is built on it — **even when it came from careful prior research, and
even when the research was right about everything around it.** Entry 90's
analysis of PROBLEM 4 was correct in every respect that mattered: `CancelOrder`
really does return only `{count, pending}`, a follow-up read really is forced,
and the one-read-no-loop resolution really is the right answer. The endpoint name
was the one detail nobody had reason to doubt, and it was the one that was wrong.

The practical rule this build now follows: **the request schema is the artefact
to read, not the endpoint list.** A published OpenAPI document answers "can this
endpoint be called with the identifier I hold" in seconds; a name in a prior
entry cannot.

## PART 3 — `getOrderStatus` READS **OPEN BEFORE CLOSED**, AND THAT IS A CORRECTNESS ARGUMENT

The same schema reading settled a second question. **No single Kraken endpoint can
answer "find this order by its client id"**: `QueryOrders` is keyed by txid (PART
2), and `OpenOrders` and `ClosedOrders` each cover one half of an order's life.
Both accept a `cl_ord_id` filter, so the method is one request or two, depending
on where the order is.

**Which one is asked first is not a style preference.** It is the difference
between a correct method and one with a silent hole:

- **Closed first** — the first call reads `ClosedOrders` and finds nothing
  because the order is still open. Between that call and the second, the order
  closes. The second call reads `OpenOrders` and also finds nothing. **The method
  reports that an order which exists was never found** — precisely the outcome
  section 9's reconciliation exists to prevent, and precisely the outcome the
  interface's own comment on `requireSingleOrder` refuses in words.
- **Open first** — an order that is open at the first call is returned by it. An
  order already closed before the first call is found by the second. **There is
  no interleaving in which a real order escapes both.**

So the ordering is chosen because one of the two has a race and the other does
not, and the one that does not also happens to be the cheaper one in the common
case (an order just placed is resting, and is found in a single request). The
docblock states the race rather than the cost, because the cost is the accident
and the race is the reason.

`trades` is deliberately **not** requested on either call. Kraken's `trades` field
on an order record is an array of trade **ids**, not executions — entry 92
recorded that `parseOrderStatus` therefore leaves `fills` **absent** rather than
`[]`, so asking for trades would enlarge the payload and change nothing the
parser reads. Per-fill detail comes from `QueryTrades`, which is reconciliation's
concern.

## PART 4 — DECISION: `getCandles(pair, "6h")` REFUSES **BEFORE** THE REQUEST, NOT AS AN UNREADABLE RESPONSE

[92.md](92.md) PART 5 settled the parse layer — a **total**
`Record<CandleInterval, KrakenTimeframe | null>` with `"6h": null`, read through
`krakenTimeframe()`, which throws — and closed by naming what it had *not*
settled: *"`client.ts` must still decide what `getCandles(pair, "6h")` returns to
a caller — whether that surfaces as an `#unreadable` failure or as a refusal
before the request is a client-level choice, not a parser one."* This is that
decision.

**DECIDED: a definite, non-retryable `exchange_error` produced locally, before
any request is built or sent** — following `#rejectedLocally`, the shape **both**
existing clients already use for a locally-decidable refusal (an order
`validateOrder` rejects is refused before sending, on Binance and Gemini alike).

Three reasons, in the order that decided it:

1. **`#unreadable` means something, and it would be false here.** Its message is
   *"could not read Kraken's response"* — an assertion that **Kraken answered and
   this code could not understand the answer**. Kraken would never have been
   asked. An operator reading that goes looking for a payload change at the
   venue, which is the wrong place entirely: the fact is local, constant, and
   known before any I/O.
2. **It is knowable without spending anything.** `KRAKEN_TIMEFRAMES` is a frozen
   constant. Sending a request to discover what it already states costs a REST
   request now and rate-limit budget once the gate exists — to be told
   `EGeneral:Invalid arguments` (live, re-confirmed today against
   `OHLC?pair=XBTUSD&interval=360`), a message that names **neither the interval
   nor Kraken's real supported set** and is therefore strictly less useful than
   the one already written.
3. **It keeps `parse.ts` the single place that knows which intervals Kraken
   lacks.** The check is written as a `try`/`catch` around `krakenTimeframe()`
   rather than as its own `=== null` test, so the caller sees **that function's
   own message verbatim** — naming the interval *and* Kraken's full published
   set — and a future change to Kraken's intervals has exactly one place to land.
   A duplicated null test here would have been a second copy of the venue's
   capability table, free to drift.

Non-retryable, because no amount of waiting grows Kraken a six-hour candle. The
test asserts the strong form of all three: the message matches `parse.ts`'s
wording, it does **not** match `/could not read Kraken's response/`, and **zero
requests are recorded** — not even the catalogue fetch, since the interval is
checked first. A companion test runs the other six intervals through to confirm
the refusal is about the one gap and not the feature.

## PART 5 — ⚠ THE RATE LIMITER IS A DOCUMENTED PLACEHOLDER, AND THE CLIENT IS CONSEQUENTLY **UNGATED**

**State of this, unambiguously: `KRAKEN_REQUEST_COSTS` is not a rate limiter, is
not Kraken's cost model, and is not wired into anything.**

### What exists

An honest **count of the HTTP requests each interface method actually sends**,
read off the code rather than assumed, recording four things per method: requests
charged to the account-wide **REST** counter (worst case — `getOrderStatus` is one
or two, per PART 3), requests charged to the **per-pair matching-engine** counter
(`placeOrder`, `cancelOrder`), whether the cost is **age-dependent**, and whether
a cold catalogue adds two more public fetches.

It is keyed by `keyof RestExchangeClient`, for exactly the reason `MethodWeights`
and `GEMINI_REQUEST_COSTS` are: **a method added to section 4.1's interface will
not compile until its cost on this venue is written down**, so no new call can
slip past unmeasured later.

### What does not exist, and why it structurally cannot yet

The table is **not** converted into `MethodWeights` and Kraken is **not**
registered in `METHOD_WEIGHTS`. That is not an omission that could be fixed by
adding a line: `METHOD_WEIGHTS` is a **total `Record<ExchangeId, MethodWeights>`**
and `ExchangeId` is still `"binance" | "gemini"`, so there is no key to register
under. Its own docblock says that absence is the intended forcing function —
widening `ExchangeId` breaks that line until Kraken's table is declared — and
widening `ExchangeId` is a wiring step with a migration behind it (PART 8), not
part of this file.

The gap it is standing in for is **structural, not numeric** ([90.md](90.md)
PROBLEM 2, all four points): Kraken's REST counter **decays continuously** where
`WeightBudget` expires whole entries after a fixed window; `AddOrder` and
`CancelOrder` charge a **separate matching-engine counter kept per pair** while
the `RateLimiter` Durable Object holds one budget per account; a cancel's cost
**depends on the order's age** (+8 under five seconds, +1 past five minutes),
which no `Record<method, number>` resolved before the call can express; and
Kraken sends **no rate-limit headers at all**, so there is no feedback channel.

### ⚠ WHAT THIS MEANS OPERATIONALLY, SAID LOUDLY

**A Kraken client today is completely UNGATED by rate limits.** Nothing between
it and the venue counts anything. That is **visible and deliberate rather than
hidden**: the venue is unwired, so the ungated client cannot currently be reached
by a bot at all — and the alternative would have been worse, because gating
Kraken with Binance's or Gemini's table would have spent a **currency Kraken's
trading limiter does not use** (weight, per account) against **the path that
matters most** (per-pair cancels during a halt), while *looking* correctly
gated.

**This is the correct interim state per entry 90 PART 6's own build order**,
which separated the rate limiter into its own session precisely so that a risk
control and a transcription exercise would not share a diff. It is a sequencing
choice, not an oversight. **But it is real, and it must not be assumed away:**
the moment Kraken becomes a valid `ExchangeId`, an unlimited client becomes
reachable, so the wiring step and the rate-limiter session are coupled in one
direction — **wiring without gating is the unsafe order**. A test pins the
absence (`METHOD_WEIGHTS` has exactly `binance` and `gemini`) with a comment
saying that if it ever fails, the dedicated session has begun and this
expectation is what that session should replace.

### One correction to entry 92, which changes the readiness picture

[92.md](92.md)'s closing section states that entry 90 PART 4's prerequisite —
*`RateLimitedExchange` gates every venue with Binance's weight table because no
call site passes `weights`* — **"is still outstanding and still live."** That is
**stale**. It was fixed in commit **`c43f40c`** (*"RateLimitedExchange requires
explicit venue, no default weight table"*), which predates entry 92 and is an
ancestor of `HEAD`: `RateLimitedExchangeOptions.exchange` is now required with no
default, the weights are derived from it, and **both** call sites pass it —
`bot-instance.ts` from `config.exchange` and `reconciliation.ts` from
`account.exchange`, in each case the same value that selected the client, so the
table charged and the client charged for cannot disagree.

Recorded because it matters to what comes next: **the rate-limiter redesign is no
longer blocked on that prerequisite.** The seam it needed — a gate that knows
which venue it is in front of — already exists.

## PART 6 — FIXTURE PROVENANCE: HALF LIVE, AND THE TEST FILE SAYS WHICH HALF

Same two-tier discipline as [91.md](91.md) and [92.md](92.md), stated at the head
of `client.test.ts` so a reader does not have to infer it.

**PULLED LIVE from `api.kraken.com`, 2026-09-03, HTTP 200 on every one:**
`GET /0/public/AssetPairs?pair=XBTUSD,ETHXBT` and
`GET /0/public/Assets?asset=XXBT,ZUSD,XETH` (one edit each, matching the other
three Kraken test files: the `fees`, `fees_maker`, `leverage_buy` and
`leverage_sell` arrays dropped — nothing this client reads is touched);
`GET /0/public/Ticker?pair=XBTUSD`; `GET /0/public/OHLC?pair=XBTUSD&interval=1`;
`GET /0/public/Time`; and the error bodies `EQuery:Unknown asset pair`
(`Ticker?pair=NOTAPAIR`), `EGeneral:Invalid arguments`
(`OHLC&interval=360`) and `EAPI:Invalid key` (`POST /0/private/BalanceEx` with a
junk key) — **all three over HTTP 200**, which is the whole reason `#request`
reads the error array before the status.

**A live finding that changed the code.** Kraken's OHLC `since` is **inclusive of
a candle's OPEN time**, established by probing rather than reading:
`?interval=1&since=1788414900` returned a **first row of `1788414900` itself**.
The interface's `since` means *"candles whose CLOSE time is after it"*, so sending
the caller's value unmodified would **drop the candle that opened before `since`
and closes after it** — which, for the price feed's gap-backfill (section 4.6
step 14), is exactly the candle that was **in progress when the connection
dropped**. The client therefore subtracts one interval before sending and applies
the exact close-time contract locally on top. Three tests pin it, including the
boundary candle. (Kraken's own documentation supplies the other half: at most 720
entries, older data unreachable regardless of `since` — the same window
asymmetry the interface already documents for Gemini, so short reconnect gaps are
always covered and deep-history backtest remains a section 13 question this
method does not promise to answer.)

**FROM KRAKEN'S PUBLISHED REFERENCE, NOT LIVE, AND LABELLED AS SUCH:** the
private payloads — `AddOrder`, `CancelOrder`, `OpenOrders`, `ClosedOrders`,
`BalanceEx` — **and the `cl_ord_id` request schemas that PART 2 and PART 3 turn
on**, read from `docs.kraken.com/openapi/spot-rest.yaml`.

**Why live verification was not possible, checked rather than assumed.** No
Kraken credentials exist yet ([92.md](92.md) records the same limitation), and
**unauthenticated probing settles nothing about a private endpoint's parameters,
because Kraken validates the API key before it validates the request body.**
Verified directly this session: `POST /0/private/QueryOrders` with a junk key and
a `cl_ord_id` but **no `txid`** answers `{"error":["EAPI:Invalid key"]}` — the
identical response it gives to the same request carrying **no parameters at
all**. An argument error never appears, so the venue cannot be made to confirm or
deny the schema without a real key.

**This matters for how PART 2's correction should be read.** The correction is
solidly grounded — the OpenAPI document is Kraken's own machine-readable
specification, not prose, and the `cl_ord_id` presence/absence is unambiguous in
it — but it is **documented, not live-verified**, and the same caution entry 92
attached to its private-endpoint parsers attaches here: **the first credentialled
call against Kraken remains a verification step with expected findings, not a
formality.** The private half of this client — `placeOrder`, `cancelOrder`,
`getOrderStatus`, `getOpenOrders`, `getAccountBalances` — is correct against the
published schema and **unverified against the venue**.

While reading that document, one of entry 90's conditional premises was
re-confirmed from the source: `AddOrder`'s `cl_ord_id` accepts *"Long UUID (36),
Short UUID (32 hex), or **Free format ascii text up to 18 characters**"*, which is
the ceiling DECISION 3 built the venue-keyed id budget around. `client.ts`
deliberately **does not re-check that length** — `VENUE_ORDER_ID_BUDGETS.kraken`
and `checkBotInstanceIdFitsVenue` enforce it at bot creation (commit `84c4e1c`),
and re-checking here would put one rule in two places to drift, and would refuse
mid-order something that should never have been creatable.

**CONSTRUCTED, AND MARKED AT THE POINT OF USE**, per entry 91's rule that a
fixture posing as pulled data teaches the wrong shape next time: the crossed
book (the live `XXBTZUSD` ticker with its bid raised above its ask), the
pending-cancel race, the duplicate client order id, the cross-pair order, a
`post_only` pair status, and a non-envelope HTML error page. Each is one edited
field of a real payload, because none can be requested on demand.
