# 90 — Kraken: the interface maps, the venue does not. Four decisions taken before any code

**NOT COMMITTED, NOTHING IMPLEMENTED.** This entry is research and four
decisions. No source file was modified, no test written, no schema, migration or
spec section changed; `HEAD` is **`e5a826f`** and stays there. The only paths this
session writes are this entry and its README row.

**NOTHING WAS DEPLOYED.** Unlike entry [89.md](89.md), which stood up five
diagnostic Workers on the real edge, this session made its live requests
directly. No Worker was created, no binding used, no state held.

Entry [89.md](89.md) chose Kraken as the primary venue and named the next step:
*"build the real Kraken exchange client, following the existing Binance/Gemini
client pattern in section 4."* This entry is the reading done before that build
starts. It exists because three of the four problems below would not have been
visible from the interface, and two of them change what gets built rather than
how.

## PART 1 — WHAT WAS RESEARCHED, AND HOW IT WAS VERIFIED

Two sources, kept distinct on purpose, because entry 89's PART 2 established
that Kraken's own documentation can be wrong about Kraken (its support article
advertises a demo host that 301s to marketing):

**Live, against `api.kraken.com`, this session.** `/0/public/Time`,
`/0/public/Ticker`, `/0/public/AssetPairs` (the **full 1440-pair catalogue**,
pulled and analysed, not sampled), `/0/public/Assets`, and
`POST /0/private/Balance` with a deliberately invalid key to read the
authenticated error path and the response headers.

**Documented, at `docs.kraken.com`.** Spot REST authentication, Spot REST rate
limits, Spot trading (matching-engine) rate limits, AddOrder, CancelOrder,
QueryOrders, OpenOrders, QueryTrades, BalanceEx, OHLC, AssetPairs, the client
order identifier guide, and the Spot error message guide.

**Nothing here is from memory.** Where a fact below is marked *live*, a request
was made and the response read. Where it is marked *documented*, it was not
verified against the venue and is labelled so, exactly as entry 89 labelled its
fee figures.

### The one place the documentation and the venue disagreed

**Kraken's pair naming is tolerant on input and canonical on output, and the
documentation describes only the tolerance.**

The AssetPairs reference gives `BTC/USD,ETH/BTC` as its example `pair` argument,
which reads as though those are the venue's names. They are not names at all —
they are aliases Kraken resolves. Live:

| Request | Response key |
| --- | --- |
| `AssetPairs?pair=BTCUSD` | `XXBTZUSD` |
| `AssetPairs?pair=XBTUSD` | `XXBTZUSD` |
| `Ticker?pair=XBTUSD` | `XXBTZUSD` |
| `AssetPairs?pair=XBT/USD` | `EQuery:Unknown asset pair` |

So `BTC` is accepted going in, the slash form is **not**, and **`BTC` appears in
no response field anywhere** — not in `altname`, not in `wsname`, not in `base`.
A client can therefore send a pair name it can never match a reply against. That
asymmetry is the root of PART 3.1 and it was found by probing, not by reading.

## PART 2 — WHAT MAPS CLEANLY, AND WHAT DOES NOT

### 2.1 What maps, with no change to anything shared

The good news first, because it is most of the surface. **Section 4.1's
interface needs no amendment**, and neither does any shared module.

| Concern | Verdict |
| --- | --- |
| `RestExchangeClient` (section 4.1) | All ten methods have a Kraken endpoint. No signature changes, no new methods. |
| `ExchangeOutcome`, `isUsable`, no-throw | Unchanged. Section 5.6's guarantee holds identically. |
| Transport skeleton | `#request` → `#transport` → parse → `#unreadable` copies structurally from `GeminiClient`. |
| **Nonce, not clock drift** | Kraken authenticates with an increasing uint64 nonce per API key. This follows **Gemini's** pattern exactly: `NonceGenerator`'s contract applies unchanged, and section 4.2's `ClockOffset`/`getServerTime` machinery has no role. Unlike Gemini, Kraken *does* publish `/0/public/Time` (live), so `getServerTime` can return a real value rather than Gemini's honest refusal. |
| **Decimal strings** | Prices, volumes, costs and fees are all decimal **strings** (live). They go straight onto `fromDecimalString`, with **none** of the JSON-number exception `gemini/parse.ts` needed for candle OHLCV. Timestamps are floats (`1688665496.7808`) needing `×1000`. |
| **Order state** | A real status string — `pending`, `open`, `closed`, `canceled`, `expired` — which is **closer to Binance's enum than to Gemini's `is_live`/`is_cancelled` booleans**, and the easiest of the three venues to map onto `OrderState`. |
| `getOpenOrders` | No pair filter on Kraken's `OpenOrders`, exactly as on Gemini's `/v1/orders`. Same local-filter treatment, same reasoning. |
| `validateOrder`, `SymbolFilterCache` | Already exchange-agnostic. Kraken re-exports them the way `gemini/filters.ts` does. |
| Order filters (section 4.3) | `tick_size` → `tickSize`, `ordermin` → `minQuantity`, `costmin` → `minNotional`, all present on all 1440 pairs (live). `stepSize` is **derived** from `lot_decimals` as 10⁻ⁿ. Kraken publishes **no maximum** price, quantity or notional at all — which maps to `ZERO`, a value `SymbolFilters` already defines as "rule disabled". |
| `instrument` (`InstrumentKind`) | **Absent, and meaningfully so.** Kraken's spot and futures APIs are separate hosts, so — as with Binance's `exchangeInfo` — there is no field to read and no ambiguity to resolve. `undefined` is the correct answer, and `checkSpotInstrument`'s per-venue policy already covers it. |

Two smaller gaps worth recording rather than discovering later: **Kraken has no
6-hour candle interval** (its OHLC intervals are 1, 5, 15, 30, 60, 240, 1440,
10080, 21600 minutes — 240 and 1440 with nothing between), so a Kraken timeframe
table cannot be a total `Record<CandleInterval, …>` without inventing one; and
`Balance` must read **`/private/BalanceEx`**, not `/private/Balance`, because
only the extended form reports `hold_trade` and the interface wants `free` and
`locked` separately.

### 2.2 The four that do not map

Everything above is transcription. These four are not.

---

#### PROBLEM 1 — Pair naming is a catalogue, not a rule

Tonight's probes in entry 89 saw `XXBT`→`BTC` and `ZUSD`→`USD` and recorded it
as "prefix mangling". **It is not a prefix rule, and treating it as one produces
a specific, silent corruption.**

From the full 1440-pair catalogue (live):

- **Only 44 of 1440 keys differ from their own `altname`.** The X/Z prefixing is
  a legacy artifact confined to the ~15 original assets — XBT, ETH, ETC, LTC,
  XMR, XRP, XLM, ZEC, MLN, DOGE-as-XDG, and the Z-prefixed fiats. Everything
  listed since is keyed plainly.
- **But the prefixing is per-FIELD, not per-pair.** `ARBUSD` is keyed plainly and
  its `altname` is `ARBUSD` — while its `quote` field still reads **`ZUSD`**. So
  a plain key does not license the conclusion that the assets are plainly named,
  and asset codes must be un-prefixed via `/public/Assets`' own `altname`
  regardless of how the pair looked.
- **Every response is a map keyed by a name the client did not choose.** A parser
  cannot do `result[requestedPair]`; it must resolve the canonical name first, or
  read the single key out of the map. This is not a Kraken quirk to work around —
  it is the shape of every endpoint's reply, public and private alike.

**The corruption a transformation function causes.** `BTC` → `XBT` as a string
substitution looks obviously right and is obviously wrong: **`WBTCUSD` (Wrapped
BTC) and `TBTCUSD` (tBTC) are both live pairs** (live), and the substitution
turns them into `WXBTUSD` and `TXBTUSD` — which do not exist. A ticker the
pipeline surfaces legitimately becomes a pair that cannot be traded, and the
failure arrives as `EQuery:Unknown asset pair` naming nothing.

This is entry [89.md](89.md)'s PART 5 sub-finding (a) — *silently routing an
order into the wrong version of a market* — reappearing one layer down, as a
**string-handling** bug rather than a pair-selection one.

**The only honest approach is a lookup.** Fetch `AssetPairs` once, cache it
beside the filter cache, and build both directions of the map — ticker → altname
→ canonical, and canonical → ticker for reading replies back. Any resolution not
backed by that catalogue is a guess, and `toGeminiSymbol`'s one-line
`replace().toLowerCase()` has **no Kraken analogue**. This is why PART 6 gives
Kraken a `catalogue.ts` that neither existing venue needed.

Separately, and still open from entry 89: `BTC` has `XXBTZUSD`, `XBTUSDT` and
`XBTUSDC` (live) — three books with different depth. Which one is *the* book is
pair **selection**, and it is not something a naming module can decide.

#### PROBLEM 2 — The rate-limit model is structurally different, not numerically different

**This does not map onto `WeightBudget`, and the mismatch is not a matter of
different constants.** Four independent breaks:

**(a) Continuous decay, not a sliding window.** Kraken's REST counter falls
continuously; `WeightBudget` expires whole entries after 60 seconds. A sliding
window is **not** a conservative approximation of a decay — it holds the full
cost for the whole window where Kraken would have shed it partway, so it
under-permits, and `#waitFor`'s arithmetic ("when does this entry leave the
window") computes a wait that corresponds to nothing Kraken is doing.

| Tier | Max counter | Decay | *(documented)* |
| --- | --- | --- | --- |
| Starter | 15 | −0.33/sec | |
| Intermediate | 20 | −0.5/sec | |
| Pro | 20 | −1/sec | |

**(b) Two independent budgets, one of them per pair.** `AddOrder` and
`CancelOrder` do not charge the REST counter above — they charge a **separate
matching-engine ratecount**, and *"each client has a rate counter **per
pair**"*. The `RateLimiter` Durable Object is one-per-account holding one
`WeightBudget`. On Kraken, order traffic on `BTC/USD` and `ARB/USD` does not
share a budget at all, while their status reads do.

**(c) Cost depends on the order's AGE, not on the method.** `MethodWeights` is
`Record<keyof RestExchangeClient, number>` — a constant resolved from the method
name before the call is made. Kraken's cancel cost is not a constant *(documented)*:

| Transaction | Fixed | <5s | <10s | <15s | <45s | <90s | <300s |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Add Order | +1 | — | — | — | — | — | — |
| Cancel Order | — | **+8** | +6 | +5 | +4 | +2 | +1 |
| Edit Order | +1 | +6 | +5 | +4 | +2 | +1 | — |

Thresholds 60 / 125 / 180 by tier, decaying −1 / −2.34 / −3.75 per second.

> **⚠ THE WORST CASE IS THE RISK-EXIT PATH.** Cancelling an order placed three
> seconds ago costs **eight times** what the same call costs on a five-minute-old
> order. Section 7.2's halt cancels **every open order for a bot instance** — and
> a grid bot that has just laid a fresh ladder is holding exactly the young orders
> that cost the most. Roughly **seven** such cancels exhaust a Starter threshold
> of 60 **on that one pair**. This is precisely the traffic
> `RISK_EXIT_RESERVE_FRACTION` exists to protect, and the existing reserve cannot
> protect it, because the reserve is denominated in a currency (weight, per
> account) that Kraken's trading limiter does not use (ratecount, per pair).

**(d) No feedback channel.** Response headers were read on both a public and an
authenticated call (live): **Kraken sends no rate-limit headers of any kind.**
`syncFromExchange` has no input, exactly as on Gemini, so local accounting is the
only accounting and must be conservative rather than corrected after the fact.
There is one partial compensation — `EService:Throttled: <unix timestamp>`
carries a real time to wait, making Kraken the first venue here able to populate
`retryAfterMs` from the exchange itself.

**Assessment.** The `RateLimiterPort` seam — `acquire`/`release` with a
re-presentable ticket — is the right abstraction and should survive untouched.
What belongs *underneath* it is a second budget class: a decaying counter, plus a
per-pair trading counter, sharing the DO's existing ticket, queue and priority
machinery. The compile-time property that a new interface method cannot be called
until its cost is declared must be preserved, but generalised — the gate has to
ask for a cost that can depend on the **pair** and, for cancels, on the order's
**age**.

**This is being treated as its own build session and is deliberately not folded
into the base client.** It changes shared infrastructure that both existing
venues run on; doing it alongside a new client's signing and parsing would put a
risk control and a transcription exercise in the same diff.

#### PROBLEM 3 — HTTP 200 always; the error lives in the body

Entry [89.md](89.md) flagged this and it is confirmed again (live):
`POST /0/private/Balance` with a bad key returns **HTTP 200** carrying
`{"error":["EAPI:Invalid key"]}`. Errors are `E<Category>:<Message>` strings in a
top-level array, and *"when non-empty, the request failed, even if a `result`
object is present."*

`GeminiClient.#request` already checks `readErrorBody` on a 200 and converts it
with `classifyFailure(400, …)`. Kraken needs the same check as its **primary**
path rather than an edge case — but **the synthetic status is a lie worth
avoiding**. `classifyStatus`'s whole rule set is "5xx means the effect is
unknown, 4xx means understood and refused, 429 is retryable", and none of it can
fire when the status is always 200. **Classification must be driven by the error
string**, which is where Kraken actually puts the information:

| Kraken error | Kind | Retryable |
| --- | --- | --- |
| `EAPI:Invalid nonce` | `exchange_error` | **yes** — mirrors Gemini's `INVALID_NONCE_REASON` |
| `EAPI:Rate limit exceeded`, `EOrder:Rate limit exceeded` | `exchange_error` | yes |
| `EService:Throttled: <ts>` | `exchange_error` | yes, **with a real `retryAfterMs`** |
| `EService:Unavailable`, `EService:Busy` | **`transport`** | yes — a server-side failure leaves the request's effect unknown (section 5.6) |
| `EAPI:Invalid key`, `EAPI:Invalid signature`, `EGeneral:Permission denied` | `exchange_error` | no |
| `EOrder:Insufficient funds`, `EOrder:Order minimum not met`, `EOrder:Cost minimum not met`, `EOrder:Tick size check failed` | `exchange_error` | no |

The `EService` row is the one that matters most: mapping it to `exchange_error`
because "the HTTP status was 200, so the exchange answered" would tell section
5.1 an order was definitely refused when its fate is in fact unknown.

#### PROBLEM 4 — `cancelOrder` cannot honour the contract entry 3.1 wrote for it

**This is the sharpest conflict, and it is with a decision this log already
made.** Step 3.1 changed `cancelOrder` from section 4.1's literal
`Promise<void>` to return the cancelled order, for a stated reason: section 7.2's
halt cancels every open order, some will be partially filled at that instant, and
the filled quantity **at the moment of cancellation** determines the position the
halted bot is left holding. The interface comment is explicit that reading it
from the cancellation response avoids a follow-up that would be *"slower when
speed matters most, more rate-limit budget at the worst moment, and racy besides,
since a resting order can fill again between the cancel and the follow-up read."*

**Kraken's `CancelOrder` returns `{count, pending}`.** Nothing else. No filled
quantity, no state, no order id. Binance echoes the cancelled order; Gemini's
cancel response carries the final `executed_amount`; Kraken carries neither.

So the Kraken client is forced into precisely the follow-up that comment was
written to rule out — `CancelOrder`, then `QueryOrders` to read `vol_exec` — and
**every objection in it applies**, with one now worse than when it was written:
the cancel has just charged the per-pair trading counter **up to +8** (PROBLEM 2),
and the follow-up read charges the account REST counter, both during a halt.

`pending: true` compounds it. The cancel may not have taken effect when the reply
arrives, so an immediate `QueryOrders` can return `status: "open"` with a
`vol_exec` that is about to change. Reading once is not sufficient for certainty;
reading in a loop spends the budget that is scarcest at exactly that moment. That
tension is what DECISION 2 below resolves, and it resolves it by giving something
up rather than by finding a way to have both.

## PART 3 — THE FOUR DECISIONS

### DECISION 1 — `testnet` refuses to build a Kraken client at all

**The problem.** `exchange.ts` and `exchange-gemini.ts` both derive the base URL
as a **pure, total function of `env.ENVIRONMENT`**, with no `*_BASE_URL` var or
secret anywhere and an explicit instruction that there must never be one. That is
what makes it structurally impossible to point the testnet Worker at production —
a guarantee this log has now protected twice, once per venue. **Kraken has no
sandbox** (entry 89, PART 2: `demo-futures.kraken.com` 301s every path including
root to marketing; spot UAT is account-manager-only, with no public host).

**DECIDED: `ENVIRONMENT: "testnet"` returns an `ok: false` resolution with a
reason naming the absence, and no Kraken client is constructed.** A Kraken
account cannot exist in the testnet environment. `KRAKEN_BASE_URLS` holds one
entry and `krakenBaseUrlForEnvironment` is total over exactly one value.

**Why, and what was rejected.**

- **Rejected: both environments → `https://api.kraken.com`, made safe by using a
  separate low-limit key in testnet.** This is the option that quietly destroys
  the guarantee. Safety would rest on *which key was pasted into which
  environment's secret* — an operator action, revocable by a typo — instead of on
  a derivation that has no branch capable of producing the wrong host. The whole
  point of deriving the URL rather than configuring it is that no combination of
  settings can get it backwards; this reintroduces exactly such a combination and
  hides it behind a convention.
- **Rejected: `testnet` → a `FakeExchange` presented as Kraken.** Safe on the
  network, and worse epistemically. Entry [89.md](89.md) ruled OKX out for its
  demo feed being *"healthy, fresh and well-formed while describing a market that
  does not exist"*, and entry [86.md](86.md) built detectors for that exact
  condition. Shipping our own version of it, under the name of the venue we chose
  *because* its data is real, would be building the failure we just rejected a
  venue for.
- **Accepted cost, stated plainly.** Kraken is unreachable in testnet, so no
  Kraken code path can be exercised end-to-end outside production. **This does
  not resolve [88.md](88.md)'s 22.7 observation-period dependency and does not
  claim to** — entry 89 already recorded that choosing a production venue left
  that unsolved. It is carried forward unchanged.

### DECISION 2 — Cancel, then exactly one status read. Never loop.

**DECIDED: `cancelOrder` issues `CancelOrder`, then a single `QueryOrders` read,
and reports the order's state honestly as of that read.** No polling, no retry
loop, no waiting for `pending` to clear.

**Why.** The budget is scarcest precisely when this path runs — a halt cancelling
a full ladder, each young cancel costing up to +8 against a per-pair threshold as
low as 60 (PROBLEM 2). A bounded single read has a cost the gate can reason about
before the halt begins. An unbounded chase for certainty has a cost that grows
with exactly the condition that makes it expensive, and it competes for budget
with the *remaining cancellations* — meaning a bot could spend its budget
confirming the first cancel and fail to issue the last.

**⚠ THE ACCEPTED TRADEOFF, RECORDED AS A DELIBERATE CHOICE AND NOT A GAP.** The
halt path can occasionally report a filled quantity that is **a few moments
stale**: if `pending: true` and the order fills between the cancel taking effect
and the read landing, the recorded quantity is the one observed at the read, not
the final one. **This is a real inaccuracy in a safety path and it is being
accepted knowingly**, on the grounds that a bounded stale number the system knows
how to reconcile is better than an unbounded read loop that may not finish.
Section 9's reconciliation is the existing mechanism that catches exactly this
kind of drift, and it does not depend on the halt having been perfectly accurate.

**Rejected: widening the interface** so `cancelOrder` can return "cancelled,
final quantity unknown". The most honest option, and it touches
`/src/shared/exchange-client.ts`, both existing clients, `FakeExchange`, and
every halt call site — to express a distinction only one of three venues can
produce. Reconsider if a second venue turns out to have the same hole; a single
venue is not enough to reshape the interface all strategy code depends on.

### DECISION 3 — Enforce an 18-character client-order-id cap at generation, for Kraken only

**The problem.** Kraken's `cl_ord_id` accepts a long UUID (36 chars), a short
UUID (32 hex), **or free-format ASCII text up to 18 characters**.
`makeClientOrderId` produces `v1-<slug>-<sequence>`, is not hex, and is therefore
free text — so the ceiling is 18, not the `MAX_CLIENT_ORDER_ID_LENGTH = 36` that
constant documents as *"Binance caps this at 36 characters."* A bot id of
`grid-btcusd-01` already yields `v1-grid-btcusd-01-7` — **20 characters, rejected
by Kraken.**

**DECIDED: enforce the 18-character cap at generation time for Kraken accounts,
rejecting a bot instance id that cannot fit, rather than changing the id scheme.**

**Why, and what was rejected.**

- **Rejected: a shorter v2 scheme for all venues.** Uniform, and it changes ids
  on Binance and Gemini for the sole benefit of a third venue — with
  `parseClientOrderId` obliged to keep understanding v1 forever for orders
  already placed. Churn on two working venues to accommodate one.
- **Rejected: a short UUID derived deterministically from bot id + sequence.**
  It fits comfortably and it **destroys the property the scheme exists for**.
  `makeClientOrderId`'s own comment states it: the slug is embedded verbatim *"so
  that reconciliation (section 9) can look at an unexpected open order on the
  exchange and say which bot owns it. A hash would fit any input but would make an
  orphaned order untraceable, which is precisely the case reconciliation exists to
  investigate."* Choosing a hash here is choosing to lose that on the venue that
  will carry the real money.

**⚠ THIS DECISION IS CONDITIONAL AND MUST BE VERIFIED BEFORE IMPLEMENTATION.**
The constraint is `v1-` (3) + slug + `-` (1) + sequence digits ≤ 18, so
**slug + digits ≤ 14** — a slug of 12 characters leaves room for only two digits
of sequence. `BOT_INSTANCE_ID_PATTERN` currently permits up to **20**. It is not
yet established that real bot instance ids in the database fit, and if they do not,
this decision is not workable as stated and the rejected options come back into
play. **Verifying it against the actual `bot_instances` rows is step (b) of the
build order in PART 6, before any Kraken code is written.**

**A second finding, recorded because it weakens a stated safety property.**
Kraken *"verifies `cl_ord_id` uniqueness across open orders for each client"* —
**only among open orders**. Once an order closes, its id can be reused. Section
5.1's second layer of duplicate protection — "the exchange rejects a reused id" —
is **true on Binance and Gemini and false on Kraken for any order that has already
closed**. The Durable Object attempt records still work and remain the primary
layer; the exchange-side backstop simply is not there. `userref` (int32, no
uniqueness enforcement at all) is not a substitute and would cost the same
reconciliation traceability as the UUID option.

### DECISION 4 — Always send `oflags=fciq`, so the fee asset is asserted rather than inferred

**The problem.** Kraken's fee currency **depends on the side of the order**:
`fcib` (fee in base currency) is the default when **selling**, `fciq` (fee in
quote currency) is the default when **buying**. And `QueryTrades` returns a bare
`fee` string with **no currency field at all**, so `Fill.feeAsset` would have to
be reconstructed at runtime from side + `oflags` + the pair's base and quote.

**DECIDED: send `oflags=fciq` explicitly on every order.** The fee asset is then
always the quote asset, known locally, on both sides.

**Why.** Section 5.5 states the rule this venue is built to break: fees must
never be assumed to be paid in the quote currency, and the fee asset must be read
from the fill. Kraken is the first venue here where that assumption is *literally
wrong half the time* — and it is also a venue that **does not report the answer**,
so "read it from the fill" has nothing to read. Of the two ways out, deriving it
leaves a safety-relevant value resting on a chain of inference (side → default
flag → pair → asset code → un-prefix), any link of which is a place to be wrong
silently. Setting the flag makes it a fact the request itself establishes.

**This is a behaviour change, not a translation, which is why it is recorded
here.** It changes which asset a **sell** is debited in versus Kraken's own
default. It is a deliberate, visible choice about the account's real behaviour,
and it belongs in this log rather than inside `placeOrder` as an unremarked
parameter.

**Rejected: accept Kraken's defaults and derive.** Nothing about account
behaviour changes, and section 5.5 is left trusting a derivation instead of an
assertion. Preferred only if a future requirement makes base-currency fees
desirable, at which point the flag is the place that decision is expressed.

## PART 4 — A FIFTH FINDING, UNRELATED TO KRAKEN AND ALREADY LIVE

**`RateLimitedExchange` gates every venue with Binance's weight table.**

`rate-limited.ts` defaults `weights` to `BINANCE_METHOD_WEIGHTS`:

```typescript
weights: options.weights ?? BINANCE_METHOD_WEIGHTS,
```

and **neither call site passes one**. Confirmed by reading both:
`bot-instance.ts:1221` (`#exchange`, the only path by which a bot reaches any
exchange) and `reconciliation.ts:364` (`gatedExchange`) each pass `priority`,
`now`, `label` and an optional `sleep`, and **no `weights`**.

**So every Gemini account in production is being gated against Binance's cost
model right now.** Gemini reports capacity as a request **count**, not a weight,
and sends no used-weight header — a fact `exchange-gemini.ts` already documents
in its own comment ("this takes no `RateLimiter` binding: Gemini sends no
used-weight header... The request-count gate a Gemini account needs is applied by
the wrapper at dispatch time, which is out of scope for this step") — and the
wrapper it defers to has been applying Binance's numbers ever since.

**This is a live, pre-existing bug, independent of Kraken.** It was found while
tracing how a third venue's cost table would be selected, and the answer is that
there is currently no mechanism to select one: `MethodWeights` is a constructor
option nobody sets.

**⚠ THIS MUST BE FIXED BEFORE THE KRAKEN RATE-LIMITER WORK BEGINS, NOT AFTER.**
Kraken's cost model cannot be wired correctly through a gate that has no way to
know which venue it is in front of. Fixing it first also keeps the change small
and reviewable on its own terms — a seam correction affecting two existing
venues — rather than arriving buried inside a new venue's integration, where a
reviewer would have to separate "this is how Kraken works" from "this is how the
gate was always supposed to work".

## PART 5 — PROPOSED FILE STRUCTURE (A PLAN. NONE OF THIS EXISTS.)

Following the existing `binance/` and `gemini/` conventions rather than inventing
new ones. **Nothing below has been created; this is the shape the work is
expected to take, recorded so the next session does not re-derive it.**

```
src/exchange/kraken/
  signing.ts     HMAC-SHA512( path + SHA256(nonce + body) ) over a BASE64-DECODED
                 secret, base64-encoded into API-Sign. Reuses NonceGenerator's
                 contract; no ClockOffset. Its own DOCUMENTED_EXAMPLE_CREDENTIALS
                 (Kraken publishes a worked example with an expected signature),
                 since the existing constant holds Binance's pair.
  catalogue.ts   NEW -- no Binance or Gemini analogue. AssetPairs/Assets fetched
                 and cached: ticker <-> altname <-> canonical in both directions,
                 asset un-prefixing, and the response-key resolution every parser
                 needs (PROBLEM 1). Pure; the client owns fetching and caching.
  filters.ts     AssetPairs -> SymbolFilters. stepSize from lot_decimals; maxima
                 as ZERO; status mapped failing closed. Re-exports the shared
```
