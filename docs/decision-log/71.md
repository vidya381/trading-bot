## PART 1 — WHAT THE STAGE D DESIGN PREDICTED

The design session read `#gridExit` (`durable-objects/bot-instance.ts`) and found
that a grid bot exiting on breakout or stop-loss does this, in order: halt (which
cancels every open order), then

```ts
const clearedLadder = { ...ladder, slots: ladder.slots.map(() => null) };
```

then place a liquidation sell for whatever `heldQuantity` was **at that instant**.

Both bots had halted on `breakout_take_profit`, which is reachable only through
`#gridExit`. So both ladders were **fully cleared — every slot null**. From that,
three consequences followed, and they are what the design was built on:

1. **`uncovered` must equal `heldQuantity` exactly.** The detector sums only
   `side === "sell"` slots; with every slot null that sum is `ZERO`, so
   `uncovered = heldQuantity - 0`. The prediction was therefore specific and
   checkable: `heldQuantity` should read **`0.00037572`** on `bot-4xcq8p` and
   **`0.00018835`** on `bot-3trlgb`, matching the previously reported uncovered
   figures.
2. **No sell price is derivable from the ladder.** There is no rung left, and no
   record of which slot the un-replaced buy occupied. Worse, an **upside**
   breakout means price broke *above* the top grid line, so every rung price is
   *below* market — a rung-priced sell would fill at market anyway or, in a thin
   book, sell below it.
3. **Therefore `liquidatePosition`, not a bespoke repair tool.** It already
   requires a halted bot, refuses when an exit order is live, no-ops when flat,
   clears stale slots, **reads a fresh live price and refuses rather than falling
   back to a stale tick**, audits the human actor, and folds its fill through
   `#applyGridExitFill` — the exit accounting entry **63** proved clean.

The design's conclusion was explicit: **do not build Stage D.** A bespoke
D1-driven repair would read a snapshot where the existing action reads a live
price and live filters at the moment it acts — strictly worse.

## PART 2 — WHAT LIVE VERIFICATION ACTUALLY FOUND

**[OPERATOR]** A live `GET` on both bots returned **`heldQuantity = 0.00000000`
on BOTH** — not the predicted non-zero amounts.

**[OPERATOR]** A subsequent `POST /api/bots/:id/liquidate` on each returned
**`action: "nothing_to_liquidate"`** on both. That is the system's own refusal
logic reporting independently, through a second code path, that there was
genuinely nothing left to sell: `#liquidatePositionPass` reads
`state.ladder!.heldQuantity` itself and returns that action only when the value
is `<= ZERO`. Two different reads, same answer.

### The bot's own durable record of that refusal

**[OPERATOR]** A later fresh `GET` on `bot-4xcq8p` shows an alert that was **not
present in the earlier pull**:

```
alertType:  liquidation_noop
severity:   info
resolved:   false
createdAt:  1787558318814      (2026-08-24 07:58:38.814Z)
```

This is **stronger evidence than the API response alone**, and it is worth

at the exact branch that returns `nothing_to_liquidate` — the `liquidation_noop`
alert is raised in that branch and nowhere else in the codebase. So the refusal is
attested by the object's own state, at a recorded instant, and not only by what
the request handler said. Third read, same answer.

**[OPERATOR]** Each bot's real order and alert history shows the condition was

## PART 3 — THE PREDICTION WAS REASONABLE, AND ITS FAILURE IS THE DESIGN WORKING

Stated carefully, because "the prediction was wrong" and "the analysis was wrong"
are different claims and only the first is true.

**The analysis holds.** Every step of it can still be checked in the source:
`#gridExit` really does null every slot; the detector really does sum only sell
slots, so `uncovered` really would equal `heldQuantity` for a ladder in that
state; there really is no rung price to recover; and **nothing in the code path
the investigation traced would have corrected the gap automatically** — the
detector detects and never places, `decide` rebuilds a ladder only while `placed`
is false, and replace-on-fill does not re-run for a rung already missed.

**What the analysis could not model was elapsed time.** Real hours passed between
the investigation that found these two bots and this session's live check. In
that window something resolved the gap through ordinary means. The prediction
described the bots as they *had been*, and was checked against the bots as they
*now are*.

**This is precisely the outcome the design's own discipline exists to catch.**
The design explicitly refused to trust the D1 snapshot and required a fresh live
read before any action — the same reasoning `liquidatePosition` itself carries
(*"the last-seen price is deliberately NOT used as a fallback"*). A bespoke
repair tool built to act on the recorded uncovered figure would have attempted to
sell `0.00037572` and `0.00018835` of base that **was no longer there**. Instead
the live read came first, returned zero, and **no order was placed against either
bot**.

The design's refuse-rather-than-guess discipline — the same pattern as
`#recordCancellation` declining to synthesise a fill id, `#foldTerminalState`
declining to close over an unrecorded fill, and Stage A's `acquisitionFor`
declining to size without history — is what turned a stale premise into a
harmless no-op instead of an unnecessary liquidation.

## PART 5 — WHAT REMAINS OPEN, UNAFFECTED BY THIS ENTRY

**1. The late-fill-after-exit gap is real, still open, and not addressed here.**

The Stage D design session found it while reading the halted-bot path, and entry
70 could not have addressed it because it was not yet known. When the poll folds
a ladder buy fill on an **already-halted** bot, `#applyGridFillToOrder` runs with
`placeReplacement: fresh.status === "running"` → **false**. `heldQuantity` grows
and **nothing tops up the liquidation sell that was already sized** — `#gridExit`
sizes the exit once, from `heldQuantity` at that instant, and never revisits it.

Stage A fixes replacement **sizing** on a running bot. Stage B fixes **dropped**
replacements on a running bot. **Neither runs on a halted bot at all.** Stage C
does detect the outcome, so it is visible rather than silent.

This narrows — and does not contradict — entry 70's Part 8 claim that Stage A
"prevents this from recurring on future fills": that holds for a **running** bot.
Entry 70 stays as written; the narrowing is recorded here. **The gap is
undeployed-against and unscheduled.**

**2. No bespoke Stage D repair tool was built, and none is needed.** If a **third**
bot is ever found holding uncovered base with no covering sell, **`liquidatePosition`
remains the correct tool**, for the reasons in Part 1 — a halted-only gate, an
exit-order-live refusal, a flat no-op, a **fresh live price** rather than a
snapshot, filter validation at the moment of action, an audited human actor, and
fills folded by the clean exit path. **Not a new build.**

The one gap against this project's report-by-default pattern remains as the
design recorded it: `liquidatePosition` has **no dry-run mode**. It was judged
non-blocking because `GET /api/bots/:id` already exposes `heldQuantity` — which
is exactly the read that resolved this session — and adding one would mean
modifying a **shared grid+DCA exit path** that is working and exercised. Recorded
as a deliberate deferral, not an oversight.
