## PART 1 — THE BUG, AND WHY THE OBVIOUS SUBSTITUTES WERE REJECTED

`gemini/parse.ts`'s `parseOrderStatus` set:

```ts
const createdAt = requireEpochMs(record, "timestampms", context);
...
  createdAt,
  updatedAt: createdAt,   // <- the fabrication
```

Gemini's order-status payload carries **one** timestamp, `timestampms`, and it is
the order's CREATION time. State arrives as the booleans `is_live` /
`is_cancelled`, which say *that* an order changed and never *when*. There is no
update, cancel, expiry or transition time anywhere in the response. The parser
satisfied the `OrderStatus` type by echoing creation time back as though it were a
last update.

**The consequence.** Reconciliation's terminated-order tolerance forgives an order
that left the book recently — section 9's *"a fill recorded a few seconds late"* —
by computing `age = at - status.updatedAt` against a 60-second `timingWindowMs`.
Fed creation time, that expression measures the order's **TOTAL AGE**. So on
Gemini the window **never applied to any order older than sixty seconds**,
regardless of when it actually terminated, and a disagreement the bot's own
30-second poll was about to resolve halted the bot on the first sighting.

### The two substitutes, considered and rejected during DESIGN, before this session

- **Order-creation time** — what the code actually did. `age` is the order's whole
  life, so the window **NEVER** applies. This is the bug, not a fix for it.
- **Receipt time** — `age` is always ≈ 0, so the window **ALWAYS** applies. That
  would silence real, persistent drift on **every** terminated Gemini order,
  unconditionally. **Strictly worse than the bug it would replace**, because the
  bug is loud and this is silent.

**Why neither works, stated plainly:** both try to answer *"how long ago did this
terminate"* using a timestamp that does not encode that information on this venue.
One is systematically too early and one is systematically too late, and no
constant can correct either, because the error is not an offset — it is the
absence of the fact.

## PART 2 — THE FIX: STOP ASKING A QUESTION THE VENUE CANNOT ANSWER

The insight is not a better clock. It is that the tolerance's real question —
*"has the other observer had its turn yet?"* — was already being answered
elsewhere in this same file **without any venue clock at all**.

Two changes:

1. **`OrderStatus.updatedAt` becomes OPTIONAL**, and Gemini's parser **omits** it.
   Not `undefined`, not `createdAt` — the key is absent. This is not a new
   principle: `shared/exchange-client.ts` already applies exactly this reasoning
   to `createdAt` on a cancellation response, in the same words — *"a fabricated
   value that looks authoritative."* Absence is a fact a consumer can branch on; a
   plausible wrong number is not.

2. **The terminated branch falls back, ONLY when `updatedAt` is absent**, to the
   SAME run-to-run confirmation mechanism entry 61 built for the LIVE-order
   branch: a first sighting is `order_drift_unconfirmed` (minor — no alert row, no
   halt, but written to the run's findings list, which is what makes it
   remembered); a sighting this account's runs have already seen inside
   `unconfirmedWindowMs` escalates to `order_state_drift` and halts,
   **unconditionally**.

### THIS IS REUSE, NOT REIMPLEMENTATION — and that is verifiable, not asserted

Entry 61 had already done three things that made the terminated branch's adoption
of its mechanism cost almost nothing:

- **`seenUnconfirmed` was already computed once per run** (in `reconcileOrders`,
  deliberately per-run rather than per-bot) and **already passed as a parameter
  into `liveOrderFindings`** — the very function the terminated branch lives in.
  Nothing had to be plumbed.
- **`driftAgainst` already sets `clientOrderId` on EVERY finding it returns**, and
  the audit payload already writes `client_order_id` structurally. So terminated
  branch findings became cross-run matchable **with zero edits**, because the
  match is on a field rather than on prose — entry 61's own refusal to
  string-match, paying off one entry later.
- **`driftAgainst` was already parameterised by `kind`**, defaulting to
  `order_state_drift`. The new call site passes the same two kinds the live branch
  passes.

**Confirmed from the diff, not from memory:** the change to `reconcile.ts` is
**two hunks, both inside `liveOrderFindings`' terminated branch**
(`@@ -826,20 +826,40 @@` and `@@ -849 +869,49 @@`). `unconfirmedDriftFromRecentRuns`,
`driftAgainst`, `RECENT_RUN_SCAN` and the live branch do not appear in the diff at
all.

### WHY THE BRANCH IS ON DATA PRESENCE AND NOT ON THE EXCHANGE NAME

The condition is `if (status.updatedAt !== undefined)`. It is **not**
`config.exchange === "gemini"`, and that is the design rather than a style
preference:

- Testing the exchange name puts a safety decision on a string, in the module that
  has twice refused exactly that — entry 58 declined to recognise a reconciliation
  halt by string-matching `haltReason`, and entry 61 declined to match a finding by
  searching its `detail` sentence. Repeating it here would have been worse for
  knowing about both.
- It generalises correctly by construction. **Any** future venue with the same
  limitation gets the right behaviour on the day it is added, with no edit here —
  and, just as importantly, a venue that reports its transitions honestly keeps
  the window automatically. The routing cannot go stale, because the payload is
  asked about itself.

## PART 3 — THE INVESTIGATION, AND THE ONE PLACE ITS OWN DESIGN DOCUMENT WAS WRONG

All three investigation questions were re-checked **against current source**, not
carried over from the design document.

**Q1 — the fabrication site.** Confirmed present and unchanged at
`gemini/parse.ts:561`, exactly as described. Working tree was clean at `04246a7`
apart from the design document itself.

**Q2 — the reused mechanism's real current state.** `unconfirmedDriftFromRecentRuns`
and the live branch were re-read in full rather than trusted from the design
document's summary. The three properties Part 2 relies on were each confirmed in
the source before being relied on.

**Q3 — every real reader of `OrderStatus.updatedAt`.** The string `updatedAt`
appears **86 times** in `src`. That number is almost entirely noise: **eight
different files declare an `updatedAt` field on some type** — `TrackedOrder`
(`shared/order-state.ts`), `OrderAttempt` (`shared/idempotency.ts`), the research
capital row (`research/capital.ts`), three dashboard types, and `OrderStatus`
itself — and separately, D1's `orders.updated_at` column produces a further crop
of near-misses.

**The real readers of `OrderStatus.updatedAt` number THREE**, and only three:

| Site | What it does |
| --- | --- |
| `reconciliation/reconcile.ts:826` | `at - status.updatedAt` — the tolerance itself |
| `durable-objects/bot-instance.ts:2771` | `closeOrder(..., remote.updatedAt)` in `#foldTerminalState` |
| `durable-objects/bot-instance.ts:5173` | `closeOrder(..., remote.updatedAt)` in `#recordCancellation` |

They were distinguished from the same-named fields by **type**, not by name — and
the distinction was then **proved by the compiler rather than by the grep**:
`tsc --noEmit` passed clean after handling exactly those three and nothing else. A
missed reader would have been a type error, not a silent survival.

### THE DEVIATION — the design document's §4 was wrong, and this session did not follow it

The approved design's specification included an additional guard on the branch:

```ts
if (isTerminal(status.state) && status.updatedAt !== undefined) {
```

with the stated justification that it **"costs nothing"** and that *"the safety
argument reads better when the branch's precondition is asserted rather than
assumed."*

**That claim is FALSE, and this session found it false while building.** The guard
does not cost nothing. It changes **BINANCE's** behaviour in a real edge case: an
order absent from `getOpenOrders` but still reported live by a direct
`getOrderStatus` call. Today that case takes the 60-second window; with the guard
it would have been routed down the clockless fallback instead. Binance supplies a
real `updateTime`, so nothing about the Gemini defect requires touching how that
case is handled.

The build brief was explicit and unambiguous that Binance's current behaviour must
be **completely** unaffected. The design document's own §4 would have violated
that requirement, in the same change that was justified by it.

**What was done: the operator's instruction was followed over the design
document's incorrect assumption.** The guard was left out, the safer version was
built, and **the disagreement was reported rather than silently resolved in either
direction** — not quietly dropped to satisfy the brief, and not quietly included
to satisfy the document.

**What this leaves.** The hazard the guard was meant to address is **still
contained**, by the fallback itself: such an order is forgiven once and escalates
on a second run, which is the correct and safe outcome. What changed is narrower
than it sounds — **the branch's precondition is now assumed rather than explicitly
asserted on the Binance side, exactly as it was before this fix.** Nothing
regressed; a latent nicety was declined.

**This remains a genuinely open design question, left open deliberately.** It is
NOT resolved by this entry, and it should not be read as resolved by the fact that
the guard is absent.

## PART 4 — THE BONUS FIX: A REAL, SEPARATE, CURRENTLY-LIVE DEFECT

The fabricated timestamp did not only disable the reconciliation tolerance. It was
also **written to disk**.

`#foldTerminalState` stamps the closed local record with `remote.updatedAt`, and
`#mirrorOrderUpdate` writes that into **`orders.updated_at` in D1**, where the
dashboard reads it. So while the parser fabricated, **every Gemini order the poll
closed after an exchange-side cancel or expiry permanently recorded its CREATION
time as its LAST-UPDATE time.**

**The concrete shape:** an order that rested for five minutes and was then
cancelled on the exchange would claim it last changed at the moment it was placed.

This is a **separate defect from the tolerance** — same root cause, different
surface, different blast radius — and it is fixed as a natural consequence of
removing the fabrication: the call site now reads `remote.updatedAt ?? this.#now()`,
and receipt time is the honest value for a LOCAL record's *"when this bot recorded
the order closed."*

Bounded honestly: it never affected filled orders (`applyFill` uses the real
`fill.executedAt`) nor locally-issued cancellations (`parseCancelledOrder` stamps
receipt time). It affected exactly the exchange-side cancel/expiry fold.

**Proven in BOTH directions, deliberately:**

- `dates a fold to RECEIPT time when the venue reports no last-update time` —
  the venue's clock stays at placement time while the object's own clock advances
  five minutes; the row must read the later value, and asserts
  `.not.toBe(T0)` explicitly against the fabricated one.
- `still prefers the venue's own last-update time when it reports one` — a venue
  that DOES report a transition time is still believed, and the object's clock does
  not overwrite it. **This second test is the one that matters for the long run:**
  without it, the fallback could quietly become the default for every venue and no
  test would notice.

A note on the second call site: `#recordCancellation` had taken a `now` parameter
and discarded it (`void now;`) since it was written. That parameter now does the
job it was evidently reserved for. In practice its fallback does not fire on
either venue today, because both cancellation parsers supply a real instant — which
is precisely why it is written as a fallback and not a replacement.

1. `PINS THE BUG: a fabricated updatedAt halts on the first sighting, with no forgiveness`

   **It deliberately still passes after the fix**: it pins the MECHANISM being

3. `DOES halt once the same terminated disagreement survives a second run` — the

6. `BINANCE IS UNAFFECTED: a real updateTime keeps both halves of its window` —
   both halves in ONE body, deliberately, so a future edit cannot satisfy half of
   it: inside the window still `order_recently_terminated`/minor on the first run;
   outside it still `order_state_drift`/meaningful/halted on the first run; and
   neither half emits `order_drift_unconfirmed`.

**Bot instance (2)** — the two D1 tests named in Part 4.

### Mutation testing: 3 mutants, 3 killed

**M1 — reintroduce the Gemini fabrication** (`updatedAt: createdAt` restored).
**Killed by 2 tests**, and **both were parser-level**. The reconciliation tests did
NOT catch it.

*That is correct layering rather than a gap, and it is worth stating plainly:* the
reconciliation tests drive `FakeExchange`, not the real Gemini parser, so they
cannot see a parser regression; the parser tests never reach reconciliation, so
they cannot see a branch regression. **Neither layer's tests alone would have
caught this bug** — it lived precisely in the seam between a parser that fabricated
and a consumer that trusted. Both layers were needed, and this mutant is the proof.

**M2 — disable the presence check entirely**, so every venue takes the fallback.
**Killed by 5 tests** — and **three of them PRE-EXISTING**: `treats an order that
left the book inside the timing window as a late fill`, `does NOT treat the same
order as minor once it is outside the window`, and entry 61's own `leaves the
TERMINATED-order branch exactly as it was`. Plus the two new ones. **Meaning this
mutant breaks currently-working behaviour, not merely new behaviour** — which is
exactly the regression the "Binance completely unaffected" requirement exists to
prevent, caught by tests that predate this session.

*(The brief anticipated two pre-existing tests here. The measured figure is three;
the measured figure is what is recorded.)*

**M3 — substitute receipt time for an absent `updatedAt`** (`at - (status.updatedAt ?? at)`),
i.e. the previously-rejected **"always applies"** failure mode, reintroduced
deliberately. **Killed by 3 tests**, including the escalation test — so the mode
that silences real drift forever cannot be reintroduced silently.

### The test-infrastructure prerequisite

`FakeExchange` set `updatedAt` unconditionally on every response, so it could model
only a venue that reports one. **The entire Gemini defect was inexpressible in the
suite**: every test that believed it was exercising the terminated-order tolerance
was exercising the Binance path. `reportsUpdateTime` (defaulting `true`, so no
existing test changed) had to exist before any of Part 5's Gemini tests could be
written.

It deliberately does **not** reach `cancelOrder`, and that asymmetry is fidelity
rather than laziness: Gemini has no last-update time on order-status but DOES have
one on a cancellation (receipt time), so a blunt switch would model a venue that
does not exist — and would let `#recordCancellation`'s fallback be "covered" by a
case it can never encounter.

## PART 6 — NOT DONE / NOT VERIFIED

- **This fix has NOT been exercised live.** No deploy, no `wrangler` command, no
  HTTP call, and **no real Gemini order has been observed going through this path**
  — not on testnet, not in production. Every result above is against test fixtures
  and the fake exchange. The live half is the operator's, as always.
- **The Binance-unification question is OPEN and is NOT decided here.** Whether to
  retire the 60-second window on Binance too, in favour of the same run-to-run
  mechanism universally, is left exactly as open as the design document left it.
  The design document's own view — that the run-to-run mechanism is the better
  design on every venue and that Binance's real `updateTime` is "an accident that
  happened to work" — is recorded there and is neither endorsed nor rejected by
  this entry.
- **The missing §4 guard remains an open design question on the Binance side
  specifically.** Not resolved. The branch's precondition is assumed rather than
  asserted there, exactly as it was before this fix.
- **Binance's own latent fabrication is untouched.** `binance/parse.ts` still falls
  back to `createdAt` when `updateTime` is absent — the same class of fabrication,
  on a branch never observed to fire. The design document flagged the honest form;
  changing it would touch a working venue and was out of scope.
- **`order_recently_terminated` is now unreachable on a clockless venue.** Deciding
  that an order left the book RECENTLY is exactly the judgement such a venue cannot
  support. Nothing is lost behaviourally — the kind is minor, raises no alert row
  and halts nothing — but the audit content for Gemini changes, and that is stated
  rather than left to be discovered.
