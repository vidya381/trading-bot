## PART 1 — ⚠ THE SENTENCE IN THE RECORD THIS STEP APPEARS TO CONTRADICT

Stated first, because a future reader will find entry 45's sentence and this

Spec 21.1 permits exactly one shape here and forbids the other, in its own words:
the only way a proposal becomes a bot is *"a human reading it and filling in **(or

unchanged and unweakened."* The parenthesis is this step. The rest of that

Entry 45's sentence remains **true and unweakened**, and the distinction is
mechanical rather than a matter of emphasis:

| | forbidden, and still is | what this step does |
| --- | --- | --- |
| who reads the proposal record | `POST /api/bots` reads the row and takes parameters out of it | nothing reads it; the backend still reads it **only** to check the row can take an outcome |
| where the values come from | a stored row the human never saw | the values already rendered on the human's screen, carried browser-side |

The mechanical statement of that: **`api.test.ts`'s test that submits a body
deliberately DISAGREEING with the proposal and asserts the bot gets the BODY's

to the server, so it still cannot supply a wrong one.

### THE PREFILL MECHANISM: URL SEARCH PARAMS. Router state was the other real candidate and lost.

`/bots/new?proposalId=…&strategy=grid&lowerBound=…&freshness=candles:…:900000,…`

Four reasons, in weight order:

1. **IT IS THE ONLY CROSS-ROUTE DATA PATTERN THIS DASHBOARD ALREADY HAS.**
   `pages/Alerts.tsx` puts its filters in `useSearchParams` and documents why.
   Nothing in `dashboard/src` uses `location.state` for anything. Inventing a
   second convention for the one screen that commits capital is the wrong place to
   be novel.
2. **IT IS VISIBLE.** A prefill in router state is invisible to the human it is
   handed to; the same prefill in the address bar can be read, checked against the
   proposal page, and pasted into a message. For a feature whose entire design
   principle is *"no hidden bridge from a proposal to a creation"*, an invisible
   transport is the wrong default.
3. **THE BANNER AND THE VALUES ARRIVE TOGETHER OR NOT AT ALL.**
   `readProposalPrefill` returns `null` unless a real `proposalId` **and** a
   recognised `strategy` are both present, so **no URL anyone can construct
   produces prefilled numbers with nothing on screen saying where they came from.**
   That is structural, not a rule each caller must remember. Router state would
   have the property only by accident of it all being one object.
4. It survives a reload, a new tab and a copy-paste, and when something IS missing
   the failure mode is an ordinary blank form.

⚠ **THE COST, STATED RATHER THAN LEFT TO BE FOUND: the URL is a snapshot of the
PROPOSAL's values and is never rewritten as the human edits.** A reload therefore
restores the proposal's numbers and discards edits — the same thing a reload of a
half-typed manual form does. Syncing edits back was considered and refused: it
would make the address bar claim to be the proposal's parameters while actually
holding a human's revisions, which is the one thing the banner must never be wrong
about.

### IT IS THE SAME COMPONENT, AND THERE IS NO SECOND ANYTHING

`/bots/new` mounts `pages/CreateBot.tsx` for a manual creation and for a prefilled
one. **There is no `mode` prop, no variant, no second route, and no branch anywhere
in the form on "did this come from a proposal"** — `App.tsx` was not touched.

What arrives is **different default values for `useState` calls**, read once at
mount and never again. From the first render the form holds ordinary state:
`validate()` is unchanged and unaware, every input has the same `onChange`, and
`buildRequest` reads the same variables it always read. **Editing a pre-filled
field and editing a hand-typed one are the same operation**, which is decision log
46's third constraint — *"a prefill a human cannot overrule is a proposal supplying
a value"*.

Three small real changes were needed to make a pre-filled form honest rather than
merely populated, and each is a fix to something that would otherwise have looked
broken:

- **The pair combobox now starts its search text at the committed value.** It was
  `useState("")`, which for a prefilled pair would have shown an empty box over a
  hidden committed value. For a manual creation `value` is `""` and the behaviour
  is byte-identical.
- **A prefilled account is reconciled against the registry once it loads.** Still
  registered → the read-only exchange is filled in from the same response the
  dropdown reads. **No longer registered → it is cleared with a field error**,
  because leaving it would put a value in the `<select>` that has no `<option>` —
  a wrong account displayed on the screen that commits capital.
- **`proposalLink.recorded: false` is handled.** See PART 5.

### THE AI-SOURCED BANNER (decision log 46's fourth constraint)

*"A visible AI-sourced banner is required on the form when it has been prefilled,
so nobody reviews model output believing they typed it."* Above the form, not
beside a field, because it is a fact about every box below it.

It states: **that these are model output and the human did not type them**; **which
proposal**, by real `proposalId`; **when the proposal was made**; **the staleness
verdict, computed now**; **anything the link could not carry**; and **that nothing
is recorded by arriving**. Two further lines appear only when they are true — a
strategy-toggle mismatch, and a value this form has no control for.

⚠ **`generatedAt` IS `selectedAt`, AND IS LABELLED AS WHAT IT IS.** The response
carries no "the proposal record was created at" field. `selectedAt` is when the
derive request resolved the pair to a candidate — the start of the call that
produced the proposal — and the banner says so in words: *"when the derive request
started (`selectedAt`) — not a data fetch time"*. That keeps `proposal.ts`'s
existing `FetchTimestamp` / `AssemblyTimestamp` distinction rather than printing
one confident timestamp.

## PART 3 — ⚠ THE STALENESS VERDICT IS RECOMPUTED AT RENDER, NOT CARRIED

**This is the part of the step most likely to be got wrong, and the failure would
be invisible.** It was traced through source line by line and then proved by
mutation, because "it recomputes" is exactly the kind of claim that reads as true
whether or not it is.

### Why a carried verdict would be actively misleading

Entry 45 measured, live and unstaged, a **`pendingMs` of 28,013,070 — 7 hours 46
minutes 53 seconds** between a real proposal and the human decision on it. A banner
displaying a verdict computed when `/derive` ran would say **"fresh"** to that
human — correctly, about a moment nearly eight hours gone — on the screen where
capital is committed, long after the price window behind every bound stopped being
current. **A grid proposal's price threshold is 15 minutes.**

### The real mechanism, traced

| link | what the source actually does |
| --- | --- |
| the URL | `` `${input.key}:${input.at}:${input.thresholdMs}` `` — **raw fetch timestamps and thresholds. No verdict.** Grepping the module for `"fresh"`/`"stale"`/`"unknown"` as values returns nothing. |
| `ProposalPrefill` | carries `stalenessInputs: readonly StalenessInput[]`. **No `verdict`, no `isStale`, no `computedAt` field exists to be stale.** |
| the banner | `const [now, setNow] = useState(() => Date.now())` plus a **1-second `setInterval`**, then `prefillStaleness(prefill, now)`. |
| the comparison | `stalenessOf` → `verdictFor`: `ageMs = now - input.at`, `verdict = ageMs > thresholdMs ? "stale" : "fresh"`. **The backend's own function, imported, not copied.** |

So the question *"was this stale when generated?"* is never asked or stored. The
only question ever asked is *"how old is this data right now?"*, asked afresh every
second the form is open.

### WHY THE FETCH TIMES TRAVEL AND THE VERDICT DOES NOT

Carrying the verdict would satisfy a literal reading of "the staleness flag must
carry over" and be **strictly worse**. The verdict is a function of time, and the
gap between generation and approval is the entire subject of 21.5 requirement 4:

- a proposal flagged stale on the proposal page is **necessarily** stale here —
  ages only increase, and the thresholds arrive with the data;
- a proposal that was fresh when the link was pressed and **goes stale while the
  human fills in the form** is flagged here, which a carried word could not do —
  and that is the case entry 45 observed for real, a control file re-flagged
  unprompted as the clock caught up;
- **the four inputs answer to four different thresholds at one instant** (15 min /
  1 h / 24 h / 7 days), so a single carried word could not have been right even if
  it were recomputed.

⚠ **AND A STRIPPED PARAMETER CANNOT LAUNDER A STALE PROPOSAL.** Deleting
`freshness` from the URL yields an empty input set, and `worstVerdict` answers
**`unknown`, never `fresh`**, for an empty set. Fail closed.

⚠ **THE THRESHOLD PAIRING IS CARRIED, NOT RE-DERIVED.** `freshnessOf` builds the
`{key, at, thresholdMs}` triples from the same four objects the ages come from, and
its docblock says why: *"a component that paired them itself could pair the capital
ledger's age against the price window's threshold and look entirely correct."* The
price threshold is per-strategy, so a create-bot page that looked it up again would
be a second place that lookup can be wrong.

⚠ **IT IS NOT A GATE, AND MUST NEVER BECOME ONE.** The verdict flags and instructs.
It disables nothing and refuses no submit. The binding checks are the server's and
run unchanged whatever colour the banner is.

⚠ **THE CLOCK IS THE BROWSER'S.** A negative age is treated as **fresh**, not as an
error — ordinary Worker/browser skew, and treating the future as stale would flag a
proposal made seconds ago on a machine a second behind. A badly wrong browser clock
would misjudge ages; that is inherent to rendering an age client-side and is the
same exposure `ProposalFreshness` has carried since step 45.

## PART 4 — THE OUTCOME LINK: STEP 45'S FIELD, REUSED UNCHANGED

**No new endpoint, no new backend code, no new safety mechanism.** `proposalId` on
`POST /api/bots` is entry 45's, live-verified there, and it is used exactly as
built: `checkProposalCanTakeOutcome` with the free checks before anything exists,
`recordProposalApproval` after `create` returns, `proposalLink` on the 201.

The dashboard's entire contribution is one function:

```ts
export function withProposalId<T extends object>(request: T, proposalId: string | null)
```

⚠ **ABSENT, NOT NULL, when there is no proposal.** `POST /api/bots` reads the field
with `optionalString`, and entry 45's whole response-shape design turns on an
ordinary creation being byte-identical to what it was before the field existed. A
body carrying `proposalId: null` is a **different request** from one carrying no
`proposalId`.

It is called from the submit handler and **from nowhere else**, which is the whole
of the guarantee on this side and is enforced mechanically (PART 6).

## PART 5 — A BRANCH THIS STEP MADE REACHABLE FOR THE FIRST TIME

Entry 45 built a deliberate soft failure: if the outcome write fails **after**
`create` returns, the endpoint still answers 201 with `proposalLink.recorded:
false` and the real error, because failing the response would tell an operator that
creation failed when it did not, and the recovery they would attempt — creating it
again — is the worst available action.

**Until this step that branch was unreachable from the dashboard, because the form
never sent a `proposalId`.** Sending one makes it reachable, so it is handled
rather than swallowed: the form **does not navigate away**, states that the bot
exists and must not be submitted again, names the proposal whose link is missing,
prints the server's own error, links to the real bot, and **removes the submit
control entirely** so the repeat action is not on the screen.

Recorded because it is the one piece of new UI whose trigger no test in this
repository can produce, and because wiring a field without handling its documented
failure mode would have weakened a mechanism this step claims to reuse unchanged.

## PART 6 — THE NAVIGATION-DOES-NOT-APPROVE GUARANTEE

**The guarantee this whole step is judged on**, and the one no typecheck can see.

### What is actually being proved, stated narrowly

`proposals.outcome` moves off NULL in exactly two places in this system:
`recordProposalApproval`, reached only from `POST /api/bots` and only after
`create` has returned a real bot, and `rejectProposal`, reached only from
`POST /api/proposals/:id/reject`. **Neither is reachable by rendering a page or
following a link.** So from the dashboard's side the complete list of ways this
breaks is (1) something sends `proposalId` outside a real submission, or (2) the
navigation path acquires the ability to make a state-changing request at all.

### Three independent verifications

**1. A real end-to-end test against real D1** (`api.test.ts`, in the property-5
block that already owns this ground). Real `/assess`, real `/derive`, build the
link from the real response, decode it — the complete set of code the dashboard
executes between reading a proposal and looking at a filled-in form — then assert
against **the real row**: all four outcome columns null, zero bot rows,
`total_allocated` still `0.00000000`, and the audit actions containing no
`proposal.approved`, `proposal.rejected` or `bot.created`. **A real check on real
state, not a restatement of the test's own setup.**

**2. A source-level guard**, 11 assertions, because the dashboard still has no
component-test harness (no jsdom, no testing-library; `react-dom/server` fails its
CJS requires in the Workers pool, so a test importing a `.tsx` collects **zero
tests rather than failing**). Same pattern as `no-raw-d1.test.ts` and entry 47's
`single-kill-switch-poll.test.ts`. It pins: `createBot` called in exactly one place
in the whole dashboard; that call is `createBot(withProposalId(…))`;
`withProposalId` called exactly once and only in the form; **no file on the
navigation path imports `api/client` or names any of the twelve write endpoints**;
the prefill module contains no `fetch`/XHR/`sendBeacon`/WebSocket/EventSource; and
the create call sits below every `useEffect` in the form.

**3. ⚠ THE GUARD WAS PROVEN TO FAIL.** Entry 47's rule: *a guard never seen to fail

| violation | assertions that fired |
| --- | --- |
| G1 the link component imports `api/client` and calls `createBot` | **3** |
| G2 the form attaches `proposalId` itself, bypassing `withProposalId` | **3** |
| G3 an effect below the submit handler reaches the create call | **1** |
| G4 the grid body reads the DCA stop-loss box | **1** |

⚠ **WHAT NONE OF THIS PROVES: that no request leaves the browser on mount.** Only a

## PART 7 — ⚠ A REPORTED FIXTURE BUG WHOSE PREMISE DID NOT EXIST

**Recorded plainly, and at length, for the reason entry 47 recorded its own: so a
future reader does not inherit a wrong framing from a brief.**

The brief for this entry described a bug found during this step's development: *a
DCA test fixture carrying `takeProfitPct: null` that passed despite the real
decoder requiring it non-nullable, meaning the DCA field-mapping path had been
verified against a constraint it did not actually meet.* It asked for that to be
written up as the Nth instance of a test passing for the wrong reason.

**It was checked at four levels before any of it was written. There is no such
fixture and there never was.**

| checked | finding |
| --- | --- |
| this step's DCA fixture | `takeProfitPct: "2.00000000"` — a non-null decimal string, from the first version |
| `grep takeProfitPct` + null across `src/` and `dashboard/` | four hits, **none of them a DCA proposal fixture**: `capital/ledger.ts` and `serialize.ts` are the stored bot ROW's nullable column, `bot-instance.ts:1284` writes null for a **grid** bot, `api/types.ts:118` is that same row |
| `DcaParams` (`api/research-types.ts`) | already `readonly takeProfitPct: string` — non-nullable, and it agrees with the decoder |
| `decodeDcaParams` (`src/strategies/dca.ts`) | `takeProfitPct: money("takeProfitPct")` — non-nullable |

**No test was passing for the wrong reason, nothing was fixed, and this is not
another instance of that pattern.** Claiming it would have put a fabricated finding
into a permanent, undeletable record — which is a worse fault than the one it
describes.

### ⚠ BUT THE INVESTIGATION FOUND SOMETHING REAL, AND IT IS KEPT

Checking the claim meant asking what would *actually* happen to a DCA proposal
carrying `takeProfitPct: null`. **Run as a probe rather than reasoned about**, and
the answer is a genuine asymmetry that was previously covered only by accident:

**`checkParamsShape` ACCEPTS `takeProfitPct: null` for DCA.** Its rule is "null is
PRESENT, undefined is MISSING" — correct for grid, whose `takeProfitAmount` and
`breakoutThresholdPct` are genuinely optional and are emitted as null when unset
(entry 45 PART 5). **DCA has no such field.** Spec 6.1/6.3 make `takeProfitPct`
mandatory because it defines the cycle's exit, and `decodeDcaParams` reads it
non-nullable. So the shape check is **strictly more permissive than the DCA decoder
for that one field.**

**That is not a hole in this feature, and a test now says so rather than leaving it
to be assumed.** The null encodes to `""`, `text()` reports it as `incomplete`
rather than substituting anything, the banner names it, and the form's own
`requirePercentPositive` refuses to submit with "Required." **It fails closed at
three layers.** Pinned by a test whose docblock records where it came from.

⚠ **AND THE REAL DCA GAP IS UNTOUCHED BY ANY OF THIS.** It predates this step and
this step does not narrow it: **DCA has still never been exercised by a real live
model call.** Every live derivation this project has produced is grid — entry
41's two, entry 42's one, entry 44's render, entry 45's, entry 46's, and whatever
the operator ran for this one. The DCA fixture here is **synthetic and is labelled
as such in the test file's header**, exactly as entry 45 labelled its own in three
places. It pins the mapping and the field lists. **It is explicitly not a claim
that the DCA path works end to end.** Closing that needs a real Derive call that
happens to answer `dca` — not a hand-built object, and not a grid response with its
label edited.

### ⚠ F10 IS AN EQUIVALENT MUTANT AND IS RECORDED AS ONE, NOT AS A CATCH

### ⚠ THE BUTTON IS AT THE BOTTOM, AFTER THE FULL EVIDENCE DUMP — the summary card is its own step

The link sits in `ProposalView`'s footer, **last, after the concentration flag, the
data limits, the freshness verdict, the reasoning, the parameters and the entire
evidence table.** That position is deliberate for now — it is after everything a
reviewer is meant to have read, which is the same argument `ProposalView` makes for
putting the concentration banner first — **but it is not the final answer, and the
proposal page is long.** Entry 46 recorded the operator raising exactly this within
minutes of the feature's first real use, and recorded why it is not trivial: entry
44 made the page long **on purpose**, listing every evidence item cited or not,
nothing behind a collapsed toggle, because *what the model ignored is visible only
from the difference.* **A summary card is in tension with that decision, not merely
additional to it**, and reconciling them is the work.

deferred to its own step. It is not forgotten and it is not this step's scope** —
which is why `ProposalCreateBotLink` is a self-contained component whose header

### ⚠ A PREFILLED FORM MAKES NO PROPOSAL BETTER

Carried forward from entries 40, 41, 42, 44, 45 and 46 **without dilution**, because
the step that finally makes a feature convenient is exactly when it is most likely
to be lost — and this step is the most convenient thing this feature has ever had.

**Making a proposal easier to act on does not make it worth acting on.** Every
check behind this flow still answers *"is this internally consistent, currently
grounded, and acceptable to the real create-bot validators?"* **Not one answers
*"was the data worth reasoning about?"*** A fresh staleness verdict says the data
is recent; it does not say the reasoning over it was sound. A form that opens
pre-filled says the numbers arrived intact; it does not say they were good numbers.

**And the economics moved again, in the direction that makes the warning matter
more.** Entry 46 observed that obtaining a proposal went from two `curl` commands
and a `jq` projection to one button. This step takes acting on one from
hand-transcribing nine parameters into a form to pressing a link and pressing
Create. **The friction that was doing part of the reviewing job is now gone from
both halves.** The human in 21.1 is still the only part of this loop that can tell
a well-grounded proposal from a good one, and everything this step removed was
friction rather than judgement.
