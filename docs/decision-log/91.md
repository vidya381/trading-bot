## PART 1 — WHAT WAS BUILT

Three files, in dependency order, each committed only once its own tests passed
against real data.

**`signing.ts` (367 lines, 36 tests).** Kraken's authentication:

```
API-Sign = base64( HMAC-SHA512( uriPath + SHA256(nonce + body),
                                base64_decode(apiSecret) ) )
```

The load-bearing detail is `base64_decode`. Binance and Gemini both
`TextEncoder().encode()` the secret's characters; Kraken's secret is base64 of a
**64-byte** key and must be decoded to those bytes first. Copying either existing
signer produces a perfectly well-formed base64 HMAC-SHA512 that Kraken answers
with a bare `EAPI:Invalid signature` and no hint as to which of the four steps
was wrong — so that specific wrong answer is pinned as a **negative** assertion
(`DOC_SIGNATURE_IF_SECRET_NOT_DECODED`), because "not equal to the documented
signature" is too weak a statement to catch a regression to the Binance idiom.
`NonceGenerator` is re-exported from the Gemini signer unchanged, per entry 90's
finding that the nonce contracts match; section 4.2's `ClockOffset` machinery has
no role.

**`catalogue.ts` (626 lines, 45 tests).** No Binance or Gemini analogue. Kraken
names one market four ways — canonical key `XXBTZUSD`, altname `XBTUSD`, wsname
`XBT/USD`, and this codebase's ticker `BTCUSD` — and only one is a name a request
may carry while a different one keys every reply. Four indexes built from
`/0/public/AssetPairs` and `/0/public/Assets` and nothing else, with collisions
**reported** rather than resolved: a name two different pairs claim resolves to
`undefined` and is listed in `ambiguousPairNames`, because picking a winner by
precedence would be a guess about which market to trade.

**`filters.ts` (426 lines, 46 tests).** AssetPairs → `SymbolFilters`. It reads
`KrakenPair.raw`, the unmodified AssetPairs entry the catalogue already holds, so
**nothing here fetches**: pulling that 1.1MB document a second time would cost
little but risk a catalogue that can name a pair whose filters disagree with it.
`validateOrder` and `SymbolFilterCache` are re-exported from `binance/filters`
exactly as `gemini/filters.ts` does it — one implementation, not a copy.

## PART 2 — THE SIGNING CORRECTION, AND THE LESSON THAT GENERALISES

**The worked example supplied in the build prompt was wrong.** A secret, a nonce
and an expected signature were handed over as Kraken's published example. They
were not. **The secret in particular did not match Kraken's real published
example**, and a signature expectation built on it would have been a test that
passed while the signer was wrong — or, worse, a signer bent until it reproduced
a value Kraken has never published.

It was caught **before any code was written around it**. The correction was
established two independent ways:

1. Against Kraken's real documentation, which publishes exactly one worked
   example — secret
   `kQH5HW/8p1uGOVjbgWA7FunAmGO8lsSUXNsu3eow76sz84Q18fWxnyRzBHCd3pd5nE9qa99HAZtuZuj6F1huXg==`,
   nonce `1616492376594`, path `/0/private/AddOrder`, and the signature now
   pinned as `DOC_SIGNATURE`.
2. By **manual reproduction with `openssl`**, outside this module entirely:

   ```
   KEYHEX=$(printf '%s' "$SECRET" | base64 -d | xxd -p | tr -d '\n')
   { printf '%s' "$PATH"; printf '%s%s' "$NONCE" "$BODY" | openssl dgst -sha256 -binary; } \
     | openssl dgst -sha512 -mac HMAC -macopt "hexkey:$KEYHEX" -binary | base64
   ```

That second tool is also what generated the three **independent** vectors
(`V2`–`V4`) over a second secret, so the documented vector is not load-bearing
alone: one signature could in principle be reproduced by a coincidence of path
and body, four cannot. `V4` reuses `V2`'s nonce and body under a different path,
pinning that the path is genuinely part of the signed message.

**THE GENERAL LESSON, and it is the most portable thing in this entry:** *treat
any "documented example", exact hash, magic constant or expected value handed
over in a prompt as a **claim to verify**, not a fact to build on.* A wrong
example is more dangerous than a missing one, because a missing example forces a
lookup while a wrong one invites a test written around it. The failure mode is
specific and silent: **the test suite goes green and the venue rejects every
request in production.** This applies with the same force to values this session
itself produces from memory — which is what happened here, and the reason the
`openssl` reproduction exists as a documented procedure rather than as a one-off
check.

## PART 3 — A THIRD CORRUPTION CASE THE RESEARCH DID NOT NAME

Entry 90 PROBLEM 1 rejected a `BTC` → `XBT` string substitution and named two
live pairs it would corrupt:

| Pair | Substitution produces | Exists? |
| --- | --- | --- |
| `WBTCUSD` (Wrapped BTC) | `WXBTUSD` | **No** |
| `TBTCUSD` (tBTC) | `TXBTUSD` | **No** |

Live testing against the **full 1440-pair / 839-asset catalogue** found a
**third case entry 90 did not anticipate**, and it fails in the opposite
direction:

| Pair | REVERSE substitution produces | Exists? |
| --- | --- | --- |
| `AIXBTUSD` (AIXBT) | `AIBTCUSD` | **No** |

All four non-existence facts are verified against the live catalogue, not
reasoned about.

**Why entry 90 missed it.** It reasoned only about the **forward** direction —
rewriting this system's `BTC` into Kraken's `XBT` — and every counterexample it
looked for was a pair whose base asset *contains* `BTC`. `AIXBT` contains `XBT`,
so it is invisible to that search and only breaks on the **reverse** mapping,
which the client also needs: every reply is keyed by a Kraken name that has to
come back to a ticker. A codebase that had passed entry 90's two named cases
would still have turned the live `AIXBTUSD` into a market that does not exist,
and the failure would have arrived as `EQuery:Unknown asset pair` naming nothing.

**This is the finding that makes the catalogue approach right rather than merely
cautious.** The argument for a lookup was previously "a substitution has two
known counterexamples, so be careful". It is now "**a substitution has
counterexamples in both directions, and the research effort that specifically
went looking for them found only two of the three**". The third was found by
running real data through real code, which is the only method that would have
found it. `KRAKEN_ASSET_TICKER_ALIASES` is keyed by **whole asset code, matched
whole, never as a substring** — which is precisely why `WBTC`, `TBTC` and `AIXBT`
all pass through it untouched.

## PART 4 — DECISION: SUFFIXED ASSETS ARE THEIR OWN ASSETS

Kraken lists **44 suffixed asset codes** (live count, all 839 assets checked):
27 `.S` (staked, e.g. `DOT.S`), 7 `.HOLD`, 5 `.M` (bonded/earn, e.g. `XBT.M`), 2
`.P`, and one each of `.INK`, `.CORE`, `.TEMPO`.

**DECIDED: each is a distinct asset that resolves to itself. `XBT.M` is not
`XBT`, so it is not `BTC`.** The alias table is not applied to it, and
`normaliseAssetName` deliberately **keeps** the `.` that `normalisePairName`
strips — on the asset side the dot is load-bearing, and collapsing `DOT.S` onto
`DOTS` would invite the reading that it is `DOT`.

**The reasoning is a wrong number, not a naming preference.** A staked or bonded
balance **is not freely tradeable the way a spot holding is**. Aliasing `XBT.M`
to `BTC` would make an earn balance indistinguishable from spot BTC in every
balance read — so the system would believe locked funds were available to trade,
size an order against them, and have it rejected for insufficient funds against a
balance this code reported as present. That is exactly the class of failure
section 9's reconciliation exists to **catch**, and this module has no business
manufacturing it upstream of the check.

**Recorded as a deliberate decision, not a default.** Resolving each suffixed
code to itself is also what falls out of doing nothing, which is exactly why it
is written down: the next session to look at `XBT.M` sitting unaliased next to
`XBT` should find a reason here, not an apparent oversight to "fix".

## PART 5 — DECISION: 45 REAL COINS DO NOT FIT IN `Money`, AND ARE COARSENED RATHER THAN REFUSED

This is the entry's one genuine design decision, and it was not anticipated by
entry 90.

### The collision

`Money` carries **`SCALE = 8`** decimal places, and `fromDecimalString` throws on
more — by design, so no monetary value is ever silently rounded. Entry 90's
mapping table says `tick_size` → `tickSize`, read directly, authoritative.

Both statements are correct, and together they refuse **45 of 1440 live pairs**:

| `tick_size` decimals | Pairs | Fits `Money`? |
| --- | --- | --- |
| 0–7 | 1,370 | yes |
| 8 | 25 | yes, exactly at the scale |
| **9** | **29** | **no** |
| **10** | **16** | **no** |

These are not obscure listings. **`BONKUSD` publishes `"0.000000001"`** and is a
real, actively-traded coin; `ANKRXBT` publishes `"0.0000000001"`. Read strictly,
45 tradeable markets become unreadable — and the failure would not have appeared
until a bot was pointed at one.

### The decision

**DECIDED: coarsen to `1e-8` when the published tick is a power of ten finer than
that. Throw a `FilterError` when a finer tick is *not* a power of ten.**

**The coarsening is mathematically sound, not a tolerated approximation.** Every
multiple of `1e-8` is also a multiple of any finer power of ten, so every price
this system can produce on the coarsened grid **is a price Kraken accepts,
exactly**. Nothing becomes invalid. The only thing lost is the ability to name
the sub-`1e-8` prices between the grid points — which `Money` cannot represent
under *any* policy, so no policy could have preserved them.

The premise was **verified against all 1440 live pairs, not assumed**: every
published `tick_size` is an exact power of ten (`1`, `0.1`, … `0.0000000001`, nine
distinct values, no exceptions). The power-of-ten check is therefore not
decoration guarding an impossible case — it is the guard on the fact the
soundness argument **depends on**, and it is what makes the argument checkable
rather than assumed. A finer tick that is not a power of ten (say `2.5e-9`) has
no such guarantee: `1e-8` is not a multiple of it, so coarsening would put every
price off the venue's grid while this code reported them as on it. **That case
does not occur today and is handled rather than assumed impossible** — the arm
throws, naming the pair and the value.

### The rejected alternative, and why

**Refuse all 45 outright**, mirroring `gemini/filters.ts`'s `incrementToMoney`,
which throws rather than round its own increments. Simpler, more conservative in
posture, and consistent with an existing file.

**Rejected.** It would make real, currently-tradeable coins permanently
inaccessible **for no safety benefit whatsoever**, because the coarsening is not
a guess about what Kraken would accept — it is a proof, resting on a property
verified across the whole venue. Conservatism that buys nothing is not
conservatism; it is a functional regression wearing its clothes. Gemini's
refusal is right *for Gemini*, whose case is a float increment finer than the
scale with no power-of-ten guarantee available to check.

**Mapping to `ZERO` was never a candidate** and is recorded to rule it out:
`ZERO` means "grid disabled" under the shared `SymbolFilters` convention, so it
would send unrounded prices straight through the one check meant to catch them.
That is the **fail-open** direction, and it is the trap `DISABLED` semantics set
for anyone reaching for a "just skip it" value.

**Verified end to end.** All 1440 live pairs parse with **zero omissions**; no
pair receives a `ZERO` tick or step; the 70 pairs landing on a `1e-8` tick
decompose as 25 genuine 8-decimal ticks plus the 45 coarsened ones.

## PART 6 — THE BUG THE TESTS CAUGHT, AND WHY INSPECTION WOULD NOT HAVE

The first implementation of the power-of-ten check stripped **trailing** zeros
from the fraction but not **leading** ones, then compared against `"1"`:

```ts
const fraction = value.slice(dot + 1).replace(/0+$/, "");   // WRONG
return whole === "" && fraction === "1";
```

For `"0.000000001"` the fraction is `"000000001"`, which ends in `1`, so nothing
is stripped and the comparison is `"000000001" === "1"` — **false**. Every one of
the 45 pairs the rule exists to admit hit the refusal branch instead.

**The rule's effect was exactly inverted.** Not degraded, not partially broken:
the branch written to admit those 45 pairs rejected all 45, and the branch
written to reject unrepresentable ticks never ran. And it inverted **silently** —
the code threw a `FilterError` with an articulate, entirely wrong message
("is finer than the money scale ... and is not a power of ten") that read as
correct behaviour if you were not checking the specific pairs.

**Caught by a real test against real pairs, not by reading the code.** Six tests
failed at once, including `coarsens a 9dp tick onto the finest representable grid
(BONKUSD)`. Inspection had already passed over that line twice.

**THE GENERAL LESSON:** *an off-by-symmetry bug in a numeric string comparison
can invert a rule's intended effect entirely, not merely weaken it.* Decimal
strings have two ends and the two are not interchangeable — trailing zeros are
insignificant, leading zeros are positional. Any predicate that strips one end
should be read twice for whether it also needs the other, and it should be tested
against a value where the two differ. `"0.1"` and `"0.000000001"` are both powers
of ten, and only the second one distinguishes a correct implementation from this
one — which is the argument for fixtures drawn from the real distribution rather
than from the easy end of it.

## PART 7 — `pair_decimals` IS DISPLAY PRECISION, AND ON FOUR PAIRS IT LIES ABOUT THE GRID

Kraken publishes both `pair_decimals` and `tick_size`. On **1,436 of 1,440**
pairs they agree — `tick_size` is exactly `10^-pair_decimals` — which is what
makes deriving the price grid from `pair_decimals` look safe. On **4 pairs they
do not**:

| Pair | `pair_decimals` | implies tick | real `tick_size` | Error |
| --- | --- | --- | --- | --- |
| `REQUSD` | 5 | `0.00001` | **`0.0001`** | 10× too fine |
| `CELRUSD` | 7 | `0.0000001` | **`0.000001`** | 10× too fine |
| `VTHOUSD` | 7 | `0.0000001` | **`0.000001`** | 10× too fine |
| `WINUSD` | 9 | `0.000000001` | **`0.00000001`** | 10× too fine |

The shortcut fails **only on these four**, and it fails in the direction that
produces rejected orders: a grid ten times finer than the venue's accepts prices
Kraken refuses. Worse, on `WINUSD` the `pair_decimals` reading is `1e-9` —
**below `Money`'s scale** — so the shortcut and PART 5's collision compound into
a pair that cannot be represented at all.

**A test was built specifically against the known-divergent pairs.** `REQUSD` and
`VTHOUSD` are in the fixtures, each asserting `tickSize` is the real value **and
explicitly `not` the `pair_decimals` one, so the assertion fails if the fields
are ever swapped** — plus an order-level test that a `REQUSD` price on the
`pair_decimals` grid is rejected `price_off_tick`, which states the consequence
as behaviour rather than as a field value.

**The point being recorded is about test selection, not about Kraken.** A fixture
set drawn from the majority — or sampled at random, where these four are a 0.3%
chance of appearing — would agree with the wrong implementation on every pair it
contained. **99.7% agreement between two fields is not evidence they are the same
field; it is the reason the difference is worth a targeted test.** Entry 90 had
already flagged `pair_decimals` as display-only from the documentation; this is
the live evidence, and the four names are written down so the next session can
test against them directly.

## PART 8 — DECISION: `post_only`, `limit_only` AND `reduce_only` ALL FAIL CLOSED TO `BREAK`

`SymbolStatus`'s real members are `TRADING | END_OF_DAY | HALT | BREAK |
CANCEL_ONLY`. Kraken publishes five pair states. The mapping:

| Kraken | → | Note |
| --- | --- | --- |
| `online` | `TRADING` | the only clean trading state |
| `cancel_only` | `CANCEL_ONLY` | the one exact member match |
| `post_only` | **`BREAK`** | **not `TRADING`** — see below |
| `limit_only` | **`BREAK`** | no live example (PART 8.2) |
| `reduce_only` | **`BREAK`** | no live example (PART 8.2) |
| anything else | **throws** | `FilterError` naming the value |

### 8.1 Why `post_only` is not `TRADING`, though Gemini's is

`gemini/filters.ts` maps its own `post_only` to `TRADING`, reasoning that the
resting ladder orders of sections 6.2/6.3 are makers and so are placeable.

**That reasoning is right about the ladder and wrong about the gate.**
`SymbolFilters.status` is checked by one `validateOrder` that every order path
shares, and **it sees a price and a quantity and cannot tell whether the order is
marketable**. Mapping `post_only` to `TRADING` would let a crossing order through
the one check whose entire purpose is to stop it, and the venue's rejection would
arrive only after the order had been constructed and sent.

**The accepted cost, recorded as a cost.** Three distinct Kraken states share
`BREAK`, so `validateOrder`'s rejection reads *"ARBUSD is BREAK, not TRADING"*
and **cannot say which Kraken state caused it**. That is a real loss of
diagnostic specificity in exactly the log line section 4.3 asks for. It is
accepted rather than overlooked: the alternative is widening a shared cross-venue
type to carry one venue's vocabulary, which is a larger change than this gate
justifies. Written down so a future session reading `BREAK` in a Kraken log knows
the ambiguity is deliberate and knows where the fix would go.

### 8.2 Two documented states with no live example

**`limit_only` and `reduce_only` appear on zero of the 1440 live pairs.** The
live distribution is `online` 1385, `cancel_only` 38, `post_only` 17, and nothing
else.

Both are still mapped **explicitly** rather than left to the `default` arm: a
state Kraken documents should be a decision, not an accident of an
unrecognised-value path. Their tests build the state by overriding `status` on a
real `ARBUSD` entry, and **say so at the point of use** — labelled *"CONSTRUCTED,
NOT PULLED"* — because a fixture that poses as pulled data teaches the wrong
shape to whoever reads it next. Every other fixture in the file is verbatim from
the live pull with one documented edit (the twelve-tier `fees` arrays dropped),
and that distinction is only worth anything if the exceptions are marked.

An unrecognised status **throws**, matching `parseStatus` on the Binance side and
`mapStatus` on Gemini's: a new Kraken state is one this code has never seen and
cannot judge. Guessing `TRADING` would trade a market on the strength of a word
nobody has read; quietly guessing untradable would leave a bot inexplicably idle.
The one place this leniency is inverted is `tradablePairs`, which **excludes** an
unmappable pair instead of throwing — there, omission *is* the fail-closed
direction, and one unrecognised listing must not refuse the answer to "which
markets are open".

## PART 9 — DECISION: `ordermin` AND `costmin` ROUND UP

These use `fromDecimalStringRounded(raw, "ceil")`, **not** the strict
`fromDecimalString`.

**Why ceiling is the fail-closed direction.** Both are **floors** — a minimum
order size and a minimum cost. A floor rounded **up** is *stricter* than the
venue's real minimum, so every order this code accepts is one the venue accepts
too; the cost is that a vanishingly small band of legal orders is skipped.
Rounding a floor **down** is the fail-open direction: orders sent below a minimum
Kraken enforces, rejected at the venue.

**Why the strict parser is not the right tool here**, per its own documented
convention: `fromDecimalString` is for values this system **sends** — a price or
quantity we invented and must not silently alter — and `fromDecimalStringRounded`
exists for values a venue **reports**, which we do not control and cannot refuse.
`ordermin` and `costmin` are reported bounds we compare against, never values
transmitted. This is the same reasoning that admitted Gemini's 11-decimal
balances rather than letting the strict parser make an account unreadable
entirely.

**Unreachable today, and kept anyway.** All 1440 live pairs publish both within
the money scale (`ordermin` at most 5 decimals, `costmin` at most 5), so the
rounding never fires against current data. It is a direction chosen in advance
for a payload that has not arrived — the same posture as PART 5's non-power-of-ten
arm.

## PART 10 — STATUS AND WHAT REMAINS

**NOT DEPLOYED, AND NOT REACHABLE.** `ExchangeId` is `"binance" | "gemini"`
([`src/db/schema.ts:34`](../../src/db/schema.ts)). No bot can name Kraken, no
resolver constructs a Kraken client, and the three files ship as tested,
committed, unreferenced code. **The widening is deliberately deferred until the
base client is complete** — turning it on before `client.ts` exists would make
Kraken selectable in the dashboard and immediately unusable, and every wiring
step below is easier to verify against a client that already works.

Remaining, in order, following entry 90's build order:

1. **`parse.ts`** — the error-**array** classification of entry 90 PROBLEM 3
   (Kraken returns HTTP 200 with the failure in the body, so classification must
   be driven by the error array and read **before** the status), order/candle/
   balance parsing, and `BalanceEx`'s `free = balance - hold_trade` derivation.
   No weight-header reader: Kraken sends none.
2. **`client.ts`** — the ten section 4.1 methods. `#request` checks the error
   array first; `cancelOrder` per entry 90 DECISION 2 (cancel, then exactly one
   status read, never a loop); `placeOrder` sends `oflags=fciq` per DECISION 4.
3. **The wiring steps**, once the client stands on its own: the workers resolver
   (`src/workers/exchange-kraken.ts`, mirroring `exchange-gemini.ts`, with
   DECISION 1's testnet refusal), exchange-dispatch, the **`ExchangeId` widening
   and its migration**, and the dashboard mirror.
4. **The rate-limiter redesign**, as its own separate and later effort. Entry 90
   recommended this ordering explicitly and it is not being collapsed into the
   client work: Kraken's decaying counter and its separate matching-engine budget
   do not fit the existing limiter's model, and that is a redesign, not an
   adapter.

Two smaller items from entry 90 still outstanding and worth not rediscovering:
Kraken has **no 6-hour candle interval** (its OHLC steps are 1, 5, 15, 30, 60,
240, 1440, 10080, 21600 minutes — 240 then 1440, nothing between), so a Kraken
timeframe table cannot be a total `Record<CandleInterval, …>` without inventing
one; and `Balance` must read **`/private/BalanceEx`**, since only the extended
form reports `hold_trade` and the interface wants `free` and `locked` separately.
