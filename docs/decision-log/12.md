## Step 12: Start-bot action (backend endpoint + dashboard control)
Date: 2026-07-29

### What was built

The explicit step-2 "start" (spec 6.2/6.3) as a human action: a `created` bot
can now be moved to `running` from the dashboard, backend endpoint and frontend
control, following the liquidate action's pattern exactly (thin wrapper over the
DO's real method, typed refusals surfaced honestly).

- **`POST /api/bots/:id/start`** (`startBot` in `src/api/handlers.ts`, routed in
  `src/api/index.ts` next to liquidate). A thin wrapper over
  `BotInstance.start(actor)`: it calls `start`, then refetches the D1 row +
  snapshot and returns `{ result, bot }`, byte-for-byte the same shape and
  refetch as `liquidateBot`. No business logic added — `start` is the sole
  authority on whether the transition is allowed.
- **`StartResult` / `StartResponse`** in `dashboard/src/api/types.ts` and
  **`startBot()`** in `dashboard/src/api/client.ts`, mirroring the liquidate
  types/client.
- **`StartAction.tsx`** — the dashboard control, mirroring `LiquidateAction.tsx`:
  renders only when `bot.status === "created"` (re-checked in the component, not
  just at the caller), a plain yes/no confirm dialog (NOT type-to-confirm),
  mounted-guard + in-flight/double-click guard, immediate `poll.refetch` on
  success. Wired into `BotDetail.tsx` between the summary and the halted-only
  liquidate control.
- **Backend tests** (`src/api/api.test.ts`): starts a created bot (200, status
  `running`, `bot.started` audited to the human actor, and `exchange.placed`
  asserted empty — proof it places nothing); refuses a non-created bot (409
  `invalid_status`).

### `start()` confirmed from source, not assumed

The brief's premises about what `start` does were checked against
`src/durable-objects/bot-instance.ts` before writing anything, and two of them
did not hold:

- **`start(actor: string): Promise<PipelineResult>` places NO order and makes NO
  exchange call.** It reads config + state, and if `status === "created"` flips
  it to `running`, mirrors to D1, audits `bot.started`, and returns
  `{ status: "running", action: "started" }`. The base order (DCA) / ladder
  (grid) is designed to fire on the *next* `onPriceUpdate`, because placing needs
  a price and reading one is an exchange call that can fail (§5.6). The method's
  own comment says exactly this.
- **`start`'s only failure is `invalid_status`** (a bot whose status is not
  `created`), surfaced as 409 by `envelope.ts`'s existing code map. It therefore
  *cannot* return the price-unusable, unreachable-exchange, or order-filter
  errors the brief asked to handle distinctly — those are `onPriceUpdate` /
  `#placeBuy` failure modes, on a code path `start` never reaches.

### Decision: honest status-flip, not faked execution

Because of the above, the brief's premises #3–5 (starting "immediately places a
real order", and distinct copy for price/reachability/filter failures) were
false against the current codebase. Rather than write dialog copy that lies or
dead error-branches that never fire, this was raised with the operator, who
chose (both recommended):

1. **Scope = honest status-flip only.** Add the endpoint + button + dialog whose
   copy tells the truth: starting moves `created -> running`; it names the real
   order the config *will* place once running (built from the bot's own config
   values — DCA base order size in the capital asset, grid line count across the
   configured range), and states plainly that no order fires yet because the
   execution path is not wired. Not the larger job of wiring that path.
2. **Handle only what `start` returns.** `invalid_status` (409), an expired
   session, a network drop, and a generic fallback. No branches for failures the
   endpoint cannot produce.

### Why nothing trades on start yet (three independent gaps)

Confirmed by grep across `src` (excluding the DO itself and tests):

1. **Nothing calls `onPriceUpdate`** — zero production callers;
   `subscribeToPriceFeed` is deliberately not wired
   (`BotInstanceDependencies` comment). No price ever arrives.
2. **No exchange is attached in production** — `attach()` is called only in
   tests; `#deps()` throws `not_attached` if anything tries to trade. There is no
   default client (needs live credentials, none exist — step 4.1).
3. **`start` places nothing anyway** (above).

This is the same "execution wiring still missing" that step 11's open Q1 named.
Starting the real `gemini-main` bot today will move it `created -> running` and
place **zero** orders — the Binance geo-block / Gemini edge reachability never
even come into play, because no order is attempted.

### Open questions carried forward

The execution wiring (step 11 open Q1) is still the one thing between a `running`
bot and a real order: attaching a live exchange client to the DO in a deployed
environment, and something that feeds prices into `onPriceUpdate`. Until then,
"Start bot" is honest arming, not a trade. Its dialog says so, in those words.
