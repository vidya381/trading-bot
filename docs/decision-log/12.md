## Step 12: Start-bot action (backend endpoint + dashboard control)
Date: 2026-07-29

### What was built

The explicit step-2 "start" (spec 6.2/6.3) as a human action: a `created` bot
can now be moved to `running` from the dashboard, backend endpoint and frontend
control, following the liquidate action's pattern exactly (thin wrapper over the
DO's real method, typed refusals surfaced honestly).

- **`POST /api/bots/:id/start`** (`startBot` in `src/api/handlers.ts`, routed in
  `src/api/index.ts` next to liquidate). A thin wrapper over
  `BotInstance.start(actor)`: it calls `start`, then refetches the D1 row +
  snapshot and returns `{ result, bot }`, byte-for-byte the same shape and
  refetch as `liquidateBot`. No business logic added — `start` is the sole
  authority on whether the transition is allowed.
- **`StartResult` / `StartResponse`** in `dashboard/src/api/types.ts` and
  **`startBot()`** in `dashboard/src/api/client.ts`, mirroring the liquidate
  types/client.
- **`StartAction.tsx`** — the dashboard control, mirroring `LiquidateAction.tsx`:
  renders only when `bot.status === "created"` (re-checked in the component, not
  just at the caller), a plain yes/no confirm dialog (NOT type-to-confirm),
  mounted-guard + in-flight/double-click guard, immediate `poll.refetch` on
  success. Wired into `BotDetail.tsx` between the summary and the halted-only
  liquidate control.
- **Backend tests** (`src/api/api.test.ts`): starts a created bot (200, status
  `running`, `bot.started` audited to the human actor, and `exchange.placed`
  asserted empty — proof it places nothing); refuses a non-created bot (409
  `invalid_status`).

### `start()` confirmed from source, not assumed

The brief's premises about what `start` does were checked against
`src/durable-objects/bot-instance.ts` before writing anything, and two of them
did not hold:

- **`start(actor: string): Promise<PipelineResult>` places NO order and makes NO
  exchange call.** It reads config + state, and if `status === "created"` flips
  it to `running`, mirrors to D1, audits `bot.started`, and returns
  `{ status: "running", action: "started" }`. The base order (DCA) / ladder
  (grid) is designed to fire on the *next* `onPriceUpdate`, because placing needs
  a price and reading one is an exchange call that can fail (§5.6). The method's
  own comment says exactly this.
- **`start`'s only failure is `invalid_status`** (a bot whose status is not
  `created`), surfaced as 409 by `envelope.ts`'s existing code map. It therefore
  *cannot* return the price-unusable, unreachable-exchange, or order-filter
  errors the brief asked to handle distinctly — those are `onPriceUpdate` /
  `#placeBuy` failure modes, on a code path `start` never reaches.

### Decision: honest status-flip, not faked execution

Because of the above, the brief's premises #3–5 (starting "immediately places a
real order", and distinct copy for price/reachability/filter failures) were
false against the current codebase. Rather than write dialog copy that lies or
dead error-branches that never fire, this was raised with the operator, who
chose (both recommended):

1. **Scope = honest status-flip only.** Add the endpoint + button + dialog whose
   copy tells the truth: starting moves `created -> running`; it names the real
   order the config *will* place once running (built from the bot's own config
   values — DCA base order size in the capital asset, grid line count across the
   configured range), and states plainly that no order fires yet because the
   execution path is not wired. Not the larger job of wiring that path.
2. **Handle only what `start` returns.** `invalid_status` (409), an expired
   session, a network drop, and a generic fallback. No branches for failures the
   endpoint cannot produce.

### Why nothing trades on start yet (three independent gaps)

Confirmed by grep across `src` (excluding the DO itself and tests):

1. **Nothing calls `onPriceUpdate`** — zero production callers;
   `subscribeToPriceFeed` is deliberately not wired
   (`BotInstanceDependencies` comment). No price ever arrives.
2. **No exchange is attached in production** — `attach()` is called only in
   tests; `#deps()` throws `not_attached` if anything tries to trade. There is no
   default client (needs live credentials, none exist — step 4.1).
3. **`start` places nothing anyway** (above).

This is the same "execution wiring still missing" that step 11's open Q1 named.
Starting the real `gemini-main` bot today will move it `created -> running` and
place **zero** orders — the Binance geo-block / Gemini edge reachability never
even come into play, because no order is attempted.

### Verification

- Backend `tsc --noEmit`: clean. Dashboard `tsc -b && vite build`: clean.
- Full backend suite: 1243 tests pass (the lone teardown "Error" is miniflare's
  RateLimiter-WebSocket close-timeout, unrelated to this change).

### Open questions carried forward

The execution wiring (step 11 open Q1) is still the one thing between a `running`
bot and a real order: attaching a live exchange client to the DO in a deployed
environment, and something that feeds prices into `onPriceUpdate`. Until then,
"Start bot" is honest arming, not a trade. Its dialog says so, in those words.

## 12.1 — Start-dialog copy corrected once the price-feed arc landed
Date: 2026-07-30

### Why this entry exists

Step 12 deliberately shipped a dialog that told the truth as of 2026-07-29: it
said, in an amber note, that "no live price feed is wired into this build yet,
and the bot has no exchange connection in this environment", so starting would
set the status to `running` but **would not place any order yet**. That was
accurate then, and the entry above records the three independent gaps behind it.

Two of those three gaps have since closed, and the third never was a gap:

- **Gap 2 (no exchange attached in production) closed at step 13** —
  `resolveExchangeForAccount` attaches a real client lazily in `#exchange`, from
  real credentials, fail-closed when they are missing.
- **Gap 1 (nothing calls `onPriceUpdate`) closed across step 14.1–14.5** — the
  `PriceFeed` DO, its subscriber registry and fan-out, and `BotInstance.start` /
  `resume` subscribing to it fail-closed **before** the status flip.
- **Gap 3 ("`start` places nothing anyway") was never a gap in itself** — it is
  the §5.6 design, not a missing piece. It only produced "no order will happen"
  in combination with gap 1. With a live feed, the very same design means the
  order fires on the next closed candle.

And critically, the feed is not merely written but **verified live**, twice, both
on 2026-07-30:

- **14.6, Tier 0 — PASS.** Cloudflare's edge really opens an outbound WebSocket
  to Gemini's sandbox feed and receives real `candles_1m_updates`. It also caught
  a real transport bug (`wss://` passed to `fetch`) whose fix is permanent.
- **14.7, Tier 1 — PASS.** The **real** `PriceFeed` Durable Object connected,
  crossed a real minute boundary, and completed its fan-out: the watermark
  advanced 1785463079999 → 1785463139999, exactly one 60 000 ms candle, with D1's
  `price_feed_fanout_failed` independently naming the throwaway subscriber.

So the dialog's caveat had become **false in both of its clauses** — a live price
feed *is* wired, and the bot *does* have an exchange connection — while its
conclusion ("will not place any order yet") had become the most dangerous kind of
UI copy: a reassurance, on a capital-committing confirm dialog, that the system
no longer honours.

### Decision: delete the reassurance, do not soften it

The caveat was **removed entirely**, not reworded into a hedge. A softened
version ("may not place an order immediately", "the execution path is still
settling") would preserve the exact reader-belief that is now wrong — that
clicking Start is safe rehearsal — while making it unfalsifiable. On a dialog
whose whole job is informed consent to spend real money, an operator who
misreads in the *cautious* direction loses nothing; one who misreads in the
*reassured* direction places a real order they did not intend. The copy now
states the capital commitment and the timing plainly:

> This commits real capital. Starting subscribes the bot to the live price feed,
> and the next closed 1-minute candle — normally within a minute — drives a real
> order on the real exchange. There is no dry run and no further prompt after
> this one.

The "What starting will place" panel above it is unchanged: it already named the
real order from the bot's own config values, and that naming is now load-bearing
rather than hypothetical.

### The same claim was removed everywhere it appeared

The stale assertion lived in five places, not one. Fixing only the dialog would
have left the codebase asserting the opposite of itself:

1. **`StartAction.tsx` dialog** — the amber note, replaced as above.
2. **`StartAction.tsx` success banner** — said "No order was placed yet (the
   price feed and exchange connection are not wired in this build)". This was the
   *more* misleading of the two, because it is read **after** the irreversible
   click. Now: the bot is subscribed to the live feed and its first order goes to
   the exchange on the next closed 1-minute candle.
3. **`StartAction.tsx` header docblock** — rewritten to describe the fail-closed
   subscribe, and to record that the step-12 caveat was deleted rather than
   softened, with the reason.
4. **`src/api/handlers.ts` `startBot` docblock** — said `start` "places NO order
   and makes NO exchange call" and that "`start`'s only failure is
   `invalid_status`".
5. **`dashboard/src/api/types.ts` start section** — the same two claims.

### One real behavioural consequence, deliberately not expanded

Step 12 decision 2 ("handle only what `start` returns") named `invalid_status` as
`start`'s *only* failure. That is no longer strictly true: the fail-closed
`#subscribeToFeed` runs before the status flip and can reject — e.g.
`not_attached` when an environment declares no `PRICE_FEED` binding, or a feed
registry error. No new UI branch was added for it. The existing generic branch
already reports `error.message` followed by "Nothing was started.", which is
**exactly right** for a fail-closed subscribe: the bot never left `created`. The
docblocks were corrected to say so rather than continuing to claim the failure
cannot occur. Adding bespoke copy for it would be new error-handling work, not a
copy correction, and belongs to whoever wires the end-to-end run.

### What this entry does NOT claim

The dialog now promises a real order attempt on the next closed candle. Honesty
about the residual gap, carried from 14.7: **feed→bot→order has still never run
end-to-end live.** Tier 1's subscriber was a fake id whose delivery deliberately
rejects; no real bot has yet received a real price and placed a real order. The
copy is nonetheless correct to promise it, because every link is now built,
attached and individually verified, and the honest failure mode of the *old* copy
(an operator believing nothing can happen) is far worse than that of the new one
(an operator expecting an order that a first-run bug might delay — which alerts
and the orders table will show). The ~15-minute eviction ceiling also remains
unobserved.

### Verification

- Backend `tsc --noEmit`: clean. Dashboard `tsc -b && vite build`: clean.
- Full backend suite: **1300 tests pass**, unchanged from the 14.7 baseline (the
  lone teardown "Error" is miniflare's RateLimiter-WebSocket close-timeout,
  unrelated to this change — as in step 12). No test asserted on the removed
  strings; a repo-wide grep for them returns nothing outside this log.
