## Step 43: The citation mechanism stays exactly as it is — a decision NOT to build, and the requirement moved onto Stage 4 instead

**This is a decision-recording step. No source file changed. Nothing was built,
deleted, deployed or measured.** The deliverable is this entry.

Entry 41 recorded two live-observed uses of the citation mechanism that nobody
designed for, flagged them as an **OPEN QUESTION**, and deliberately refused to
settle them in the same session that found them — *"because changing the citation
rules is a change to the safety mechanism itself and deserves its own decision
rather than a same-session judgement call."* Entry 42 carried them forward
untouched, by intent.

This is that decision. **Made by the operator after discussion.**

**The citation mechanism — evidence-id citations resolved through
`resolveCitations` — stays EXACTLY as-is. No new parser logic, no new prompt
instructions, no new validation.**

### The question, as entry 41 left it

Both stages require every claim and every proposed value to cite one or more
evidence ids, and `resolveCitations` (`assess-parse.ts`) refuses any response
citing an id the run's prompt did not emit. That check is **a set-membership test
over a finite set of strings**, which is precisely what step 37 argued for and
got: it turns *"did the model use only the provided data?"* from a judgement into
something deterministic.

Two live runs then used that mechanism in ways its design did not anticipate.

### The two uses, restated precisely

1. **An ABSENCE MARKER cited as justification for a null/disabled value.** The
   model cited `news.status` — whose rendered value is
   `NOT COLLECTED -- no request was made and nothing failed …` — as grounds for
   setting `takeProfitAmount` to `null`.
2. **A PRIOR STAGE'S OWN CLAIM cited as justification for a parameter.** The
   model cited `assessment.claim.N` — Stage 2's reasoning, carried into Stage 3's
   prompt as citable evidence — rather than citing the fetched datum underneath
   it. Those ids exist on purpose (`collectAssessment`, `derive-prompt.ts`), but
   the intent was that a parameter would rest on a **datum** and the assessment
   would be **context**. It was used as a **premise**.

### What is NOT in question, and must not be lost in what follows

Neither case is a fabrication, a malfunction, or a hole in the grounding check.
Stating this plainly because a decision to change nothing is easy to misread as a
decision to tolerate something:

- **Both ids were real ids those runs really emitted**, carrying real rendered
  values. The set-membership check did exactly what it exists to do.
- **Both are checkable by a human.** The cited item travels on the response with
  its `id`, `label`, `value` and `source`, so a reviewer reads the sentence beside
  the thing it points at. Nothing is hidden or summarised away.
- **Both produced sound reasoning on inspection.** *"I set no take-profit target
  because I have no news signal"* is honest, and a parameter that follows from the
  strategy choice made on this same data is not obviously wrong.
- **Neither has produced an unsound or hard-to-verify result.** That is an
  observation about two runs, not a guarantee — see *What would reopen this*.

The discomfort entry 41 recorded is real and is narrower than "these are bad
citations": **"the news slot reports nothing was collected" offered as evidence
FOR a choice is a different ACT from citing a price**, and the prompt's own rule 5
(`RULE_MISSING_IS_UNKNOWN`) says an absent input *"is UNKNOWN … do not treat its
absence as good news, bad news, or a quiet market."* The question is whether that
difference should be enforced, and where.

### The three options considered

#### Option A — do nothing further at the parser level ✅ **CHOSEN**

Leave `resolveCitations` as a set-membership test. Emit no new marker, add no new
prompt rule, create no new refusal. Record the two patterns, the reasoning, and
the conditions that would reopen the question.

#### Option B — add a parser-level marker distinction ❌ rejected

Mark absence-reporting evidence so a citation of one can be treated differently —
a distinct id namespace, or a flag on `EvidenceItem` — and then, for example,
forbid an absence marker as the **sole** citation for a value.

**Rejected on a fact about the current code, not on taste.** Absence is a
**per-run STATE of an id, not a property of the id**:

| id | when the input succeeded | when it failed / was not collected |
| --- | --- | --- |
| `candles.status` | `"PRESENT"` | `MISSING -- …` |
| `concentration.status` | `"PRESENT"` | `MISSING -- …` |
| `capital.status` | `"PRESENT"` | `MISSING -- …` |
| `filters.status` | `"PRESENT"` | `MISSING -- …` |
| `news.status` | *(no success arm exists)* | `NOT COLLECTED -- …` |

**The same id is an absence marker in one run and an ordinary datum in the next.**
So an id-namespace scheme would have to rename ids per run — which destroys the
stable evidence vocabulary that **step 42's whole resubmission re-verification
depends on**, since a client resubmitting yesterday's assessment resolves its
citations against today's ids. And a flag on `EvidenceItem` runs straight into a
decision this project already made once, in `assess-prompt.ts`:

> There is deliberately no `derived: boolean` flag. Values this module computed
> (the aggregates, the buckets, the percentages) say so in their `label` and in
> the prompt's own text, where a model and a human both actually read it.

The same argument applies unchanged. The information is already in the `label`,
the rendered `value` and the `source` — see the Stage 4 requirement below.

There is a second, sharper problem. `news.status` is the **only** id with no
success arm, and that is true **only because no news vendor has been chosen**
(entry 30). It is a temporary property of an unfinished input, not a permanent
class of evidence. **Building a namespace around it would be designing a
mechanism around a placeholder.**

#### Option C — split citations into two formal kinds ❌ rejected

Make the response contract distinguish, say, `evidence` citations from
`reasoning` citations, and have the parser enforce which kind is acceptable
where.

**Rejected because it changes what the parser IS.** Today `resolveCitations`
answers one question — *is this id in the set this run emitted?* — and its whole
value is that the question is mechanical and cannot drift. Option C requires the
parser to decide **which kind a citation is** and **whether that kind is
permitted here**, which is a semantic judgement about the model's reasoning. That
is a materially larger change to the safety mechanism than it looks, and it
manufactures an entirely new refusal class — *"right id, wrong kind"* — **with no
observed failure behind it.**

It also does not survive its own first test case. A parameter can legitimately
rest on both a datum and the assessment at once, so the kinds are not disjoint,
and the parser would need a rule about mixtures that nothing observed has ever
asked for.

### The reasoning for choosing A, in full

**The core argument is over-fitting.** There are **two observed data points**,
from **two live runs**, and building enforcement machinery against them would fit
a fix to *what has been seen* rather than to *what genuinely needs solving*. Both
cases are real, checkable and sound. A parser rule written now would be a rule
about the only two shapes anyone has looked at, and its most likely failure is
not that it is too strict — it is that a third, unanticipated shape arrives and
the rule neither catches it nor is obviously the wrong rule for it.

Three supporting reasons, in descending weight:

1. **The existing mechanism did not fail.** Nothing was fabricated, nothing was
   hidden, and every cited value reached the human alongside the sentence about
   it. A change here would be a change to a safety mechanism that is currently
   doing its job, in response to something that is not a defect.
2. **The check's value is that it is mechanical.** Every semantic rule added to
   `resolveCitations` makes it a little less true that *"did the model use only
   the provided data?"* is a deterministic question — and that determinism is the
   entire reason step 37 preferred a set-membership test to a judgement.
3. **The distinction is genuinely useful — just not HERE.** Nobody argued the
   three kinds of citation are equivalent. They are not. The disagreement was only
   ever about which layer should know that, and the answer is the layer that
   speaks to a human.

### ⚠ THE SCOPE OF THIS DECISION IS THE PARSER AND VALIDATION LAYER, AND NOTHING ELSE

**This decision means: no new parser logic, no new prompt instruction, no new
validation, no new refusal.**

**IT DOES NOT MEAN THE DISTINCTION DOES NOT MATTER, AND IT DOES NOT MEAN A LATER
STAGE MAY IGNORE IT.** Read as *"the project looked at this and concluded all
citations are interchangeable"*, this entry would be actively harmful — that is
the opposite of what was concluded. What was concluded is that **enforcement is
the wrong tool and the parser is the wrong place**, and that the distinction
belongs where a human actually reads the result.

### ⚠ A REQUIREMENT PLACED ON STAGE 4'S FUTURE DESIGN

**Stage 4 (Explain and assemble) does not exist.** When it is built, this is a
requirement on it, recorded here in advance:

> **Stage 4's presentation layer MUST be designed with explicit awareness that a
> citation may point to (a) real fetched data, (b) an absence marker, or (c) a
> prior stage's own claim — and MUST describe these differently to a human
> reader rather than rendering all three as interchangeable "here is the source"
> citations.**

**This is a requirement ON Stage 4, not something Stage 4 gets to rediscover
independently, and not a suggestion it may weigh against its own convenience.**
It is written here because the session that builds Stage 4 will otherwise meet a
uniform list of `EvidenceItem`s and have every reason to render them uniformly —
which is exactly the outcome this decision assumes will not happen.

Concretely, a human reading a proposal should be able to tell these apart at a
glance:

- *"orderSize 50.00 — because the last close was 63757.71"* **(a)**
- *"takeProfitAmount null — because no news was collected"* **(b)**
- *"gridLines 5 — because an earlier stage judged the range tight"* **(c)**

(b) and (c) are not weaker citations, and the requirement is not to hide or
demote them. **It is to stop them reading as (a).** A reviewer who cannot tell
that a parameter rests on a non-observation, or on another model's judgement
rather than on a fetched number, is being shown a proposal that looks better
grounded than it is — and 21.1 puts that reviewer there as the only part of the
loop that can catch a bad upstream judgement (entries 40, 41, 42).

**The classification needs no parser change, and this is what makes the whole
decision coherent rather than merely deferred.** `EvidenceItem.source` already
carries it, today, with no new field:

| source | class |
| --- | --- |
| `assessment.strategy`, `assessment.claims[N]` | **(c)** a prior stage's own claim |
| `news` | **(b)** absence marker — the paused news slot |
| `candles.error`, `concentration.error`, `capital.error`, `filters.error` | **(b)** absence marker — a failed read |
| everything else | **(a)** real fetched or computed data |

Stage 4 can therefore make the distinction from data it will already be handed.
**Option B would have added a field to say what `source` already says.**

One observation for whoever builds it, recorded rather than acted on: the Derive
prompt's own worked shape example cites `capital.status` for `allocatedCapital`
(`derive-prompt.ts`, `shapeExampleFor`). That is a **status** id rather than the
`capital.row.NN.available` figure underneath it. The example's values are
deliberate placeholders and its ids are deliberately real ones the prompt always
emits, so this is not a defect — but it does mean **the prompt itself
demonstrates citing a status id**, which is worth knowing when interpreting why
pattern (b) appeared at all.

### What would reopen this

Stated as conditions so that reopening is a check rather than a matter of
whoever next feels uneasy:

1. **A THIRD kind of citation use appears** — something that is neither fetched
   data, nor an absence marker, nor a prior stage's claim. Two shapes may be a
   coincidence; three is the beginning of a pattern worth building against.
2. **Either of these two kinds is found to have produced an UNSOUND result** —
   a parameter a human would reject, resting on an absence marker or on a prior
   claim in a way that made it look better supported than it was.
3. **Either kind is found to be HARD TO VERIFY in practice** — a reviewer with
   the response in front of them unable to tell, in reasonable time, what a value
   actually rests on.

Condition 3 is the one Stage 4's design most directly bears on, and it is the
reason the requirement above is a requirement rather than a recommendation: **a
presentation layer that renders all three kinds identically would itself CREATE
condition 3.**

### What this entry does NOT claim

- **It does not claim two data points are enough to conclude the patterns are
  safe.** It claims two data points are not enough to justify building
  enforcement, which is a different and weaker claim. The asymmetry is
  deliberate: the cost of a wrong "do nothing" is a revisit; the cost of a wrong
  parser rule is a change to the safety mechanism plus everything later built on
  it.
- **It does not settle whether citing `assessment.claim.N` satisfies 21.5
  requirement 1.** Entry 41 asked that and was right that *"the id was real"* does
  not answer it. This entry says the question is not answered by a parser rule
  either, and routes it to the human via Stage 4.
- **It does not touch the citation rules, the prompts, or any validator.**
- **No live run, no measurement, and no new evidence was produced here.** Every
  observation cited is entry 41's, re-read from the entry, with the supporting
  source facts re-read from `assess-prompt.ts` and `derive-prompt.ts`.
