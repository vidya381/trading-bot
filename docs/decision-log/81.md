## PART 1 — THE SYMPTOM, AND WHY IT WAS INVISIBLE FOR A MONTH

The **Jul 22 – Aug 21** billing cycle showed **$12.65**, of which **$12.50 was
Durable Objects Compute Duration** — and the whole charge landed on a **single
day, Aug 12**.

**It did not happen on Aug 12.** Compute Duration is metered against a
**400,000 GB-second monthly allowance**, and a dollar figure only appears on the
day the running total crosses it. Usage had been accruing every day of the cycle,
invisibly, and Aug 12 is merely the day the counter passed the line. **The single
-day appearance is an artifact of allowance accounting, not a spike**, and reading
it as an incident on that date would have sent the investigation to the wrong day.

The leak was confirmed **still active** in the following cycle:

| | |
| --- | --- |
| Usage, first 6 days of the new cycle | **284.44k GB-seconds** |
| Daily rate | **~47.4k GB-s/day** |
| Implied objects resident continuously | **~4.4** (47.4k ÷ 0.125 GB at 128 MB/object ÷ 86,400 s) |
| `(exchange, pair)` pairs legitimately running | **2** |
| Projected to cross the 400,000 allowance again | **~Aug 29** |

**~4.4 objects resident against 2 that should be** is the entire finding, stated
as a number. A `PriceFeed` cannot hibernate while connected — step 14 established
that an **outbound** WebSocket does not hibernate, only inbound server sockets do
— so every resident feed bills continuously for as long as its socket is up.

## PART 2 — ROOT CAUSE, PRIMARY: FAN-OUT NEVER PRUNED

`#fanOut` delivered each closed candle with `Promise.allSettled` and, on a
rejection, **raised an alert and did nothing else**. There was no path anywhere in
the system that removed a subscriber which had stopped being reachable.

The comment that stood at that site deferred the case explicitly: a genuinely
orphaned subscriber was *"section 9 reconciliation's concern, not the per-candle
hot path's."* **No such reconciliation was ever written.** `grep` over
`src/reconciliation/` and `src/workers/reconciliation.ts` for `PRICE_FEED`,
`priceFeed`, `subscriber` or `unsubscribe` returns nothing. The deferral had no
owner, and the case it deferred was the leak.

Confirmed against D1: **six halted or stopped bots still held live subscriber
rows and were still failing delivery** —

`bot-328qgw`, `bot-3trlgb`, `bot-4xcq8p`, `bot-9wzfci`, `bot-xs0ufw`,
`prop-live-1`

The chain from there is mechanical, and every link was already in the source:

1. A dead subscriber's row stays in the feed's `subscribers` table forever.
2. `unsubscribe`'s zero-subscriber check (`before > 0 && count === 0`) therefore
   **never fires** — the count never reaches zero.
3. `stopFeed` is called from **exactly one production site**, inside that check.
   So `stopFeed` never runs.
4. `stopFeed` held the **only** `deleteAlarm` in the file. Every other path
   re-armed: `alarm()`'s healthy branch at `HEALTH_CHECK_MS`, `#ensureConnected`
   on a successful open, `#scheduleReconnect` on backoff and then at
   `SLOW_RETRY_MS` **forever**.
5. So the alarm chain re-armed indefinitely on a feed with nothing listening,
   holding the object — and its un-hibernatable socket — resident and billing.

**The failure mode is not that prices were lost. It is that the feed kept working
perfectly for an audience that had gone.**

## PART 3 — ROOT CAUSE, SECONDARY: `stopFeed`'S SELF-INFLICTED RECONNECT

A second, independent path produced the same end state, and would have survived a
fix to PART 2 alone.

`openOutboundSocket` wired **both** `close` and `error` to the same handler, and
never removed them:

```
ws.addEventListener("close", onClose);
ws.addEventListener("error", onClose);
```

`onClose` reaches `#onSocketClosed` → `#scheduleReconnect`, which **re-arms the
alarm unconditionally**. And `stopFeed` began by calling `this.#socket?.close()`
— which dispatches that very `close` event — while its `deleteAlarm()` was the
**last** statement in the method.

**So a feed tearing itself down was asking, through its own teardown, to be
reconnected.** If the event landed after `deleteAlarm`, a fresh alarm was set on a
feed with zero subscribers.

It then reconnected **for real**, because `stopFeed` reset only the watermark and
**left `#state.config` set**. The next alarm found no socket, called
`#ensureConnected`, passed its `config !== null` guard, opened a live socket and
re-armed at 15s — indefinitely.

This ordering dependency is why the fix is layered rather than a single guard.

## PART 4 — THE FIX, ITEM BY ITEM

### 1. Per-subscriber failure streaks, pruning at five

A `consecutive_failures` column on the `subscribers` table. A rejected delivery
increments it; a **fulfilled** delivery resets it to zero. At
**`MAX_FANOUT_FAILURES = 5`** the subscriber is unsubscribed — which, if it was
the last, takes the feed down through `unsubscribe`'s existing `stopFeed`.

A non-running bot's `"ignored"` is a **successful RPC** and so resets the streak.
Only unreachability accumulates.

**Durable, not in-memory, and the reason is specific:** a feed whose only
subscriber is dead is precisely the feed most likely to be evicted, and an
in-memory counter would reset on every eviction — resetting fastest in exactly the
case it exists to catch. The table survives eviction; the counter had to live
there.

Already-deployed feeds carry the one-column table, and a Durable Object class has
no migration mechanism — **the constructor is the migration point**. It now runs
a guarded `ALTER TABLE ... ADD COLUMN`, whose throw on an existing column is the
"already migrated" signal.

Five failures at one closed candle a minute is **~5 minutes of proven-dead
delivery** before a prune: far longer than any transient cross-object RPC
failure, and far shorter than the forever it used to be.

### 2. The `#stopped` latch, and listener removal

`openOutboundSocket`'s `close()` now **removes the `close`/`error` listeners
before** calling `ws.close()`, so the event has nowhere to land. `#onSocketClosed`
returns immediately when `#stopped` is set, catching events that bypass that path
(an injected double, or one already queued).

### 3. `stopFeed`, reordered

Latch → drop the socket **reference** → close → clear `config` **and** watermark →
persist → `deleteAlarm` **last, after everything that could re-arm**. Dropping the
reference before closing means a re-entrant `#onSocketClosed` sees `null`;
clearing the config means a stray alarm hits `#ensureConnected`'s guard and
returns without reconnecting.

`reconnectAttempts` / `blindSince` / `escalated` are **deliberately left alone** —
a successful reopen already clears them, and resetting them here would change when
`price_feed_blind` fires, which is out of scope for this entry.

### 4. `#armAlarm(at: Timestamp | null)`

Now takes a nullable instant with a `deleteAlarm` branch, mirroring
`bot-instance.ts`'s `#armAlarm` / `#nextAlarmAt` pattern, including its
read-before-write so a re-arm to the same instant is not a storage write.

**The old non-nullable signature was itself part of the bug**: with no disarm
branch, every path could arm and none could stand down.

### 5. `alarm()`'s zero-subscriber backstop

`alarm()` reads the registry **first**. Empty means `stopFeed()` and return,
**regardless of how it got that way** — which is the point. It closes not only the
two causes above but any future gap that leaves a feed running with an empty
registry.

The invariant it must not break: **a subscriber that is halted, unreachable, or
failing still counts.** Only an empty registry stops a feed. Losing prices is a
trading risk, so the connection outlives every failure short of having no reader
at all. A test pins this (PART 7, test 6).

### 6. `status()` and `GET /api/price-feeds`

A read-only RPC returning config, connection state, `alarmAt`, `stopped`,
watermark, reconnect state, subscriber count and per-subscriber failure counts;
and an admin route over it with a computed **`leaking`** flag (zero subscribers
**and** an armed alarm). See PART 5 for what this route can and cannot do.

## PART 5 — DEVIATIONS FROM THE BUILD BRIEF

Four, recorded here rather than left to be inferred from the diff.

### Deviation 1 — the `#stopping` flag as specified would not have worked

The brief specified: set a `#stopping` flag at the top of `stopFeed`, clear it at
the end.

**That would not have closed the race it was written to close.** `deleteAlarm()`
is `stopFeed`'s last statement, so a flag cleared "at the end" would already be
down at the moment a late `close` event lands — which is exactly the ordering
described in PART 3.

Implemented as a **persistent `#stopped` latch** instead: set by `stopFeed`,
cleared **only** by a deliberate `startFeed`. It means *"this feed is torn down
and must not resurrect itself"*, which is the invariant that actually holds.
Verified that `subscribe`'s non-`startFeed` branch is unreachable while the latch
is set: the latch implies zero subscribers, so the next `subscribe` is always a
0→1 transition and always takes the `startFeed` branch.

### Deviation 2 — "list live feeds" is not achievable, and the route says so

The brief asked for an admin route to **list live feeds**. **Durable Object
namespaces are not enumerable by the platform, full stop**, and `idFromName` is
one-way — there is no API that returns the objects that exist, and no way to
recover a name from an id.

What was built instead: derive every feed that **could** exist from
`DISTINCT (exchange, pair)` over `bot_instances` — a feed is addressed by
`"<exchange>:<pair>"`, so that set is exactly the set of names any bot can have
brought into being — then probe each with `status()` on demand.

**This is a real scope reduction, from "list what is live" to "list what is
possible and check each," and it is recorded as a stated limitation in the
route's own docblock** rather than left implicit. That is the same disclosure
this codebase already applies to `CandleWindow.truncated` (entries 29, 37, 44) and
to `NewsInput = NewsNotYetAvailable` (entry 35), where the shortfall is named in
the type or the response instead of being quietly absorbed.

Archived and stopped bots' markets are **included deliberately**: their feeds are
the ones most likely to be leaking, and filtering to running bots would hide
precisely the rows worth reading.

### Deviation 3 — `#alert` gained a `botInstanceId`, which is a behaviour change beyond the leak

`PriceFeed.#alert` hardcoded `bot_instance_id: null` on **every** row it wrote,
including `price_feed_fanout_failed`, with the failing bot's id interpolated into
the free-text `message` and nowhere else. The stated reason was that the column is
a foreign key and a **deleted** bot would violate it.

**There is no bot-deletion path anywhere in this system** — bots are archived,
never removed; the route table has exactly one `DELETE`, for
`/api/watchlist/:id`. Every id reaching that site resolves. The column stayed
null for a case that cannot occur, and the cost was real: these alerts could not
be joined, filtered or counted per bot.

`#alert` now takes an optional `botInstanceId`, passed at the fan-out and prune
sites. **This is an intentional side effect, not a bug fix, and it changes two
things beyond the leak:**

- These alerts **now appear on their bot's detail page** via `GET /api/bots/:id`,
  which queries by `bot_instance_id` with no `source` filter.
- The Discord notification cooldown key is `cooldown:{alertType}:{botInstanceId
  ?? "__account__"}`, so it moves from **shared to per-bot**: five failing bots
  now means **five pings instead of one**, bounded by the new pruning cap of five
  failures each.

`price_feed_blind` and `price_feed_malformed` keep their null id — they are feed
concerns with no bot to name, and `bot-instance.ts`'s own note on that (line 742)
remains accurate.

One consequence had to be corrected in place: `alerts/halt.ts` recorded that
these rows were *"excluded twice over"* from a resume's sweep — by `source` **and**
by carrying a null id. **The second exclusion is now gone**, so that comment was
made false by this change and has been rewritten. The `source` filter is now
load-bearing on its own (with `isHaltAlertType` excluding them again regardless,
since neither starts with `halt_`). Every other alert query was checked and is
unaffected: `standing.ts` and `reconcile.ts` filter on `source` or on an explicit
`alert_type` list, and neither `INGESTED_ALERT_TYPES` nor `isReceiptAlertType`
contains these types.

### Deviation 4 — an FK-failure fallback in `#alert`, disclosed here rather than only in the diff

If an attributed insert throws, `#alert` retries with a **null** id rather than
letting the exception propagate.

**The rationale is about the hot path, not about the old reasoning.** `#alert` is
awaited inside `#fanOut`, which is awaited inside `#forwardClosed` **before the
watermark advances**. A throw there would leave the watermark un-advanced and the
candle re-delivered on every subsequent pass — turning one constraint failure into
an endlessly retried candle. An alert is this object's only voice; losing its
**attribution** beats losing the **alert**.

The shape is **"attribute when possible, degrade to null rather than fail"** — the
same disclosed-degradation stance as `GatheredInput`'s three-state envelope
(`ok` / `failed` / not-attempted, entry 45), where a partial result is carried
forward with its shortfall named instead of the whole call being failed or the gap
being papered over. It is written into `#alert`'s docblock so it is **findable by
someone reading that method cold**, not only visible to someone reading this diff.

A live consequence worth knowing: the pre-existing fan-out test passed unchanged
after this work **because the fallback fired** — its bots have no `bot_instances`
row. Real rows were seeded so the test now proves attribution rather than the
fallback.

## PART 6 — WHAT THIS DOES NOT FIX, AND MUST NOT BE ABSORBED INTO "THE LEAK IS FIXED"

### `price_feed_blind` has no resolve path at all

Confirmed by `grep` this session: `price_feed_blind` is **raised** in
`price-feed.ts` and **nothing anywhere marks it resolved**. The system's four
alert-resolving paths — `resolveHaltAlerts`, `resolveClearedStandingAlerts`,
reconciliation's own, and the two maintenance endpoints — are each filtered by
`source` or by an explicit type list, and **none covers the `price-feed:*`
source**.

The cost was concrete: **two 20-day-old unresolved rows** for `gemini:BTCUSD` and
`gemini:DOGEUSD` turned out to be **stale bookkeeping, not a live outage** — but
ruling that out consumed real investigation time during this work. A standing
alert with no resolve half is the drift `/src/alerts` exists to prevent (entry
80's PART 2 makes the same point about giving one row two owners; this is the
opposite failure — a row with none).

**Not fixed here.** Deliberately out of scope: it is an alert-lifecycle defect,
not a compute leak, and the brief for this work explicitly excluded changing
`price_feed_blind` behaviour.

### Skipped candles: a fan-out failure permanently drops that candle, and nothing records whether it mattered

`#forwardClosed` advances the watermark **after** `forward()` returns, and
`#fanOut` never rethrows — it collects with `allSettled` and alerts. **So the
watermark advances regardless of delivery outcome**, and the dedup guard then
suppresses that candle permanently for the subscriber that missed it. There is no
retry, no per-subscriber watermark, and no backfill for a failed delivery.

(This entry's `#stopped` guard in `#forwardClosed` does **not** change that: it
only prevents a watermark write after a teardown that has already reset it.)

The second half is the harder one. **The system has no per-tick record anywhere —
D1 or DO storage — of prices received.** `#onPriceUpdatePass` writes `lastPrice`
and `lastPriceAt` as a **two-field overwrite** on `BotRuntimeState`; there is no
history, no counter, no audit entry on a price update, and no candle log. So for
any given dropped candle it is **not determinable, retrospectively, by anyone,
whether a running bot's decisions were affected** — a bot that did not trade in a
window either received prices and correctly held, or received nothing, and the
stored data cannot distinguish those.

`bot-instance.ts`'s own note (lines 728–745) already records that **fan-out
failure is structurally invisible to the feed's alerts** — a subscriber returning
`"ignored"` is a successful RPC — which is why the per-bot staleness check exists
at all.

**This is a distinct, deliberately deferred question: are skipped candles safe to
keep skipping?** It needs its own entry. It was not answered here, and the leak
being fixed does not answer it. A per-tick counter was explicitly excluded from
this work's brief and remains excluded.

## PART 7 — VERIFICATION

### The eight new feed tests

All in `price-feed.test.ts`, under
`describe("subscriber pruning and feed teardown (the leak)")`.

1. **Prunes at `MAX_FANOUT_FAILURES` and stops the feed when it was the last** —
   five closed candles, every delivery throwing; asserts registry empty, socket
   closed, **`getAlarm()` null**, and one attributed `price_feed_subscriber_pruned`
   row naming the bot and `price-feed:gemini:BTCUSD`.
2. **Does not prune a subscriber that fails then succeeds** — alternating
   failures over five candles; asserts still subscribed, still connected, streak
   below the cap, zero prune alerts.
3. **No alarm armed when the close event fires DURING `stopFeed`.**
4. **No alarm armed when the close event fires AFTER `stopFeed` has finished** —
   the PART 3 race, driven explicitly in both orderings as separate tests.
5. **An alarm at a zero-subscriber feed disarms and does not reconnect** — the
   registry emptied behind the feed's back, which is the shape *any* cleanup gap
   leaves; asserts no second socket.
6. **A feed with subscribers stays alive through eight failed reconnects** — the
   scope-proof: asserts the subscriber is **not** pruned, the alarm **stays**
   armed, and `price_feed_blind` still fires exactly once. **A live bot must not
   be silently cut off by this change.**
7. **Re-subscribing after `stopFeed` re-establishes the config and reconnects** —
   asserts `config` null / `stopped` true after the stop, then restored and
   connected after the re-subscribe, and that the watermark reset still holds so
   the restart primes rather than backfilling.
8. **`status()` reports registry, connection and alarm without changing any of
   them** — asserts two consecutive calls are identical and arm nothing.

Plus four route tests in `api.test.ts` (`GET /api/price-feeds`): the listing with
its subscribers, the **`leaking` flag on an armed zero-subscriber feed**, archived
and stopped bots' markets included, and the auth gate.

**Five existing tests were changed, and the reason is recorded:** each called
`startFeed` with no subscriber and then drove `alarm()`, which the new backstop
correctly stops. Each was given a real subscriber so it still tests reconnect and
backoff rather than the backstop. **One existing test was rewritten**: it asserted
`bot_instance_id === null` on fan-out alerts and passed unchanged after this work
only because the FK fallback fired — real rows are now seeded so it proves
attribution.
