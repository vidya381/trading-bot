## PART 1 — THE REAL QUESTION, AND WHY ITS ANSWER HAS TWO HALVES

The session opened with the right question rather than the obvious one: **is
this already handled?** Kraken rejects an over-ceiling order itself, and entry
[92.md](92.md) built the error classification that catches such rejections. If
that path were adequate, the correct output of this session would have been a
note saying so and no code at all.

**HALF ONE: THE CLASSIFICATION IS CORRECT, AND IT WAS CORRECT BEFORE THIS
SESSION TOUCHED IT.**

`EOrder:Orders limit exceeded` appears in none of `parse.ts`'s tables, so it
lands on `classifyKrakenError`'s default arm: a **non-retryable**
`exchange_error`. That is exactly right, and it is right for the reason entry 92
wrote the default arm that way — the order was definitely refused, its effect is
not unknown, and re-sending it changes nothing. No phantom order is created. No
bad retry is issued. Nothing in the reactive path is broken, and this entry
corrects nothing entry 92 decided.

**HALF TWO: CORRECT IS NOT SUFFICIENT, AND THE GAP BETWEEN THEM IS THIS ENTRY'S
FINDING.**

A non-retryable `exchange_error` reaching `bot-instance.ts:4676` **halts the
bot**:

```ts
await guard.markFailed(decision.clientOrderId, outcome.message, now);
return await this.#halt(config, "order_rejected", `exchange refused the order: ${outcome.message}`, "system");
```

and `#placeInitialLadder` bails on the first halt it sees:

```ts
if (result.status === "halted") return result; // a hard rejection halted the bot
```

So a grid configured with more rungs than Kraken will hold does this: places
around sixty real orders, then halts mid-build, **with every one of those orders
still resting live on the exchange**, requiring human review under section 7.2
before it can run again. And because the root cause is `gridLines` — a stored
configuration value that a resume does not change — **it halts again on the very
next resume, and every resume after that.** `gridLines` is bounded by `>= 2` and
nothing else, in `grid.ts` and in the dashboard's `requireInteger` alike, so
nothing anywhere refuses the configuration that guarantees this.

**The distinction worth carrying forward is between "the failure is classified
correctly" and "the resulting behaviour is acceptable."** They are separate
properties, a code review of the classifier alone will only ever show the first,
and the answer to "is this already handled?" was genuinely *yes* to one and *no*
to the other. Either answer was a legitimate finding; the useful part is that
they turned out to be different answers.

## PART 2 — THE RATE LIMITER CANNOT PREVENT THIS, AND THAT WAS CHECKED RATHER THAN ASSUMED

There is a coincidence here that looks like protection. On Starter tier the
per-pair trading threshold is **60** ([96.md](96.md)'s `KRAKEN_TRADING_TIERS`)
and the per-pair open-order ceiling is also **60**, and `KRAKEN_ADD_ORDER_COST`
is 1. Entry 96 CORRECTION 3 noticed the coincidence in passing — *"On Starter it
is the same number as the rate threshold"* — and it would be easy to conclude
that a gate already refusing the sixty-first placement in a burst is a gate that
already prevents a sixty-first resting order.

**It is not, and the arithmetic was walked rather than eyeballed.** The routine
allowance is `60 − floor(60 × 1/6) = 50` after `RISK_EXIT_RESERVE_FRACTION`, so a
burst is refused at fifty. But the counter **decays at 1/sec**, and
`#placeInitialLadder` is deliberately built to leave `placed` false and re-enter
on later ticks when anything was throttled — that re-entry is not incidental, it
is the mechanism entry-era grid work added so a throttled ladder completes rather
than stranding its remaining rungs. So the limiter converts a burst into a
trickle, the trickle keeps placing as the counter recovers, and the resting count
climbs to sixty regardless of how slowly it gets there.

**THE GENERAL LESSON, AND THE REASON ENTRIES 96 AND 98 WERE RIGHT.** A rate is a
velocity; a ceiling is a level. A velocity limit is cleared by *waiting*, which
is why `DecayingCounter`, `Budget`, `AcquireCost` and the claims-ahead queue are
all built on the assumption that a refusal is temporary and that queueing is the
remedy. A quantity ceiling is cleared only by a **fill or a cancel** — waiting
does nothing to it, forever. Both entries deferred this work with exactly that
one-line reason, and both were right: had it been forced into the decaying-counter
design, a request queued against a level that never falls would have queued
**forever**, and the gate built to protect the halt path would have become a
place halts hang. Modelling it outside the limiter is that decision carried out,
not reversed.

## PART 3 — ⚠ THE NEAR-MISS ON SCOPE, WHICH WOULD HAVE MADE THE WHOLE DESIGN THE WRONG SHAPE

This is the sharpest finding in the session, and it is a finding about method
rather than about Kraken.

Everything built here rests on one structural fact: **the ceiling is per pair.**
If it were an account-wide total, then a per-pair check is not a slightly
inaccurate design — it is a design measuring something the venue does not
enforce, and every number in it would be wrong.

*(docs)* `docs.kraken.com/api/docs/guides/spot-ratelimits`, re-read live on
2026-09-04 as raw markdown, is unambiguous:

> "The open order limit is the maximum number of open orders **per pair**. When
> the open order threshold is reached, the engine will generate
> `EOrder:Orders limit exceeded` rejection message."
>
> | | Starter Tier | Intermediate Tier | Pro Tier |
> | Max open orders per pair | 60 | 80 | 225 |

**60 / 80 / 225 CONFIRMED**, unchanged from what entry 96 recorded in passing —
which is the figure this session was asked to verify rather than trust, in
keeping with entry [89.md](89.md) PART 2's standing rule that Kraken's own
documentation can be wrong about Kraken.

Then the second source was consulted, as it should have been, and **it appeared
to contradict the first on scope.** *(support)* article 209090607 (updated
2025-12-11) phrases the same limit as applying *"across each trading pair"* — a
phrase that reads just as naturally as an account-wide total. A **summarised
fetch of that page returned it as "The limit applies across all trading pairs
combined."** Taken at face value, that reading kills the per-pair design outright.

**IT WAS RESOLVED BY READING THE ARTICLE'S RAW TEXT, AND THE ARTICLE'S OWN WORKED
EXAMPLE SETTLES IT — AGAINST THE SUMMARY:**

> "You have 78 buy limit orders BTC/EUR and 60 sell limit orders on ETH/EUR. …
> The maximum limit for open orders for your account is 80. This means that you
> can place 2 more orders on BTC/EUR and 20 more open orders on ETH/EUR before
> you reach the maximum number of open orders on those pairs. **On other pairs,
> you can place 80 orders each.**"

Under an account-wide reading, 78 + 60 = 138 is already past 80 and the answer to
"how many more" is zero on both pairs. Under a per-pair reading it is 80 − 78 = 2
and 80 − 60 = 20, which is precisely what Kraken says, and the closing sentence —
eighty *more* on every other pair — admits no other interpretation.
**PER-PAIR, corroborated twice**, and `rate-limits.test.ts` now pins that exact
arithmetic (`intermediate − 78 === 2`, `intermediate − 60 === 20`) so the
reasoning is in the suite rather than only in this entry.

**⚠ THIS WAS CAUGHT ONLY BY INSISTING ON RAW SOURCE TEXT OVER A SUMMARY.** The
summary was fluent, plausible, and wrong about the one property the design turns
on. That is the same discipline that has corrected a wrong "fact" at nearly every
step of this Kraken build — entry 89's demo host that 301s to marketing, entry
91's documented example that was not one, entry 92's precision correction, entry
93's endpoint correction, entry 96's `ClosedOrders` contradiction and stale tier
table, entry 98's Batch-Cancel-is-not-Batch-Add. **The failure mode is always the
same: a confident restatement of a source is not the source.** A summary is
evidence about a document; only the document is evidence about the venue.

Two smaller notes from the same pass, both recorded rather than smoothed over:

- That support table is **stale in exactly the way entry 96 CORRECTION 4 found
  article 206548367 to be** — it lists only "Verified" (80) and "Verified with
  high limits" (225) and has **no Starter row at all**. So the second source
  corroborates two of the three numbers and **cannot corroborate the third**.
  Asserted in the test rather than glossed, so the weakest-evidence figure is the
  one named as such. The tier *set* is taken from *(docs)*, for the same reason
  `KrakenTier` is.
- *(docs)*, same page: the ceiling is *"agnostic of the API used, i.e. there is a
  shared limit across REST, Websockets and FIX"* — identical to the rate
  counters, so a future WebSocket order path consumes the same ceiling.

## PART 4 — THE OFF-BY-ONE, AND WHY PROXIMITY DID NOT IMPLY APPLICABILITY

`validateGridParams` already contains a ladder-vs-ceiling check, and it reasons
in `gridLines - 1`:

```ts
const buyLevels = BigInt(params.gridLines - 1);
const peakExposure = params.orderSize * buyLevels;
```

with the stated justification that *"the topmost line only ever holds a sell"*.
The new check sits **three lines away from that one**, does the same shape of
thing — take the ladder, compute a peak, compare it to a ceiling — and the number
was sitting right there.

**Reusing it would have been wrong.** That reasoning is about **money**: the top
rung holds a sell, a sell consumes no *quote* capital, so it contributes nothing
to peak exposure. The new ceiling counts **orders**, and the top rung is a real,
resting order regardless of what it cost to fund. `peakLiveOrders()` therefore
returns the full `gridLines`, derived from the structure that actually governs it
— `slots` is one entry per level and `claimSlot` is what holds it to one live
order each.

The size of the mistake is exactly one, which is why it deserves the space: it
would have been invisible in every test that did not sit on the boundary, and the
boundary is the only place a ceiling check is ever exercised. `grid.test.ts` now
pins it there deliberately, including the deliberately odd-looking
`expect(peakLiveOrders(p)).toBe(p.gridLines - 1 + 1)` — written that way so the
relationship to the capital check is legible rather than implied.

**THE GENERAL LESSON: two checks that look alike and sit beside each other in one
file can be measuring genuinely different things.** Before reusing a number from
a neighbouring check, verify that its *reasoning* transfers, not merely that its
*shape* does. Proximity and similarity are not evidence of applicability, and
here they pointed the wrong way.

## PART 5 — THE DESIGN: CREATION-TIME, NOT RUNTIME

The failure is a **configuration** fact, not a runtime one. It is fully knowable
the moment the bot is created, from a stored parameter, before anything exists to
go wrong. So the check goes where the other configuration checks go.

**PRECEDENT FOLLOWED EXACTLY.** `validateGridParams`' own docblock describes the
`exceeds_allocated_capital` failure as *"a bot is created happily and then fails
at the exchange when the ladder fills out, mid-run, with a position open, which
section 7.5 turns into a halt"* — a verbatim description of the bug in PART 1,
against a different ceiling. Same file, same call site, same "before any capital
is reserved" guarantee, same shape of thrown `GridError`. The new code
`exceeds_venue_open_order_ceiling` joins `exceeds_allocated_capital` in
`GridErrorCode`.

**A SIBLING FUNCTION, NOT A NEW PARAMETER, AND THE REASON IS A REAL CALL SITE.**
`validateGridParams(params, allocatedCapital)` is venue-blind, and the LLM
proposal path calls it venue-blind through
`validateWithRealValidator(params, allocatedCapital)` in `derive-parse.ts`, which
has no exchange to pass. Adding a required venue parameter would either break
that call site or force a venue to be invented for it — and an invented venue in
a safety validator is worse than no check. Kept separate,
`checkOpenOrderCeiling(exchange, peak)` reads `request.exchange`, which
`createGrid` already holds, and `derive-parse.ts` keeps compiling untouched.

**THE CONSEQUENCE IS STATED, NOT HIDDEN:** an LLM-proposed grid with too many
rungs is **not** refused at derive time. It is refused at `createGrid` — still
before any capital is reserved, still before any order exists, still before any
`bot_instances` row is written. It is not silently allowed through to placement.

**LAYERING.** `strategies/grid.ts` gained no import from `/src/exchange`, which
section 13's backtest requirement depends on: the strategy answers *"how many
orders can I hold"* (`peakLiveOrders`), and the caller owns the limit. The
ceiling module is correspondingly strategy-agnostic — it takes a **number**, not
`GridParams` — so the next strategy that needs it does not have to edit it.

**WHERE THE CONSTANTS LIVE.** `KRAKEN_OPEN_ORDER_CEILINGS` sits in
`kraken/rate-limits.ts` beside the two tier tables, because it is transcribed
from the *same docs page*, keyed by the *same* `KrakenTier`, on the *same*
per-pair axis, and read through the *same* `KRAKEN_DEFAULT_TIER` — splitting one
docs page across two files would cost the next person confirming a real account's
tier more than it bought. The **model** stays separate: nothing here touches
`AcquireCost`, `Budget` or the `RateLimiter` Durable Object, which is PART 2's
distinction enforced in code rather than asserted in prose.

**THE VENUE TABLE, AND WHY BOTH NULLS ARE HONEST.**
`OPEN_ORDER_CEILINGS: Record<ExchangeId, number | null>` is total, for the same
reason `BATCH_CANCEL_COSTS` is: a fourth exchange must **fail to compile** rather
than silently inherit Kraken's number. But its nulls are a **weaker claim** than
entry 98's, and the code says so — there, null is a finding (*no such endpoint
exists*); here it means only that **no figure has been verified**. Binance really
does publish a per-symbol `MAX_NUM_ORDERS` filter; `binance/filters.ts` does not
parse it and `SymbolFilters` has no field for it, so there is no verified number
to record and **a guessed constant in a creation-time refusal would reject valid
bots**. Wiring that filter through is its own session. A null venue keeps exactly
today's behaviour — the reactive path — which is worse than prevention and better
than a wrong refusal.

**THE HEADROOM: 5, AND IT IS POLICY, NOT A VENUE FACT.** The check allows
`ceiling − 5`, so a Starter-tier grid may be 55 lines. Five is sized against what
the *other* strategies can actually hold on a shared pair, which is **one resting
order each**: DCA gates every additional buy on `hasOpenOrder`, and a trailing
stop has a single entry. It absorbs that case specifically. It is small enough
not to meaningfully narrow a legitimate grid, and the constant's docblock states
plainly that it is a chosen number rather than a published one.

## PART 6 — THE KNOWN LIMITATION, STATED AS A LIMITATION

**This check is per-bot. The venue's limit is per-pair-per-account. Those are not
the same thing, and this entry does not claim otherwise.**

A true cross-bot count is not available without new infrastructure, and each
piece of that was checked rather than assumed:

- **`orders` has no `pair` column.** Pair lives on `bot_instances`, so counting
  open orders on a pair requires a JOIN across the two tables.
- **The existing index does not support the query shape.** `idx_orders_open` is
  `(bot_instance_id, status)` — keyed by bot, not by pair.
- **Nothing prevents two bots sharing one account and pair.** There is no
  `UNIQUE (account_label, exchange, pair)` on `bot_instances`, and Durable Objects
  are addressed by `idFromName(botInstanceId)`, not by account+strategy+pair.

So the concrete uncovered case, stated explicitly: **two 40-line grids on the
same pair and the same account. Each passes this check individually. Together
they need 80 resting orders on a pair that holds 60.** That bot will hit PART 1's
halt exactly as before.

This is **accepted as a known gap, not silently unaddressed**. It is pinned by a
test named *"does NOT catch two grids sharing one account and pair, and does not
pretend to"*, and it is written into `OPEN_ORDER_HEADROOM`'s docblock. Closing it
fully is real, separate work: a schema change or a new index, a cross-DO read on
the order-placement hot path from inside a Durable Object, and a decision about
what to do with the fact that any such count **lags the exchange** — which is
what reconciliation exists for and would need its own safety margin regardless.

The reactive path remains the backstop for precisely this case, which is why
PART 7's second note matters.

## PART 7 — TWO SMALL, HONEST NOTES

**1. A SECOND DIMENSION NOBODY HAD RECORDED: THE SCHEDULED-ORDER LIMIT.**
*(support)* 209090607, found during this investigation: scheduled orders have
their **own separate ceiling — 25 (Verified) / 40 (Verified with high limits) —
and they also count toward the open-order limit above.** A scheduled order is one
*"placed with a start time five seconds or more in the future"*. Neither entry
90, 96 nor 98 recorded that this dimension exists.

**Nothing is built for it, deliberately**, because this client cannot create one:
`KrakenClient` never sends `starttm` on any path, verified by grep. It is written
into `rate-limits.ts` anyway, and framed carefully — **the inertness is a property
of THE CLIENT, not of the venue.** The day any path sets `starttm`, that ceiling
becomes live, it is *tighter* than the one modelled here, and there is no error
string in `parse.ts` and no check anywhere that would catch it. The comment exists
so the next person does not have to rediscover it from the same support page.

**2. THE NEW `parse.ts` TEST CANNOT PROVE IT CAUGHT A BUG, AND SAYS SO.**
`DEFINITE_REFUSALS` now names `EOrder:Orders limit exceeded` explicitly, and a
named test asserts its classification. **This changes no behaviour whatsoever** —
the default arm already returned exactly that, so the assertion passed before the
set existed and passes now, and the mutation check in PART 8 could not red it.

It was written anyway, for a reason the test's own comment states rather than
implies: **a string classified correctly by accident and a string classified
correctly on purpose are indistinguishable from the outside, and they call for
opposite responses the day somebody edits the default arm.** The specific mistake
guarded against is one word wide — `EOrder:Rate limit exceeded` sits two
assertions above in `RETRYABLE_EXCHANGE_ERRORS` and differs by *Orders*/*Rate*.
It is not a sibling: a rate limit clears by waiting, a ceiling is a level, and
retrying into it re-sends forever while the book stays full. Classifying it
retryable by analogy with its near-namesake is now a visibly wrong edit rather
than a plausible one.

Also recorded here rather than left to be inferred: **`RETRYABLE_EXCHANGE_ERRORS`
is consulted BEFORE `DEFINITE_REFUSALS`**, so a string added to both would be
classified retryable. That precedence is asserted through the public function,
which is the only thing that can observe it.
