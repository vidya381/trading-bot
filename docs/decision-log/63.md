## PART 1 — THE QUESTION, AND THE VERDICT

**The question:** can a partially-filled-then-cancelled order leave a GRID bot's
tracked position overstated, the way it left `bot-b23y63` believing it held 3.7×
what it actually did?

**The verdict: NO. Grid was never vulnerable to this bug shape.**

**This is a "checked, clean" result, not an assumption.** The session was
explicitly instructed to *prove* immunity from source rather than infer it from
grid's model looking different — and that instruction earned its keep, because
**the obvious explanation for grid's immunity is wrong** (Part 2). A verdict
reached by pattern-matching "grid is per-line, so it must be fine" would have
been the right answer for the wrong reason, and would have left the next person
believing something false about the model.

## PART 2 — WHY GRID WAS NEVER VULNERABLE

### First, the WRONG explanation, recorded so it is not repeated

It is tempting to say grid is immune because it tracks state per grid line, so
"position" is a derived sum rather than a running total that can drift. **That is
false.** `GridLadder` (`src/strategies/grid.ts:202`) is a **hybrid**: it carries
per-level `slots[]` **and** real aggregates — `heldQuantity` (documented in place
as *"Base held: sum of filled buys not yet sold"*), `heldCost`, and
`realizedGross`.

`heldQuantity` is a direct structural analogue of `DcaPosition.quantity`: a
persisted running total that the stop-loss and breakout sells both read. **If it
could drift from reality, grid would be exposed exactly as DCA was.** Grid's
safety has to come from somewhere else, and it does.

### The real reason: `planFill` is ONE function that moves the position BOTH ways

Grid's equivalent of `applyEntry` is `planFill` (`src/strategies/grid.ts:781`).
The difference from DCA is not the shape of the data — it is that **DCA had an
adder with no subtractor, and grid has a single primitive handling both
directions.**

The property that matters, stated exactly: **on a partial fill, the position has
already moved BEFORE the early return, on both sides.**

```
// buy branch
heldQuantity: ladder.heldQuantity + fillQuantity,
heldCost:     ladder.heldCost + cost,
if (!fullyFilled) return { ladder: next, replacement: null, realized: ZERO };

// sell branch
heldQuantity:  ladder.heldQuantity - fillQuantity,
heldCost:      ladder.heldCost - releasedCost,
realizedGross: ladder.realizedGross + realized,
if (!fullyFilled) return { ladder: next, replacement: null, realized };
```

`fullyFilled` controls **only** slot-clearing and whether a replacement rung is
planned. **It never gates the position arithmetic.** That is precisely the
property fix 5 (entry 60) had to ADD to DCA, where the exit branch of
`#applyFillToOrder` was `if (!isExit) { applyEntry(...) }` with no `else` at all.

### Grid's exit path is genuinely separate code, and it is correct too

This was the specific place to look, because DCA's bug lived in the WIRING rather
than only in the model. Grid does not share that wiring.
`#applyGridFillToOrder` (`src/durable-objects/bot-instance.ts:4341`) dispatches
its exit case to its own function:

```ts
if (state.exitOrderId === order.clientOrderId) {
  return await this.#applyGridExitFill(config, state, effect.order, effect.fullyFilled, fill);
}
```

And `#applyGridExitFill` (`bot-instance.ts:4596`) decrements `heldQuantity` and
`heldCost` on **every** fill, prorating the cost against the current held
quantity and booking realized profit incrementally — with `fullyFilled` again
controlling only the clearing of `exitOrderId` / `exitKind` / `openOrderIds`.

**That is the proportional cost model with incrementally-booked PnL: the exact
design fix 5 introduced for DCA, already present on grid's liquidation path, and
arrived at independently and earlier.**

### The confirming check from history

`git show 84a7b6e -- src/durable-objects/bot-instance.ts | grep -E "^[+-]" |
grep -icE "grid|ladder"` returns **0**. Fix 5's own commit touched **zero** grid
or ladder lines — which is only consistent with grid never having needed it.

### Entry 09 records this as a DELIBERATE decision, not a lucky accident

The distinction matters: a model that happens to avoid a bug can lose that
property to a refactor by someone who never knew it was load-bearing. Entry
**09** shows this was designed, and says why the two strategies' shared field
stays coherent:

> *"Realized profit lives in `ladder.realizedGross`, and `state.realizedGross`
> (the field DCA also uses) is kept equal to it, so the shared field is
> meaningful for both strategies and nothing is double-counted."*

Entries **18** and **19** both treat `applyEntry` / `planFill` as the paired
position primitives of the two strategies, which is the same premise seen from
the other side.

### Grid is ALSO covered by the generic fixes — a second, independent layer

Stated as an ADDITIONAL protection, **not** as the reason grid is clean. Grid is
clean because of `planFill`; this is what would have contained the damage had it
not been.

- **Fix 1 (entry 57)** — `#gridExit` calls `#halt` → `#cancelOpenOrders` →
  `#recordCancellation`, whose signature takes `BotConfigBase`. Grid gets the
  gate that stops a cancellation locking in an understated fill count.
- **Fix 2 (entry 58)** — `#resumePass` is strategy-agnostic and refuses on an
  open drift alert keyed by `bot_instance_id`.
- **Fix 4 (entry 61)** — `liveOrderFindings` iterates
  `snapshot.state.openOrderIds`, which grid populates through
  `ladderOpenOrderIds`.

So even a hypothetical FUTURE gap in grid's position model could not become the
kind of **permanent, unrecoverable** damage DCA suffered before those three
existed. Grid is protected *and* precise — not "protected but imprecise."

## PART 3 — TWO UNRELATED FINDINGS

### (a) A plain `halt()` can leave grid's ladder slots stale — recorded, NOT fixed

`#gridExit` explicitly clears every slot after halting, with the reason stated in
place: *"The cancelled orders leave the ladder slots stale; clear them."* But a
**plain** `halt()` — manual, kill-switch, or reconciliation-driven — does **not**
clear slots. Three sites then rebuild `openOrderIds` **wholesale** from the slots
(`openOrderIds: ladderOpenOrderIds(ladder)`), which can re-add an id
`#cancelOpenOrders` had filtered out. `#foldTerminalState` returns early on
`isTerminal(order.state)`, so an already-terminal order re-added this way is
never removed again, and the poll re-reads it every 30 seconds indefinitely.

**Stated plainly: this costs rate-limit budget and log noise, NOT correctness and
NOT money.** It does not touch `heldQuantity`, `heldCost` or `realizedGross`, and
it is not a variant of the bug this entry was written to check for. It is
pre-existing.

**Not fixed here. Not scheduled.** Recorded as a known, low-priority item.

### (b) Checked and RULED OUT: fix 1's retention versus grid's derived `openOrderIds`

A plausible cross-fix hole, checked rather than assumed. Fix 1 keeps a refused
order in `openOrderIds` so the poll can still repair it — but grid DERIVES
`openOrderIds` from its ladder slots in three places, which could have silently
dropped exactly that retained id.

**It does not.** `#placeLiquidationSell` **appends** to the existing list
(`openOrderIds: [...current.openOrderIds, decision.clientOrderId]`) rather than
recomputing it, and a retained ladder order keeps its slot, so the derivation
preserves it. Recorded because a negative result on a plausible hole is worth as
much as a positive one, and because the next person will have the same worry.

## PART 4 — VERIFICATION METHOD, STATED HONESTLY

**This was a SOURCE-ONLY investigation.** No file was modified and **no live
system was queried by this session.** The verdict rests on reading `grid.ts`,
`bot-instance.ts`, one `git show`, and three prior decision-log entries.

**No live D1 query was run.** Three were specified and offered to the operator;
**as of writing, none has been run and no result has been reported back**, so
nothing in this entry rests on live data. They were offered as corroboration
rather than as a precondition, because the source-level proof does not depend on
them: `planFill` either decrements on a partial sell or it does not, and it does.

The queries, for whenever the operator wants them:

**1. Grid bots with the shape that exposed the DCA bug.**

```sql
SELECT b.id AS bot, b.status AS bot_status, b.archived,
       o.id AS order_id, o.side, o.status AS order_status,
       o.filled_quantity, o.quantity, o.updated_at
FROM orders o
JOIN bot_instances b ON b.id = o.bot_instance_id
WHERE b.strategy_type = 'grid'
  AND o.status IN ('cancelled', 'expired', 'rejected')
  AND o.filled_quantity > 0
  AND o.filled_quantity < o.quantity
ORDER BY o.updated_at DESC;
```

**A matching row would NOT indicate a bug**, and this is stated in advance so the
result is falsifiable rather than reassuring. Given `planFill`, every such fill
should already have moved `heldQuantity`. The rows say where to look, not that
anything is wrong. (D1 cannot see `heldQuantity` at all — it lives in Durable
Object storage — which is why this query finds an order shape rather than a
position error.)

**2. The corroborating check — how a real grid position error WOULD have
surfaced**, through reconciliation's existing grid-specific detector:

```sql
SELECT id, bot_instance_id, alert_type, severity, resolved, created_at, message
FROM alerts
WHERE alert_type LIKE '%uncovered_held_inventory%'
   OR alert_type LIKE '%order_state_drift%'
ORDER BY created_at DESC
LIMIT 50;
```

**3. Part 3(a)'s stale-slots finding, against live data:**

```sql
SELECT id, status, halt_reason, halted_at
FROM bot_instances
WHERE strategy_type = 'grid' AND status = 'halted' AND archived = 0;
```

For any bot returned, `GET /api/bots/:id` shows whether `openOrderIds` names
orders D1 records as `cancelled`.
