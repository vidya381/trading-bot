## PART 1 — THE GRID BREAKOUT THRESHOLD DISPLAY (Task A: built)

### The finding, and why it is NOT a bug

Live testnet bot **`bot-ri6iml`** (grid, `BTCUSD`, `gemini-main`) sat halted on an
upside breakout. Its CONFIGURATION panel showed:

> **BREAKOUT THRESHOLD:** Not set

while all of its halt alerts named a concrete number: *"breakout 6337800000000,
above the highest grid line 6325200000000"* — raw `Money` at SCALE 8, i.e.
**63378.00** and **63252.00**.

**The field was not broken and the value was not lost.** A prior investigation
step traced it end to end and the conclusion is worth stating plainly, because
the obvious reading is the wrong one:

- `breakoutThresholdPct` is an **optional percentage OVERRIDE**, nullable by
  design (`grid.ts:145`). Null is stored, null is served, null is displayed.
  The dashboard reads the very field the halt-check reads — `snapshot.config` IS
  the `GridConfig` handed to `gridDecide` (`serialize.ts:697`). There is no
  binding bug, no dropped field, no naming mismatch.
- What null MEANS is `breakoutPrice`'s default branch (`grid.ts:476-482`):
  **one grid step above the highest line** — `top + topRungGap(levels)` — which
  is spec 6.2 step 5 as resolved by **entry 09's decision 4** (*"a fixed default
  percentage — rejected"*, *"a mandatory parameter with no default — rejected"*).

So: **a gap, not a bug.** Nothing is stored, so there was nothing for the UI to
fail to render; the system simply had no concept of "the effective breakout
threshold" anywhere outside the decision function. `breakoutPrice` has exactly
one non-test call site in the repository — `grid.ts:727`, inside `decide()`. It
reaches no API response and no component.

**The label was a genuine defect on top of the gap**, and this is the half worth
fixing: "Not set" tells an operator that **no breakout protection is in force**,
on the detail page of a bot that had halted on breakout protection. The create
form's own help text for the same field says *"leave blank to use the default"*
(`CreateBot.tsx:1542`). Two screens in one app disagreed about whether blank
meant "nothing" or "the default", and the alert text was the third voice — the
only one naming a number.

### Three corrections to the working assumptions the task was briefed on

**1. `BotInstance.close()` already exists, is implemented, and releases capital.**
The brief stated *"there is no route to a `stopped` status that releases it"* —
right about the ROUTE, wrong about the MECHANISM. `bot-instance.ts:2588-2615`
cancels open orders through the halt path, calls `releaseBotCapital`, flips DO
state to `stopped`, writes a `bot.closed` audit entry and unsubscribes from the
feed. It is exercised from three test files. What is missing is **one line in the
route table** — `src/api/index.ts` lists start, halt, resume, liquidate,
apply-missed-fills, check-open-orders, archive, unarchive, and no close. This
materially changes what "build a stopped route" means: it is wiring, not design.

Entry 36 already said this in one clause — *"`BotInstance.close()` has no route in
the table"* — and it is restated here at full weight because the brief had
generalised it into "no mechanism".

**2. The bots' last known state was stale.** The most recent recorded live read
(entry 34, 2026-08-10T20:35:36Z, pinned in `concentration.test.ts:786-787`) has
both bots as **`status: "created"`** — never started, therefore never halted,
therefore not archivable at all, since `ARCHIVABLE_STATUSES` is
`["halted", "stopped"]` (`handlers.ts:919`). The brief's premise that both were
archived could not be checked from source. Part 3 settles it live: the brief was
right and the log was stale.

**3. `halt_manual` does not imply a human actor.** `halt("manual", …)` is the same
call the kill-switch worker (`workers/kill-switch.ts:97`) and reconciliation
(`workers/reconciliation.ts:385`) make. The alert type carries no actor. The
`audit_log.actor` column is what distinguishes them. Part 3 settles this live
too.

### 1. What archive actually does: two rows, nothing else

`archiveBot` (`handlers.ts:1009`) → `setArchived` (`handlers.ts:939`). The
complete write set is one boolean plus `updated_at` on `bot_instances`, and one
`audit_log` entry. **It does not touch `alerts`, `capital_ledger`, `status`, or
the Durable Object** — the DO is read for the response and never asked to mutate.

Not a delete, structurally rather than by promise: `Repository` exposes no
`delete` method, and `no-raw-d1.test.ts` fails the build if any file outside
`/src/db` reaches for the raw binding. `archived` is **orthogonal to `status` by
explicit design** (`schema.ts:186-189`: *"NOT a delete and not a status"*), so a
bot can be `stopped` AND `archived`.

The handler's own docblock states the capital consequence outright: *"an archived
bot still holds its allocation (only the `stopped` transition releases capital,
via `releaseBotCapital`), still counts toward the account-level totals."* The
dashboard's archive dialog agrees in words a human reads —
*"archiving is not closing"* (`ArchiveAction.tsx:157`).

### 2. THE FINDING: archiving forecloses the only path that resolves the alerts

The halt alerts are rows in `alerts`: `alert_type = 'halt_manual'`,
`source = 'bot-instance'`, `resolved = 0`, written by the unconditional insert in
`#halt` (`bot-instance.ts:4060`).

**Exactly four writers in the codebase set `resolved = true`, and none is
reachable by a human:**

| Writer | Scope | Can it close `halt_*`? |
| --- | --- | --- |
| `alerts/halt.ts:102` | the resume path only | **Yes — the only one** |
| `alerts/standing.ts:190` | the poll's own standing types | No |
| `reconciliation/reconcile.ts:1528` | ingested findings | No |
| `workers/reconciliation.ts:478` | `poll_blind` incidents | No |

`/api/alerts` is **GET only** (`api/index.ts:101`). There is no manual-resolve
route, no override, no admin action. The task's hypothesis was right: resolution
exists ONLY tied to a specific alert-producing code path, and **entry 27's fix is
the only owner of `halt_*` rows**.

**And `resume` is gated on not-archived.** `handlers.ts:202-207` refuses an
archived bot with `bot_archived` (409) *before* the Durable Object is called.
So today:

> The only way to resolve these alerts is to **resume** the bots. The only way to
> resume them is to **unarchive** first. Resuming makes them **running** — live
> bots trading real testnet capital, the opposite of disposing of them. Halting
> them again writes a **NEW** `halt_manual` alert, returning to the start.

**Two independently-correct pieces of code combine into a trap.** Entry 27's
resume-resolves-halt-alerts fix is right. Entry 26's archived-bots-cannot-resume
gate is right — *"a running bot must never be hidden from the default view"*. The
defect is in neither; it is in their composition, and it is invisible from either
one's own source.

**⚠ `close()` does NOT resolve halt alerts either.** `#closePass` writes a
`bot.closed` audit entry and never calls `resolveHaltAlerts`. A `stopped` route
built over `close()` exactly as it stands today would release the capital and
**still leave both alerts open**.

### 3. Entry 25's finding re-confirmed, and now known to be schema-enforced

`releaseBotCapital` (`capital/ledger.ts:491-545`) does three things: a conditional
update `{ id, status: { ne: "stopped" } }` → `{ status: "stopped" }` whose
`changes !== 1` throws `bot_already_stopped` (this is the mutual exclusion against
a double release); a decrement of `capital_ledger.total_allocated` by
`bot.allocated_capital` through the compare-and-swap loop; and a
`capital.released` audit row.

**`bot_instances.allocated_capital` is never cleared — and CANNOT be.**
`migrations/0001_initial_schema.sql:78` declares
`allocated_capital INTEGER NOT NULL CHECK (allocated_capital > 0)`. Entry 25
recorded that the value is left behind as history; what is added here is that
this is **not a design preference that could be revisited — the column rejects a
zero.** `status = 'stopped'` is the marker instead, exactly as the docblock says.

Consumers already honour it: `dashboard/src/accountTotals.ts:204` skips `stopped`
bots, and `src/research/concentration.ts` applies the same rule. Entry 34 took
both as rules rather than code, since `accountTotals.ts` lives in the dashboard
and touches no database.

**⚠ That exclusion rule has never run against real data.**
`src/research/README.md:538-542`: *"No bot in this account has ever been stopped,
so the rule has only ever run against fixtures."* Whatever happens next, these two
bots would be the first live exercise of it. Part 3 confirms this is still true.

### 4. Archive vs stop: five interpretations, NONE chosen

From source they are currently **orthogonal**: one is a visibility boolean, the
other a terminal member of the `status` enum about capital.

- **A — genuinely different states, both needed.** Archive = "hide from my list";
  stop = "return the money". A full disposal is two actions. ⚠ Cost: archiving
  alone silently leaves capital reserved, which is exactly what happened here,
  and the dialog already warning *"archiving is not closing"* did not prevent it.
- **B — one concept, two names.** "I am done with this bot" is a single intent
  and splitting it produced the stuck state. ⚠ Cost: archive is **reversible**,
  close is **irreversible** (`bot_already_stopped` throws on a second attempt and
  nothing un-stops a bot). Merging makes an unarchive button that can no longer
  restore what it hid.
- **C — archive stays visibility-only; a new terminal `stop` implies archiving.**
  One-directional; unarchive still works and still does not restart. ⚠ Cost:
  `unarchive`'s docblock argues it must never be gated, and this creates an
  "unarchived but stopped" state to reason about.
- **D — archive releases capital immediately; unarchive re-allocates it.** The
  operator's actual goal, stated after the investigation. Recorded in full in
  PART 4, with its open question.
- **E — do nothing; treat these two bots as accepted history.** The null option,
  listed because it is currently the default by inaction. ⚠ Cost: the
  unresolved-critical count stays permanently off by two, and that count is the
  number entry 18 went to some trouble to make meaningful.

**The coding session chose none of these, was instructed not to, and did not.**
The discriminating question it named: whether **irreversibility** is acceptable on
the control an operator reaches for most often.

Options enumerated for how a `stopped` route might work — also **not chosen**: a
thin `POST /api/bots/:id/close` over the existing method; the same plus
`resolveHaltAlerts` in `#closePass`; a close gated on a flat position (`close`
cancels orders but does not flatten inventory); close implies archive; alert
resolution as its own route independent of lifecycle (⚠ which cuts against
`/src/alerts`' one-owner-per-row rule — a human resolver becomes a second owner
for every standing alert in the system).
