### CONFIRMED, unchanged from entry 90

### ⚠ CORRECTION 1 — "no feedback channel" is right about REST and wrong about Kraken

Entry 90 PROBLEM 2 (d) recorded: *"Kraken sends no rate-limit headers of any
kind… local accounting is the only accounting."* The first half is **confirmed
live**: neither the public nor the authenticated response carried a rate-limit
header, and `access-control-expose-headers` listed only `date`,
`x-internal-auth`, `x-trace-id` — so there is not a hidden one either.

The general claim is wrong. **The trading counter is published.** WebSocket v2
`executions` subscribed with `ratecounter: true` carries:

- `ratecount` — *"the value of the user's trading rate-limit counter at the time
  of the event, as evaluated by the trading engine"*, per pair;
- `maxratecount` — *"the max rate counter value for the user transaction rate.
  It is based on user tier"*, on the snapshot.

`maxratecount` is the more valuable of the two: **the tier need not be
configured**. A limiter started on Starter's conservative numbers learns the
account's real threshold from its own traffic.

The subscription is **not built this session** (see PART 4). The seam is.

### ⚠ CORRECTION 2 — the REST counter is per API key, not account-wide

*(docs)* *"Each API key's counter is separate."* Entry 90 called it account-wide
and the `RateLimiter` Durable Object is one per account. Those coincide only
while an account holds exactly one key, which is what `credentials.ts` provides.
Two accounts sharing one key would be **under**-counted, which is the unsafe
direction, so it is stated in `rate-limits.ts` rather than assumed.

Also: *(docs)* says the REST counter *"is reduced every couple of seconds"* while
its table gives a per-second rate. The decay may be stepwise. It is modelled
continuously at the published rate, and nothing relies on sub-second recovery.

### ⚠ CORRECTION 3 — entry 90's table is incomplete, and one omission matters a lot

Rows entry 90 did not record: **Amend Order** (+1 fixed, +3 / +2 / +1 by age —
cheaper than Edit at every age), **Batch Add** (+n/2), **Batch Cancel** (+8n /
+6n / … — no per-order discount).

And, *(docs)*, beside Batch Cancel:

> **"If the rate counter in the batch exceeds maximum for a batch cancel, the
> requests in batch are still accepted."**

**This is the real answer to entry 90's risk-exit warning.** A single
`CancelOrderBatch` gets through where the eighth sequential `CancelOrder` is
refused. Entry 90's arithmetic stands; the venue simply provides an escape hatch
it did not find. Not taken this session — it needs a new `RestExchangeClient`
method — and recorded as its own decision in PART 5.

Further semantics entry 90 did not capture, all *(docs)* or *(support)*:

- The fixed count applies *"even if the transaction fails validation"* — a
  rejected AddOrder still costs 1.
- Age runs from *"the number of seconds since the order was created **or
  amended**"* — **amending resets the age clock**.
- Failed IOC auto-cancels incur **no** cancellation penalty.
- **⚠ Rejected post-only orders cost 9** (1 to place, 8 for the automatic
  cancel). `client.ts:456` deliberately does not set `post`. That was a
  fill-semantics decision; it is now also a rate-limit decision, and the
  docblock says so.
- **Max open orders per pair: 60 / 80 / 225.** A second per-pair limit entry 90
  records nowhere. On Starter it is the *same number* as the rate threshold. Not
  modelled — see PART 5.

### ⚠ CORRECTION 4 — the REST per-call cost, which entry 90 never recorded at all, and on which Kraken contradicts Kraken

| Source | Account history | Everything else | Trading |
| --- | --- | --- | --- |
| **docs** | "Ledger/trade history calls increase the counter by `2`" | +1 | separate limiter |
| **support** (updated 2026-08-10) | "(Ledgers, TradesHistory, **ClosedOrders**) — **+4**" | +1 | 0 |

They differ on the multiplier **and** on the membership of the expensive class.
Only the support page names `ClosedOrders` — and `ClosedOrders` is an endpoint
this client really calls, on the cancel path (`client.ts:581`) and the status
path (`client.ts:654`). The disagreement is not academic here.

Neither source is wholly reliable: the *same* support article's tier table is
**stale**, listing only "Standard 20 / −0.5" and "Higher Limits 20 / −1" with no
Starter row at all. So the tiers are taken from docs and the endpoint costs from
support — the more specific source for each fact, stated rather than blended.

**DECISION: charge 4.** The higher figure, from the only source that names the
endpoint. Over-charging throttles; under-charging spends a counter of 15 twice
as fast as the venue counts it, on the exact path a halt runs down. The
contradiction is written into `KRAKEN_REST_COUNTER_COSTS`'s docblock and asserted
in `rate-limits.test.ts`, so changing it to 2 is a deliberate edit against a
stated reason rather than a tidy-up.

**This choice turned out to change where the risk sits — see PART 3.**

## PART 2 — THE FOUR STRUCTURAL CHANGES

`RateLimiterPort` — `acquire`/`release` with a re-presentable ticket — is
**unchanged**, as entry 90 asked. So is the Durable Object's ticket, queue,
priority-ordering and head-of-line machinery.

### (a) Decay vs sliding window → `DecayingCounter`, beside `WeightBudget`

A new class in `shared/rate-limiter.ts`, not a reshaped `WeightBudget`. Its whole
state is `(value, at)`, so `used(now) = max(0, value − decay × elapsed)` and

    wait = (used + wanted − ceiling) / decayPerSecond

is closed-form and exact — it describes what the venue is actually doing, where a
window's "when does the oldest entry expire" describes something Kraken does not
do at all. Two consequences worth naming: the snapshot is two numbers instead of
a list that grows with traffic, and the exchange-reported figure needs **no
expiry rule**, because a decay ages it on its own at the venue's own rate.

Both classes now implement a shared `Budget` interface, so the Durable Object's
grant logic is written once.

### (b) One budget vs two → `acquire` takes a cost vector

`AcquireRequest.weight: number` became `AcquireRequest.cost: AcquireCost`:

```ts
{ rest: number; trading?: { pair: string; count: number } }
```

The object holds one account counter plus a lazily-created `Map<pair,
DecayingCounter>`. A grant is **all-or-nothing across every counter the call
names**, under one ticket in one queue — which a Kraken cancel needs, since entry
90 DECISION 2 makes it one engine charge *and* one REST read.

`#claimedAhead` returns a **map keyed by counter** rather than a total. That is
load-bearing: a single total would let a cancel queued on `BTC/USD` hold back a
cancel on `ARB/USD` that shares none of its counters — refusing traffic the venue
would accept, on the risk-exit path.

And the reserve is now **per counter**, which is the direct fix for entry 90's
complaint that `RISK_EXIT_RESERVE_FRACTION` was *"denominated in a currency
(weight, per account) that Kraken's trading limiter does not use"*. Each pair
counter carries its own risk-exit reserve.

`AcquireRequest` also carries `exchange`, checked against the venue the object is
already serving. An account has exactly one exchange, so two venues at one
limiter is a wiring bug; it is refused as `wrong_exchange`, without a ticket.

### (c) Cost by method name → cost as a function of the call

`MethodWeights = Record<keyof RestExchangeClient, number>` became

```ts
type MethodCost = (context: { pair: Pair | null; orderAgeMs: number | null }) => AcquireCost;
type MethodCosts = Record<keyof RestExchangeClient, MethodCost>;
```

Still a `Record` over `keyof RestExchangeClient`, so entry 90's compile-time
property survives: a new interface method fails to compile until its cost is
declared. Binance and Gemini become constant functions built from their existing
tables — **not one existing call was re-priced.**

Age reaches the gate through an optional `orderPlacedAt(pair, clientOrderId)`
resolver returning the placement time (which is what a call site holds:
`orders.created_at`). Two fail-closed rules:

- **Unknown age is charged +8**, the dearest rung. No resolver, no record, or a
  resolver that *throws* — all three collapse to the same answer, because the
  path least likely to hold a local record is reconciliation, which cancels
  orders this system has lost track of. A halt that could not cancel because its
  gate could not read a timestamp would be a risk control defeated by its own
  accounting.
- **Ages are biased one second younger** before the ladder is walked, because
  `orders.created_at` is written *before* Kraken accepts the order — so the
  measured age runs long, and every rung gets cheaper with age. Naive measurement
  under-charges exactly at the boundaries. The real fix is to record Kraken's own
  `opentm`; that is a client and schema change and is not in this diff.

The cost is computed **once**, before the retry loop. Re-pricing per attempt
would let an order age into a cheaper rung mid-queue, so a caller that waited
long enough would be granted a charge smaller than the one it queued for — and
everything behind it would have been ordered against a claim that no longer
existed.

### (d) No feedback → the seam, without the subscription

`syncFromExchange` now accepts `(pair, ratecount, maxratecount, at)` alongside
its existing `(usedWeight, at)`. A reported `maxratecount` rebuilds that pair's
counter on the real threshold, carrying the spend across, and sets `limitSource`
to `exchangeCounter`.

**It is one signature with union-typed parameters, not two overloads, and that is
not a style choice.** It was two overloads; a `DurableObjectStub<T>` is built by
a mapped type, a mapped type keeps only the **last** signature of an overloaded
method, and the stub promptly stopped satisfying `WeightReporter` — breaking
`workers/exchange.ts`'s handoff to `BinanceClient`. A platform constraint,
recorded at the method.

## PART 3 — ⚠ THE FINDING THIS SESSION TURNED UP: THE BINDING CONSTRAINT IS NOT WHERE ENTRY 90 LOOKED

Entry 90's worst case reasoned about the **engine** counter: a fresh cancel costs
8 against a Starter threshold of 60, so *"roughly seven such cancels exhaust a
Starter threshold of 60 on that one pair."* That is correct, and the test
`reproduces entry 90's worst case` drives it through the real object.

But a real Kraken `cancelOrder` is not only an engine charge. DECISION 2 makes it
a cancel **plus one `ClosedOrders` read**, and `ClosedOrders` is account history
— 4 units of a Starter REST counter whose entire ceiling is 15:

    engine: 60 / 8 = 7 cancels
    REST:   15 / 4 = 3 cancels     <-- binds more than twice as early

**The account-wide counter is the tighter constraint on a halt, not the per-pair
one.** This would have been invisible to a design that only added the second
budget, and it is invisible to entry 90's analysis, which priced the engine and
did not price the REST leg at all — because entry 90 never recorded the REST
per-call costs (CORRECTION 4).

It also puts real weight on the +2 / +4 contradiction: **on the docs' reading of
2 this would be 7 cancels rather than 3.** That is why the contradiction was
resolved deliberately, with the conservative figure and a stated reason, rather
than noted and left open.

Pinned by `⚠ but a REAL Kraken cancel is bound by the REST counter first`.

## PART 4 — THE THREE DECISIONS TAKEN, AS INSTRUCTED

1. **Starter tier.** No real Kraken account exists, so no tier has been
   confirmed. Starter is the most conservative *real* tier — smallest counter and
   slowest decay on both budgets — so every model built on it over-estimates for
   a higher account and never under-estimates. `KRAKEN_DEFAULT_TIER` is one
   constant, and `rate-limits.test.ts` asserts it really is the conservative one
   on all four axes, so confirming the real tier is a one-line change.
2. **WebSocket feedback: seam only.** `syncFromExchange` takes the per-pair form
   and `maxratecount` rebuilds the ceiling; **no subscription is built.** A
   persistent WebSocket held in a Durable Object is real scope and its own
   decision.
3. **`ClosedOrders` at 4**, with the contradiction written into the code comment
   and this entry rather than silently resolved. See CORRECTION 4 and PART 3.

## PART 5 — DELIBERATELY NOT IN THIS DIFF

- **The batch-cancel escape hatch.** `CancelOrderBatch` is accepted even when it
  blows the counter, which is the genuine answer to entry 90's worst case. It
  needs a new `RestExchangeClient` method, so it is a separate decision. Recorded
  in `rate-limits.ts`'s header so it cannot be lost.
- **The open-order ceiling** (60 / 80 / 225 per pair). A **level**, not a rate:
  it does not decay and does not belong in a decaying counter.
- **Recording Kraken's `opentm`**, which would remove the need for the age safety
  margin.
- **Retiring `KRAKEN_REQUEST_COSTS`.** Kept — a request *count* and a counter
  *cost* are different facts — with its docblock now pointing at the real model.

Entry 95 claimed the venue-wiring derivation would close *"on its own the moment
that row lands, with no manual step."* **It did, and this is the receipt.**

Landing `METHOD_COSTS.kraken` made `hasRateLimitCostModel("kraken")` true, which
made `isWiredExchange("kraken")` true, which turned **eight tests red without a
single line of wiring being edited** — every one of them a test that had encoded
"Kraken is not wired". Each was updated to the new truth, not to pass:

- `rate-limited.test.ts`'s two long-red tests went green — the `tsc` error at
  `rate-limited.ts:196`, standing since entry 90, is **gone**.
- `kraken/client.test.ts`'s placeholder assertion said *"if this test ever fails,
  that session has begun and this expectation is what it should replace."* It was
  replaced, with the inverse.
- `create-bot-venue-gate.test.ts`'s precondition *"still refuses kraken, on venue
  wiring"* has **fallen**, and now records that the last remaining blocker is
  migration 0006's `CHECK (exchange IN ('binance','gemini'))`. Its inertness loop
  iterated `wiredExchanges()` on the reasoning that it *"widens on its own the
  day Kraken is wired"* — it did, and that broke the block, because the venue it
  let in is the one venue the gate is *for*. Now derived from the rule itself.
- **Two regression tests had their subject removed by this change**, and rather
  than delete them, both now **construct** an unwired venue by removing the
  `kraken` row for the duration (`api.test.ts`'s unregistered-account fallback,
  `exchange-attachment.test.ts`'s halt-by-name). Borrowing whichever venue
  happens to be unwired is the staleness entry 95 removed; these guard the *next*
  venue that is half-added.

**⚠ A BUG THIS SESSION INTRODUCED AND CAUGHT.** The first `#adoptExchange`
rebuilt the account budget whenever the venue was first named. That would discard
a budget **restored from storage** — including one restored from the pre-Kraken
persisted shape, which is exactly the state that has spend in it and no venue
recorded — and hand a full ceiling to an account that had already spent one: the
double-rate failure the persistence exists to prevent, arriving through the door
built to prevent it. It now rebuilds only on a genuine shape change, and
`does not hand a fresh budget to a restored object when it first names its venue`
pins it. The pre-Kraken persisted shape is still read, once, on wake.

## PART 7 — TESTS, AND WHAT "REAL DATA" COULD AND COULD NOT MEAN HERE

**92 tests added.** The honest limit, stated in `rate-limits.test.ts`'s header
rather than glossed: this is the one Kraken area where live fixtures are
impossible. Kraken publishes no rate-limit headers (**confirmed live**, both
paths), so there is no response to capture; and observing the counters directly
means deliberately exceeding them on a funded account.

So the constants are pinned against the **documented** tables, each block naming
its source and date, and the contradiction is asserted as a contradiction. The
strongest evidence available is **Kraken's own worked examples**, which check the
