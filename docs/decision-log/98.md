## PART 2 — THE INTERFACE DECISION, WHICH IS THE REAL DECISION IN THIS ENTRY

### The two other venues were checked, not assumed

Entry 90's whole method was that a venue's behaviour is read from that venue's
own current reference. The same standard applies to a question about whether a
capability is shared, so **Binance's and Gemini's real current APIs were read
before anything was designed** — not recalled, and not inferred from what this
codebase already calls.

**Binance spot** publishes exactly three cancellation endpoints:

| Endpoint | Cancels |
| --- | --- |
| `DELETE /api/v3/order` | one order, by `orderId` or `origClientOrderId` |
| `DELETE /api/v3/openOrders` | *"Cancels all active orders on a symbol"* |
| `DELETE /api/v3/orderList` | one OCO/OTO order list |

**Gemini** publishes three: `/v1/order/cancel` (one order), *Cancel All Session
Orders*, and *Cancel All Active Orders*.

**Neither venue has any endpoint that takes a LIST of order ids.** Binance's
`orderList` form cancels one OCO list, a construct this system never creates.

### ⚠ "Cancel all on this symbol" IS NOT A WEAKER VERSION OF THIS CAPABILITY

This is the part that would have been easy to get wrong, and it is a safety
distinction rather than a technicality.

`bot_instances` **has no uniqueness constraint on `(account_label, pair)`** —
checked in `migrations/0001_initial_schema.sql`, which constrains `id`,
`strategy_type`, `status`, the DCA take-profit rule and the halt-reason rule, and
says nothing about the pair. **Two bot instances may legitimately run the same
market on the same account.** Nothing in the schema, the creation path or the
capital ledger forbids it.

So `DELETE /api/v3/openOrders?symbol=BTCUSDT`, issued during one bot's section
7.2 halt, would **cancel a completely unrelated bot's entire live ladder** —
orders that bot still believes are resting, that its poll is still watching, and
that its `openOrderIds` and ladder slots still name. The victim bot would not
halt, would not alert, and would discover the damage only when reconciliation
next ran.

Offering that as the Binance implementation of a method named `cancelOrderBatch`
would put a foot-gun behind a name that reads as safe. **The two venues do not
have a smaller version of this capability. They have a different and, here,
actively destructive one.**

### The rejected alternative, and why it recreates entry 90's own bug

The obvious shape was a **required** method on `RestExchangeClient`, implemented
on Binance and Gemini by looping `cancelOrder` internally.

**Rejected.** It reads as one request and costs N. The gate prices a call from
`METHOD_COSTS` **before** the call is made, keyed by the method name, so a
looping implementation would be charged **one** call's budget while issuing N
calls' worth of traffic — on the risk-exit path, on a halt, cancelling a ladder.

That is not a new hazard invented for this entry. It is precisely the mismatch
entry 90 PROBLEM 2 exists to describe: **a call spending a budget that does not
describe what it actually does**, discovered there as Kraken's per-pair engine
counter being charged against an account-wide weight, and reappearing here as one
method name standing in for N requests. Entry 96 CORRECTION 2 and the
`RateLimitedExchangeOptions.exchange` docblock both record what that class of
error already cost this system once: every Gemini account in production and
testnet gated against Binance's numbers, silently, because a wrong weight
produces no error.

A stub that instead **threw** was rejected for a simpler reason: it makes every
caller write the runtime check anyway, while the type says the method is there.

### DECIDED

**An optional capability, checked at runtime, per venue.**

```
BatchCancellingClient   — cancelOrderBatch() + batchCancelMaxOrders
supportsBatchCancel()   — a runtime guard on method presence
```

`RestExchangeClient` is **unchanged**. A venue that cannot do this does not
implement it, does not stub it, and does not lie about it.

**The guard is runtime rather than static, and that is forced rather than
chosen.** Every call site holds a `RestExchangeClient` that has already been
through `withRateLimit` and, on the halt path, `withPriority` — and
`withPriority` deliberately returns the *plain interface* so a call site that has
chosen its priority cannot choose again (its docblock says so). A compile-time
capability cannot survive that seam. Method presence can.

`RateLimitedExchange` therefore **defines `cancelOrderBatch` conditionally, in
its constructor**, and only when BOTH hold:

1. the wrapped client implements it, and
2. `BATCH_CANCEL_COSTS[exchange]` is not `null`.

Condition 2 is fail-closed: a client that somehow offered the method on a venue
with no cost entry would be an **uncosted call through the gate**, which is the
one outcome `exchange/rate-limited.ts` exists to prevent. `withPriority` rebuilds
the wrapper over the same inner client, so the capability is **re-derived** at
that seam rather than copied — tested directly, because a capability lost at
`withPriority` is a capability that never runs, the halt path being its only
caller.

`BATCH_CANCEL_COSTS` is a **total `Record<ExchangeId, BatchCancelCost | null>`**,
not a `Partial`, for the reason `METHOD_COSTS` is total and
`resolveExchangeForAccount`'s switch has no `default`: a fourth venue must fail
to compile until somebody has looked. Both `null`s are **findings**, written out,
not placeholders.

## PART 3 — THE RESPONSE-SHAPE FINDING: KRAKEN CONTRADICTS KRAKEN, AGAIN

Entry [89.md](89.md) PART 2 established that Kraken's documentation can be wrong
about Kraken; entries 93 and 95 each caught a documented fact that had gone
stale. So `docs.kraken.com/openapi/spot-rest.yaml` was **fetched raw and read
directly (2026-09-04)** rather than taken from a summary.

### What the response actually is

```yaml
  /private/CancelOrderBatch:
    post:
      responses:
        '200':
          description: Open order cancelled.
          content:
            application/json:
              example:
                error: []
                result:
                  count: 2
```

**There is no `schema` key. Only an `example`.** No per-order array, no ids, no
statuses, no filled quantities.

**⚠ AND THE CONTRAST IS WHAT MAKES THAT DELIBERATE RATHER THAN A GAP IN THE
READING.** The neighbouring `AddOrderBatch`, in the same document, **does**
declare a response schema, **does** return a per-order `orders` array, and its
response description reads *"The order of returned `orders` in the response array
is the same as the order of the order list sent in request"*. **Kraken knows how
to write a per-order batch response. It did not write one here.**

### The internal contradiction

The `batchcancel` **request** schema disagrees with its own example:

- `orders` is **declared** as `type: array` of `type: object`, each carrying
  `txid`;
- the same schema's `example` shows `orders` as an array of **bare strings**:

```yaml
      example:
        nonce: 1695828490
        orders:
          - OP5V2Y-RYKVL-ET3V3B
          - OP5V2Y-7YKVL-ET3V3B
```

Both cannot be right. **`cl_ord_ids`** — the field this client uses, because the
interface hands it client order ids — is declared as an array of
`{cl_ord_id: string}` and carries **no example at all**, so there is exactly one
documented shape for it and that is what is sent.

### DECIDED

**Treat the response as aggregate-only, and read each order's real outcome back.**

`count` is carried through as `BatchCancelResult.cancelledCount` and is
**explicitly documented as unattributable**: a batch of eight answering `count: 6`
says six were cancelled and does *not* say which six. A shortfall is an **ordinary
answer**, not an error — the same "already filled, already cancelled" case
`parseCancelResult` records for a single cancel.

Then **one `ClosedOrders` read for the whole batch**, and each requested id is
resolved from it into a `BatchCancelEntry`:

- `resolved: true` with the order the read actually saw, or
- `resolved: false` with a reason.

A discriminated union, not an optional `order`, so a caller **cannot read a final
state nobody observed**.

**This is entry 90 DECISION 2's discipline extended, not weakened.** One cancel,
one read, never a loop; and an id the one read did not see is reported honestly
rather than fabricated into "cancelled, nothing filled" — which would be a
quantity nobody observed, in the field that decides the position a halted bot is
left holding. `parseBatchCancelResult` is deliberately **separate** from
`parseCancelResult` rather than reusing it with a different context string,
because reusing it would report `pending: false` — an assertion that Kraken said
the cancels had taken effect, which Kraken did not say.

The read is **deliberately unfiltered**: `ClosedOrders` accepts one `cl_ord_id`
and this method has up to fifty, so asking per id would restore exactly the
per-order read cost the batch exists to remove. Matching is local, which is what
`#singleOrder` was already doing anyway — and `#singleOrder` is **reused whole**,
so the batch path cannot be laxer than the single-cancel path about a duplicate
id or an order returned on the wrong market.

**The limit of one read is stated rather than hidden:** `ClosedOrders` returns a
bounded recent page, so an id pushed off it by other account traffic comes back
`resolved: false`. That is the safe direction and the same treatment a single
cancel's empty read gets — keep the order open, alert, let section 9 settle it.

## PART 4 — THE JSON SIGNING FINDING, AND HOW IT WAS VERIFIED

`CancelOrderBatch` takes an **array**. `buildBody` is `URLSearchParams`, which can
express a flat map of scalars and nothing else, and **Kraken documents no form
encoding for this parameter anywhere** — not in the endpoint reference, not in the
OpenAPI document, not in the auth guide. Inventing one would be a guess about a
venue's parser, on the halt path.

**Kraken documents the JSON path itself**, which is why this is transcription
rather than invention. Its own signing helpers on
`docs.kraken.com/api/docs/guides/spot-rest-auth` (read 2026-09-04) **branch on the
payload type**:

```js
// Node
if (typeof data === 'string') {
  const jsonData = JSON.parse(data);
  encoded = jsonData.nonce + data;          // ← raw JSON text IS the "POST data"
} else if (typeof data === 'object') {
  const dataStr = querystring.stringify(data);
  encoded = data.nonce + dataStr;
}
```

```go
// Go
case string:
    var jsonData map[string]interface{}
    if err := json.Unmarshal([]byte(v), &jsonData); err != nil { return "", err }
    encodedData = jsonData["nonce"].(string) + v
```

Two facts fall out, and **only the Go snippet reveals the second**: the "POST
data" in `SHA256(nonce + POST data)` is the **raw JSON text**, and the nonce
inside it is read back as a **string** — `jsonData["nonce"].(string)` would panic
on a JSON number, while Node's `+` would silently coerce one. So `buildJsonBody`
writes `"nonce": "1616492376594"`, and `signJson` **refuses** a body carrying a
numeric nonce rather than producing a well-formed signature Kraken answers
`EAPI:Invalid signature` to.

`signJson` parses the body and compares its `nonce` — stricter than `sign`'s
`startsWith("nonce=")` check, not looser, and it catches three things that check
cannot see. The cryptography itself is **shared** via a private `#signRaw`, so the
venue's algorithm is written down once and neither caller can reach it without
first proving the body carries the nonce being signed.

### ⚠ THE VERIFICATION METHOD, STATED PLAINLY, BECAUSE THE OBVIOUS TEST IS WORTHLESS

Kraken publishes **no worked example for a JSON body** — its only one is the
form-encoded `AddOrder`. So an expected signature cannot simply be quoted, and a
test that derived the expectation the way the code derives it would agree with a
broken implementation. `signing.ts`'s own header already records that this signer
has three separate ways to be broken while still returning a well-formed base64
string.

**So the trust chain has two links, in this order:**

1. `krakenSignatureFromDocs` is written in the test **from the quoted snippets
   above**, not from `signing.ts`. It is first pointed at Kraken's
   **form-encoded published example** and asserted to reproduce
   **`4/dpxb3iT4tp/ZCVEwSnEsLxx0bqyhLpdfOpc6fn7OR8+UClSV5n9E6aSS8MPtnRfp32bAb0nmbRn6H8ndwLUQ==`**
   — a number **Kraken published**, not one this system computed. That
   establishes the reimplementation is right.
2. **Only then** is that same reimplementation used to judge `signJson` on a JSON
   body.

The chain therefore ends at a value Kraken published, rather than at this
implementation agreeing with itself. A further test signs two JSON documents that
parse equal but differ by whitespace and asserts the signatures **differ**, which
pins that the signer signs the bytes it was given and never a re-serialised copy
— the failure mode that yields a signature verifying against a body nobody sent.

## PART 5 — PREFERRED AT TWO ORDERS, NOT KEPT AS AN EMERGENCY FALLBACK

The alternative considered was to keep the sequential loop and reach for the
batch only when the run was about to exceed the per-pair budget. **Rejected, on
four grounds.**

**1. It is never more expensive, on either counter.** Kraken gives batch cancels
no per-order discount (PART 6), so the engine charge is **identical** to the same
orders cancelled singly — it is literally the sum of the same rungs. The
account-wide counter is where it differs, and it differs a lot: **one**
follow-up `ClosedOrders` read for the whole set instead of one per order. Eight
cancels cost **4 units instead of 32**, on a Starter counter of **15**. There is
no dimension in which preferring it costs more.

**2. One round trip instead of N, and the window is itself a hazard.**
`#cancelOpenOrders`' own existing comment records what went wrong in that window
once already: the poll added a grid replacement mid-sweep and the sweep's closing
write dropped it — "a live order on the exchange, no longer tracked, no longer
polled, and never cancelled, on a bot that had just been halted". Every awaited
cancel widens that window, and a throttled one widens it by up to
`DEFAULT_MAX_WAIT_MS` (60s). Collapsing eight round trips into one **shortens the
race** rather than reasoning about it.

**3. A fallback fires too late to be the escape hatch.** Kraken's guarantee is
that a batch overshooting the counter is still accepted. But a fallback triggers
only *after* the sequential run has already spent the counter down and cancelled
part of the ladder — so it arrives at a drained counter and a half-cancelled bot.
**The venue's promise is worth most when the batch is the first thing tried.**

**4. Code that only runs in an emergency is untested in the conditions that
matter.** Fallback-only puts the least-exercised path on the highest-stakes
event: a halt of a freshly-laid grid. Preferring the batch means the **ordinary**
halt exercises it. Making the safe path the *normal* path rather than a rare
backup is itself a safety property, and this log has the scar to prove it —
entry 96's whole reason for existing was a risk-exit reserve denominated in a
currency Kraken's limiter does not use, which never fired correctly because
nothing ordinary ever ran it.

**The threshold is TWO**, not something higher: at n=1 a batch buys nothing at
all — same engine rung, same single read, one request either way — while spending
a less-verified code path; at n=2 it already halves both the account-counter cost
and the round trips. Pinned by a test that was **mutation-checked**: changing
`< 2` to `< 1` makes it fail.

### ⚠ THE FALLBACK IS NARROW, AND THE NARROWNESS IS THE POINT

**A NON-RETRYABLE failure falls back to sequential cancels.** That is the venue
saying it understood the request and refused it — a rejected body shape, a pair it
does not list, a batch this client refused to send. **Nothing was cancelled**, so
re-issuing as singles is not a second cancellation of anything. This branch is not
hypothetical: PART 3 and PART 4 both record that the body shape is
**documented, not live-verified**, and that no unauthenticated probe can settle it
because Kraken checks the key before the parameters. If that encoding is wrong,
this is what keeps a halt cancelling orders instead of merely alerting about all
of them.

**ANY OTHER failure does NOT fall back**, and the distinction is section 5.6's:

- `transport` — the request left this process and its effect is **unknown**.
  Re-sending as N single cancels would spend the engine counter **a second time at
  the worst possible moment**, on orders that may already be cancelled.
- `rate_limited` — nothing was sent, and the sequential path costs strictly
  **more**, so it cannot succeed where the batch did not.

Both leave every id mapped to the failure, and `#cancelOpenOrders`' existing
`!isUsable` branch does what it has always done: keep the order open, alert
`cancel_failed`, let section 9 settle it. **A successful batch carrying unresolved
entries** is treated the same way — the batch *was* accepted, so those orders'
fate is unknown rather than untried, and they are not re-cancelled.

**Degradation is never silent.** A fallback raises a `batch_cancel_unavailable`
warning naming the venue's own refusal. Quietly reverting to the expensive path is
exactly how a broken batch endpoint would go unnoticed until the counter ran out
again — which is the failure this entry exists to close.

Everything below the cancellation in `#cancelOpenOrders` is **unchanged**: the
sweep judges a batched result and a sequential one with the same code, which is
what kept the diff to one map lookup at the call site.

## PART 6 — THE COST MODEL, AND THE ASSUMPTION THAT WOULD HAVE HALVED IT

### ⚠ BATCH CANCEL DOES NOT MIRROR BATCH ADD

Re-read live from *(docs)* on 2026-09-04 rather than carried over from entry 96:

| Transaction | Fixed | <5s | <10s | <15s | <45s | <90s | <300s |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Add Order | +1 | — | — | — | — | — | — |
| **Batch Add** | **+(n/2)** | — | — | — | — | — | — |
| Cancel Order | — | +8 | +6 | +5 | +4 | +2 | +1 |
| **Batch Cancel** | — | **+(8×n)** | +(6×n) | +(5×n) | +(4×n) | +(2×n) | +(1×n) |

Entry 96 CORRECTION 3 recorded Batch Add at `+(n/2)` — a genuine **half-price**
bulk discount. The natural assumption is that Batch Cancel mirrors it. **It does
not. Batch Cancel has no per-order discount at all.**

Had symmetry been assumed, the gate would have charged **32 where Kraken charges
64** for eight fresh cancels — **half**, in the **undercharging** direction, on the
risk-exit path, on the exact counter entry 90's worst case is about, at the exact
moment a halt is running it down. There is a test asserting the **non**-equality,
not just the value.

**The cost takes a list of ages, not a count.** The published `+(8×n)` form prices
a batch whose orders sit in one age band; a real ladder laid over several minutes
does not. So `krakenBatchCancelCost` **sums each order's own rung** — which
reduces to exactly `8n` when every order is under five seconds, and is provably
never cheaper than the same orders cancelled one at a time, **because it is that
same sum**. A `null` age is charged the maximum per entry, `krakenCancelCost`'s
fail-closed rule applied per order rather than relaxed for the batch.

### THE STRUCTURAL CHANGE: `Budget.record`

Kraken's guarantee — *"the requests in batch are still accepted"* — means **the
gate must not be the thing that refuses this call**. Refusing locally protects
nothing (the venue was never going to refuse) and would stop a halt from
cancelling its ladder: entry 90's worst case arriving by the other door.

But **not refusing is not the same as not counting.** Kraken's own counter really
does end up over its threshold, and anything issued afterwards must see that.

So `AcquireCost.trading` gained an **`unconditional`** flag, and `Budget` gained
**`record(weight, now)`** — applied, never checked. In the Durable Object an
unconditional charge is excluded from the ceiling test, the blocked test and the
queue-claim map (`costKeys`), and is applied through `record` instead of
`consume` at the end. Passing it through `consume` would trip the
"internal inconsistency" guard **precisely when the counter is where this whole
mechanism exists to work from** — already past the threshold — turning the escape
hatch into an exception thrown at the gate during a halt.

**`DecayingCounter.record` is the one place a counter may legitimately exceed its
own limit.** It must be able to: a counter clamped at 60 would claim recovery
twenty seconds early after an 80-unit batch, which is under-counting on the very
counter the hatch just overshot. Everything downstream already copes —
`usedWeight` decays whatever it holds, `remainingFor` floors at zero, `waitFor`
walks from the real value — so an overshoot simply takes proportionally longer to
drain, exactly as the venue's own does. Tested directly, including the drain
arithmetic at ±1 second either side of the boundary.

### ⚠ THE EXCEPTION DOES NOT REACH THE ACCOUNT-WIDE COUNTER

**Kraken's sentence is about the trading-engine counter and says nothing about the
REST call counter.** Nothing here claims otherwise. The batch cancel's REST
component — the one `ClosedOrders` read, charged at `accountHistory` — is
**metered and gated exactly like any other read**, and a Starter account with 14
of 15 units spent is refused it. Both halves are asserted separately, and a
vector whose *only* component is unconditional is **rejected outright** as an
unmeasured path through the gate: a call with nothing the gate can refuse would
make the gate decorative. Kraken's batch cancel is not that case, on purpose.

`WeightBudget.record` exists because `Budget` is an obligation rather than a menu
— a venue later gaining an unconditional charge on an account-wide counter must
fail at the **type**, not at runtime. **It is unreachable today** (only Kraken has
a trading counter) and is stated as such in the tests rather than left as a method
nothing runs and nothing checks.
