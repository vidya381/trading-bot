## Step 23: The manual halt control (dashboard) — and the backend session's missing entry
Date: 2026-08-04

### What was built

The dashboard half of `POST /api/bots/:id/halt`. The endpoint has existed since
2026-08-03 (commit `1d4d39e`) and has been reachable only by `curl`: a human
looking at one misbehaving bot had two options, both wrong for the job — pull the
**global** kill switch (every bot, every account; section 7.4 is deliberately
all-or-nothing) or wait for reconciliation to react to drift the system detected
on its own. Neither is "stop THIS one, now, because I do not like what I am
seeing".

It is also the precondition two controls already on this page assume:
`LiquidateAction` and `ApplyMissedFillsAction` both refuse a running bot and tell
the operator to halt it first. Until this button, following that instruction
meant reaching for the systemwide switch.

- **`HaltResult` / `HaltResponse`** in `dashboard/src/api/types.ts` and
  **`haltBot(id, reason)`** in `dashboard/src/api/client.ts` — the first bot
  action with a request body.
- **`HaltAction.tsx`** — renders only when `bot.status === "running"` (re-checked
  in the component, not just at the caller), a plain confirm dialog carrying a
  **required free-text reason**, mounted guard + in-flight/double-click guard,
  immediate `poll.refetch` after any attempt that may have written.
- Wired into `BotDetail.tsx` **below** `CheckOpenOrdersAction` and **above**
  `ResumeAction`/`LiquidateAction`.
- **Six backend tests** in `src/api/api.test.ts` (below), each pinning a sentence
  this dialog puts in front of an operator.

### First: the manual-halt session left no decision-log entry

Asked to read it, and it is not there. `docs/decision-log/` has no file for the
endpoint, no entry mentions `haltBot` or `/api/bots/:id/halt`, and
`git log -- docs/decision-log` shows `1d4d39e` touching only `src/api/*` and
`src/api/README.md`. The session's written record is its handler docblock
(`handlers.ts:315-361`), its commit message, and its six tests — all of which are
unusually thorough, which is probably how the omission went unnoticed.

Recorded here rather than silently worked around, and the endpoint's facts are
carried into this entry so the log is not missing them. **The docblock was
verified against source rather than trusted**, and it holds up on every point
this UI depends on.

`#halt` (`bot-instance.ts:3719`), in execution order:

| # | Step | Consequence for the UI |
| --- | --- | --- |
| 1 | `halted` → return `already_halted`, change **nothing** | a double-click is harmless, and the operator's reason is **discarded** |
| 2 | `stopped` → throw `invalid_status` | the only status refused; capital already released |
| 3 | mark `halted` + record `manual: <reason>`, **durably, first** | a 200 means the bot is stopped even if step 4 goes badly |
| 4 | cancel every open order | the dialog's central claim |
| 5 | mirror to D1, alert `halt_manual`, audit `bot.halted` | actor is the verified Access email, not `kill-switch`/`reconciliation` |
| 6 | unsubscribe from the price feed | the next closed candle drives nothing |

Neither latch is asserted — not `assertGlobalArmed`, not `assertAccountArmed` —
the exact inverse of `resume` (step 15) and deliberate: a halt reduces risk and
must stay available while the kill switch is pulled or an account's breaker is
tripped. That is precisely the bot a sweep failed to reach.

### Decision: `running` only, and `created` is a scope choice, not a mirrored limit

The brief said running-only, and the three exclusions have three different
justifications, which the component's docblock states rather than presenting as
one rule:

- **`halted`** — the endpoint returns 200 `already_halted` and changes nothing. A
  button here would teach an operator that the control does nothing.
- **`stopped`** — the backend genuinely refuses it (`invalid_status`, 409). The
  one exclusion that mirrors a rule.
- **`created`** — **the backend would allow it.** `#halt` accepts `created` and
  `running`; nothing was mirrored here. A created bot has placed nothing, holds
  nothing and is subscribed to nothing, and "halting" it would move it into a
  status whose only exit is `resume` — a heavier, latch-asserting action than the
  `start` it never took. The honest control for a bot that should not run is to
  not start it.

That last one is pinned by a test (below) so the reasoning stays legible: if the
test ever fails, what changed is the docblock's argument, not the button.

### Decision: a plain confirm with a required reason, not type-to-confirm

Type-to-confirm (`HALT ALL BOTS`) stays reserved for the systemwide pull, whose
blast radius is total. Halting one bot is the same weight category as start,
resume and liquidate — consequential, one bot — so it gets the same plain dialog
those use, with the kill switch's **reason input** grafted on because this
endpoint, alone among the bot actions, requires one.

The reason is not decoration: it is stored as `manual: <reason>`, and it is
exactly what `ResumeAction`'s dialog shows the next person before they bring the
bot back. The confirm button is disabled until the **trimmed** reason is
non-empty, mirroring `requireString`, which trims before testing — a button that
could only ever return 400 is the thing this codebase refuses to ship (10.11's
`sellOnStopLoss` decision, 18's pre-flight refusal).

The dialog focuses the **reason field** rather than the cancel button, diverging
from `ResumeAction`/`ApplyMissedFillsAction`. Typing is the first thing to do
here, the destructive button is unreachable until something is typed, and Enter
inside a textarea inserts a newline rather than submitting — so the safety
property those dialogs get from focusing Cancel is not lost.

### Decision: `already_halted` is its own outcome, not a success

The endpoint has **two** success actions and they are not interchangeable.
Reporting both as "halted, reason recorded" would be a lie that surfaces later,
when someone opens the resume dialog and finds a different explanation than the
one they wrote. So `already_halted` renders as its own `info` banner saying
plainly that the bot was stopped before this request arrived, that no order was
cancelled, and that **the reason just typed was not recorded** — quoting the
reason the bot actually kept (`result.detail`, which `#halt` returns from the
early exit for exactly this).

### Decision: the success banner does not promise a clean exchange

The strongest true statement after a 200 is "the bot is stopped", not "its orders
are gone". `#cancelOpenOrders` does not abort on the first failure — a halt that
stops at the first failure is a halt that half happened — and an order whose
cancellation cannot be **confirmed** is not assumed cancelled (section 5.6): it
stays in `openOrderIds` with a `cancel_failed` critical alert, and the halt still
returns 200. So the banner sends the operator to the alerts instead of reporting
a book it cannot verify, and the dialog says the same thing before the click.

This is step 15's discipline pointed at the success path again: there, an error
branch was dropped because the endpoint could not fail that way and the honest
caveat moved to the success banner. Here, the caveat is that success is partial.

### Decision: the dialog spends a box on "the position is NOT sold"

The most likely wrong assumption about a control labelled *halt*. A halt stops
trading and cancels resting orders; whatever the bot holds, it keeps, and the
capital reservation stands (releasing it is a close). Selling out is
`LiquidateAction` — which becomes available **because** this button ran. The box
renders either way, worded for whether the bot is actually holding: a flat bot
still has capital reserved, and saying nothing would leave the operator to guess.

**Placement:** below the observation pass, above resume and liquidate. That is
the order the decisions happen in — find out what is true, stop the bot, then
choose whether to bring it back or sell out — and the two controls below are
reachable only through this one.

### Tests: six, at the layer the control actually talks to

The dashboard still has no test runner (open since 10.6; typecheck and build
only), so these are backend tests in `src/api/api.test.ts`. The six that already
existed are the **endpoint's**; these six are the **control's** — each pins a
specific claim the dialog or its banner makes, end to end:

1. **Cancels the resting order the dialog names, and empties the list it counts** —
   `state.openOrderIds` before (what the dialog reads for "its 1 open order"), the
   cancellation reaching the exchange, the D1 order row `cancelled`, and the list
   empty after.
2. **Keeps the position and its capital** — still holding exactly what it bought,
   no sell placed on the way out, no `bot.closed` audit.
3. **Still halts when a cancellation cannot be confirmed** — 200 with
   `action: "halted"`, the order **still open**, and a real `cancel_failed` alert
   on the detail payload the banner points at.
4. **Rejects a whitespace-only reason (400)**, the same as a missing one, and the
   bot is untouched — the gate the confirm button mirrors.
5. **Refuses a stopped bot with `invalid_status` (409)** — documented in the
   handler since the endpoint was written, untested at this layer until now.
6. **Halts a `created` bot** — so the button's absence there reads as the UI scope
   choice it is.

**Mutation-checked, five mutants, and the fourth found a real defect in my own
test:**

| mutant | result |
| --- | --- |
| `#cancelOpenOrders` returns before cancelling anything | caught — tests 1, 3 |
| an unconfirmable cancellation is treated as cancelled (dropped from `openOrderIds`, no alert) | caught — test 3 (plus 5 pre-existing) |
| `requireString` stops trimming | caught — test 4 |
| `#halt` zeroes the position on the way out | **NOT caught at first** |
| `#halt` drops the `stopped` refusal | caught — test 5 |

Test 2 originally asserted `heldQuantity` was `not.toBe("0")` and stayed green
against a bot whose position had been zeroed — because a flat DCA position
serialises as **`"0.00000000"`**, not `"0"` (line 271 of the same file has said so
all along). The assertion was vacuous and the mutation is the only reason it was
found. It now compares against `toDecimalString(fill.quantity)` — the exact
quantity the fill reported — and catches the mutant. The lesson is the one 14.8
recorded: a test that asserts a serialised value must be written against the
serialiser's real output, not against what the value looks like in the source.

1. **This control has never been exercised against a real deployed origin.** Like
   every dashboard write before it, it is verified against real D1 and real
   Durable Objects in the Workers runtime, with only the exchange faked.
2. **The missing entry above is a process gap, not a one-off.** The backend halt
   session shipped tests, a route-table row and a docblock, and still left no log
   entry — nothing in the workflow catches that. Worth deciding whether the log
   index gets a check, or whether the omission is simply accepted when the
   docblock carries the reasoning.

   halted and later resumed keeps a standing `halt_*` alert. This session adds a
   new way to create one.
