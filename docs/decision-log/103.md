## PART 1 — THE ASSUMPTION THAT WAS CHECKED FIRST, AND WAS WRONG

The session opened by tracing whether any safe path existed to verify the
`DISCORD_WEBHOOK_URL` secret end to end. The trace produced a correct mechanical
finding and then an incorrect conclusion drawn from it, and the order matters.

**The mechanical finding, which held up:** `dispatch.ts:150` is the *only* writer
of a non-null `notified_at` anywhere in the codebase. All nineteen other
references are inserts writing `notified_at: null` (reconciliation, kill-switch,
circuit-breaker, `bot-instance`, `price-feed`, standing alerts). The dispatcher's
queue is `WHERE notified_at IS NULL`, and `runNotificationDispatch` returns
`ran: false` **before any D1 access** when the secret or the KV binding is
missing. So while the dispatcher no-ops, nothing is ever stamped.

**The conclusion drawn from it, which was wrong:** that a backlog of un-notified
alerts had therefore accumulated in production, and that setting the secret would
fire a burst of stale pings — one per distinct `(alert_type, bot_instance_id)`
pair, up to the 500-row scan limit. This was stated to the operator as a risk of
the obvious "just set the secret and watch" approach.

**It was checked before being acted on, and production's `alerts` table is
empty:**

```
SELECT COUNT(*) AS total_alerts,
       SUM(CASE WHEN notified_at IS NULL THEN 1 ELSE 0 END) AS pending
  FROM alerts;
-->  total_alerts 0,  pending null
```

`pending` is `null` rather than `0` because `SUM` over zero rows is `null` — the
shape of an empty table, not of a table with nothing outstanding.

**Why it is empty, established rather than assumed:**

| table | rows |
| --- | --- |
| `accounts` | 1 |
| `bot_instances` | 0 |
| `orders` | 0 |
| `alerts` | 0 |
| `audit_log` | 375 |

The audit log explains it: **374 `reconciliation.run`** and **1
`capital.placeholder_balance_seeded`**, and nothing else. The most recent
reconciliation ran at **2026-09-10 03:50:56 UTC — 55 seconds before the query**.
So production is deployed, migrated, and both crons are firing on schedule; with
one account, no bots and no orders, reconciliation simply finds nothing to
reconcile and raises no alerts. Production has been idling cleanly since the
placeholder balance was seeded on 2026-09-08.

**The consequence for the plan was total.** The backlog risk was imaginary, and
so was the value of the cheap approach: with an empty queue, setting the secret
and waiting proves *nothing*, because the cron logs
`scanned=0 sent=0 throttled=0 failed=0` every minute without ever handing
`DiscordNotifier` an alert to POST. A healthy-looking cron log is fully
compatible with a completely invalid webhook URL. **The gap this exposed is that
the production send path had never once executed** — `DiscordNotifier`'s unit
tests all inject a mock `fetch` and a fake URL by design, so they never touch the
network either.

**The discipline that saved it is the one entry 71 recorded**: a prediction was
made falsifiable, checked against live state before anything was acted on, and
found wrong — and the cost of skipping that check would have been an operator
warned about a nonexistent burst, and very likely a "verification" that consisted
of watching a cron report zeros. The general rule from README entry 10.14 applies
directly: **anything that can change after it is written must be read from the
system, not inferred from the code or quoted from this log.**

## PART 2 — THE DIAGNOSTIC ROUTE: BUILT, RUN ONCE, REMOVED

### What was already true before anything was built

Checked first, because each of these could have ended the session early:

- **`ALERT_COOLDOWNS` KV exists in both environments**, and not merely in
  `wrangler.jsonc` — `wrangler kv namespace list` returns
  `testnet-ALERT_COOLDOWNS` (`bf4f637666bd42a09a25b729744a7c16`) and
  `production-ALERT_COOLDOWNS` (`f62b31ae1787470ebc81b93f07d55521`).
- **`DISCORD_WEBHOOK_URL` is set in both environments** —
  `wrangler secret list` (names only; values are not readable, by design).
- **The `alerts` table exists in production**, so migrations have been applied.

All three dispatcher gates therefore passed, and the single remaining unknown was
whether the URL behind the secret is one Discord accepts. **No amount of reading
can answer that.**

### The route

`POST /api/debug/notification-check`
(`src/api/debug-notification-check.ts`, wired in `src/api/index.ts`), following
the convention of `/api/debug/ws-check` (14.6), `/api/debug/feed-check` (14.7),
`/api/debug/exchange-check`, and `/api/debug/derive-probe` (41, 42): a
banner-marked temporary file, built, deployed, run once live, and deleted the
same day, route AND read path.

**It constructs the REAL `DiscordNotifier` from the REAL secret** — any mock
would have defeated the purpose — and hands it ONE synthetic alert built in
memory. It reads and writes **no table**, calls **no dispatcher**, touches **no
KV**, and advances **no cooldown**. A run leaves D1 and KV byte-for-byte
unchanged.

One D1 read does occur per invocation, and is recorded here rather than glossed:
`handleApiRequest`'s schema guard runs `tableExists("bot_instances")` on *every*
`/api/*` request, before any handler is reached. That read is the framework's,
not the route's, and it does not touch `alerts`.

**The synthetic alert is `system`/`info` on purpose** — the least alarming pair in
`discord.ts`'s palette (grey stripe, `⚙️`, `🟢`) — and its message opens with
`SYNTHETIC TEST PING -- this is NOT a real alert`. Its id is
`debug-notification-check-<ms>`, deliberately **not** a UUID, so nothing can
mistake it for or correlate it with a real `alerts` row; no such row exists.
A test ping must not be mistakable for a real trading or critical alert by
whoever is watching the channel.

**POST, not GET, unlike the earlier diagnostics** — it has a side effect. This
had a real cost, recorded in the next section.

### Verification before deploying: the test suite could not run

`vitest.config.ts` **fails to load on this machine**:

```
TypeError: mixinBody is not a function
    at node_modules/undici/lib/web/fetch/response.js:314
```

**Node v25.4.0 against undici 7.28.0.** This is **pre-existing and unrelated** —
confirmed by running the untouched `src/notifications/discord.test.ts`, which
fails identically. It is a config-load failure, so **no test in the repository
can run**, not merely the new one. `package.json`'s `engines` says `>=20`, which

`src/api/debug-notification-check.test.ts` was written anyway (9 tests, `fetch`
injected, no real URL in the file) so it exists when the environment is fixed.
**It has never been executed.**

Rather than deploy to production on an unrun suite, the logic was verified a
second way, using this project's own `esbuild && node` pattern (14.9): the real
module was bundled and driven with an injected `fetch` in plain Node.
**14 of 14 checks passed** — `204` → delivered; `401` → not delivered with the
reason naming `401`; a thrown transport error surfaced as a reason rather than
propagating; missing **and** blank secret both send *nothing* (zero fetch calls);
and the posted payload carries `[SYSTEM]` and a description opening
`SYNTHETIC TEST PING`. `npm run typecheck` was clean throughout.

This is weaker than the suite and is not presented as equivalent: it exercises the
module's own logic, not its wiring through `handleApiRequest`.

### Deploy, and the Access wall

`wrangler deploy --env production --dry-run` was clean first; then
`npm run deploy:production` → version **`d65b8944-1605-48fc-b1d6-87fa91c74958`**.

**The route could not be invoked from the CLI, and this is by design, not a
misconfiguration.** Cloudflare Access fronts the *entire* production hostname —
even unauthenticated `/health`, which is deliberately public at the application
layer, returns `302` to the Access login page. An Access **service token would
not help either**: `access.ts:271` requires an `email` claim and a matching
`Cf-Access-Authenticated-User-Email` header, and service tokens carry
`common_name` and set no such header, so they are refused by construction. This
is the same wall 14.6 recorded ("a raw `curl` without an Access token gets 401")
and the reason those diagnostics were all hit "through the browser session that is
already behind Cloudflare Access".

Because the route is **POST**, it could not simply be visited as a URL the way the
earlier **GET** diagnostics were. The operator ran it from the dashboard origin's
devtools console, where the Access cookie rides along same-origin:

```js
fetch('/api/debug/notification-check', { method: 'POST' })
  .then(r => r.json().then(j => console.log(r.status, JSON.stringify(j, null, 2))))
```

**RESULT — PASS [OPERATOR]:** `200`, `"delivered": true`, and the message
confirmed visible in the production Discord channel. **This is the first time the
production `DISCORD_WEBHOOK_URL` has ever been POSTed to.**

### Removal, verified three ways here and a fourth by the operator

Both files deleted; both marked blocks stripped from `src/api/index.ts`.

1. **Source is clean.** `git diff -- src/api/index.ts` and
   `git status --porcelain -- src/api/` both return **empty** — the directory is
   byte-identical to `HEAD`. The route count is back to its baseline **37**. A
   repo-wide grep for `notification-check`, `handleNotificationCheck`,
   `runNotificationCheck` and `syntheticAlert` across `src/` and `dashboard/src`
   finds nothing.
2. **The compiled artifact is clean, with a control.** The bundle was built to an
   outdir and grepped *before* upload: **0** occurrences of `notification-check`
   — while `notification dispatch` (the real cron path) still appears **4** times.
   **The control is the point**: it proves the grep would have found residue, and
   that the removal was surgical rather than the search being broken.
3. **The deploy superseded it.** `npm run deploy:production` → version
   **`6dce78a0-22c8-4d38-8d80-e0424cb63a56`**, which
   `wrangler deployments list` shows at **100%**, replacing `d65b8944…`.
4. **CONFIRMED — the live 404 [OPERATOR].** Run from the same
   Access-authenticated devtools console that ran the PASS above, against the
   deployed `6dce78a0…`:

   ```
   HTTP 404
   {"data": null,
    "error": {"code": "not_found",
              "message": "no API route for POST /api/debug/notification-check"}}
   ```

   **This is the observation that actually proves removal**, and it proves a
   sharper thing than absence: the request **authenticated successfully and then
   failed to resolve a route**. `handleApiRequest` runs auth first and routing
   second, so a 404 in this envelope means the caller got *past* Access and the
   router still had no such path — the route is gone from the running Worker, not
   merely unreachable. The `code`/`message` pair is the router's own
   `not_found` envelope, matching the shape predicted before the check was run.

   **Recorded alongside it, because it is a trap for the next reader:** this
   session's own unauthenticated CLI probe returned **`302`**, twice, both before
   and after the removal deploy — the Access login redirect, generated at the edge
   before the request ever reaches the Worker's router. **A 302 proves only that
   Access is gating; it is worthless as a removal check**, and would have read
   identically had the route still been live. A CLI `curl` cannot verify this and
   must not be used to try.

**All four are independent, and none is redundant.** Items 1–3 are this session's
own evidence, at three different layers — absent from the source (`git` clean),
absent from the compiled artifact (bundle grep, with a working control), and
superseded by a 100%-rolled-out version. Item 4 is the live confirmation from
outside, on the deployed Worker, through the real auth path. Items 1–3 establish
that the code shipped without the route; item 4 establishes that the thing
actually serving traffic behaves accordingly. **The operator-run check is
corroborated by the static evidence rather than resting on it, and vice versa** —
which is the standard the earlier diagnostics were held to (14.6, 14.7), where the
live browser run was likewise the operator's and likewise decisive.
