## PART 1 — THE BUG THIS CLOSES

### What `#recordCancellation` did

`#recordCancellation` (`src/durable-objects/bot-instance.ts`, now at line 4214),
reached from `#cancelOpenOrders` (line 4094) on every halt, did this first and
unconditionally:

```ts
const cancelled = closeOrder(order, "cancelled", remote.updatedAt);
await this.#putOrder(cancelled);
```

It marked the order **permanently terminal at whatever fill quantity this bot
locally believed at that moment** — including when that number was already known
to be behind the exchange's real fill count, because the very next lines detected
exactly that condition and raised `cancel_fill_discrepancy` about it. The
detection was already there. It fired *after* the damage.

### Why terminal is unrecoverable

`ALLOWED_TRANSITIONS` in `src/shared/order-state.ts` gives every terminal state
an **empty successor list**, and `applyFill` throws `fill_after_terminal` on a
terminal order. So once the sweep closed the record:

- the 30-second poll could no longer apply the missing execution, even when the
  venue later handed it over with its own real trade id;
- `applyMissedFills` could not reach it either — it iterates `openOrderIds`, and
  the sweep had just removed the id;
- reconciliation's `liveOrderFindings` stopped re-detecting the drift, because it
  also iterates `openOrderIds`, so the finding did not recur and the standing
  alert auto-resolved on the next pass.

The number was locked in, and every mechanism built to correct it had been
stepped past.

### This is the confirmed loss-causing step, not a theoretical one

On two live testnet bots (`bot-b23y63`, `bot-bl4e7c`), reconciliation detected
**genuine** drift — the exchange reporting more filled than the bot believed,
while the order was still open — and halted each bot. The halt that followed ran
this exact path and closed the order at the understated number. The audit trail
the operator captured shows both halts stating the two quantities and their delta
in the system's own generated text. That is where the fills stopped being
recoverable.

### The codebase already had the right pattern, for a different trigger

`#foldTerminalState` (line 2034) refuses precisely this, and its own docblock
states the reasoning in terms that need no restating:

> "Closing it would bake a position that is known to be understated into a
> terminal record — and a terminal order can never accept a fill afterwards
> (`ALLOWED_TRANSITIONS` gives every terminal state an empty successor list), so
> the understatement would be permanent and unrepairable. That is exactly how one
> incident's base order became unrecoverable, and it is not repeated here."

It was repeated here. `#foldTerminalState` guards the door the **poll** comes
through — an order the *exchange* ended. `#recordCancellation` guards the door
the **halt** comes through — the order ended by *us*. Same order, same condition,
two doors, and only one of them had a gate. `#recordCancellation` had no
equivalent check before this fix.

## PART 2 — WHAT WAS BUILT

Two edits, both inside the halt's cancel sweep. Nothing else in the chain was
touched.

### 1. The gate, using `#foldTerminalState`'s own predicate, copied verbatim

`#recordCancellation` returns `Promise<boolean>` instead of `Promise<void>`, and
now tests, before any write:

```ts
if (order.filledQuantity < remote.filledQuantity) { /* alert; return false */ }
```

That is `#foldTerminalState`'s line, character for character.

**Why the exact predicate and not a fresh one.** A second, independently-worded
comparison of the same two quantities is exactly the kind of thing that drifts
from the original over time: someone tightens one, or flips a boundary, or
switches to a helper, and the two doors quietly stop agreeing about what "the bot
is behind" means — while both still look correct in isolation. Reusing the
literal predicate means there is one definition of that condition in the halt/
poll pair, and a future change to it is either made in both places or visibly
made in neither.

Three properties carried over deliberately:

- **One-sided.** A local record *ahead* of the cancellation response still closes
  normally. Nothing is lost by closing a record that already knows about more
  than the response reports.
- **Refuse before any write.** `closeOrder`, `#putOrder` and `#mirrorOrderUpdate`
  are all downstream of the gate, mirroring `#foldTerminalState`'s ordering. A
  refusal leaves the Durable Object record and the D1 mirror both untouched.
- **Refusal returns `false` and the caller keeps the id.** `#foldTerminalState`
  returning `false` means its caller does not close and the order stays in
  `openOrderIds`; `#cancelOpenOrders` now pushes a refused id onto its existing
  `stillOpen` list for the same effect.

### There is NO tolerance in this comparison — a correction to the build brief

**Recorded as a self-caught correction rather than silently absorbed.** The build
brief asked to reuse "whatever tolerance `#foldTerminalState` already uses". The
session read `#foldTerminalState` in full before writing anything and found that
**no tolerance exists**: the comparison is exact `<` on scale-8 `bigint` `Money`.
**One satoshi of disagreement refuses.**

That is deliberate in the original — thresholds in this system live in
`DriftThresholds` in reconciliation, not in the order state machine — so the fix
was built to the real comparison. Inventing a threshold here to satisfy the
brief's assumption would have put a number in the one place the codebase had
carefully kept free of one, and would have created a band of "small enough to
destroy silently" that nothing in the design supports.

### 2. What happens on disagreement

The order is **not closed**, **not mirrored to D1**, and **stays in
`openOrderIds`**. That last part is the point rather than a side effect:
`#pollArmed` excludes only `stopped`, so a halted bot is still polled, and
`openOrderIds` non-empty keeps the 30-second alarm armed on exactly this order.
The next pass reads it with per-fill detail, `applyFill` accepts the missing
execution **under the exchange's own trade id**, and `#foldTerminalState` — whose
gate now passes, because the counts finally agree — closes it properly. The
refusal is a deferral to the one path that can repair it, not a dead end.

**The alert is the existing one, reused rather than invented.**
`cancel_fill_discrepancy` keeps its `alertType`, `severity: "warning"` and
`category: "trading"`, so `INGESTED_ALERT_TYPES`, the notification dispatcher and
`shared/alert-types.ts` are all untouched. The condition was already being
detected and already had a name; what was wrong was that it was reported *after*
the damage instead of *instead of* it. Only the message text changed, because
what happens to the order changed and the old wording described the old
behaviour.

`#foldTerminalState`'s literal `refuse(reason)` callback was deliberately **not**
reused: that closure is `#pollOpenOrders`' plumbing into the `skipped`/`refused`
arrays of a `bot.open_orders_checked` audit row, and there is no poll pass on the
halt path to record into. The durable record here is the alert row, which already
existed.

### 3. The halt is not swallowed

`#halt` sets `halted` **before** the sweep, and the sweep still returns normally,
so the status write, the halt alert, the `bot.halted` audit row and the feed
unsubscribe all proceed exactly as before. **This was tested explicitly, not
assumed** — see Part 3, test 1.

## PART 4 — FOUND, NOT FIXED

**`#closePass` has the same unconditional wipe, on a different trigger.**
`#closePass` (line 2592) runs `openOrderIds: []` unconditionally after its own
cancel sweep, so on a `close()` — not a `halt()` — a refused order is dropped
from the list the poll reads.

**This is a genuinely smaller problem than the halt case was, and the difference
is the whole reason it is recorded rather than fixed here.** After this fix the
order **record itself stays non-terminal with its true fills intact**: nothing is
destroyed, the information is only left **unobserved**, and anything that can
find the order can still act on it. The halt case destroyed the information
outright — a terminal record that `applyFill` will refuse forever. Unobserved is
recoverable; terminal is not.

It is also pre-existing and already discards `cancel_failed` ids the same way,
and `close()` releases capital, which makes it a different decision from a halt.
**Flagged as relevant to fix 3** — whatever repair action reaches stuck orders
will have to decide what `close()` does with one — and deliberately left alone.

## PART 5 — NOT DONE / NOT VERIFIED

- **This fix does NOT and CANNOT recover `bot-b23y63` or `bot-bl4e7c`. Stated as
  a hard fact, not a caveat.** Their orders are **already terminal** in Durable
  Object storage. `ALLOWED_TRANSITIONS` gives every terminal state an empty
  successor list, so `applyFill` throws `fill_after_terminal` on them
  permanently, regardless of this change; and they have already left
  `openOrderIds`, so neither the poll nor `applyMissedFills` can reach them. This
  gate stops **new** instances of the bug and does nothing whatsoever for the two
  that exposed it. No reader should come away thinking otherwise. Their state was
  not touched this session and no action was retried on them.
- **Fix 2 — `resume()` must not silently proceed after a drift halt.** Not built,
  not started. `#resumePass` clears status, `haltReason` and `haltedAt` and
  resolves the halt alerts, and never reads an order, re-checks the condition, or
  inspects why the bot halted. Separate future session.

  built, not started. **This is the next priority**, because it is the only one
