### Why it looked unexplained: the poll was starved of rate-limit budget

The audit row for the poll that ran at **07:20:58Z** — forty seconds *after* the

> `applied: v1-bot-x93xux-0 (TPVKWX…), v1-bot-x93xux-1 (TC5OFN…)`
> `skipped: v1-bot-x93xux-2: rate_limited … could not obtain 7 account-counter`

⚠ **The 0.00000000 discrepancy on the following run is NOT independent
confirmation, and must not be read as one.** `reconcile.ts` defines
`internal_calculated_balance = previous run's exchange balance + everything this
system itself did since`, so every run re-baselines on the last exchange
reading. The zero at 07:25:20Z was structural. The proof is the arithmetic
above, the 07:26:59Z audit row, and the exchange holding exactly
`2.59420419 LINK` = 3 × 0.86473473.

### ⚠ This is the SAME shape as the earlier incident, now recurring under load

The `kraken-main` balance-drift incident earlier the same night — a trailing-stop
entry that filled on Kraken while the bot's books said it held nothing,
`$20.0725` of USDT moving with no recorded activity, breaker tripped, all three
bots halted — **has no decision-log entry of its own.** Its record is commit
`aa20014` ("wire Kraken QueryTrades, enable missed-fill repair for real
executions") and the header of
`src/durable-objects/kraken-missed-fill-repair.test.ts`, which is worth reading
in full rather than summarised here.

That incident's root cause was one boolean (`trades: false` on Kraken's order
reads, so no fill ids came back and every repair path refused). **This one has a
different proximate cause — rate-limit starvation, not a missing field — but the
identical shape: a real fill racing a balance check.**

The useful conclusion is not "same bug twice". It is that **the earlier
incident's root cause is a recurring pattern under concurrent bot load, not a
one-off.** Fix the field and the race still exists; it just needs more bots
sharing one account counter to surface. Six did.

## PART 3 — THE REAL, NEW FINDING: A 10.00 USDT BOT SPENT 30.20 USDT

### What happened

`bot-x93xux` is a trailing stop. Spec 22.2 decision 4: **a trailing stop has
exactly one entry in its whole life, sized by its entire allocation.** Its
allocation was **10.00000000 USDT**.

It placed **three full-allocation entry orders in six seconds**:

| client order id | placed | quantity | limit price | outcome |
| --- | --- | --- | --- | --- |
| `v1-bot-x93xux-0` | 07:19:09Z | 0.86473473 | 11.56424 | **filled** |
| `v1-bot-x93xux-1` | 07:19:12Z | 0.86473473 | 11.56424 | **filled** |
| `v1-bot-x93xux-2` | 07:19:15Z | 0.86473473 | 11.56424 | **filled** |

**All three filled for real.** Gross spend `29.955590113004355` USDT plus
`0.2396446` in fees against a **10.00 USDT** allocation — **3.02×**.

### Root cause

`decide()` in `strategies/trailing-stop.ts`, before this session:

```ts
if (position.quantity <= ZERO) {
    if (input.hasOpenOrder) return { kind: "hold" };
    if (input.entryAttempts >= MAX_ENTRY_ATTEMPTS) return { kind: "halt", ... };
    return { kind: "open_entry", quoteAmount: config.allocatedCapital };
}
```

`hasOpenOrder` was fed `state.openOrderIds.length > 0`. The rate-limited poll
meant the fills were not ingested, so `position.quantity` stayed **zero** while
real orders were leaving the book — and the bot, seeing a flat position and
nothing it recognised as outstanding, asked for its **entire allocation** again.
Three times.

### ⚠ `MAX_ENTRY_ATTEMPTS` bounded the damage and was never designed to prevent it

The cap stopped this at 3.02× rather than running indefinitely, and that is the
only reason the number is not larger. But its own header says what it is for:

> Three allows two transient cancellations to be absorbed silently and surfaces
> a structural fault within about three candles instead of ten-plus.

It is a **damage cap against an entry that never fills**. It reasons about
attempts, never about whether a prior attempt actually **succeeded**. Its halt
message — "an order that did not fill was almost certainly cancelled on the
exchange" — states the assumption outright. That assumption was false here, and
a cap was the only thing standing between a 10 USDT bot and its allocation being
spent an unbounded number of times. **A damage cap is not a control.**

### The same class, smaller, on the DCA bot

`bot-q4xcjr` placed **two base orders one second apart** at an identical price
(07:10:09Z and 07:10:10Z, both filled 07:13:48Z, `2 × 10.0399999957888` USDT).
DCA's only guard is the same `hasOpenOrder`, and the second decision ran before
the first placement was visible to it. Its `dropPct` is 5%, so two entries at
the same price are not a legitimate ladder.

**No capital breach** — 20.08 against a 30.00 allocation — so this one cost
nothing and would not have been found on its own. It is the same defect with a
shorter race window, and it is why the fix below is not trailing-stop-specific.

## PART 4 — THE STRUCTURAL FIX (deployed `b36930ab`, 08:39:14Z)

### The distinction that did not exist

`openOrderIds` means "believed live on the exchange". Its **absence** meant two
incompatible things at once:

- there is definitely nothing outstanding, **and**
- something was sent and this object does not know what became of it.

On a `transport` failure `#placeBuy` deliberately writes **no** `openOrderIds`
entry — correctly, because the order's fate is unknown and inventing a live
order would be a lie in the other direction. The code's own comment admitted the
consequence and named the cap as the only thing containing it:

> …it is counted because `openOrderIds` is NOT written on that path, so
> `hasOpenOrder` stays false and the next candle asks for the entry again — an
> unbounded loop of its own.

### `unconfirmedOrderIds`

A new **optional** `BotRuntimeState` field, genuinely distinct from
`openOrderIds`:

- **Written BEFORE the order is sent**, mirroring the attempt record and for the
  same reason — a re-entry arriving while the placement await is parked must see
  that something is outstanding. This is what closes `bot-q4xcjr`'s one-second
  race.
- **Cleared only by a definite answer.** `rate_limited` clears it (§5.4 refused
  the budget, nothing reached the network, the order provably does not exist);
  an outright exchange refusal clears it. **A `transport` failure does NOT** —
  that is precisely the case where the order may be resting and filling.
- Promotion to `openOrderIds` happens in **one** mutation, so no re-entry can
  observe an order in neither list.

`FailureKind` having three values rather than two is what makes this
expressible; the distinction it was built for is exactly the one that was being
lost.

### `hasOpenOrder` → `hasOutstandingOrder`, across all three strategies

⚠ **This was the structural half, and it is the reason the change is a rename
rather than a patch.** The bug was not a wrong computation at one site. Every
site computed `openOrderIds.length > 0`, and at every site that **looked
complete** — on grid, on DCA and on trailing stop — for as long as the
transport-failure path stayed rare. A second term added at one call site and
missed at another would have reproduced the bug on whichever strategy was
missed.

So there is now **one** accessor, `hasOutstandingOrder(state)`, returning
`openOrderIds.length > 0 || outstandingUnconfirmed(state).length > 0`, and the
strategy-facing field carries the honest name. `false` from it is a **positive
claim** — "this bot has nothing outstanding, a new order is safe" — and every
path that can make that untrue has to pass through it. `gridOutstanding` gained
the same term. The old name is what made this readable-past for three
strategies, which is why it did not survive.

The type checker found all 44 call sites, including three test files. That is
the property the rename was for.

### The deliberate behavioural change, stated rather than buried

**After a transport failure a bot now HOLDS instead of re-entering.** An
over-entry becomes a stall. That is the right direction — refusing to spend is
recoverable, spending 3.02× an allocation is not — but it is a real change and
a bot that quietly declines to trade is its own failure mode, harder to diagnose
than the loud overspend it replaced.

So the stall is **visible**: a new `entry_suppressed_unconfirmed` alert naming
the exact client order ids. It is **standing**, through the same mechanism the
poll already uses, because the condition is re-derived every candle and an
unconditional insert would write thousands of identical rows a day. It is
**raised and resolved by the poll** — not by the price path that feels the
effect — because a standing alert must have one owner and only the poll can
resolve this one. It auto-closes on the first pass that finds nothing
outstanding, with no human action.

### ⚠ The recovery mechanism that had zero production callers

`IdempotencyGuard.unresolvedAttempts()` — documented as "the recovery worklist",
built for exactly this condition — **was never called anywhere in production
code.** The `attempting` record was written before every send and then read by
nothing. The 30-second poll iterated `openOrderIds` only, so the one order a bot
most needed an answer for was never asked about.

The poll's read set is now `openOrderIds ∪ unconfirmedOrderIds`. A readable
unknown order is **adopted**: `OrderStatus` carries every field `createOrder`
needs, so the record is reconstructed from the venue's own answer and the
existing fill/fold machinery handles it with no special case, including folding
the fills it took while the object did not know it existed. That is the repair
this incident actually needed.

**One existing test's expectation was changed, deliberately.**
`bot-instance.test.ts`'s "leaves an order of unknown outcome unresolved"
asserted `placed-base` under a fresh sequence — an order of unknown outcome
followed immediately by a second, real one. Its actual invariant (never re-send
the **spent id**) is untouched and still asserted; the outcome is now `hold`.

## PART 5 — THE CLEANUP, AND WHY IT WAS A LIQUIDATION

### The blocker first

Both the breaker reset and every resume sit behind Cloudflare Access, which
verifies a JWT and records the actor from the **verified claim**, not a header,
so that nothing can act as anyone. There is no service-token path in
`access.ts`. The cached token on the operator's machine had **expired seven
minutes before it was checked** (issued 2026-09-10 08:59:41Z, 24-hour life).

The work therefore stopped and the operator ran `cloudflared access login`. This
is recorded because the correct division held: the human proved presence, the
agent did the sequencing and verification, and the audit rows name the human,
who is the person who decided.

### The sequence

Breaker reset to `armed` at **09:31:51Z** with a note recording the full
reconciliation. Then, one at a time with a ≥60s stability hold and a re-read
between each:

## PART 6 — THE SECOND BUG: A RESUME GATE THAT LIED ABOUT THE POSITION

### The refusal

`POST /api/bots/bot-x93xux/resume` returned `entry_budget_spent`:

> its single entry order was placed 3 times **without ever filling** … this bot
> **never got it, so there is no position to trail** and nothing for a resume to
> do.

Both claims are false. The Durable Object's own state at that moment:

```
entryAttempts : 3
position.qty  : 2.59420419 LINK
cost          : 29.95559011 USDT
trailLevel    : 10.50119070
```

The entries did not fail to fill. **All three filled — that is the entire
incident.** The gate read `entryAttempts` and nothing else, then *spoke* as
though it had checked the position.

Its **prediction** was wrong too. `decide()` checks `position.quantity <= ZERO`
**first**; `entryAttempts` is consulted only inside that empty-position branch.
A bot holding anything takes the trailing branch and never reaches the cap. The
refusal predicted a re-halt that `decide()` would not have produced.

This is the **same buried assumption as PART 3**, in a second place: *entry
budget spent ⇒ nothing was acquired.*

### ⚠ The real cost: a genuinely unprotected position

While halted, `bot-x93xux` held **2.59420419 LINK ≈ 29.61 USDT** with
**no trailing stop enforced**, against a `trailLevel` of `10.50119070` at a
market price of `11.41470000` — **8.70% of headroom**. Had LINK fallen through
that level, nothing would have sold. This was the state for a real window
between the resume attempt and the liquidation, and it is why the operator chose
the forced exit.

### ⚠ NOT a legacy-state-only bug — found while building the test

The obvious reading is that this only affects bots already wedged by PART 3's
defect, which the PART 4 fix now prevents. **That reading is wrong**, and
constructing the test is what showed it.

The state is reachable through **entirely ordinary behaviour**:

1. An entry is cancelled at the venue. Attempt 1 spent, bot still flat.
2. A second is cancelled. Attempt 2 spent. **This is exactly what the cap was
   sized to absorb** — "three allows two transient cancellations to be absorbed
   silently".
3. The third entry **fills**. The cap is now spent and the bot holds a real
   position. This is the strategy *working*.
4. Any account-wide halt — a circuit breaker, an operator pause — halts it.

That bot is now **permanently unresumable**, having done nothing wrong. Any
healthy trailing stop hitting this sequence would have been.

### The fix (deployed `49723239`, 09:58:30Z)

```ts
if (spent >= MAX_ENTRY_ATTEMPTS && state.position.quantity <= ZERO) {
```

Both halves required, **copied from `decide()`, which is the authority**. A
refusal predicated on the cap is only ever truthful when the position is also
empty, and the two must agree about that or the gate goes on predicting a halt
`decide()` will not produce. The message now says "and it holds no position"
rather than asserting it never filled.

### Falsifiability, both fixes

**Fix 1.** The tests use a **new** `FakeExchange.nextPlaceAcceptedButUnreported`
— the order reaches the venue, rests, and is fillable, while the caller sees
`transport`. This distinction is load-bearing: the existing `nextPlaceFailure`
models an order that *never arrived*, and re-placing **that** is correct
behaviour, so a test built on it would have passed against the broken code and
proved nothing. Reverting the gate to `openOrderIds.length > 0` failed **4 of
8** — including "places the entry ONCE", "stops at one, not at the 3-attempt
cap", and the DCA double-base-order case.

**Fix 2.** Reverting `&& state.position.quantity <= ZERO` reproduced **the exact
refusal on the exact reproduced scenario**: "resumes a bot at the cap that
actually HOLDS a position" failed with `entry_budget_spent`, while "still
refuses when the cap is spent AND the bot is genuinely flat" continued to pass —
confirming the fix narrows the latch rather than deleting it.

Both fixes also assert the **other** direction, without which each would just be
a bot that stops working: fix 1 proves a `rate_limited` placement (provably
never sent) **is** still retried; fix 2 proves the flat-position refusal is
untouched.
