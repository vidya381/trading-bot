## Step 28: The section 21.3 watchlist, in D1 and behind an API
Date: 2026-08-08

### What was built

Section 21 is still **PLANNED, NOT YET BUILT** and stays that way: no pipeline,
no prompt, no proposal record, no Workers AI call. What exists after this step is
the first of 21.3's two candidate sources — the fixed, human-chosen watchlist —
moved out of code and configuration into D1, with a write path that enforces the
things a config constant cannot, and an HTTP surface over it.

Two sessions, recorded together because the first deliberately stopped short of a
production caller and the second closed exactly that gap.

  note, added_by, added_at, removed_by, removed_at)`, STRICT, purely additive.
  One unique **partial** index on `(account_label, pair) WHERE removed_at IS
  NULL`, one partial index on `added_at`, one CHECK requiring a removal to be
  recorded whole.
- **`src/research/watchlist.ts`** — `addToWatchlist`, `removeFromWatchlist`,

### The rule this step exists to hold

21.3 names two candidate sources and keeps them **structurally separate**: this
watchlist, and a live trending pull. Nothing automated may write this table.
There is no `syncFromTrending`, no upsert, no bulk import, and both entry points
refuse the automated actors `placeholder-balance.ts` already names — imported
rather than re-listed.

The merge is tempting on convenience grounds, which is why it is worth naming:
both sources produce pairs, both feed one pipeline (21.2: "one feature, not
two"), and one table would mean one read path. It is wrong twice over.

**First**, 21.5 requires every proposal to display "the real source the candidate
came from — which watchlist entry, or which trending pull, and when". Merged,
that distinction is destroyed at the moment of writing and nothing downstream
recovers it.

**Second**, 21.3's hype hazard. Trending measures **attention**, not quality, and
its coins are "disproportionately the ones with the least history and the most
noise". A watchlist entry carries a human's stated reason (`note`, NOT NULL); a
trending hit carries a popularity number. Stored together they are
indistinguishable to every later reader, which is precisely how a proposal comes
to read as confident because its input was loud.

The cap makes the merge unattractive as well as forbidden: a trending pull
emptying itself into a 10-row table fails on the eleventh coin.

### Three shape decisions the spec sketch did not settle

**1. `account_label` is in the table.** The brief sketched `(id, pair, added_by,
added_at, note)`. That shape cannot support the requirement attached to it,
because "validate the pair against `listTradablePairs`" has no meaning without an
account: that call resolves `accounts.exchange` (migration 0006) to pick a venue,
and the two venues do not spell a pair the same way. A bare `pair` column holds a
string nothing can check — the "store it to fix later" this table is forbidden
from doing. It also matches every other operational table here, and 21.5's
capital-availability check is account-scoped regardless. It gives `accounts` its
first foreign key, which changed the teardown order in `db/test-helpers.ts`.

**2. Removal is a soft delete.** Forced, not chosen: `Repository` offers no
`delete` method at all (`/src/db/table.ts`, for section 8.7) and
`no-raw-d1.test.ts` fails the build on any file outside `/src/db` reaching past
it. So "remove a pair" could not have been a row deletion without widening the
access layer or routing around it. Step 26 had already established the shape —
`bot_instances.archived` is "explicitly not a delete, and structurally so rather
than by intention" — and this is that, one table over. The history earns its
keep on its own terms: *someone considered this coin and then changed their mind*
is the same negative signal 21.5 wants recorded about proposals nobody acted on.

**3. The cap counts live rows globally, not per account.** What the bound
protects is the cost and attention of a pipeline **run** — "each candidate costs
candle fetches, news fetches, and two LLM calls" — and that cost is per candidate
wherever the candidate is registered. A per-account cap would let two accounts
fund twenty candidates while each looked compliant.

### The cap is in code and deliberately NOT also a trigger

`WATCHLIST_MAX_ENTRIES = 10`, checked against a `COUNT` of live rows immediately
before the insert, and checked **before** the exchange call so an eleventh add
spends no venue request or rate-limit budget.

A `BEFORE INSERT` trigger would close the raw-SQL bypass, and was rejected. This
schema has no triggers anywhere, and putting 21.3's number in two places is the
thing 21.5 is explicit about: "a second implementation of a risk check drifts
from the first, and the copy that drifts is the one nobody is watching."
Widening the list is meant to be one line plus a test; SQLite cannot ALTER a
trigger in place.

The consequence was stated rather than hidden while raw SQL was the editing
path: **the cap, the tradability check and the audit entry are all bypassed by a
hand-written INSERT**, and the only guarantee that survives it is the unique
partial index. That was the strongest argument for building the endpoints, and
session 2 built them.

The honest limit that remains: the count-then-insert is not atomic, so two
concurrent adds could both see 9 and land 11. Not serialised, because the
intended writer is one human and the alternative is the trigger just rejected.
The duplicate case — the one a rushed operator actually hits — **is** closed
structurally by the unique index.

### Removal does not re-check tradability. Final, not open.

This deviates from the requirement as written ("every insert/delete must validate
the pair against `listTradablePairs`"), was raised as a deviation before
building, and has since been **accepted by the operator as a settled decision**.
Recorded here so it is a documented choice rather than a silent gap.

The reasoning: refusing to remove a pair the venue has **delisted** would trap
exactly the entry most in need of removing, and an exchange outage would be
enough to freeze the list. The failure runs the wrong way — a gate belongs on the
action that adds risk, not on its reversal.

This is not a new principle here; it is the stance this codebase already takes
everywhere a shrinking action meets the gate that governs its opposite:

| action | gate on the risk-adding direction | gate on the reversal |
| --- | --- | --- |
| archive / unarchive | `halted` or `stopped` only | **none** — "a gate here could only ever strand a bot" (step 26) |
| halt | — | asserts **neither** risk latch, unlike `resume`, which asserts both (steps 15, 23) |
| watchlist add / remove | cap + fail-closed tradability | **none** |

What removal does check is the precondition that actually matters — that the pair
is on the live list — and it writes its own audit entry. A test drives a removal
with a lister that always fails and asserts it both succeeds and never calls it.

### Fail closed means both directions

`assertTradable` refuses on two distinct grounds, and the second is the one that
rots quietly:

- **listed, pair absent** → `pair_not_tradable`
- **the listing itself failed** → `tradable_set_unreadable`

An outage produces no tradable set, and treating that as permission to store the
pair is the same substitution section 5.6 forbids when it refuses to read "could
not reach the exchange" as a price move. The entry stored during an outage is
never revisited; it is simply a row nothing validated, in the one list whose
entire value is that a human vouched for every row.

### The endpoints

Thin in the strict sense: the cap, the tradability check, the duplicate check,
the human-actor rule and both audit entries live in the module and none are
re-implemented, re-ordered or second-guessed in `handlers.ts`. What the layer
adds is the HTTP shape, the registry lookup that turns a label into a
`WatchlistAccount`, and the port wiring.

**The `TradablePairSource` port is the real one.** `tradablePairsFor` calls the
same `listAccountSymbols` as `GET /api/accounts/:label/symbols`, with the same
`KvSymbolCacheStore` and the same `ctx.symbolLister` (defaulting to
`envSymbolLister` → `listTradablePairs`). Shared deliberately: the watchlist's
idea of what a venue lists cannot drift from the dropdown an operator reads, and
a check does not spend a full-catalogue request per add. A test asserts two adds
cost **one** venue call, which is what proves it goes through `listAccountSymbols`
rather than around it.

The cache's one consequence, stated up front and since confirmed live: a set up
to an hour old can approve a pair delisted in the meantime. That is the safe
direction — a stale *accept* costs one wasted candidate, a stale *reject* would
block a real one — and failures are **never** cached, so a fail-closed refusal is
always against a live attempt.

**Status mapping reuses codes with the same shape of refusal** rather than
inventing per-endpoint ones:

| code | status | why that one |
| --- | --- | --- |
| `cap_exceeded`, `already_watched` | 409 | conflicts with current state, like `duplicate_bot_instance`; the identical request works once a pair is removed |
| `not_watched` | 404 | the thing named is not there to act on, like `unknown_bot_instance` |
| `pair_not_tradable` | 400 | a bad field value the caller can fix by asking differently |
| `tradable_set_unreadable` | 503 | the "dependency is down" tier with `not_attached`. **Not** the symbols endpoint's 502 — this is a refusal to write on unverifiable input, not a relayed read failure |
| `requires_human_actor` | 403 | already mapped for the kill switch; the watchlist reuses the spelling rather than adding a second row |

**A body `actor` is refused (400), not ignored.** The actor is always
`ctx.actor`, verified off the Access JWT. That is the layer's standing rule, and
it bites hardest here because the module refuses automated actors on purpose: a
body-supplied actor would let any authenticated caller write "chosen deliberately
by the operators" under someone else's name, in the one table whose entire value
is that a named human vouched for each row. Silently overriding it would record a
different person than the caller believes they recorded. **This is a new
convention** — no other endpoint refuses a field it would otherwise ignore — and
is recorded as such rather than presented as the existing pattern.

**One guard the handler adds that the module cannot.** `DELETE` is addressed by
entry id, because an id is what `GET` just handed the caller; the module is
addressed by `(account, pair)`. The unique index is **partial**, so a removed row
and a live row may share a pair. Passing a dead row's pair straight through would
make `removeFromWatchlist` match the **live** one — a DELETE on a stale id
silently killing a different entry. The handler refuses a non-live id; the module
still owns the liveness decision itself (its `UPDATE` is conditional on
`removed_at IS NULL`, so a removal racing another loses properly). The two answer
different questions, which is why this is not a duplicated check.

### The casing finding, and the comment it disproved

**The single most useful thing the live run produced was a refusal nobody
predicted.** `POST` with `"btcusd"` was rejected, and it was rejected because the
system was right and this log's own source comments were wrong.

`listTradablePairs` does **not** report the venue's wire format. Gemini's
`/v1/symbols` returns lowercase, separator-less symbols, and `parseSymbolList`
upper-cases them to this system's `Pair` convention (`gemini/parse.ts`, and the
client's own docblock has said so since step 3.4). The real listing is `BTCUSD`.

Migration 0008's header and `watchlist.ts`'s `assertTradable` both asserted
"Gemini's BTC/USD is `btcusd`" — written from memory of the Gemini API rather
than read off `parseSymbolList`, in the very comment justifying an exact match.
Both are corrected. The test fixtures were corrected with them: they modelled a
lowercase Gemini catalogue, and a stub that models the wrong catalogue teaches
the wrong shape to whoever reads it next. The near-miss test now runs in the
direction the operator actually hit — `btcusd` refused, message naming `BTCUSD`.

**This confirms the decision not to case-fold, on evidence rather than
argument.** A case-insensitive match would have accepted `btcusd` and stored a
symbol every later exchange call would have had to re-spell — a validation that
validated nothing, and one that would have looked fine until the first
`getCandles` on that pair. The refusal message carrying near-matches is what
turned a dead end into a one-line fix, and that is the design paying for itself
in the only test that counts.

It also earns a general rule this project keeps re-learning (10.14, 14.10, 17):
**the shape of a value is read from the function that produces it, not recalled
from the vendor's documentation.** `parseSymbolList` was four lines long and in
the repository the whole time.

### The first verification attempt failed, and it was not the code

Worth recording because it cost a round trip. **Every request 302'd to the Access
login page**: `cloudflared` was not installed and not logged in locally. An
environment and tooling gap, not a code defect — no request ever reached the
Worker.

The process lesson is on the commands, not the operator: they were handed over
with `TOKEN="$(cloudflared access token -app="$BASE")"` and a note that the
minting step was unverified, but they still **assumed a local login state that
did not exist**, and the failure mode of that assumption is a redirect that looks
nothing like an auth error. A verification script that begins by asserting its
own preconditions — is `cloudflared` present, is there a session, does
`/health` answer unauthenticated — would have said so in one line instead of
producing a page of HTML. Nothing was built for that here.

### Tests and mutation results

**Session 1** — 24 tests, **13 mutants, 13 caught**. Twelve fell on the first
pass. The survivor is recorded because it was right to survive: the removal's
`{ id, removed_at: null }` guard looks redundant beside the `findOne` two lines
above it and every **sequential** test passed without it. It defends the
interleave where both callers read the live row before either writes — without
it the second `UPDATE` matches by id and rewrites `removed_at`, so both callers
believe they removed the pair and the log carries two removals of one entry, the
second naming an actor who removed nothing. A `Promise.allSettled` test asserting
exactly one winner and exactly one audit row closed it. **That is the guard the
live run's second-removal `404` exercised against real D1.**

**Session 2** — 34 tests, **17 mutants, 16 caught**. The first run caught only
**11**, and all five survivors were real gaps rather than harness noise:

| survivor | what it exposed |
| --- | --- |
| removal actor from a query param | nothing asserted the removal actor against a *competing* value |
| `pair` from the query string | nothing pinned "the pair validated is the pair stored" |
| exchange from the request body | the handler's docblock claimed the registry was authoritative and no test said so — step 11's exact lesson |
| `not_watched` mapped to 400 | **no test at all**; the handler's own `ApiError(404)` shadows the map row entirely |
| `note` becomes optional | SKIPPED, not survived — the anchor matched four places; re-anchored, then caught |

The fourth is the one that changed the shape of the work. Rather than manufacture
an HTTP path to reach an unreachable row, `src/api/envelope.test.ts` now tests
the map directly — which also covers `requires_human_actor`, unreachable over
HTTP today because `ctx.actor` is always a verified email, and which exists so
that path cannot degrade to a silent 400 the day something else calls the module.

**One mutant still survives and is equivalent rather than uncaught.** Changing
`actor: ctx.actor` to `actor: (body.actor as string) ?? ctx.actor` in
`addWatchlistEntry` passes everything, correctly: the `actor_not_accepted` guard
eight lines above throws whenever `body.actor !== undefined`, so `body.actor` is
provably `undefined` at that line. It becomes live the day that guard is relaxed.
Recorded rather than tested around, as step 26 did with its own.

Full suite **1667 pass** (1633 after session 1, 1600 before it). Both harnesses
were re-run after the casing correction and are unchanged at 13/13 and 16/17. The
pre-existing teardown error and the uncounted test file (`63 passed (64)`) were
present at the 1600 baseline and are unchanged.

**What the numbers do not prove.** Every exchange interaction in the suite is an
injected lister; no test in this repository has spoken to Gemini or Binance. What
the live run above verified is the real thing — and it verified the endpoints,
not the tests.

### Deliberately not done, and open questions

- **No dashboard UI, deliberately.** Flagged as deferred in session 1, again in
  session 2, and still deferred. The endpoints are the curl-callable surface that
  replaced editing the table by hand; a control is its own step.
- **No candidate selection, no trending pull, no `getCandles` for arbitrary
  pairs, no Workers AI call, no proposal record.** All of section 21 beyond this
  table remains unbuilt, and 21.7's five open questions are untouched.
- **`readWatchlist` still has no non-test caller.** It is the seam the pipeline
  will consume. That is the intended state, not an oversight.
- **The schema guard's premise now has a counterexample.**
  `handleApiRequest` gates on `db.tableExists("bot_instances")` on the stated
  grounds that "every migration runs as one set, so if it is absent they all
  are". 0008 is the first migration that can be missing while `bot_instances` is
  present — a deploy that lands before migrations are applied — and in that
  window `POST /api/watchlist` returns a generic **500 `internal_error`** rather
  than the `no_schema` 503. Not changed here: the sentinel is a considered
  decision and widening it is its own call. Recorded so the 500 is not a mystery
  if it appears.
- **The cap's count-then-insert is not atomic** (above), and nothing asserts it
  under real concurrency.
- **`unpricedCount`-style honesty is absent from the read path**: `readWatchlist`
  returns entries and says nothing about the tradable set having gone stale
  underneath them. A pair delisted after it was added stays on the list until
  someone removes it, and only the pipeline's own re-read will notice.
- **Not deployed by this session.** The operator deployed testnet to run the
  verification above; production is untouched.
