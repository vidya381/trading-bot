## PART 1 — THE GAP

`resolveHaltAlerts` had exactly one caller: `#resumePass`. That is coherent as
far as it goes — a halt alert describes a condition that resuming ends.

But a bot can also leave `halted` by being **closed**, and that exit had no
counterpart. `resume()` requires `halted`, a stopped bot can never be resumed,
and nothing else in this system closes a `halt_*` row. So any halt alert open at
the moment a bot reached `stopped` **stayed open forever** — not because
anything was still wrong, but because **nothing was ever wired to say "this is
over."**

**This is COSMETIC, and that framing is deliberate.** It inflates the
unresolved-alert count, which is the number an operator reads to decide what is
on fire — the number step 18 went to some trouble to make meaningful again. It
is not a safety issue: the alert describes a state that has already ended, not an
ongoing problem, and no money or position was ever at stake in it.

## PART 2 — PIECE 1: `close()` RESOLVES `halt_*` ALERTS GOING FORWARD

### The scope already existed — this is a second CALLER, not new logic

`resolveHaltAlerts` was re-read in full and found **unchanged** by fixes 1, 2 and
64. It already filters on `source`, `bot_instance_id`, `resolved: false`, and
`isHaltAlertType` — the narrow, documented, tested scope. **This session invented
no new filter.** The change is one additional call site; `resolveHaltAlerts`
itself was not touched.

### The WIDER option was considered and REJECTED, with a concrete counterexample

The tempting version is: on a successful close, resolve **every** open alert on
the bot, on the reasoning that entry **64**'s gate (close refuses while any order
is unresolved) guarantees a clean bot by then.

**It does not guarantee that.** Entry 64 gates on unresolved **orders**, and an
order can be entirely resolved while an alert about it remains true. The
counterexample found: `#onOrderStateError` raises `order_state_drift` on an
`overfill`; that order can then **fully fill**, leave `openOrderIds` normally,
and satisfy entry 64's gate completely — while the drift alert about a real
accounting disagreement is still open and still **true**.

The distinction that decides it:

- A **`halt_*`** row on a stopped bot is **STALE** — the state it describes is
  over. Closing it is bookkeeping.
- An **`order_state_drift`** / **`unattributable_fill`** row on the same bot is
  **UNRESOLVED** — it describes base that really moved and really was never
  attributed. That stays true whatever the bot's status becomes. Closing it would
  **falsely assert a discrepancy went away when nothing resolved it** — and on a
  stopped bot, nothing ever will.

So the fix reuses `resolveHaltAlerts`' existing scope rather than widening it,
and the exclusions its header spells out hold here by construction rather than by
a second list that could drift.

### Tied to STATUS, not to `archived`

Closing is the stronger of the two claims. A **resumed** bot may halt again for
the same reason — it is not terminal. And **`archived` is a reversible visibility
flag** that `unarchiveBot` can undo, which would leave the alerts closed on a bot
that is back in view. **`stopped` is the one irreversible transition**, and it is
the one that makes a halt past tense.

### Recorded in the existing audit row

`resolved_halt_alert_ids` inside the **existing** `bot.closed` entry, mirroring
`bot.resumed`'s identical field. One event closed those rows; one row says so. No
new audit action.

### Five tests

1. **`resolves the bot's halt alert when it is closed, not only when resumed`** —
   the core case. Asserts the row is **resolved, not deleted**, and that
   `bot.closed` carries one id.
2. **`closes a stop-loss halt alert too, not just a manual one`** — every open
   `halt_*`, parity with resume's treatment.
3. **`does NOT resolve alerts that describe a real, still-true discrepancy`** —
   the safety scope, with **seven** seeded types across **three** sources, all
   asserted still open: `order_state_drift`, `unattributable_fill`,
   `cancel_fill_discrepancy`, `cancel_failed`, `poll_blind`,
   `reconciliation_meaningful_order_state_drift`, `price_feed_fanout_failed`.
4. **`resolves per bot: closing one leaves another bot's halt alert open`**.
5. **`closes a never-halted bot without inventing anything to resolve`** — an
   empty list in the audit entry.

The existing resume-path tests pass unchanged and were not duplicated.

### Mutation — both mutants recorded, and the second matters more

| Mutant | Result |
| --- | --- |
| Close resolves nothing (pre-fix behaviour) | **4 failed \| 165 passed** |
| **Blanket-resolve every open alert on close** (the REJECTED wide scope) | **1 failed \| 168 passed** — `does NOT resolve alerts that describe a real, still-true discrepancy` |

**The second is the more important safety proof.** The first only shows the
feature is wired. The second shows the **narrowing itself is tested and
load-bearing** — that the decision not to widen is enforced by a failing test
rather than by a paragraph of comment that a future edit could quietly
contradict.

### A self-caught tooling safeguard, recorded as a real finding

The first mutation attempt **aborted itself**. Its targeting pattern matched
`resolveHaltAlerts`' call site — and after this change there are **two** of them,
resume and close. The helper's `count == 1` assertion refused rather than
mutating the first match.

**Had it not, it would have mutated the RESUME path and reported the result as
the close path's**, producing a mutation figure that looked like evidence and was
about the wrong code. That is the specific way mutation testing goes quietly
wrong: the number is still produced, still plausible, and no longer means what
it claims. The fix was to target the close call by line number. Worth keeping in
the record as test-tooling discipline, not a minor detail: **a mutation run is
only evidence if you can prove what it mutated.**

## PART 3 — PIECE 2: THE ONE-TIME BACKFILL ENDPOINT

### ⚠️ Piece 1 does NOT help `v-spot-1` / `v-perp-1`, and this must not be blurred

**Stated as plainly here as it was during the build.** Piece 1's resolution fires
**during** `close()`. Every bot affected by this gap is **already stopped**, and
`close()` can never run on them again — `releaseBotCapital` refuses a second
release (`bot_already_stopped`). Piece 1 is purely forward-looking.

**This endpoint is a SEPARATE, one-time tool, not an extension of piece 1.**

### What it is

`POST /api/maintenance/resolve-stale-halt-alerts`, human-actor only,
**report-only by default** — `?commit=true` is the only thing that writes,
matching `repair-position` (entry **59**) and for the same reason: this is a bulk
write to the rows an operator reads to decide what is on fire, so the list is
meant to be read before it is trusted.

### The predicate, enforced in code — twice — not trusted to data

Both conditions required:

- the owning bot's **`status = 'stopped'`** — terminal, so no halt on it can be
  current;
- **`isHaltAlertType(alert_type)`** — **imported from `halt.ts`, not re-spelled.**

That second point is the discipline entries **57** and **61** established against
exactly this kind of drift: a `LIKE 'halt\_%'` in SQL here would have been a
second, independently-worded spelling of a rule `halt.ts` owns, free to diverge
from it silently. Importing it means this endpoint inherits
`alert-types.test.ts`' existing pin against the real `HaltReason` union for free.

The operator's live data happened to be clean of anything outside that class.
**The endpoint enforces the predicate anyway**, in code, rather than relying on
that remaining true.

### A distinct audit action

`alerts.stale_halt_backfill`, with `target_bot_instance_id: null` because it
spans bots — the same pattern `reconciliation.run` uses. Deliberately **not**
filed under `bot.closed` or `bot.resumed`: those record a resolution that
happened as part of a **lifecycle transition**, and this one happened as part of
**no transition at all**. Filing it there would misrepresent a manual correction
as a bot's own action.

### Idempotent, and never scheduled

A second run finds the rows already resolved, so nothing is reported and nothing
is written. **No cron, no alarm, no startup hook** — operator-triggered only. A
cleanup that runs forever is a mechanism, and a mechanism for a condition nothing
can produce any more is a thing that will one day fire on something it was never
meant to touch.

### Six tests

1. **`reports exactly the operator's five stale alerts, and writes nothing`** —
   the real population as a fixture, asserting the exact bot-id set, the exact
   sorted type multiset, and that report mode leaves all five rows open with zero
   audit entries.
2. **`resolves all five on commit, and records the correction in audit_log`** —
   rows **resolved, not deleted**; one audit row, human actor, null bot target.
3. **`NEVER touches a discrepancy-type alert, even on the same bot as a halt
   alert`** — one stopped bot carrying `halt_manual` **plus six** others
   (`order_state_drift`, `cancel_fill_discrepancy`, `unattributable_fill`,
   `cancel_failed`, `poll_blind`,
   `reconciliation_meaningful_order_state_drift`). Only the `halt_manual`
   resolves.
4. **`NEVER touches a bot that is not stopped, even with a halt alert open`** —
   a genuinely halted bot returns `no_change`.
5. **`is idempotent: a second commit reports no_change and writes no second audit
   row`**.
6. **`rejects a malformed ?commit value rather than guessing`** — 400
   `invalid_field`.

### Mutation — both halves of the predicate, independently

| Mutant | Result |
| --- | --- |
| **A** — alert-type filter dropped (widen to any open alert) | **1 failed \| 258 passed** — the discrepancy test |
| **B** — `status = 'stopped'` filter dropped (any bot) | **1 failed \| 258 passed** — the not-stopped test |

**Both being independently caught is the point.** Either check failing open would
resolve alerts that still mean something — A would close real discrepancies, B
would close the alert of a bot that is halted right now and genuinely needs
attention. Two separate tests hold the two halves, and neither would notice the
other's failure.

### One implementation detail worth recording

An empty bot-id set is handled with an **early return** rather than being passed
into an `IN ()` query, because this project's data layer **refuses an empty `in`
as a SQLite syntax error by design** — deliberately, rather than silently
rewriting it to "match nothing", which would hide a caller bug. Found while
building, not by a failing test.
