## PART 2 — THE REAL FINDING: TWO INDEPENDENT BUGS THAT COMPOUND

The `-2.59420419` is not an approximation of anything and not a coincidence. It
is `bot-x93xux`'s entire LINK holding, to the satoshi, resurrected as a baseline
hours after that position ceased to exist. Two separate defects were needed to
produce it, in two different functions, each correct-looking on its own.

### (a) The baseline lookup trusts the newest row, and nothing writes the zero

`reconcileBalances` picks an asset's baseline like this
(`src/reconciliation/reconcile.ts:1359`):

```ts
const previous = await db.balanceSnapshots.findMany({
  where: { account_label: accountLabel, asset },
  orderBy: [{ column: "checked_at", direction: "desc" }],
  limit: 1,
});
const baseline = previous[0];
```

**No recency check. No continuity check.** Nothing asks whether that row came
from the previous run, or from five runs and twenty-five minutes ago. The lookup
is only sound if every run writes a row for every asset, and it is the asset set
thirty lines above that breaks that premise
(`src/reconciliation/reconcile.ts:1341`):

```ts
const assets = new Set<string>([
  ...ledgerRows.map((row) => row.asset),
  ...balances.filter((balance) => balance.free + balance.locked > ZERO).map((b) => b.asset),
]);
```

`capital_ledger` on `kraken-main` holds **exactly one row — USDT**:

```
asset  total         alloc         updated
USDT   452.14727530  125.00000000  2026-09-11 10:05:32
```

So **every base asset on this account — BTC, ETH, LINK, SOL, XRP — is in the
reconciliation loop only while its balance is strictly greater than zero.** The
moment one hits exactly zero it is not skipped-and-logged, not adopted, not
recorded: it is **not considered at all**. No snapshot row, no finding, no entry
in `skipped`. The zero is never written down, and `ORDER BY checked_at DESC`
then reaches straight back past it to the last pre-zero observation and calls
that "the last observation".

⚠ Note that this is **entirely internal**. The filter is on this system's own
arithmetic, not on what Kraken sent: even if the venue explicitly reported
`LINK: 0`, the row would still be discarded by `> ZERO` before the loop ever saw
it.

⚠ It is also the exact **opposite** of the treatment the account-wide case gets.
`auditEmptyBalanceSet` exists precisely to insist that an empty balance response
is **unread, not a set of true zeros**, and its tests assert the baseline
survives. A single asset vanishing from a populated response is the genuine
zero — and it is the one the code silently throws away.

### (b) `recordedActivity` excludes stopped bots, so an archived bot's closing sale disappears

The delta side is computed by `recordedActivity`, which is handed the bot list
built in `reconcileAccount` (`src/reconciliation/reconcile.ts:211`):

```ts
const bots = await db.botInstances.findMany({
  where: { account_label: accountLabel, status: { in: [...RECONCILED_STATUSES] } },
});
```

with `RECONCILED_STATUSES = ["created", "running", "halted"]` and this stated
justification at `src/reconciliation/reconcile.ts:128`:

> `stopped` is excluded: its capital is released and it holds no position, so
> there is nothing of its to compare.

**That reasoning is correct for orders and positions and wrong for balance
activity, and the distinction is the whole bug.** For section 2 of the pass it
is right: a stopped bot has no live order to chase and no position to compare.
But the balance delta is not a statement about what a bot *currently holds* — it
is a statement about **money that moved**. And a stopped bot holds nothing
**precisely because it sold**. That sale is not incidental to its stopped
status; it is the *cause* of it, and it is exactly the movement this calculation
exists to explain.

The consequence is concrete and it is not rare:

> ⚠ **A liquidate-then-close sequence — the standard cleanup flow, run twice
> earlier this same night, on `bot-x93xux` and on `bot-653x4g` — makes the
> bot's own closing trade permanently invisible to every future reconciliation
> run.** The instant `status` becomes `stopped`, the sale that produced the
> proceeds drops out of the activity set forever.

### How the two combined here

`bot-x93xux`'s liquidation brought LINK to zero, and the zero was **never
recorded**. `bot-1gxj0h`'s fresh, correctly-sized $10 entry brought LINK back
non-zero. The stale **2.59420419** baseline and the now-invisible **2.59420419**
sale then met in one subtraction:

```
baseline (stale, 09:40:32Z)          2.59420419
+ recorded activity (new buy only)  +0.87215742
= internal_calculated_balance        3.46636161
- exchange_reported_balance          0.87215742
= "unexplained"                     -2.59420419
```

Exact, to the satoshi, and **fully mechanical**. It looks like a coincidence —
the gap being precisely the liquidated bot's holding — because it *is* that
holding, counted once in a baseline that should have been superseded and never
cancelled by the sale that superseded it.

### ⚠ CORRECTION TO THE FRAMING THIS ENTRY WAS OPENED WITH: both bugs are real and independent, but either fix alone would have prevented THIS trip

This entry was opened on the premise that both defects were **required** for the
incident, verified by reverting each alone. **That premise is wrong as stated,
no such test has been run — the fix is not implemented — and the accurate
version is more alarming, not less.**

Traced against the real timeline above:

- **Fix (b) alone would have prevented it.** With archived bots included, the
  10:05:32Z delta becomes `-2.59420419 + 0.87215742 = -1.72204677`, so
  `internal = 2.59420419 - 1.72204677 = 0.87215742` and the discrepancy is
  **zero**, stale baseline and all.
- **Fix (a) alone would have prevented it.** The 09:45:32Z run fell **28 seconds
  before** `bot-x93xux` was archived, so the sale was *still visible to it*. Had
  LINK been carried forward, that run would have written `exchange 0, internal
  0, discrepancy 0` and the 10:05:32Z baseline would have been the correct zero.

⚠ **So this incident survived on a 28-second accident of ordering, and that is
the finding, not a mitigation.** Had the operator closed `bot-x93xux` at 09:44Z
instead of 09:46Z — two minutes earlier, an entirely arbitrary difference — the
zero row written at 09:45:32Z would *itself* have carried a `-2.59420419`
discrepancy, and fix (a) alone would **not** have saved it. The ordering that
made one fix sufficient here is not guaranteed by anything.

Both defects are therefore live hazards with distinct failure modes, and **both
must be fixed**:

| | fixed alone | still broken |
| --- | --- | --- |
| **(a) only** | this trip | any archive landing before the recording pass (a ≤5-minute window, hit by the standard cleanup flow) |
| **(b) only** | this trip | **the silent false negative in PART 4** — a non-trade drain to zero is still invisible |

The test in PART 7 is constructed to require both, by archiving the selling bot
**before** the pass that would record the zero — the ordering this incident
happened not to take.

## PART 4 — ⚠ THE MORE SERIOUS HALF: A STANDING, SILENT BLIND SPOT ON EVERY NON-USDT ASSET

**This is the part that matters most, and it is categorically different from the
other two incidents tonight.**

Entries [104](104.md) and [105](105.md) were both **false alarms in the safe
direction**. In each, reconciliation and the circuit breaker did their job: they
detected a real condition, halted the fleet, and the money turned out to be
exactly where the exchange said it was. The controls worked, and the cost across
both was under $2. A system that over-halts is expensive and annoying; it is not
dangerous.

**This bug's dangerous direction is a false NEGATIVE.**

Because an asset outside `capital_ledger` leaves the reconciliation loop
entirely the moment its balance reaches zero, the code path that would report an
*unexplained* drain to zero **does not execute**. Consider LINK going
`2.59420419 → 0` through something genuinely wrong — an unauthorized withdrawal,
a compromised API key, a transfer nobody authorized, any real problem at all:

1. The asset's balance is `0`, so `> ZERO` drops it from `assets`.
2. It has no `capital_ledger` row, so nothing puts it back.
3. The `for` loop never iterates over it. **No baseline is fetched, no delta is
   computed, no discrepancy is calculated.**
4. No `balance_drift` finding. No alert. No breaker trip. **No entry in
   `skipped`** — the run reports itself as fully successful and clean.
5. `resolveClearedAlerts` is gated on `skipped.length === 0`, so such a run is
   even entitled to **close live standing alerts** on the strength of it.

**An attacker draining a non-ledger asset to exactly zero is, today, invisible
to reconciliation.** Draining it to a dust remainder would be caught; taking all
of it is not. That is the wrong way round.

⚠ **This is a live, standing blind spot on `kraken-main` right now, for every
asset except USDT.** At the time of writing the exposed holdings are:

| asset | balance | in `capital_ledger`? | protected? |
| --- | --- | --- | --- |
| USDT | 452.14727530 | ✅ yes | ✅ yes |
| XRP | 14.73014376 | ❌ no | ❌ **no** |
| LINK | 0.87215742 | ❌ no | ❌ **no** |
| ETH | 0.00242250 | ❌ no | ❌ **no** |
| BTC | 0.00025435 | ❌ no | ❌ **no** |

and SOL joins the list the moment `bot-wfemoo` holds any.

The false positive that tripped the breaker tonight and this false negative are
**the same defect seen from opposite sides**: one asset going to zero and coming
back produced a loud, wrong halt; one asset going to zero and staying there
produces nothing at all. The loud half is what got this investigated. **The
quiet half is the one worth fixing for.**

## PART 5 — THE FIX, THREE PARTS

All three are proposed, **none is implemented**. No raw SQL is used anywhere:
`Database` accepts no SQL on its surface and `no-raw-d1.test.ts` fails the build
if any file outside `/src/db` reaches past it, so both queries below use
existing `Repository` primitives.

### (a) Record a zero balance exactly once, by carrying forward the previous run's asset set

In `reconcileBalances`, immediately **after** the existing `empty` check:

```ts
// An asset that has gone to zero must be recorded AT zero, or the next
// non-zero reading measures from the pre-zero baseline -- which is this
// incident. Carry forward the previous run's non-zero assets: writing the
// zero row makes the NEXT lookup correct, and because that row is itself
// zero the asset drops out on the run after. Self-terminating; no unbounded
// zero rows for an asset that was traded once and never again.
//
// AFTER the `empty` check on purpose. An empty balance SET is an unread
// signal, not a set of true zeros (`auditEmptyBalanceSet`), and adding
// assets here before that decision would mask it and report every holding
// as drained at once.
const [last] = await db.balanceSnapshots.findMany({
  where: { account_label: accountLabel },
  orderBy: [{ column: "checked_at", direction: "desc" }],
  limit: 1,
});
if (last !== undefined) {
  const previousRun = await db.balanceSnapshots.findMany({
    where: { reconciliation_run_id: last.reconciliation_run_id },
  });
  for (const row of previousRun) {
    if (row.exchange_reported_balance > ZERO) assets.add(row.asset);
  }
}
```

Two `findMany` calls; `idx_balance_snapshots_run` already covers the second.
**Termination, stated explicitly** because it is the property that makes this
safe to run every five minutes forever:

| run | balance | previous run's row | in `assets`? | row written |
| --- | --- | --- | --- | --- |
| N | 2.59 | — | ✅ (non-zero) | `2.59` |
| N+1 | 0 | `2.59`, non-zero | ✅ **carried forward** | **`0`** |
| N+2 | 0 | `0`, zero | ❌ | none |
| N+k | 0.87 | — | ✅ (non-zero) | `0.87`, baseline `0` ✅ |

This also closes PART 4: the zero row is now *computed*, so an unexplained drain
produces a real `balance_drift` finding instead of silence.

### (b) Widen the bot filter for balance activity specifically

```ts
// Balance activity is about money that MOVED, not about what a bot currently
// holds. RECONCILED_STATUSES is the right filter for orders and positions
// and the wrong one here: a stopped bot holds nothing precisely BECAUSE it
// sold, and that sale is the movement this delta exists to explain.
const allBots = await db.botInstances.findMany({ where: { account_label: accountLabel } });
const activity = await recordedActivity(ports, accountLabel, allBots, skipped);
```

`reconcileAccount`'s existing `bots` list is **unchanged** and still drives
order and position reconciliation, where `RECONCILED_STATUSES` is correct. Only
the balance-activity call is widened.

**Safe against double-counting, and that is not an assumption.** `activitySince`
already drops every contribution with `executedAt <= since`, where `since` is
the asset's own baseline `checked_at` — the per-asset window that step
[24](24.md) installed for exactly this reason. Widening the bot set adds trades
to the pool; it cannot add any that the baseline already absorbed.

Cost: a few extra `getSymbolFilters` calls for pairs only archived bots traded,
cached per pair within the run, issued at ROUTINE priority through the account
rate limiter. Given entry [105](105.md)'s open item 1 — rate-limit starvation
under fleet load is still unaddressed — this is worth measuring rather than
assuming, but the per-pair cache bounds it to one call per distinct historical
pair per run.

### (c) Make the baseline's age explicit in the alert text

The current wording — *"From the last observation of 2.59420419"* — is
true-sounding, and was twenty-five minutes and five runs stale. The message
should carry the baseline's own timestamp and age:

> `LINK: the exchange reports 0.87215742. From the observation at 2026-09-11T09:40:32Z (25 minutes and 5 runs ago) of 2.59420419 plus …`

⚠ This changes no behaviour and prevents no incident. It is in the fix because
**this investigation should not have taken an investigation.** A stale baseline
is currently indistinguishable, on the incident-response surface, from a fresh
one — and that surface is the same one entry [105](105.md) PART 1 already flags
for the undiagnosed five-hour timestamp offset. Both are cheap defects on the
one screen an operator reads under time pressure.

There is currently **no coverage of a single asset going to zero**. The

case and asserts the **opposite** treatment (baseline survives, nothing recorded
as drained) — correctly, for that case. The per-asset case has never been
exercised, which is why two defects sat in `reconcile.ts` through step 24's
rework of this exact function.

The test, in `reconcile.test.ts`:

1. Seed a non-zero baseline for a non-ledger asset (LINK), with a selling bot
   holding it.
2. Sell the entire holding to **exactly zero**.
3. **Archive the selling bot (`status: "stopped"`) BEFORE the next
   reconciliation pass** — the ordering this incident happened not to take, and
   the reason both fixes are independently required.
4. Run reconciliation across **several** passes at zero, so the carry-forward's
   termination is exercised rather than assumed: pass 1 must write exactly one
   zero row, passes 2 and 3 must write **none**.
5. With a **second** bot, buy a **different** quantity (0.87215742 against
   2.59420419 — different on purpose, so a test that silently compares the wrong
   pair of numbers cannot pass by coincidence).
6. Assert `discrepancy === ZERO`, no `balance_drift` finding, and
   `circuitBreakerTripped === false`.

**Both fixes must be independently required**, and that is the property the test
is for:

| revert | expected result |
| --- | --- |
| fix (a) alone | **must fail** — no zero row, baseline reaches back to 2.59420419 |
| fix (b) alone | **must fail** — archived bot's sale invisible, zero row at step 4 carries `-2.59420419` |
| both | must pass |

A test in which either revert still passes is testing the wrong ordering and
must be rewritten — that is exactly the trap this incident's real timeline
falls into (PART 2's correction).

**The other direction must be asserted too**, or the fix is just a detector that
stopped detecting: a separate case must confirm that an asset drained to zero
with **no** recorded activity explaining it — PART 4's unauthorized-withdrawal
shape — now produces a **severe** `balance_drift` where today it produces
silence. That case is the reason for the fix, and it must fail against current
`main`.

### ⚠ TWO FURTHER DEFECTS, FOUND WHILE BUILDING THE FIX, BOTH REQUIRED FOR IT TO WORK

Neither was in PART 5's three-part plan. Both were found by building it, and
**each would have made the planned fix useless or harmful** rather than merely
incomplete.

#### 1. A COMPLETE drain would have classified as harmless

PART 4 is the whole reason for this work: an asset draining to zero must stop
being silent. Recording the zero row was necessary and **not sufficient**.

`classifyFinding` escalates on `exceedsFraction(amount, reference, pct)`, and
`exceedsFraction` returns `false` outright for a non-positive reference — "a
non-positive reference means there is nothing to take a fraction OF". The
reference passed was `exchangeTotal`, **which is exactly zero when everything is
gone**. `balance_drift`'s floor is `minor`, whose defined action is
"auto-correct, log, **no alert**".

So the fix as planned would have written the zero row, computed
`-2.59420419` correctly, classified it `minor`, and **said nothing** — a
detector that detects and then stays quiet, which is the same blind spot wearing
a row in the table.

The reference now falls back to the expected balance when the exchange total is
non-positive:

```ts
magnitude: {
  amount: discrepancy,
  reference: exchangeTotal > ZERO ? exchangeTotal : internal,
},
```

⚠ Deliberately narrow. It touches **only** the case `exceedsFraction` already
refuses to judge, so **no existing classification moves** — a wider change
(taking the larger of the two, say) would have raised the denominator on live
findings and could silently downgrade a real one.

#### 2. `auditEmptyBalanceSet`'s empty check was confirmed genuinely dead — and this fix would have made it dangerous

Entry 106's open item 4 flagged this as noticed and uninvestigated. **It is
confirmed, not refuted**, and it is worse than the note supposed.

`empty` was `assets.size === 0`, and `assets` is a union with `capital_ledger`.
A ledger row is this system's own **configuration**, not an observation of
anything — so on any account that has capital, `assets` can never be empty and
the check can **never** fire. On `kraken-main` one USDT row killed it. Every
test in the `when the exchange reports an empty balance set` suite passes only
because **none of them seeds a ledger**.

Measured directly, with a ledger row present and the venue returning nothing:

```
skipped "NO holdings" : false          <- step 24's protection never fires
empty-set alerts      : 0
findings              : [ '0G/balance_drift/severe', 'USDT/balance_drift/severe' ]
breaker tripped       : true
```

⚠ **That output is with the new zero-recording logic in place, and it is why
this was fixed in the same pass rather than deferred.** Dormant, the dead check
cost nothing: a drained asset vanished silently. Combined with carrying forward
the previous run's assets, an **unreadable** balance response — a venue
mid-transition, or a client authenticated against the wrong account — would be
read as a **total drain of every holding at once**, reported `severe`, and would
**trip the breaker on it**, with `skipped: []` so the run still counted as a
clean observation entitled to resolve standing alerts. That is precisely the
failure step [24](24.md) built this check to prevent, and the planned fix would
have armed it.

Emptiness is now measured on the venue's own answer rather than on a set that is
half this system's configuration:

```ts
const heldAtVenue = balances.filter((b) => b.free + b.locked > ZERO);
const empty = heldAtVenue.length === 0;
```

**Not** fixed, and left for its own step: whether a genuine total drain across
every asset should ever be reportable at all, rather than always read as
"unread". That is step 24's documented decision and reversing it is a deliberate
change, not a side effect of this one.
