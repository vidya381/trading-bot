## Step 44: Stage 4 (Explain and assemble) — the proposal rendered for a human, entry 43's citation requirement discharged in the layer it was placed on, and the (c)-only pattern seen live in the rendering itself

Stage 4 is the first thing in this arc that is **not a backend endpoint**. Stages 2
and 3 are real, live-verified HTTP surfaces (`GET /assess`, `GET /derive`), and
this step adds **no third endpoint, no model call and no new backend code at
all**. It takes the two real responses a client already holds from two real calls
and presents them as one complete, human-readable proposal.

That is the whole of it, and stating the boundary first matters because the
temptation in this stage is to do a little more: to re-check a citation, to
re-validate a parameter, to store the proposal "just for now". None of those
happened, and each is argued below.

**Confined to `dashboard/`. `src/` was not touched, verified by diff.**

### ⚠ ENTRY 43'S REQUIREMENT WAS ON THIS LAYER, AND IT IS DISCHARGED HERE

Entry 43 decided **not** to build a parser-level distinction between kinds of
citation, and placed the requirement on Stage 4 in advance:

> Stage 4's presentation layer MUST be designed with explicit awareness that a
> citation may point to (a) real fetched data, (b) an absence marker, or (c) a
> prior stage's own claim — and MUST describe these differently to a human reader
> rather than rendering all three as interchangeable "here is the source"
> citations.

It also predicted exactly how this would go wrong: *"the session that builds
Stage 4 will otherwise meet a uniform list of `EvidenceItem`s and have every
reason to render them uniformly."* That is precisely what the response contains —
one flat array — and the requirement is the reason it is not rendered flat.

**No citation anywhere on the page is rendered as a bare "source".** Every one
carries a class badge, and every badge carries **words as well as a colour**,
because a distinction a colour-blind reviewer cannot make is the same as no
distinction. Amber and violet rather than red, deliberately: **(b) and (c) are
not errors and must not read as ones.** Entry 43 is explicit that the requirement
is not to hide or demote them, only to stop them reading as (a).

### The rule, traced from source — with one correction to how it had been paraphrased

Read from `assess-prompt.ts` (`collectCandidate`, `collectCandles`,
`collectNews`, `collectConcentration`, `collectBundleEvidence`) and
`derive-prompt.ts` (`collectAssessment`, `collectCapital`, `collectFilters`).
**Entry 43's table is accurate.** The implementation is:

| test on `source` | class | every real value today |
| --- | --- | --- |
| `startsWith("assessment.")` | **(c)** | `assessment.strategy`, `assessment.claims[N]` |
| `=== "news"` | **(b)** | `news` |
| `endsWith(".error")` | **(b)** | `candles.error`, `concentration.error`, `capital.error`, `filters.error` |
| everything else | **(a)** | `candidate.*`, `*.outcome`, `*.value.*`, `assembledAt`, `gatheredAt` |

**⚠ THE NEWS TEST IS EXACT EQUALITY, NOT A PREFIX, AND THE DIFFERENCE IS A REAL
FUTURE BUG.** The brief for this step paraphrased the rule as *"source starting
with `news`"*, which is correct **today and only today**. The paused slot's source
is the literal string `"news"`. The moment a news vendor is chosen (entry 30) that
slot emits `news.value.*` for **genuine fetched headlines**, and a prefix test
would label real data an absence marker — the exact inversion this module exists
to prevent. A future `news.error` is still caught, by the suffix rule. Recorded
here because the paraphrase is the kind that gets quoted forward.

**The failed-read test is a SUFFIX rather than a hardcoded set of four.** No
non-error source can collide with it — every other source is a path into a value
or an outcome discriminant — and a fifth slot added later follows the same
convention and classifies correctly with no edit here.

### ⚠ TWO REAL BRANCHES READ AS ABSENCE BUT CLASSIFY AS (a)

Found while tracing, recorded rather than silently worked around. **Entry 43's
table is the specified rule, and deviating from it in this layer would be Stage 4
rediscovering the decision independently — which that entry explicitly forbids.**
So the table is implemented as written and both branches are **pinned by tests**
so they are visible rather than surprising:

1. **`collectCandles`' empty-window branch** emits `candles.status` with the value
   `"MISSING -- the candle slot reports success but carries no candles at all…"`
   and the source `candles.value.candles`. That is an absence under an (a) source.
   `assess-prompt.ts` states the branch is **unreachable** (`fetchCandleWindow`
   refuses an empty answer with `no_candles_returned`) and exists only so a
   fabricated price can never be printed from an empty window. **This one is
   arguably a genuine gap in the rule** and is left open for the operator.
2. **`collectCapital`' zero-rows branch** emits `capital.status` with the value
   `"NONE -- …This is NOT a failed read."` and the source `capital.value.assets`.
   **This one is probably correctly (a):** the read SUCCEEDED and found nothing,
   and the value says so in its own words.

In both cases **the full rendered `value` is shown verbatim beside the badge**, so
a reader still sees MISSING/NONE in full. That is the property that makes the
deviation survivable, and it is why every citation row prints the whole value
rather than a summary of it.

### ⚠ CHECK 4 IS THE FINDING: the (c)-only pattern rendered live, unscripted

**This is the observation of the step, and it is the one entry 43 was written in
anticipation of.**

Entry 41 first flagged a parameter grounded in `assessment.claim.N` rather than in
a fetched datum, and called it an OPEN QUESTION. Entry 43 declined to enforce
anything about it and routed it to Stage 4's presentation layer instead. **On the
very first real proposal this layer rendered, a real model — unprompted, on data
nobody staged — cited `assessment.strategy` and nothing else for three separate
parameters at once.**

Three things are worth separating, because they are easy to run together:

1. **The rendering worked.** The reviewer could see, at a glance and per field,
   that three numbers rested on an earlier stage's judgement rather than on any
   observation this run made. That is the entire purpose of the requirement.
2. **Nothing here is a fault.** The citations were real ids the run really
   emitted. The model was told the strategy was already decided and its reasons
   were in the DATA section to build on (`deriveRules`), so citing the decision
   for fields that follow from it is coherent. The operator reviewed the values
   and did not judge the result unsound.
3. **This does NOT meet any of entry 43's reopening conditions, and the reasoning
   should be checkable rather than asserted:**
   - *Condition 1 — a THIRD kind of citation use appears.* **Not met.** This is
     pattern (c), already known. No fourth class appeared.
   - *Condition 2 — either kind produced an UNSOUND result.* **Not met on this
     run.** One reviewed proposal is not a clearance, and is not offered as one.
   - *Condition 3 — either kind is HARD TO VERIFY in practice.* **The opposite was
     observed.** The reviewer identified all three cases immediately, from the
     field-level warning, without reading badges one at a time. Entry 43 argued
     that *"a presentation layer that renders all three kinds identically would
     itself CREATE condition 3"*; this is the first evidence that a layer which
     does not, does not.

**One frequency observation, recorded and not acted on.** Entry 43 reasoned from
**two** data points across two runs, one of which was a single (c) citation on a
single parameter. This run produced **three (c)-only parameters in one response**.
That is a change in how often the pattern appears, **not a change in kind**, and
it does not satisfy any stated condition — but it is the sort of thing that looks
obvious in hindsight if the pattern later turns out to matter, so it is written
down now rather than reconstructed later. **The right response to a frequency
observation is to keep looking, not to build enforcement**, which is entry 43's
own argument applied to its own successor.

### Requirement 4 (21.3) — the panel that states limitations without inventing verdicts

Spec 21.3 requires the Explain stage to **state plainly** when a coin has limited
price history, thin liquidity, or hype-driven interest. **A judgement was made
here and it should be visible:** that duty was read as a duty on this layer to
STATE it, not a duty to forward it if an upstream model happened to mention it.

The reasoning, in one line each:

- The Assess prompt does ask for it (*"If the evidence is thin, shallow, or partly
  missing, SAY SO as one of your claims"*), but **a prompt instruction is a thing
  a model may or may not follow** — the same reason `assess-prompt.ts` pairs its
  grounding rule with a mechanical citation check rather than trusting the rule.
- 21.3's named failure mode is *"a proposal that reads as confident because the
  input was loud"*, and **a limitation rendered as claim four of six, in the same
  weight as the reasoning, is one a confident proposal absorbs.** So it is a
  distinct panel, between the concentration flag and the reasoning.
- It does **not** try to identify WHICH of Stage 2's prose claims is the honest
  one. That would be classifying model prose by meaning — a judgement, and exactly
  what entry 43 rejected in option C. The claims are shown; these facts are shown;
  the reader compares.

`dataLimits` reads `truncated`, `missingHistoryMs`, `requestedSince`, unclosed
candles, the news slot, each failed read, and `trending` provenance directly from
the bundle, and names the evidence ids that show each one.

**The live run found 4 real items**, which settles the most likely criticism of a
panel like this — that it is decorative and empty on real data:

1. **No specific history depth was requested** — the venue's own recent window,
   not a decision anyone made about how much history this judgement needs.
2. **1 open candle** in the window, so its OHLCV is partial and every aggregate
   includes it.
3. **No news collected** (entry 30), with the standing warning that this is not
   evidence of a quiet market.
4. **NO LIQUIDITY TEST EXISTS.**

**⚠ ITEM 4 IS THE DESIGN PRINCIPLE, AND THE OPERATOR'S REVIEW CALLS IT THE
CLEAREST REAL-DATA CONFIRMATION OF IT YET.** 21.3 names thin liquidity as a
hazard and **nothing in this system decides it** — no threshold in the spec, in
`concentration.ts`'s policy, or in the venue filters. The panel therefore names
the absence as **a decision this system has never made**, points the reader at
`candles.volume_total` for their own judgement, and **does not invent a number**.

Picking a threshold here would be a rendering layer inventing a risk rule in the
place least equipped to own it, then presenting its verdict as a finding. **An
unstated gap is the failure mode; a stated one is a limitation.** The same
argument is applied twice more in this step, to the staleness threshold and to
`minimumOrderCheck: none_published`, and it is the same argument section 5.6 makes
about not treating "could not reach the exchange" as a price move.

### Requirement 6 — four timestamps, ranked, with the reason attached to each

Four real fetch times stand behind a proposal and **they age at completely
different rates**, so collapsing them to one number would be an arbitrary choice
presented as an answer. `freshnessOf` publishes all four with a plain-language
sentence saying why each matters to someone deciding *now*:

1. **Price history** (`candles.value.fetchedAt`) — the headline. Every proposed
   bound, size and reference price is denominated against it, and entry 42's live
   run moved `candles.last_close` by 17.60 in ten minutes.
2. **Capital ledger** (`context.capital.value.readAt`) — `allocatedCapital` is a
   PREFILL; a stale figure makes a form fail validation, not a bad bot.
3. **Bot list** (`concentration.value.readAt`) — what the prominent flag rests on.
   Changes only when a human starts or stops a bot.
4. **Venue rules** (`context.filters.value.fetchedAt`) — slowest-moving.

Plus **the OLDEST of the four**, because a proposal is no fresher than its stalest
input, and those two rows are frequently not the same. `assembledAt`, `gatheredAt`
and `selectedAt` are shown **separately and labelled as NOT fetch times** —
`serialize.ts` says so at each of them, and this is the same statement at the
point a human reads it. The operator confirmed the ranking reads correctly against
the real ageing rates.

**⚠ 21.5 REQUIREMENT 4 IS ONLY HALF SATISFIED, AND THE PAGE SAYS SO.** The
timestamp half is done. The other half — *"flag the proposal as stale and prompt a
refresh"* — needs a number that **nothing in this system defines**: not the spec,
not any entry, not any constant. So no threshold is applied and the page states
that outright rather than looking satisfied. The one freshness rule that IS
defined is enforced, in the backend, where it belongs: `/derive` re-resolves every
resubmitted citation against evidence gathered by that request and refuses a
stale one with `citation_unknown` (entry 42, check 7).

### Requirement 5 of 21.5's transparency clause — the full evidence, and the difference

`assessResultView` and `deriveResultView` both publish `evidence` as **everything
the model was offered**, not only what it cited, and both say why: *what the model
ignored is visible only from the difference*. **That difference is only visible if
something computes it**, so every item is listed with whether it was cited, and
the uncited ones are **not** hidden behind a collapsed toggle.

Live: **31 of 75 cited on Derive, 9 of 56 on Assess.** Both stages therefore left
most of what they were given untouched, which is a fact about these two answers
that no summary would have surfaced.

### The cross-gather drift table — entry 42's check 5, now visible to a human

When the original `/assess` response is supplied alongside, ids present in both
runs with differing rendered values are tabled side by side. Live it showed real
drift, e.g. **`candles.volume_total` 0.60404208 → 0.60421708**.

This is a **second, independent confirmation of entry 42's decisive check**, from
a different direction: that entry proved the two gathers were independent by
comparing two saved response bodies with `jq`; this shows the same fact **to a
human reading the proposal**, in the place where it changes how they read it. The
table is framed as expected behaviour rather than as an inconsistency to
reconcile — the proposal was derived against the newer values, and every claim is
rendered beside the newer values too.

### WHAT STAGE 4 DELIBERATELY DOES NOT DO

Each of these was a live temptation and each is refused for a stated reason.

- **NO RE-VERIFICATION OF CITATIONS.** `/assess` resolved every citation against
  its own run's evidence; `/derive` re-resolved every resubmitted citation against
  evidence it gathered freshly, **before** spending an inference. Doing it again
  here would duplicate step 42's work and would invite the idea that the backend's
  answer needs a second opinion from a rendering layer.
- **NO RE-VALIDATION OF PARAMETERS.** The set already passed the real create-bot
  decoders, the mandatory stop-loss, the sanity bounds, the venue floor and the
  headroom check (21.5 req 3). **A second implementation of a risk check drifts
  from the first, and the copy that drifts is the one nobody is watching** — the
  spec's own words, applied to the last layer.
- **NO MODEL CALL AND NO NEW ENDPOINT.** Deterministic presentation over data that
  already exists and has already been verified.
- **NO APPROVE BUTTON AND NO PREFILLED CREATE-BOT LINK.** 21.1: the only way this
  output becomes a bot is a human reading it and filling in the create-bot form,
  which runs every check it runs today, unchanged and unweakened. A one-click
  bridge from a proposal to a creation is the affordance that turns "the human
  approves" into a rubber stamp, which is the thing 21.1 exists to prevent.
- **NO PERSISTENCE OF ANY KIND.** See below.

### ⚠ 21.5 REQUIREMENT 5 IS NOT SATISFIED, NOT PARTIALLY SATISFIED, AND NOT BEGUN

**Nothing on this page is stored.** No D1 row, no `audit_log` entry, no KV key, no
`localStorage`, no cache. Reloading the page loses the pasted responses, and **the
rendered footer says so to the reader**: *"If you close this tab, this proposal is
gone."*

This is the same constraint entry 42 carried in the open rather than bridging, and
for the same reason: requirement 5 specifies a real, persistent proposal record —
prompt text, settings, model id, raw responses, both upstream inputs, and the
outcome including *ignored* — and **a throwaway store invented in a rendering
layer would have a different shape, a different lifetime and a different owner
than the thing actually coming.** The scoping is stated in four places (
`proposal.ts`, `ProposalView.tsx`, `pages/Proposal.tsx`, and the rendered footer)
specifically so that a working Stage 4 is not mistaken for requirement 5 landing.

### The transport: pasted responses, not a trigger — and why that is a 21.6 question

The page takes the two response bodies pasted in. **It makes no network request of
any kind**, which also means it can be viewed with no backend, no Access session
and no `wrangler dev` running.

Making it CALL the endpoints instead would be a different decision belonging to a
different part of the spec:

- It is a **TRIGGER** decision (21.6), not a rendering one. Every research endpoint
  is curl-only today by explicit choice (entry 42).
- Each `/derive` costs a real paid inference, and a pair of calls has taken
  **41,712–88,480 ms** of model time across the three chains measured in entries 41 and
  42. **A button that spends money and blocks for a minute is a design problem of
  its own**, not a side effect of building a renderer.
- The two-call flow needs step 42's client-side projection
  (`citations: [.citations[].id]`), which is genuinely new client BEHAVIOUR rather
  than presentation.

**Recorded as a judgement call, not as an obvious one.** If a trigger UI is built
later, the renderer is unchanged and only `pages/Proposal.tsx` swaps.

### ⚠ STAGE 4 STILL CANNOT DETECT A BAD UPSTREAM JUDGEMENT

Carried forward from entries 40, 41 and 42 **without dilution**, because a
successful live render is exactly when it is most likely to be lost — and because
this stage is the one most likely to be mistaken for the check that catches it.

**A page that presents a proposal beautifully has made the proposal no better.**
Every check behind it answers *"is this internally consistent, currently grounded,
and acceptable to the real create-bot validators?"* **Not one answers *"was the
data worth reasoning about?"*** Classifying a citation says what a value rests on;
it does not say whether resting on it was wise. Naming a data limitation says what
was not covered; it does not say whether what was covered supports the conclusion.

**What this stage does change is narrower and is the point of it:** the human in
21.1 is the only part of the loop that can tell a well-grounded proposal from a
good one, and until this step that human was reading `jq` output. The rendered
footer states the limit in its own words, on the page, where it cannot be lost.

### Assumptions and limits, stated so they can be checked rather than discovered

1. **Never rendered against a live DCA proposal.** Every live derivation this
   project has produced has been **grid** — entry 41's two, entry 42's one, and
   the one behind this render. `ProposalParameters`' DCA field
   list is built from `DcaParams` and is **exercised by no real response**.
2. **The two edge branches above are pinned by tests, not resolved.** The
   empty-window one in particular may be a genuine gap in entry 43's rule.
3. **One reviewed proposal is not a clearance** for the (c)-only pattern. Entry
   43's condition 2 is not met *on this run*, which is weaker than not met.
4. **The transport choice was this session's**, argued above but not mandated by
   the brief.
5. **No staleness threshold, no liquidity threshold**, by design — both restated
   here because "the UI does not flag stale proposals" is true and should not
   surprise anyone reading this later.
6. **`minimumOrderCheck: none_published` is rendered as honest, not as a pass**, in
   the same spirit: on Gemini no notional floor exists, and the copy says nothing
   was checked rather than implying something was.
7. **The evidence-difference counts describe two answers**, not a rate. 31/75 and
   9/56 are two observations.
8. **Nothing was deployed by this step.** The code is in the working tree; the live
   results above are the operator's, from a local render against saved real
   responses.
