the silent path reachable.

## PART 3 — THE ROOT CAUSE, WHICH IS LARGER THAN ITEM (2)

**This is the main finding of the step, and it is not what was deferred.**

Entry 51 PART 3's failure table lists the silent case as **"connection accepted,
no response ever"** → bar appears **"never"**. That row reads as exotic — a
hung socket, a black-holed connection, something rare. **The real entry
condition is not exotic.**

```
tick() {
  controller?.abort();          // usePolling.ts:61 — kills the PREVIOUS request
  controller = new AbortController();
  ...
}
setInterval(() => void tick(), intervalMs);   // :82 — every 5000 ms
```

**If the API responds consistently SLOWER THAN THE 5 s POLL INTERVAL, each tick
aborts the previous still-pending request before it can resolve.** The abort
rethrows unwrapped at `client.ts:83`, is swallowed at `usePolling.ts:69`, and
**no `setState` ever runs**. The poll can never settle.

No hang. No dropped connection. No exotic failure. **Only latency above 5 s,
against a completely healthy server that is answering every request** — just too
slowly, and its answers are thrown away by the client before they arrive.

**How close that is, from this log's own measurements.** Entry 47 (`47.md:41`)
recorded a **legitimate real response at ~4,957 ms** in its HAR, against a poll
interval of 5,000 ms. **43 ms of headroom.**

⚠ **43 ms is an upper bound, not the margin.** Entry 47's 4,957 ms is a *server
wait time* — one component of total response time. Total elapsed time for that
request was necessarily **greater**, so the true headroom that day was **less
than 43 ms**. The condition that starves this poll has already been approached
by a normal, successful request on this system.

The consequences differ by page state, and this is the shape of the real problem:

| page state when latency rises above 5 s | what `usePolling` holds | what the operator sees |
| --- | --- | --- |
| **cold** — no poll has ever succeeded | `data: null`, `loading: **true** forever` | list views: `"Loading…"` forever. **Banner: NOTHING.** |
| **warm** — a poll succeeded earlier | `data: <stale>`, `error: **null**`, `lastUpdated` **frozen** | **stale data, presented with no error at all** |

**The warm row is the more dangerous one and it is not what entry 51 was
looking at.** No `setState` runs, so `error` stays `null` and `lastUpdated` stops
advancing — the dashboard keeps displaying old numbers with nothing marking them
as old.

## PART 4 — LIVE REPRODUCTION — THE OPERATOR'S, NOT ANY CODING SESSION'S

**Every live observation in this part was run by the operator, personally, in a
real browser. The coding sessions in this step ran nothing** — no `wrangler`
command, no HTTP request, no D1 query, no deploy. They read source and argued.
This section exists so that attribution is unambiguous.

**Method.** `window.fetch` patched in the browser console to delay every request
by a fixed amount before dispatch. Firefox, against the deployed testnet
dashboard (`trading-bot-testnet.vidya-991.workers.dev`).

| test | injected delay | duration | result |
| --- | --- | --- | --- |
| **1** | **6000 ms** | ~60 s | repeated `start` → **`FAIL AbortError`** on `/api/bots`, `/api/alerts` and `/api/kill-switch`. **ZERO successful responses.** |
| **2** | **20000 ms** | ~60 s | identical pattern. **Zero successes.** |

**CONFIRMED, OBSERVED, NOT INFERRED: the abort chain is real, and 6 s of latency
is sufficient to starve the poll indefinitely.** 6000 ms is 1.2× the poll
interval — the mechanism does not need a pathological delay, only one above
5,000 ms. Test 2 shows the behaviour does not change as latency grows; there is
no threshold beyond the interval itself.

## PART 5 — WHAT THE REPRODUCTION DID *NOT* SHOW

**The original symptom — the banner rendering NOTHING — was never reproduced.**

The test instructions had the page load **fully before** the `fetch` patch was
applied. By then `data` was already populated, so `loading` was already `false`
and the last-good rule kept displaying the previously fetched status for the
whole run. The banner had a real status object to reason from and correctly
rendered nothing, for the correct reason. **The silent-banner case requires a
COLD load in which no request ever succeeds** — the patch must be in place before
the first tick.

**That setup error was the operator's own, and it is recorded rather than
smoothed over.** The consequence is a split verdict that must not be collapsed:

- **The underlying defect is CONFIRMED.** The abort chain starves the poll; this
  was observed directly, twice.
- **Entry 51's specific described symptom is NOT confirmed.** The banner has
  never been observed rendering nothing under starvation.

**Also not established: whether the `"Live · updated <time>"` indicator continues
to claim liveness while every request is being cancelled. This was not checked.**
The indicator is `{error ? "Update failed" : "Live"} · updated {formatTime(lastUpdated)}`
(`Dashboard.tsx:35`, `Alerts.tsx:72`, `BotDetail.tsx:67`, `KillSwitchPage.tsx:160`),
and since no `setState` runs during starvation, reading the source suggests
`error` stays `null` and the indicator keeps reading **"Live"** beside a frozen
timestamp. ⚠ **That is a source-level inference, NOT an observation.** It was not
looked at in the browser and is listed in PART 8 as unverified.

**Test 3 (the control) was inconclusive.** Unpatching `window.fetch` removes the
console instrumentation along with the delay, so no success lines could be
printed either way. The control neither confirms nor refutes anything; it
produced no evidence at all.

## PART 7 — THE DECISION: NOT BUILDING

**Item (2) is NOT being built in this step.** Three reasons, recorded **as
reasons and not as excuses** — each is a fact about risk, and each would stop
applying if the fact changed:

1. **Testnet only.** The affected deployment is the testnet dashboard. No real
   capital is behind the numbers this defect would let go stale.
2. **It requires a latency condition never observed arising on its own.** The
   entry condition is sustained response times above 5,000 ms. Entry 47's HAR
   recorded **266 of 266 kill-switch requests succeeding** over 1373.7 s, with a
   worst case of ~4,957 ms server wait. The condition has been produced **only
   deliberately** — by DevTools request blocking in entry 51, and by the operator
   patching `window.fetch` in PART 4. It has never been caught happening by
   itself.
3. **The repair is riskier today than the defect.** The fix lands in
   `usePolling` — **five call sites and ZERO tests** (PART 2). Editing an
   untested hook that every polling surface in the dashboard depends on, to fix
   a condition that has never occurred unprompted, trades a rare unobserved
   failure for an immediate and real regression risk across all five consumers.

⚠ **Reason 3 is the load-bearing one, and it names its own expiry condition.**
It is an argument about *test coverage*, not about the defect's severity. **Cover
`usePolling` with tests and reason 3 evaporates.** That is what makes it a
deferral rather than a dismissal.

## PART 8 — RE-SCOPED: THIS IS NOT UI POLISH

**The item stays deferred, but it must NOT go back into the redesign queue under
its old description.** Entry 51 filed it as a banner-level design question with a
correctness caveat attached. That framing is now known to be too small.

> **RESTATED, AS THE THING IT ACTUALLY IS:**
>
> **The dashboard displays stale data confidently when the network is slow.**
> The root cause is in `usePolling`'s abort handling, not in the kill-switch
> banner. **It affects all five pollers**, not one. The kill-switch banner is
> where it is *most dangerous* — because that surface renders nothing rather than
> something — but it is not where the bug lives, and fixing only the banner would
> leave four other surfaces silently stale.

**Four options were enumerated by this investigation. NONE IS CHOSEN HERE**, and
choosing among them is deliberately left to the step that builds it:

| # | option | scope |
| --- | --- | --- |
| **A** | An elapsed-time threshold **in the banner** — entry 51's original item (2), costed there at 15 s / three poll intervals | one surface |
| **B** | An elapsed-time threshold **in the shared kill-switch provider** (`killSwitchStatus.tsx`) | both kill-switch consumers — banner and page |
| **C** | **Fix `usePolling` itself**, for all five pollers | every polling surface |
| **D** | **Stop aborting a still-pending first request** — let the in-flight request live rather than cancelling it each tick | every polling surface, different mechanism from C |

They are not equivalent in scope, cost, or risk, and they are not mutually
exclusive. **A deliberate non-decision, recorded as one.**
