## PART 1 — GAP A: `liquidatePosition` sold without ever checking what its own sweep left behind

`#liquidatePositionPass` cancelled, re-read state, and went straight on to size
and place the liquidation sell. **It never inspected the residual
`openOrderIds`.**

Its own comment, directly above the sweep, asserted the outcome:

> *"Clearing them mirrors `#gridExit`, so the liquidation sell is the only live
> order afterwards."*

**Nothing enforced that.** `#cancelOpenOrders` deliberately leaves two classes
behind — an unconfirmed cancellation (`cancel_failed`, where the order **may
still be resting on the exchange**) and entry 57's gate refusing to close a
record over a fill the venue reported and this bot had not.

**AND THE `exitOrderId` GUARD DOES NOT SEE THE DANGEROUS ONE.** That guard
refuses a live *exit* order. **A grid LADDER sell is not an exit order.** So an
unconfirmed ladder sell for part of the position could be resting while this
method sized a fresh sell from the **whole** of it — both filling would dispose
of more base than the bot holds, on the exact action an operator took to get
flat.

### The fix, and why its placement is not a copy of entry 64's

A refusal, **reusing entry 64's existing `orders_unresolved` code rather than
minting a new one** — already in the error union, already mapped to 409 at
`api/envelope.ts:123`. The residual list is read rather than the venue
re-queried, for entry 64's own reason: `#cancelOpenOrders` has already done the
local-versus-remote comparison, and asking again would be a second,
independently-worded comparison of the same two quantities — the drift entries
**57** and **61** were both built to eliminate.

**IT SITS ONE STEP EARLIER THAN `#closePass`'s EQUIVALENT, and that is an
adaptation rather than a copy.** Entry 64's gate sits immediately before
`releaseBotCapital`, because that call is `close()`'s point of no return. **A
liquidation has no capital release.** Its point of no return is
`#placeLiquidationSell`, so the refusal goes before the **ladder clear** as well
— which means a refused liquidation has mutated **nothing of its own**. The
ladder is still standing, the ids are still watched, and the sweep's writes are
its legitimate work either way. Recoverable exactly as a refused close is:
resolve the order, then call again.

### The second half of Gap A: the quantity was read from a stale snapshot

`heldQuantity` was computed from the **pre-sweep** state and used, several
awaits later, to size the sell.

**CONFIRMED A REAL RACE, NOT A THEORETICAL ONE, from the code's own record.**
`#outsidePoll` is a **counter, not a lock** — its docblock states that every
writer "proceeds exactly as before and is never delayed", and step 21's probe
measured the window as genuinely re-entrant, with an RPC and an alarm both
delivered while the object sat inside an await. The cancel sweep is **N
throttled network cancellations — the longest await in the method.** A fill
folded into that window moves the held position.

Fixed with a **second, post-sweep read**, carrying its own `liquidation_noop`
branch for a position that went flat mid-sweep.

**THE PRE-SWEEP FLAT CHECK STAYED EXACTLY WHERE IT WAS**, deliberately. Moving
it after the sweep would give entry **71**'s live-verified `nothing_to_liquidate`
no-op a side effect: a bot that is already flat must return having cancelled
nothing. A no-op that cancels orders on its way to doing nothing is not a no-op.

## PART 2 — GAP B: an unconditional ladder clear, one hop from a live liquidation

`liquidatePosition`'s grid branch nulls **every ladder slot unconditionally**,
without recomputing `openOrderIds`. A later ladder fill then re-derived the list
purely from slots — dropping **both** a retained unresolved id **and the
liquidation sell's own id**, which has never held a slot because
`#placeLiquidationSell` grants it none by design (it is strategy-agnostic, and
DCA, which shares it, has no ladder at all).

If the resulting list empties, **`#pollArmed` goes false and the alarm disarms**
— a sell still resting on the exchange, no longer observed by anything.

**Reachable, not exotic:** the poll folds fills on an already-halted bot, and
`#gridLevelOf` **reconstructs** a rung from the order's own `levelIndex`, so the
cleared ladder does not stop a fill reaching the write.

### The fix was NARROW by design

Rather than widen the pure slot-derivation function — a **broad blast radius**,
three call sites plus tests, and a function that would have to be handed runtime
state it has no business knowing — the fix preserved a live exit id **at that one
call site**, and only **if it was already on the list**. That predicate can
decline to drop something; it can **never resurrect** an exit a sweep resolved or
a fold closed.

### The finding that made Part 3 necessary rather than redundant

**Fixing Gap A closes one of Gap B's two routes and not the other.** Once a
liquidation cannot begin with an unresolved order on the list, the human path
into that state is shut. **`#gridExit` has no such refusal and never did.** So
the automated path remained open — which is why Part 3 is a separate piece of
work rather than a repetition of Parts 1 and 2.

## PART 3 — THE REAL FIX: maintained, not re-derived, at two sites

### The core defect, shared by both

`openOrderIds` was being **RE-DERIVED from ladder slots** on every fold and every
placement. For a grid that is *usually* the same list, which is exactly what made
it wrong where it is not.

**SLOT-ABSENCE HAS NEVER MEANT RESOLUTION IN THIS CODEBASE.** Every genuine
removal is **by name** — `#cancelOpenOrders`' resolved set,
`#foldTerminalState`'s by-name filter, `#completeLiquidation`'s
`filter(id !== exit)`. There are exactly two reasons a tracked id has no rung,
and neither is that it ended:

- `#placeLiquidationSell` appends its sell and grants it no rung, by design;
- `#gridExit` and `liquidatePosition` null **every** slot on their way out, while
  `#cancelOpenOrders` deliberately **retains** what it could not resolve.

The real-incident shape is already on record: **2026-07-31, "all five
cancellations failed on one parse bug."** After a grid exit in that state, every
retained id is rungless — and the irony is exact: **retention exists to hand the
order to the poll, and the poll's own fold was what dropped its siblings.**

### The rule, and the codebase's own precedent for it

`#cancelOpenOrders` already states the discipline in as many words:

> *"REMOVE WHAT THIS SWEEP RESOLVED, rather than assigning the list it believed
> in when it started."*

Both sites were the **assign-form of that same mistake**, so both take the same
cure rather than a second one that could drift from it. `openOrderIds` is
**maintained**: what was already tracked, minus what **this** operation actually
resolved, plus what **this** operation actually created.

### Why a refusal gate — Part 1's shape — was WRONG here

**`#gridExit` is the automated stop-loss and breakout response.** `close()` is a
human action with no time pressure, so refusing costs nothing. Refusing to place
a **protective exit sell** because a cancellation could not be confirmed would
leave a real position **genuinely unhedged in a falling market.** The fix had to
let the exit proceed **and** preserve tracking. It could not block the exit, and
no version of it does.

### Two sites, genuinely different treatment — confirmed from source, not assumed

**Site 4856, the fold (`#applyGridFillToOrder`).** `resolved` = rungs this plan
cleared, plus the folded order itself if it completed. A partial fill resolves
nothing and the id stays, which is correct — it is still live.

This **replaced the earlier `keepsExit` special case ENTIRELY** (it greps to 0).
The exit sell is now preserved as an **ordinary consequence of never being
resolved**, not as a named exception.

**THE `created` TERM WAS FOUND TO BE STRUCTURALLY ALWAYS EMPTY HERE**, and this
was checked in source rather than assumed: `planFill` **never claims a slot**. It
returns a replacement as an **intent**; the claim happens at site 4707. So
`afterSlots ⊆ beforeSlots` always, and **no dead code was written** for a term
that cannot occur.

**Site 4707, the placement (`#placeGridOrder`'s slot claim).** Confirmed **not**
a copy-paste of 4856: it is a **claim with a possible eviction**, not a fold. The
created id is the order just placed and is already in the new ladder; the
resolved id is the evicted occupant, if any. **Eviction still drops its id,
unchanged** — that is not tracking loss, it is the documented outcome of a slot
collision, which `grid_slot_collision` states explicitly.

**A RETRY-SAFETY CORRECTION FOUND AND APPLIED HERE**, as a real additional
improvement rather than incidental tidying: the eviction is now read **from the
`claim` itself** rather than from the outer `evicted` binding, so a retried
mutation callback cannot act on a value left by a previous attempt.

**Both collapse to one symmetric expression** — the new ladder's slot ids in
level order, followed by any tracked id that has no rung. On a healthy bot
nothing is rungless, so it writes **exactly the ids in exactly the level order it
always did.**

### The specific dangerous scenario this closes

**A `#gridExit`-halted bot carrying retained, unresolved orders can be RESUMED
into live trading, and nothing stops it.** `#resumePass` never clears
`openOrderIds`, and its drift latch (**step 57, fix 2**) reads
`ORDER_STATE_DRIFT_ALERT_TYPES` — which contains **neither `cancel_failed` nor
`cancel_fill_discrepancy`**. So the bot resumes carrying them, and its next
replacement placement **silently dropped every retained id while it was actively
trading.**

**Site 4707 was assessed as the MORE dangerous of the two, not equally
weighted:** 4856 fires on a halted bot, 4707 on a running one.

## PART 4 — TWO SELF-CORRECTIONS, CAUGHT BY THIS SESSION'S OWN MUTATION TESTING

Both were **real errors in this session's own design document and test code**,
not refinements, and neither is softened here.

### 1. The design document's safety claim was FALSE, and its own test proved it

The design stated the rule "never adds an id that was not already tracked, so an
order the sweep genuinely resolved cannot be resurrected here."

**That holds for the `retained` term and NOT for the `slotIds` term.** A manually
halted bot's ladder keeps **stale, never-cleared rungs** (see Part 5), so
`ladderOpenOrderIds` can name orders this bot already resolved — and both the new
write **and the one it replaced** include them. **Byte-identical, therefore not a
regression, but the design's universal claim was wrong.**

**The first correct-drop test asserted the design's claim and correctly FAILED
against the real fix.** It was **rewritten to pin the invariant that genuinely
holds** — that nothing enters the list which was neither tracked before nor on
the ladder now — **not weakened to force a pass**, and the stale-slot exception
is documented in the test body so the next session finds it.

### 2. The first site-4707 test was VACUOUS and passed anyway

It used resume plus a price update. **That never triggers a placement at all** —
`decide` rebuilds a ladder only while `placed` is false, so a resumed grid does
not re-place its rungs. The test passed while testing nothing.

**Found because mutation M4 did not kill it**, which is the entire reason for
running mutants against new tests. Rebuilt on the real triggering path,
**replace-on-fill**.

## PART 5 — FOUND, RECORDED, DELIBERATELY NOT FIXED

**Site 2868 (`#foldTerminalState`) — the opposite-direction defect.**

A manually halted grid bot's ladder slots are **never cleared**:
`#recordCancellation` does not touch the ladder, and only `#foldTerminalState`
clears a rung — reached solely from the poll, which reads only `openOrderIds`.
So the rungs of cleanly cancelled orders **stand indefinitely**.

Folding one retained order can then re-derive `openOrderIds` from a ladder
**still holding already-cancelled, already-resolved orders**, putting them back
on the tracked list. **That is the opposite direction to everything fixed in this
entry** — resurrection rather than loss.

**It is left unfixed per an explicit scope decision by the operator**, made for a
stated reason: mixing two opposite-direction bugs into one change makes mutation
testing harder to trust. **It is a real, separate defect. It is not minor, not
scheduled, and not fixed.**

**NEW INFORMATION THIS SESSION FOUND, BEYOND THE DESIGN DOCUMENT:** the same
stale-ladder mechanism **also reaches site 4707**, through its `slotIds` term —
discovered when the first correct-drop test failed (Part 4). **A future fix for
2868 must therefore account for both sites together, not 2868 in isolation.**
