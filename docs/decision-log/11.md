## Step 11: Account registry, live pair listing, and exchange dispatch
Date: 2026-07-28

### What was built

The piece step 3.4 (decision 0) deferred to "its own step": choosing the
Binance-vs-Gemini client for an account instead of always building a Binance one,
plus the account registry that makes that choice a registered fact rather than a
free-typed guess.

- **Migration `0006_accounts.sql`** — an `accounts` table (`account_label`
  primary key, `exchange` CHECK-constrained to `binance`/`gemini`, timestamps),
  STRICT, with a backfill from existing `bot_instances`. Mirrored into
  `src/db/schema.ts` (new `ExchangeId` union + `isExchangeId` guard, the
  `accounts` table, `AccountRow`, `ALL_TABLES`), `src/db/database.ts` (an
  `accounts` repository), and `src/db/test-helpers.ts` (delete list + `accountRow`
  factory).
- **`listTradablePairs()` added to `RestExchangeClient`** (section 4.1) and
  implemented in both clients — Binance via the full `exchangeInfo` catalogue
  (`parseTradablePairs`, TRADING-only), Gemini via `/v1/symbols`
  (`parseSymbolList`). Propagated to the `RateLimitedExchange` wrapper and the
  `FakeExchange`.
- **`src/workers/exchange-dispatch.ts`** — `resolveExchangeForAccount`, the single
  seam that dispatches an `ExchangeId` to `resolveDefaultExchange` (Binance) or
  `resolveGeminiExchange` (Gemini).
- **`src/workers/symbols.ts`** — `listTradablePairs` behind a KV cache
  (`KvSymbolCacheStore` over a new `SYMBOL_CACHE` namespace) plus `envSymbolLister`
  and the `listAccountSymbols` orchestration.
- **Three endpoints** — `GET /api/accounts`, `GET /api/accounts/:label/symbols`,
  and the reworked `POST /api/bots`, wired in `src/api/handlers.ts`,
  `src/api/router.ts` (a `symbolLister` port on `ApiContext`), and
  `src/api/index.ts` (routes + default).
- **Docs** — account-registration runbook in `docs/d1-provisioning.md`,
  `SYMBOL_CACHE` provisioning in `docs/kv-provisioning.md`.

1241 tests pass (up from 1208), typecheck clean. No live network call anywhere in
the suite: the symbols endpoint's exchange call is injected (`symbolLister`), the
clients' new methods are driven by a mocked `fetch`, and the resolvers are only
constructed. (The suite also emits one unrelated miniflare worker-teardown error
on close — a pre-existing environment artifact, not a test failure.)

Nothing about the strategies, reconciliation, or either client's existing methods
changed. Both exchanges still coexist; this wires them to the account model.

### Decisions made

**0. This is the dispatch step 3.4 named, built now in full.** *(scope)*

Step 3.4 built Gemini fully behind the interface and left "which exchange does a
bot use" for a separate step, because it is a data-model decision. This is that
step. Two facts reshaped it before any code was written and are worth recording,
because the task's framing predated them:

- `bot_instances.exchange` **already existed** (`TEXT NOT NULL`, no CHECK) and
  `POST /api/bots` already stored whatever string the request typed. So this step
  did not *add* exchange to bots; it made the account→exchange fact authoritative
  and *used* it, replacing "trust the request" with "derive from the registry".
- `RestExchangeClient` had **no list-all-pairs method** — only per-pair
  `getSymbolFilters`. "Live tradable pairs" (the task's point 4) therefore needed
  a new capability, which is where it met the "don't disturb the clients" ask
  (point 6). Both were confirmed with the owner before building (see decisions 4
  and 6).

**1. A separate `accounts` table, not a per-bot column, and the exchange enum
mirrors an app-side union.** *(asked implicitly via the design; owner approved)*

The exchange is a property of the ACCOUNT, not of each bot. Recording it per bot
let two bots on one account disagree about the account's exchange — a
contradiction nothing could detect. `account_label` is the primary key, so the
fact is single-valued. `bot_instances.exchange` stays (denormalised, convenient,
and now validated against this table at create time), but `accounts` is
authoritative.

The `exchange` CHECK lists the two exchanges exactly as
`bot_instances.strategy_type IN ('grid','dca')` does, and the new `ExchangeId`
union in `schema.ts` is the single source that CHECK shadows — the same pattern as
`StrategyType`/`OrderState`. Adding a third exchange is deliberately a VALUE
change: one member on the union, one string on the CHECK (a table-rebuild
migration, since SQLite cannot ALTER a CHECK, but touching only this small table).
`resolveExchangeForAccount`'s `switch` has no default, so a new `ExchangeId`
member fails to compile until its resolver is wired — the "a new value must be
handled, not guessed" property carried into the dispatch.

**2. Credential mapping is by CONVENTION, and no unused column was added.**
*(the point-1 question the task asked me to decide)*

The two resolvers already read fixed secret names (`BINANCE_API_KEY`/`_SECRET`,
`GEMINI_API_KEY`/`_SECRET`) and are the single home for secret→client. A per-row
`secret_name` column today would be metadata NOTHING reads — precisely the "looks
wired but isn't" gap steps 3.2 and 3.4 warn against, and the same class of dead
authoritative-looking field step 3.1's decision 2 refused. So convention it is,
and — following the codebase's no-dead-fields stance — the column that *would*
carry an explicit mapping is deliberately NOT added yet.

*Storing secret names per row now — rejected.* It only becomes real when two
accounts on the SAME exchange need DIFFERENT keys, which cannot happen today (one
account per exchange per environment). At that point the forward path is a plain
append-only `ALTER TABLE accounts ADD COLUMN credential_ref TEXT` (the shape of
`capital_asset` in 0002, `notified_at` in 0004) PLUS teaching the resolvers to
honour it — built when a reader for it exists, not before. Adding the column now
would cost the same later and buys nothing but an always-NULL field in the
meantime.

**3. Registration is a manual D1 insert, not a `POST /api/accounts` endpoint.**
*(the point-2 question the task asked me to decide)*

Mirrors how `capital_ledger.total_balance` is seeded by hand today
(`seedPlaceholderTotalBalance`, step 5 decision 6). Registering a real account is
a rare, high-privilege human act done a handful of times per environment. A POST
endpoint would be speculative auth/validation/audit surface for that frequency,
and this codebase's ethos is to build the endpoint when it is needed, not before.
`docs/d1-provisioning.md` carries the exact INSERT, for one Binance and one Gemini
account. If self-service is ever wanted, it is a small, well-scoped addition
against a table that already exists.

**4. `listTradablePairs` is a NEW interface method, added additively to both
clients.** *(asked; owner chose "add to interface + both clients")*

The interface could not list pairs, and the task wanted the list to come from the
real client (point 4) while leaving the clients' suites unaffected (point 6). The
owner chose to add the method. It is purely additive: no existing method changed,
so every existing client test passes untouched (point 6's substance), while new
tests cover the new method. The alternative — a worker-layer read straight to the
public symbols endpoint, bypassing the client — was rejected for duplicating
transport and defeating the abstraction point 4 asks for.

The two implementations diverge where the venues do, stated rather than hidden:

- **Binance** hits the SAME `exchangeInfo` endpoint as `getSymbolFilters` but with
  no `symbol` param, so the body is the whole catalogue. `parseTradablePairs` is
  deliberately leaner than `parseSymbolFilters` — it reads only each entry's
  `symbol` and `status` and keeps the `TRADING` ones. A full catalogue is
  thousands of symbols in every state; forcing them all through
  `parseSymbolFilters` (which throws on any entry missing an asset or a recognised
  status) would let one odd delisted symbol refuse the entire list. A nameless or
  non-TRADING entry is excluded, not thrown on; only a missing top-level `symbols`
  array is loud, since that is a real API change.
- **Gemini** hits `/v1/symbols`, which returns lowercase separator-less names and
  — unlike Binance — carries NO per-symbol status (Gemini exposes status only via
  the per-symbol `/v1/symbols/details/{symbol}`). So the Gemini list is taken as
  the tradable set directly and NOT status-filtered; `parseSymbolList` upper-cases
  each name back to this system's `Pair` convention (the inverse of
  `toGeminiSymbol`). Confirming a symbol is actually `TRADING` remains
  `getSymbolFilters`' job at order time on both sides, so nothing is lost.

The `RateLimitedExchange` weight table (`MethodWeights = Record<keyof
RestExchangeClient, number>`) forced the new method's weight to be declared — it
uses `exchangeInfo`'s weight — which is exactly the compile-time guard step 8 built
to stop a new call slipping past the budget.

**5. The pair list is cached in a DEDICATED `SYMBOL_CACHE` KV namespace, and a
missing cache DEGRADES rather than fails.** *(decided)*

The tradable set changes rarely while a dropdown might ask for it constantly, and
the underlying call is a full-catalogue request that spends budget — so it is
cached with a one-hour TTL, matching `bot-instance.ts`'s own `FILTER_MAX_AGE_MS`
(the two are the same kind of periodically-refreshed reference data, section 4.3).
This is the KV pattern `cooldown.ts` uses and section 8.3 assigns KV: a transient,
self-expiring value where staleness costs at worst a slightly out-of-date list,
never a trading decision. It is the second place KV staleness is harmless, for the
same reason as the first.

*A dedicated namespace rather than reusing `ALERT_COOLDOWNS`* — this codebase
keeps concerns in separate stores deliberately (the breaker chose D1 over KV; the
kill switch chose its own table over a breaker row). Introduced the way
`ALERT_COOLDOWNS` was: declared for tests via miniflare, kept out of
`wrangler.jsonc` until a real id exists (no placeholder ids), with an optional
`declare global` in `symbols.ts`.

*Degrade, don't fail, when `SYMBOL_CACHE` is absent.* A missing cache is a
performance concern, not a correctness one — unlike a missing credential, which
fails closed. So the endpoint still returns pairs (with `cached: false`) via a live
call, and a KV read/write error is treated as a miss (as `KvCooldownStore` treats
a garbled value). A transient exchange FAILURE is never cached, so an outage is not
remembered for an hour.

**6. `POST /api/bots` derives the exchange from the registry: authoritative when
registered, soft-fallback when not.** *(asked; owner chose "backfill +
soft-enforce")*

This is the actual dispatch fix. The account registry is authoritative:

- Account IS registered → its exchange is used; a request `exchange` that
  disagrees is REJECTED (`exchange_mismatch`, 400), not silently overridden. A bot
  quietly wired to the wrong venue is the failure this step removes.
- Account is NOT registered → soft fallback to the request's `exchange` (the
  pre-registry behaviour), validated to be a known `ExchangeId`. Creation still
  works for an un-backfilled or not-yet-registered account.

The soft half is what keeps point 6 true: ~10 test files create bots without an
`accounts` row, and strict enforcement would have made every one of them seed the
registry first. Soft-enforce leaves those on the fallback path, undisturbed, while
a registered account becomes authoritative the moment it exists. Migration 0006's
backfill means real pre-existing accounts start registered, so in practice the
fallback is for accounts that never existed yet, not for a gap in coverage.

**7. `resolveExchangeForAccount` is the single dispatch home the future execution
path reuses.** *(honours step 3.2's open question 2)*

Step 3.2 asked that when order execution is wired, it reuse the base-URL derivation
rather than re-deriving it "so the 'impossible to get backwards' property has a
single home." This function is that home. Today its only live consumer is the
symbols endpoint; when a bot's execution client is built, it resolves through the
same function and inherits the same fail-closed, environment-derived guarantees.

**8. The symbols endpoint takes an injected `symbolLister`.** *(testability)*

`resolveDefaultExchange` builds a client with the global `fetch` — no injection
point — so the only way to test the endpoint's caching without a live network call
is a seam at the handler. `symbolLister` on `ApiContext` (default `envSymbolLister`)
is that seam, the same shape as the injected `access.fetchJwks`. The KV cache is
NOT injected: miniflare supplies a real local `SYMBOL_CACHE`, so tests exercise the
real `KvSymbolCacheStore` end to end, exactly as `cooldown.test.ts` uses the real
`ALERT_COOLDOWNS`.

### Deviations from the spec / prior entries

- **Section 4.1 grows a ninth method.** `listTradablePairs` is not in the spec's
  literal interface; it is added for the same reason step 3's decision 1 and 3.1's
  decision 1 reshaped that interface — the real work needs it and both venues
  provide it. Additive, so no implementation's existing behaviour changed.
- **`accounts` is not in section 8.2's table list.** Added by migration 0006, the
  way `circuit_breakers` (0003) and `global_kill_switch` (0005) were: a control the
  spec describes in prose that needs to exist as real, validated data.
- **The backfill cannot be exercised by `applyD1Migrations`.** That helper applies
  every migration to an EMPTY database, so `bot_instances` has no rows when 0006
  runs. The backfill's behaviour is pinned by a separate test
  (`accounts-backfill.test.ts`) that seeds bots and runs the same statement; the
  statement is duplicated there and a comment ties the two together.

### Open questions carried forward

Binance and Gemini client open questions from steps 3–3.4 are unaffected (their
existing methods are untouched). New:

1. **Bots still do not execute, so the dispatch selects a client for a path that
   does not run yet.** `POST /api/bots` now stores the RIGHT exchange and
   `resolveExchangeForAccount` can build the right client, but nothing constructs a
   live bot execution client (step 3.2 open question 2, 3.4 open question 4 remain
   the gate). Today the dispatch's only live consumer is the symbols endpoint. When
   execution is wired it reuses this function — that is the point of decision 7 —
   but the wiring itself is a later step.

2. **Soft-enforce leaves a standing window.** An unregistered account can still
   create bots with a free-typed `exchange`. Tightening to strict enforcement
   (reject creation for an unregistered account) is a one-line change once every
   real account is registered; it was deliberately not made now to keep this step
   from touching the existing bot-creation tests (decision 6). Worth revisiting
   once the account list is known to be complete.

3. **`credential_ref` is unbuilt, on purpose** (decision 2). The moment two
   accounts share an exchange with different keys, add the column and teach the
   resolvers to read it. Until then convention is honest and a column would be dead.

4. **`SYMBOL_CACHE` is unprovisioned, so caching is inert in the deployed
   environments** until `docs/kv-provisioning.md` step 4 is run — the endpoint
   degrades to a live call meanwhile. And the live call itself is subject to the
   geo-block standing risk (step 3.3 open question 1, 3.4 open question 3): a
   Binance `exchangeInfo` from a Cloudflare edge may be refused by request-origin
   IP, which would surface here as a 502 on the symbols endpoint. Gemini's sandbox
   reachability from the edge is still unverified. The read-only symbols endpoint is
   a cheap first place to observe both.

5. **A label that carried two different exchanges across bots backfills to one,
   arbitrarily.** `INSERT OR IGNORE ... GROUP BY account_label` keeps the first and
   completes rather than failing the migration. This is pathological (the free-typed
   column allowed it, but nothing should have written it), and a mis-registered
   account is correctable by hand — but if it ever happens, the backfill will not
   flag it.

## Step 11.1: Wiring the create-bot form to the account registry
Date: 2026-07-28

### What was built

Step 11 built the backend the create-bot form should have been reading all along;
step 10.11 built that form while it still had to free-type Account, Exchange and
Pair (10-frontend.md's own note: "there is no accounts endpoint to depend on, and
none is invented here"). This step connects the two: the three fields that a
person could previously get *silently wrong* now come from real data.

- **`dashboard/src/api/types.ts`** — added `Account` (`GET /api/accounts`) and
  `AccountSymbols` (`GET /api/accounts/:label/symbols`) read models, and REMOVED
  `exchange` from `CreateBotBase` (the create request no longer carries it). The
  removal is the type-level statement of decision 2 below.
- **`dashboard/src/api/client.ts`** — `fetchAccounts()` and
  `fetchAccountSymbols(label)`, each documenting the failure codes the form
  branches on (`exchange_unavailable` 502, `unknown_account` 404).
- **`dashboard/src/pages/CreateBot.tsx`** — the rewire:
  - **Account** is a `<select>` populated from `GET /api/accounts`; selecting one
    stores its label AND its exchange from the same response (`onSelectAccount`).
  - **Exchange** is a read-only `ExchangeDisplay`, never an input, never sent.
  - **Pair** is a new inline `PairCombobox` — a searchable typeahead over the
    account's live symbols, keyed on the account so it fully resets per change,
    disabled until an account is chosen, and refetched on every account change.
  - Two sequential loading states (`accountsLoading`, then `pairsLoading`) each
    render a `LoadingRow`; the symbols failure renders `describeSymbolsError`'s
    distinct copy with a Retry.
  - The pre-existing `submitting` double-click guard is unchanged.

Strategy fields and risk controls were not touched. The dashboard builds clean
(`tsc -b && vite build`), the root typecheck is clean, and the deploy guard's 9
tests pass.

### Decisions made

**1. Pair is a constrained typeahead, not a `<select>` and not a `<datalist>`.**
*(the UI-pattern question the brief asked me to decide and explain)*

Gemini alone returns 300+ symbols and Binance returns thousands. A native
`<select>` that long is unscannable and sluggish; a `<datalist>` filters nicely
but still lets a person *commit free-typed junk* — the exact mistake this whole
step exists to remove. The combobox is the only option that filters fast AND
guarantees the committed value is a real symbol: `pair` is only ever set to a
member of the fetched `pairs` (via click, keyboard-Enter, or an exact-match blur),
and `validate()` re-checks membership as a backstop. Prefix matches sort ahead of
other substrings; the render is capped at 100 rows with a "N more — keep typing"
hint so a thousands-long set never floods the DOM. Built inline, no new dependency.

**2. `exchange` is omitted from the create request entirely, not sent-to-match.**
*(the brief offered both; chose the stronger one)*

The brief allowed either "don't send exchange" or "send only the value matching
the account." Omitting is strictly safer: `resolveBotExchange` (handlers.ts)
derives the exchange from the registry and rejects a disagreeing body value, so
the ONLY value that can ever reach a bot's row is the account's own. There is no
second value to keep in sync and nothing a UI bug could desynchronise. The
read-only `ExchangeDisplay` is pure confirmation for the human; the wire carries
only `accountLabel`, and the backend turns that into the venue. This is the same
"a wrong-venue bot is structurally impossible" property step 11 decision 6 built,
now honoured from the client side too.

**3. `exchange_unavailable` gets its own honest copy; the account list is the
reason `unknown_account`/`unregistered_account` are only defensive.** *(brief item 4)*

The geo-block is real and was seen live, so its message says plainly that the
exchange couldn't be reached *on our end* and to try another account — not a
generic failure that reads as the user's mistake. `unknown_account` (symbols) and
`unregistered_account` (create) are handled but framed as "reload to refresh the
list," because the dropdown only ever offers registered accounts: the only way to
hit them is an account de-registered mid-session, a genuine rarity now that the
registry, not free text, is the source.

**4. The account/pair suggestion `datalist`s are gone; the capital-asset one
stays.** *(scope)*

Those best-effort lists scraped from existing bots (step 10.11) were a stand-in
for the endpoints that did not exist yet. Account and pair now have authoritative
sources, so their `datalist`s are removed. Capital asset still has none — it is a
free-text field this step was told not to touch — so its suggestion list (and the
`fetchBots` call that feeds it) is kept, narrowed in comment to that single job.

### Deviations from the spec / prior entries

- **10-frontend.md's create-bot entry (10.11) is partly superseded.** Its
  "shared fields are free text with best-effort suggestions" description no longer
  holds for Account/Exchange/Pair. The entry is append-only and left as written;
  this section is the update. The capital-asset and strategy/risk fields it
  describes are unchanged.

### Open questions carried forward

Step 11's open questions 1–5 are unchanged (this is a client, and changed no
backend behaviour). Specifically relevant to trying a real bot now:

1. **Creating a Gemini bot should work end to end; it will not TRADE yet.**
   `POST /api/bots` saves config and reserves capital but places no orders
   (creation never touches the exchange), so a `gemini-main` bot can be *created*
   once (a) its symbols endpoint is reachable from the edge to populate the pair
   list — step 11 open Q4's still-unverified Gemini-from-edge reachability, which
   this form is now the live probe for — and (b) a capital-ledger row exists for
   the chosen capital asset. Note the asset: Gemini pairs quote in USD, while the
   form defaults capital asset to `USDT`; a Gemini bot needs the capital asset set
   to match an existing ledger row or it is a `no_ledger_row`. The bot then sits
   `created` until execution wiring exists (step 11 open Q1) — that is what is
   still missing before it actually trades.

2. **The Binance account will likely surface `exchange_unavailable`** on pair load
   from a Cloudflare edge (step 11 open Q4's geo-block). That is the honest error
   path, not a regression: the form says so and points to a different account.

3. **`SYMBOL_CACHE` is still unprovisioned in deployed environments** (step 11
   open Q4), so every pair-list open is an uncached live call. Functionally fine;
   provisioning it (docs/kv-provisioning.md step 4) is what makes the dropdown cheap.
