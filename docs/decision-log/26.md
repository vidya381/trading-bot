## Step 26: The archive action, and what it deliberately is not
Date: 2026-08-06

### What was built

A finished bot — a completed experiment, a superseded parameter set, a testnet
run whose conclusions are already recorded — had nowhere to go. It stayed on the
bot list forever, and the bot list is the page an operator reads to see what is
happening *now*. Ten dead rows above two live ones is not a cosmetic problem; it
is the main risk surface of this dashboard getting harder to read every week.

- **`migrations/0007_bot_instances_archived.sql`** — one additive
  `ALTER TABLE bot_instances ADD COLUMN archived INTEGER NOT NULL DEFAULT 0`.
- **`POST /api/bots/:id/archive`** and **`/unarchive`** — thin, idempotent, both
  writing an `audit_log` entry with the verified human actor.
- **`archived` on every bot summary**, and a `bot_archived` (409) refusal added
  to `start` and `resume`.
- **`ArchiveAction.tsx`**, an `archived` tag in `BotList`, and a **"Show
  archived"** toggle on the dashboard.
- **13 tests** in `src/api/api.test.ts`, mutation-verified. **1594 pass**, 1581
  before.

**This is explicitly not a delete, and no data is removed from D1 or the Durable
Object at any point.** The rest of this entry is mostly about why that is a
structural fact rather than an intention.

### Where the flag lives

`bot_instances.archived`, in D1. **Last** in the column list, because
`ALTER TABLE ADD COLUMN` appends and `schema.test.ts` compares column *order*
against the live database — the same reason `capital_asset` (0002) and
`alerts.notified_at` (0004) sit where they do.

**Not in the Durable Object**, and that was the one real placement decision.
Section 8.1 makes each object the source of truth for its own *trading* state:
configuration, status, position, ladder or DCA entries, order history,
idempotency records. Archived is none of those. No strategy branches on it, no
order is placed or withheld because of it, and the object would never read it
back. Putting it there would have meant a stored-state shape change and
therefore a `schemaVersion` migration on every existing bot (section 16), plus a
new mirror path, for a flag whose only consumer is a list view already built
from the D1 row. That row is already authoritative for `status`,
`strategy_type` and `allocated_capital` — facts the dashboard reads without
waking an object. This is that kind of fact.

**No index**, deliberately. Nothing queries on the column (see decision 5), and
an index on a column no `WHERE` clause mentions is dead weight that reads as
intent.

### Why there is no data-loss path

Five reasons, none of which is "the handler doesn't do that":

1. **The storage layer has no `delete` method at all.** `/src/db/table.ts` says
   so in its header and means it: `insert`, `update`, `findMany`, `findOne`,
   `count`, `sumMoney`, and nothing else, precisely so section 8.7's indefinite
   retention cannot be violated by accident. The archive handler cannot delete a
   row because there is no call to make.
2. **Routing around that layer is a build failure.** `no-raw-d1.test.ts` fails
   if any file outside `/src/db` matches `.prepare(`, `D1Database`, `env.DB` or
   `.batch([`. So no handler can issue a raw `DELETE` either.
3. **The migration is purely additive.** One `ADD COLUMN`; no `DROP`, no table
   rebuild, no rewrite. Every pre-existing row reads `0`.
4. **The write is column-disjoint from every other writer, both ways.** Archive
   patches exactly `{ archived, updated_at }`. The DO's `#mirrorStatus` patches
   only `status`/`halt_reason`/`halted_at`/`updated_at`; the capital ledger
   patches only `status`/`allocated_capital`/`updated_at`. Nothing touches
   `archived` but these two endpoints, and they touch nothing else — so neither
   can clobber the other.
5. **The Durable Object is never asked to mutate.** The handler calls only the
   read-only `snapshotIfCreated()`, for the response. `orders`, `trades`,
   `alerts`, `audit_log` and `capital_ledger` are untouched, and
   `GET /api/bots/:id` queries them by `bot_instance_id` with no archived
   condition, so the detail page renders identically before and after.

Capital is not released either: releasing is `releaseBotCapital`, keyed on the
`stopped` transition, and archiving never writes `status`.

The test that holds this still is **"removes nothing: the whole detail payload
survives an archive intact"** — a deep comparison of the entire
`GET /api/bots/:id` body across an archive, with exactly two fields permitted to
differ (`archived` and `updatedAt`). A list of field assertions can only check
the fields whoever wrote it thought of; a deep compare fails on the one nobody
predicted. Its three history assertions *before* the archive are load-bearing:
without them the test would pass just as happily against a bot with no history,
comparing empty arrays and proving nothing — the vacuous-assertion failure this
suite has hit more than once (10.14, 23).

### The three scope questions, settled by the operator before any code

Recorded because each had a defensible other answer:

1. **`created` is not archivable.** Only `halted` and `stopped`. A bot that has
   never started is not finished with, it is not started — and the same
   deliberate exclusion step 23 made when `HaltAction` refused a `created` bot
   the backend would have accepted. Pinned by a test so it stays legible as a
   choice.
2. **`start` and `resume` refuse an archived bot** with `bot_archived` (409),
   rather than auto-unarchiving or allowing it. This preserves the invariant
   that **nothing hidden from the default view is capable of trading**. The
   alternative — silently unarchiving as a side effect of resuming — was
   rejected as magic on a capital-committing action.
3. **Archived bots still count toward the account-level totals.** An archived
   bot is halted or stopped, not closed: it still holds its capital allocation
   and may still hold inventory. This is what made the filter client-side (see
   decision 5).

### Decisions

**1. The gate reads the D1 row, not the object's snapshot.** Every other action
here delegates its status rule to the Durable Object, so this is a deviation
worth naming. Two reasons: archived is a property of the row, and an **orphaned**
bot — a row whose object holds no state, which `botSummary` already surfaces as
`orphaned: true` — must still be archivable, which a snapshot-authoritative gate
cannot answer because there is no snapshot to ask. Archiving also never needs to
wake an object.

**2. The conditional `UPDATE` is the only decision, and the callers do not
duplicate it.** The `WHERE` carries the current value of `archived` (and, when
archiving, that the status is still archivable), so inspecting `changes` answers
"did this change anything" against the database rather than against a row read a
moment earlier. Same `update(...) → inspect changes` idiom the capital ledger
uses for its `status <> 'stopped'` claims. **This shape came out of a surviving
mutant** — see the mutation notes below; the first version had an
`if (row.archived) return` branch in the caller that made the guard unreachable
and therefore untested.

**3. The status refusal is the one thing the caller decides**, because a `WHERE`
that matches nothing cannot say *why*, and "halt it first" is the whole point of
the message. It is skipped for an already-archived bot, so idempotence does not
depend on the status: an already-hidden bot is reported as such whatever it is
doing, rather than being refused for a state it is already in.

**4. Unarchive has no status gate of any kind** — not even the one archiving
uses. It is the reversing half, and a gate there could only ever strand a bot in
the hidden state, which is the one outcome this feature must never produce. It
is also the risk-*reducing* direction (it makes a bot more visible), and this
codebase already keeps such actions unconditionally available — `halt` asserts
neither risk latch for the same reason.

**5. The filter is client-side, and `GET /api/bots` has no archived parameter.**
Following from scope question 3: the dashboard needs every bot in hand for the
account totals regardless of the toggle, so it would never send anything but
"all". A server parameter the only caller never uses is the kind of unexercised
branch this codebase refuses elsewhere. The endpoint's existing behaviour is
therefore byte-identical, and hiding is a view decision made in one place.

**6. Archiving gets a confirmation dialog; unarchiving does not.** Not risk —
neither direction commits capital, which is what the halt/start/resume dialogs
exist for. **Surprise**: archiving makes a bot vanish from the page the operator
was just looking at, and the dialog is where "nothing is deleted", "it is behind
Show archived", and "an archived bot cannot be started or resumed" get said.
Unarchiving surprises nobody, so it is one click.

**7. `halt`, `liquidate`, `apply-missed-fills` and `check-open-orders` are NOT
blocked on an archived bot.** Only the two actions that make a bot trade again
are. Halting is risk-reducing; the other three operate on the books of a bot
that is already halted and start nothing. Blocking them would mean an operator
had to unarchive a bot to close it out properly, which serves no one.

### Tests and mutation results

13 tests. **12 mutants, 11 caught, and the two that survived the first pass were
both right to.**

- **The idempotence guard was unreachable.** Deleting `if (changed !== 1) return
  false` changed nothing, because the caller's own `if (row.archived)` branch
  returned before `setArchived` was ever called — so the guard existed only for
  a race, and the "archiving twice writes one audit entry" test was passing
  through a *different* code path than the one it was written to protect.
  Removing the redundant caller branch (decision 2) made the guard the live path
  and the mutant fails 2 tests.
- **"Unarchive has no status gate" was not observable.** Adding archive's gate
  to unarchive passed every test, because every bot reachable through the
  archive endpoint is `halted` or `stopped` — a copied gate would let all of
  them through unnoticed. The case needs a bot archived in a status archiving
  itself refuses, which is reachable only by writing the flag directly; that
  test now exists, and it is the only one that can see this property at all.

**One mutant still survives, deliberately.** Dropping
`status: { in: ARCHIVABLE_STATUSES }` from the archive `WHERE` breaks nothing in
the suite, because it defends only a race: a row read as halted whose status is
flipped by a concurrent `resume` before the `UPDATE` lands. Driving that needs
genuine in-flight concurrency through the stub harness (step 21's
`concurrency-model.test.ts` apparatus), which is heavy machinery for a flag whose
worst-case failure is cosmetic. It is recorded here rather than claimed as
covered.

`start`'s gate is **unreachable through the archive endpoint today** — a
`created` bot cannot be archived and `start` accepts nothing else — so its test
writes the flag directly. It is not dead code: it becomes reachable the moment
`created` joins `ARCHIVABLE_STATUSES`, which decision 1's own comment names as a
one-line change, and testing it now is what stops that change from silently
opening the "running and hidden" hole the resume gate exists to close.

### Deliberately not done, and open questions

- **The frontend has no test runner**, unchanged since step 25: `vitest.config.ts`
  runs only the Worker suite. `ArchiveAction`, the `archived` tag, the toggle and
  the filter were verified by a TypeScript build and a production `vite build`
  only. The filter and count are three lines inline in `Dashboard.tsx` rather
  than a pure module like `accountTotals.ts`, so unlike step 25's fold they could
  not have been scenario-checked off-tree without extracting them first.
- **An archived bot still costs what a live one costs.** `GET /api/bots` fans out
  one Durable Object read and two D1 reads *per bot* on a 5-second poll, and
  archiving does not reduce that — the fleet's polling cost now grows
  monotonically with every bot ever created. This is the strongest argument for
  a server-side filter, and it loses today to totals correctness (decision 5). At
  v1's ten bots it is not yet a real number; the honest fix when it becomes one
  is to make the totals a server-computed figure rather than a client fold, at
  which point the list can filter without under-reporting anything.
- **The toggle does not persist.** Component state, reset by a reload or a
  navigation away and back. A URL parameter would be shareable and survive both;
  not built, because nothing yet asks for it.
- **One residual race is open by design.** An archive that commits in the window
  between `resume`'s archived check and the object's status flip yields a running
  bot hidden from the default view. It needs two operators acting on one bot in
  the same instant, its worst outcome is cosmetic, and it is recoverable from the
  UI (the toggle reveals it, unarchive is one click). Documented in
  `assertNotArchived` rather than serialised behind a lock this flag does not
  otherwise need.
- **Nothing here has run against a live bot, and nothing is deployed.**
