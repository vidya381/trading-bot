## PART 2 — THE URGENT FINDING: A LIVE BOT ON A VENUE WITH NO CLIENT

**In the working tree as it stood after the one-line widening,
`POST /api/bots` with an unregistered account and `exchange: "kraken"` returned
`201` and created a real bot.** Not a 400 with a stale error code. A
`bot_instances` row on disk, capital reserved against it in the ledger, an audit
entry, and a live Durable Object — wired to a venue for which **no exchange
client exists anywhere in the running system**: no `case "kraken"` in
`resolveExchangeForAccount`, no `workers/exchange-kraken.ts` to resolve
credentials, and no `METHOD_WEIGHTS` row to gate its calls. All three remain
unbuilt, deliberately, each deferred to its own session by entry
[90.md](90.md)'s build order.

That bot's first trade would have halted it on:

```
unhandled_error: TypeError: Cannot read properties of undefined (reading 'ok')
```

— because the dispatch `switch` has no `default`, so it returns `undefined`, and
`#rawExchange` reads `.ok` off it. Capital reserved, an operator holding a crash
with no venue named in it, and nothing in the message pointing at the real cause.

**Why the type system could not see this.** `resolveBotExchange`'s
unregistered-account soft fallback validated the request body's `exchange` with
`isExchangeId` **alone**. That guard answers *"can this string be named as a
venue"*. It had also, accidentally, answered *"is there a client for this venue"*
— because until this session the two sets were identical. Widening `ExchangeId`
separated them, and the guard kept answering the first question while every
caller went on believing it answered the second. **A value being a valid
`ExchangeId` says nothing whatsoever about whether a real client exists for it**,
and no amount of type-checking can close that gap, because both sides of it are
the same type.

**Why `accounts.exchange`'s CHECK was no defence, and never was.** The D1
constraint `CHECK (exchange IN ('binance','gemini'))` (migration 0006) was still
in place, unwidened, and it did its job — a **registered** Kraken account cannot
exist. But an **unregistered** account is by definition absent from the accounts
table, so the constraint is never consulted on that path at all. The SQL still
looked closed while the door beside it stood open. `bot_instances.exchange`, for
its part, is plain `TEXT NOT NULL` with **no CHECK** (migration 0001), so the row
wrote cleanly.

**HOW IT WAS CAUGHT, AND THE PROCESS POINT THAT MATTERS.** It was found because
the compile-error investigation **ran the test suite as well as `tsc`**, and then
read what the failures actually said rather than filing them as "tests that need
updating". `api.test.ts`'s existing assertion — a test that had pinned
`exchange: "kraken"` → 400 `invalid_exchange` since step 11 — did not merely go
red. It **inverted**:

```
AssertionError: expected 201 to be 400
```

A test whose expectation flips from *refused* to *created* is not a stale
expectation; it is a report that behaviour changed in the dangerous direction.
The same run turned up its runtime twin in `exchange-attachment.test.ts`, where a
stored `"kraken"` row that used to halt with a named reason now halted on the
`TypeError` above.

**Had the investigation stopped at the five compile errors — which is the
natural place to stop, since the compiler is what a union widening is supposed to
break — this would have been committed.** The type system reported the widening
as a five-site mechanical change and was, on its own terms, correct. The class of
bug it cannot report is precisely this one: a widened value that every consumer
accepts and one runtime cannot serve.

## PART 3 — THE FIX: `EXCHANGE_IS_WIRED`

`src/workers/venue-wiring.ts`, following the shape `METHOD_WEIGHTS` and
`VENUE_PUBLISHES_INSTRUMENT_TYPE` already establish:

```ts
export const EXCHANGE_IS_WIRED: Readonly<Record<ExchangeId, boolean>> = {
  binance: true,
  gemini: true,
  kraken: false,
};
```

**Rejected: `exchange === "kraken"` at the call site.** A hardcoded venue name is
a statement about today that becomes silently wrong on the day Kraken is wired,
and wrong again on the day a fourth venue is added unwired. It also has to be
remembered in more than one place. No venue name appears at any call site in this
fix.

**Considered and rejected: deriving the answer by calling dispatch.**
`resolveExchangeForAccount(id, env, now) === undefined` is, strictly, the true
test of "has a `case`". It was rejected because it makes the guard *depend on*
the exact unsoundness being fixed — a function whose declared return type
excludes `undefined` returning `undefined` — and because it needs an `Env` at
every call site. TypeScript cannot be asked "does this `switch` have a `case`"
directly, so the answer is stated and then **verified**, in two halves:

**COMPILE-TIME — no venue can be OMITTED.** A total
`Readonly<Record<ExchangeId, boolean>>`: widening `ExchangeId` again fails to
compile here until someone states whether the new venue can be traded.

**RUNTIME — no venue can be MISLABELLED.** `venue-wiring.test.ts` calls the real
`resolveExchangeForAccount` for **every** `ExchangeId`, with every secret and
binding present (so the only variable is dispatch itself, not configuration), and
asserts it hands back a resolution **exactly** for the venues marked `true`. It
pins the unsoundness openly, including `dispatchFor("kraken")` being `undefined`.

**Neither half alone is sufficient, and the reason is not symmetric.**
Totality alone would happily accept `kraken: true` sitting above an empty
dispatch `switch` — a green build, a 201, and the `TypeError` of PART 2 back
again. The runtime cross-check alone would never **prompt** anyone about a
genuinely new venue: it can only test the venues someone thought to list.
Together, adding a `case` without flipping the row fails the test, flipping the
row without adding a `case` fails the test, and adding a fourth venue without
answering at all fails the build.

### The three enforcement points, all confirmed closed

**1. Bot creation — `assertExchangeIsWired` (`api/handlers.ts`).** 400
`exchange_not_wired`. It guards the value `resolveBotExchange` **returns**, not
the body field, so it covers the **registered-account branch as well as the
unregistered fallback**. That is deliberate and forward-looking: the fallback is
the only door open today, but the CHECK-widening migration is the whole point of
this build, and **on the day it lands the registry branch becomes a second door
to the same failure**. Guarding the return value means that migration cannot
reopen this. It runs *after* `assertBotInstanceIdFitsVenue` — that gate is about
the operator's input, which they can fix and resend, so it keeps the more
actionable message at the front; this one is a fact about the build that no edit
to the request can satisfy. Both are free, and both run before the pair, the
params, the proposal and any network call, so either refusal leaves **nothing
done**.

**2. The `invalid_exchange` message.** Now built from `wiredExchanges()`, not
`EXCHANGE_IDS`. It was about to tell an operator `exchange must be one of
binance, gemini, kraken` and then refuse `kraken` at the very next line. A
refusal that names a venue the next check rejects is worse than an unhelpful one,
because it sends the reader somewhere specific and wrong.

**3. `BotInstance#venue`, at first trade.** A stored `"kraken"` row passes
`isExchangeId` and used to reach the resolver. It is now refused **before** the
resolver is called, in the same `not_attached` shape as every other fail-closed
reason on that path, naming the venue, what is missing, and what to use instead.
This guard is not redundant with (1): a `bot_instances` row **predates any
handler gate** — it is read back from storage — and that column carries no D1
CHECK, so it can hold whatever a past write or a manual edit put there.

**One correction to an earlier reading made during this session**, recorded
because the distinction matters for anyone reading a halt: the `unhandled_error:`
**prefix is the halt category for any throw on that path**, including the
pre-existing "not a known exchange" case. What the bug destroyed was not the
category but the **diagnosis**. The assertion that carries weight is therefore
`/BotInstanceError/` and `not /TypeError/`, not the prefix.

Two adjacent stale-literal fixes went in with it: `bot-instance.ts`'s message had
`("binance" or "gemini")` **spelled out as a string**, which `tsc` cannot check
and which went wrong the instant the union widened — it is now built from
`EXCHANGE_IDS`. And `create-bot-venue-gate.test.ts`'s no-regression loop iterated
`EXCHANGE_IDS`, which after the widening generated a `kraken` case inside a block
titled *"the gate does not touch binance or gemini"*; it now iterates
`wiredExchanges()`. That file's canary block was **inverted rather than deleted**
— `isExchangeId("kraken")` is now asserted `true`, with `isWiredExchange("kraken")
=== false` as the replacement precondition — so the record of what happened
survives in the test that predicted it.

## PART 4 — DECISION: `DERIVATIVE_NAME_SUFFIXES` GETS `kraken: []`, AND WHY THAT IS AN ANSWER

The table was one of the five compile errors. The value is an empty array; the
decision is why, and it was settled by **reading the downstream path first**
rather than by pattern-matching Binance's row.

**What the table actually guards.** `derivativeNameSuffix` is reached only from
`checkTradable`, only **after** the venue's catalogue has confirmed the pair is
listed, and only under the `reject-derivative-names` policy (watchlist,
candidates, candles). The bot-creation gate passes `structural-check-elsewhere`
and never consults it. Its refusal code is `pair_not_spot_by_name` and the harm
it names is the one section 4.5 cannot model: **margin, funding, liquidation**.
It is a perpetuals heuristic, not a general non-spot filter.

**The structural half, same as Binance's row.** Kraken Spot
(`api.kraken.com/0/public/AssetPairs`) and Kraken Futures (`futures.kraken.com`)
are separate products on separate hosts; this system has a client for the first
and none for the second, so no perpetual can appear in the catalogue this
heuristic runs against. `kraken/filters.ts` reached the identical conclusion from
the other direction and omits `instrument` entirely rather than setting it to
`unknown` — which is also why `VENUE_PUBLISHES_INSTRUMENT_TYPE` gets
`kraken: false`.

**The staked/bonded question — asked, not skipped.** Entry [91.md](91.md) PART 4
found **44 suffixed asset codes** across all 839 assets: 27 `.S` (staked,
`DOT.S`), 7 `.HOLD`, 5 `.M` (bonded/earn, `XBT.M`), 2 `.P`, and one each of
`.INK`, `.CORE`, `.TEMPO`. They are real, they are genuinely not freely tradeable
the way spot is, and this codebase treats them as distinct assets on purpose. Do
they belong in this row? **No — for two independent reasons, either sufficient.**

**(a) THEY STRUCTURALLY CANNOT REACH THIS FUNCTION.** It matches on a **PAIR**
name. All 44 are **ASSET** names, and **no pair name Kraken publishes contains a
`.`** — checked across all 1440, and load-bearing enough that
`normalisePairName` strips punctuation on the strength of it while
`normaliseAssetName` deliberately keeps it (entry [91.md](91.md)). A suffix that
never occurs in this function's input cannot be matched by listing it here.

**(b) EVEN IF THEY COULD, THE RISK IS ALREADY GUARDED, CORRECTLY, ELSEWHERE.** A
staked or bonded balance involves no margin, funding or liquidation. Its real
hazard is a **wrong number** — an earn balance read as spot BTC, so the system
sizes an order against locked funds — and entry [91.md](91.md) PART 4 already
placed that guard where it belongs: `catalogue.ts` refuses to alias a suffixed
code onto its base, so `XBT.M` resolves to itself and never reads as `BTC`.
Routing that risk through a derivative-naming heuristic would **misplace**
protection rather than add it, and would weaken the guard actually doing the work
by implying it has a second line it does not have.

**THE GENERAL LESSON, and the reason this is written down rather than left as an
empty array.** A row reading `[".s", ".m"]` would have been **worse than `[]`** —
not merely useless. It would be **inert code that LOOKS like a real guard**:
never matching anything, never failing a test, and read by the next person as
evidence that the staked-asset case is handled here. An honestly empty array with
its reasoning attached is safer than a plausible-looking one, because the danger
is not the missing check, it is the future reader who stops looking. Following
the Binance row's precedent, the row also records what is **not** claimed — that
everything on Kraken's AssetPairs is something this system should trade
(liquidity and pair selection are entry [90.md](90.md) PART 5's pipeline concern)
— and names the tripwire: a Kraken pair name containing a `.` would falsify
reason (a) **and** `normalisePairName` at once, and would surface in the
catalogue, not here.

## PART 6 — STATUS AND BUILD ORDER

**Nothing was committed.** `HEAD` is `581d05b`. Ten source paths on disk plus
this entry and its README row.

**No migration was written, and `accounts.exchange`'s
`CHECK (exchange IN ('binance','gemini'))` remains unwidened.** Stated plainly:
**the registered-account creation path is still closed by SQL, not by this
session's code.** `assertExchangeIsWired` guards it too, and is the mechanism that
will be the **only** thing standing at that door the day the CHECK is widened.
That is why it guards `resolveBotExchange`'s return value rather than the request
body.

One correction to entry [90.md](90.md) PART 5 for whoever writes that migration:
it says the migration must widen the CHECK "and the partial index beside it".
**There is no index on `accounts.exchange`** — every migration was checked. The
only other `exchange IN ('binance','gemini')` is the one-time backfill `SELECT`
in migration 0006, inside an already-applied migration, which must **not** be
edited. So the migration is the CHECK alone — but SQLite cannot `ALTER` a CHECK,
so it is a table rebuild against a populated `accounts` table, which is the part
that needs the care entries [83.md](83.md)/[85.md](85.md) describe.

**Remaining work, in order — entry [90.md](90.md)'s original sequencing, now
reinforced by this session's finding:**

   (`KRAKEN_API_KEY` / `KRAKEN_API_SECRET`, fail-closed on a missing secret,
