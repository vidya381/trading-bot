## Step 47: One kill-switch poll instead of two — a duplicate subscription found in a HAR and confirmed from source, a reported "wrong account" bug whose premise did not exist, and a real safety-communication gap deliberately left for its own step

Date: 2026-08-13 · **live verified by the operator** with a fresh HAR capture
against the deployed testnet dashboard: **266 `GET /api/kill-switch` requests
over 1373.7 s real elapsed time = ~5.16 s per request**, confirmed by timestamp
arithmetic on the raw HAR rather than by trusting request counts.

**The coding session made no live call of any kind** — no `wrangler` command, no
HTTP request, no deploy, and it never saw the rendered page. Every number in the
"before" and "after" columns below is the operator's, from two real HAR captures.
What this session did was read source, trace git history, change four files, add
one guard test, and run the suite.

**Confined to `dashboard/src`. `src/` was not touched.**

### The arc

Entry 46 closed by naming this as still open: *"a real, still-open dashboard
polling investigation (kill-switch ~2.6s vs bots/alerts ~5.25s — HAR evidence
rules out progressive slowdown or a client leak; a plausible duplicate-poller
hypothesis recorded, unconfirmed, and explicitly not attributed to this
feature)."* This entry closes it: the hypothesis was right, the fix is in, and
the operator has measured the result.

Two things found along the way are worth more than the fix itself: **a reported
bug whose premise turned out not to exist**, and **a real one this step
deliberately did not fix**.

### 1. The original investigation

The operator captured 609 s from the deployed dashboard sitting on `/` with
**nothing clicked**:

| endpoint | requests | mean interval |
| --- | --- | --- |
| `GET /api/kill-switch` | **232** | **~2.625 s** |
| `GET /api/alerts` | 116 | ~5.25 s |
| `GET /api/bots` | 113 | ~5.39 s |

Server wait times were **not** climbing (first-20 avg 1881 ms, last-20 avg
1363 ms, one outlier ~4957 ms). That is what **ruled out** a progressive
server-side slowdown and an accumulating client-side timer leak — the two
explanations that would otherwise fit "one endpoint is faster than the others."
This was never a leak. It was a duplicate, present from the feature's first day.

`POLL_INTERVAL_MS` is 5000 and every call site uses the default. The decisive
arithmetic: **5.25 ÷ 2.625 = 2.000**, and 232 ≈ 113 + 116. Two independent 5 s
`setInterval` timers at arbitrary phase produce a mean inter-arrival of exactly
half. `usePolling` uses `setInterval`, not a chained timeout, which is also why
the cadence is flat and latency-independent rather than interval-plus-RTT.

### 2. What was duplicated — three call sites, but never three at once

| call site | mount scope |
| --- | --- |
| `components/KillSwitchBanner.tsx` | mounted in `App.tsx` **outside `<Routes>`** — never unmounts |
| `pages/Dashboard.tsx` | route `/` only |
| `pages/KillSwitchPage.tsx` | route `/kill-switch` only |

**Recorded plainly because it has been miscounted more than once, including in
the brief that commissioned this fix:** three *call sites* exist, but the maximum
ever mounted *simultaneously* is **two** — banner + Dashboard on `/`, banner +
KillSwitchPage on `/kill-switch`, banner alone on the other six routes. **No
route ever ran three.**

The HAR is the proof, in both directions. Two pollers predict ~2.5 s and ~232
requests in 609 s; that is what was measured. **Three would have predicted
~1.72 s and ~354 requests** — and after the fix, three-down-to-one would have
had to show a 3× change rather than the 2× that was actually observed. The
"~2.6 s from three overlapping pollers" framing is arithmetically impossible and
should not be inherited by a future reader.

All three read the **same singleton row** — `global_kill_switch`, migration 0005,
`id INTEGER NOT NULL PRIMARY KEY CHECK (id = 1)`, commented in the migration as
*"Global state is not per-anything."* Three subscriptions could only ever return
the same answer at three times the cost.

### 4. The "wrong account shown" bug: the premise did not exist

This step was commissioned to fix a second, stated-as-confirmed correctness bug:
that `KillSwitchBanner` polls with no `accountLabel` and therefore lands on a
default account (`"main"`/Binance) regardless of which account the operator is
viewing — a safety element silently showing the wrong account's state.

**Checked at five levels before writing any code. It is false at every one.**

| checked | finding |
| --- | --- |
| `migrations/0005_global_kill_switch.sql` | `id INTEGER NOT NULL PRIMARY KEY CHECK (id = 1)`. **No `account_label` column.** Comment: *"Global state is not per-anything."* |
| `src/reconciliation/kill-switch.ts` | `readGlobalKillSwitch(db)` → `findOne({ id: SINGLETON_ID })`. Header: *"it sweeps EVERY account, not one. There is no `account_label` anywhere in this file."* |
| `src/api/handlers.ts` `getKillSwitch` | Reads **no** search params. Two lines: read the row, serialise it. |
| `dashboard/src/api/client.ts` | `fetchKillSwitch(signal)` — no account parameter, because there is nothing to pass. |
| `dashboard/src/api/types.ts` | `KillSwitchStatus` has no account field. |

Then the router, traced exhaustively because the follow-up question was
specifically "which routes lack an `accountLabel`":

| route | dynamic segments |
| --- | --- |
| `/` · `/bots/new` · `/alerts` · `/kill-switch` · `/manual-adjustments` · `/proposal` · `/proposal/run` | **none** |
| `/bots/:id` | `:id` — a **bot instance id**, not an account |
| `*` | redirect to `/` |

**Zero of the nine routes carry an `accountLabel`.** The only `useParams` call in
the entire dashboard is `BotDetail.tsx:231`, extracting a bot id. Every one of
the ~50 `accountLabel` usages is either a **form field** bound to `useState("")`
(`CreateBot`, `ManualAdjustment`, `ProposalRun`) or a **field on a fetched object
being displayed** (`BotList`, `BotSummary`, `ProposalView`). `"main"` appears in
this repository only in `src/db/test-helpers.ts` fixtures and README examples;
**there is no default-account fallback in any production code path.**

The question "what does the banner show on a route with no `accountLabel`" has no
answer because it has no subject: **no account is an input to this poll, so none
can be missing.** `KillSwitchStatusProvider` imports nothing from
`react-router-dom`.

**The banner was showing the correct — and only — kill-switch state all along.**
Scoping it to an account would have been a genuine regression: section 7.4's
control halts *every bot on every account*, and a banner narrowed to one account
would **understate the blast radius** of the most severe state in the system. **No
account-scoping change was made, and none should be.**

**Recorded this plainly so a future reader does not inherit the wrong framing.**
The corrected premise is: *the global kill switch has no per-account dimension
anywhere in this system, by design, at every layer from the migration to the
banner.*

**What is genuinely per-account, and genuinely missing:** the **circuit breaker**
(`circuit_breakers`, `GET /api/circuit-breakers`,
`POST /api/circuit-breakers/:accountLabel/reset`) — the global switch's
account-scoped sibling, described as such in `kill-switch.ts`'s own header. It
has **no dashboard surface whatsoever**; `grep circuit-breakers dashboard/src`
returns nothing. If per-account safety state ever looks wrong, that is the real
gap. **Additive work, deferred, not silently dropped.**

### 5. The fix

**1 new source file, 1 new test file, 4 modified.**

| file | what |
| --- | --- |
| `api/killSwitchStatus.tsx` | **new.** `KillSwitchStatusProvider` + `useKillSwitchStatus()`. The one subscription. |
| `api/single-kill-switch-poll.test.ts` | **new.** Source-level guard, +6 tests. |
| `App.tsx` | Provider wraps the banner *and* the routed area. |
| `components/KillSwitchBanner.tsx` | Reads the shared hook. |
| `pages/Dashboard.tsx` | Reads the shared hook; its own poll deleted. |
| `pages/KillSwitchPage.tsx` | Reads the shared hook; its own poll deleted. |

**The banner did not move, and there is no `AppShell` in this codebase** (`grep
AppShell dashboard/src` returns nothing). It stays exactly where `db52912` put
it — in `App.tsx`, outside `<Routes>` — for the reason it was put there: a
tripped switch must be visible on every route, and navigation must not unmount
it. What changed is that a `KillSwitchStatusProvider` now wraps both it and the
routed area, so the banner reads a shared subscription instead of owning one.

**Why a context and not a store.** This codebase holds all client state in React
hooks and passes it down as props — no store library, no global mutable singleton
anywhere in `dashboard/src`. A context ties the poll's lifetime to the component
tree exactly as `usePolling` already assumes (it aborts in-flight requests on
unmount), so nothing has to reason about a subscription outliving the app.

**Why the whole `PollState`, not just the data.** This is where a consolidation
quietly loses a consumer. `KillSwitchPage` needs `lastUpdated` and `error` for
its freshness indicator, `loading` for first-load, and `refetch` to hand to
`KillSwitchTrigger` and `KillSwitchReset`. Exposing only `data` would have
dropped three consumers silently.

**A staleness bug fixed as a side effect.** `KillSwitchPage.tsx`'s header has
claimed since 2026-07-24 that after a trigger or reset, `poll.refetch` makes
*"the card, the strip and the banner all reflect the real state at once."* **That
sentence was false when written** — `refetch` calls a per-instance `tickRef`, so
it refreshed the page's own poller only, leaving the banner showing a stale armed
state for **up to a full 5 s after a real pull**, on the one screen where the
operator is watching for exactly that transition. One shared subscription makes
the existing sentence describe the actual behaviour. **The duplicate was not only
a cost bug; it was a staleness bug in the most severe state this system has.**

### 6. Verification

**The dashboard has no component-test infrastructure.** `dashboard/package.json`
has no vitest, no jsdom, no testing-library; its scripts are `dev`, `build`,
`preview`, `typecheck`. **Stated plainly rather than worked around: no test in
this repository can observe two live timers, and none was fabricated to pretend
otherwise.**

What was done instead is the pattern this repository already uses for exactly
this class of invisible defect — `src/db/no-raw-d1.test.ts`, which enforces "no
raw D1 outside `/src/db`" by scanning source via `import.meta.glob(..., '?raw')`.
`api/single-kill-switch-poll.test.ts` enforces the same way, with six assertions:
the glob is non-empty (no vacuous pass), only the provider calls `usePolling`
with `fetchKillSwitch`, the provider does so exactly once, no component imports
`fetchKillSwitch`, **all three original consumers still read the shared hook**,
and the provider is mounted in `App.tsx`.

**The guard was proven to fail.** The duplicate poller was temporarily
reintroduced into `KillSwitchBanner.tsx` and the suite re-run: **3 of 6
assertions failed** with the intended messages, then the file was restored and
all 6 passed. A guard never seen to fail is not evidence.

| | before | after |
| --- | --- | --- |
| tests passed | **2632** | **2638** (+6, all from the new guard) |
| test files | 93 passed (94) | 94 passed (95) |
| errors | 1 | 1 |

The single error is `EnvironmentTeardownError: Closing rpc while "resolve" was
pending` — miniflare shutdown noise, **present identically in the before run**,
not a test failure and not introduced here. `npm run build:dashboard:testnet`
(which runs `tsc -b` first) succeeds: 106 modules, 481.05 kB.

**What the guard proves and what it does not:** it proves there is exactly one
subscription in source, therefore one timer to fire. **It does not prove one HTTP
request leaves the browser per interval.** Only a real capture does — and that is
the next section, which is not this session's work.

### 7. Live verification — the operator's, not this session's

Fresh HAR capture against the deployed testnet dashboard, confirmed by
**timestamp arithmetic on the raw HAR file, not request counts alone**:

| | before | after |
| --- | --- | --- |
| kill-switch requests | 232 | **266** |
| real elapsed | 609 s | **1373.7 s** |
| **mean interval** | **~2.625 s** | **~5.164 s** |

**Ratio after ÷ before = 1.967 ≈ 2.** Exactly one poller where two were running —
the halving the two-poller diagnosis predicted, and *not* the 3× that a
three-poller diagnosis would have required. The measurement confirms the fix and
the count simultaneously.

The residual **+3.29 %** over the nominal 5000 ms is ordinary `setInterval` drift
under a busy main thread, and is **tighter than the same session's other pollers
measured pre-fix** (alerts +5.00 %, bots +7.80 %) — consistent with one timer
rather than two contending.

### 8. Found, real, and deliberately NOT fixed here

`KillSwitchBanner.tsx:35`, blamed to **`db52912`, 2026-07-24** — the same commit
as the duplicate pollers:

```tsx
if (status === null || status.state !== "tripped") return null;
```

The banner renders nothing in three situations: **armed** (correct), **before the
first poll resolves** (avoids a red flash on load), and — the real one — **when
the poll has errored and has never once succeeded.** `usePolling`'s catch keeps
`data: prev.data`, which is still `null`, so `status` stays `null` and the banner
stays silent.

**The gap, stated exactly:** if `/api/kill-switch` fails from the very first
request — expired Access session, `no_schema` 503, a D1 error — **while the
switch is actually tripped**, the banner shows nothing and says nothing. Once a
poll has succeeded even once, last-good data keeps the bar up through later
failures; that half is deliberate and commented. The blind spot is only
"never succeeded at all."

**This step neither introduces nor worsens it** — same `usePolling`, same
last-good semantics, same null-until-first-success. The consolidation does make
one thing strictly better: before, the banner and the `/kill-switch` page had
independent failure fates, so the page could load and show TRIPPED while the
banner's separate poll failed and stayed blank — an inconsistent UI on the exact
screen where it matters. One subscription means they now always agree.

**Why it is scoped out rather than folded in.** The current code conflates *"the
switch is armed"* with *"I do not know what the switch is"*, and those are not
the same fact — an unknown safety state arguably deserves its own visible,
distinct bar. But that is a **visible change to the most severe communication
element in the system**, with real design questions attached (what does it say,
how loud is it, does it appear during ordinary first-load latency, does it risk
crying wolf often enough to train the operator to ignore the red bar that
matters). **That deserves its own design pass and its own entry, not a silent
rider on a consolidation commit.** Named here so it is not lost.

### Also not done, deliberately

- **No interval changed.** `POLL_INTERVAL_MS` is still 5000. The investigation
  recommended reviewing 5 s for all three endpoints; that is the operator's
  decision and is not smuggled in under a bug fix.
- **No `/api/bots` N+1 fix.** At 12 bots it costs ~38 round trips per poll
  (1 schema guard + 1 list + 12 × [1 DO RPC + 2 D1 queries]). The real cost
  centre, untouched.
- **No fix for the ~1.4 s baseline latency**, including the uncached
  `db.tableExists("bot_instances")` every `/api/*` request pays before routing.
  Whether that time is inside the Worker or outside it is answerable from
  Workers Logs, already enabled, using `GET /api/kill-switch` as the probe
  precisely because it does almost no work.
- **No circuit-breaker dashboard surface** (section 4 above).
