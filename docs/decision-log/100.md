## PART 1 — WHAT WAS FOUND

**`bot-xs0ufw`'s `audit_log` carries a `bot.cycle_completed` row at
2026-09-04T16:16:38Z. Its `bot_instances` row was last written at
`1787650864861` — 2026-08-25T09:41:04Z, the stop-loss halt, ten days earlier.**
`status`, `halt_reason`, `halted_at` and `updated_at` were untouched by the
cycle completion. Nothing in the bot's own row records that it happened.

### The sequence, and every step of it is correct until the last

1. A DCA bot held a position and rested a take-profit sell.
2. It halted for an **unrelated, earlier, safety-relevant reason** — a
   stop-loss. Its cancel sweep could not confirm the cancellations, so per
   §5.6 it kept the ids and alerted `cancel_failed`. **The sell stayed live on
   the exchange.** This is entry [82.md](82.md)'s incident, and PART 8 below
   is about that link.
3. Ten days later that sell filled. The 30-second poll read it and folded it
   through `#applyFillToOrder` — **correctly**. That path has no status gate,
   deliberately: the books of a halted bot must still be right, and
   `applyExit` booked the profit per fill as it landed.
4. It was a fully-filled exit carrying `exitKind: "take_profit"`, so it reached
   DCA's `#completeCycle`, **on a bot that had been halted for ten days.**

### What `#completeCycle` then did

It ran in full. It has no status precondition anywhere. The state write, the
`bot.cycle_completed` audit row, the `take_profit` receipt alert — all correct,
all real, all still correct today. **The accounting half of this method was
never wrong and is unchanged by this entry.**

Then it reached its fork, and both branches assume a running bot:

- **`autoRestart: true`** returned
  `{ status: "running", action: "cycle_completed", detail: "auto-restarting" }`.
  Entry [83.md](83.md) established that this branch **performs no action at
  all** — the restart is EMERGENT, working only because the cleanup has already
  left the bot flat *and running*. On a halted bot that premise is false: the
  bot is halted, `#halt` unsubscribed it from its price feed, and
  `#onPricePass` returns `ignored` before reaching any order-placing site.
  **Nothing restarted. The return value was the entire "restart".**
- **`autoRestart: false`** called `#halt(config, "take_profit_reached", …)`,
  which sees `state.status === "halted"` and returns `already_halted` having
  **written nothing** — no status, no reason, and critically no `#mirrorStatus`,
  which is the only writer of `bot_instances.status` / `halt_reason` /
  `updated_at` outside `start`, `resume` and `releaseBotCapital`.

**⚠ WHICH BRANCH `bot-xs0ufw` TOOK IS NOT ESTABLISHED, and this entry will not
guess.** Both leave `bot_instances` untouched, so the D1 evidence cannot
distinguish them; the answer is in that bot's `params.autoRestart`, which was
not read in these sessions. It does not change the fix — both branches were
wrong and both are now unreachable on a non-running bot — but recording a
finding as settled when it was not is how a log stops being trustworthy.

### ⚠ THIS IS NOT ENTRY 82's BUG

They produce a similar-looking symptom — a transition that leaves some state
written and some not — and they are **different failures with different fixes**,
which is worth stating precisely because "82 again" was the first hypothesis:

| | Entry 82 | This entry |
| --- | --- | --- |
| What went wrong | A **throw**, partway down a chain of bare `await`s, aborted every remaining step | **Nothing threw.** Every step ran and succeeded |
| The defective thing | Failure *handling* — five independent steps sequenced so the first failure decided how much of the halt happened | A missing **precondition** — lifecycle semantics applied without checking the state they assume |
| The fix | `#cleanupStep`: make each step independently best-effort | A status check before the transition, and an honest result when it cannot run |
| Would 82's fix have caught this? | — | **No.** There is nothing here for `#cleanupStep` to wrap |

82 was a correct transition that could not finish. This was a transition that
should never have been attempted, reporting that it had.

## PART 2 — THE FIX

`#completeCycle` now reads the bot's **real post-mutation status** — off the
return of its own `#mutateState`, which is a delta and therefore leaves `status`
untouched and authoritative — and refuses the transition when it is not
`running`:

```ts
if (completed.status !== "running") {
  return await this.#recordPostHaltCycleCompletion(config, completed, exit, gross, auditId, at);
}
```

**Everything above that line is unmoved.** The position clearing, the
`unmodelledBase` accumulation, the audit row, the take-profit receipt, the
stranded-base warning — all of it runs on any status, because none of it is
conditional on the bot being alive. The check sits at the fork and nowhere
earlier, deliberately: putting a status gate at the top of the method would have
stopped recording a real fill, which is the opposite mistake.

### The new path answers in its own words

`#recordPostHaltCycleCompletion` returns:

```ts
{ status: <the real status>, action: "cycle_completed_while_not_running", detail: … }
```

**A DISTINCT `action` STRING, NOT `cycle_completed`.** This is the part that
matters for callers. `status` alone is not enough — a caller reading
`{ status: "halted", action: "cycle_completed" }` has to *infer* that something
unusual happened, and inference is what fails silently. A string no existing
caller knows fails loudly instead, or at minimum reads as unfamiliar rather than
as routine. `detail` names the transition that was refused, in words, so the
refusal is legible without reading this file.

### ⚠ THE BONUS FINDING: A LATENT THROW, REMOVED

The old `autoRestart: false` branch called `#halt` unconditionally. `#halt`'s
second guard is:

```ts
if (state.status === "stopped") {
  throw new BotInstanceError("invalid_status", "a stopped bot cannot be halted; its capital is released");
}
```

So a cycle completing on a **stopped** bot would have thrown `invalid_status`
out of a completion path, where `#onFillPass` would have caught it into
`#haltOnUnexpected` — an "unhandled error" halt raised by a bot that is already
stopped and whose capital is released.

**It was unreachable, and it is worth being precise about why:** `#closePass`
empties `openOrderIds`, `checkOpenOrders` refuses a stopped bot outright, and
the poll reads only `openOrderIds` — so no fill can reach a stopped bot through
any path that exists today. This was found by reading the branch, not by a
failing test, and it is fixed as a **consequence** of the precondition rather
than as a target: `!== "running"` covers `stopped` for the same reason it covers
`halted`, and naming the real status in the result means the stopped case
reports itself correctly instead of throwing.

## PART 3 — THE NEW FIELD, DESIGNED NOT TO FIGHT THE SAFETY MACHINERY

Refusing the transition silently would have been a worse bug than the one being
fixed: the event would still be invisible, and now deliberately so. So the
refusal is recorded — **beside** the halt reason, never instead of it.

### `PostHaltEvent` / `postHaltEvents`

Additive and optional (`readonly postHaltEvents?: readonly PostHaltEvent[]`),
following `highWaterMark`, `unmodelledBase`, `exitKind` and
`pendingReplacements` exactly. `#state()` **casts** stored JSON rather than
parsing it, so a non-optional declaration would be a type lie for every bot
already on disk and would need a `schemaVersion` bump and a migration to become
true. **Absent and empty mean the same thing and no reader may distinguish
them.** Bounded by `POST_HALT_EVENT_LIMIT`; the real bound is 1 per halt episode
(a halted bot places no orders, `exitOrderId` is a single field
`#placeTakeProfitSell` refuses to overwrite, and completing the cycle clears
it), and the cap is defence in depth against a future `kind` loosening that
argument.

### ⚠ `halt_reason` IS NEVER OVERWRITTEN, AND `#mirrorStatus` IS NEVER CALLED

This is the design, not an omission:

- **The first halt reason stays primary.** A stop-loss says the position moved
  against the bot. A later `take_profit_reached` arriving from a resting order
  describes a smaller, incidental fact. Letting the second win — by overwrite
  *or* by string concatenation — would replace the safety-relevant reason with
  an incidental one purely because it arrived second, on the exact field a human
  reads first.
- **There is no transition to mirror.** `#mirrorStatus` writes a status change;
  no status changed. Entry 82 already declined to widen `#halt` into that
  convergence, reserving it for the detector in
  `docs/open-items/resume-split-brain.md` part 3b, and this path has even less
  claim to it.

So `bot_instances.updated_at` still does not move on this path — and that is now
correct for a stated reason rather than by accident.

### ⚠ WHY THE ALERT IS NOT NAMED `halt_*`

`POST_HALT_ACTIVITY_ALERT_TYPE` is `"post_halt_activity"`. That name was chosen
against a specific hazard, and it is the most easily-lost decision in this entry:

`isHaltAlertType` matches on the **`halt_` prefix**, and `resolveHaltAlerts`
closes *everything* it matches on any successful resume. `haltAlertType`'s own
header already carries the warning — *"A future alert type that is ABOUT halting
without BEING a halt must not be named `halt_*`, or `resolveHaltAlerts` would
close it on the next resume."* This is the first type that fits that
description, and it is exactly the trap.

**MAKING AN EVENT VISIBLE IS WORTHLESS IF THE SYSTEM'S OWN MACHINERY HIDES IT
AGAIN THROUGH AN UNRELATED PATH.** A `halt_post_halt_activity` row would have
been swept resolved by a sweep that never evaluated its condition, by a resolver
that has no opinion about it, on a resume that happened for entirely other
reasons — leaving a row that says "resolved" about a thing nobody looked at.
That is the same failure `/src/alerts/halt.ts` spends a section refusing (one
row, two owners) and the same class as the silent gaps `shared/alert-types.ts`
exists to end.

It **is** closed on resume — by `#resolvePostHaltActivityAlerts`, named
explicitly in `#resumePass`, so it has exactly one owner: the object that raises
it. `alert-types.test.ts`'s "recognises NOTHING else" list now contains it, so a
future rename into the `halt_` namespace fails the suite rather than quietly
handing the row a second owner.

It is also **not** a `RECEIPT_ALERT_TYPE`. The `take_profit` row beside it is a
receipt — the cycle closed, nothing is left to do. This one is an open condition
(*a halted bot's books moved and nobody has looked*) and is raised `warning` and
**unresolved**, which is what makes it appear in the one number an operator reads
to decide what needs attention.

### The pointers are real row ids

`#audit` and `#alert` now **return the row id they generate** — a widening every
existing caller ignores (`#cleanupStep` widened to `Promise<unknown>` to absorb
it). A `PostHaltEvent` therefore holds the actual `audit_log.id` and `alerts.id`,
not a `(action, created_at)` lookup key to be re-derived later. A re-derived
pointer is one rename away from addressing nothing, silently.

### `#resumePass` clears the field in the same write that clears `haltReason`

One write, so the two cannot disagree about whether there is a halt to annotate.
A running bot advertising events that happened during a halt it is no longer in
would be step 16's bug 3 and step 27's, one layer out again. The cleared events
are preserved in the `bot.resumed` audit entry as `previous_post_halt_events`,
alongside `previous_halt_reason` — history belongs in an append-only log, not in
a mutable status field.

## PART 4 — THE `openOrderIds` FIX, MADE UNCONDITIONAL

### The secondary finding

`#completeCycle` wrote `openOrderIds: []` — **wholesale**. On the bot this was
found on, that meant completing the cycle also dropped the *other* order still
live on the exchange: the additional buy whose cancellation entry 82's halt
could not confirm. D1's `orders` table still carried the row, so
`findInactiveBotsWithOpenOrders` would still have found it. **The bot itself
would not.** The 30-second poll reads `openOrderIds` and nothing else, so an id
dropped from that list is an order this system has stopped watching, while every
external record still says it exists.

### The determination: unconditional, not gated on halted

The obvious minimal fix is to be surgical only when the bot is halted. **That
was rejected, on three pieces of evidence:**

1. **`#completeCycle` was the odd one out.** `#completeLiquidation` and
   `#completeTrailingStopExit` — the two sibling completion paths — already do
   `openOrderIds: current.openOrderIds.filter((id) => id !== exit.clientOrderId)`.
   Making the third match them is the conservative change; keeping a special case
   would have been the novel one.
2. **The wholesale clear was never a garbage collector.** `#foldTerminalState`
   and `#cancelOpenOrders` both remove ids **by name**, and `#foldTerminalState`'s
   own comment records that assigning the list wholesale is precisely what
   resurrected dead ids on the grid path. The maintained discipline this codebase
   converged on is name-filtering; this was the last holdout.
3. **It is a no-op exactly when everything went well.** `#applyFillToOrder` has
   already removed the exit's own id on `fullyFilled` before `#completeCycle`
   runs, and `#placeTakeProfitSell` cancels the resting buys before sizing the
   exit. On a healthy cycle the list is already empty.

So the two versions differ **only** where an id was deliberately retained — and
every such id means the same thing on a running bot as on a halted one: *this
order may still be live on the exchange.* Either a cancellation whose outcome
could not be confirmed (§5.6: not a cancellation), or one `#foldTerminalState`
refused to close because the venue reported more filled than was recorded. Both
are conditions a human owns, and both are retained on purpose by code that says
so.

**The wholesale version was not safer on a healthy bot — it was less often
noticed there.** A retained id on a running bot makes `decide` return `hold`
instead of opening a new base order, which is correct while an unconfirmed order
may be resting, and the poll clears it by name as soon as the venue answers.

## PART 6 — THE TEST FIXTURE'S RIGOR

The six tests live in one describe, `"a take-profit exit that fills after the
bot has already halted"`, and the fixture is the point of them.

**It reproduces entry 82's incident shape exactly, through the public API — not
a simplified "a fill arrives on a halted bot".** `haltedWithRestingExit()`:

1. Creates and starts a real DCA bot; base buy placed and **fully** filled.
2. Drives a 5% drop so `decide` opens a real **additional buy**, which is left
   resting and unfilled.
3. Sets `exchange.cancelFailure` to a transport failure — so from here on **no
   cancellation can be confirmed**, which is why anything survives to fill later.
4. Drives the price to take-profit. `#placeTakeProfitSell` sweeps the resting
   buy first, **fails to confirm it**, retains its id and alerts `cancel_failed`,
   then places the exit.
5. Halts the bot for `stop_loss` — an unrelated, earlier reason. That sweep
   fails to confirm too. **Both orders survive both sweeps**, asserted.

Only then does the exit fill. The clock advances ten days first, mirroring the
live gap.

**Why this matters more than a generic fixture.** The additional buy is not
scenery — it is the load-bearing part, and it is what makes *"does completion
drop it?"* an observable question instead of a hypothetical. A generic fixture
(halt a bot, inject a fill) would exercise the status precondition and **miss
PART 4 entirely**, because there would be no second id to lose. The historical
failure shape had two orders in flight and an unconfirmable cancel sweep;
testing the approximation would have tested a bug that was easier than the real
one.

The assertion carrying the original evidence:

```ts
const row = (await db.botInstances.findOne({ id: BOT_ID }))!;
expect(row.halt_reason).toBe(before.halt_reason);
expect(row.updated_at).toBe(before.updated_at);
```

`updated_at` still not moving is the observed live fact — now true for a stated
reason rather than by accident.

The drop test asserts **both halves**: the id survives in `openOrderIds`, *and*
the bot still asks the exchange about it. The second needed a new `FakeExchange`
recorder (`getOrderStatusCalls`, pushed **before** the failure branches, so it
answers *"did the bot ASK?"* rather than *"did it get an answer?"*), because
membership in a list is worth nothing if the poll no longer reads it.

The six: the honest result and untouched D1 row; the visible record and its real
row-id pointers; the unrelated order surviving and still observed; resume
clearing state and alert in lockstep; the `autoRestart: true` branch reporting
the *other* suppressed transition and still not restarting; and a regression
guard that the healthy running path is completely unchanged (same action, same
halt, and D1 **does** move there — the difference from the halted case).

## PART 7 — THE DASHBOARD FOLLOW-UP

The backend fix made the event **recorded**. It did not make it **seen** — and
the whole defect was invisibility, so the arc is not finished at a field nobody
renders.

### One thing had to be added first

`PostHaltEvent` carried the gross profit only as **prose inside `summary`**.
Parsing a number back out of a sentence is the re-derived-pointer failure this
entry spends PART 3 refusing, so the event gained `grossProfit` and
`capitalAsset` instead — built from the **same `toDecimalString(gross)`
expression** the audit row is built from, with a test asserting the two strings
are identical. The screen and the log cannot tell different stories about one
cycle.

It is stored as a **decimal string, not a `Money` bigint** — the one place in
this state that departs from the convention, documented at the field. Nothing
computes with it (it is a record, not an input), and `botSummary` returns these
events verbatim rather than through `jsonSafe`, so a bigint there would not
survive `JSON.stringify` at all.

### ⚠ THE CONVENTION WAS FOUND, NOT INVENTED

`docs/open-items/component-test-harness.md` is explicit: **no test in this
repository can mount a React component**, and a test importing a `.tsx`
**collects zero tests rather than failing** — a green suite on a file that never
ran. Building a harness is a tracked item the operator deliberately deferred.
The established two-part pattern was followed exactly:

1. **A React-free rule module.** `dashboard/src/postHaltEvents.ts` holds every
   verdict — labels, pluralisation, the profit/counterfactual split, the
   status cross-check — and `postHaltEvents.test.ts` covers it in **22 tests**.
   Same shape as `killSwitchBannerState.ts`, `proposalFields.ts`,
   `pollFreshness.ts`. `proposalFields.ts`'s header records why this is not
   optional: a mutant deleting a guard's call site **survived**, because the
   call site was one line inside a `.tsx`.
2. **A source-scan call-site guard.** `components/post-halt-notice.test.ts`,
   **14 tests** via `import.meta.glob(…, '?raw')`, modelled on
   `kill-switch-banner-states.test.ts`. It pins that the notice is actually
   rendered, that it sits **below** the halt banner in source order, that it is
   **not nested inside** the halted-status condition, that the list tag appears
   in **both** layouts (count-matched against `ArchivedTag`), that the component
   wears **no red**, and that neither side hand-builds the anchor string.

### What is visible, and how it is told apart from the halt banner

**Colour was not a choice made here.** `AlertList.tsx` fixes the dashboard's
severity vocabulary — **info sky, warning amber, critical red** — and the
backend raises `post_halt_activity` at `warning`. So:

- **RED** — `BotSummary`'s existing band: *why this bot is halted*. Primary,
  safety-relevant, never overwritten.
- **AMBER** — `PostHaltNotice`, rendered **directly below it**: *and then this
  happened underneath it.*

Placement is the argument: the two are read together or not at all, and anywhere
further down the page an operator reading the halt reason would already have
decided. It is deliberately **not** nested inside `bot.status === "halted"` —
it carries its own gate, so events that somehow outlive their halt are shown and
flagged (`staleForStatus`) rather than hidden by a condition that stopped being
true.

Per event: the kind in words (never the raw enum), when, the booked profit in
emerald with its unit, the causing order, the halt it landed under, and — kept
visually apart — a **"Did not happen:"** line for the suppressed transition.
That separation is enforced as two distinct fields in the rule module and
asserted in both directions, because the two facts are of opposite kinds:
`grossProfit` is **real and booked**; `suppressed` is a **counterfactual**, and
an operator who conflates them concludes the bot restarted.

**The list view carries a `post-halt activity` pill** next to the bot id, in the
table *and* the card, copying `OrphanTag`'s styling exactly and putting the whole
fact in the `title`. This is not decoration: on every column of that table a bot
whose take-profit filled after halting is **identical** to one that has sat
untouched — same status badge, same halt reason, same updated time, because the
backend deliberately writes none of them. An indicator only on the detail page
would help an operator who already suspects something, leaving the fleet view
lying exactly as before.

### ⚠ ONE POINTER IS DELIBERATELY NOT A LINK

The **alert** links: `AlertList` gained a per-row `id` through a shared
`alertRowAnchor()` (same arrangement as `APPLY_MISSED_FILLS_ANCHOR` and
`CHECK_OPEN_ORDERS_ANCHOR`, one spelling both sides read), so *"See the alert
below"* lands on that exact row on the same page.

The **audit id is rendered as copyable text, not a link, because this dashboard
has no audit-log route** — `App.tsx` has `/`, `/bots/*`, `/alerts`,
`/kill-switch`, `/manual-adjustments`, `/proposal*` and nothing else. A link to
a page that does not exist is the silent-gap-on-a-correction-surface failure
this project refuses everywhere else. A guard test asserts no `href`/`to` is
ever built from `auditId`. An audit-log screen is its own piece of work.

### The standing caveat

**Colour, contrast, placement and whether the amber genuinely reads as secondary
on the deployed page are unverified by anything here.** They are the operator's,
as every UI step in this project has been, and the component-test-harness open
item is why.

### ⚠ THIS IS A DOWNSTREAM CONSEQUENCE OF ENTRY 82, NOT MERELY A SIMILAR BUG

The distinction is the most important cross-reference in this entry, and PART 1
gives the mechanism. To state it directly:

**Entry 82's incident is what created the resting sell that filled here.** Its
stop-loss halt threw partway through its cleanup, leaving the cancellations
unconfirmed and the sell live on the exchange. Ten days later that specific
order — the one 82 left behind — filled, and drove a cycle completion into a bot
