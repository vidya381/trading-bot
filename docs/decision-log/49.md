## PART 3 — ⚠ THE CONCENTRATION VERDICT HAS THREE STATES, AND THIS WAS FOUND IN SOURCE RATHER THAN ASSUMED

**The brief for this step specified two states — flagged and clean. The source has
three, and the third is the one the badge exists for.**

`derive.bundle.concentration` is a `GatheredInput<ConcentrationResult>`, so there
are two independent discriminants and therefore three genuinely different facts:

| state | what actually happened |
| --- | --- |
| `flagged` | the check ran and found something to weigh |
| `clean` | the check ran and found nothing (`assessment: "no_concentration"`) |
| **`unknown`** | **the read FAILED or THREW. Whether this proposal would over-concentrate the account was never established.** |

⚠ **WHY THE THIRD STATE REACHES A REAL PAGE IN ORDINARY OPERATION, WHICH IS THE
PART THAT MAKES IT DANGEROUS RATHER THAN THEORETICAL:** `/assess` and `/derive`
both **deliberately let a failed concentration read through** rather than failing
the request, because a usable, grounded proposal should not be lost to an unrelated
D1 error. That is the right call and it is not being revisited. **Its consequence
is that "the check did not run" is a state a human really sees.**

`ProposalConcentration` has rendered these as three distinct things since step 44,
and its header states the reason in one line: ***an unknown is not a clean
result***, and the failure mode is *"a reviewer glancing at a quiet strip and
reading 'nothing shown' as 'nothing there'."*

### Why folding `unknown` into `clean` would have been the worst available bug

**It would be a false negative, in green, at the top of the page, in the only case
where the badge had nothing behind it.** Stated plainly because it is easy to read
as a styling nicety:

- It would **not throw**, would **not fail a typecheck**, and would look correct in
  every screenshot taken on a healthy run.
- It would be wrong **only when the D1 read failed** — which is to say, **only in
  the case the badge exists for**.
- It would **contradict the panel forty lines below it**, which would still say
  `Over-concentration: NOT CHECKED` in loud amber. A page that disagrees with
  itself teaches a reviewer to trust whichever half they read first, and the card
  is the half they read first.
- And it is **precisely the failure mode this project's entire citation and
  evidence discipline exists to prevent**. Entry 43 built a three-way citation
  classification rather than a flat list because rendering an absence marker
  identically to fetched data makes a proposal *look better grounded than it is*.
  Entry 44 refused to invent a liquidity threshold because *an unstated gap is the
  failure mode; a stated one is a limitation*. Entry 45's `worstVerdict` answers
  `unknown` and **never `fresh`** for an empty input set, and its docblock calls
  that fail-closed shape *"the thing this whole module is written against"*. **A
  two-state concentration badge would have been the one place in this pipeline
  where an unestablished fact renders as an established good one.**

**So the type is a three-member union and a boolean is unspellable**, `unknown` is
styled **exactly as loudly as `flagged`** (asserted by a test, not by review), and
`concentrationVerdictOf` tests `outcome !== "ok"` **first**, so an unrecognised
future outcome falls to `unknown` rather than to `clean`.

### ⚠ AND NO VERDICT IS COMPUTED IN THIS STEP AT ALL

The property the whole card is judged on. `concentrationVerdictOf` **reads the
backend's own `ConcentrationResult.assessment` field** — a value written after
`src/research/concentration.ts` ran its real policy against real bot rows. It
applies no threshold, counts no bots and compares no capital share. A test asserts
that a result the backend called `no_concentration` reads `clean` **even when its
own `samePairBots` count is 11**, because a second implementation of that policy
would drift, and the copy that drifts is the one nobody is watching. The source
guard forbids `samePairBots`, `committedBots`, `capitalShare` and `flags` from
appearing in `proposalSummary.ts` at all.

The staleness side is the same shape: `stalenessVerdictOf` composes
`freshnessOf` + `stalenessFor`, which compose the **backend's** `stalenessOf` and
`worstVerdict` over `DEFAULT_STALENESS_POLICY`. It is recomputed on a 1-second tick
rather than carried, for entry 48 PART 3's reason, and mutant M7 proves the
recomputation is load-bearing.

## PART 4 — ⚠ A REPORTED BADGE-PRECEDENCE BUG WHOSE PREMISE DID NOT EXIST

**Recorded plainly, and at length, for the reason entry 48 PART 7 recorded its own:
so a future reader does not inherit a wrong framing from a brief, and so a
fabricated finding does not enter a permanent, undeletable record.**

The brief for this entry asked for a "badge-precedence fix" to be written up: that
when concentration is **flagged** and staleness is **stale** at the same time, an
initial version *"let staleness silently override concentration"*, and that this
was *"found and fixed via mutation testing (M3/M4/M5) before it shipped"*.

**It was checked at four levels before any of it was written. There is no such
mechanism, there was no such version, and no such fix was made.**

| checked | finding |
| --- | --- |
| the render, `ProposalSummaryCard.tsx` | `<Badge {...concentration} />` and `<Badge {...staleness} />`, **both rendered unconditionally**, side by side in one flex row. There is no conditional, no precedence expression and no suppression anywhere in the file. |
| the source history of this step | the badge pair was written in this form in the first version of the file and never changed. **No commit, no edit and no mutation result altered it.** |
| what M3/M4/M5 actually were | **concentration-verdict mutants, not precedence mutants**: M3 inverted the flagged/clean branches, M4 hardcoded `clean`, M5 hardcoded `flagged`. All three were caught. |
| what mutation testing did to the source | **nothing.** All 14 caught mutants were injected faults against already-correct code, applied and then reverted by the harness. **Catching a mutant is evidence of test sensitivity, not the discovery of a bug.** The only survivor, M13, is equivalent. |

**No bug was found, nothing was fixed, and this is not another instance of that
pattern.** Claiming it would have put a fabricated finding into this log — which is
a worse fault than the one it describes.

### ⚠ BUT THE DESIGN QUESTION UNDERNEATH IT IS REAL, AND THE REASONING IS KEPT

Checking the claim meant asking what *actually* happens when both verdicts are
non-clean, which is a case that will occur. The answer is that **both badges render
and neither suppresses the other** — and the brief's own reasoning is the right
argument for why that must stay true, so it is recorded here as a **constraint on
future edits** rather than as a fix:

> **Staleness has a remedy and concentration does not.** A stale proposal is fixed
> by re-running the pipeline: the data is old, and new data is obtainable. **An
> over-concentration flag is a fact about the account, not about the data** — it is
> just as true after a refresh, and re-running changes nothing about it. A design
> that ever collapsed the two into one "worst" badge would therefore hide the
> permanent finding behind the temporary one, and the reviewer's natural response
> to the temporary one (*refresh and look again*) would make the permanent one
> **disappear from the card on the second look**.

That is a genuine hazard and it is worth having written down. It is **not** a
description of anything that happened.

⚠ **AND ONE HONEST GAP FOLLOWS FROM IT.** "Both badges always render" is currently
enforced only indirectly — by the source guard's forbidden-string list, which stops
the card deciding a verdict, and by the operator's eyes. **There is no test that
asserts a flagged-and-stale proposal shows two badges.** It is one assertion and it
should exist; it is named here rather than quietly added after the fact, and it is
the kind of thing PART 6's harness gap makes harder than it should be.

## PART 6 — THE TEST-HARNESS DECISION, AND WHY `<details>` IS A DESIGN CHOICE RATHER THAN A WORKAROUND

### The constraint, stated exactly

**No test in this repository can mount a React component, read the rendered DOM, or
simulate a click.** Not "nobody wrote them" — a test importing a `.tsx` **collects
ZERO TESTS RATHER THAN FAILING**, because React's CJS build does not resolve inside
the Workers pool the root suite runs in. **A component test added today would
report "0 tests" and a green suite**, and nothing would tell the author their file
never ran. Recorded as an absence in entries 44, 45, 46 and 48.

### The decision taken, and it was put to the operator explicitly

**Two options were laid out with their costs before any code was written**, and the
operator chose: build the card under the existing pattern, and write the harness gap
up as its own standing item. **A UI step should not silently become a toolchain
step.**

So every decision lives in `proposalSummary.ts`, which is React-free and driven by
the root suite. This is not a preference. `proposalFields.ts` was extracted for this
exact reason after a mutation run proved its inline predecessor's guard call site
**unreachable by any test**: *a decision that cannot be tested is a decision nobody
is watching.*

### ⚠ AND THE `<details>` CHOICE IS THE INTERESTING PART, BECAUSE IT IS NOT A WORKAROUND

A `useState(false)` toggle would have been the obvious implementation and would have
put **both halves of the requirement inside a `.tsx` where nothing could reach
either**. Native `<details>` moves both halves somewhere checkable:

- **"expands on click" becomes the BROWSER's behaviour** — HTML's own disclosure
  element. **This project does not implement it and therefore cannot regress it.**
  There is no application code between the click and the expansion to break.
- **"defaults to collapsed" becomes the ABSENCE of an `open` attribute** — a
  property in the source text, which a source scan can and does check across every
  `<details>` in the dashboard.

**That is a better design under any harness, not a compromise made for want of
one.** It has fewer moving parts, no state to desynchronise, and it works with the
browser's find-in-page and accessibility tree rather than around them.

⚠ **ITS LIMIT, STATED SO IT IS NOT OVER-GENERALISED:** this works for a disclosure
widget. **It does not generalise to a form, a combobox, or anything with real
state** — and `pages/CreateBot.tsx`, the screen that commits capital, is full of
exactly that.

### The harness gap is a STANDING, NOT-YET-DECIDED item

`docs/open-items/component-test-harness.md`. It records the gap, the dangerous
"0 tests and green" failure mode, the three mitigations **with their limits**, and
what closing it would involve: `jsdom`/`happy-dom`, `@testing-library/react`, a
**second vitest project** (the root config wraps everything in the `cloudflareTest`
plugin), and a decision about `dashboard/tsconfig.app.json`'s test-file exclude and
entry 44's standing consequence that dashboard test files are *executed but
typechecked by no `tsc` project*.

**It is explicitly not scheduled and not begun.** The cost is a shifted suite
baseline, new dependencies, and a change to what `npx vitest run` means; the benefit
is that the currently-impossible tests are the ones covering the screen where a
human commits capital. **That trade deserves its own step and its own entry.**

⚠ **WHAT IS CONSEQUENTLY UNVERIFIED BY ANYTHING BUT A HUMAN'S EYES:** position,
prominence, colour, legibility, and the rendered open/closed state. That is exactly
what PART 7 is for.

## PART 8 — ⚠ THE LIVE OBSERVATION: A "FRESH" PROPOSAL WHOSE UPPER BOUND THE MARKET HAD ALREADY PASSED

**This is the finding of the step, it is the operator's, and it is not a bug.**

While verifying the card, the operator checked the proposal's numbers against the
account's **actual current market price** and found:

| | |
| --- | --- |
| the proposal's computed **upper bound** | **62,912.34** |
| the **real current price** at review time | **62,944.83** |
| | **the market was already 32.49 above the top of the proposed grid** |

**And the staleness badge said `fresh`, correctly.** Every fetch timestamp was
inside its own threshold. The grid price-history threshold is 15 minutes and the
window had not come close to it.

### Why this is the clearest real-data argument for 21.5's staleness discipline yet

**Both facts are true at once, and holding them together is the whole point:**

> **"Fresh" is a claim about WHEN the data was fetched. It is not a claim that the
> data still describes the market.** Those are different guarantees, and only the
> first one is checkable by a timestamp.

A price window fetched four minutes ago is *fresh* by every definition this system
has, and a fast enough move can invalidate what was derived from it **inside that
window**. Entry 42 measured `candles.last_close` moving **17.60 in ten minutes**;
entry 44 ranked price history first among the four timestamps precisely because it
is *"the fastest-moving input and the one most likely to have moved since"*. **This
observation is that ranking being right, measured against a live price rather than
argued from one.**

It also settles a question the staleness thresholds could otherwise be read as
answering. `staleness.ts`'s header already says the absolute values are the part
its reasoning does **not** support — *"a different operator would defend 5 minutes
and 30 for grid, just as well"* — and **this is why no threshold could be the right
one.** The honest reading is not "15 minutes is too long." It is:

⚠ **NO STALENESS THRESHOLD, AT ANY VALUE, CAN CERTIFY THAT A PROPOSAL STILL
DESCRIBES THE MARKET.** It can only certify that the data is recent. The badge is
doing exactly what it was built to do, and what it was built to do is narrower than
what a reviewer might read into a green "fresh".

### ⚠ BREAKOUT TAKE-PROFIT WAS ENABLED ON THIS PROPOSAL, AND WHETHER THAT MAKES IT RIGHT IS NOT THIS SYSTEM'S CALL

The proposal carried `breakoutTakeProfit: true` with a real `breakoutThresholdPct`.
**That parameter exists for exactly this scenario** — price breaking above the upper
bound — and its presence may well mean the proposal anticipated the case and handles
it. That is a coherent reading and it should be said.

**But whether it is the RIGHT call on this pair, at this moment, with this account
already holding 13 bots on BTCUSD, is a judgement this system does not make and must
not appear to make.** Stated plainly and consistently with 21.1 throughout:

- **Nothing in the pipeline evaluated whether a breakout flag is an adequate answer
  to a bound the market has already passed.** No check asks it. `checkParamsShape`
  asks whether the field is present; the decoders ask whether it is well-formed; the
  sanity bounds ask whether it is in range. **Not one asks whether enabling it here
  was wise.**
- **The staleness verdict cannot ask it either.** It compares ages to thresholds. It
  has no access to the current price and no concept of a bound being exceeded.
- **The card certainly cannot.** It renders four facts and two verdicts.

**The human in 21.1 is the only part of this loop that can weigh it**, and this
observation is the sharpest illustration this project has produced of what that
actually requires: the operator did something no component in this system does —
**they compared a rendered number against the live market** — and found something
that every automated check passed over, correctly, because none of them was looking.

⚠ **AND THIS IS NOT A CALL FOR A NEW CHECK.** A "is the current price inside the
proposed bounds?" gate in the rendering layer would be the fourth time this arc has
been tempted to invent a risk rule in the layer least equipped to own it — entry 44
refused a liquidity threshold, refused a staleness threshold, and refused to
re-validate parameters, each time for the same reason: **a second implementation of
a risk check drifts from the first, and the copy that drifts is the one nobody is
watching.** The right response to a live observation is to record it and keep
looking, which is entry 44's own argument applied to its successor.

actually happens.
