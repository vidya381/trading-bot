## Step 76: Universal run-to-run terminated-order tolerance — one reconciliation behaviour for every exchange, and the prerequisite that had to ship with it

Date: 2026-08-24 · **NOT COMMITTED** as of writing. `HEAD` is `c180f08`
("Fix the actual root cause behind order-tracking resurrection") — entry **75**'s
work, committed since that entry was written. Eight files sit modified on disk;
they are enumerated in PART 6.

### What this is

A **design-then-build cycle**, prompted by the operator's stated goal of adding
more exchanges and wanting **one** reconciliation behaviour with no
per-exchange judgement call. The design was written in an earlier, build-free
session as `docs/open-items/universal-run-to-run-tolerance.md`; **this session
built exactly what that document specified.**

It generalises entry **68**, which fixed this for Gemini specifically
(committed as `87a1924`).

**The document was not taken on trust.** Every line number, count and structural
claim in it was independently re-verified against current source *before* any
code was touched, and the discrepancies that surfaced were reported to the
operator and resolved before proceeding — PART 3 and PART 4 below. That
re-verification is the reason this entry can distinguish what the design got
right from what it missed.

**The split held: no `wrangler`, no deploy, no HTTP call, no real D1, no
browser. Nothing was run against any live bot, and no live verification is
claimed anywhere in this entry.**

## PART 1 — THE DECISION, AND WHY

**Decided by the operator before this session and not reopened here:**
reconciliation's terminated-order forgiveness **stops branching on whether an
exchange reports a real last-update timestamp.** Every venue — Binance today,
any future venue — uses the same run-to-run confirmation: **a first sighting is
recorded and does not halt; a second sighting escalates and halts.**

### The reasoning

Branching on timestamp presence requires **every future exchange integration to
correctly self-report something no test and no compiler can check.** The branch
was on data presence rather than on a venue name — which was the better of the
two bad options — but it still meant a new venue's parser silently selected
which safety path reconciliation would take.

**Gemini already got this wrong once, silently.** Its parser satisfied the type
by setting `updatedAt = createdAt`, so `age` measured the order's *total life*
and the 60-second window never applied to any Gemini order older than a minute.
That was caught only because the resulting failure was **loud** — it halted
bots. Entry 68 records the reasoning in full.

**The same defect was found already sitting in the Binance parser, latent and
unfired.** `src/exchange/binance/parse.ts` falls back to `createdAt` when
`updateTime` is absent. The design reasoned it has never been observed to fire,
because `updateTime` is documented present on both endpoints — **that is the
design's claim and this session did not measure it.** The point stands
regardless: the identical bug class was sitting in a second parser, unnoticed,
in the venue everyone believed was the safe one.

### The structural proof, not a convention

`liveOrderFindings`'s signature dropped **from seven parameters to five**,
removing `at: Timestamp` and `thresholds: DriftThresholds` entirely. The
function that decides whether to halt a bot over a terminated order now has
**no clock of any kind in scope** — not the venue's, not the worker's.

This was verified rather than asserted. A word-boundary sweep of the function
body found `at` used as a code identifier on exactly two lines (its own
declaration and the deleted age computation) and `thresholds` on three, all
inside the deleted block. After removal, every remaining textual hit inside the
function is **prose in comments**. Reintroducing a timestamp comparison here now
requires **re-plumbing a clock into the signature first** — a visible,
reviewable act rather than a one-line slip.

*(A methodological note worth keeping: the first sweep used `\b`, which macOS
`awk` silently does not support, and returned a false negative. It was caught
and redone with `grep -nw`. A verification tool that fails open is worse than no
verification, and this one nearly supplied false confidence for the entry's
central structural claim.)*

## PART 2 — THE PREREQUISITE, AND WHY IT HAD TO BE MORE THAN WHAT WAS FIRST PROPOSED

The run-to-run mechanism's **own memory** — the thing that detects a "second
sighting" — was itself defective, and the defect is a silent one.

`unconfirmedDriftFromRecentRuns` read recent `reconciliation.run` rows with a
**fixed row-count limit of 20, applied in SQL across every account**, then
filtered to one account **in JavaScript**. `audit_log` has no account column, so
it could not have been otherwise. One cron tick writes **one row per account**,
so reaching this account's previous run means traversing every other account's
rows first.

**Past roughly ten accounts the prior sighting becomes invisible**, `alreadySeen`
is permanently `false`, every run re-records an unconfirmed finding, and
**nothing ever escalates — with no alert**, because a minor finding raises no
alert row by design. That is the "never halts" failure mode, reached by scale
rather than by logic. Today only Gemini rides this memory; **under universal
run-to-run every venue does**, which is why it could not ship afterwards.

### The correction the design found: a time bound ALONE is not sufficient

The prerequisite as originally framed was "bound the query by time". **That
alone does not fix it.** `LIMIT` is applied *after* `WHERE` and *after*
`ORDER BY created_at DESC`, and each tick writes its rows near-simultaneously —
so with enough accounts, the current tick's own rows exhaust a modest cap before
the scan ever reaches the previous tick. The prior sighting is still missed, now
for a different reason.

**The fix required both parts together:**

- a **time-bound SQL predicate** — `created_at: { gte: at - windowMs }`;
- a **raised cap** — `RECENT_RUN_SCAN` → **`RECENT_RUN_SCAN_CAP`, value 500**.
  The rename is load-bearing: the old name read as *"how far back we look"*,
  which is exactly the misreading that produced the defect. Rows inside the
  window are `accounts × (600s ÷ 300s)` = `2 × accounts`, so **500 supports
  roughly 250 accounts**.
- the JS `break` that previously stood in for the time bound was **deleted**, so
  two things do not both claim to be the bound.

**No migration.** `migrations/0001_initial_schema.sql` already indexes
`audit_log(created_at)` and there is **no index on `action`**, so the new query
is a bounded index range and is **cheaper** than the unbounded backwards walk it
replaces.

### Proven, not assumed

Per the design's own instruction, **the test was written first and run against
UNMODIFIED source**, and the real failure was recorded:

```
FAIL  reconcile.test.ts > PINS THE PREREQUISITE: escalation survives other
      accounts filling the row budget
AssertionError: expected false to be true
    1824| expect(second.findings.some((entry) => entry.kind === "order_state_drift"))
Tests  1 failed | 1 passed | 71 skipped (73)
```

Thirty filler `reconciliation.run` rows for other accounts — comfortably past the
old cap of 20, modelling an 11+ account deployment — push the real sighting out
of the scan; escalation never fires and no alert is raised. **That is the defect,
reproduced.** The fix then closed it.

**A test that has never been seen to fail has not been shown to test anything**,
and this one was seen to fail first.

## PART 3 — THE DISCOVERY BEYOND THE DESIGN DOCUMENT'S OWN SCOPE

**This is the part of the entry that most deserves weight.**

The design document searched for tests pinning the old timestamp-branching
behaviour and found **four**, all in `src/reconciliation/`. It stated the count
explicitly and corrected a prior estimate upward to reach it — *"Four, not the
three the prior investigation estimated"* — which reads as a carefully measured
figure.

**There was a fifth, and it was not in that directory.**

Running the actual change and the actual suite produced **three failures in
`src/alerts/standing.test.ts`** — a file the design document never mentions, and
which its file table does not list. Its `beforeEach` carried
`clock += 600_000` under the comment *"Past reconciliation's 60-second timing
window, so the order that left the book is real drift"*. It was pinning the
retired mechanism as squarely as the four the document found.

That it is genuinely the terminated branch was confirmed rather than assumed: at
`fake-exchange.ts:363`, `getOpenOrders` excludes a resting order once
`filledQuantity >= quantity`, so the fully-filled fixture really has left the
book.

**The real file count is 8, not 6.**

### Why this matters as evidence about the design/build split

The document was thorough, its arithmetic was sound, and its every line-number
citation verified. **Re-reading it more carefully would not have found this.**
The dependency was found because the change was *built* and its suite was *run*.

A design session can enumerate what it thought to search for. It cannot
enumerate what it did not know to look outside of. **The build is not a
transcription step, and this is the concrete evidence.**

The three tests were repaired exactly as the document's own PART 4.2 specifies
for this behaviour change — a second reconciliation pass to reach escalation —
and the false comment was rewritten. They are now **real coverage rather than
collateral**: all three kill mutant F.

## PART 4 — OTHER DISCREPANCIES FOUND AND RESOLVED DURING THE BUILD

### 4.1 Two stale comments the document's file list marked untouched

`timingWindowMs` had **11 references in `src`**, and the document's count of 11
was right — but it **enumerated only nine**. The two it never listed:

- `src/reconciliation/reconcile.ts` — a doc block asserting the terminated branch
  forgives via `timingWindowMs`, **false after this change**;
- `src/shared/exchange-client.ts` — prose describing the window as live, and
  describing `liveOrderFindings` as *falling back* to the clockless mechanism,
  when it becomes the only path.

**`shared/exchange-client.ts` is a file the document's PART 10 explicitly lists
as untouched.** The document forbade the edit that would keep its prose true —
not as a decision, but because it never noticed the reference existed. Both
readings were defensible, so **this was put to the operator rather than decided
alone.**

**The operator chose to fix both**, on the reasoning that leaving them
contradicts the design document's own stated principle: a passing test — or a
comment — **carrying a false explanation is how the next reader learns something
wrong from a green suite.** That principle is the document's own words, applied
consistently.

### 4.2 The mutant-to-test prediction was wrong in one case — reported, not quietly reconciled

The design predicted **mutant B** (removing the SQL time predicate) *"must be
killed by"* the cap test, 7.1.

**It was not. 7.1 passes under mutant B.** The two mutants exercise **two
different dimensions of the same fix**: 7.1 tests the *cap*, mutant B mutates the
*time predicate*, and with the cap at 500 the filler rows no longer truncate.
Mutant B is killed by the **upper-edge** tests instead.

The mutant dies either way. **The document's attribution does not hold, and it is
recorded here as a genuine mismatch rather than silently restated to match the
prediction** — the same standard entry 68 applied when it recorded a measured
figure of three against a brief that anticipated two.

This also delivered the measurement the document specifically asked to be
recorded either way: with the JS `break` deleted, removing the SQL predicate
leaves **no** time bound, so both upper-edge tests fail. **The `break` really was
redundant**, and the SQL predicate demonstrably carries the semantics it carried.

### 4.3 Two further stale comments in `findings.ts`

Same class, fixed under the same principle: the `DriftThresholds` header
described *"the two magnitude thresholds and the timing window"*, and
`unconfirmedWindowMs` was documented as scoped to *"the same **live** order"* —
though it now governs terminated orders too, and is the one member the design
says becomes **more** load-bearing, as the only remaining time bound.

### 4.4 One claim checked and found harmless

The document stated `FindingKind` is imported *"in exactly two places outside
`findings.ts`"*. It is not — it missed two real imports, one of which
(`shared/alert-types.test.ts`) derives every kind programmatically from
`TIER_FLOOR` and is **absent from the document's file table**. Its conclusion
nonetheless held: those loops are fully derived, name no removed kind, and the
file **passes unmodified**. Verified empirically rather than reasoned.

## PART 5 — WHAT THIS PROVES, NOT MERELY CLAIMS

**Mutant D is the decisive result, and its *survival* was the goal.**

Binance's parser was forced to fabricate `updatedAt` from creation time
unconditionally — **the exact pre-entry-68 Gemini defect, reproduced in the other
venue's parser.**

- **Killed by 1 parser test** — `REPORTS A REAL updateTime, distinct from
  creation time`.
- **SURVIVED all 145 reconciliation-side tests, unchanged.**

**A reconciliation test killing this mutant would have been a failure of the
design, not a success of the suite.** Its survival is the empirical demonstration
that **no safety decision anywhere in this system reads what any exchange claims
about time**: corrupting that data outright changes nothing about the
halt/forgive outcome.

That is the property that makes a new exchange safe on the day it is added, and
it is now shown by measurement rather than argued from the shape of the code.

### Mutation — six mutants, applied ONE AT A TIME and `diff`-verified restored between each

Entry 68's convention was followed deliberately, because that entry recorded a
doubly-mutated file **overstating coverage fivefold in the flattering direction.**

| Mutant | Result |
| --- | --- |
| **A** — restore the timestamp-presence branch | **killed by 5** |
| **B** — remove the SQL time predicate | **killed by 2** — *not the test predicted; see 4.2* |
| **C** — cap back to 20 | **killed by 2** |

**A's killers (5):** `a terminated order is unconfirmed on its first sighting,
whatever the venue's clock says` · `a terminated order still halts, one run

`THE BUG CLASS IS DEAD: a fabricated updatedAt is now harmless` · `BINANCE IS NOW

**B's killers (2):** `the time bound still has an upper edge, at high row counts`
and the **pre-existing** `does not escalate on an unconfirmed sighting older than
the window` — i.e. it breaks **currently-working** behaviour, not only new
behaviour.

**C's killers (2):** `PINS THE PREREQUISITE: escalation survives other accounts
filling the row budget` and `the scan cap does not bind at the documented
supported account count`. **C exists because the prerequisite as first framed was
incomplete, and it is the proof that the time predicate alone does not fix the
defect** — with the predicate in place and the cap back at 20, 7.1 fails again.

**E and F both killed by 11** — the pair proving the mechanism cannot collapse in
either direction. F's killers include **all three repaired
`alerts/standing.test.ts` tests** plus the two others in that file, which is what
makes PART 3's discovery load-bearing rather than incidental.

### The rewritten Binance test, and why its ORDER is the test

`BINANCE IS UNAFFECTED: a real updateTime keeps both halves of its window` is the
guard entry 68 built **precisely so this change could not be made silently.** It
has done its job, and is **rewritten, not deleted**, as
`BINANCE IS NOW LIKE EVERY VENUE: a real updateTime changes nothing, in either
direction`.

**The naive rewrite — flipping the old assertions in place — would have produced
a test that passed while proving nothing.** The original's two halves were
independent, because the retired window decided each run from scratch. Under
run-to-run they are **not**: run one writes an unconfirmed row that run two reads
back as a second sighting. Keeping the old order would have made half two halt
**because it was the second sighting, not because of anything a timestamp did.**

So the halves are **inverted**: the old-timestamp case runs **first**, on fresh
memory (now minor, no halt — flipping *"used to halt on the first run"*), and the
young-timestamp case runs **second** (now escalates and halts — flipping *"used
to be forgiven indefinitely"*). Both assertions genuinely flip, and **the memory
carry-over becomes the subject of the test rather than an obstacle to it.**

Both halves stay in **one body**, exactly as entry 68 wrote it: the property —
*the outcome does not depend on the timestamp* — is a statement about the **pair**,
and split in two, one could be deleted while the other kept passing.

**That the ordering is right was confirmed by measurement, not by reasoning:** the
design named "does this test alone kill mutant A" as the check, and it does.

## PART 7 — WHAT WAS REMOVED, CONFIRMED UNREACHABLE FIRST

`timingWindowMs` and the `order_recently_terminated` finding kind were **removed
entirely — not left as dead code with a "no longer read" comment.**

A dead threshold and an unreachable finding kind inside a **safety** module are
worse than the deletion churn: they leave the retired mechanism's vocabulary
sitting in the `FindingKind` union and in both classification tables,
indistinguishable from kinds that actually fire — reintroducing one level down
exactly the judgement call this change exists to remove.

**Confirmed safe across the whole codebase before removal, not from the
reconciliation module alone:**

- **Zero references in `dashboard/`.** Zero in `migrations/` — **no D1 `CHECK`
  constraint names either string**, so no migration is needed.
- **No `alerts.alert_type` row can contain the kind**: its floor and ceiling
  capped it below the tiers that raise rows, and the raise path only builds an
  alert type for meaningful and severe findings.
- **Nothing maps a stored kind string back onto the union**, so historical
  `audit_log.details_json` rows containing the string stay readable — that column
  is typed `unknown` and the only code inspecting finding kinds inside it
  compares against a string literal.
- Both classification tables are `Readonly<Record<FindingKind, …>>`, so removal
  is **compiler-checked**.

`unconfirmedWindowMs` and its 600s default were **deliberately kept and
documented as more load-bearing**: it is now the only time bound in the
mechanism, and PART 2 puts it into the SQL.

`FakeExchange.reportsUpdateTime` was **kept**. It is now the thing that lets a
test assert the timestamp makes no difference — the rewritten Binance test sets
it `true` deliberately.

## PART 8 — NOT DONE / NOT VERIFIED

- **NOT DEPLOYED, NOT EXERCISED LIVE.** No `wrangler`, no HTTP call, no real D1,
  no browser. **No real order on any real exchange has gone through the universal
  run-to-run path.** Fixtures only. **No operator verification is claimed.**

- **The escalation-delay cost remains REASONED, not measured.** A genuine
  persistent drift now halts **at most one ~5-minute cron cycle later** than the
  timestamp path did — bounded at one cycle, never indefinite, and the identical
  trade entry **61** made deliberately for the live branch after zero-forgiveness
  halted two real bots. The design reasoned this applies to *most* terminated
  orders. **A specific percentage is NOT supportable and is not asserted here:**
  a 60s window inside a 300s interval implies roughly four-fifths falling outside
  it *only* under a uniform-arrival assumption, and **no figure in this
  repository measures when terminations actually land within the cycle.** The
  design document says the same in its own limitations section.

- **The Binance parser's timestamp fabrication is UNTOUCHED, deliberately** — the
  same class of D1 data-quality defect entry 68 fixed for Gemini. **Confirmed by
  an empty `git diff` on `src/exchange/binance/parse.ts`.** It is a separate,
  later, already-scoped follow-up: the design gives evidence-based reasons for
  not bundling it, chiefly that entry 68 measured these two layers as unable to
  cover each other, so one commit spanning both would leave a bisect unable to
  separate *"reconciliation stopped halting when it should"* from *"the parser
  changed what it reports"*. **It is not fixed here.**

- **The dashboard toolchain was not run** (PART 6), and no dashboard file was
  touched.

- **Mutant D's survival proves the reconciliation layer ignores parser
  timestamps. It does not prove the parser is correct** — that is precisely what
  the deferred follow-up is for.

- **Nothing is committed**, and no code was written in the session that produced
  this entry.
