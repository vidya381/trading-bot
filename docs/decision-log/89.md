## PART 1 — WHY THIS STARTED, AND THE REQUIREMENT THAT CHANGED MID-WAY

The trailing-stop live test across entries [86.md](86.md)–[88.md](88.md) ended
with a finding that was not about our code at all: **Gemini's sandbox BTCUSD
market is dead.** A crossed book, zero volume, and a price series that did not
move — 1439 of 1440 daily candles identical at `78172.34`. That was not inferred
from a failing bot; it was **confirmed by direct probe against Gemini's own
public ticker**. Entry 86 built three detectors so the condition is reported
rather than traded against, and entry 88 recorded the consequence: 22.7's
observation period cannot run on that data, because a week of operating history
against a frozen market says nothing about whether the strategy works.

That left one question: **where does honest market data come from?** This session
went looking for a real alternative venue.

**The requirement was corrected part-way through, and the correction is the
reason this entry is worth keeping.** The search began as *"find a testnet with a
live market"* — a replacement sandbox for 22.7's observation period. It was
corrected to: **any new exchange must work for PRODUCTION, with real fills, not
merely for testing.** The goal is bots that can actually keep trading, not bots
that pass a sandbox check.

This inverts what counts as a good result. Under the original framing, OKX's demo
environment would have looked like a find. Under the corrected framing it is
disqualifying — see PART 2.

## PART 2 — REACHABILITY, MEASURED FROM THE REAL EDGE

Every row below was produced by a deployed Worker making a real request from
Cloudflare's edge (colo **DFW**, egress `2a06:98c0:3600::103`). **None of it is
from documentation, and none of it is assumed.** That distinction is
load-bearing: Kraken's own support article advertises a demo host that no longer
exists, and only a live request found that.

| Venue / host | Result | What it actually means |
| --- | --- | --- |
| `api.binance.us` | **Reachable.** Clean `200`s, real prices | Works from the edge. **No sandbox or testnet exists for this venue at all** — not blocked, simply never built |
| `api.binance.com` | **451** | Binance's own jurisdiction / eligibility refusal |
| `testnet.binance.vision` | **451** | Same block, same shape |
| `api.bybit.com` | **403**, AWS CloudFront | Country-level block **before any Bybit code runs** |
| `api-demo.bybit.com` | **403**, AWS CloudFront | Demo domain blocked identically to live |
| `api.kraken.com` | **Reachable**, public *and* authenticated | Genuine API responses on both paths |
| `demo-futures.kraken.com` | **301 → marketing** | The advertised demo host is **dead** |
| `www.okx.com` | **Reachable**, public *and* authenticated | Genuine API responses on both paths |
| `www.okx.com` + `x-simulated-trading: 1` | Reachable, but **fictional prices** | Disqualifying — see below |

### The two block shapes are not equally hard

**Binance's 451 is application-level.** The request reaches Binance, Binance
identifies the origin as ineligible, and Binance answers in its own error
envelope. It is a decision made by the venue.

**Bybit's 403 is infrastructure-level.** It comes from AWS CloudFront with
CloudFront's own headers, and it lands **before any Bybit code runs**. Nothing
about our request — credentials, headers, account standing — can influence it,
because Bybit never sees it. `api-demo.bybit.com` returns exactly the same 403,
confirming it is a property of the CDN edge and not of any one Bybit service.
**Bybit is ruled out entirely**, and it is the only venue here ruled out on
reachability alone.

### Kraken is reachable on the path that matters

Public `/0/public/Time` and `/0/public/Ticker` both returned real data. More
importantly, `POST /0/private/Balance` with a deliberately invalid key returned
**`{"error":["EAPI:Invalid key"]}`** — Kraken's own credential error. That is a
*reachable* result: the authenticated trading path works and only a real key is
missing. A venue can pass a public-endpoint check and still block authenticated
traffic; this rules that out.

Note the shape — **HTTP 200 carrying an error**. Kraken returns 200 for nearly
everything and signals failure in a top-level `error` array. Status code alone is
not a success test at this venue, and every probe parsed the envelope explicitly.

### Kraken has no usable spot sandbox

`demo-futures.kraken.com` **301-redirects every path, including the root**, to
`https://www.kraken.com/gb/features/futures`. There is no demo API behind that
hostname — it is a dead hostname serving marketing content. Kraken's support
article still advertises it as self-service, a documentation/reality mismatch
only a live probe would have caught. Kraken's spot UAT is **request-only via an
account manager**, with no public host.

### OKX's demo environment is a fictional price feed

OKX demo trading is not a separate domain; it is `www.okx.com` plus an
`x-simulated-trading: 1` header. The header works. **What comes back is not the
real market.** Same endpoint, same instrument, moments apart:

| `BTC-USDT` | live | `x-simulated-trading: 1` | gap |
| --- | --- | --- | --- |
| last | `76823.9` | `78166.6` | **~1.7%** |
| `vol24h` | `5128.98` | `9126.93` | **~1.8×** |
| `open24h` | `77883.6` | `77890` | — |

**This is a simulated feed, not a mirror of real prices.** It is the same failure
shape entry [86.md](86.md)'s integrity detectors were built to catch: a feed that
is healthy, fresh and well-formed while describing a market that does not exist.
Under PART 1's corrected production requirement this rules OKX demo out as an
observation environment — it would produce another week of confident operating
history about a fiction.

## PART 3 — THE LIQUIDITY FINDING

**This is the evidence the decision in PART 4 rests on, and it is the part that
was not anticipated.**

Reachability and fees are venue-level properties, and they were the only two
questions the search had been asking. Neither answers the question the system
actually faces at runtime:

> **Is *this specific coin* — the small, currently-trending kind that section
> 21.3's trending pull exists to surface — actually listed, and actually liquid,
> on the venue we picked?**

General exchange reputation and fee comparisons cannot answer that. It was tested
directly, against three real currently-trending coins — **PONS, ARB and LIGHTER**,
with **PONS at #1 on CoinGecko's trending list at the time of testing** — across
**Kraken, OKX and binance.us**.

Catalogue sizes, each pulled live and matched on the venue's own `base`/`quote`
fields, never against a guessed pair string:

| Venue | Total spot pairs | Distinct base assets |
| --- | --- | --- |
| Kraken | 1,440 | 664 |
| OKX | 1,389 | 398 |
| binance.us | 264 trading | 203 |

### 3.1 Listing results

| --- | --- | --- | --- |
| **PONS** | **not listed** | **not listed** | **not listed** |
| **ARB** | `ARB/USD` | `ARB-USD`, `ARB-USDT`, `ARB-USDC` | `ARBUSDT` only |
| **LIGHTER** | **`LIGHTER/USD`** | **not listed** | **not listed** |

**⚠ CORRECTION TO THE WORKING ASSUMPTION: LIGHTER IS LISTED ON KRAKEN.** This
entry was drafted on the belief that PONS *and* LIGHTER were absent from all
three venues. That was true of the venue LIGHTER had actually been checked
against — `binance.us` — and had never been tested on Kraken or OKX. It was
tested before writing this, and **Kraken lists `LIGHTER/USD`, online, with a real
book** (measured in 3.2). The "absent everywhere" claim was wrong and is recorded
here rather than quietly dropped, because it changes PART 5's framing: the
problem is not only *absence*, it is **thin presence**, which is harder to detect
and therefore worse.

**Absences were verified two independent ways per venue**, because a negative
result is only as good as the matcher that produced it:

1. **Any-quote presence.** Not just USD/USDT — the check asked whether the base
   asset appears against *any* quote at all. If PONS were listed only against BTC
   or EUR it would have surfaced. It did not, on any venue.
2. **Alternate-ticker / substring sweep against the full base-asset catalogue.**
   PONS surfaced Kraken's `POND` and `PONKE` — **different coins**, confirmed by
   inspection, not alternate tickers for PONS. LIGHTER's alias sweep
   (`LIGHT`/`LIT`/`LGHT`/`LGR`) found Kraken's and OKX's unrelated `LIT`, and
   found nothing whatsoever on binance.us.

The matcher is proven working **in the same runs**, resolving `UNI`, `HYPE`, `ARB`
and `BTC` correctly on all three venues, including Kraken's `XXBT`→`BTC` and
`ZUSD`→`USD` prefix mangling. **PONS's absence is genuine, not a matcher bug.**

### 3.3 SUB-FINDING (a) — OKX's `-USD` pairs are a liquidity trap

**They list. They report `state: "live"`. They answer depth queries normally.
They carry a small fraction of the real liquidity, which is sitting under the
`-USDT` pair for the same coin on the same exchange.**

| Comparison | Thin side | Real book | Gap |
| --- | --- | --- | --- |
| `UNI-USD` vs `UNI-USDT` (both OKX) | $3,577 | $103,970 | **~29×** |
| `ARB-USD` (OKX) vs `ARB/USD` (Kraken) | $2,291 | $290,115 | **~127×** |

Every check the system currently knows how to make passes on `UNI-USD`. It is
listed, it is live, it returns a book, it has a spread. **A naive "resolve the
coin to the first matching pair" implementation would silently route real orders
into the worst available version of that market** — with no error, no warning,
and nothing in the order response indicating a 29× better book existed one pair
over. This is a routing bug no reachability test, fee comparison, or listing
check can detect. It is visible only by reading the book.

### 3.4 SUB-FINDING (b) — binance.us splits sharply by coin size

binance.us is **not uniformly thin, and not uniformly deep.** It showed a
consistent split:

- **Strong on BTC and majors.** `BTCUSDT` had the **tightest spread of any venue
  measured tonight** (0.00001%), and on a full 100-level pull holds $771,444 bid
  / $691,871 ask within ±1% — genuinely competitive with Kraken.
- **Among the weakest on smaller trending names.** `ARBUSDT` at ~$4.4k total book
  (3.2), roughly 66× behind Kraken on the same coin.
- **Zero measurable depth on `UNIUSD` specifically.** Spread is 2.1996%, so the
  ±1% band around mid (6.0761–6.1989) sits *entirely inside the spread* — best
  bid 6.070 and best ask 6.205 both fall outside it. **The $0 is a real
  measurement, not a missing one.** The same coin's `UNIUSDT` pair on the same
  venue holds $24,512 — sub-finding (a)'s trap, reproduced on a second exchange.

Whatever venue is chosen, **liquidity is a property of the (venue, coin, pair)
triple, not of the venue.**

## PART 4 — THE DECISION: KRAKEN

**This is a judgment call across imperfect options, not a clean win.** Every venue
tested fails at least one requirement, and Kraken fails one of them too — it has
no usable spot sandbox, so [88.md](88.md)'s 22.7 observation period still has no
honest venue to run on. That dependency is **not** resolved by this decision.

Kraken is chosen on three grounds, in descending order of evidential strength:

**1. Depth — the strongest evidence, measured tonight.** On every trending or
mid-cap coin that was listed there, Kraken carried substantially more resting
depth than OKX or binance.us: **ARB** $290k vs OKX's $24k and binance.us's $4.4k;
**HYPE** $568k vs OKX's $33k and binance.us's $99k; **UNI** competitive with OKX's
best pair and ahead of binance.us on the ask side. Kraken was also the **only**
venue of the three carrying `LIGHTER` at all. This is the ground the decision
actually rests on, because it is the only one measured directly against the coins
the pipeline will really see.

**2. Reachability — measured, PART 2.** Cleanly reachable on public *and*
authenticated paths, with no network-level or jurisdictional block. Bybit is
excluded outright; `binance.com` is excluded by 451.

**3. Fees — secondary evidence, NOT verified tonight.** Kraken is cited at roughly
**0.16% maker / 0.26% taker**, against Coinbase Advanced Trade's **0.40–0.60%** —
the best fee/compliance balance among realistic US-compliant venues. **This comes
from public comparison sources, not from a request this system made**, and must
not be read with PART 2's or PART 3's confidence. Fee schedules are volume-tiered
and change without notice; **the live fee endpoint should be read from the account
that will actually trade** before this informs anything irreversible.

**`binance.us` is recorded as the stronger venue specifically for BTC and
majors** (3.4) and is worth keeping available for that narrow case — as a
secondary venue for major-pair execution, **not as the primary venue**. Its
catalogue is 203 base assets against Kraken's 664, and it carried neither PONS nor
LIGHTER.

## PART 5 — THE STANDING LIMITATION, CARRIED FORWARD AS A BUILD REQUIREMENT

**No venue tested reliably carries the newest, smallest trending coins.** PONS —
**the #1 trending coin at the time of testing** — is absent from all three. LIGHTER
exists on exactly one of three, with a book an order of magnitude thinner than the
same venue's ARB. Choosing Kraken does not fix this; Kraken is simply the best of
three venues that all fail it.

**This is a requirement for the Kraken integration work, not deferred research,
and not a caveat to be noted and moved past.**

The coin-selection and proposal pipeline (section 21.3) must treat these as **two
separate facts**:

> **(i) the AI suggested this coin** — and — **(ii) this coin is actually
> tradeable, with real depth, on Kraken, on a specific pair.**

Fact (ii) **does not follow from fact (i), and does not follow from listing
either.** Section 21.3 already requires the trending pull be *"filtered to coins
actually tradable on the target exchange"* via `listTradablePairs`. **That filter
is necessary and not sufficient**: `listTradablePairs` answers *listed*, and
tonight's data shows *listed* and *tradeable* diverge by up to **127×**
(sub-finding (a)), reach **$0 of resting depth inside the band** (3.4), and admit
coins like LIGHTER whose real book is a fraction of what a proposal would imply.

**A liquidity/listing verification step is required before a candidate coin is
proposed or traded.** It must answer, per candidate:

- does a pair exist on Kraken for this coin;
- **which** of the possible pairs is the real book — pair *selection*, not merely
  pair existence, because sub-finding (a) is a routing bug that silently picks
  the worst one;
- what is the spread and the resting depth within a band of mid, **measured
  against the intended order size** — sub-finding (b) shows spread and depth
  disagree about which venue and pair is better, so neither alone is sufficient.

Section 21.3's hype-hazard paragraph already anticipates the *symptom*: it
requires the Explain stage (21.4 stage 4) to state plainly when a coin has thin
liquidity. **But that is stage 4, after selection.** It annotates a pipeline run
that should never have started. Tonight's data argues the check belongs at
**candidate selection**, where it can prevent the run rather than describe it.
Whether 21.3 is amended to filter on real liquidity before surfacing a candidate
is a **spec decision** and should be recorded as one, not settled as an
implementation detail.

## PART 6 — MEASUREMENT CAVEATS, STATED HONESTLY

- **Most depth figures are floors, not measurements.** Kraken and OKX were pulled
  at 20 levels per side; where every returned level fell inside the ±1% band
  (marked ⌊), the true depth is **higher** than recorded. **Real depth is
  understated, never overstated.** binance.us's ARB/UNI/HYPE figures are *not*
  floors — those books are shorter than 20 levels in band, so they are true
  totals. **The Kraken-vs-binance.us gaps in PART 3 are therefore conservative:
  the real gaps are wider, not narrower.** Proper sizing needs `count=500` on
  Kraken and `sz=400` on OKX.
- **Trending lists rotate within minutes, so this is a snapshot.** Two runs of the
  same probe ~2 minutes apart returned different members and orderings, and
  returned **materially different depth for the same pairs** — Kraken `UNI/USD`
  bid depth read $30,061 in one run and $18,654 in the next. No number here is a
  stable property of a coin or a venue.
- **Some cross-venue comparisons use different quote currencies.** binance.us
  quotes no `USDC` pair for ARB/UNI/HYPE and no USD pair for ARB, so USD-, USDT-
  and USDC-quoted books are compared side by side where a venue's pair selection
  differed. Sub-finding (a) is precisely the demonstration that this is not a
  neutral substitution.
- **The venues were not measured simultaneously.** Kraken/OKX and binance.us runs
  were ~22 minutes apart, over which BTC drifted 76,845 → 76,547 (**−0.39%**).
- **Absence is not permanent.** PONS being unlisted tonight says nothing about
  next week, and the LIGHTER correction in 3.1 is a direct demonstration of how
  an unverified absence claim goes wrong.
