## PART 1 — WHAT WAS BUILT

`parse.ts`, the **fourth of the five core files** entry 90 PART 5 planned, and the
last one before `client.ts`. It is structurally the third of `binance/parse.ts`
and `gemini/parse.ts` and reuses rather than reimplements: pair and asset names
are resolved through `catalogue.ts`, and nothing filter-shaped appears in it at
all, because `filters.ts` already owns that.

The six requirements confirmed in entry 90, and how each landed:

**1. Error classification, as the primary path.** Kraken answers **HTTP 200** to a
bad key, an unknown pair and a throttle alike, with the failure in a top-level
`error` array of `E<Category>:<Message>` strings. `classifyKrakenError` maps one
string; `classifyFailure` maps the array to an `ExchangeOutcome` failure.
`EService:Unavailable`/`Busy` become **`transport`**, not `exchange_error` — entry
90's most consequential row, since a server-side failure leaves the request's
effect unknown and calling it a definite refusal would tell section 5.1 an order
was rejected when its fate is open. `EService:Throttled:<ts>` extracts a genuine
**`retryAfterMs`**, making Kraken the first venue here able to supply one.
**Unrecognised strings fail closed** as non-retryable `exchange_error`.

**2. Order placement.** `AddOrder` returns `{descr: {order: "<prose>"}, txid: [...]}`
and almost nothing structured. `exchangeOrderId = txid[0]`; `clientOrderId` and
`pair` come **from the request**, which is the only other source; `state` is
`pending` (Kraken's `open` in this system's vocabulary); `fills` is `[]`;
`acceptedAt` is **receipt time, commented as such**, because `AddOrder` carries no
timestamp of any kind. **`descr.order` is never parsed** — entry 90 rejected
pattern-matching that sentence, and a test passes a request that contradicts the
prose and asserts the request wins.

**3. Order status.** Kraken's real enum maps directly: `pending`→`pending`,
`open`→`pending`/`partially_filled` by fill progress, `closed`→`filled`,
`canceled`→`cancelled` (one `l` on the wire, two in `OrderState`),
`expired`→`expired`. **An unrecognised status throws**, the same fail-closed shape
`filters.ts` uses for `SymbolStatus`. There is no `rejected` arm and its absence
is a fact rather than a gap: Kraken reports a rejection as an error string, so it
never reaches this function.

**4. Fee asset.** `feeAssetFor(pair, side, oflags)`. Per DECISION 4 the client
asserts `oflags=fciq` on every order, so the fee asset is the quote asset
deterministically. The **derived fallback** — `fciq` on a buy, `fcib` on a sell,
against the pair's own tickers — is carried for reconciliation reading state this
system did not place, and is tested on both a fiat-quoted and a crypto-quoted
pair, in both directions.

**5. Candles.** `last` is stripped before the pair is resolved (see PART 4 for why
the ordering matters). **Volume is read from index 6, not 5**: a Kraken OHLC row
is `[time, open, high, low, close, VWAP, volume, count]`, and both Binance's
klines and Gemini's `/v2/candles` put volume at index 5 — so the field that reads
across from both other venues is wrong here, and wrong *plausibly*, because VWAP
is a price-shaped number in the right magnitude range. Close time is derived from
the interval as `GEMINI_TIMEFRAMES.ms` does.

**6. Balances.** `BalanceEx`, `locked = hold_trade`, `free = balance - hold_trade`,
asset codes un-prefixed through `catalogue.tickerForAsset`. The two fields round
in **opposite directions** — `balance` floors, `hold_trade` ceils — because the
derived quantity here is `free`, where Gemini's derived quantity is `locked`.
Copying Gemini's double-floor would have copied the code rather than the
reasoning; flooring what can be spent and ceiling what is reserved is the pair of
directions that cannot overspend.

Beyond the six: the `{error, result}` envelope reader, server time, ticker/price,
`CancelOrder`'s `{count, pending}`, and `parseTrades`. `pending` is **surfaced
rather than swallowed** precisely because DECISION 2 accepts a known staleness on
the halt path — a caller that cannot see the flag cannot report the tradeoff it is
making. `parseTrades` exists because `feeAssetFor` needs a consumer to be more
than a declaration.

## PART 2 — ⚠ THE ENTRY-90 CORRECTION: RIGHT ABOUT THE FORMAT, WRONG ABOUT THE PRECISION

**This is a factual correction to prior research, not an implementation note.
Entry 90's claim should be read as superseded by this section.**

Entry [90.md](90.md) PART 2.1 records, in the table of things that map cleanly:

> **Decimal strings** — Prices, volumes, costs and fees are all decimal
> **strings** (live). They go straight onto `fromDecimalString`, with **none** of
> the JSON-number exception `gemini/parse.ts` needed for candle OHLCV.

**The first sentence is correct and the second is not.** Kraken does send decimal
strings everywhere, and there is indeed no JSON-number exception to make — that
half held up under every payload read during this build. But "goes straight onto
`fromDecimalString`" is a claim about **precision**, and `fromDecimalString`
throws on more than `SCALE = 8` decimal places. Pulled live during this build:

```
GET /0/public/Ticker?pair=BONKUSD   ->  "a": ["0.000002926000", ...]     12 dp
                                        "c": ["0.000002926000", ...]     12 dp
GET /0/public/OHLC?pair=BONKUSD     ->  "0.000002924"                     9 dp
GET /0/public/Ticker?pair=ANKRXBT   ->  "b": ["0.0000000601", ...]        10 dp
```

**These are real, currently-active markets, not edge cases held for delisting.**
Under the strict parser every one of those calls throws, and `BONKUSD` and
`ANKRXBT` become **entirely unreadable** — no price, no candles, no backfill.

The failure mode is exactly the one `fromDecimalStringRounded` was written for.
Its own docblock records the precedent: a Gemini sandbox balance arrived as
`"99829.54180779832"` (11 places), the strict parser rejected it, and **the
account became unreadable entirely — no balance snapshot, no drift detection.**
And entry 91 PART 5 hit the same wall from the other side, where 45 of 1440 live
pairs publish a `tick_size` finer than the money scale and `filters.ts` had to
coarsen rather than refuse.

**So this is the third appearance of one pattern, and it is worth naming as a
pattern:** *a venue's own published precision is not this system's scale, and the
strict parser's refusal is correct for values the system SENDS and wrong for
values a venue REPORTS.*

**FIXED.** Every Kraken-reported decimal value in `parse.ts` goes through
`fromDecimalStringRounded` with a direction **named at the call site**, following
the arrangement `filters.ts` already established:

| Values | Direction | Why |
| --- | --- | --- |
| Candle OHLCV, ticker `last`, order `vol` / `vol_exec` / `cost` / `descr.price`, trade `price` / `vol` | `half-even` | No directional bias, so representation error does not accumulate across many reads — the reason `order-state.ts` gives for `NOTIONAL_ROUNDING`. It is also **monotone**, which is load-bearing: `vol_exec <= vol` on the wire stays `filledQuantity <= quantity` after rounding, so a fine-priced pair cannot manufacture an overfill out of arithmetic. |
| Trade `fee` | `ceil` | A fee is money owed; rounding up never understates what was paid. |
| `BalanceEx.balance` | `floor` | Never overstate what can be spent. |
| `BalanceEx.hold_trade` | `ceil` | Never understate what is reserved. |

**`fromDecimalString` is untouched and remains the only way a value going back
out to an exchange is brought in.** Nothing in `parse.ts` is sent anywhere, which
is what makes the whole file the reported-value side of that line.

**The opposed balance directions have a cost, and it is bounded and handled.**
`free = floor(balance) - ceil(hold_trade)` can land up to 2e-8 below the true
figure, and for an account almost fully reserved it can cross zero. So the
negative-balance refusal — which Gemini's parser has, and which must stay, since
clamping would turn a genuine API change into a plausible-looking wrong balance —
permits **exactly that two-unit margin explicitly** and refuses anything beyond
it, rather than being loosened into meaninglessness. Both the clamp and the
refusal are tested.

## PART 3 — ⚠ THE CROSSED-BOOK CHECK FIRES FALSELY ON CHEAP COINS

Entry [86.md](86.md) built the spec 5.7 detectors, and `gemini/parse.ts` carries
detector 2, the crossed-book refusal, with an unusually strong claim attached to
it:

> A book whose bid is at or above its ask is ARITHMETICALLY IMPOSSIBLE on a real
> venue: the two sides would have matched. So this needs no threshold, no
> tolerance and no tuning — **unlike every other plausibility check in this
> system, it has no false-positive case to trade against.**

**That claim is true of the check and false of the implementation, and Kraken's
real data is where the difference shows.** The Gemini implementation parses both
sides to `Money` and compares. `ANKRXBT`'s live book:

```
b: "0.0000000601"      ->  0.00000006  at SCALE 8
a: "0.0000000607"      ->  0.00000006  at SCALE 8
```

Two genuinely different prices, six units apart at the tenth decimal, **identical
once rounded**. `bid >= ask` is then true, and the detector refuses the price —
not once, but **on every read of that pair forever**, and the same on `BONKUSD`
and on every other sub-satoshi market Kraken lists. A safety mechanism whose
stated virtue is having no false-positive case would have acquired one covering a
whole class of pairs, and it would have presented as the venue publishing broken
books.

**FIXED.** `compareDecimalStrings` — pad both fractions to a common width,
compare as `BigInt`. Exact, no float, no `Number`, **no scale limit at all**, and
it returns `undefined` rather than a guess for anything that is not a plain
decimal string, which the caller treats as "no book to judge" rather than as a
broken one. The crossed-book check is the one place in the file that deliberately
does **not** go through `Money`.

The tests pin both directions: the constructed crossed book is refused, the
touching book (`bid == ask`) is refused, and **`ANKRXBT`'s real book is
explicitly asserted not to throw**, with the reasoning in the test body so the
next person to "simplify" it back to a `Money` comparison sees what breaks.

**THE LESSON, and it is the portable one.** *A safety check built and verified
against one venue's typical price ranges can misfire silently on another venue's
real data, without either the check or the data being wrong.* Gemini's
implementation is correct on Gemini — no Gemini symbol prices below the money
scale, so the rounding is never lossy there. Nothing about the check was
carelessly written; the implicit assumption was simply *"prices have at most 8
significant decimals"*, which was true of every payload it had ever seen. **This
was caught by running the detector against Kraken's actual prices rather than
assuming it generalised** — the same discipline entry 91 PART 5 applied to
`tick_size` and PART 7 to `pair_decimals`, arriving at the same kind of answer.

## PART 4 — THE `selectPairResult` GAP, FOUND BY THE TEST NOBODY THOUGHT WORTH WRITING

`catalogue.ts`'s `selectPairResult` resolves the key of a Kraken reply — every one
of which is keyed by a name the client did not choose (entry 90 PROBLEM 1). It
tries the canonical name, then the altname, and **if neither matches and the map
holds exactly one entry, returns that entry marked `sole-key`.** That fallback is
entry 90's own *"or read the single key out of the map"*, and `catalogue.ts`
reports **how** it matched precisely so each caller can set its own bar.

The test being written was housekeeping: *a request for a pair that is not in the
result should throw.* It was expected to pass on the first run.

**It failed, and the code was wrong.** The map was `{BONKUSD: [...], last: ...}`,
the request was for `ETHBTC`. `parseCandles` strips `last` first (it must — see
below), which leaves a **one-entry map**, which fires the sole-key fallback, which
hands **BONKUSD's candle array back as ETHBTC's candles**. No error, no warning,
plausible-looking data under the wrong name. That is entry 89 PART 5's *"silently
routing an order into the wrong version of a market"* arriving through the front
door, in the module whose entire premise is that Kraken's names must never be
guessed at.

**FIXED, in `parse.ts`, not in `catalogue.ts`.** `requireIntendedPair` narrows the
fallback: **if the sole key resolves to a pair, it must be the pair that was
requested**; if it resolves to nothing, that is the unrecognised-name case the
fallback was written for and it is still accepted. `catalogue.ts` is deliberately
left alone — `selectPairResult` reports `matchedBy` so that an order path can
insist on `canonical` while a ticker read accepts `sole-key`, and turning that
report into a refusal would take the choice away from every caller at once. The
guard is applied to both `parseCandles` and `parseTickerResult`, and both the
refusal and the still-accepted unrecognised-key case are tested.

**Why `last` has to be stripped first**, since it is what exposed this: leaving it
in means the map always holds at least two entries, so the sole-key fallback can
**never** fire and a reply keyed by a name the catalogue cannot place is refused
outright. Stripping restores the fallback entry 90 explicitly allows; narrowing it
is what makes the restoration safe.

**THE LESSON.** *The "obviously correct" case is exactly where a boundary
condition hides, because nobody writes a targeted test for a case they assume
cannot fail.* This bug survived writing `catalogue.ts`, writing its 45 tests,
writing `parse.ts`, and reading both — and it fell out of a throwaway assertion
about a shape nobody was interested in. It is the same shape as entry 91's
leading-zero inversion: **caught by a test failing, not by inspection**, which had
already passed over it.

## PART 5 — DECISION: `"6h"` IS `null` IN A **TOTAL** RECORD, NOT AN OMITTED KEY

Entry 90 recorded the problem and left it open: Kraken's OHLC intervals are 1, 5,
15, 30, 60, 240, 1440, 10080, 21600 minutes — **240 then 1440, nothing between** —
while `CandleInterval` is a closed union that includes `"6h"`. So *"a Kraken
timeframe table cannot be a total `Record<CandleInterval, …>` without inventing
one."*

**There is no existing convention for this, and that was checked rather than
assumed.** `GEMINI_TIMEFRAMES` and Binance's pass-through are both total because
both venues support all seven intervals. The only `Partial<Record<…>>` in the
repository is in `reconcile.ts:971`, and it is a **lookup table** — keys present
where data exists — not a **capability table** asserting what a venue supports.
Different purpose; not a precedent.

Live confirmation that this is not pedantry: `GET /0/public/OHLC?pair=XBTUSD&interval=360`
answers `{"error":["EGeneral:Invalid arguments"]}`. Kraken refuses it too, just
later and less clearly.

**DECIDED: a total `Readonly<Record<CandleInterval, KrakenTimeframe | null>>` with
`"6h": null`, read through a `krakenTimeframe()` accessor that throws a
`ParseError` naming the interval and what the venue actually offers.**

**Rejected: `Partial<Record<CandleInterval, KrakenTimeframe>>`, omitting the key.**
It drops the compile-time forcing function. Adding an interval to
`CandleInterval` would leave every venue's table silently incomplete instead of
breaking the build — and being a closed union that the code must handle
exhaustively is the entire reason `CandleInterval` and `SymbolStatus` are declared
the way they are.

**Rejected outright: map `"6h"` onto 240 or 1440 minutes.** It answers a request
for six-hour candles with four-hour or daily ones and the caller cannot tell. A
wrong number wearing the right label.

The chosen shape keeps totality — a new `CandleInterval` still fails to compile
until Kraken's answer for it is written down — and states the absence **in the
data** rather than hiding it in the type. Only `"1m"` is exercised in v1 (the
price feed's gap-backfill, section 4.6); the rest are the declared extension
surface for section 13's backtest and remain unverified against the live
endpoint, exactly as on the other two venues.

## PART 6 — FIXTURE PROVENANCE, AND THE HALF THAT IS NOT LIVE

The test file states this at its head and it is repeated here so a future reader
does not have to open the tests to find out. **The two halves are not equally
trustworthy and are not presented as though they were.**

**PULLED LIVE from `api.kraken.com` on 2026-09-03, verbatim, HTTP 200 on every
one:**

- `GET /0/public/AssetPairs?pair=XBTUSD,BONKUSD,ANKRXBT,ETHXBT` and
  `GET /0/public/Assets?asset=XXBT,ZUSD,BONK,ANKR,XETH` — the catalogue the tests
  build on. One edit only, matching `catalogue.test.ts` and `filters.test.ts`: the
  `fees`, `fees_maker`, `leverage_buy` and `leverage_sell` arrays are dropped.
  Nothing this module reads is touched.
- `GET /0/public/OHLC?pair=XBTUSD&interval=1` and the same for `BONKUSD` — rows
  and the `last` sibling exactly as returned, only the row **count** trimmed.
- `GET /0/public/Ticker` for `XBTUSD`, `BONKUSD` and `ANKRXBT` — the last of which
  is PART 3's whole argument.
- `GET /0/public/Time`.
- **The error strings**: `EQuery:Unknown asset pair`, `EAPI:Invalid key`,
  `EGeneral:Unknown method`, `EGeneral:Invalid arguments`. Every one arrived over
  **HTTP 200**, which is the confirmation entry 90 PROBLEM 3 rests on.

**FROM KRAKEN'S PUBLISHED API REFERENCE, NOT LIVE CAPTURES:** `AddOrder`,
`QueryOrders`, `BalanceEx`, `QueryTrades`, `CancelOrder`. **No Kraken credentials
exist yet**, so no private endpoint could be called during this build. These are
Kraken's own documented example responses, and they are **documentation, not
observed behaviour** — the same gap entry 91 PART 2 turned into a general warning
about treating a supplied example as a claim to verify. A field Kraken documents
but renders differently in practice would not be caught by these tests.

**CONSTRUCTED, AND LABELLED AT THE POINT OF USE:** the crossed book (the live
`XBTUSD` ticker with `a` and `b` swapped), the negative balance, and the
unrecognised order statuses. None can be requested on demand. This is the same
treatment `filters.test.ts` gives `limit_only` and `reduce_only`, and for the same
reason entry 91 gave: **a fixture posing as pulled data teaches the wrong shape
next time.**

**What this means for `client.ts`.** Every private-endpoint parser in this file is
correct against Kraken's documentation and **unverified against Kraken**. The
first real credentialled call is where that gets settled, and it should be treated
as a verification step with expected findings, not as a formality.

   Kraken files belongs here too.
3. **The rate-limiter redesign, as its own separate and later effort.** Entry 90
   PROBLEM 2 and PART 6 recommended this ordering explicitly and it is not being

   venue-agnostic weight-table bug, where `RateLimitedExchange` gates **every**
   venue with Binance's table because no call site passes `weights` — **is still
   outstanding and still live**, and remains a prerequisite for it.

Also still outstanding from entry 90 and now partly answered: the 6-hour interval
gap is **resolved for the parse layer** by PART 5 above, but `client.ts` must

throws, and whether that surfaces as an `#unreadable` failure or as a refusal
before the request is a client-level choice, not a parser one.
