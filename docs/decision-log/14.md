### The correction that reframed everything: outbound WebSockets do not hibernate

Section 4.6 says to "maintain the exchange price feed connection inside the
relevant Durable Object using the WebSocket Hibernation API," and step 6 question
3 and step 13 both inherited that premise, framing the work as *redesigning the
section 4.1 callback closure around `ctx.acceptWebSocket()` + `webSocketMessage`
handlers so the socket survives eviction*. That premise is wrong, and it was
verified against the current Cloudflare documentation before any design was built
on it, precisely because the whole redesign hung on it:

> "Hibernation is only supported when a Durable Object acts as a WebSocket
> server. Outgoing WebSockets do not hibernate."
>
> "an active outbound WebSocket connection keeps the Durable Object alive and
> prevents eviction for up to 15 minutes per connection."

The exchange feed is an **outbound** connection — our object dials *out* to the
exchange. So:

- **Hibernation does not apply to it at all.** `ctx.acceptWebSocket()` /
  `webSocketMessage` are server-side only; they exist so a DO can sleep while
  *inbound clients* stay connected, and they cannot adopt an outbound socket. The
  interface shape step 6 and step 13 assumed we would build toward is not
  available for this socket.
- **The constraint is the inverse of what the spec assumed.** An active outbound
  socket *pins the DO in memory* — no eviction — for up to ~15 minutes per
  connection, after which the object can be evicted and the socket dropped. There
  is no hibernating-socket state to preserve a closure across; there is a live
  connection that periodically dies and must be re-established.

This does not kill the design — it simplifies the interface question (nothing is
"adopted," no handler is registered for hibernation) and sharpens the reconnect
question (a forced ~15-minute teardown is now a normal, expected event, not an
error path). It is recorded here as a **deviation from section 4.6**: the feed is
NOT built on the Hibernation API, because that API does not cover the outbound
case section 4.6 describes. See deviations below.

### The five decisions

**1. Topology: one shared `PriceFeed` Durable Object per (exchange, pair), not a
socket per bot.** *(recommended, confirmed)*

The step-13 note leaned toward a shared feed to avoid redundant connections; the
hibernation correction makes it decisive rather than merely preferable. Under
per-bot sockets, *every* BotInstance holding an outbound feed would be pinned in
memory continuously (an outbound socket prevents eviction while open), each would
independently hit the ~15-minute ceiling and reconnect, and each would
independently fire a REST gap-backfill on every reconnect. N bots on one pair = N
pinned objects, N sockets, N reconnect cycles, N backfill storms. The shared feed
collapses that to exactly one pinned object, one socket, one reconnect cycle, one
backfill per (exchange, pair), and leaves every BotInstance free to evict normally
— woken only by an RPC when a price actually arrives.

**Keyed by (exchange, pair), not (account, pair)** — a refinement of step 13's
framing. Market data on both exchanges is public and unauthenticated, so the
stream is identical regardless of which account watches it; account is not part of
a price stream's identity, the exchange is. Two accounts on Gemini BTCUSD share
one feed named `gemini:BTCUSD`. A consequence worth having: the feed carries no
credentials and touches no funds — it never calls `resolveExchangeForAccount` and
reads no secret.

*A socket per bot — rejected*, per the above; the hibernation correction turned
its cost from "redundant" to "every bot permanently pinned in memory."

*Keying per (account, pair) — rejected*: it would open duplicate identical
sockets for two accounts watching the same market, for no isolation benefit, since
the data is public.

*A single per-exchange socket multiplexing all pairs — noted, deferred.* Gemini's
v2 marketdata can subscribe to many symbols on one connection, so this is possible
and would reduce connections further. Per-(exchange, pair) is chosen for v1
because independent backfill windows, staleness tracking and blast radius are
simpler to reason about per pair; consolidation is a future option if the active
pair count grows.

**Subscribe on entering `running`, unsubscribe on leaving it** — the invariant,
owned by whatever writes the status transition. `start()` (created→running) and
`resume()` (halted→running) call `PRICE_FEED.getByName(key).subscribe(ownId)`;
`#halt`, stop, and a DCA take-profit that halts call `unsubscribe(ownId)`. A DCA
bot that auto-restarts stays `running` and stays subscribed. The subscriber set is
durable (SQLite, survives eviction) and both calls are idempotent, so a redelivered
transition cannot corrupt it. First subscriber opens the socket and arms the alarm;
emptying the set closes the socket and deletes the alarm.

Honest cost of the shared feed, stated: a new component, a new failure domain, and
cross-bot coupling — all bots on a pair go blind together if the feed dies.
Mitigations: `onPriceUpdate` already self-guards on status (a stale subscriber is
harmless); the feed alerts on give-up (decision 5); reconciliation is the backstop.

**2. Interface redesign: no closure crosses a boundary; nothing is adopted.**
*(recommended, confirmed)*

Step 6 was right that a callback closure cannot survive eviction — but the fix is
not hibernation handlers (unavailable here). The fix is that **no closure is
passed in at all**, and the socket's message listener is recreated by the object
itself on every connect, which is safe because the outbound socket pins the object
in memory for as long as it is open.

- **Delete `subscribeToPriceFeed` and `WebSocketHandle` from the shared
  interface.** `ExchangeClient` collapses into `RestExchangeClient`. This is the
  hard-to-reverse change, and it is a *deletion* — the callback shape ceases to
  exist anywhere rather than being reshaped.
- **New `PriceFeed` DO** owns the socket lifecycle internally: `#ensureConnected()`
  does `fetch(url, { headers: { Upgrade: "websocket" }})`, `ws.accept()`, then
  attaches `message`/`close`/`error` listeners — the ordinary outbound WebSocket
  API, NOT `acceptWebSocket`. The listener is an internal method-bound handler,
  never injected.
- **New per-exchange `PriceFeedCodec` (pure, stateless)**, mirroring the existing
  per-exchange `parse.ts` split: `socketUrl(env)`, `subscribeMessage(pair)`,
  `parseMessage(raw) -> Candle[]`. Keeping it pure keeps exchange specifics
  testable and out of the object, exactly as `parse.ts` already does for REST.
- **BotInstance receives updates through its existing `onPriceUpdate(price)` RPC**
  — no new receive path, no closure. The subscription IS durable data (DO id
  strings) plus RPC fan-out: on a closed candle the feed iterates its subscriber
  set and calls each `BOT_INSTANCE.get(idFromString(id)).onPriceUpdate(price)`,
  concurrently with `allSettled` so one slow or throwing bot cannot stall the rest
  (and `onPriceUpdate` already returns `ignored` for a non-running bot).

Why this is the right shape: the two things that must survive eviction — the
subscriber list and the candle watermark — are durable storage, reconstructed on
wake; the one thing that cannot — the live socket and its listener — is rebuilt by
the object on every (re)connect, driven by its alarm. Nothing external ever holds
a closure.

**3. Candle → Price: the closed 1-minute candle's close price.** *(recommended,
confirmed; ~1-minute stop-loss lag accepted for v1)*

The feed forwards a `Price` to `onPriceUpdate` only when a candle is *closed*
(`closed === true`), dropping in-progress updates. `Price.price = candle.close`;
`Price.at =` feed receipt time (matching `getCurrentPrice`'s "when we heard"
semantics, which is what section 5.6's freshness check needs — not the candle's
own `closeTime`).

Reasoning: section 1 states the system is explicitly not latency-sensitive; the
`Candle.closed` field's own comment says strategy logic "generally acts only on
closed ones"; and section 13's backtest feeds historical *closed* candles through
the same strategy code — so using closed candles live means the live and backtest
inputs are the same shape and cadence, with no second reality for the strategy to
behave differently in. It also bounds fan-out to one RPC per subscriber per
minute, where a trade/ticker stream would fire many RPCs per second into every
subscriber object and run a full strategy pass on each.

**The consequence, stated plainly:** a bot reacts up to ~1 minute after a real
move, and a stop-loss can be up to one candle late. Accepted for v1 as consistent
with section 1. It lands hardest on the stop-loss, which is the one place latency
has teeth.

*A last-trade / ticker stream — rejected* for v1: near-real-time, but a
high-frequency fan-out into every subscriber object, noisier, and a mismatch with
the backtest's candle input.

*Fast-path deferred, not discarded.* If the ~1-minute stop-loss lag proves too
slow during the section 17 testnet period, the clean extension — without
disturbing the candle-driven main cadence — is a trade-stream fast-path used
*only* for the stop-loss threshold check: the feed carries both, forwarding closed
candles as the strategy clock and trade prices only to a lighter "has the stop
been breached" check. Not built now; recorded so it is not painted over.

**4. Gemini's WebSocket is built and verified first; Binance is not.**
*(confirmed)*

Two reasons, one absolute. Binance is unreachable from the Cloudflare edge at all
— step 3.3 saw HTTP 451 (geo-block) live, and a Binance WS from a Worker/DO fails
for the identical reason its REST does, so there is nothing to test. And Gemini's
WS is completely unbuilt while its market data is public/unauthenticated — the
feed needs no signing, no clock-drift handling, no credential resolution, making
it the simplest possible first real socket.

**What Binance's WS needs later, without building it now:** only a
`BinancePriceFeedCodec` (URL, subscribe message, kline parse) — the object, the
alarm loop, the backfill and the fan-out are all exchange-agnostic. But that codec
is the easy tenth: Binance WS is blocked on the *same* reachability problem as
Binance REST — the section 4.4 / section 12 relay/VPS with a static, non-geo-blocked
IP. So Binance WS is not gated on this feed design; it is gated on the infra
decision that already gates Binance REST, and building the codec before that is
solved would produce a component that cannot connect. Because the Candle→Price
contract is normalised in the codec, Gemini-first locks nothing Binance-specific
into the feed object.

**5. Reconnect-with-backoff, gap-backfill, and keep-alive are driven by one
multiplexed alarm; `getCandles` is added to the REST interface; the blind-feed
policy is alert-only with a 30-minute severity escalation.** *(recommended,
confirmed with one operator addition)*

A correction first: **DO alarms are not currently used anywhere in this project.**
No object has an `alarm()` method; this project's scheduled work is cron-trigger
Workers (reconciliation's `scheduled` handler). The alarm here is therefore a NEW
mechanism for this codebase, not the existing one — but it is the right one, since
a cron worker cannot target one feed object's reconnect. Recorded so "the
mechanism this project already uses" is not asserted where it is not true.

Critical constraint: **one alarm per DO** (`setAlarm` replaces any existing one),
so heartbeat and backoff-reconnect must be multiplexed into a single alarm whose
next-fire time is computed from current state.

- `#ensureConnected()` — on first subscribe and on every alarm wake: if there is
  no live in-memory socket, open it, `accept()`, attach listeners, send the
  subscribe message, reset `reconnectAttempts = 0`, record `connectedAt`.
- **Heartbeat** — while connected, re-arm the alarm for `now + HEARTBEAT` (~30–60s,
  under the ~15-minute ceiling and short enough to notice a dead feed). On wake:
  if the socket is gone (the object was evicted at the ceiling and the in-memory
  socket vanished) or stale (no message within a threshold), treat as a disconnect
  and reconnect. This is how the design survives the no-hibernation reality:
  eviction drops the socket, the alarm wakes the evicted object, it reconnects and
  backfills.
- **Backoff (section 4.6, 5 attempts)** — on `close`/`error`, set the alarm to
  `now + base·2^k` (capped), k up to 5. After 5 failures: stop the fast cycle,
  fire a `system` alert through the existing alerts path, and keep a slow retry
  alarm (~60s) alive so a longer outage self-heals rather than the feed dying
  silently.
- **REST gap-backfill on reconnect (section 4.6)** — on every successful
  (re)connect, if `lastCandleCloseTime` exists, fetch the missed *closed* candles
  from `lastCandleCloseTime → now` and push each through the same fan-out path, in
  order, before live resumes; dedup by `closeTime` so the overlap between backfill
  and the first live candle is not delivered twice. For 1-minute candles across a
  short reconnect this is a handful of candles.

**`getCandles` added to `RestExchangeClient` now.** The backfill needs historical
klines, and the interface has no such method today (verified — nothing anywhere
fetches candles). New method
`getCandles(pair, interval, sinceCloseTime): Promise<ExchangeOutcome<Candle[]>>`,
implemented for Gemini, public/unsigned like the socket. It is shared, not
feed-only: section 13 (backtest) and section 8.4 (R2 klines cache) both require
it. The feed uses an unauthenticated REST client for it, keeping the feed
credential-free.

**Blind-feed policy — alert-only + slow retry, with a 30-minute severity
escalation** *(the operator's addition to the recommendation)*. When the feed
exhausts its 5 fast attempts or an outage runs long, subscribed bots receive no
prices; section 5.6 correctly stops them acting on silence, which also means
stop-losses do not evaluate while the feed is blind. The policy is NOT to halt
subscribers — section 7.5 is about a bot's own errors, and halting every bot on a
transient exchange-side outage is heavy-handed and itself disruptive. Instead:
alert on give-up and keep slow-retrying, AND **escalate the alert's severity (not
force a halt) once the feed has been blind for longer than 30 minutes**, so a
genuinely extended outage grows louder over time rather than remaining a single
quiet alert forever. The escalation is a severity bump on a re-fired alert, driven
by the same alarm that is already retrying.

*Escalating to halt subscribers — rejected*, per the above, but recorded as the
alternative because a prolonged blind feed genuinely means unmonitored
stop-losses; the 30-minute severity escalation is the chosen middle path.

### Deviations from the spec / prior entries

- **Section 4.6's "using the WebSocket Hibernation API" is not followed**, because
  that API does not cover the outbound connection section 4.6 describes (the
  correction above). The feed uses the ordinary outbound WebSocket API; the socket
  pins the object in memory rather than hibernating, and an alarm handles the
  ~15-minute teardown and reconnect. This is the most consequential deviation in
  the session and the reason it was design-first.
- **Section 4.1's interface changes shape.** `subscribeToPriceFeed` and
  `WebSocketHandle` are deleted; `ExchangeClient` collapses into
  `RestExchangeClient`; and `getCandles` is added. Step 6 question 3 and step 13
  anticipated the deletion; the addition is new here.
- **Step 6 question 3's framing is superseded.** It diagnosed the closure as
  needing `acceptWebSocket` + `webSocketMessage` handlers. Correct that the
  closure cannot survive eviction; wrong that hibernation handlers are the answer,
  since they do not apply to outbound sockets. The answer is decision 2: no
  closure is injected, and the listener is rebuilt on every connect.
- **DO alarms are new to this project** (decision 5). Prior scheduled work is
  cron-trigger Workers.

### Flagged uncertainties — verify at Tier 0, do not assume

1. **Exact Gemini v2 marketdata wire framing** — candle message shape, whether it
   emits an in-progress candle versus only closed, whether it replays recent
   candles on subscribe. Confident it is public, that v2 supports `candles_1m` and
   a trade feed, and that the sandbox is `wss://api.sandbox.gemini.com/v2/marketdata`
   — but the wire shapes are confirmed against the real sandbox before the codec is
   trusted, the same read-only-first discipline as every prior exchange check
   (step 3.3, step 3.4, step 13's tiered plan).
2. **Whether ~15 minutes is a hard eviction ceiling or an upper bound** that can
   fire sooner under memory pressure. The design tolerates either (alarm +
   backfill), but the actual reconnect cadence should be observed, not assumed.

### Open questions carried forward

Everything the prior list carries, plus, new to this design:

1. **A prolonged blind feed means unmonitored stop-losses** (decision 5). The
   chosen policy alerts and escalates severity at 30 minutes but does not halt.
   The section 17 testnet period is where an induced feed outage should be watched
   to confirm the escalation fires and the alert actually reaches a human.
2. **The Gemini v2 wire framing is unverified** (uncertainty 1). The codec cannot
   be trusted until Tier 0 observes the real sandbox messages.
3. **`getCandles` is specified but unbuilt**, and it is now a dependency of the
   feed, the backtest (section 13) and the R2 cache (section 8.4) alike — three
   callers for one method, which argues for building it as shared REST
   infrastructure rather than inside the feed.

## Step 14 — Gemini WebSocket reachability probe (pre-Session-A gate)
Date: 2026-07-29

Before any build, the throwaway local probe (`scripts/verify-gemini-ws.ts`,
git-ignored, same convention as `verify-gemini.ts`) was run against
`wss://api.sandbox.gemini.com/v2/marketdata`. **PASS.** It settled the two
design-critical facts uncertainty 1 flagged:

- The message type is **`candles_1m_updates`**, carrying a `changes` array of
  `[timeMs, open, high, low, close, volume]` rows. On subscribe, Gemini sends a
  large historical batch (~1441 rows in the run), then live updates. **Heartbeat**
  messages also arrive.
- There is **no `closed` flag**. Closure is inferable ONLY by a newer candle
  timestamp appearing — a real rollover was observed live during the 90-second
  window, and the most recent candle updates in place until then. This confirms
  the codec's closure-by-timestamp inference (decision 3) is the only option, and
  it is sound.
- OHLCV values arrive as **JSON numbers** (`63610.21`), not the decimal strings
  the rest of Gemini's API uses. This is what forced the Session A money-boundary
  decision below; it was discovered here, not guessed.

**Scope of the PASS, stated honestly:** this ran on a LOCAL machine, so it proves
the wire shapes and that Gemini's sandbox WS accepts a connection — it does NOT
prove Cloudflare-edge reachability (the 451 risk that killed Binance is
edge-IP-specific and invisible from local Node). Edge reachability (step 13
Tier 0 / step 11 open Q4) stays the separate open gate that must be cleared before
Session C's Durable Object is trusted in a deployed environment.

## Step 14.1 (Session A) — the exchange-interface reshape + `getCandles`
Date: 2026-07-29

The first build session of the price-feed arc, and deliberately the contained,
no-new-component half — the same "smaller, low-risk piece first" ordering step 13
used for attachment. It reshapes the REST interface into its feed-era form and
adds the historical-candle read, all inside the automated suite with no live call,
no Durable Object, no binding, and no migration. The `PriceFeed` object, the
codec, and the bot wiring are the later sessions (B, C, D) proposed for this arc.

### What was built

- **`src/shared/exchange-client.ts`** — deleted `WebSocketHandle`,
  `subscribeToPriceFeed`, and the `ExchangeClient extends RestExchangeClient`
  block; `RestExchangeClient` is now the whole interface. Added a `CandleInterval`
  union and a `getCandles(pair, interval, since?)` method. `Candle` stays (now
  consumed by `getCandles` rather than the deleted feed callback).
- **Gemini** (`gemini/client.ts` + `gemini/parse.ts`) — `getCandles` as an
  unsigned `GET /v2/candles/:symbol/:timeframe`, plus `parseCandles` and a
  `GEMINI_TIMEFRAMES` map.
- **Binance** (`binance/client.ts` + `binance/parse.ts`) — `getCandles` as
  `GET /api/v3/klines`, plus `parseKlines` and a `klines` weight in
  `ENDPOINT_WEIGHTS`.
- **`rate-limited.ts`** — delegating `getCandles`; `BINANCE_METHOD_WEIGHTS` gained
  its entry (the `Record<keyof RestExchangeClient, number>` type forced this — the
  intended compiler guard fired).
- **`fake-exchange.ts`** — a `getCandles` returning canned candles for tests.
- Stale doc/comment references to `subscribeToPriceFeed` / `ExchangeClient` /
  "hibernation" updated across both client headers, `bot-instance.ts`, and the
  `exchange`, `durable-objects`, and `shared` READMEs.
- Tests: `parseCandles`/`parseKlines` unit tests and client `getCandles` tests
  (mocked `fetch`) for both exchanges.

**1260 tests pass** (up from 1247), typecheck clean. The one miniflare
worker-teardown error on close is the same pre-existing artifact steps 11–13
recorded, unrelated to this change.

### Decisions made (the three confirmed up front, plus one the probe forced)

**1. `getCandles(pair, interval, since?)` returns candles OLDEST-FIRST, each with
`closed` derived from `closeTime <= at`.** *(confirmed up front)*

REST gives no closed flag on either venue (the probe confirmed it for Gemini's
feed, and Binance's klines are the same in spirit), so closure is derived from
whether the candle's close time has passed at request time. The current
in-progress candle comes back `closed: false`; a backfill consumer drops it. Both
implementations sort ascending rather than trusting the venue's ordering (Gemini
sends newest-first).

**2. `CandleInterval` is the small common union, but only `"1m"` is exercised.**
*(confirmed up front)*

`"1m" | "5m" | "15m" | "30m" | "1h" | "6h" | "1d"`, following the `SymbolStatus`
precedent of declaring the whole closed set even when only one member is acted on.
Gemini's spelling for the three longest (`"1hr"/"6hr"/"1day"`) is mapped in
`GEMINI_TIMEFRAMES`; Binance's spelling matches the canonical form for every
value, so it passes straight through. Only `"1m"` — what the feed's gap-backfill
needs — is verified; the rest are the declared extension surface for section 13,
unverified against either live endpoint.

**3. `since` is BEST-EFFORT and window-bounded, and the two venues differ.**
*(confirmed up front — the one consequential asymmetry)*

Gemini's `/v2/candles` takes no time-range parameter and returns a fixed recent
window, so the Gemini client filters `closeTime > since` locally and CANNOT serve
candles older than that window. Binance's klines takes `startTime`, so `since` is
pushed to the exchange AND filtered locally for an exact boundary. This asymmetry
is documented on the interface itself, not hidden. For the feed's short reconnect
gaps the Gemini window always covers the miss; Gemini deep-history is a section 13
backtest open question, not something `getCandles` promises.

**4. Gemini candle OHLCV are JSON NUMBERS, so they are rounded EXPLICITLY to the
money scale — the one number→Money boundary in the codebase.** *(forced by the
probe, not anticipated in the design)*

Everywhere else Gemini sends monetary values as decimal strings that go straight
into `fromDecimalString` with no `Number(...)` anywhere — the section 5.2 guard.
Candles are the documented exception the probe surfaced: `/v2/candles` (and the
live feed) render OHLCV as JSON numbers, with no string form to reach for.
`candleMoney` in `gemini/parse.ts` converts via `value.toFixed(SCALE)` — which IS
the "rounding must be explicit" `fromDecimalString` demands, applied at the one
boundary that forces it, and which also removes the scientific notation
`String(1e-7)` would produce. This is acceptable precisely because a candle drives
strategy DECISIONS (compare a close to a grid level), never settlement arithmetic:
a candle value is never summed into a balance. Binance renders klines as strings,
so `parseKlines` stays on the ordinary string path with no number boundary — the
exception is Gemini-specific and contained to its parser.

### Deviations from the spec / prior entries

- **Section 4.1's interface changed shape**, as step 14's design set out:
  `subscribeToPriceFeed` / `WebSocketHandle` deleted, `getCandles` added.
- **The Binance `klines` weight (2) is from published docs, unmeasured**, and
  doubly unverifiable because Binance is geo-blocked from this infrastructure
  (step 3.3) — the same standing caveat as every Binance figure (section 17
  amendment). It is wired into `BINANCE_METHOD_WEIGHTS` so the rate limiter gates
  candle reads, but the number itself is untested against the real venue.
- **No live call anywhere in the suite**, per section 14. The Gemini candle path
  is verified against the real sandbox at the feed arc's Tier 0, not here.

### Open questions carried forward (new to Session A)

1. **Gemini deep-history for section 13's backtest** (decision 3). `getCandles`
   on Gemini cannot reach past its fixed recent window; a backtest wanting older
   candles needs another source (R2 cache seeded differently, or a different
   endpoint) — a section 13 problem, flagged here so it is not discovered inside a
   backtest session.
2. **The Binance klines weight and the whole Binance candle path are unverified**
   against the real venue (geo-blocked). They compile and are unit-tested against
   mocked responses only.
3. **The wider `CandleInterval` members are declared but unexercised** — each needs
   per-venue verification before section 13 relies on it.
