### The correction that reframed everything: outbound WebSockets do not hibernate

Section 4.6 says to "maintain the exchange price feed connection inside the
relevant Durable Object using the WebSocket Hibernation API," and step 6 question
3 and step 13 both inherited that premise, framing the work as *redesigning the
section 4.1 callback closure around `ctx.acceptWebSocket()` + `webSocketMessage`
handlers so the socket survives eviction*. That premise is wrong, and it was
verified against the current Cloudflare documentation before any design was built
on it, precisely because the whole redesign hung on it:

> "Hibernation is only supported when a Durable Object acts as a WebSocket
> server. Outgoing WebSockets do not hibernate."
>
> "an active outbound WebSocket connection keeps the Durable Object alive and
> prevents eviction for up to 15 minutes per connection."

The exchange feed is an **outbound** connection — our object dials *out* to the
exchange. So:

- **Hibernation does not apply to it at all.** `ctx.acceptWebSocket()` /
  `webSocketMessage` are server-side only; they exist so a DO can sleep while
  *inbound clients* stay connected, and they cannot adopt an outbound socket. The
  interface shape step 6 and step 13 assumed we would build toward is not
  available for this socket.
- **The constraint is the inverse of what the spec assumed.** An active outbound
  socket *pins the DO in memory* — no eviction — for up to ~15 minutes per
  connection, after which the object can be evicted and the socket dropped. There
  is no hibernating-socket state to preserve a closure across; there is a live
  connection that periodically dies and must be re-established.

This does not kill the design — it simplifies the interface question (nothing is
"adopted," no handler is registered for hibernation) and sharpens the reconnect
question (a forced ~15-minute teardown is now a normal, expected event, not an
error path). It is recorded here as a **deviation from section 4.6**: the feed is
NOT built on the Hibernation API, because that API does not cover the outbound
case section 4.6 describes. See deviations below.

### The five decisions

**1. Topology: one shared `PriceFeed` Durable Object per (exchange, pair), not a
socket per bot.** *(recommended, confirmed)*

The step-13 note leaned toward a shared feed to avoid redundant connections; the
hibernation correction makes it decisive rather than merely preferable. Under
per-bot sockets, *every* BotInstance holding an outbound feed would be pinned in
memory continuously (an outbound socket prevents eviction while open), each would
independently hit the ~15-minute ceiling and reconnect, and each would
independently fire a REST gap-backfill on every reconnect. N bots on one pair = N
pinned objects, N sockets, N reconnect cycles, N backfill storms. The shared feed
collapses that to exactly one pinned object, one socket, one reconnect cycle, one
backfill per (exchange, pair), and leaves every BotInstance free to evict normally
— woken only by an RPC when a price actually arrives.

**Keyed by (exchange, pair), not (account, pair)** — a refinement of step 13's
framing. Market data on both exchanges is public and unauthenticated, so the
stream is identical regardless of which account watches it; account is not part of
a price stream's identity, the exchange is. Two accounts on Gemini BTCUSD share
one feed named `gemini:BTCUSD`. A consequence worth having: the feed carries no
credentials and touches no funds — it never calls `resolveExchangeForAccount` and
reads no secret.

*A socket per bot — rejected*, per the above; the hibernation correction turned
its cost from "redundant" to "every bot permanently pinned in memory."

*Keying per (account, pair) — rejected*: it would open duplicate identical
sockets for two accounts watching the same market, for no isolation benefit, since
the data is public.

*A single per-exchange socket multiplexing all pairs — noted, deferred.* Gemini's
v2 marketdata can subscribe to many symbols on one connection, so this is possible
and would reduce connections further. Per-(exchange, pair) is chosen for v1
because independent backfill windows, staleness tracking and blast radius are
simpler to reason about per pair; consolidation is a future option if the active
pair count grows.

**Subscribe on entering `running`, unsubscribe on leaving it** — the invariant,
owned by whatever writes the status transition. `start()` (created→running) and
`resume()` (halted→running) call `PRICE_FEED.getByName(key).subscribe(ownId)`;
`#halt`, stop, and a DCA take-profit that halts call `unsubscribe(ownId)`. A DCA
bot that auto-restarts stays `running` and stays subscribed. The subscriber set is
durable (SQLite, survives eviction) and both calls are idempotent, so a redelivered
transition cannot corrupt it. First subscriber opens the socket and arms the alarm;
emptying the set closes the socket and deletes the alarm.

Honest cost of the shared feed, stated: a new component, a new failure domain, and
cross-bot coupling — all bots on a pair go blind together if the feed dies.
Mitigations: `onPriceUpdate` already self-guards on status (a stale subscriber is
harmless); the feed alerts on give-up (decision 5); reconciliation is the backstop.

**2. Interface redesign: no closure crosses a boundary; nothing is adopted.**
*(recommended, confirmed)*

Step 6 was right that a callback closure cannot survive eviction — but the fix is
not hibernation handlers (unavailable here). The fix is that **no closure is
passed in at all**, and the socket's message listener is recreated by the object
itself on every connect, which is safe because the outbound socket pins the object
in memory for as long as it is open.

- **Delete `subscribeToPriceFeed` and `WebSocketHandle` from the shared
  interface.** `ExchangeClient` collapses into `RestExchangeClient`. This is the
  hard-to-reverse change, and it is a *deletion* — the callback shape ceases to
  exist anywhere rather than being reshaped.
- **New `PriceFeed` DO** owns the socket lifecycle internally: `#ensureConnected()`
  does `fetch(url, { headers: { Upgrade: "websocket" }})`, `ws.accept()`, then
  attaches `message`/`close`/`error` listeners — the ordinary outbound WebSocket
  API, NOT `acceptWebSocket`. The listener is an internal method-bound handler,
  never injected.
- **New per-exchange `PriceFeedCodec` (pure, stateless)**, mirroring the existing
  per-exchange `parse.ts` split: `socketUrl(env)`, `subscribeMessage(pair)`,
  `parseMessage(raw) -> Candle[]`. Keeping it pure keeps exchange specifics
  testable and out of the object, exactly as `parse.ts` already does for REST.
- **BotInstance receives updates through its existing `onPriceUpdate(price)` RPC**
  — no new receive path, no closure. The subscription IS durable data (DO id
  strings) plus RPC fan-out: on a closed candle the feed iterates its subscriber
  set and calls each `BOT_INSTANCE.get(idFromString(id)).onPriceUpdate(price)`,
  concurrently with `allSettled` so one slow or throwing bot cannot stall the rest
  (and `onPriceUpdate` already returns `ignored` for a non-running bot).

Why this is the right shape: the two things that must survive eviction — the
subscriber list and the candle watermark — are durable storage, reconstructed on
wake; the one thing that cannot — the live socket and its listener — is rebuilt by
the object on every (re)connect, driven by its alarm. Nothing external ever holds
a closure.

**3. Candle → Price: the closed 1-minute candle's close price.** *(recommended,
confirmed; ~1-minute stop-loss lag accepted for v1)*

The feed forwards a `Price` to `onPriceUpdate` only when a candle is *closed*
(`closed === true`), dropping in-progress updates. `Price.price = candle.close`;
`Price.at =` feed receipt time (matching `getCurrentPrice`'s "when we heard"
semantics, which is what section 5.6's freshness check needs — not the candle's
own `closeTime`).

Reasoning: section 1 states the system is explicitly not latency-sensitive; the
`Candle.closed` field's own comment says strategy logic "generally acts only on
closed ones"; and section 13's backtest feeds historical *closed* candles through
the same strategy code — so using closed candles live means the live and backtest
inputs are the same shape and cadence, with no second reality for the strategy to
behave differently in. It also bounds fan-out to one RPC per subscriber per
minute, where a trade/ticker stream would fire many RPCs per second into every
subscriber object and run a full strategy pass on each.

**The consequence, stated plainly:** a bot reacts up to ~1 minute after a real
move, and a stop-loss can be up to one candle late. Accepted for v1 as consistent
with section 1. It lands hardest on the stop-loss, which is the one place latency
has teeth.

*A last-trade / ticker stream — rejected* for v1: near-real-time, but a
high-frequency fan-out into every subscriber object, noisier, and a mismatch with
the backtest's candle input.

*Fast-path deferred, not discarded.* If the ~1-minute stop-loss lag proves too
slow during the section 17 testnet period, the clean extension — without
disturbing the candle-driven main cadence — is a trade-stream fast-path used
*only* for the stop-loss threshold check: the feed carries both, forwarding closed
candles as the strategy clock and trade prices only to a lighter "has the stop
been breached" check. Not built now; recorded so it is not painted over.

**4. Gemini's WebSocket is built and verified first; Binance is not.**
*(confirmed)*

Two reasons, one absolute. Binance is unreachable from the Cloudflare edge at all
— step 3.3 saw HTTP 451 (geo-block) live, and a Binance WS from a Worker/DO fails
for the identical reason its REST does, so there is nothing to test. And Gemini's
WS is completely unbuilt while its market data is public/unauthenticated — the
feed needs no signing, no clock-drift handling, no credential resolution, making
it the simplest possible first real socket.

**What Binance's WS needs later, without building it now:** only a
`BinancePriceFeedCodec` (URL, subscribe message, kline parse) — the object, the
alarm loop, the backfill and the fan-out are all exchange-agnostic. But that codec
is the easy tenth: Binance WS is blocked on the *same* reachability problem as
Binance REST — the section 4.4 / section 12 relay/VPS with a static, non-geo-blocked
IP. So Binance WS is not gated on this feed design; it is gated on the infra
decision that already gates Binance REST, and building the codec before that is
solved would produce a component that cannot connect. Because the Candle→Price
contract is normalised in the codec, Gemini-first locks nothing Binance-specific
into the feed object.

**5. Reconnect-with-backoff, gap-backfill, and keep-alive are driven by one
multiplexed alarm; `getCandles` is added to the REST interface; the blind-feed
policy is alert-only with a 30-minute severity escalation.** *(recommended,
confirmed with one operator addition)*

A correction first: **DO alarms are not currently used anywhere in this project.**
No object has an `alarm()` method; this project's scheduled work is cron-trigger
Workers (reconciliation's `scheduled` handler). The alarm here is therefore a NEW
mechanism for this codebase, not the existing one — but it is the right one, since
a cron worker cannot target one feed object's reconnect. Recorded so "the
mechanism this project already uses" is not asserted where it is not true.

Critical constraint: **one alarm per DO** (`setAlarm` replaces any existing one),
so heartbeat and backoff-reconnect must be multiplexed into a single alarm whose
next-fire time is computed from current state.

- `#ensureConnected()` — on first subscribe and on every alarm wake: if there is
  no live in-memory socket, open it, `accept()`, attach listeners, send the
  subscribe message, reset `reconnectAttempts = 0`, record `connectedAt`.
- **Heartbeat** — while connected, re-arm the alarm for `now + HEARTBEAT` (~30–60s,
  under the ~15-minute ceiling and short enough to notice a dead feed). On wake:
  if the socket is gone (the object was evicted at the ceiling and the in-memory
  socket vanished) or stale (no message within a threshold), treat as a disconnect
  and reconnect. This is how the design survives the no-hibernation reality:
  eviction drops the socket, the alarm wakes the evicted object, it reconnects and
  backfills.
- **Backoff (section 4.6, 5 attempts)** — on `close`/`error`, set the alarm to
  `now + base·2^k` (capped), k up to 5. After 5 failures: stop the fast cycle,
  fire a `system` alert through the existing alerts path, and keep a slow retry
  alarm (~60s) alive so a longer outage self-heals rather than the feed dying
  silently.
- **REST gap-backfill on reconnect (section 4.6)** — on every successful
  (re)connect, if `lastCandleCloseTime` exists, fetch the missed *closed* candles
  from `lastCandleCloseTime → now` and push each through the same fan-out path, in
  order, before live resumes; dedup by `closeTime` so the overlap between backfill
  and the first live candle is not delivered twice. For 1-minute candles across a
  short reconnect this is a handful of candles.

**`getCandles` added to `RestExchangeClient` now.** The backfill needs historical
klines, and the interface has no such method today (verified — nothing anywhere
fetches candles). New method
`getCandles(pair, interval, sinceCloseTime): Promise<ExchangeOutcome<Candle[]>>`,
implemented for Gemini, public/unsigned like the socket. It is shared, not
feed-only: section 13 (backtest) and section 8.4 (R2 klines cache) both require
it. The feed uses an unauthenticated REST client for it, keeping the feed
credential-free.

**Blind-feed policy — alert-only + slow retry, with a 30-minute severity
escalation** *(the operator's addition to the recommendation)*. When the feed
exhausts its 5 fast attempts or an outage runs long, subscribed bots receive no
prices; section 5.6 correctly stops them acting on silence, which also means
stop-losses do not evaluate while the feed is blind. The policy is NOT to halt
subscribers — section 7.5 is about a bot's own errors, and halting every bot on a
transient exchange-side outage is heavy-handed and itself disruptive. Instead:
alert on give-up and keep slow-retrying, AND **escalate the alert's severity (not
force a halt) once the feed has been blind for longer than 30 minutes**, so a
genuinely extended outage grows louder over time rather than remaining a single
quiet alert forever. The escalation is a severity bump on a re-fired alert, driven
by the same alarm that is already retrying.

*Escalating to halt subscribers — rejected*, per the above, but recorded as the
alternative because a prolonged blind feed genuinely means unmonitored
stop-losses; the 30-minute severity escalation is the chosen middle path.

### Deviations from the spec / prior entries

- **Section 4.6's "using the WebSocket Hibernation API" is not followed**, because
  that API does not cover the outbound connection section 4.6 describes (the
  correction above). The feed uses the ordinary outbound WebSocket API; the socket
  pins the object in memory rather than hibernating, and an alarm handles the
  ~15-minute teardown and reconnect. This is the most consequential deviation in
  the session and the reason it was design-first.
- **Section 4.1's interface changes shape.** `subscribeToPriceFeed` and
  `WebSocketHandle` are deleted; `ExchangeClient` collapses into
  `RestExchangeClient`; and `getCandles` is added. Step 6 question 3 and step 13
  anticipated the deletion; the addition is new here.
- **Step 6 question 3's framing is superseded.** It diagnosed the closure as
  needing `acceptWebSocket` + `webSocketMessage` handlers. Correct that the
  closure cannot survive eviction; wrong that hibernation handlers are the answer,
  since they do not apply to outbound sockets. The answer is decision 2: no
  closure is injected, and the listener is rebuilt on every connect.
- **DO alarms are new to this project** (decision 5). Prior scheduled work is
  cron-trigger Workers.

### Flagged uncertainties — verify at Tier 0, do not assume

1. **Exact Gemini v2 marketdata wire framing** — candle message shape, whether it
   emits an in-progress candle versus only closed, whether it replays recent
   candles on subscribe. Confident it is public, that v2 supports `candles_1m` and
   a trade feed, and that the sandbox is `wss://api.sandbox.gemini.com/v2/marketdata`
   — but the wire shapes are confirmed against the real sandbox before the codec is
   trusted, the same read-only-first discipline as every prior exchange check
   (step 3.3, step 3.4, step 13's tiered plan).
2. **Whether ~15 minutes is a hard eviction ceiling or an upper bound** that can
   fire sooner under memory pressure. The design tolerates either (alarm +
   backfill), but the actual reconnect cadence should be observed, not assumed.

### Open questions carried forward

Everything the prior list carries, plus, new to this design:

1. **A prolonged blind feed means unmonitored stop-losses** (decision 5). The
   chosen policy alerts and escalates severity at 30 minutes but does not halt.
   The section 17 testnet period is where an induced feed outage should be watched
   to confirm the escalation fires and the alert actually reaches a human.
2. **The Gemini v2 wire framing is unverified** (uncertainty 1). The codec cannot
   be trusted until Tier 0 observes the real sandbox messages.
3. **`getCandles` is specified but unbuilt**, and it is now a dependency of the
   feed, the backtest (section 13) and the R2 cache (section 8.4) alike — three
   callers for one method, which argues for building it as shared REST
   infrastructure rather than inside the feed.

## Step 14 — Gemini WebSocket reachability probe (pre-Session-A gate)
Date: 2026-07-29

Before any build, the throwaway local probe (`scripts/verify-gemini-ws.ts`,
git-ignored, same convention as `verify-gemini.ts`) was run against
`wss://api.sandbox.gemini.com/v2/marketdata`. **PASS.** It settled the two
design-critical facts uncertainty 1 flagged:

- The message type is **`candles_1m_updates`**, carrying a `changes` array of
  `[timeMs, open, high, low, close, volume]` rows. On subscribe, Gemini sends a
  large historical batch (~1441 rows in the run), then live updates. **Heartbeat**
  messages also arrive.
- There is **no `closed` flag**. Closure is inferable ONLY by a newer candle
  timestamp appearing — a real rollover was observed live during the 90-second
  window, and the most recent candle updates in place until then. This confirms
  the codec's closure-by-timestamp inference (decision 3) is the only option, and
  it is sound.
- OHLCV values arrive as **JSON numbers** (`63610.21`), not the decimal strings
  the rest of Gemini's API uses. This is what forced the Session A money-boundary
  decision below; it was discovered here, not guessed.

**Scope of the PASS, stated honestly:** this ran on a LOCAL machine, so it proves
the wire shapes and that Gemini's sandbox WS accepts a connection — it does NOT
prove Cloudflare-edge reachability (the 451 risk that killed Binance is
edge-IP-specific and invisible from local Node). Edge reachability (step 13
Tier 0 / step 11 open Q4) stays the separate open gate that must be cleared before
Session C's Durable Object is trusted in a deployed environment.

## Step 14.1 (Session A) — the exchange-interface reshape + `getCandles`
Date: 2026-07-29

The first build session of the price-feed arc, and deliberately the contained,
no-new-component half — the same "smaller, low-risk piece first" ordering step 13
used for attachment. It reshapes the REST interface into its feed-era form and
adds the historical-candle read, all inside the automated suite with no live call,
no Durable Object, no binding, and no migration. The `PriceFeed` object, the
codec, and the bot wiring are the later sessions (B, C, D) proposed for this arc.

### What was built

- **`src/shared/exchange-client.ts`** — deleted `WebSocketHandle`,
  `subscribeToPriceFeed`, and the `ExchangeClient extends RestExchangeClient`
  block; `RestExchangeClient` is now the whole interface. Added a `CandleInterval`
  union and a `getCandles(pair, interval, since?)` method. `Candle` stays (now
  consumed by `getCandles` rather than the deleted feed callback).
- **Gemini** (`gemini/client.ts` + `gemini/parse.ts`) — `getCandles` as an
  unsigned `GET /v2/candles/:symbol/:timeframe`, plus `parseCandles` and a
  `GEMINI_TIMEFRAMES` map.
- **Binance** (`binance/client.ts` + `binance/parse.ts`) — `getCandles` as
  `GET /api/v3/klines`, plus `parseKlines` and a `klines` weight in
  `ENDPOINT_WEIGHTS`.
- **`rate-limited.ts`** — delegating `getCandles`; `BINANCE_METHOD_WEIGHTS` gained
  its entry (the `Record<keyof RestExchangeClient, number>` type forced this — the
  intended compiler guard fired).
- **`fake-exchange.ts`** — a `getCandles` returning canned candles for tests.
- Stale doc/comment references to `subscribeToPriceFeed` / `ExchangeClient` /
  "hibernation" updated across both client headers, `bot-instance.ts`, and the
  `exchange`, `durable-objects`, and `shared` READMEs.
- Tests: `parseCandles`/`parseKlines` unit tests and client `getCandles` tests
  (mocked `fetch`) for both exchanges.

**1260 tests pass** (up from 1247), typecheck clean. The one miniflare
worker-teardown error on close is the same pre-existing artifact steps 11–13
recorded, unrelated to this change.

### Decisions made (the three confirmed up front, plus one the probe forced)

**1. `getCandles(pair, interval, since?)` returns candles OLDEST-FIRST, each with
`closed` derived from `closeTime <= at`.** *(confirmed up front)*

REST gives no closed flag on either venue (the probe confirmed it for Gemini's
feed, and Binance's klines are the same in spirit), so closure is derived from
whether the candle's close time has passed at request time. The current
in-progress candle comes back `closed: false`; a backfill consumer drops it. Both
implementations sort ascending rather than trusting the venue's ordering (Gemini
sends newest-first).

**2. `CandleInterval` is the small common union, but only `"1m"` is exercised.**
*(confirmed up front)*

`"1m" | "5m" | "15m" | "30m" | "1h" | "6h" | "1d"`, following the `SymbolStatus`
precedent of declaring the whole closed set even when only one member is acted on.
Gemini's spelling for the three longest (`"1hr"/"6hr"/"1day"`) is mapped in
`GEMINI_TIMEFRAMES`; Binance's spelling matches the canonical form for every
value, so it passes straight through. Only `"1m"` — what the feed's gap-backfill
needs — is verified; the rest are the declared extension surface for section 13,
unverified against either live endpoint.

**3. `since` is BEST-EFFORT and window-bounded, and the two venues differ.**
*(confirmed up front — the one consequential asymmetry)*

Gemini's `/v2/candles` takes no time-range parameter and returns a fixed recent
window, so the Gemini client filters `closeTime > since` locally and CANNOT serve
candles older than that window. Binance's klines takes `startTime`, so `since` is
pushed to the exchange AND filtered locally for an exact boundary. This asymmetry
is documented on the interface itself, not hidden. For the feed's short reconnect
gaps the Gemini window always covers the miss; Gemini deep-history is a section 13
backtest open question, not something `getCandles` promises.

**4. Gemini candle OHLCV are JSON NUMBERS, so they are rounded EXPLICITLY to the
money scale — the one number→Money boundary in the codebase.** *(forced by the
probe, not anticipated in the design)*

Everywhere else Gemini sends monetary values as decimal strings that go straight
into `fromDecimalString` with no `Number(...)` anywhere — the section 5.2 guard.
Candles are the documented exception the probe surfaced: `/v2/candles` (and the
live feed) render OHLCV as JSON numbers, with no string form to reach for.
`candleMoney` in `gemini/parse.ts` converts via `value.toFixed(SCALE)` — which IS
the "rounding must be explicit" `fromDecimalString` demands, applied at the one
boundary that forces it, and which also removes the scientific notation
`String(1e-7)` would produce. This is acceptable precisely because a candle drives
strategy DECISIONS (compare a close to a grid level), never settlement arithmetic:
a candle value is never summed into a balance. Binance renders klines as strings,
so `parseKlines` stays on the ordinary string path with no number boundary — the
exception is Gemini-specific and contained to its parser.

### Deviations from the spec / prior entries

- **Section 4.1's interface changed shape**, as step 14's design set out:
  `subscribeToPriceFeed` / `WebSocketHandle` deleted, `getCandles` added.
- **The Binance `klines` weight (2) is from published docs, unmeasured**, and
  doubly unverifiable because Binance is geo-blocked from this infrastructure
  (step 3.3) — the same standing caveat as every Binance figure (section 17
  amendment). It is wired into `BINANCE_METHOD_WEIGHTS` so the rate limiter gates
  candle reads, but the number itself is untested against the real venue.
- **No live call anywhere in the suite**, per section 14. The Gemini candle path
  is verified against the real sandbox at the feed arc's Tier 0, not here.

### Open questions carried forward (new to Session A)

1. **Gemini deep-history for section 13's backtest** (decision 3). `getCandles`
   on Gemini cannot reach past its fixed recent window; a backtest wanting older
   candles needs another source (R2 cache seeded differently, or a different
   endpoint) — a section 13 problem, flagged here so it is not discovered inside a
   backtest session.
2. **The Binance klines weight and the whole Binance candle path are unverified**
   against the real venue (geo-blocked). They compile and are unit-tested against
   mocked responses only.
3. **The wider `CandleInterval` members are declared but unexercised** — each needs
   per-venue verification before section 13 relies on it.

## Step 14.2 (Session B) — the pure Gemini `PriceFeedCodec`
Date: 2026-07-29

The second build session of the price-feed arc: the transport-free, per-exchange
codec that turns Gemini's marketdata framing into this system's types. Pure and
stateless by design — no socket, no reconnection, no alarm, no Durable Object.
This is the WebSocket analogue of `parse.ts`, and it is the piece that had to come
before the `PriceFeed` Durable Object (Session C) so that the exchange-specific
framing was settled — and unit-tested against the REAL captured shapes — before
any socket lifecycle was built on top of it.

### What was built

- **`src/exchange/price-feed-codec.ts`** — the `PriceFeedCodec` interface
  (`socketUrl` / `subscribeMessage` / `parseMessage`) and the `FeedEvent` union.
- **`src/exchange/gemini/price-feed.ts`** — `GeminiPriceFeedCodec` and
  `GEMINI_WS_URLS`.
- **`src/exchange/gemini/price-feed.test.ts`** — 10 tests driven by the real
  fixtures the step 14 probe captured (the actual timestamps `1785346020000…`,
  prices `63610.21`/`63621.05`, volumes `0.0`/`0.000784`/`0.003769`, and the real
  heartbeat `{"timestamp":1785346088542,"type":"heartbeat"}`), not invented ones.
- Barrel exports in `src/exchange/index.ts`.

**1270 tests pass** (up from 1260), typecheck clean; the one miniflare
worker-teardown error on close is the same pre-existing artifact steps 11–13 (and
Session A) recorded.

### Decisions made

**1. The codec is the transport-free half; the DO is the stateful half.** The
codec is a pure function of its inputs — the same reason `parse.ts` is pure — so
it is testable against captured payloads with no network, and the socket,
reconnection, watermark, and alarm all belong to Session C. This is the boundary
the design fixed, held exactly.

**2. `parseMessage(raw, pair, at)` — two parameters beyond the design sketch, each
a necessity, not a widening.** A `Candle` needs a `pair`, and a v1 feed socket
carries exactly one (exchange, pair), so the DO supplies it rather than the codec
trusting a `symbol` field on every frame — which the probe's truncated preview
never actually showed, so depending on it would have been guessing. `at` is
receipt time, needed for the `closed` inference (below). Both are supplied by the
caller that has them; the codec stays pure.

**3. `parseMessage` reuses Session A's `parseCandles` verbatim.** The
`candles_1m_updates` `changes` array is the SAME `[tsMs, o, h, l, c, v]` row
format as the REST `/v2/candles` response — the probe confirmed the WS rows, and
they match the endpoint. So the codec calls `parseCandles`, inheriting the
JSON-number→Money rounding (`candleMoney`, the one explicit number-boundary from
14.1) and the `closed = at > closeTime` inference, with nothing duplicated. This
is the "reuse the money-handling and closed-inference already built for
`getCandles`" the session brief asked for, and it fell out cleanly because the two
payloads are genuinely identical.

**4. Closure is time-derived at this layer; the cross-message watermark is
Session C's.** Gemini sends no closed flag — the probe confirmed closure is
inferable only by a newer timestamp appearing over time. At the pure layer that is
captured by `closed = at > closeTime`: the same candle parsed at a receipt time
past its minute comes back closed. Remembering the last-forwarded closed candle so
each closes exactly once (dedup across messages) is stateful and explicitly
deferred to the Durable Object. The rollover test demonstrates the codec half: as
receipt time advances into the next minute, the previous candle flips to closed.

**5. `FeedEvent` is a 4-way, and `parseMessage` is TOTAL (never throws).** The
kinds are `candle`, `heartbeat`, `ignored`, and `malformed`, chosen for what the
DO must do with each:
- `heartbeat` is *recognised*, not silently dropped — it yields no candle, but
  it is surfaced because Session C uses it as a **liveness signal** for the
  staleness alarm. That is a real use, not cosmetic.
- `ignored` is a well-formed message of a type this feed did not subscribe to
  (`l2_updates`), handled gracefully.
- `malformed` is the deliberate split from `ignored`: a message of a type we DID
  recognise but could not parse, or a non-JSON frame. `parseMessage` catches the
  `parseCandles` throw and returns `malformed` rather than propagating it, so one
  bad frame cannot crash the feed — but the kind is distinct so Session C can
  ALERT on it. This keeps "surface an API change loudly" (the codebase's standing
  rule) true without letting a live socket take down the object.

### Deviations from the spec / prior entries

- **`socketUrl` mirrors `geminiBaseUrlForEnvironment` exactly**: `"testnet"→`
  sandbox WS, `"production"→` production WS, anything else throws — the same
  non-configurable, fail-closed derivation, so testnet can never dial production's
  feed. It takes the `ENVIRONMENT` string directly (like its REST twin) rather than
  a whole `Env`, keeping the codec trivially testable.
- **The WS subscribe frame sends the pair UPPER-CASE**, unlike the REST path where
  `toGeminiSymbol` lower-cases it into the URL. The probe subscribed upper-case and
  it worked; recorded because it is a real divergence between Gemini's REST and WS
  conventions.
- **No live call in the suite**, per section 14. The codec is verified against
  captured real payloads; the live socket is exercised in Session C's integration
  and the arc's Tier 0.

### Open questions carried forward (new to Session B)

1. **Whether a single live-update `candles_1m_updates` carries both the new and
   the just-closed candle, or only the current one, is still unconfirmed.** The
   probe proved a rollover happens but did not capture the rollover message's row
   count. The codec does not depend on the answer (it derives `closed` per row from
   time), but Session C's watermark logic should be written to tolerate EITHER —
   and the live socket there is where the real payload is finally observed.
2. **The heartbeat cadence is unmeasured.** Session C's staleness threshold and
   heartbeat-alarm interval need a real cadence to be set sensibly; the probe saw
   heartbeats arrive but this session did not characterise their spacing.

## Step 14.3 (Session C1) — the PriceFeed Durable Object (stream engine + connection)
Date: 2026-07-29

The heavy session of the arc: the `PriceFeed` object itself. Per the sizing check,
C split into **C1** (this entry — the feed as a stream engine: socket lifecycle,
alarm, backoff, backfill, blind-feed, driven in isolation with the `#forward` seam
a test collector) and **C2** (the durable subscriber registry and real fan-out,
still to come). In practice C1 was built core-first: the CURRENT-ONLY forwarding
engine was written and verified against the real captured messages BEFORE the
socket/alarm layer was added on top, so the part the probe fully determines was
green before anything network-shaped touched it.

### What was built

- **`src/durable-objects/price-feed.ts`** — the `PriceFeed` DO. Config
  (`configure`/`startFeed`/`stopFeed`), the CURRENT-ONLY stream engine
  (`handleMessage` → `#ingestCandles` → `#forwardClosed`), the outbound socket
  lifecycle (`#ensureConnected`/`#onSocketClosed`, a `connect` dependency wrapping
  `fetch(Upgrade)`/`accept()`), the single multiplexed `alarm()`, backoff, WS-batch
  backfill, and blind-feed alerting. The `#forward` seam is a no-op in production
  until C2 and a collector in tests.
- **`wrangler.jsonc`** — `PRICE_FEED` binding + `v3` `new_sqlite_classes` migration
  in BOTH environments. **`src/workers/api.ts`** re-exports the class (a DO must be
  exported from the `main` module).
- **`src/durable-objects/test-helpers.ts`** — `inFeed`/`priceFeedStub`, mirroring
  the `inBot`/`inLimiter` helpers.
- **`src/durable-objects/price-feed.test.ts`** — 15 tests against real DO storage,
  driven by the probe's verbatim captured payloads and a fake injected socket. No
  live call, per section 14.

1285 tests pass (up from 1270), typecheck clean; the one miniflare worker-teardown
error on close is the same pre-existing artifact steps 11–13 and Sessions A/B
recorded.

### Decisions made

**1. WS-batch backfill, NOT REST `getCandles` — a deliberate deviation from
decision 5, at the operator's confirmation.** Decision 5 / section 4.6 specified a
REST `getCandles(since=watermark)` gap-backfill on reconnect. This session replaces
it with backfill from the WS replay batch: the probe confirmed the exchange
replays the full recent 24h on every connect, so on RECONNECT the priming step
forwards the batch's closed candles newer than the watermark (deduped), filling the
outage gap. The reasoning, recorded here as the brief asked:
- **Equivalent coverage.** Gemini's REST `/v2/candles` returns only a fixed recent
  window (14.1 decision 3) — no more history than the WS batch already delivers. So
  REST adds no data the batch lacks.
- **Race-free.** WS-batch backfill happens SYNCHRONOUSLY inside the one batch-frame
  handler. A REST backfill runs during an `await` on `getCandles`, and in a Durable
  Object live WS `message` events can interleave with that await — a live rollover
  advancing the monotonic watermark past a not-yet-forwarded backfill candle would
  drop it. WS-batch backfill has no such window.
- **Simpler.** No public/unsigned REST client in the feed, no second code path.
`getCandles` is NOT wasted — it remains for section 13's backtest and the section
8.4 R2 cache, its original shared justification. This deviation is about the FEED's
backfill only.

**2. The forwarding engine is CURRENT-ONLY (from Q1), and priming forwards no
history on first connect.** `#current` holds the in-progress candle's last-seen
OHLCV; a newer `openTime` finalises it (forwards close price at receipt time);
same `openTime` refreshes it. On the FIRST connect ever (`watermark === null`) the
replay batch is consumed only to set `#current` and prime the watermark to
`newest.openTime - 1` — no bot wants a day of stale candles on startup. A monotonic
`watermark` dedups everything, which is what makes both reconnect priming and
out-of-order frames safe.

**3. One multiplexed alarm, with constants measured from Q2, not guessed.** A DO
has ONE alarm, so heartbeat/staleness and backoff-reconnect share it, its next-fire
computed from connection state: connected+fresh → re-arm health check
(`HEALTH_CHECK_MS` 15s); connected+stale (no frame within `STALENESS_MS` 20s, ~4
missed 5s heartbeats) → tear down and reconnect; no socket (a scheduled reconnect,
or a wake after eviction) → reconnect. The 20s/15s figures come from the measured
~5s heartbeat cadence, replacing 14.2's placeholder "~30–60s". This alarm is also
the eviction-recovery path: an evicted DO wakes with its in-memory socket gone and
reconnects.

**4. Backoff → blind → escalation (section 4.6 + the operator's addition).**
Reconnect uses exponential backoff (1/2/4/8/16s) for `MAX_RECONNECT_ATTEMPTS` (5).
After that the feed is BLIND: it fires ONE `warning` `price_feed_blind` alert, keeps
a 60s slow retry alive (a long outage self-heals rather than dying silent), and — if
it stays blind past `BLIND_ESCALATION_MS` (30 min) — fires a `critical`
`price_feed_blind_escalated` alert, exactly once. A successful reconnect clears the
attempt count and blind state. The policy is alert-only, NOT halting subscribed
bots: section 7.5 is about a bot's own errors, and halting every bot on a transient
exchange-side outage is heavier than the outage. But a blind feed means unmonitored
stop-losses, which is why it gets louder over time.

**5. What persists vs what is rebuilt.** Persisted (survives eviction): the config,
the `watermark`, and the backoff/blind counters (so an eviction mid-outage does not
reset the escalation clock). Transient (rebuilt on every reconnect from the replay
batch): the live socket, `#current`, and `#primed`. This is the whole point of the
CURRENT-ONLY design surviving the no-hibernation reality — the only thing that must
outlive an eviction is "how far have I forwarded", and that is one integer.

**6. A dependency-injected `connect` seam keeps the suite off the network.** The
socket transport is a `connect(url, handlers)` dependency; production wraps
`fetch(Upgrade)`/`accept()`, tests inject a `FakeSocket` they drive (deliver
frames, drop the connection, fail the next N connects). This is the same
injected-wins shape `BotInstance`/`RateLimiter` use, and it is what lets the socket
lifecycle, backoff, staleness, and blind escalation all be tested deterministically
with no live call.

### A process note: the `wrangler types` regression, caught and reverted

Regenerating `worker-configuration.d.ts` with `wrangler types` (to pick up the new
binding) pulled in two bindings the project deliberately keeps OUT of that file —
`ACCESS_TEAM_DOMAIN` and `SYMBOL_CACHE`, which are provided by `declare global`
augmentations per the `vitest-env.d.ts` convention. The regenerated literal
`ACCESS_TEAM_DOMAIN: "vidya-991.cloudflareaccess.com"` clashed with the `string`
augmentation (TS2430), breaking typecheck. Fixed by reverting the full regeneration
and adding ONLY the `PRICE_FEED` line by hand. Recorded because it is a real trap:
`wrangler types` is not idempotent against this project's deliberate augmentation
setup, and the safe move is a minimal manual binding add, not a blind regen.

### Deviations from the spec / prior entries

- **Decision 5's REST gap-backfill is replaced by WS-batch backfill** (decision 1
  above). The most consequential deviation this session, confirmed by the operator.
- **Section 4.6's "WebSocket Hibernation API" remains not followed** (the step 14
  correction): the socket is a plain outbound connection that pins the DO, and the
  alarm handles the ~15-minute teardown — now built, not just designed.
- **DO alarms are used for the first time in this project** (step 14 decision 5
  foresaw this): `PriceFeed` is the first object with an `alarm()` handler.
- **No live call in the suite**, per section 14. The real socket and edge
  reachability are exercised in the deployed integration, not here.

### What C1 does NOT do (deferred to C2 and beyond)

1. **No real subscribers yet.** `#forward` is a production no-op; nothing calls
   `startFeed`. C2 adds the durable subscriber registry, makes `#forward` a fan-out
   to each subscriber's `onPriceUpdate`, and gates `startFeed`/`stopFeed` on the
   set becoming non-empty/empty. Until then a deployed `PriceFeed` is inert.
2. **The ~15-minute eviction ceiling is still only reasoned, not observed** (14.md
   uncertainty 2). The alarm + reconnect tolerate any teardown cadence, but the real
   figure is a deployed-integration observation.
3. **Edge reachability (step 11 Q4 / step 13 Tier 0) is unchanged** — the gate
   before a deployed `PriceFeed` is trusted. The probe proved message contents, not
   that the Cloudflare edge can open the Gemini socket.

### Open questions carried forward (new to C1)

1. **The blind-feed escalation and the whole reconnect/backfill path are verified
   only against a faked socket.** Deterministic and thorough, but the real socket's
   close/error semantics and the real reconnect replay batch are observed only in

   the rate limiter and alerts carry (section 17).
2. **`stopFeed` deletes the alarm, but C1 has no caller for it.** Correct in
   isolation; the lifecycle only becomes real when C2 drives start/stop from the
   subscriber set. Recorded so the inert-in-production state is not mistaken for a
   gap.

## Step 14.4 (Session C2) — the subscriber registry and fan-out
Date: 2026-07-30

The last piece of the `PriceFeed` object: the durable subscriber registry and the
fan-out that fills the `#forward` seam C1 left as a production no-op. With this the
object is feature-complete — a closed candle now reaches every subscribed bot —
though still inert until Session D makes bots actually subscribe.

### What was built

All in `src/durable-objects/price-feed.ts` (+ tests):

- A **SQLite `subscribers(bot_instance_id TEXT PRIMARY KEY)` table**, created in the
  constructor, with `subscribe(botInstanceId, config)` / `unsubscribe(botInstanceId)`
  RPCs.
- **`#fanOut`** — the production `forward` default — delivering each closed candle
  to every subscriber concurrently, and the `deliver` seam whose default is the
  cross-DO RPC.
- The **count-transition gating** of C1's `startFeed` / `stopFeed`, and the
  **watermark reset** in `stopFeed`.
- 5 new tests (20 in the file now). 1290 tests pass, typecheck clean; the one
  miniflare teardown error on close is the same pre-existing artifact.

### Decisions made

**1. The registry is a real SQLite table, and idempotency falls out of SQL.**
`INSERT OR IGNORE` makes a redelivered `subscribe` a no-op; `DELETE … WHERE` makes
an `unsubscribe` of a non-member a no-op. Section 5.1 warns that status transitions
can be redelivered, so the set had to be corruption-proof under replay by
construction, not by careful checking — and set semantics in SQL give exactly that.
The table survives eviction, which is the whole requirement.

**2. `subscribe` CARRIES the `{exchange, pair}` config — a refinement of the brief's
`subscribe(botInstanceId)`, forced, not chosen.** A Durable Object cannot read its
own name, so the feed cannot derive its market from the `gemini:BTCUSD` key. The
subscriber, which knows its own config, supplies it; the first subscriber's config
configures the feed (idempotent, first-wins). There is no other way for the feed to
learn which socket to open.

**3. Cross-DO delivery uses `idFromName(botInstanceId)`, NOT the design's sketched
`idFromString`.** BotInstances are addressed by name everywhere in this codebase
(`test-helpers.botStub` = `get(idFromName(botInstanceId))`), and the RPC carries a
`botInstanceId` which IS that name. `idFromString` needs a serialized 64-hex id we
do not have. So the fan-out is
`env.BOT_INSTANCE.get(idFromName(id)).onPriceUpdate(price)`. The design entry's
`idFromString` was an imprecise sketch; this is the corrected, codebase-consistent
pattern.

**4. First subscribe opens the feed, last unsubscribe closes it — by count
transition.** `subscribe` compares the count before/after the insert: `0 → >0` calls
`startFeed`, otherwise just records the config. `unsubscribe`: `>0 → 0` calls
`stopFeed`. This composes C1's existing connection primitives without touching its
connection logic, exactly as the split intended, and it is idempotent because the
transition only fires on a real edge (a redelivered first-subscribe sees `>0 → >0`
and does nothing).

**5. Fan-out is `Promise.allSettled` over a `deliver` seam.** `allSettled` isolates
failures so one slow or throwing bot cannot stall or break delivery to the others.
`deliver` is injected (default: the real cross-DO RPC) so fan-out and failure
isolation are testable with a spy rather than real BotInstances — the same DI shape
C1 used for `connect`. A non-running bot's `onPriceUpdate` returns `"ignored"`, a
SUCCESSFUL RPC, so a stale subscriber needs no special-casing, exactly as the
original design noted.

**6. A failing subscriber is NOT auto-pruned.** *(the point-4 decision, reasoned
rather than guessed)* A fan-out exception is not a reliable "permanently dead"
signal — it is more often transient (an RPC hiccup, a momentarily-busy bot). The
risk is asymmetric: auto-pruning a live bot on a transient error would silently stop
its price flow, and nothing re-subscribes a running bot until it halts and resumes
(Session D subscribes on ENTERING running), so its stop-loss goes unmonitored —
the exact failure this system is built to prevent. The cost of NOT pruning is one
wasted RPC per minute returning `"ignored"`. So: alert on a real rejection, keep the
subscriber, and leave cleanup to the bot's own unsubscribe (Session D) and to
section 9 reconciliation, whose entire job is believed-vs-actual drift like an
orphaned subscriber. Pruning from the per-candle hot path, on an unreliable signal,
is the wrong place and the wrong trigger.

**7. `stopFeed` RESETS the watermark — a correctness fix C2 surfaced.** C1 left the
watermark intact on `stopFeed`, which was harmless only because C1 had no caller.
C2 gives it one, and revealed the bug: a feed that stops (all bots gone) and later
restarts would treat the stale watermark as a reconnect gap and "backfill" up to a
day of candles that closed while nobody was subscribed, dumping them on a
freshly-started bot. `stopFeed` is the "going idle" teardown, so it forgets the
watermark; a transient reconnect (which does NOT call `stopFeed`) keeps it and
backfills correctly. This is the one place C2 touched C1's teardown, and it is a
fix, not a feature.

### A constraint the tests caught: fan-out alerts cannot attribute to `bot_instance_id`

The first cut attributed the `price_feed_fanout_failed` alert to the failing bot via
`alerts.bot_instance_id`, to get per-bot cooldown throttling. A test immediately hit
`FOREIGN KEY constraint failed`: that column is a foreign key into `bot_instances`,
and the bot most worth alerting about — an orphaned/deleted subscriber — has no row.
So the attribution moved into the alert MESSAGE and the column stays null. Recorded
because it is a real interaction between the fan-out failure path and the D1 schema,
and because the throttling consequence (fanout failures now share one null-keyed
cooldown rather than one per bot) is a deliberate, acceptable trade — the outbound
ping is coarser, the D1 record still names each bot.

### Deviations from the spec / prior entries

- **`idFromString` → `idFromName`** (decision 3): the design's cross-DO sketch was
  imprecise; the built pattern matches how bots are addressed everywhere else.
- **A `deliver` dependency was added** beyond the design's method list — a
  testability seam, not a behaviour change; its default IS the design's cross-DO
  call.
- **No live call in the suite**, per section 14. Fan-out is verified with a spy
  `deliver` and a fake socket; a real `onPriceUpdate` over a real stub is a
  deployed-integration / Session D concern.

### The state of the whole price-feed effort after C2

The `PriceFeed` object is **feature-complete**: it connects, survives eviction via
its alarm, forwards closed 1-minute candles CURRENT-ONLY, backfills reconnect gaps
from the replay batch, alerts when blind, and now fans each candle out to a durable,
idempotent set of subscribers, opening on the first and closing on the last. What
remains true from C1 is unchanged: it is **inert until Session D**, because nothing
calls `subscribe`/`unsubscribe` yet, and the **edge-reachability gate** (step 11 Q4
/ step 13 Tier 0) and the **~15-minute eviction ceiling** remain deployed-integration
observations, not local ones.

### Open questions carried forward (new to C2)

1. **The whole fan-out path is verified with a spy `deliver`, never a real
   `onPriceUpdate` over a real stub.** The cross-DO call, the `"ignored"` return for
   a non-running bot, and the RPC's own failure modes are observed only once Session
   D wires real bots and the deployed integration runs — "tests prove the code, not
   the wire" again.
2. **The fanout-failure cooldown is coarse** (null-keyed, shared across bots) because
   of the foreign key. Acceptable, but if per-bot outbound throttling is ever wanted,
   it needs a cooldown key that does not go through `bot_instance_id`.

## Step 14.5 (Session D) — wiring BotInstance's status transitions to the feed
Date: 2026-07-30

The final piece of the whole price-feed arc: making bots actually subscribe. With
this a `running` bot receives live closed candles through its existing
`onPriceUpdate` and trades on them — the loop from 14.1's design to a real, driven
bot is closed.

### What was built

- **`BotInstance`** gained a `feedFor?` dependency (mirroring `limiterFor`),
  defaulting to the `PRICE_FEED` binding keyed by `${exchange}:${pair}`, plus
  `#subscribeToFeed` / `#unsubscribeFromFeed` helpers.
- **The four call sites**, verified precise before writing: subscribe in `start`
  and `resume` (entering running); unsubscribe in `#halt` and `close` (leaving it).
- **`PriceFeedPort`** exported from `price-feed.ts` (the real stub satisfies it);
  `noopFeed` / `recordingFeed` test doubles.
- 7 wiring tests, plus a `noopFeed` injected into every existing `BotInstance` test
  helper. 1297 tests pass, typecheck clean; same pre-existing teardown artifact.

### Decisions made

**1. The four call sites, and why they are exactly these.** All halt-like exits
(stop-loss, breakout, DCA take-profit-off, grid exits, order rejection, unhandled
error) funnel through `#halt`, so a single unsubscribe there covers every one. The
only other leaving-running transition is `close` (which can go running → stopped
directly, bypassing `#halt`). Entering running is only `start` (created → running)
and `resume` (halted → running). And the DCA auto-restart (a take-profit with
`autoRestart` on) returns `running` WITHOUT calling `#halt`, so it never
unsubscribes — which is correct, because it never leaves running. A test asserts
exactly this (auto-restart keeps one subscribe and zero unsubscribes; take-profit-
off unsubscribes).

**2. Subscribe is FAIL-CLOSED, unsubscribe is BEST-EFFORT — a deliberate
asymmetry.** *(the point-4 judgment call)*

- **Entering running (subscribe): fail-closed.** It is awaited BEFORE the status
  flip, so a failure propagates and the bot stays created/halted — it does not
  enter running without a confirmed price connection. Reasoning: a running bot
  *should* be subscribed (the invariant this session establishes); subscribe-before-
  flip makes it clean with NO rollback (a failure means nothing changed); it is safe
  because a bot that fails to start takes no action and holds no position; and it
  gives clear operator feedback ("couldn't start — feed unreachable, retry") rather
  than a silently-priceless running bot with no self-heal. The `PriceFeed` is a
  Cloudflare DO reached by DO-to-DO RPC, so a failure is rare and transient, and
  retry is the right response.
- **Leaving running (unsubscribe): best-effort.** Wrapped in try/catch; a failure
  alerts (`price_feed_unsubscribe_failed`) but NEVER throws. Reasoning: halting and
  closing are safety actions that must never be blocked by a feed-registry hiccup —
  a bot that cannot unsubscribe must still halt — and a stale subscriber is harmless
  (the feed's fan-out gets an `"ignored"` from a non-running bot) and reconciliation-
  visible. The alternative (proceed-into-running-and-alert on subscribe failure) was
  rejected: it creates a "running but priceless" state that looks active, does
  nothing, and has no automatic recovery — strictly less clear and less safe than a
  clean start failure.

**3. No extra idempotency guard here — the registry already owns it.** *(point 3)*
`subscribe`/`unsubscribe` are idempotent in C2 (`INSERT OR IGNORE` / `DELETE`), so a
redelivered status transition cannot corrupt the set. This session adds NO guard
logic of its own on top; a retried `start` or `#halt` simply re-issues an idempotent
call.

**4. An unresolvable exchange SKIPS the subscribe rather than blocking the
transition.** `config.exchange` is a `string`; if it is not a known exchange (a
corrupt config the registry prevents in practice), `#subscribeToFeed` returns
without subscribing rather than throwing. This preserves step 13's contract: the
existing exchange-RESOLUTION guard is the single place that halts such a bot, at its
first trade — this session does not duplicate that validation or move the failure
earlier. A test caught this (step 13's "kraken" test expects a halt at trade time,
not a throw at start), and the skip is the surgical fix. For every real bot the
exchange is valid and this always subscribes.

**5. A `noopFeed` MUST be injected into every BotInstance test.** The default
`feedFor` reaches the real `PRICE_FEED` binding, whose `subscribe` opens a live
Gemini socket — so a test that drives a status transition with no injected feed
would make a live call, violating section 14. The fake feed is now injected in
every test helper across the four DO test files, exactly as `FakeExchange` is. This
is a real coupling worth stating: wiring the feed into the lifecycle means every
lifecycle test must fake the feed.

### The price-feed arc (14.1 → 14.5) is complete — and what that does and does not mean

The whole arc is done: an outbound-socket `PriceFeed` object (no hibernation, alarm-
driven reconnect) that forwards closed 1-minute candles CURRENT-ONLY, backfills
reconnect gaps from the replay batch, alerts when blind, fans out to a durable
idempotent subscriber set, and — now — is driven by real bots that subscribe on
entering running and unsubscribe on leaving it.

**What the automated suite proves:** the wiring is correct — the right transitions
call the right RPCs with the right arguments, the asymmetry (fail-closed subscribe /
best-effort unsubscribe) behaves as intended, and the CURRENT-ONLY forwarding,
backfill, backoff, blind-feed, and fan-out logic all hold against captured real
payloads and fakes.

**What it does NOT prove, and remains a DEPLOYED, MANUAL step:** a real, live,
end-to-end run — a running Gemini-sandbox bot actually receiving a real price over a
real socket and placing a real order. The suite makes no live call (section 14), the
socket transport and the cross-DO `onPriceUpdate` are exercised only against fakes,
and edge reachability (step 11 Q4 / step 13 Tier 0) and the ~15-minute eviction
ceiling remain observations only a deployment can make. This is the same "tests prove
the code, not the wire" boundary every real-exchange control in this project carries
(section 17), and it is called out so "the arc is complete" is not misread as "it has
traded live."

### Open questions carried forward (new to D)

1. **The entire feed→bot delivery path is unproven against a live socket.** Every
   prior C1/C2/D caveat rolls up here: the deployed, tiered, read-only-first sandbox
   verification (below) is what turns "the wiring is correct" into "a real bot took a
   real price and placed a real order."
2. **A subscribe failure blocks start, by design (decision 2).** In the rare event
   the `PriceFeed` DO is unreachable, bots cannot start until it recovers. Accepted
   as safe (a bot that does not start has no risk) and clear (an explicit error), but
   recorded as a real operational coupling: bot startup now depends on `PriceFeed`
   availability.

## 14.6 — Tier 0 edge→Gemini WebSocket reachability (temporary diagnostic)

The price-feed arc (14.1–14.5) proves the code but not the wire: the whole design
rests on Cloudflare's edge being able to open an outbound WebSocket to Gemini's
sandbox marketdata feed and receive real `candles_1m` frames. That is **Tier 0** —
the gate nothing downstream proceeds past, and the same class of risk that killed
Binance locally (the HTTP 451 "restricted location" geo-block, decision-log 03 and
step 3.3). Until it is confirmed live, "the arc is complete" cannot be read as "a
bot can receive a real price." Carried open since step 11 Q4 / step 13 "Tier 0".

To answer it once, from where the bot ACTUALLY runs, a **temporary diagnostic
route** `GET /api/debug/ws-check` (`src/api/debug-ws-check.ts`, wired in
`src/api/index.ts`). Directly from the Worker's own fetch handler — NOT via the
`PriceFeed` Durable Object — it opens an outbound WebSocket to
`wss://api.sandbox.gemini.com/v2/marketdata`, sends the real `candles_1m` BTCUSD
subscribe frame, listens ~10s, and returns a JSON summary: whether the connection
opened, how many frames arrived, the first frame's `type`, and whether any
`candles_1m_updates` frame arrived. Read-only market data only — no order path, no
credentials (the feed is public).

### Decisions made

**1. The `/api/debug/ws-check` route is TEMPORARY, not a feature.** *(explicit)*

It answers one question once — can the deployed edge reach the Gemini sandbox feed?
— and is removed immediately after a single confirming request. Not a monitoring
endpoint, not a health probe, nothing a real user or bot should ever call. Both the
file header and the wiring block in `index.ts` carry removal instructions; removal
is: delete `src/api/debug-ws-check.ts` and `src/api/debug-ws-check.test.ts`, delete
the marked block and its `handleWsCheck` import in `src/api/index.ts`. Recorded here
so the route's absence later is expected, and its reappearance would be a
regression. This mirrors the now-removed `/api/debug/exchange-check` (decision-log
03) exactly. *Revisit if:* never — it is meant to be deleted. A permanent
reachability signal, if ever wanted, should be designed as one (rate-aware,
alerting), not by promoting this stub.

**2. It verifies the feed INDEPENDENT of the `PriceFeed` DO, but via the same
handshake.** The route runs from the Worker's own fetch handler, so a failure
cannot be blamed on DO lifecycle, hibernation, or the alarm — it isolates edge
reachability. Yet it opens the socket with the SAME fetch-Upgrade handshake
`PriceFeed.openOutboundSocket` uses, and resolves the URL and the subscribe frame
from the SAME `GeminiPriceFeedCodec` (`socketUrl`/`subscribeMessage`), so a green
run proves the exact path the DO will take, not a lookalike. No second copy of
Gemini's wire format is introduced.

**3. It reuses the `/api/*` gating, adding no new surface.** Wired AFTER
`authenticate()` (behind Cloudflare Access + the JWT re-check, like every real
route) but BEFORE the schema guard and `ApiContext`, because the diagnostic needs
neither D1 nor the `BOT_INSTANCE` binding — the same placement and reasoning as the
removed `/api/debug/exchange-check`. `/api/debug/*` inherits Access with zero
config; a bare `/debug/*` would be ungated (Access is scoped to `/api/*`, which is
why `/health` is public).

**4. Tests prove the logic; the wire is a deployed, manual step.** `runWsCheck`'s
transport and timing are injected, so `debug-ws-check.test.ts` drives it against a
mock socket that replays captured frames with no live call and no real 10s wait
(section 14). It covers the pass path (opened, tallied, candles seen), the two fail
paths (connect throws; opens but no `candles_1m_updates`), and that an
unauthenticated request is rejected (401) before any socket opens. The real
verification is the one live run below.

### How to run it (the one live check)

1. Deploy to testnet: `npm run deploy:testnet` (this is `wrangler deploy --env
   testnet`; on that env `socketUrl("testnet")` resolves to the sandbox URL — the
   default `--env`-less deploy reports `ENVIRONMENT: "unconfigured"` and the route
   would 500 on `socketUrl`, which is intended).
2. Hit `GET https://<testnet-dashboard-host>/api/debug/ws-check` through the browser
   session that is already behind Cloudflare Access (the route is Access-gated, so a
   raw `curl` without an Access token gets 401 — same as every `/api/*` route).

**PASS** — the edge can feed the bot:
`{ "connectionOpened": true, ..., "candlesUpdateReceived": true }` (at least one
`candles_1m_updates` frame; `messagesReceived` > 0).

**FAIL** — two shapes, each meaningful:
- `"connectionOpened": false` with an `error` → the edge could not open the socket
  at all (geo-block / the Binance-451 failure mode reaching Gemini).
- `"connectionOpened": true` but `"candlesUpdateReceived": false` (only heartbeats,
  or zero frames) → the socket opened but no real market data arrived, i.e. the
  market is being fed differently at the edge than it was to the local step-14
  probe.

### Open questions carried forward

The step 14 D open questions stand. This route, once run green, is what turns D's
open question 1 ("the entire feed→bot delivery path is unproven against a live
socket") from unproven to *edge-reachability proven* — it does NOT prove the full
feed→bot→order path, which remains the deployed manual end-to-end run. Note also the
Workers routing caveat from decision-log 03 (open question 1) applies here too: a
single green hit proves the edge location that served THAT request is not blocked,
not that every edge location that might serve a future request is clear.

### Update — the diagnostic caught a REAL feed bug on its first live run

The first deployed run failed `connectionOpened: false` with *"Fetch API cannot
load: wss://api.sandbox.gemini.com/v2/marketdata"* — NOT a geo-block. Cloudflare's
outbound-WebSocket client is `fetch()` with an `Upgrade: websocket` header, and
`fetch` REJECTS a `ws://`/`wss://` URL: the scheme must be `http://`/`https://`, and
the socket is then read off `response.webSocket`. Both `PriceFeed.openOutboundSocket`
(the real feed) and this diagnostic's `openWsCheckSocket` passed the `wss://` URL
straight to `fetch` — the **identical bug**. Because every `PriceFeed` engine and
lifecycle test injects a fake `connect`, the real transport had never been exercised,
so the feed would have failed this exact way on its own first live connect. **The
Tier 0 diagnostic did precisely what it was built to do: it caught a real bug in the
actual feed before the feed ever ran live.**

*Fix:* a shared, exported `httpUrlForWebSocket(url)` in `price-feed.ts` translates
`wss://`→`https://` (and `ws://`→`http://`); both openers now call it, so the two
cannot diverge again. Both openers also take an injectable `fetchImpl`, so the
corrected handshake shape (http(s) scheme + `Upgrade` header + reading `.webSocket` +
`.accept()`) is now covered by tests that assert it without a live socket — the gap
that let the bug survive is closed. Typecheck clean; full suite green (1310 tests).

### Closing note — confirmed PASS, route removed (2026-07-30)

**Live result (2026-07-30), the run this route existed for:** `connectionOpened:
true`, `candlesUpdateReceived: true`, `messagesReceived: 3`, first message type
`candles_1m_updates`. Tier 0 is **PASS** — Cloudflare's edge opens an outbound
WebSocket to the Gemini sandbox marketdata feed and receives real `candles_1m`
frames. The "451 killed Binance" geo-block risk (step 11 Q4 / step 13 Tier 0) does
NOT reproduce for Gemini sandbox from the edge. The step-14 D open question 1 is
narrowed from "the feed→bot path is unproven against a live socket" to
*edge-reachability proven*; the full feed→bot→order end-to-end run remains the
separate deployed manual step. (The decision-log 03 caveat still applies: one green
hit proves the edge location that served THAT request, not every future one.)

**Route removed, same day.** `src/api/debug-ws-check.ts` and
`src/api/debug-ws-check.test.ts` deleted; the marked block and its `handleWsCheck`
import removed from `src/api/index.ts`. No route, handler, or reference to the
diagnostic remains — its absence is expected, and any reappearance is a regression.
This entry is the historical record of why it briefly existed. Typecheck clean; full
suite green (1300 tests, down exactly the 10 diagnostic tests).

**What the diagnostic leaves behind, permanently.** It caught a real bug in the
actual feed's transport (the `wss://`-to-`fetch` mistake above), so the FIX stays
even though the route is gone: `httpUrlForWebSocket` in `price-feed.ts` (the
`ws(s)://`→`http(s)://` scheme translation Cloudflare's outbound-WebSocket client
requires), now used by `PriceFeed.openOutboundSocket`, plus the injectable `fetchImpl`
and the handshake tests in `price-feed.test.ts` that assert the correct shape without
a live socket — closing the gap (every engine/lifecycle test injects a fake `connect`)
that let the bug survive until this live run. That residue is the lasting value of the
Tier 0 gate: a temporary route deleted, a permanent bug fixed and covered.

## 14.7 — Tier 1: the REAL `PriceFeed` object, live (temporary diagnostic)
Date: 2026-07-30

Tier 0 (14.6) proved the edge can open a WebSocket to Gemini's sandbox feed — but
deliberately from the Worker's own fetch handler, INDEPENDENT of the `PriceFeed`
Durable Object, so that a failure could not be blamed on DO lifecycle. That
isolation was the right call and it leaves the obvious next question unanswered:
does the **real object** connect, survive a real minute boundary, and forward a real
closed candle to a subscriber? The automated suite cannot answer it — every engine
and lifecycle test injects a fake `connect` (14.3 decision 6) and a spy `deliver`
(14.4 decision 5), and that exact blind spot is what let the `wss://`-to-`fetch`
transport bug survive until Tier 0 ran live. **Tier 1** closes it.

A second temporary route, `GET /api/debug/feed-check`
(`src/api/debug-feed-check.ts`, wired in `src/api/index.ts`), plus a temporary
read-only `debugSnapshot()` on the feed object itself. It subscribes a throwaway id
to `PRICE_FEED.getByName("gemini:BTCUSD")`, holds the request open across at least
one real minute boundary, records whether a closed candle was actually fanned out,
unsubscribes in a `finally`, and returns a verdict. Read-only market data: no bot is
created, no order path is reachable, no credentials are touched.

### Decisions made

**1. The route AND the `debugSnapshot()` read path are TEMPORARY, not features.**
*(explicit)*

Same convention as 14.6 and, before it, `/api/debug/exchange-check` (decision-log
03). Removal is four deletions, recorded in both file headers and the wiring block:
delete `src/api/debug-feed-check.ts` and `src/api/debug-feed-check.test.ts`, delete
the marked block and the `handleFeedCheck` import in `src/api/index.ts`, and delete
the marked `TEMPORARY DIAGNOSTIC READ PATH` block (`debugSnapshot`) and the
`PriceFeedDebugSnapshot` interface in `src/durable-objects/price-feed.ts`. Recorded
here so the absence of all four later is expected and their reappearance is a
regression. *Revisit if:* never — a permanent feed-health signal, if ever wanted,
should be designed as one (alerting, rate-aware), not by promoting this stub.

**2. Observing the fan-out from outside needed a read path, so one was added to the
object — read-only, and it is the load-bearing decision of this session.**

Everything worth observing is private: `#socket`, `#current`, the persisted
`watermark`, the subscriber table. A Durable Object's storage cannot be read from
outside, `#fanOut` records nothing per-subscriber, and every existing RPC
(`subscribe`, `unsubscribe`, `configure`, `startFeed`, `stopFeed`, `handleMessage`,
`beginConnection`, `alarm`) is a WRITE path. There was no way to observe the object
without giving it one, so `debugSnapshot()` returns `{config, connected, subscribers,
watermark, lastMessageAt, reconnectAttempts, blindSince}`. It mutates nothing, arms
no alarm, opens no socket, and has no production caller.

The **watermark is the evidence**, and precisely why it works:
`#forwardClosed` writes it ONLY after `await this.#deps.forward(price)` resolves, and
in production `forward` IS `#fanOut` over the subscriber table. So a watermark that
advances past its baseline, while `debug-check` is in `subscribers`, proves a real
closed candle went through the real fan-out with this subscriber in the list. The
route treats the FIRST non-null watermark as a baseline, never as evidence, because
a first-ever connect primes it to `newest.openTime - 1` without forwarding anything
(14.3 decision 2) — mistaking that for a forward would produce a false PASS on a feed
that had merely connected. A test pins exactly this.

*Alternatives rejected:* reading the DO's storage from outside (impossible);
`attach()`-ing a spy `deliver` over RPC (it would hijack delivery for any REAL bot
subscribed to that market — unacceptable on a shared object).

**3. D1 gives per-subscriber attribution for free, via the expected failure.** The
throwaway id is not a real bot, so its `onPriceUpdate` throws `not_created`
(`bot-instance.ts` `#config`), the fan-out delivery REJECTS, and `#fanOut` records a
`price_feed_fanout_failed` alert **naming `debug-check` in the message** — the
attribution-in-the-message shape 14.4 was forced into by the `bot_instance_id`
foreign key. That row is written by the real feed and read back by the route: direct
evidence that the cross-DO RPC was issued for THIS id, where the watermark alone only
proves "the fan-out ran over a set containing it". `allSettled` isolates the
rejection, so no real bot is affected. Cost, stated: the run leaves 1–2 `warning` rows
in testnet D1, visible in `/api/alerts`. Nothing is paged — the notification cron
no-ops without `ALERT_COOLDOWNS` and `DISCORD_WEBHOOK_URL`, neither of which is
provisioned. A PASS on the watermark with no such row is still reported as a PASS,
but the summary says the delivery rests on the watermark alone rather than quietly
claiming both.

**4. A missing `alerts` table makes the route REFUSE, not report.** `#fanOut` awaits
`#alert(...)` when a delivery rejects, and that insert throws on a schema-less
database — which propagates out of `forward` and stops `#forwardClosed` from ever
writing the watermark. A perfectly healthy feed would then look broken. So the
handler runs its own narrow `tableExists("alerts")` check first and returns
`verdict: "unavailable"` with that explanation. This is a real interaction between
the diagnostic's fake subscriber and the fan-out's alert path, and it is the reason
the route needs D1 at all.

**5. The wait is 120s by default (`?waitMs=`, clamped 10s–180s), and a quiet market
is INCONCLUSIVE, not FAIL.** The constraint, checked against current Cloudflare docs
rather than assumed: there is **no hard wall-clock limit** on an HTTP-triggered
Worker while the client stays connected (CPU time is the real limit, and waiting on a
timer costs none), and 524 is an ORIGIN timeout that does not apply to a
Worker-generated response. The one real hazard is that a runtime update gives
in-flight requests a **30-second grace period**, so a long hold is not free — which is
why the window is bounded rather than "wait as long as it takes".

The number comes from the probe's MEASURED cadence, not a guess: the replay batch
primes `#current` without forwarding, and the first forward needs a frame carrying a
newer `openTime` — and candle frames arrive only on activity, 35–70s apart (Q2), with
~5s heartbeats. Worst case ≈ 60s to the boundary + up to 70s of quiet ≈ 130s; typical
30–70s. Hence 120s, with the option of 180s. And because a connected feed that simply
saw no rollover is a short window rather than a fault, that outcome is its own verdict
— `inconclusive`, "re-run" — distinct from `fail`. The route also breaks out the moment
the forward is observed, so a typical PASS returns in well under the full window.

**6. The throwaway subscriber is removed in a `finally`, including when the subscribe
threw.** `subscribe` inserts the registry row and THEN calls `startFeed`, so a
failure in the second step can leave the row behind. `unsubscribe` is idempotent
(14.4 decision 1), so an unnecessary call is free, where a skipped one would leave the
phantom subscriber this check is explicitly required not to leave. A failed
unsubscribe is reported loudly (`unsubscribed: false`, an error naming the phantom)
rather than thrown, so a cleanup hiccup does not discard the result the run was for.
Note the deliberate side effect of a successful cleanup: as the LAST subscriber
leaving, it triggers `stopFeed`, which closes the socket, deletes the alarm and resets
the watermark (14.4 decision 7) — so the check leaves the feed exactly as idle as it
found it. If a real bot is subscribed, the count never reaches zero and the feed is
left untouched.

**7. Tests prove the logic; the wire is the deployed, manual step.** 14 tests drive
`runFeedCheck` against a scripted feed port, an injected D1 read, and a clock the
injected `wait` advances, so two minutes of market data elapse instantly with no live
call (section 14). They cover the pass path, the primed-watermark trap, inconclusive,
both fail shapes (never connected; subscribe threw), a failing unsubscribe, a failing
snapshot RPC, alert filtering, the wait clamp, the schema refusal, and a 401 before
anything is subscribed. 1314 tests pass (up from 1300), typecheck clean; the one
miniflare worker-teardown error on close is the same pre-existing artifact.

### How to run it (the one live check)

1. `npm run deploy:testnet` (`wrangler deploy --env testnet` — on that env
   `socketUrl("testnet")` resolves to the sandbox URL; a deploy with no `--env` has
   no `PRICE_FEED` binding and the route returns a 503 explaining exactly that).
2. Confirm the environment has its D1 schema (any `/api/*` data route returning
   `no_schema` means migrations are not applied; the route will refuse with
   `verdict: "unavailable"` for the reason in decision 4).
3. Hit `GET https://<testnet-dashboard-host>/api/debug/feed-check` from the browser
   session already behind Cloudflare Access (a raw `curl` without an Access token
   gets 401, like every `/api/*` route). Expect it to hang for **up to ~2 minutes**,
   typically 30–70s. `?waitMs=180000` buys a longer window on a quiet market.

**PASS** — `"verdict": "pass"`: `feedConnected: true`, `candleForwarded: true`,
`forwardedAfterMs` set, and normally `deliveredToDebugSubscriber: true`. The real
`PriceFeed` object connected from the edge, crossed a real minute boundary, finalised
a real candle CURRENT-ONLY, and fanned it out to a subscriber.

**INCONCLUSIVE** — `"verdict": "inconclusive"` with `feedConnected: true` and
`framesObserved: true`: connected and alive, but no candle closed in the window. Not
a fault; re-run with a longer `?waitMs`. With `framesObserved: false` it is NOT
benign — heartbeats are ~5s, so zero frames means a socket that opened and delivered
nothing.

**FAIL** — two shapes: the subscribe RPC failed (nothing was checked), or the feed
never held a socket. Tier 0 already proved edge reachability, so the second shape
points at the DO's own connect path (`socketUrl` for this `ENVIRONMENT`, the
fetch-Upgrade handshake, the alarm), not at a geo-block. `feedAlerts` carries any
`price_feed_blind` / `price_feed_malformed` row raised during the window, so a live
failure usually says why without a second trip.

### Open questions carried forward

1. **The ~15-minute eviction ceiling is still unobserved** (14.md uncertainty 2, C1
   open question 2). A ~2-minute window cannot see it. This check proves connect →
   boundary → forward; it does NOT prove the reconnect-after-eviction cycle, which
   needs a longer deployed observation with a real subscriber.
2. **A PASS still does not prove feed→bot→order.** The subscriber here is a fake id
   whose delivery deliberately rejects. What remains unproven is the same D open
   question 1 residue: a REAL running bot receiving a real price through
   `onPriceUpdate` and acting on it. That is the end-to-end run, and it is a separate
   deployed step involving a real bot.
3. **The decision-log 03 routing caveat still applies**: one green hit proves the
   edge location that served THAT request, not every future one.
