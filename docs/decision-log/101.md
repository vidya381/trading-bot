## PART 1 — WHAT PROMPTED THIS

**A review before registering a real Kraken account**, asking one question: is
the dashboard actually built for a THIRD exchange, or is it structured around
Binance and Gemini being the only two that exist?

**The dashboard itself came back clean, and that is the useful finding.** A grep
for `gemini|binance|kraken` across `dashboard/src` returns hits in **comments
only** — there is no hardcoded venue list, no icon or display-name map, no
`Record<ExchangeId, …>` and no `switch` on an exchange name anywhere in the tree.
The only `exchange ===` comparisons are against `""`, meaning "no account
selected yet". Every account-enumerating site is dynamic: `CreateBot` and
`ProposalRun` both `.map()` over `GET /api/accounts`, `accountTotals` folds every
bot the poll returned with no venue filter, and `availableCapital` iterates every
account × every asset. There is no account switcher to be two-exchange-shaped,
because the dashboard is one fleet-wide view.

**A caveat on the evidence, because the obvious citation is the wrong one.**
Entry [94.md](94.md) recorded that widening `ExchangeId` produced **zero** compile
errors in the dashboard tree. That is true, and it is **not** evidence of
exchange-agnosticism — `dashboard/src/api/types.ts` types `exchange` as plain
`string` and never narrows it, so the compiler was never going to look. The grep
above is the actual evidence. The clean `tsc` was the *absence* of a check, not
the passing of one.

**What the review did find was three separate gaps, none of them in the render
path**: stale setup documentation, a swallowed error message, and an incomplete
suggestion list on one page. All three are fixed here.

## PART 2 — THE TESTNET TRAP, CAUGHT IN A DOCUMENTED EXAMPLE

`docs/d1-provisioning.md` still said `exchange` **"must be `'binance'` or
`'gemini'`"** — written for migration 0006 and never updated by **migration
0012**, which widened the CHECK to accept `'kraken'`. Since there is deliberately
no `POST /api/accounts` endpoint, that page is **the only documented path to
registering an account at all**, so its being one value out of date is the whole
procedure being wrong.

**The correction was not the interesting part. The example was.**

The section registers one account per exchange, and both existing examples use
`--env testnet` — which is correct for them, and is exactly what a reader adding a
third would copy. **Copying it for Kraken would have produced an account that is
visible, selectable, and guaranteed to fail on every real use.**

`resolveKrakenExchange` (`src/workers/exchange-kraken.ts`) **refuses to construct
a client in the testnet environment at all.** Not a missing secret, not a
misconfiguration — a hard refusal, checked before the secrets are even read.
Kraken publishes no sandbox or testnet host, a fact established by entry [89.md](89.md) and made a
refusal by entry [90.md](90.md)'s DECISION 1: `demo-futures.kraken.com`
serves marketing and spot UAT is account-manager-only. There is no non-real venue
to point at, so the resolver fails closed rather than aiming testnet at
`https://api.kraken.com` and trading real funds out of the test environment.
Setting `KRAKEN_API_KEY` there does not change it, and the resolver's own message
says so.

**What a testnet-registered Kraken row would therefore be: a dead entry that
looks alive.** `GET /api/accounts` reads the table and does not consult the
resolver, so the account appears in the create-bot dropdown like any other. It is
selectable. Choosing it fires `GET /api/accounts/:label/symbols` → `clientForAccount`
→ the refusal → a `502 exchange_unavailable`, the pair typeahead never populates,
and no bot can ever be created on it. The failure arrives one step **after** the
UI has already presented the account as usable.

So the Kraken example is `--env production`, alone among the three, **with the
reason stated in the prose above it** rather than left as an unexplained
inconsistency a future reader would smooth back out. It also says to set
`KRAKEN_API_KEY`/`KRAKEN_API_SECRET` **before** the INSERT, so the account is
never selectable during a window where it cannot build a client.

**This trap was not sprung, and the precise claim is narrower than "no Kraken
account exists".** No remote database was read by this work, so remote state is
not asserted here (PART 5). What *is* verified is the local dev database: zero
account rows. What was caught was a *documented example that would have created
the trap*, on the one page
whose entire purpose is to be followed literally by someone who cannot check the
resolver themselves. Commit `aab77ee`'s message — *"Kraken accounts now creatable
in testnet"* — is true of the SQL CHECK and false of usability, and is precisely
the reading this example would have reinforced.

## PART 3 — THE SWALLOWED REASON

`CreateBot.tsx`'s `describeSymbolsError` handled `exchange_unavailable` by
**discarding `error.message`** and substituting a fixed sentence: *"This is most
likely a connection problem on our end reaching the exchange, not anything you
did. Try again, or pick a different account."*

That copy was written when the only known cause was the confirmed Binance
geo-block — a genuinely transient, our-side failure, for which it was accurate
and kind. **It stopped being the only cause.** For the Kraken testnet refusal the
substituted sentence is not merely vague, it **actively contradicts** the message
it is throwing away: the failure is permanent, retrying can never succeed, and
the discarded 502 said exactly that, including that setting the API key will not
help.

The arm now carries `error.message`, which is what the `default` arm three cases
below it has always done. The guess is gone rather than appended to — a
"most likely" beside the real reason is still an invitation to disbelieve the
real reason. What survives is the part true of every cause: this is our side, not
anything you did.

**A note on where this class of bug lives.** Nothing was wrong with the error
plumbing: the resolver's reason reaches the handler, the handler puts it on the
502, the client throws it as `ApiError.message`. The message was carried
faithfully the whole way and then dropped at the last hop, by copy written before
the second cause existed.

## PART 4 — UNION, NOT REPLACE

`ManualAdjustment.tsx` offered account suggestions from a `<datalist>` built by
mapping **the bot list**, under a comment asserting *"there is no accounts
endpoint, and none is invented"*. That comment had been true and had quietly
stopped being so: `GET /api/accounts` landed at step 11 and `Dashboard` and
`CreateBot` both read it.

The consequence is narrow and exactly wrong for the case at hand: **an account
with no bots yet does not appear.** That is the state a freshly registered,
freshly funded Kraken account is in — and logging its opening deposit is the
reason to be on this page.

**The fix unions the registry with the bot-derived labels. It does not replace
one with the other, and that was the actual decision here.** `accounts` is not a
superset of the labels in use:

  * Bot creation **falls back to the request's own `exchange`** for an
    unregistered account (`docs/d1-provisioning.md`, "Seeding order"). Such an
    account is real, has bots, has ledger rows, and is not in the table.
  * Migration 0006's backfill **deliberately skipped** any bot whose free-typed
    `exchange` was never a recognised value, so the row could not violate the
    CHECK and abort the migration. Those accounts are real too, and also absent.

A pure replacement would have fixed the new-account gap **by silently dropping
real, existing accounts** from the suggestions — trading a visible omission for
an invisible one, in a list whose whole job is to stop an operator retyping a
label wrong. Both fetches run independently and each failure is ignored on its
own, so one endpoint being down leaves the other's suggestions standing; neither
can block a form that never needed either.

## PART 5 — WHAT REMAINS

**The asset datalist on the same page still derives only from bots.** A freshly
registered account's asset will not suggest until it has one, which is the same
root cause PART 4 fixed one field to the left. `accounts[].capital.assets[].asset`
is the obvious source and the fix is about a line. **Deliberately out of scope**:
this session's brief named the account field, and widening a narrow fix on my own
judgement is how a small verified change becomes a large unverified one. Recorded
here so it is a known open item rather than a thing nobody noticed.

**Two facts are not knowable from source, and this entry does not claim them:**

  * **Whether migration 0012 is applied to the remote testnet or production D1.**
    It is committed (`aab77ee`) and **is** applied to the local dev database —
    verified directly: `sqlite_master` shows the CHECK reading
    `IN ('binance', 'gemini', 'kraken')`, and that database holds **zero** account
    rows. Remote state was not read; nothing here touched a live database.
  * **Whether `KRAKEN_API_KEY` / `KRAKEN_API_SECRET` are set as production
    secrets.** Secrets are not readable from the tree by design.

**The `capital_ledger` seed is a separate, required manual step after the
INSERT.** Registering the account is not sufficient: `createBotInstanceWithCapital`
draws from a `(account_label, asset)` ledger row, and without one bot creation
fails outright with *"no capital_ledger row for account …"* (`src/capital/ledger.ts`).
The provisioning doc's "Seeding order" note already states this; it is repeated
here because the Kraken path now has two manual steps that must both happen and
only the first is new.
