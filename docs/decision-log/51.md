## PART 1 — THE GAP, AND WHERE IT WAS NAMED

Entry 47 section 8 found this while consolidating three kill-switch pollers into
one, and **deliberately refused to fix it in that step**:

> `KillSwitchBanner.tsx:35`, blamed to `db52912`, 2026-07-24 — the same commit as
> the duplicate pollers:
>
> ```tsx
> if (status === null || status.state !== "tripped") return null;
> ```
>
> **The gap, stated exactly:** if `/api/kill-switch` fails from the very first
> request — expired Access session, `no_schema` 503, a D1 error — **while the
> switch is actually tripped**, the banner shows nothing and says nothing.

And it stated why it was deferring rather than folding it in, which is also why
this is its own entry:

> That is a **visible change to the most severe communication element in the
> system**, with real design questions attached (what does it say, how loud is
> it, does it appear during ordinary first-load latency, does it risk crying wolf
> often enough to train the operator to ignore the red bar that matters).

All four of those questions are answered below. **Three of them were answered
wrongly on this session's first attempt and corrected by the operator mid-step**
— that is PART 4, and it is the more useful half of this entry.

**The mechanism, confirmed from source rather than assumed.** `usePolling`'s
catch keeps `data: prev.data`. `prev.data` is `null` until the first SUCCESS, so
a poll that has only ever failed leaves `status === null` — and the old one-line
rule sent `null` down the same branch as a confirmed `armed`. **"We do not know"
was pixel-identical to "we checked, and it is safe"**, on the one element whose
entire job is to make a halted fleet impossible to miss anywhere in the app.

⚠ **This was never observed happening in production, and this entry does not
claim it was.** It is a source-level defect, proved by the differential test in
PART 5 and reproduced on demand by the operator in PART 6. What is known live,
from entry 47's own HAR, is the opposite: **266 of 266 kill-switch requests
succeeded** over 1373.7 s. The failure window is real and reachable — the
operator reached it deliberately — but it has not been caught arising on its own.

## PART 2 — THE STATES, AND THE ONE FIELD THAT SEPARATES THEM

The verdict moved out of the `.tsx` into `dashboard/src/killSwitchBannerState.ts`,
a React-free module, for the reason `statusCounts.ts` and `proposalSummary.ts`
exist: the suite runs inside the Workers runtime, and **a test importing a `.tsx`
collects ZERO TESTS and reports a green suite**
(`docs/open-items/component-test-harness.md`). `proposalFields.ts` was extracted
after a mutation run proved its inline predecessor's call site unreachable by any
test. **A decision that cannot be tested is a decision nobody is watching**, and
this is the most safety-relevant decision in the dashboard.

```ts
if (poll.data !== null) {
  if (poll.data.state === "tripped") return "tripped";
  if (poll.data.state === "armed")   return "armed";
  return "unknown";              // an unrecognised state string
}
if (poll.loading) return "pending";
return "unknown";
```

| state | means | renders |
| --- | --- | --- |
| `tripped` | confirmed pulled | solid red bar — **unchanged from `db52912`** |
| `armed` | confirmed safe, **from a status object that said so** | nothing |
| `pending` | first poll still in flight | nothing |
| `unknown` | first poll settled with no data, **or** an unrecognised `state` | **the new amber bar** |

**Four values, three renderings.** `pending` renders exactly what `armed` renders
and is still a separate value, because folding "not yet known" into "confirmed
safe" is the precise mistake this module exists to undo. Keeping it separate is
also what makes *"the bar must not flash during ordinary first-load latency"* a
**tested property** rather than an implicit one.

⚠ **`pending` IS A STATE, NOT A SCREEN.** There is no visible "checking"
indicator in this banner and this step did not build one — see PART 7, where it
is deferred on purpose rather than forgotten. A future reader looking for a calm
neutral loading bar will not find one, because none exists.

**An unrecognised `state` string resolves to `unknown`, not `armed`** — added
beyond the brief. `requestJson` does `(await response.json()) as ApiEnvelope<T>`:
**a cast with no runtime validation.** A backend that ever answers a renamed,
added or malformed `state` reaches the banner as a value TypeScript believes is
impossible. Reading "not tripped" as "armed" is *how the original bug worked*, and
the same reading would reintroduce it one schema change later.

## PART 3 — THE TRIGGER IS EVENT-DRIVEN, NOT TIMED

**There is no elapsed-time threshold and no poll counter in this commit.**
`usePolling` sets `loading: false` when the first request *settles*, in both its
success path and its catch path. The rule is:

```
unknown  ⟺  data === null && !loading
```

— "a request came back, and it brought nothing."

**Why no timer was built.** A timer would be a second, independent notion of "how
long is too long" sitting beside the one `usePolling` already owns, and it would
have to be kept calibrated against a poll interval it does not control. The
settle event is the *actual* fact being reported and needs no tuning. **That
argument is good but not complete**, and PART 7 records where it runs out.

What that means per failure mode:

| failure | when the bar appears |
| --- | --- |
| request blocked, offline, DNS failure | ~immediately — `fetch` rejects in ms |
| 401/403 expired Access session | one round trip (~1.4 s, entry 47's measured baseline) |
| 503 `no_schema`, D1 error | one round trip |
| **connection accepted, no response ever** | **never** |

⚠ **THE LAST ROW IS A REAL HOLE AND IT IS NOT FIXED IN THIS COMMIT.** Each 5 s
tick calls `controller?.abort()` on the previous request; the resulting
`AbortError` is explicitly swallowed by `usePolling.ts:71` without touching
state. So `loading` never flips to false, the state stays `pending`, and **the
banner stays silent indefinitely**. No request ever survives long enough to reach
the browser's own network timeout, because the next tick aborts it first — the
abort always wins. **This is the concrete cost of the event-driven choice**, and
it is the reason deferral (2) in PART 7 exists.

## PART 4 — THE VISUAL DESIGN, AND THE ITERATION THAT MATTERED

Two constraints, pulling opposite ways, both correct:

- **Not styled as tripped.** A second red bar erodes the real emergency state —
  entry 47's own crying-wolf question. A different HUE is what stops habituation
  to one bar from dulling the other.
- **Not styled as informational.** The copy says the operator cannot confirm the
  fleet would be halted. **A bar that says that must not look like a tooltip.**

**This session's first answer got the second constraint wrong, and the operator
caught it before deploy.** Recorded because the correction is the useful part:

| | v1 — this session's first answer | v2 — shipped in `7809245` |
| --- | --- | --- |
| fill | `bg-amber-950` `oklch(27.9% 0.077)` — a dark band | `bg-amber-900` `oklch(41.4% 0.112)` — **a solid bar** |
| edges | hairline `border-y border-amber-500/60` | **`border-b-2 border-amber-400`**, bottom only |
| heading | `text-amber-300` | `text-amber-50` |
| button | **outlined** — reads "optional" | **filled** `bg-amber-400` on `text-amber-950` |
| height / icon | `py-2.5`, body-size `⚠` | `py-3`, `text-lg` `⚠` |

The operator's argument, which is the right one: *the message content is
genuinely serious, and the proposed treatment under-communicated it relative to
what the text actually says.* v1's fill sat only 14 lightness points above the
`zinc-950` page and needed its border to exist at all. **The outlined button was
the single clearest "this is optional" signal in v1**, and this session had argued
FOR it on severity-encoding grounds. That argument lost, correctly: a filled
call-to-action says *act on this*.

### ⚠ THE SHIPPED BAR IS AMBER, AND A LATER FRAMING SAID OTHERWISE

Recorded plainly because it would otherwise be inherited as fact. **After** the
work was committed, a framing was proposed describing the unknown state as using
*"the same alert-red hue as tripped, distinct icon/layout"*. **That is not what
`7809245` contains, and it is not what was verified live.** The commit contains no
`red-` utility anywhere in the unknown branch — a property now mechanically
enforced by a source guard (PART 5).

The framing also inverts the decision the operator themselves had made one round
earlier, in their own words: *"Not asking to make it look identical to 'tripped'
(agreed that risks crying-wolf erosion of the real red state)."* **The amber
choice is the deliberate one and it stands.**

**The severity ordering survives the escalation, and the numbers are the
argument.** Red-700 is `oklch(50.5% 0.213 27.5)`; amber-900 is
`oklch(41.4% 0.112 45.9)`. **Red is 9.1 lightness points higher and carries 1.9×
the chroma**, 18.4° away in hue. Both are solid filled bars, and red is still
unambiguously the louder one at any glance distance.

**The two axes are kept independent on purpose:**

> **HUE says which CATEGORY** — red is confirmed danger, amber is caution.
> **WEIGHT says how URGENT** — and weight is where the escalation was spent.

**⚠ The bottom-only rule is not an aesthetic choice.** On testnet the
`EnvironmentBanner` directly above is a solid `bg-amber-400` bar — *the exact
colour of this rule*. A matching top rule would abut it and read as the
environment banner being 2 px thicker. The top edge needs no drawn rule:
amber-400 at 82.8% against amber-900 at 41.4% is a **41-point lightness step**,
which is its own edge.

**ARIA carries the ordering where visual weight cannot:** `role="status"`
(polite) against the tripped bar's `role="alert"` (assertive). **Two assertive
bars is where alert habituation starts.**

**The shipped copy, verbatim**, because a paraphrase of a safety string is not the
safety string:

> ⚠ **KILL-SWITCH STATUS UNCONFIRMED** — No kill-switch check has succeeded yet,
> so this bar cannot say whether the switch is armed or tripped. A tripped switch
> would not be shown here until one does. `Last attempt: {error.message}.`
> `[ Check kill switch → ]`

The `Last attempt:` clause is omitted entirely when `error` is null.

**⚠ It deliberately makes NO claim about what the bots are doing.** A sentence of
the form *"bots continue to trade normally"* was considered and rejected: if the
endpoint is failing because the Worker itself is degraded, that is a false
reassurance this banner has no way to verify. It reports what it knows — that it
cannot confirm the switch — and stops there.

## PART 6 — LIVE VERIFICATION — THE OPERATOR'S, NOT THIS SESSION'S

Against the deployed testnet dashboard, in a real browser.

**1. The failure case, forced.** `/api/kill-switch` blocked via DevTools request
blocking, with **real failed network requests visible in the capture** — the
failure was observed at the network layer, not inferred from the UI. The **real
amber unconfirmed banner rendered, with the exact reviewed copy.** This is the
first time the never-succeeded path has been seen rendering anything at all; under
the old one-line rule the same conditions produced a blank bar.

**2. The healthy case.** On a normal load the banner **showed nothing throughout,
and the switch resolved to armed** — no amber bar, no red flash, at any point.

⚠ **What that second observation is, stated precisely, because the wording
matters.** It is the confirmation of an **ABSENCE**: the banner renders nothing in
`pending` *and* nothing in `armed`, so what was verified is that **no bar appears
during ordinary first-load latency** — the no-false-alarm property, and the
answer to entry 47's "does it appear during ordinary first-load latency" question.
**It was NOT the observation of a distinct calm "checking" UI, because no such UI
exists** (PART 2). The armed state itself remains visible where it already was —
the status strip's kill-switch tile and the `/kill-switch` page — not in this
banner.

**Together the two observations are what the source tests cannot reach:** that the
event-driven trigger really does separate "just loaded" from "genuinely failing"
on the deployed build, and that the amber treatment renders as designed.

## PART 7 — DEFERRED, NOT FORGOTTEN: TWO REAL IMPROVEMENTS AND WHY THEY ARE NOT HERE

Both are genuine improvements, both are wanted, and **both are deliberately held
for a planned whole-dashboard visual redesign** rather than built now. The reason
is one sentence: **building visual work now means re-doing it weeks later**, and a
safety element is a bad place to churn styling twice.

**(1) A genuine "checking" state.** A calm, neutral treatment distinguishing *"the
first poll has been issued and has not come back"* from *"confirmed armed"*. The
state already exists and is already tested — `pending` is a distinct value in
`killSwitchBannerState.ts` and has its own assertions — **it simply has no
appearance.** So this is a rendering decision, not a logic one, and the logic will
not need revisiting when it is built. That is precisely why it is cheap to defer:
**the hard half is already done and pinned by tests.**

⚠ **Its cost while deferred:** during the first ~1.4 s of every page load, the
banner is silent for a reason the operator cannot distinguish from an all-clear.
That is a much narrower version of the very gap this step closed, bounded to
first-load latency rather than unbounded — but it is the same shape, and it should
be named as such rather than described as merely cosmetic.

**(2) An elapsed-time threshold instead of the event-driven flip.** A deadline on
`loading && data === null` resolving to `unknown`, replacing PART 3's settle-event
trigger. **This is the fix for the hanging-request hole in PART 3** — the one case
where the current banner stays silent when it should not — so it is a correctness
improvement wearing a design question's clothing, and it should not be lost among
the visual items.

The design is already costed: **15 s, or three poll intervals.** Three rather than
one because entry 47's HAR recorded a legitimate single response at **4,957 ms**,
so one interval cannot separate slow from dead; and deliberately **not the 5 s
poll interval itself**, which would race the very tick meant to clear it. It needs
a mount timestamp and a re-render trigger in the banner, plus its own tests and
mutants.

**Neither is in `7809245`.** Recorded here as tracked items with their arguments
intact, so the redesign inherits the reasoning and not just the to-do.

## PART 8 — WHAT IS UNCHANGED, AND WAS TESTED TO STAY THAT WAY

**Step 47's last-good behaviour is untouched.** `usePolling.ts` is byte-identical.
Once a poll has succeeded even once, a later failure keeps the bar up rather than
dropping it.

`error` is therefore an input the verdict **deliberately ignores** whenever `data`
is present. It is in the signature, and pinned by its own test, **precisely so a
future `if (poll.error) return "unknown"` fails loudly** — that edit would retract
a confirmed TRIPPED bar on the first transient blip, which is strictly worse than
the bug this step fixed. It is mutant **M5**, killed by 19 assertions.

The boundary, as one pair of cases differing in exactly one field:

| both `loading: false`, same error | verdict |
| --- | --- |
| `data: TRIPPED` — succeeded once, now failing | `tripped` — bar stays up |
| `data: null` — never succeeded | `unknown` — the new bar |
