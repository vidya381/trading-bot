## Step 19: Observing fills on resting orders, part 1 of 3
Date: 2026-08-03

`bot-44400a`'s base DCA order was placed at 03:30:21 UTC, filled on Gemini some
hours later, and was recorded `cancelled` with `filled_quantity = 0`. No human
touched it. The investigation that followed found the cancellation was not a
stop-loss, not a take-profit, and not a bug in the halt path — it was the halt
path working as designed, on a bot reconciliation had just halted, seven seconds
earlier, for drift the bot could not have avoided.

The root cause is one sentence: **nothing observes a fill on an order that
rests.**

### The gap, stated precisely

`onFill` has four callers, all inside this object, all at order-placement sites,
and each only drains `result.fills` — the executions attached to the placement
RESPONSE. There is no WebSocket user-trade feed and no status poll. An order that
is accepted, rests on the book, and fills ten minutes later reaches the position
through nothing at all.

For DCA that is not a latency problem, it is a **liveness** one. `decide` returns
early on `position.quantity <= ZERO` before it ever reaches the stop-loss or
take-profit branches, so a bot whose base order rests sits in `hold` forever
while genuinely holding coin. It cannot take profit, cannot stop out, and cannot
place its additional buys. Reconciliation eventually halts it. Resting-limit
strategies were structurally non-functional, not merely slow.

### One premise checked and corrected before designing anything

The obvious framing — "reconciliation only notices hours later" — is **false**,
and building for it would have produced the wrong fix. `balance_snapshots` shows
unbroken 5-minute reconciliation passes across the incident: `08:20:47` clean,
`08:25:47` finding the drift. The order rested ~4h55m because the price never
reached it, not because detection was slow.

So this step is not about detection latency. Reconciliation is a competent
backstop and stays one. What it cannot do is keep a **running** bot's books
current, because §9 halts and alerts and **deliberately never auto-corrects**.
That judgement is unchanged and correct. This path is the one that keeps the
books current in the first place, so the backstop has less to find.

### What is built here, and what is deliberately not

`#pollOpenOrders` reads each id in `openOrderIds` via `getOrderStatus` at
**`routine`** priority — keeping the books current is ordinary work and must not
draw on the slice §5.4 reserves for getting OUT of a position — and folds any
unseen execution in through the ordinary live path. `checkOpenOrders(actor)` is
the explicit wrapper.

**It is not scheduled.** Arming this on an alarm is step 20, and making it safe
to interleave with `onPriceUpdate` is step 21. Every caller today is explicit, so
the interleaving that makes this hard cannot yet occur. That split is the whole
point: the fill-application semantics are the risky part and are shared by both
strategies, so they get their own step rather than riding along with scheduling.

Everything reused verbatim — `applyFill`, `applyEntry`/`planFill`,
`#mirrorOrderUpdate`, `#mirrorTrade`. **No new arithmetic exists in this path**,
which is the property that stops a poll-recorded position from disagreeing with a
pushed one. Idempotency is step 18's, unchanged: dedup on the exchange's own
`fillId`, defended by the same identity check the live path uses rather than by a
flag.

### `placeReplacement` is `true` here — but derived, not hardcoded

Step 18 passes `false` because a repair runs on a **halted** bot and must not put
a live order on the exchange. The instinct for a live poll is to invert that to
`true`: a grid buy that fills while resting SHOULD place its paired sell, because
that is the grid working, not a repair resuming trading by the back door.

Both are right, and neither is the whole rule. What is actually passed is
`fresh.status === "running"`. A poll on a halted bot — which is permitted, and
useful, since observing costs nothing — must still place nothing, or step 18's
invariant is defeated through a path whose normal answer is `true`. Hardcoding
`true` passes every test written for the running case and silently breaks the
halted one; a mutant confirms the test suite catches exactly that.

### Two exchanges, two different capabilities

Gemini's `getOrderStatus` has always sent `include_trades: true` and its parser
populates `fills` from `trades`, so Gemini supplies real `tid`s and this path can
fully repair a Gemini bot. **Binance's cannot**: `GET /api/v3/order` carries no
fills array at all, and `parse.ts` is explicit that it leaves `fills` absent
rather than defaulting it to `[]`.

So case 2 exists and is not hypothetical: more filled than recorded, with no id
behind it. It is alerted (`unattributable_fill`) and **skipped**. Synthesising an
id is refused for exactly the reason `#recordCancellation` already documents —
`applyFill` dedupes on `fillId`, so a made-up one means the real execution later
either double-counts or is silently swallowed. All four live bots are Gemini
today, so nothing is blocked; the asymmetry is encoded honestly rather than
left as a silent no-op that would look like success.

### `#foldTerminalState`, and the gate that is the whole point of it

Without folding, an order cancelled or expired ON THE EXCHANGE never leaves
`openOrderIds` and is re-read forever. So a terminal remote state closes the
local record — for a grid, by clearing the ladder slot, since the ladder owns
`openOrderIds` and filtering the array directly would be undone by the next fill.

**It is gated on the fill quantities agreeing, and that gate is the reason this
step exists at all.** An order that ended with more filled than this bot recorded
is left OPEN and reported, never closed. `ALLOWED_TRANSITIONS` gives every
terminal state an empty successor list and `applyFill` throws
`fill_after_terminal`, so closing such an order makes the understatement
**permanent and unrepairable**.

That is not a hypothetical either. It is precisely what happened to
`v1-bot-44400a-0`: the halt sweep closed it while it was under-recorded, and the
0.00031777 BTC it holds can no longer be attributed to that bot by any existing
code path. `filled` is deliberately not a foldable case for the same family of
reasons — an order is recorded filled by applying its fills, never by asserting
the end state over them.

### Audit volume, decided now because step 20 makes it matter

`bot.open_orders_checked` is written **only when something moved**. Once this
runs every 30s the no-op pass is overwhelmingly the common one, and a row per
pass would measure how long the bot has been running rather than what happened to
it — the same reasoning that made step 18's standing alerts one row per incident
instead of one per detection.

The alert side of that is **not** solved here and must be before step 20 arms the
timer: `raiseStandingAlert` is module-private to `reconcile.ts`, and reusing it
from this object is a refactor that does not belong in this step. Until then an
`unattributable_fill` condition would write one row per pass — 2,880/bot/day,
step 18's 186-identical-criticals problem in a new place. Recorded as an explicit
precondition, not a nice-to-have.

### Tests

13 new (1440 → **1453**), four mutants all caught: unconditional
`placeReplacement`, the removed terminal-fold quantity gate, an unconditional
audit write, and a dropped `unattributable_fill` alert.

The fold-gate mutant is worth recording because **it survived the first test
written for it**. That test set up the bot-44400a shape faithfully — cancelled
remotely, filled beyond what was recorded, no per-fill detail — and asserted the
order stayed open, which it did. But it reached that outcome through the
`unattributable_fill` branch's `continue`, never executing the gate at all. The
assertion was true, the invariant was untested, and only the mutant showed the
difference. The replacement drives a venue that DID report per-fill detail whose
fill overfills the order, so the fill cannot be applied, the local record stays
behind, and the gate is the only thing standing between that order and a
permanent understatement.

### Deliberately not done

- **Not scheduled.** No alarm, no timer, no caller in production. Step 20.
- **`applyMissedFills` and the halt-sweep interaction untouched**, at the
  operator's explicit direction. The sweep destroying `openOrderIds` before the
  repair path can read it is real and is its own step.
- **`bot-44400a`'s 0.00031777 BTC is not recovered by this**, and this step must
  not be read as recovering it. The coin exists on Gemini; what is gone is this
  system's ability to attribute it. See the open questions.

### Open questions

1. **The 0.00031777 BTC has no in-system home.** `manual_adjustments` is
   account+asset scoped with no `bot_instance_id`, no price and no fill id, so it
   can make account-level capital accounting truthful but cannot reconstruct a
   DCA position. Whether to dispose of the coin on Gemini directly, log an
   adjustment, or both, is the operator's call and is not a code change.
2. **Alert lifecycle before scheduling** — see above. A precondition for step 20.
3. **Poll interval is 30s by decision, not by measurement.** Four bots make the
   rate-limit cost trivial today; it is worth re-deriving when that changes.
