## PART 1 — WHAT PROMPTED THIS: ENTRY 94'S OWN PLAN WAS WRONG

Entry [94.md](94.md) PART 6, remaining-work item 1, ends with this instruction:

> Flipping `EXCHANGE_IS_WIRED.kraken` at that point is not optional:
> `venue-wiring.test.ts` fails until it happens.

"That point" is the moment `workers/exchange-kraken.ts` and the dispatch `case`
exist — that is, the end of this session. The prediction was accurate:
building those two things turned `venue-wiring.test.ts` red, exactly as designed,
with two failures. The suite went from **2 failed / 3850 passed** to **4 failed /
3871 passed**, and the two new failures were the forcing function firing:

```
FAIL venue-wiring.test.ts > kraken: the table and resolveExchangeForAccount say the same thing
  AssertionError: expected true to be false
FAIL venue-wiring.test.ts > reports kraken as unwired, and dispatch really does fall through
  AssertionError: expected { ok: false, …(1) } to be undefined
```

**Following the instruction at that moment would have recreated the exact class
of bug entry 94 found and closed.**

`EXCHANGE_IS_WIRED` gates two things: `createBot`'s `assertExchangeIsWired`
(whether a bot may be created on a venue) and `BotInstance#venue` (whether a
stored row may trade). Flipping the Kraken row to `true` opens both. But
`METHOD_WEIGHTS.kraken` is still undefined — entry [90.md](90.md) step (d)
deliberately defers Kraken's cost model to its own session, because a decaying
counter, a **second per-pair** budget and an age-dependent cancel price do not fit
`Record<keyof RestExchangeClient, number>` at all. So the flip would have
produced:

> a bot that can be created, reserves capital, writes a row, starts a Durable
> Object — and crashes at the rate-limit gate the first time it tries to trade,
> on `methodWeightsFor("kraken")` returning `undefined`.

That is entry [94.md](94.md) PART 2's finding with one word changed. PART 2's bot
halted on `TypeError: Cannot read properties of undefined (reading 'ok')` because
the dispatch `switch` had no `case`; this one would halt on
`Cannot convert undefined or null to object` because the weight table has no row.
Same shape, same cost — capital reserved against a bot that cannot trade, and an
operator holding a crash with no venue named in it.

**`venue-wiring.ts`'s own docblock already said so**, and disagreed with the
remaining-work note in the entry that created it. It listed three blockers and
was explicit that the flag flips when all three close, not when the first two do:

> Trading Kraken through another venue's weight table is the exact bug commit
> `c43f40c` removed, so an ungated Kraken bot is not an acceptable interim state
> either.

So entry 94 contained both the correct rule and an instruction that violated it.
**STATE IT PLAINLY: this is a correction to entry [94.md](94.md)'s own stated
plan, caught before it became a real bug rather than after.** Nothing shipped, no
bot was created, nothing was deployed. What made it catchable was that the
instruction was checked against the invariant it was supposed to serve instead of
being followed because a test was red — and the red test was, correctly, only
ever a prompt to think, never an answer.

**The deeper problem is not the wrong instruction. It is that a red test could be
silenced by editing a boolean.** `EXCHANGE_IS_WIRED` was a hand-maintained
opinion; the test existed because "does a `case` exist in a `switch`" is not a
question code can ask, so a person had to answer it and the test had to police
them. That design has exactly one failure mode, and this session walked into it
on schedule. PART 2 removes the person from the loop.

## PART 2 — THE FIX: WIREDNESS IS DERIVED, NOT DECLARED

**`EXCHANGE_IS_WIRED` is deleted.** There is no boolean anywhere. In its place:

```ts
isWiredExchange(v)  ==  EXCHANGE_RESOLVERS[v] !== null      // blocker 1
                     && METHOD_WEIGHTS[v] !== undefined      // blocker 2
```

Both conjuncts are required and neither is redundant: a resolver with no cost
model is an ungated bot on a live venue (Kraken today); a cost model with no
resolver is a bot that cannot authenticate.

### Making blocker 1 askable: the `switch` became a table

The obstacle was real — a `switch` cannot be inspected. Entry [94.md](94.md) had
already considered and **rejected** deriving the answer by *calling* dispatch,
for two good reasons that still hold: it makes the guard depend on the very
unsoundness being fixed (a venue with no `case` returning `undefined`), and
`isWiredExchange` has no `Env` to call it with.

So the `switch` was lifted into the table it always implicitly was:

```ts
export type ExchangeResolver = (env: Env, now: () => Timestamp) => ExchangeResolution;

export const EXCHANGE_RESOLVERS: Readonly<Record<ExchangeId, ExchangeResolver | null>> = {
  binance: resolveDefaultExchange,
  gemini: resolveGeminiExchange,
  kraken: resolveKrakenExchange,
};
```

`resolveExchangeForAccount` now dispatches through it, and `venue-wiring.ts`
reads **the same table** — not a copy, and not a call. The two are physically
incapable of disagreeing.

**The compile-time forcing function is preserved exactly.** This is still a total
`Readonly<Record<ExchangeId, …>>`, like `METHOD_WEIGHTS` and
`VENUE_PUBLISHES_INSTRUMENT_TYPE`: widening `ExchangeId` again fails to compile
here until the new venue is answered for. What changed is **what an honest answer
looks like while a venue is half-built**. Under the `switch`, the only way to
compile was to write a `case`, so a venue mid-build had to either lie or block
the build. Now it is `null` — which is the truth, is checkable, and every
downstream gate reads it automatically. `null` is not a policy statement that a
venue should not be traded; it means only that no resolver exists yet.

### Blocker 2 is a runtime presence check, on purpose

```ts
export function hasRateLimitCostModel(exchange: ExchangeId): boolean {
  return METHOD_WEIGHTS[exchange] !== undefined;
}
```

Not a type-level check, and the reason matters: **`METHOD_WEIGHTS` is declared as
a total `Record<ExchangeId, MethodWeights>` while its object literal is missing
the `kraken` key. The type currently lies.** That mismatch *is* the open `tsc`
error at `rate-limited.ts:196`, left standing deliberately as entry
[90.md](90.md) step (d)'s forcing function. A type that lies cannot be trusted to
answer this question, so the object is asked instead — which is correct both
today and after the row lands.

### `describeUnwiredExchange` is built from the same two checks

The old message was one fixed sentence asserting both gaps at once — *"no
resolver in `resolveExchangeForAccount` and no rate-limit cost model"* — and it
**went stale for its first half the moment `exchange-kraken.ts` landed**. It
would have sent an operator looking for a resolver sitting right there in the
tree. It now composes only the blockers that are genuinely open, so it cannot
drift from the condition it describes. For Kraken today it names the cost model
and says nothing about a resolver.

**Net effect: venue-wiring status is a checkable fact rather than an opinion
someone has to remember to update.** Nobody can silence a red test by editing a
boolean, because there is no boolean.

## PART 3 — THE LIVE SIMULATION: THE PROOF, NOT THE ARGUMENT

The claim that matters is that Kraken flips to wired **automatically** when the
rate-limiter session lands its row, with no manual step. That claim was not left
as design reasoning. **It was executed.**

A real `kraken: GEMINI_METHOD_WEIGHTS` row was temporarily added to
`METHOD_WEIGHTS` — one line, nothing else in the tree touched — and every
downstream consequence was observed directly:

| Observed | Before the row | With the row |
| --- | --- | --- |
| `tsc --noEmit` | **1 error** (`rate-limited.ts:196`) | **0 errors** |
| `rate-limited.test.ts` | 2 failed | **green** |
| `isWiredExchange("kraken")` | `false` | **`true`** |
| `wiredExchanges()` | `binance, gemini` | **`binance, gemini, kraken`** |
| `create-bot-venue-gate.test.ts` — *"still refuses kraken, on venue wiring rather than on the union"* | passes | **`expected true to be false`** |
| `POST /api/bots` with `exchange: "kraken"` | `exchange_not_wired` | **passes the wiring gate, on to the next check** (`missing_field`) |

That fifth and sixth row are the proof. The wiring refusal did not merely stop
being asserted in a unit test — **the real `createBot` request path stopped
refusing Kraken and carried the request through to the next validation step**,
with zero code changes anywhere outside the one added row.

The row was then **reverted, and the clean state reconfirmed**: `diff` against a
pre-simulation backup byte-identical, `grep -c kraken src/exchange/rate-limited.ts`
→ `0`, `tsc` back to its single expected error, suite back to its two expected
failures.

**This is stronger evidence than reasoning about the design on paper.** A
derivation that *should* propagate and a derivation that *was observed to
propagate end-to-end, through the type checker, the unit tests and the real HTTP
handler* are different claims, and only the second one is now on the record.
Arguing the first would have missed the two defects in PART 5.

## PART 4 — A PERMANENT FIX FOUND ALONG THE WAY: DISPATCH IS NOW TOTAL

Not requested, and not specific to Kraken. It is a **natural and correct
consequence** of lifting the `switch` into an inspectable table, and it closes a
failure mode permanently.

The old `default`-less `switch` returned `undefined` for any venue with no
`case` — a value its own signature said could not happen.
`venue-wiring.test.ts` used to state that unsoundness openly, casting the return
to `ExchangeResolution | undefined` to measure it. Entry [94.md](94.md) PART 2
recorded what it cost: a bot on an unwired venue halting at its first trade on

```
unhandled_error: TypeError: Cannot read properties of undefined (reading 'ok')
```

— capital reserved, and **no venue named anywhere in the message**. What that bug
destroyed was the diagnosis.

`resolveExchangeForAccount` is now total. A `null` entry produces a real refusal
that names the venue and the gap:

```ts
const resolve = EXCHANGE_RESOLVERS[exchange];
if (resolve === null) {
  return { ok: false, reason: `${exchange} has no credentials resolver in this build, …` };
}
return resolve(env, now);
```

**This closes that failure mode for ALL future venues, not just Kraken.** The day
a fifth exchange is added to `ExchangeId` and given `null` while its client is
built, no path exists that can produce `undefined` for it. `venue-wiring.ts`
still stops such a bot from being created at all; this is the second line, so the
failure stays legible if the first is ever bypassed. The unsound cast in the test
is gone, because there is no longer an unsoundness to state.

## PART 5 — TWO BUGS THE SIMULATION CAUGHT THAT INSPECTION DID NOT

Both were in this session's own new test code, both passed a full green run
before the simulation, and **neither was found by reading the code.**

**1. A `noUncheckedIndexedAccess` type error in the test harness.** The
save/restore helper read `resolvers[exchange]`, which is
`ExchangeResolver | null | undefined` under an index signature, and assigned it
back to a slot typed `ExchangeResolver | null`. `venue-wiring.test.ts` was
**green — 31 passing** — while carrying a `tsc` error, because `vitest` does not
type-check. It surfaced only when the simulation's `tsc` run reported **1 error**
where **0** was expected, and the error was in the test file rather than the
production file being simulated. Counting errors instead of reading them would
have hidden it: the total happened to match the number expected from a different
cause.

**2. A restore-check that could not fail.** A test named *"restores both tables,
so the rest of the suite sees the real build state"* asserted:

```ts
expect(hasCredentialsResolver("kraken")).toBe(true);
expect(hasRateLimitCostModel("kraken")).toBe(false);
```

It passes whether or not the harness restores anything, because it asserts
today's answer against today's answer. It proved nothing. It was rewritten to
capture each venue's state, mutate to the **opposite** of it, assert the mutation
took effect, and then assert the original state came back — including the subtle
half the first version could not have seen, that an **absent** `METHOD_WEIGHTS`
key must be restored as absent rather than as a key holding `undefined`
(`hasOwnProperty` is what distinguishes them).

**THE GENERAL LESSON: running an actual state transition is what surfaced both.**
A static assertion checks that today's answer is today's answer, which is
consistent with a harness that does nothing and with a test file that does not
compile. Only moving the system from one real state to another and back exercises
the machinery that is supposed to carry it. This is the same lesson entry
[94.md](94.md) drew from mutation-testing its three fixes, applied one level up:
there, each fix was removed to prove the test caught it; here, the *condition the
whole derivation keys on* was changed to prove the system followed.

The restructure had a second benefit worth recording. The tests now construct
wiring states rather than asserting against whichever venue happens to be unwired
today — so `venue-wiring.test.ts` is **green in both states**, before and after
the transition. Pinning today's answer is precisely the staleness this entry
exists to remove; a test that must be hand-edited on the day the thing it
describes changes is a boolean flag wearing a different hat.

## PART 6 — WHAT WAS DELIBERATELY LEFT RED

The simulation also showed what the rate-limiter session will walk into: **six
pre-existing tests fail the moment `METHOD_WEIGHTS.kraken` exists** — five in
`api/create-bot-venue-gate.test.ts`, one in
`durable-objects/exchange-attachment.test.ts`.

**They were left alone on purpose. They are not a bug to fix now.** They are
correct today and they document the real, current gap. One of them lives in a
`describe` block whose title states it outright:

> `why a real POST /api/bots round trip against kraken is not possible yet`

and the `exchange-attachment.test.ts` one is *"refuses a KNOWN exchange with no
client wired, by name rather than by crash"* — which needs some unwired venue to
exist in order to test anything at all. Once Kraken is wired there is none among
the real `ExchangeId`s.

**Their failure at that future point is a deliberate forcing function**, in the
same spirit as `rate-limited.ts:196` and the `default`-less `switch` before it:
it makes the rate-limiter session confirm that Kraken genuinely went live
end-to-end, through the creation path and the attachment path, rather than
silently. Rewriting them pre-emptively now would convert a tripwire into an
assumption about work that has not been done.

**One stale literal WAS fixed, and it is a different thing.**
`exchange-attachment.test.ts` asserted `/no exchange client wired/` — a match
against message wording that **no longer exists**, and whose first clause had
become false. That is a test pinned to an obsolete string, not a tripwire; it was
updated to assert the properties it was actually written for (the halt names the
venue, is a `BotInstanceError` rather than a `TypeError`, names the real open
blocker, and is not reported as an unknown venue). The distinction: the six
tripwires assert **true things about today that will stop being true**; the stale
literal asserted a **thing that had already stopped being true**.
