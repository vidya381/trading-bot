## PART 1 — WHAT THIS CLOSES

Entry [86.md](86.md) built three price-feed detectors and then, in its PART 6,
wrote down the gap it could not close that night:

> **Cross-checking the feed against the same venue's REST endpoint would NOT
> have caught this.** The sandbox's REST ticker reported the identical frozen
> `78172.34`. Both sources agreed because **both were the same fiction**. [...]
> The real fix for that is a **genuinely independent reference** — a second
> venue, or a published index price. **Not built tonight**, recorded as future
> work.

Its PART 7 was blunter about what that meant in practice: *"there is still no
independent price reference, so a production venue publishing a frozen-but-fresh
price would now be DETECTED — which it would not have been this morning — but
still could not be CROSS-CHECKED."*

**Every detector entry 86 built is a SYMPTOM detector, and each one requires the
fault to arrive in a particular shape.** That is not a criticism of any of them;
it is the reason a fourth thing was needed:

| Detector | What it watches | The fault it cannot see |
| --- | --- | --- |
| `price_feed_blind` / `price_updates_stale` | liveness — heartbeats, `lastPriceAt` | a feed publishing a **wrong** price briskly looks perfectly healthy |
| `price_feed_value_frozen` | an unchanged close **and** zero volume | a wrong price that **moves normally** has neither property |
| the crossed-book refusal | `bid >= ask`, arithmetically impossible | a wrong price with a **sane book around it** is not impossible, only wrong |

So a feed that is **simply wrong** — fresh timestamps, an uncrossed book, a price
ticking along, describing a market that is not the one the bot thinks it is
trading — **passes all three**. That is precisely the shape of the 2026-09-02
incident, and it is what cost entry 86 four rounds of investigation that blamed
the order type, then the venue, then the subscription, before anyone questioned
the number itself.

**The only thing that can catch that class of fault is a number from somewhere
else.** Entry 86 could not build one because there was no second venue. Entries
90–96 built one: Kraken is now a real, fully wired, independently operated
source, and its market data is public and unauthenticated. This entry is the
check that uses it.

## PART 2 — THE DESIGN

### It rides reconciliation's cron, and is not a trading-critical path

**Every five minutes, on the existing `*/5 * * * *` trigger**, not per price
update. The reasoning is a cost/benefit that comes out one-sided:

- **Per tick** it would be two REST reads *per price* for a question whose answer
  changes on the scale of an outage, on the one path in the system that must stay
  cheap.
- **On this cron** it is at most one round of reads per distinct pair per five
  minutes — the same budget shape section 9 already runs on.

It is also **structurally at home there**. This is already the system's periodic
re-derived-condition pass: it has a standing-alert lifecycle wired, an `observed`
flag whose meaning is settled, and a place for exactly this kind of audit
(`auditBlindness` is its neighbour, added for the same reason in step 16).

**Deliberately last in the account loop**, after everything section 9 owns. See
PART 5 on why it also cannot throw into that loop.

### Only pairs that genuinely exist on both venues

For each pair with at least one **RUNNING** bot, the reference venue's listing is
read once per pass and the pair is looked up in it. **A pair Kraken does not
carry is a routine skip carrying its reason — never an error, never an alert.**
That is not a defensive nicety; it was confirmed earlier tonight that the two
venues carry materially different markets, and a check that alerted on the
difference would be reporting the catalogue rather than the prices.

Two smaller scoping decisions, both recorded at the code:

- **`status === "running"` and nothing else.** A `halted` bot has unsubscribed
  and *"a halted bot's clock is frozen BY DESIGN"* (`bot-instance.ts`), so its
  price is *expected* to disagree with the live market — it would produce a
  permanent, meaningless alert. A `created` bot never traded; a `stopped` one is
  finished.
- **`archived` is deliberately NOT consulted.** The schema's own comment says it
  is a dashboard view filter, orthogonal to status. A running bot someone hid
  from a list is still trading real money on a real feed, and filtering on it
  would let a **UI preference silently switch off a risk control**.

### A credential-free Kraken client, and why one is possible at all

`KrakenClient` takes a `CredentialProvider`, but **it does not use one until it
signs something**. `KrakenSigner`'s constructor stores a closure
(`signing.ts:260`) and calls `getCredentials()` only inside `sign`/
`signedRequest`; `#transport` reaches the signer only on its `spec.signed === true`
branch. **A public GET — `AssetPairs`, `Assets`, `Ticker`, `OHLC`, `Time` — never
touches it.**

So `PublicOnlyCredentialProvider` **throws**, and that is not a hack around a
required constructor argument — it is the accurate statement of what this client
holds. It converts "a public-data client was asked to sign" from a request that
leaves the process carrying some other account's key into a **local, loud,
nothing-was-sent failure**. `#transport` already classifies a throw on that
branch as `reached: false` with its reason attached, so the refusal arrives as an
ordinary failed outcome rather than an unhandled exception.

Deliberately **not** `StaticCredentialProvider` with blank strings: that
constructor refuses blanks (`requireNonBlank`), and defeating it with a
placeholder like `"none"` would produce a client that signs a **real request with
a fake key** — a request that leaves this process and is rejected at the venue,
which is the exact failure `credentials.ts` exists to prevent.

### ⚠ No environment parameter on the base URL, and why that is not entry 90 DECISION 1 reopened

The base URL is `KRAKEN_BASE_URLS.production`, hard, with **no environment
argument to get wrong**. The reason is entry 86's own finding turned around:
**a simulated reference is not a reference.** A sandbox publishes fiction with a
fresh timestamp — that is the whole subject of entry 86 — so pointing this check
at a simulator, if Kraken even had one, would rebuild the exact fault it exists
to catch.

**This does not soften entry [90.md](90.md) DECISION 1**, and the distinction is
worth stating precisely rather than waving at, because the two look similar and
are not:

- **DECISION 1 is about ORDERS.** `resolveKrakenExchange` refuses to construct a
  client in the testnet environment because there is no Kraken sandbox, so a
  testnet client pointed at `api.kraken.com` **would trade real funds from the
  test environment**. Safety there rests on a derivation with no branch capable
  of producing the wrong host.
- **This client cannot place an order at all.** It holds no credentials, so every
  private endpoint is closed to it **by construction rather than by policy**.
  There is no key for Kraken to match an order to, and `getCredentials()` throws
  before a signed request is ever built.

The property DECISION 1 protects — *no code path can send a testnet order to a
real venue* — is untouched, and is **stronger here than at any other Kraken call
site**, because this client cannot sign one. `public.test.ts` asserts exactly
that against `placeOrder`: the refusal happens locally and **no POST is emitted**.

*One thing that test corrected about this file's own first draft, recorded
because it is the kind of claim that should not be allowed to stand unexamined:
the guarantee is **"no signed request"**, not **"no request"**.
`getAccountBalances` fetches the catalogue — two public GETs — before it signs, so
a misrouted private call does emit public reads before refusing. That is harmless
and it is not what the guarantee is about, but the test now says the true thing
rather than the tidier one.*

## PART 3 — THE THRESHOLD, AND THE EVIDENCE UNDER IT

**2%, measured rather than chosen.** Seventeen pairs were sampled from Gemini's
and Kraken's public tickers **in the same pass on 2026-09-04** — `/v1/pubticker/
{symbol}`.`last` against `/0/public/Ticker?pair={altname}`.`c[0]` — and the
divergence recorded for each:

```
  XRPUSD   0.008%     BONKUSD  0.097%     AVAXUSD  0.148%
  BTCUSD   0.011%     AAVEUSD  0.099%     PEPEUSD  0.193%
  SOLUSD   0.016%     SHIBUSD  0.151%     LTCUSD   0.197%
  DOGEUSD  0.034%     ETHUSD   0.200%     ATOMUSD  0.225%
  DOTUSD   0.230%     FILUSD   0.364%     LINKUSD  0.375%
  CRVUSD   0.430%     UNIUSD   0.647%
```

**Worst observed: 0.647% (UNIUSD). Every one of the seventeen came in under 1%.**
That matches what cross-exchange arbitrage keeps true of any pair liquid enough
to run a bot on — two books are held within a fraction of a percent of each other
by people whose entire job is that.

2% is therefore **roughly 3x the worst normal reading**, which leaves room for the
things that legitimately widen a spread without anything being wrong: a fast
minute where two venues' last trades are seconds apart on a moving market, a thin
book on one side, a venue-specific listing event.

**⚠ AND IT IS DELIBERATELY NOT A FINELY TUNED NUMBER.** The failure class this
exists for **does not arrive at 2.1%**. Entry 86's sandbox published `78172.34`
against a real BTC market — that is 3.27% against the live Kraken close in the
same capture, and the general case is orders of magnitude, not a percentage point
either way: a decimal place lost or gained, a different market entirely, a price
weeks stale. Any threshold between "above spread noise" and "below broken"
catches that class identically. So the constant sits where **a false positive is
implausible**, rather than where the last basis point of sensitivity is squeezed
out. Tightening it would buy no detection and cost real alerts, and entry 86
already recorded what happens to an alert surface people stop trusting.

**The seventeen captures are pasted verbatim into `price-cross-check.test.ts`.**
That is the point of them being there rather than only in a docblock: **the
constant and the tests defending it rest on the same seventeen observations**,
not on two independently guessed numbers. A test asserts the worst of them is
`UNIUSD` at `0.647064%`, that it is under a third of the threshold, and that
**none of the seventeen alerts**.

*A note on the arithmetic, since the first draft of those tests failed.* Five
expected strings were computed with floating point and were wrong in the last
digit or two — `0.647019%` where the code produces `0.647064%`. **The code was
right and the test was wrong**, confirmed by re-deriving each value with exact
integer arithmetic independently of the implementation before touching the
expectations. `divergenceBetween` measures against the **midpoint** and multiplies
by two before dividing rather than halving the sum first, precisely so the
check's own arithmetic does not discard a quantum inside a function whose job is
measuring rounding-sized quantities.

## PART 4 — ⚠ THE ROUNDING BLIND SPOT, FOUND BEFORE IT COST ANYTHING

**This is the sharpest thing in this entry, and the ordering matters: it was
looked for and built for, not discovered afterwards as a bug.**

### The mechanism

Both compared prices arrive as `Money` — fixed-point, `SCALE = 8`. Each therefore
carries up to **half a quantum** of rounding, and their **difference carries up to
a whole one**. Expressed as a fraction of the price, that error is not constant:
it is `1 quantum / price`, so it **scales inversely with how cheap the coin is**.

| Pair | Price | One quantum, as a fraction of it |
| --- | --- | --- |
| BTCUSD | 80,760 | **1.2e-13** — nothing could care less |
| SHIBUSD | 0.00000530 | **~0.19%** — *a tenth of the entire 2% threshold* |
| a coin at 1e-7 | 0.00000010 | **~10%** — five times the threshold |

**On SHIB, roughly a tenth of the alert budget is consumed by the representation
alone, before a single unit of real disagreement.** Push the price one more order
of magnitude down and rounding by itself clears 2% while both venues agree
perfectly.

### What a naive fixed threshold would have done

**It would have made real, legitimately-traded low-priced coins quietly less
protected than high-priced ones** — not by refusing to check them, which someone
would notice, but by spending their tolerance band on arithmetic noise so that a
smaller and smaller share of it remained for actual divergence. A silent,
coin-dependent weakness in a safety check, invisible from inside the check, and
presenting as normal operation.

**This project has caught that exact shape before.** Entry [92.md](92.md) PART 3
found the crossed-book detector — built and verified against Gemini, where no
symbol prices below the money scale — refusing `ANKRXBT`'s **real** book forever,
because two genuinely different prices six units apart at the tenth decimal are
identical once rounded to `Money`. Its portable conclusion was written down
precisely so it would be usable the next time:

> *A safety check built and verified against one venue's typical price ranges can
> misfire silently on another venue's real data, without either the check or the
> data being wrong.*

**This is the next time, and the lesson was applied in advance rather than
re-learned.** The exposure was identified while writing `quantumAllowance`, from
the arithmetic, before any test failed and before any pair misbehaved. Nothing
here was found by a bug report. That distinction is the whole reason this PART is
long: entry 92's cost was a live pair refused on every read forever; this one's
cost was an afternoon of thinking about a divide.

### The fix, and the option deliberately rejected

**Each pair's tolerance band is widened by its own derived rounding allowance:**
`allowed = DIVERGENCE_THRESHOLD + quantumAllowance(primary, reference)`, where
the allowance is one quantum expressed against the same midpoint the divergence
uses, **rounded up** — an allowance that under-states the representation's own
error is an allowance that lets rounding present as a finding.

**The rejected alternative was a minimum-price floor**, and it is worth recording
why, because it is the obvious move:

- It would be **a second arbitrary number**, needing its own justification, sitting
  next to a threshold that has real evidence under it.
- It would **silently exclude real, actively-traded pairs from the check
  entirely**. SHIB, PEPE and BONK are all in the live capture above at
  3.1e-06–5.3e-06; any floor high enough to make rounding negligible drops some
  or all of them, and a bot on a dropped pair would have *no* independent
  reference while every dashboard said the check was running.

The allowance is instead **exact, derived per pair from the price itself, and
degrades in the safe direction.** As a price approaches the scale limit the band
widens until the check **explicitly declines to conclude anything**: once the
allowance alone would meet or exceed the threshold, `evaluateCrossCheck` returns
a `skipped` outcome whose reason says a divergence and a rounding artefact would
be indistinguishable, and cites entry 92 PART 3 so the next reader finds the
argument rather than the symptom.

**That is the important property: it degrades toward "cannot tell", never toward
false confidence.** A pair too cheap to judge is reported as unjudged. It is not
reported as `agreed`, which would be a green light this check has not earned.

Four tests pin it: the SHIB allowance is asserted at `0.188502%`; the near-floor
case is asserted to skip with entry 92's citation in the reason; both-zero is
asserted to report rather than divide; and **a tenfold error on BONK is asserted
to still fire**, so the allowance cannot quietly neuter the check on the pairs it
exists to protect.

## PART 5 — OBSERVE, NOT GATE — AND WHY IT IS STRUCTURAL

Entry [92.md](92.md) established the rule. This applies it, and it is **enforced
by the interface rather than by discipline**.

**`runPriceCrossCheck` takes a `Database` and three read-only ports** —
`primaryPrice`, `referenceListing`, `referencePrice`. That is the entire surface.
It receives **no `BotInstance` stub, no namespace, no halt callback, and no
`snapshotBot`** — nothing analogous to the `haltBot` that `reconcileAccount` is
handed one function away in the same worker. **There is no path from a divergence
to a bot's trading state to accidentally take.** A future change that wanted one
would have to widen this signature, which is a deliberate and visible act in a
diff, not a line quietly added inside a branch.

The reasoning behind the rule, for the record:

- **A divergence is indistinguishable from this check's own bugs.** A stale
  catalogue, a name resolving to the wrong market, a thin Kraken book on a pair
  that is liquid on the primary — each produces the same signal a broken feed
  does. Gating on it would let **the observer stop the observed**.
- **A bot deprived of prices is not safe, it is blind.** It stops updating its
  stop-loss and its trailing high-water mark **while its position stays open**.
  Entry 86 measured the cost of a wrong price; the cost of *no* price is worse and
  arrives faster.
- The right response to "two venues disagree by 40%" is **a human deciding which
  one is lying**, which is what an alert is for.

**The alert message says so, in the row, in capitals.** `NOTHING HAS BEEN
WITHHELD FROM THEM: they are still receiving and acting on the {venue} price.`
That sentence is there for a specific reason and not for tone: **an operator who
assumes trading paused will make a different and worse decision than one who
knows it did not** — they will take their time, or unwind something that did not
need unwinding, on the strength of a safety action that never happened. A test
asserts the phrase is present.

The row itself follows the established convention exactly: `critical` /`system`,
matching `price_feed_value_frozen`, because the severity is about **what the
condition means** — every bot on the pair is sizing entries and evaluating
stop-losses against a number a second venue says is wrong — and not about what
this check does with it. It is **one standing row per incident**, raised through
`raiseStandingAlert` and closed through `resolveClearedStandingAlerts`, naming
every diverged pair, both prices and both venues. The known cost of one row per
account is written down at `divergenceMessage`: a pair that starts diverging
while the row is already open is not named in it. That is the same trade
`#trackFrozenValue` and `auditBlindness` both take, for entry 86's reason — a row
per detection would be 288 a day per pair, *"which is how an alert surface stops
being read."*

### The check's own failures raise nothing and resolve nothing

**Kraken timing out says nothing whatsoever about Gemini's prices.** Every way
this can fail to reach an answer — Kraken unreachable, the catalogue unreadable,
the pair unlisted, the primary read refused by the rate budget, a price too small
to compare — produces a `skipped` outcome carrying its reason, and `observed`
goes false.

**And `observed: false` neither raises nor resolves.** Closing a live divergence
row because the checker was down is section 5.6's own mistake committed on the
alert table — *"a pass that could not reach the exchange found nothing because it
SAW nothing"* — and `StandingAlertPass.observed` exists for precisely this. A test
opens a divergence, takes Kraken away, and asserts the row is **still open**.

Two more refusals worth naming:

- **The reference venue cannot check itself.** A Kraken account's prices *are* the
  reference; comparing a number to itself would report perfect agreement on every
  pass, which is a green light this system has not earned. Skipped with a reason.
- **A failed primary read is not a second `price_feed_blind`.** A feed this system
  cannot read is already reported by machinery built for it. A second row saying
  the same thing in different words is noise.

### It cannot take reconciliation down

`crossCheckAccountPrices` wraps itself, and the reasoning is the one
`#trackFrozenValue` gives for wrapping its own D1 writes, with more force: **this
is a sanity check riding on the back of a risk control.** Section 9's drift
detection halting because a Kraken catalogue parse threw would be **strictly worse
than never having built this check at all.** Every *anticipated* failure is already
an ordinary `skipped` outcome and never reaches the catch; what it catches is the
unanticipated, and it is logged rather than swallowed. A test throws from the port
factory and asserts reconciliation still runs and still reconciles.

## PART 6 — SCOPE LIMIT: PRODUCTION ONLY

**The check does not run outside production, and the reason is entry 86's own
finding.**

On testnet the primary feed **is** the simulator — that is the entire subject of
entry 86, and the reason `SANDBOX_PRICE_WARNING` exists. Cross-checking a
known-fictional feed against the real market would **diverge on every pair, every
pass, forever**, and report as a dynamic "finding" a thing the operator has
already been told statically and correctly: *the testnet venue is a simulator.*
An alert surface that is wrong 100% of the time in one environment is how the
surface stops being read.

**Environment-gated rather than condition-gated, and that follows entry 86 PART 6's
precedent verbatim.** That entry made the same call for the sandbox warning, in
the same words: environment-gated *"because 'the testnet venue is a simulator' is
a standing property of the deployment, true whether or not any particular feed is
stuck."* The same is true here, so it is answered from `ENVIRONMENT` and not from
the data.

**THE COST, STATED PLAINLY, as entry 90 states its own:** *no live, end-to-end
exercise of this check exists outside production.* Nothing in the suite has ever
watched a real Gemini price meet a real Kraken price through the real cron.

What *is* exercised outside production is **every decision it makes**, because all
of them live in `divergenceBetween`, `quantumAllowance` and `evaluateCrossCheck`,
which take numbers and return verdicts and have never heard of an environment.
The gate itself is tested from both sides — `crossCheckRunsIn` over five inputs,
and the cron asserting that a testnet pass asks **neither** venue for a price.

A test seam (`ScheduledOptions.environment`) exists only because the suite is
pinned to the testnet wrangler environment by `vitest.config.ts`, deliberately, so
tests can never load production config. **It gates only the cross-check.** It
reaches no base-URL derivation and no credential resolution —
`resolveExchangeForAccount` still reads the real `env.ENVIRONMENT` — so it cannot
be used to point a testnet Worker at a production venue. That containment is what
makes a plain override acceptable here where it would not be in `exchange-kraken.ts`.

## PART 8 — STATUS

**Not committed and not deployed as of this entry.** `HEAD` remains **`aab77ee`**.
No `wrangler deploy` ran, no live bot was touched, no live database was written.
Live access during this work was **unauthenticated public market data only**, and
every response quoted in a test is labelled with its source and date.

`ExchangeId`, the schema, the migrations, the dashboard and the notification
dispatcher are all **untouched**. The new alert type needs no registration: it
flows through the generic path, which was checked rather than assumed —
`notifications/dispatch.ts` reads `row.alert_type` only for the cooldown key, and
no dashboard file enumerates alert types.

**What this does not cover, so nobody builds on a false assumption:**

- **A pair listed on neither venue in common has no independent reference at
  all**, and this check reports that honestly rather than closing the gap. It is
  narrower than "every bot is corroborated"; it is "every bot on a pair both
  venues carry is corroborated."
- **Two venues agreeing is not proof of correctness**, only of independence. A
  fault upstream of both — an index both track, a wire both consume — would
  produce agreement. That is a much smaller surface than one venue's sandbox and
  it is not zero.
- **The cron that runs this could itself never fire**, and this check cannot
  detect that, for the same reason `auditBlindness` cannot: it is run by that
  cron. The external dead-man's switch remains the open item it already was.
- **PART 6's environment gate stands**, and with it the fact that no live
  end-to-end exercise of this path exists yet. The first production pass should
  be treated as a verification step with expected findings, not as a formality —
  the same treatment entry 92 prescribed for Kraken's first credentialled call.
