### The reuse investigation, and the assumption it corrected

**The brief asked for research before code, naming `src/research/accountTotals.ts`
(step 25) as existing logic that "already reads `bot_instances` and folds
per-account totals", and asked whether it or "the same underlying D1 queries"
could be reused. The premise was wrong, and finding that out was the most
valuable thing the research produced.**

There is no `src/research/accountTotals.ts`. The file is
**`dashboard/src/accountTotals.ts`**, and it is not the thing described:

- **It never touches D1.** It folds a `Bot[]` the dashboard already fetched over
  HTTP from `GET /api/bots`. No `Database`, no query, no `bot_instances` read. So
  there were no "same underlying D1 queries" in it to share — the actual read is
  in the API handler, shaped for a list view.
- It imports `./api/types` and `./derive`, so calling it from `src/` would be a
  **Worker-importing-dashboard layering inversion**.
- It has **no tests** — `vitest.config.ts` runs only the Worker suite, recorded
  in steps 25 and 26.

**Nothing was reusable, and the honest answer was to say so rather than to
manufacture a shared abstraction across the layer boundary.** What was actually
reused:

| reused | how |
| --- | --- |
| `Candidate` / `CandidateSet` (step 31) | **by import.** This module declares no pair, account or exchange type of its own |
| the account resolution | **not repeated at all.** The candidate already carries `accountLabel` and `exchange` that `resolveAccount` read from the registry; reading them again would be a second answer to a settled question |
| `db.botInstances` (`Repository`) | the only sanctioned D1 path (`no-raw-d1.test.ts`), so money arrives via `CAST(… AS TEXT)` / `fromStorageString` and is exact past 2^53 |
| two **rules** from `accountTotals.ts` | taken as rules, since the code was unusable — see below |

**The two borrowed rules, and why they are rules worth borrowing:**

1. **`stopped` bots are excluded from committed capital.**
   `releaseBotCapital` subtracts a closed bot's allocation from the ledger but
   **leaves `bot_instances.allocated_capital` on the row** as history. Summing
   every row reports returned capital as still committed — an overstatement that
   grows monotonically with every bot ever closed. They are **counted and
   reported beside** the figures rather than discarded, because `close` does not
   flatten a position, so a stopped bot can genuinely still hold inventory.
2. **Grouped by capital asset, always.** A share over a total blending USD and
   USDT is a percentage of nothing, and it looks completely normal.

**Archived bots count**, per step 26's settled answer: `archived` is a view flag
orthogonal to `status`, an archived bot still holds its allocation, and a figure
that moved when someone flipped a dashboard toggle would be step 25's silent
omission in a new place. Pinned by a test.

### It is a flag, and structurally not a filter

21.4's "not a silent filter" is held by shape rather than by intention. Nothing
here refuses, drops, reorders or scores a candidate.
`assessCandidateSetConcentration` returns **exactly one result per candidate, in
the candidate's own order, with no filtering of any kind**, and there is no
return value a caller could read as a rejection. The only two error codes are a
blank field and a **failed read** — never "this candidate is bad".

**That is a different shape from every other refusal in this folder**
(`pair_not_tradable`, `interval_not_verified`, `not_covered`), and the difference
is the point: those answer *can this system honestly do this at all*, a
capability fact. This answers *should you want to*, which 21.1 puts on the
human's side of the boundary.

### The two thresholds are POLICY, and the code says so in those words

21.4 names two cases and gives **no numbers**. Both live in one named constant,
`DEFAULT_CONCENTRATION_POLICY`, for exactly the reason `VERIFIED_INTERVALS`
(step 30) and `DERIVATIVE_NAME_SUFFIXES` (step 33) are single named constants: a
change to what this system believes must appear in a diff.

| | value | the judgement inside it |
| --- | --- | --- |
| `samePairBotCountFlagAt` | **2** committed bots already on the pair | 21.4's own example ("a third bot on a pair that already has two") read as a **boundary** rather than an illustration. The spec says a third bot on a pair with two is worth flagging; it does not say a second on a pair with one is not. **The looser of two available readings of one sentence** |
| `assetCapitalShareFlagAtPct` | **40%** of committed capital in the candidate's base asset | **An argument, not evidence.** 21.3 bounds the watchlist at 5–10 coins, so the design assumes a book spread over several; at 40% one asset is more than two equal-weight positions' worth. **25% or 60% is equally defensible** |

**Neither number is verified against anything.** No backtest supports them, no
market data was consulted, and no operator has yet said they are right. This is
stated in the constant's own docblock, in the folder README, and in the flag
messages a human reads — every flag statement ends *"that number is a policy
choice, not a verified limit (see DEFAULT_CONCENTRATION_POLICY)"*.

**And the live data cannot discriminate between candidate values either**, which
is recorded in the code rather than discovered later: with 11 of 13 bots on
`BTCUSD`, **any threshold below about 80% fires identically** on this account.
Choosing 40% over 25% or 60% is therefore currently unfalsifiable by observation.

**Both comparisons are "at or above"** — exactly 2 flags, exactly 40.00000000%
flags — which the `FlagAt` in each name exists to state. The money comparison is
**cross-multiplied bigint** (`part * 100n * ONE >= flagAtPct * total`), never a
share rounded to SCALE and then compared, so a value a hair under 40% that
*renders* as `40.00000000` does not flag. That distinction is real and is tested
one satoshi out in both directions.

### Facts first, verdict second (21.5 requirement 2)

Every result — **flagged or clean** — carries the counts, the exact `bigint`
money totals, **the bot ids**, the pairs held, the quote assets used and the
policy applied, so a human can re-run the same `SELECT` and get the same numbers.
The flag's `statement` renders those facts and adds nothing to them.

Bot ids specifically: *"3 existing bots on BTCUSD"* is checkable only if you can
go and look at **which three**.

### Three states, never two

| | |
| --- | --- |
| the `bot_instances` read **failed** | throws `bot_list_unreadable` |
| the account has **no bot rows at all** | clean, `rowsRead: 0` |
| it has rows and **all are stopped** | clean, `rowsRead > 0`, `committedBots: 0` |

**The first is the whole reason this discipline matters here more than anywhere
else in the folder.** A check built to surface risk that reported *no
concentration* because it could not look would hide **the exact risk it exists to
catch**, inside a proposal that then reads as reassuring. Section 5.6's rule at
the place it bites hardest. The `catch` is deliberately total — this module
cannot enumerate every way D1 fails, and the alternative to catching broadly is a
caller receiving a raw error from a check whose contract is *never silently
clean* — with the original attached as `cause`.

The last two are **both clean and not the same sentence**: step 24's
`audit_empty_balance_set` distinction and step 30's coverage variants, one module
further on. `rowsRead` is the count **before** the status split, which is the
field that keeps them apart.

And clean is a **variant** (`assessment: "no_concentration"`), not an empty flag
array: the flagged variant's `flags` is a **non-empty tuple**, so "flagged with
nothing to show" cannot be constructed — `news.ts`'s covered-with-zero-articles
trick reapplied.

### The case-sensitivity reversal: a mutation test overturned a design decision

**The initial version compared the candidate's pair to each bot's pair EXACTLY
and case-sensitively, with a comment arguing that this matched `checkTradable`'s
deliberate refusal to case-fold (step 28).** The argument was written down
confidently and it was wrong.

**A mutant that changed the comparison to case-insensitive left the whole suite
green.** Nothing checked it. Investigating why produced the actual answer:
`checkTradable`'s exactness is load-bearing because **the pair it validates is
about to be sent to a venue**, so an inexact match hands an exchange a symbol it
must re-spell, and the refusal exists precisely to tell the caller the venue's
own spelling. **Here the string is a grouping key that never leaves the
process.** The two rules answer different questions and copying one into the
other was reasoning by resemblance.

**The failure directions are not symmetric, and that decides it:**

- **Folding when it was unnecessary** over-counts a flag a human weighs and
  dismisses, having been shown the spellings.
- **Not folding when it was necessary** reports *"0 existing bots on BTCUSD"*
  while nine `btcusd` rows sit in the table — **a false clean result**, which is
  the one output the module header forbids outright.

So the comparison now **folds**, and `samePairSpellings` reports every spelling
it matched, so the fold is **never silent**: anything other than the candidate's
own spelling appears in the report and in the flag statement (*"differs from the
candidate's spelling in case only … this is worth looking into"*). Three tests
were added; the reverted-to-exact mutant now dies.

**This is the entry's most useful process result.** The mutant did not find a bug
in the code — the code did what it was written to do. It found a **wrong
argument** in a comment, in the direction that produces silence, and it found it
because the surviving mutant forced the question *"why does no test care about
this?"* to be answered rather than waved at.

### The base-asset split: a narrow heuristic with a narrow safety argument

21.4's second case is about an **asset**, and **`bot_instances` has no base-asset
column** — only `pair` and `capital_asset`. Neither is the asset in question:

- **By pair**, `BTCUSD` and `BTCUSDT` are two unrelated things when they are the
  same BTC exposure twice.
- **By capital asset**, every bot on the real account is `USD`, so the share is
  **100% for every candidate forever**. A flag that always fires is not a flag.

**`news.ts` (step 30) already refused to split a pair** — *"a guess at the split
point is wrong for exactly the newly-listed, oddly-named coins 21.3's trending
source exists to surface"* — and **that refusal stands; this does not overturn
it.** What this does is narrower and does not guess:

- The quote assets are **observed, not invented**: the distinct `capital_asset`
  values on the account's own bots, plus any the caller states (the same list
  `SelectGeneralCandidatesRequest.quoteAssets` already asks an operator for).
- A pair is split only when it **ends in one of them, longest first**, so
  `BTCUSDT` strips `USDT` rather than becoming `BTCT`. The ordering is
  load-bearing and has its own mutant.
- A pair matching **none** is **not split, not assumed, and counted**
  (`undeterminedBaseAssetBots`), which makes every base-asset figure that had one
  a **stated floor** rather than a total — `accountTotals`' `Incompleteness`
  pattern.

**WHY IT IS SAFE HERE AND WOULD NOT BE IN `news.ts`, stated as the actual
argument rather than as reassurance:** the output is a flag a human reads, and
this module **cannot block, filter, order or score anything**. A wrong split
therefore produces **a sentence a human can see is wrong** — the report names the
suffix it stripped — and never a refused pair, a skipped candidate, or an order.
`news.ts` is deciding *what to ask a vendor*, where a wrong guess becomes a false
claim about coverage that reads like a finding.

**Known limits, both real and both written down:** a venue writing `BTC-USD`
splits to nothing and reports undetermined for everything (neither venue here
does; both concatenate), and a base ticker ending in a quote asset's letters
would mis-split. **When no split is possible the signal degrades to the exact
pair and says so** — `assetSignalBasis: "pair_only"`, and the statement carries
*"this share is for that EXACT PAIR only and understates any exposure the account
holds to the same asset under a different pair"*. It never degrades to silence.

### Deliberately not done, and open questions

- **No HTTP endpoint.** Deliberately, matching the order the news fetch took: the
  endpoint exists once there is something to check with it.
  **Note for whoever builds it:** `ConcentrationFacts.policy.assetCapitalShareFlagAtPct`
  is a **`bigint`** and will need `api/serialize.ts` treatment before it can cross
  HTTP, the same as every money field. It serialised cleanly in the verification
  only because the print harness used a JSON replacer.
- **No dashboard surface.** 21.4 requires the flag be *"presented prominently"*;
  nothing renders it yet, and prominence is a UI decision that belongs with the
  proposal view that does not exist.
- **Not wired into a combined Gather-stage bundle.** `concentration.ts` consumes
  step 31's `Candidate` and `CandidateSet` types, but **nothing calls candidate
  selection and this in sequence** — the thing that would is the proposal
  pipeline. `readWatchlist` → `selectGeneralCandidates` is still the only
  composition in the folder, and it still has no caller either.
- **The stopped-bot rule and the multi-asset path remain unobserved**, as above.
- **`assetCapitalShareFlagAtPct` at 40% is unfalsifiable on current data.** Any
  value below ~80% behaves identically on this account. The threshold becomes
  testable the first time the account holds a genuinely diversified book.
- **Existing bots are still never re-validated by anything**, unchanged from
  steps 32 and 33. This module reads them; it does not check them.
- **`v-spot-1` and `v-perp-1` are both still there and still undecided.** Named
  again rather than allowed to fade into being bots nobody remembers creating.
