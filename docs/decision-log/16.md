## Step 16: Two production bugs found live — reconciliation's wrong venue, and its silent failure
Date: 2026-07-31

### How they were found

Not by a test. By asking a much smaller question: the Gemini sandbox UI was
hanging, and the operator wanted to know whether that was a Gemini-side outage
or a fault in this system. `scripts/verify-gemini.ts` Tier 0 answered the
literal question immediately — the sandbox REST API was healthy, answering
`/v1/symbols/details`, `/v2/candles` and (see 14.10) `/v1/pubticker` with fresh
data. Nothing was wrong with Gemini.

The bugs surfaced from the comparison that followed: what does the exchange
actually hold, versus what does this system believe? Tier 1 could not be run
(the credentials are Worker secrets and cannot be read back), so the question
was put to D1 instead, and `balance_snapshots` for `gemini-main` held **445
assets per run**, among them `1MBABYDOGE`, `1000CHEEMS`, `1000CAT`, `1000SATS`,
`2Z`, `456` and `0G`.

None of those exist on Gemini. Confirmed rather than assumed, with an unsigned
public call: Gemini's sandbox lists 392 symbols and not one of the seven appears
in any of them. Those balances came from Binance's testnet faucet account, and
they were recorded under a Gemini account label.

Worth stating for the next investigation: the first read of the evidence was
**wrong**. `balance_snapshots` stopped at 07:20:45Z and the conclusion drawn was
"the reconciliation cron has been silent for eleven hours". It had not been.
`audit_log` carried a `reconciliation.run` row every five minutes throughout,
right up to the current minute — 143 of them. The cron never missed a beat; what
stopped was the **writing**. Reading absence-of-output as absence-of-execution
cost a wrong diagnosis, and only the second table corrected it.

---

### Bug 1: reconciliation read every account from Binance

`src/workers/reconciliation.ts` called `resolveDefaultExchange(env, now)` — the
**Binance** resolver — once, above the account loop, and handed the resulting
client to every account whatever its registered exchange. `BotInstance` has
dispatched correctly through `resolveExchangeForAccount` since step 11. So for a
Gemini account, orders went to Gemini and balances were read from Binance.

**Why it survived this long.** Two things compounded:

1. **It appeared to work.** The Binance reads *succeeded* at first. A 445-asset
   Binance testnet faucet balance was written under `gemini-main` every five
   minutes, and nobody was reading a Gemini account's asset list closely enough
   for `1MBABYDOGE` to look wrong.

2. **The control could not detect it.** `reconcile.ts` sets
   `internal_calculated_balance` to the *previous run's* exchange balance, so
   `discrepancy` is the drift between two consecutive reads. Point both at the
   wrong venue and the drift is exactly zero, forever. Every one of the 176,354
   snapshot rows reads `discrepancy: 0`. Reconciliation was comparing the wrong
   exchange against itself and reporting a clean bill of health.

That second point is the more important lesson: a differential check cannot
detect a constant error in its own input. It has no fixed reference to
disagree with.

**The fix.** Dispatch is per account, inside the loop, through the same
`resolveExchangeForAccount` seam `BotInstance` uses. The account's exchange comes
from the `accounts` registry (migration 0006), falling back to its bots'
`exchange` column; an account with neither is **refused, not defaulted**, because
guessing a venue is the entire failure mode above. Resolution moving inside the
loop also means one account's missing secret no longer aborts the whole pass.

**The test that was missing.** The existing tests asserted that reconciliation
called *an* exchange client — which one Binance client for every account
satisfies perfectly. They could not have caught this: the injected `exchangeFor`
seam only ever received an account label, so "routed to Gemini" and "routed to
Binance" were indistinguishable from inside a test. The seam now receives the
account's registered exchange (`TestExchangeFactory`, deliberately separate from
the resolvers' own `ExchangeFactory`, which stays label-only because each
resolver already *is* one exchange), and four tests assert the routing itself —
including one that runs the **real** dispatch path with no network at all, by
withholding the Gemini secret and reading which secret the failure names.

All four fail against the reintroduced bug; verified by mutation, not assumed.

### Bug 2: the monitoring system failed silently for eleven hours

At 07:25:21Z, Binance began refusing the Worker's reads: `Service unavailable
from a restricted location according to 'b. Eligibility'` — a geo-block on the
Worker's egress. From then until the fix, every pass failed both reads.

`reconcile.ts` handled this **correctly** and that is worth preserving: an
unreadable balance is pushed onto the run's `skipped` list and no snapshot is
written, because recording an unread balance as an unchanged one would make the
next run measure its delta from a fiction (section 5.6). Right call.

The failure was in what happened to `skipped`. Tracing every consumer: it went
into the run's `audit_log` `details_json`, and into a `console.log`. That is
all. No alert row, no notification, no escalation, no circuit breaker. So the
control that exists to catch everything else could fail completely, on every
pass, in total silence — and did, 143 times consecutively, while both bots
stayed `running` and the dashboard showed nothing wrong.

**This is downstream of bug 1.** `gemini-main` is a Gemini account; it was only
ever talking to Binance because of the hardcoded dispatch, and Gemini's sandbox
was healthy the whole time (Tier 0 proved it). Binance's geo-block is incidental.
But the silence is its **own** bug: any future cause of blindness would have been
equally invisible, so it is fixed separately rather than as a side effect.

**The fix.** `auditBlindness` runs after every account's pass. An account with no
balance observation newer than `BLIND_AFTER_MS` (16 minutes — three missed passes
at the five-minute cron) gets one standing `critical` alert, and that alert is
**resolved automatically** when observation resumes.

Three deliberate choices:

- **One row per incident, not per pass.** At five-minute granularity an
  alert-per-pass is 288 rows a day for a single incident. Section 10's dispatcher
  already applies a 15-minute notification cooldown; this keeps the `alerts`
  table readable as a list of incidents rather than a log.
- **A threshold, not a hair trigger.** One failed read is a blip. Alerting on
  every transient error is how an alert channel becomes something people mute,
  which is its own way of failing silently.
- **Resolved, not deleted, on recovery.** The incident stays in the record; it
  just stops being presented as current. (Same principle as bug 3 below.)

**What this deliberately does NOT cover.** It detects "the pass ran and saw
nothing". It cannot detect "the cron never fired at all", because it is itself
run by that cron. A true dead-man's switch needs an external prober and is not
invented here — recorded as an open question below rather than half-built.

An account no client can be built for gets the same standing alert, so the newly
per-account refusal path cannot become a fresh silent skip.

Six tests, all verified to fail against a mutant with `auditBlindness` removed.

### Bug 3: `halt_reason` outlived the halt (a reversal of step 15)

A `running` bot carried `halt_reason = "order_rejected: ... (MissingAccounts)"`
— a 14.8 failure that had already been fixed and resumed past. `resume` had
never cleared the column, and step 15's entry records that as deliberate, citing
migration 0001's one-directional `halt_requires_reason` CHECK.

**That reasoning is now reversed.** The CHECK *permits* keeping the reason; it
does not require it. `halt_reason` is a current-state column that the API and
dashboard render, so keeping it meant a healthy bot advertising a resolved
failure indefinitely. `start` had always cleared both fields; `resume` was the
inconsistent one.

`resume` now clears `haltReason` and `haltedAt` in both the Durable Object's own
state and the D1 mirror. Nothing is lost: both values are written into the
resume's own `bot.resumed` audit entry (`previous_halt_reason`,
`previous_halted_at`), which is where the history of a past event belongs — an
append-only log, not a mutable status column the next halt would overwrite
anyway. The resume dialog is unaffected: it reads the bot while still `halted`.

Two tests that asserted the old behaviour were inverted, not deleted, with the
reversal explained at each site — as were the docblocks in
`dashboard/src/api/types.ts` and step 15's index entry.

### Deployment hazard found before deploying (not yet resolved)

The dispatch fix cannot simply be shipped at the existing data, and this was
caught by reading `reconcileBalances` rather than by deploying and finding out.

`internal_calculated_balance` is seeded from the most recent snapshot for
`(account, asset)`. Those snapshots are currently **Binance** figures filed under
`gemini-main`. On the first corrected pass, `USD` (in the ledger, so always
evaluated) would be compared against a $10,000 Binance baseline, and `BTC`
against a 1.0 baseline. Whatever Gemini actually reports, the difference is
unexplained by definition — and `balance_drift` is the one finding kind whose
**magnitude can carry it to `severe`**, which trips the account circuit breaker
and halts every bot on the account.

The 444 Binance-only assets are harmless (absent from the ledger and from
Gemini's response, they drop out of the loop). The overlapping ones are not.

`exceedsFraction` returns false for a non-positive reference, so a Gemini balance
of zero would stay `minor` — but a non-zero one that differs materially escalates.
Which it is cannot be predicted from here without the Tier 1 credentials.

The correct remedy is to invalidate the wrong-venue baselines for `gemini-main`
so the first corrected run hits `baseline === undefined` and takes the existing
**"adopt, do not accuse"** first-observation path (discrepancy zero,
classification `minor`) — exactly what that branch is for. That means deleting
176,354 corrupt snapshot rows, which is destructive and is the operator's call,
so **nothing has been deployed and no live data has been touched.** The code
fixes, tests and this entry are complete; the deploy and the data remediation are
pending that decision.

Note also that `Repository` exposes no `delete` by design (section 8.7
retention), so this is necessarily a manual `wrangler d1 execute` operation, in
the same class as the step 11 provisioning steps.

### Open questions

1. **No dead-man's switch for the cron itself.** `auditBlindness` cannot fire if
   the scheduled handler never runs. Something outside this Worker has to notice
   that. Until it exists, "the cron is alive" is unmonitored — which is precisely
   the assumption that made the first read of this incident wrong.
2. **Reconciliation still cannot detect a constant error in its own input.** The
   per-account dispatch fix removes today's instance, but the differential design
   means any *new* systematic error in the exchange read would again produce zero
   drift. A periodic absolute cross-check (does the venue this client is pointed
   at agree with the account's registered exchange?) would close the class rather
   than the instance.
3. **Tier 1 remains unverified.** The signed `getAccountBalances` /
   `getOpenOrders` comparison against the five resting orders was never run —
   the credentials are Worker secrets. The five pending orders carry genuine
   Gemini order IDs, so the order path is sound, but the orders themselves are
   still unreconciled against the venue. Untouched here on purpose.
