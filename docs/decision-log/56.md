**This is STAGE 1 ONLY.** The redesign has a second stage — reusing a retired

## PART 1 — WHAT WAS BUILT, AND WHY

### The trap, restated from step 55

Entry 55 Part 2 found it and deliberately did not fix it: **archiving a bot never
released its capital**, and there was **no route to `close()` at all** — even
though `close()` had existed in `bot-instance.ts` since **step 6** and
`releaseBotCapital` since **step 5**, both tested, both correct, both reachable
only from the test suite. `src/capital/ledger.ts` is the sole writer of
`status = 'stopped'` in the entire system, and it is reached only from
`close()`. With no route to `close()`, **`stopped` was unreachable in production
and an allocation, once made, could never be returned.** A finished bot held its
capital forever, and the only visible symptom was that new bots could not be
funded.

### The decision, made by the operator, not open to reinterpretation

- **No auto-selling. Ever.** The gate refuses; it never sells on anyone's behalf.
- **A bot holding a position cannot be archived.** The operator manually clicks
  the existing **Liquidate** action first.
- **Only once flat** does close-and-archive proceed, as **one click**, not two
  the operator has to chain.
- Archived bots stay **fully read-only with permanent history**. No delete
  capability exists in this system and none was added.

That first bullet is the one the rest is built around. Both strategies already
decline to sell a held position on their own — DCA's `sellOnStopLoss` is refused
outright (step 6, decision 14), grid's stop-loss liquidates only for its own
three exit reasons (step 9, decision 2) — and `liquidatePosition`'s own header
calls itself *"the deliberate, human-triggered counterpart"* to exactly that. A
gate that auto-sold to unblock itself would be the one thing every one of those
decisions was written to prevent.

### File by file

**`src/api/index.ts`** — one route added:
`route("POST", "/api/bots/:id/close", handlers.closeBot)`, placed beside
`liquidate` in the existing table. This is the whole of what was missing.

**`src/api/handlers.ts`** — the substance:

- **`heldQuantityOf(snapshot)`** — reads the held quantity from the bot's OWN
  Durable Object state, not from the `bot_instances` row. The row carries
  `allocated_capital` (a reservation) and `status`; the POSITION lives only in DO
  storage, which §8.1 makes the source of truth for it. This is the **third copy**
  of an expression that already exists twice — in `serialize.ts`'s `positionOf`
  and in `#liquidatePositionPass` — and it is kept character-identical
  deliberately.

- **`assertFlatBeforeRelease(row, snapshot, action)`** — the gate. **It checks
  `state.position.quantity` for DCA and `state.ladder.heldQuantity` for grid,
  SEPARATELY, and that distinction is the single most load-bearing detail in this
  build.** The two strategies keep their held quantity in completely different
  places. A DCA-shaped-only check would have passed every other test in the
  archiving block while **silently letting every grid bot release its capital over
  live inventory** — the exact failure the gate exists to prevent, in the strategy
  that was not looked at. This is not hypothetical: mutation 1 below confirms the
  grid case is caught only by a grid-specific test.

  Two deliberate skips, each with a reason that is not tidiness:
  - **Already `stopped`** — its capital is already returned, so refusing could not
    prevent a release, only strand the bot. And `liquidatePosition` requires
    `halted`, so a stopped bot **cannot take the action the error message names**.
  - **`snapshot === null`** (an orphan) — it cannot answer, and cannot be closed
    either. See the orphan exception below.

- **`closeBot`** — thin, the same shape as `startBot` / `haltBot` / `resumeBot` /
  `liquidateBot`. The DO owns the mechanics.

- **`archiveBot`** — now **gate → close → set the archived flag, in that exact
  order**, and the order is the decision, not an implementation detail.

  **Every partial failure must leave the bot MORE visible, never less.** If
  `close()` succeeds and the flag write then fails, the operator sees a `stopped`
  bot still on the list, and clicking Archive again finishes the job — the close
  is skipped for a bot already `stopped`, so the retry is safe. **Flag-first would
  leave a HIDDEN bot silently still holding its allocation** — capital gone from
  the pool with nothing on screen to say so, which is precisely what migration
  0007 names as *"the one outcome archiving must never produce."*

- **`setArchived`** — the audit entry gains `capital_released`. `status` keeps
  meaning *the status the gate was checked against* (read pre-close, deliberately
  not re-read), because since archiving now closes, the row is usually `stopped`
  by the time the entry is written and recording that would destroy the only
  evidence of what was actually gated. Neither fact is recoverable from the row
  afterwards.

**`dashboard/src/api/types.ts`** — `CloseResponse`; `ArchiveResponse.result`
gains **`capitalReleased: boolean`**, which is false for three different reasons
(a repeat, an already-stopped bot, an orphan) that a caller must not have to infer
from the status.

**`dashboard/src/api/client.ts`** — `closeBot()`.

**`dashboard/src/components/ArchiveAction.tsx`** — the gate made visible. When the
bot holds a position the **Archive button renders disabled** with a `title`, and
an **amber panel below names the exact held quantity and base asset**, states that
archiving would return the full allocation while that capital is still sitting in
inventory rather than cash, and **points at Liquidate by name**.

This **deliberately breaks** the convention `LiquidateAction` states and this
component had followed — *"if it's not a valid action, don't render it at all."*
The other unavailable states are self-evident from the page: a running bot
obviously cannot be retired yet. But **"halted, finished, and still refusing to
archive" looks like a broken button**, and a component that rendered nothing could
not hand the operator the sentence naming the next step. A 409 they have to read
and interpret is the thing this exists to avoid.

**`src/api/api.test.ts`** — see Part 2.

Verified diffstat: **6 files, 955 insertions, 145 deletions.**

### A deviation, flagged rather than made silently

The build brief said to gate the new close route *"the same way `close()`'s own
logic already expects"* — which is **nothing**, since `close()` is thin and imposes
no position check of its own. **The coding session made it stricter than
specified**: the close route shares the *same* `assertFlatBeforeRelease` gate as
archive, through the same function.

The reasoning, recorded because the deviation was the session's own call: an
ungated capital-release route sitting beside a gated one is a hole straight through
the operator's first decision bullet, and this releases real capital on testnet.
Loosening it later is deleting one line in `closeBot`. **The deviation was
reported at delivery rather than buried, and the operator confirmed it
afterward.**

### The orphan exception, and a gap it leaves open

An **orphaned bot** — a `bot_instances` row whose Durable Object holds no state,
the step-6 open-question-6 case that `botSummary` already surfaces as
`orphaned: true` — is **archived WITHOUT any release: the gate is skipped and
`capitalReleased` is false.**

This was forced, and it contradicts the shape of the brief. `archiveBot`'s own
step-26 header states plainly that *"an ORPHANED bot ... must still be archivable.
A snapshot-authoritative gate could not answer for one, since there is no snapshot
to ask."* And `close()` reaches `#config()`, which throws `not_created` on an
orphan — so **calling it would turn that guarantee into a 404.** The contradiction
was reported before it was worked around.

The resolution keeps the allocation **reserved**, which is the safe direction by
this codebase's own rule (`ledger.ts`: *"Every partial failure then leaves capital
over-reserved rather than under-reserved. The bad outcome is losing access to
capital you own, which a human can see in the audit log and correct"*), and
reconciliation stays consistent because the row is not `stopped`.

**Stated plainly: an orphaned bot's capital currently has NO recovery path.** No
route can release it. This is a **known, recorded gap, not fixed here.**

### Stale claims corrected — and one deliberately left alone

The old behaviour was asserted in prose in four places, and every one of them was
not merely stale but **the exact reassurance an operator would now act on
wrongly**:

- `client.ts`'s `archiveBot` doc — *"its ... capital allocation are untouched"*
- `types.ts`'s `Bot.archived` doc — *"it still holds its capital allocation"*
- `ArchiveAction.tsx`'s dialog copy — *"archiving is not closing"*
- `handlers.ts`'s `invalid_status` message — *"Archiving removes nothing"*

All four corrected. The dialog now leads with the irreversible half: the amount
returning to the account, and that a stopped bot cannot be started or resumed.

**`migrations/0007_bot_instances_archived.sql` still says the allocation is
"untouched by archiving", and was deliberately NOT edited**, per this project's
convention against editing applied migrations (0002 and 0004 both record why:
`applyD1Migrations` records by filename, so an edited file never re-runs). Editing
only a comment would be harmless to the SQL, but the convention was followed
rather than reasoned around. **Flagged here because that comment is now misleading
to a future reader**, and this entry is the amendment.

### The round-trip consequence, intentional and pinned

Archiving now sets `status = 'stopped'`. `resume()` accepts **only** `halted`.
Nothing in this system moves a bot out of `stopped`. Therefore
**unarchive → resume no longer works for any NEWLY archived bot** — it returns 409
`invalid_status` after unarchiving, where before this step it returned 200.

This is **intentional**: a retired bot is retired. It is also a one-way door the
operator must not meet by surprise, so it is pinned by a test named for exactly
that, giving any future work something explicit to flip.

**The operator's two pre-existing testnet bots, `v-spot-1` and `v-perp-1`, are
UNAFFECTED.** They are `halted` with their capital intact — not `stopped` — because
nothing could ever reach `close()` before this step. Unarchive → resume still
works on them exactly as it always did. That path is covered by its own test,
built on a bot whose `archived` flag is written directly, since the endpoint no
longer produces that combination.

Worker and dashboard — clean.

### The step-26 guarantee, split in two on purpose

Entry 26's headline test asserted *"archiving removes nothing"* via a **deep
comparison of the entire `GET /api/bots/:id` payload** across an archive, two
fields permitted to differ. That claim is now **false for a successful archive and
still exactly true for a refused one**, so it is two named tests instead of one:

- **`refused archive changes nothing at all: the whole detail payload survives
  intact`** — carries the original deep compare, now with **not one field
  permitted to differ, not even `updatedAt`**, because nothing is written at all.
  The bot it uses is the very bot entry 26 used; building real history for a DCA
  bot means giving it a real position, which is now precisely the bot the gate
  refuses.
- **`archives a FLAT halted bot: it is CLOSED, its capital returns, and nothing is
  deleted`** — the new half, asserting both what changed and what did not.

**The deep compare was not deleted and not weakened.** It was pointed at the case
where the old guarantee still holds completely. The block's header comment says
so, so a future reader finding entry 26's one-line claim reads this as an
amendment rather than assuming a test was quietly softened.

### Mutation testing — three mutants, three caught, one near-miss self-caught

**Mutant 1 — the position gate accepts a held position.** `if (held <= ZERO)` →
`if (held >= ZERO)`. **CAUGHT by 4 tests:**

- `closing > refuses a bot that still holds a position, and sells nothing`
- `archiving > refused archive changes nothing at all`
- `archiving > names the held amount and points at liquidation, and never sells anything itself`
- `archiving > refuses a GRID bot that is holding base asset, through the ladder rather than a DCA position`

**The grid catch is the one that mattered most.** The other three exercise DCA and
would all have passed against a gate that read only `state.position.quantity`.
Only the grid test reaches `state.ladder.heldQuantity`. Without it, a
DCA-shaped-only gate would have shipped looking fully tested while leaving every
grid bot free to release capital over live inventory.

**Mutant 2 — archive no longer calls `close()`** (reverted to the boolean-only
behaviour). **CAUGHT by 5 tests:**

- `archives a FLAT halted bot: it is CLOSED, its capital returns, and nothing is deleted`
- `is idempotent: archiving twice writes one audit entry, not two`
- `unarchives, and reports a bot that was not archived rather than failing`
- `leaves reconciliation's ledger invariant intact: a real reconciliation run finds no drift`
- `cannot be resumed after archiving, even once unarchived: archiving closes, and closing is final`

**Mutant 3 — capital released WITHOUT the status flip** (close, then write the row
back to `halted`). This reproduces exactly the hazard entry 55's investigation
flagged: `reconcileAllocations` compares `total_allocated` against
`SUM(allocated_capital)` over bots whose status is **not `stopped`** — a predicate
that names `status` and knows nothing about `archived`.

**CAUGHT — but the first attempt was a FALSE CATCH, found and fixed before the
result was reported, and that is the part worth recording.**

Two separate defects in this session's own test, both self-caught:

1. **The test recomputed the invariant's arithmetic inline.** The first version
   summed `allocated_capital` itself and compared it to the ledger — the auditor's
   own arithmetic copied into the test, which **would have agreed with a bug in
   the real predicate just as happily as with correct code.** Rewritten to build
   real `ReconciliationPorts` and call the actual **`reconcileAccount`**, asserting
   on the real `findings` array. More setup, for one reason: it is the auditor
   that would actually page the operator.
2. **It then failed for the wrong reason.** With the mutant applied it failed on
   `expect(status).toBe("stopped")` — a **precondition** that ran before the drift
   assertion, which therefore never executed. The test would have been reported as
   catching the mutant when it had not exercised its own subject at all. The
   assertions were reordered so reconciliation's verdict fires first.

Only after both fixes does the mutant fail honestly, with
`expected [ 'ledger_allocation_drift' ] to not include 'ledger_allocation_drift'`
— **from the real reconciliation code.** This is the first *empirical* confirmation
of entry 55's reasoning about the invariant, rather than an inference from reading
it: releasing without the status flip **does** produce permanent drift on every
run, and releasing through `close()` **does** avoid it, because the bot leaves both
sides of the comparison at once.

All three mutants were reverted and the full suite re-run green afterwards.

## PART 3 — LIVE VERIFICATION, RUN BY THE OPERATOR

Two separate real bots, watched live, not inferred. Every figure below is the
operator's and is reproduced as returned.

### The release path — `bot-f170nr`

A **flat halted DCA bot**, archived through the new flow.

- The account-level **ALLOCATED rollup dropped from `5708.06` to `3708.06` USD** —
  **exactly `-2000`**, which the operator attributes to **two bots' worth of
  released allocation**.
- A **live D1 query** confirmed the row directly:
  `status = 'stopped'`, `archived = 1`,
  `allocated_capital = 100000000000` — **1000.00 USD at scale 8**.

That last figure is the one worth pausing on. **`allocated_capital` is kept as
history and is never zeroed** — it carries a `CHECK (> 0)` and cannot be — so the
release marker is **`status`, not the column.** Entry 55's investigation asserted
this from reading the schema and `ledger.ts`; it is **now confirmed against the
real database with a real query** rather than assumed.

### The refusal path — `bot-b23y63`

A **halted DCA bot holding `0.00158519 BTC`**, used to exercise the gate directly.

- The **Archive button rendered visibly disabled.**
- The **amber panel named the exact held quantity**, stated plainly that archiving
  would release capital still sitting in inventory rather than cash, and **pointed
  at Liquidate** — matching the built behaviour exactly.

**This is the actual safety property Stage 1 exists for, confirmed live against a
real bot holding a real position — not only by test.**

## PART 4 — A NEW, SEPARATE FINDING, DISCOVERED DURING LIVE VERIFICATION

While testing the refusal path on `bot-b23y63`, the operator found that **its
liquidation had previously failed**: the last sell order is **`CANCELLED`**, and
**the position could not be liquidated.**

Stated plainly, and no further:

- This is a **PRE-EXISTING bug in the liquidate flow itself.** It was **not
  introduced by Stage 1's build** — nothing in this step touches
  `liquidatePosition`, the exit-order path, or any order state.
- **`bot-b23y63` is currently STUCK**: halted, holding a real position, unable to
  liquidate, and therefore **correctly and permanently blocked from archiving by
  the new gate.** That is the gate **working correctly against a bot in a
  genuinely bad state** — it is refusing to release capital that is not cash, which
  is exactly its job. The block is a symptom of the underlying failure, not a
  defect in the gate.
- **This is NOT investigated and NOT fixed in this entry.** It is a discovered,
  **open item to be investigated separately.** No cause is proposed here, and none
  should be read into the above.
