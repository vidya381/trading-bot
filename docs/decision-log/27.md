## Step 27: The halt alert that outlived the halt
Date: 2026-08-07

### What was built

A bot halts. Someone reads the alert, fixes the underlying problem, and resumes
the bot. The `critical` row describing the halt stays `unresolved` **forever** —
not because anything failed, but because nothing in the system was ever
responsible for closing it. `#halt` inserts it and no code path anywhere sets
`resolved` on a `halt_*` row.

- **`haltAlertType` / `isHaltAlertType`** in `src/shared/alert-types.ts`, the
  format now spelled once instead of inline at its single construction site.
- **`src/alerts/halt.ts`** — `resolveHaltAlerts(db, { source, botInstanceId })`,
  a ~15-line query, deliberately not a call into `standing.ts`.
- **The call in `#resumePass`**, after the status writes, with the closed ids
  recorded in the existing `bot.resumed` audit entry as
  `resolved_halt_alert_ids`.
- **6 tests** (4 in `bot-instance.test.ts`, 2 in `alert-types.test.ts`),
  4 mutants, all 4 caught. **1600 pass**, 1594 before.

### This is step 16's bug 3, one layer out

Step 16 found a `running` bot advertising `halt_reason = "order_rejected: ...
MissingAccounts"` — a 14.8 failure that had already been fixed and resumed past —
and made `resume` clear the column, reversing step 15. That entry named the shape
exactly: **a current-state surface that keeps describing a condition which has
stopped applying.**

It fixed the column. The `alerts` row recording the *same* halt was left standing,
and that row is arguably the more consequential of the two: `halt_reason` is one
field on one bot's detail view, while an unresolved `critical` is counted on the
dashboard's status strip and is the number an operator uses to decide whether
anything needs attention at all. Step 18 did real work to make "how many
unresolved criticals are there" mean something again after the
186-identical-criticals incident; every halt-and-resume cycle since has been
adding one to that count permanently.

The bug was correctly identified at the time and half-fixed. This is the other
half.

### Why this is NOT `resolveClearedStandingAlerts`

The reuse question was the one thing worth checking before writing anything, and
the answer went the other way from what the folder layout suggests.

`resolveClearedStandingAlerts` **would produce exactly the right rows** — pass
`owns: isHaltAlertType`, `inScope: id === this bot`, an empty `stillOpen`,
`observed: true`, and every open halt row for the bot closes. Mechanically it
works. It is still wrong, for one reason:

**`observed` would have to lie.** That flag exists because a pass which could not
reach the exchange found nothing *because it saw nothing*, and closing live
incidents on the strength of an outage is section 5.6's exact prohibition — the
module's own header calls it the nastiest failure available in there. A resume
observes nothing and re-derives nothing; it is a state **transition**, not a
detection pass. Passing `observed: true` from it means something different by the
word than every other caller does, and a guard that one caller is allowed to mean
something else by is a guard for nobody.

The shapes differ for the same underlying reason, which is worth stating plainly
because it is the thing that decides the question:

| | standing alert | halt alert |
| --- | --- | --- |
| what the row records | a CONDITION re-derived on a schedule | an EVENT that happened once |
| how many rows | one per open incident, deduped at raise | one per halt, unconditional insert |
| what closes it | a pass that observed and did not re-find it | the bot leaving `halted` |
| who is competent to close it | whoever re-derives it | whoever performs the transition |

So `halt.ts` sits next to `standing.ts` — same folder, because the alert
lifecycle staying in one place is the whole point of `/src/alerts` — and shares
its **ownership** rule (`source` scopes the resolve, a writer may only close what
it was in a position to observe) without pretending a halt is a standing
condition. The query is also scoped to one bot in SQL rather than filtering an
account's rows in memory, which follows from a resume knowing its bot up front.

### Which rows a resume closes, and which it must not

**Every open `halt_*` row for that bot**, settled with the operator before
implementing. The bot is `running` again, so by definition no halt is current and
every open halt row for it describes a past state.

The alternative considered was matching only the episode this resume ends, which
needs `halt_{reason}` re-parsed out of `halt_reason`'s `"{reason}: {detail}"`
text — a second place hand-building a format, which is the precise bug
`shared/alert-types.ts` exists to end — and would strand every row written before
today permanently. **The safety comes from the `alert_type` + `bot_instance_id`
filter, not from identifying the episode.**

What a resume must NOT close, since "the bot came back" is not "the problem went
away":

- **`cancel_failed`** is the sharp one. It is raised *by* the halt path, so it
  looks like part of the same incident. It means an order may still be live on
  the exchange — resuming does not cancel it — and reconciliation already owns
  the row through `INGESTED_ALERT_TYPES`. Closing it here would both hide a live
  problem and give one row two owners.
- **`poll_blind`, `poll_blind_escalated`, `price_updates_stale`,
  `unattributable_fill`, `grid_replacement_queued`** — standing alerts owned by
  the poll's own resolve half.
- **`order_state_drift`** — reconciliation's, ingested.
- **`price_feed_fanout_failed`** — the `PriceFeed` object's, under its own
  `source`, excluded twice over.

### Decisions

**1. The call goes after the status writes, not at the top of `#resumePass`.**
Three things can refuse a resume before it commits — a latched global kill
switch, a latched account breaker, a price feed that will not re-subscribe — and
a bot that stayed halted must keep its halt alert open. This is behaviour, not
tidiness, and it has its own test with its own mutant.

**2. The halt alert stays an unconditional insert.** It was never the problem. A
halt is a discrete event and one row per halt is exactly what history wants;
`#halt` already refuses to re-halt an already-halted bot, so they cannot pile up.
What was missing was only the closing half. The comment at the insert site now
names its counterpart, the way `standing.ts`'s two halves name each other.

**3. `haltAlertType` moved to `shared/alert-types.ts` even though the format has
one writer.** One construction site is not a duplication problem, which is why it
stayed inline until now. Adding a resolver makes two places that must agree about
what a halt alert looks like, and that is exactly the moment
`reconciliationAlertType`'s treatment starts paying: a rename now moves both
sides or fails, instead of leaving a resolver quietly matching nothing. Its
failure mode is the silent one this project refuses everywhere — no error, no
failed request, just alerts that stop being closed.

**4. Prefix matching, checked rather than assumed.** `isHaltAlertType` is
`startsWith("halt_")`, like `isReconciliationAlertType` before it. Every alert
type in the system was read to confirm nothing else begins that way —
reconciliation's `reconciliation_halt_failed` contains `halt_` but does not start
with it, and the test asserts that specific non-match. Recorded as a constraint:
a future alert type that is *about* halting without *being* a halt must not be
named `halt_*`.

**5. The closed ids go into the audit entry.** `resolveHaltAlerts` returns them
for the same reason `resolveClearedStandingAlerts` does, and `bot.resumed`
already carries `previous_halt_reason` — so the append-only log now records the
alert-table effect of a resume, not just the status change.

### Tests and mutation results

Six tests. Four mutants, all four caught:

| mutant | caught by |
| --- | --- |
| resolve nothing (the bug itself) | 3 tests |
| drop the `isHaltAlertType` filter | "does NOT resolve this bot's other alerts" |
| drop `bot_instance_id` from the `WHERE` | "resolves per bot" |
| move the call above `assertGlobalArmed` | 2 tests, incl. the refused-resume guard |

The per-bot test needed a **second Durable Object driven against the same
database**, so `run()` took an optional object name — the property is invisible
to any single-object test, and a resolve scoped only by `source` and alert type
would close both bots' rows. On an account halted by the circuit breaker that is
every bot's critical disappearing because one of them was reviewed.

The exclusion test inserts all five untouched types at once rather than checking
one, because the risk here is a filter that is *slightly* too broad, and one
example cannot show the difference between "narrow" and "narrow enough".

`alert-types.test.ts` ties the predicate to the **real** `HaltReason` union
through a `Record<HaltReason, true>`: a reason added to `DcaHaltReason` or
`GridHaltReason` and not listed there fails the typecheck, so the coverage
extends itself without anyone remembering this file exists. Same property
`EVERY_KIND` gives the reconciliation tests. Without it, a new halt reason would
produce alerts that are never closed and nothing would say so.

Full suite: **1600 pass**, 1594 before. The one pre-existing teardown error
("Worker exited unexpectedly", 61/62 files) was verified identical on a clean
tree before and after.

### Deliberately not done, and open questions

- **`close()` has the identical gap, and it is not fixed here.** A bot halted and
  then closed leaves its `halt_*` row open forever, exactly as resume did — the
  bot is `stopped`, so the halt is no less historical. It was left alone
  deliberately: the operator scoped this session to the resume path, and closing
  is not obviously the same decision (a stopped bot's last halt is arguably the
  record of *why* it was stopped, which is a question worth answering separately
  rather than by extension). `resolveHaltAlerts` takes a bot and a source and
  would work unchanged from `#closePass` if the answer turns out to be yes.
- **Nothing sweeps the backlog on its own.** Rows written before today close on
  the next resume of that bot — every open `halt_*` row for it, not just the
  latest, which is why decision (a) was taken. A bot that never resumes again
  keeps its row, and no migration or one-off script was written to clear them.
- **`halt_*` still has no reader anywhere.** The dashboard does not key off these
  types the way it keys off `ORDER_STATE_DRIFT_ALERT_TYPES`, so nothing surfaces
  "this bot is halted" from the alert table specifically. Unchanged by this step
  and not obviously wanted — `bot_instances.status` is the authority for that.
- **Not deployed, and not run against a live bot.**
