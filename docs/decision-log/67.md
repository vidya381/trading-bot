## PART 1 — THE BUG, AND TWO CORRECTIONS TO ITS RECORDED SCOPE

### The mechanism, restated exactly

`usePolling`'s `tick` opened by aborting the previous still-pending request:

```
tick() {
  controller?.abort();          // usePolling.ts:61 as it stood — kills the PREVIOUS request
  controller = new AbortController();
  ...
}
setInterval(() => void tick(), intervalMs);   // :82 — every 5000 ms
```

**If the API answers slower than the 5-second interval, every tick kills the
previous request before it can resolve.** The abort rethrows unwrapped at
`client.ts:83`, is swallowed at `usePolling.ts:69`, and **no state update ever
runs**. Not a hang, not a dropped connection — **only latency above 5,000 ms
against a server answering every single request**, whose answers the client throws
away before they arrive.

Entry 54 PART 4 confirmed this live, by the operator personally, patching
`window.fetch` in Firefox against the deployed testnet dashboard: at **6,000 ms**
and again at **20,000 ms** of injected delay, **zero successful responses in ~60
seconds** across `/api/bots`, `/api/alerts` and `/api/kill-switch`.

This step reproduced the same mechanism **mechanically**, and the numbers agree:
at 6,000 ms of latency against the 5,000 ms interval, **13 requests dispatched
over 60 seconds, and not one answer survived** (test A7, in its original form —
see PART 3).

Two failure rows, and entry 54 was right about which is worse:

| page state | what the poll held | what the operator saw |
| --- | --- | --- |
| **COLD** — no poll had ever succeeded | `data: null`, `loading: **true** forever` | `"Loading…"` forever |
| **WARM** — a poll succeeded earlier | `data: <stale>`, `error: **null**`, `lastUpdated` **frozen** | **stale numbers, with nothing marking them stale** |

### ⚠ CORRECTION 2 — beyond entry 54's scope entirely: MANUAL REFETCH STARVED TOO

Entry 54 analysed the interval. **`tick` was reachable two ways, not one:** the
interval (`:82`) **and** `refetch` (`:92` → `tickRef.current()`). They shared the
same `controller`, so:

- **a manual refetch aborted the in-flight interval poll, and the next interval
  tick aborted the refetch** — the manual path was subject to the identical abort
  chain;
- `refetch` is therefore **not** an escape hatch from the starvation; under the
  entry-54 condition it starved on exactly the same mechanism.

**Why this is the part that matters most, stated plainly.** `refetch` is what runs
**immediately after a mutation** — `usePolling.ts:29-31` names liquidation, and
`LiquidateAction` awaits it to know the view reflects what just happened. **The
moment an operator most needs a confirmed fresh read — the instant after moving
money — was served by the code that could silently never complete.** A liquidation
would fire, the refetch would be aborted by the next tick, and the screen would
keep showing the pre-liquidation position with no error and a frozen timestamp.

This was found by reading the code in the design step; entry 54 never examined
`refetch`. It is **in scope and fixed here**, not deferred — see PART 5's C4.

## PART 2 — THE FIX, AND WHY THIS SHAPE

### The extraction: `pollEngine.ts`, and `usePolling.ts` as wiring

Every branch — when to fetch, what to do with an abort, how a failure combines
with the last good data — moved into `pollEngine.ts`, which **imports no React**.
The reason is the constraint this repository has recorded four times over: **a test
importing a `.tsx` collects ZERO TESTS RATHER THAN FAILING** inside the Workers
pool the suite runs in (`docs/open-items/component-test-harness.md`; decision logs
44, 45, 46, 48). React's CJS build does not resolve there, and **the failure is
silent** — such a test file reports "0 tests" and a green suite.

Time is an **injected port**, not an ambient global: `now: () => Timestamp`,
following the convention already in `src/research/candidates.ts:343`,
`watchlist.ts:112`, `proposal-log.ts:171` and `reconciliation/reconcile.ts:147`,
and tested the same way those are (a mutable clock variable —
`proposal-log.test.ts:57`, `reconcile.test.ts:89`). `Timestamp` is `number` and is
deliberately **not** imported from `src/shared/exchange-client.ts`, which would
drag an exchange module into the dashboard bundle for one type alias.

**⚠ A CLAIM IN `pollEngine.ts`'s OWN HEADER IS WRONG, AND IS RECORDED HERE RATHER
THAN QUIETLY FIXED.** That header calls this *"the fifth application of that
pattern"*. **It is not the fifth.** Counting non-test `.ts` files under
`dashboard/src` that import no React, there are **24** including the two added
here — so **22 predate this step**. The defensible narrower claim is the one
`availableCapital.ts`'s header actually makes: it names the lineage
`accountTotals.ts`, `statusCounts.ts` and `killSwitchBannerState.ts`, and
`pollEngine.ts` is the fifth **in that named lineage**. The header overstates its
own precision. **The file was not edited to correct it — this step's brief
restricted writes to this log — so this paragraph is the correction**, in the
same spirit as entry 54 PART 6.

**The public surface is unchanged.** `POLL_INTERVAL_MS`, `PollState<T>` and
`usePolling<T>` are the same three exports with the same shapes, before and after.
**All six callers required ZERO EDITS**, confirmed by `git status` showing exactly
one modified pre-existing file (`usePolling.ts`) and by the six call sites reading
identically to `HEAD`.

### The fix itself: three rules replacing the unconditional abort

1. **SKIP-TICK SINGLE-FLIGHT.** An interval tick that finds a request already in
   flight **does nothing** — no abort, no second request. The answer in flight is
   allowed to arrive. **This is what fixes the starvation.**
2. **A REAL TIMEOUT OF 20,000 ms**, and a timeout is an **error**, not a silent
   abort. This restores the only useful thing the old abort did — bounding a
   request that will never answer — without discarding answers that were going to
   arrive. Without it, rule 1 would trade starvation for a permanent silent stall
   on a genuinely hung socket.
3. **`refetch` SUPERSEDES; THE INTERVAL DOES NOT.** A manual refetch is a
   deliberate *"throw away the old answer, I changed the world"* signal, so it may
   abort the in-flight poll and start its own. Its abort stays swallowed, because
   superseding is intentional.

The invariant the three preserve: **a new request only ever starts by REPLACING the
old one, never ALONGSIDE it.** Requests never overlap, so the "let both run"
variant's two hazards — unbounded pileup against a server already struggling, and
older responses overwriting newer data — are closed structurally rather than
mitigated.

### ⚠ WHY THE TIMEOUT HAD TO BE DISTINGUISHABLE, OR THE FIX WOULD HAVE DONE NOTHING

`client.ts:83` rethrows an `AbortError` **unwrapped** while wrapping every other
rejection in an `ApiError`. The consequence: **every abort looks identical to the
polling code.** A timeout implemented as a plain `controller.abort()` would be
caught by the same swallow that ignores unmount and supersession, and **the entire
fix would have done nothing while appearing to work.**

So a timeout is **not** recognised by inspecting the `DOMException` — the browser
gives ours and the lifecycle's the same `name`. It is recognised because **the
engine records which sequence it timed out** (`timedOutSeq`, `pollEngine.ts:308`),
and that record is what turns the abort into a `PollTimeoutError`. This is not a
theoretical concern: mutant **M2** in PART 5 reverts exactly this and is caught.

### `pollFreshness.ts` — built, tested, and WIRED INTO NOTHING

Entry 54 found two defects wearing one bug's clothes: **the poll could not
complete** (fixed above) and **the UI did not admit it**. Single-flight makes the
poll *able* to complete; it cannot make a dead server answer. When requests time
out, the last-good rule keeps previous numbers on screen — correctly — and
`pollFreshness` is what would stop them reading as current.

Its shape is borrowed from `src/research/staleness.ts` and `ProposalFreshness`,
**not its code** (that module lives in `src/research/`, is keyed to the four
proposal inputs, and its thresholds span 15 minutes to 7 days):

- **three states, and the third is not `fresh`** — `fresh` / `stale` / `never`;
- the threshold is a **named policy in one place with its lack of evidence stated
  in place**, not a constant inside a component;
- **it flags; it does not gate**;
- **words as well as colour** (`ProposalFreshness.tsx:95-96`).

The third state is named `never` rather than `unknown` for one reason: **`unknown`
already means something else one import away.** `killSwitchBannerState`'s
`unknown` is entry 54's COLD row only — its own header states *"it is never
reached while any last-good status is held"* — and `killSwitchBannerState.ts:41-51`
exists specifically to make an edit adding staleness to that verdict fail loudly,
because it would **drop a confirmed TRIPPED banner on the first transient blip**.
**That file was not touched.** Test D7 enforces the distance mechanically.

`formatAge` is **reused from `proposal.ts`, not duplicated** — it already handles
the clock-skew case and is already what `ProposalFreshness` renders with.

> **⚠ `pollFreshness` IS WIRED INTO NO UI. NOTHING ON ANY SCREEN CHANGED.** The
> four duplicated `"Live · updated <time>"` indicators (`Dashboard.tsx:35`,
> `Alerts.tsx:72`, `BotDetail.tsx:67`, `KillSwitchPage.tsx:160`) are **exactly as
> they were**. This is a deliberate scope boundary — a data-layer fix, kept out of

### No fake timers, deliberately

`grep -rn "useFakeTimers\|advanceTimersByTime"` over this repository returned
**nothing** before this step, and returns nothing after it. Vitest's fake timers
patch global `setTimeout`/`setInterval` via `@sinonjs/fake-timers`, and whether
that behaves correctly inside workerd is **unproven here**. **A polling test is the
worst possible place to be the first to find out** — a fake-timer subtlety would
manifest as a passing test that proves nothing. The injected scheduler exists so
that question never had to be asked; test **E1** now fails the build if anyone
reaches for them.

1. **`pollEngine.ts` was extracted with NO BEHAVIOUR CHANGE** — the unconditional


## PART 4 — ⚠ TWO PLACES THE DESIGN DOCUMENT WAS WRONG, PLUS ONE IT UNDERSOLD

**The design was not correct throughout, and this section is not a footnote.** All
three were found *during the build*, by tests and by a mutation run — none by
re-reading the design.

### 4.1 — The cadence claim was WRONG

The design stated that single-flight yields a cadence of roughly
**`max(interval, latency)`**. **It does not.**

A skipped tick **does not fire the moment the in-flight request lands** — it waits
for the **next scheduled interval boundary**. So the real behaviour is

> **`ceil(latency / interval) × interval`**

**Concretely: a 6-second response on a 5-second interval polls every 10 seconds,
not every 6.** That is why A7's post-fix count is **7 requests in 60 seconds** and
not 10 — a number that would have been quietly "wrong" against the design's own
prediction had the test not pinned it.

**It was documented in `pollEngine.ts`'s header rather than shipped silently**,
together with what the alternative would cost: firing a tick on settle when one was
skipped would recover the difference, at the price of carrying "did we owe a tick?"
state. **The operator has not decided whether that refinement is wanted** — see
PART 6.

### 4.2 — A REAL CORRECTNESS BUG THE DESIGN MISSED ENTIRELY

**The in-flight lock must be released ONLY by the request that acquired it.** The
`finally` that clears it is guarded by a sequence check:

```
} finally {
  if (mySeq === seq) {
    inFlight = false;
    ...
  }
}
```

**Without that guard, a superseded request settling late releases the lock while
its true replacement is still in flight** — and the very next interval tick, seeing
`inFlight === false`, starts a **second concurrent request**. That silently
reintroduces **the exact overlap the entire fix exists to prevent**, and with it
both hazards single-flight was chosen to avoid.

**The design document did not anticipate this. It would have shipped if the design
had been trusted as final** — the design's own reasoning ("at most one in flight,
by construction") is precisely the kind of claim that is true of the intent and
false of the code.

### 4.3 — The ordering guard was undersold as "cheap insurance"

The design called the sequence guard at the write boundary **belt-and-braces**, on
the theory that overlap was structurally impossible and the guard merely made the
invariant testable.

**Mutation testing proved that framing understated it.** Reverting the guard
(mutant **M3**) caused **three real tests to fail** — C1, C2 and C3. **Refetch
supersession opens a genuine window**: `controller.abort()` is not synchronous
cancellation, and a request whose response has already been received does not
un-receive it, so a superseded request really can come back with a full,
successful, **stale** answer. **The guard closes a real hole, not a hypothetical
one.**

### The refetch proof, added because an argument is not evidence

**C4 — *"RULE 3 — a MANUAL REFETCH supersedes, survives the interval, and resolves
on its OWN settle"***. A refetch with a **12-second** response, on the 5-second
interval: **two interval ticks pass while its request is in flight and neither
kills it**, it completes, `maxInFlight` is **1**, and the promise resolves on **its
own** request's settle — not the superseded one's, which would resolve against data
fetched *before* the mutation.

This proves the **same mechanism** fixes both paths: rule 1 makes an interval tick
yield to any in-flight request **regardless of which path started it**.

**This assertion was added mid-build, after the fact.** The first version of C4
used a disabled interval and proved only supersession; the manual-refetch claim was
being carried by the design's reasoning alone. **Reasoning is not evidence, so it
was made a test** — and the strengthened C4 then also began killing M1, taking that
mutant's kill count from 8 to 9.
